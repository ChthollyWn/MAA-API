# 数据模型与持久化

## 1. 选型与文件布局

技术栈为 **SQLite + SQLModel + Alembic + aiosqlite**。SQLite 是本项目的正确选择：单机单用户、写入量以日志为主、无横向扩展需求，一个文件即备份单位。SQLModel 让表定义与 API 出入参共享 Pydantic 语义，Alembic 负责 schema 演进，aiosqlite 让所有读写走异步驱动而不阻塞事件循环。

数据库文件位于 `resource/maa_api.db`。选这个位置的原因有三：`resource/` 已在 `.gitignore` 中被整体忽略，数据库及其 WAL 副产品不会误入版本库；`resource/` 已是运行期数据的既有落点（`image/`、`lib/`、`log/`、`temp/`），备份时打包一个目录即可；相对路径不依赖部署位置。

```
resource/
├── maa_api.db              主库
├── maa_api.db-wal          WAL 日志（运行期存在）
├── maa_api.db-shm          WAL 共享内存（运行期存在）
├── backup/
│   └── maa_api.db.20260916-113000.bak    迁移前自动备份
├── image/
│   └── screenshot/20260916/{uuid}.jpg    截图归档，screenshot 表存相对路径
└── temp/
    └── screencap/{uuid}.jpg              IPC 中转图，1 小时后清理
```

`-wal` 与 `-shm` 是 SQLite 在 WAL 模式下自动管理的文件，不要手工删除；备份数据库时必须三个文件一起拷，或先执行 `VACUUM INTO`。

## 2. 引擎与连接配置

应用侧用异步引擎，Alembic 侧用同步引擎，两者指向同一个文件。

```python
# maa_api/db/session.py
from pathlib import Path

from sqlalchemy import event
from sqlalchemy.ext.asyncio import AsyncSession, async_sessionmaker, create_async_engine

DB_PATH = Path("resource") / "maa_api.db"
ASYNC_URL = f"sqlite+aiosqlite:///{DB_PATH}"
SYNC_URL = f"sqlite:///{DB_PATH}"          # Alembic 与维护脚本使用

engine = create_async_engine(
    ASYNC_URL,
    echo=False,
    connect_args={
        "timeout": 15,              # 获取写锁的等待上限，秒
        "check_same_thread": False,
    },
)

session_factory = async_sessionmaker(engine, expire_on_commit=False, class_=AsyncSession)


@event.listens_for(engine.sync_engine, "connect")
def _apply_pragmas(dbapi_conn, _record):
    cur = dbapi_conn.cursor()
    cur.execute("PRAGMA journal_mode=WAL")
    cur.execute("PRAGMA synchronous=NORMAL")
    cur.execute("PRAGMA foreign_keys=ON")
    cur.execute("PRAGMA busy_timeout=15000")
    cur.execute("PRAGMA temp_store=MEMORY")
    cur.execute("PRAGMA cache_size=-16000")     # 16 MB 页缓存，负数表示 KiB
    cur.close()
```

PRAGMA 必须挂在 `connect` 事件上，因为它们是**连接级**而非库级设置。`foreign_keys` 尤其容易漏：SQLite 默认关闭外键约束，不显式打开则所有 `ON DELETE CASCADE` 都是装饰。

各项配置的作用：

**WAL 模式**让读写不互相阻塞。默认的 rollback journal 模式下写事务会阻塞所有读，而本项目的写入主体是高频日志落盘，如果每次落盘都冻结前端的历史查询，体验会很差。WAL 是库级持久设置，设过一次即写入文件头，但保留上面的语句以便新库首次创建时生效。

**`synchronous=NORMAL`** 在 WAL 下只在 checkpoint 时 fsync，写入吞吐相比 `FULL` 有数量级提升。代价是操作系统崩溃可能丢失最后几个事务——对日志与流水线历史而言可以接受，本项目不存储不可重建的金融级数据。

**`busy_timeout=15000` 与 `connect_args.timeout=15`** 两处都要设：后者是 Python DBAPI 层的超时，前者是 SQLite 引擎内部的忙等重试。SQLite 只允许一个写者，遇到 `database is locked` 时正确的处置是延长忙等并缩短写事务，而不是扩大连接池——加大连接池只会让更多连接同时抢同一把写锁。

**`auto_vacuum=INCREMENTAL`** 必须在建表之前设置，之后再改需要整库 `VACUUM`。因此它写在初始迁移的第一条语句里，而不是 `connect` 事件里：

```python
# 初始迁移 upgrade() 的首行
op.execute("PRAGMA auto_vacuum=INCREMENTAL")
```

会话管理遵循两条纪律。HTTP 请求通过依赖注入拿到 `AsyncSession`，请求结束即关闭；后台任务（`PipelineRunner`、`LogHub` 刷盘、清理任务）**各自开新会话**，绝不跨任务共享——`AsyncSession` 不是线程安全也不是任务安全的，共享会导致游标交错。`expire_on_commit=False` 是必须的：提交后仍要读取 ORM 对象的字段用于 WebSocket 广播，否则每次访问都会触发一次隐式 refresh 查询。

## 3. 通用约定

### 3.1 主键

分两类。**对外暴露的资源**用 36 字符 UUID 字符串主键：`pipeline`、`task`、`screenshot`、`schedule`、`confirmation`、`update_record`、`notify_channel`、`agent_session`、`resource_asset`。理由是这些 id 会出现在 URL、WebSocket 事件、agent 的工具参数里，自增整数会泄露业务规模且容易被遍历，UUID 还允许客户端在落库前先生成 id。

**高频追加表**用 `INTEGER PRIMARY KEY AUTOINCREMENT` 自增：`log_entry`、`agent_message`、`agent_audit`。SQLite 的 `INTEGER PRIMARY KEY` 是 rowid 的别名，插入成本最低，且自增 id 单调——这个性质被 WebSocket 的断线续传直接利用（客户端带上最后收到的 `log_entry.id`，服务端补发之后的记录）。

`AUTOINCREMENT` 关键字在这里不能省。不带它时 SQLite 用「当前最大 rowid + 1」分配 id，删掉末尾若干行之后新插入的行会**复用已被删除的 id**；而日志表恰好有一个按天清理的保留策略，一旦某次清理删到了尾部，续传游标就会漏掉或重复一批记录。`AUTOINCREMENT` 用一张内部序列表保证 id 永不回退，代价是每次插入多一次序列表更新，对本项目的写入量可以忽略。

UUID 存为 `VARCHAR(36)` 字符串而非 `sa.Uuid`。后者在 SQLite 上会存成不可读的 BLOB 或非标准格式，用 `sqlite3` 命令行排查问题时极其别扭。

### 3.2 时间戳

全库统一存 **UTC 的 naive datetime**。SQLite 没有时区类型，SQLAlchemy 的 `DateTime` 在 SQLite 上落为 ISO 字符串，带时区的 datetime 存进去再读出来会丢失偏移信息，不如从一开始就规定库内只有 UTC。

```python
# maa_api/db/models.py
from datetime import UTC, datetime


def utcnow() -> datetime:
    """库内统一时间源。不要用已废弃的 datetime.utcnow()。"""
    return datetime.now(UTC).replace(tzinfo=None)
```

API 层序列化时补上 `Z` 后缀输出 ISO 8601，本地化交给前端。定时任务是唯一的例外：`schedule.timezone` 显式存业务时区（默认 `Asia/Shanghai`），因为 cron 表达式必须按用户所在时区解释。

命名统一为 `created_at` / `updated_at` / `started_at` / `finished_at` / `resolved_at` / `expires_at`。现有代码里 `Task.create_time` 存的是 `'%Y-%m-%d %H:%M:%S'` 本地时间字符串，重构后一律改为 `DATETIME` 列。

### 3.3 枚举的存储

枚举在 Python 侧是 `enum.StrEnum`（Python 3.11 起内置，项目已要求 `^3.11`），在数据库侧存为**纯字符串列**，不用 `sa.Enum`。

原因是 SQLite 上的 `sa.Enum` 会生成 `CHECK (status IN (...))` 约束，而 SQLite 不支持 `ALTER TABLE ... DROP CONSTRAINT`。一旦将来给 `TaskStatus` 加一个值，就得走 batch 迁移把整张表复制重建——对 `log_entry` 这种几十万行的表是灾难。改用字符串列 + 应用层校验，枚举演进零成本，代价是数据库不再兜底拼写错误，这个风险由 SQLModel 的类型标注和测试覆盖。

列宽统一给 `VARCHAR(16)`（状态、来源、级别）或 `VARCHAR(24)`（阶段、角色），错误码给 `VARCHAR(48)`。SQLite 不强制长度，这些声明是给 Alembic 和其他工具读的文档。

### 3.4 外键与级联

所有跨表引用都声明外键，配合 `PRAGMA foreign_keys=ON` 生效。级联策略按"日志能否比主体活得久"来分：

- `task` → `pipeline`：`ON DELETE CASCADE`。任务是流水线的组成部分，没有独立意义。
- `agent_message` → `agent_session`：`ON DELETE CASCADE`。同上。
- `log_entry` / `screenshot` → `pipeline` / `task`：`ON DELETE SET NULL`。日志与截图有独立的保留策略，清理流水线历史时不应连带清空日志；它们变成"无归属"记录后由自己的策略管理。
- `agent_audit`、`confirmation` 的关联字段：`ON DELETE SET NULL`。审计必须比被审计对象活得久，这是审计的定义。

### 与现有枚举的对应关系

`TaskStatus` 的五个值原样保留（`pending` / `running` / `completed` / `failed` / `cancelled`），只是基类从 `Enum` 换成 `StrEnum`。这一步很关键：现有代码里 `Task.to_dict()` 需要手工 `result['status'] = result['status'].value` 才能序列化，换成 `StrEnum` 后 Pydantic 与 `json.dumps` 直接吃字符串，那段补丁代码随之消失。

新增的 `SKIPPED` 填补了现有执行器的一个表达空白。`executor.py` 在任务重试耗尽后打印"达到最大重试次数，跳过该任务"然后继续下一个，但任务状态仍停留在 `FAILED`，于是"失败后跳过继续"和"失败后整条中止"在数据上不可区分。重构后：重试耗尽且流水线继续 → `SKIPPED`；因内核崩溃或取消而未能收尾 → `CANCELLED`；任务链明确报错且不再重试 → `FAILED`。

`PipelineStatus` 与现有 `TaskPipelineStatus` 的差异只有一处：`IDLE` 改名 `PENDING`。原来的 `IDLE`（"命令尚未开始执行"）在单实例内存模型里是"空闲"，而在队列语义下它精确对应"已入队待取"，`PENDING` 与 `TaskStatus.PENDING` 对齐后状态机更好读。

## 5. 表设计

共 14 张业务表。`alembic_version` 由 Alembic 自行维护，不计入。

### 5.1 `pipeline` — 流水线执行记录

队列的唯一事实来源。`PipelineRunner` 按 `ORDER BY priority ASC, created_at ASC` 取 `PENDING` 记录，取用与执行的每一次状态变更都落库。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | VARCHAR(36) | PK | UUID4 |
| `core_id` | VARCHAR(32) | NOT NULL, default `"default"` | 多实例扩展口，首版恒为 `default` |
| `core_epoch` | INTEGER | NULL | 执行时子进程的启动世代号，崩溃排查用 |
| `source` | VARCHAR(16) | NOT NULL | `PipelineSource`，服务端判定，客户端不可指定 |
| `priority` | INTEGER | NOT NULL | `Priority`，默认由 `source` 推导，可被队列接口调整 |
| `status` | VARCHAR(16) | NOT NULL, default `"pending"` | `PipelineStatus` |
| `title` | VARCHAR(64) | NULL | 前端显示名，如"日常"、"肉鸽通宵" |
| `task_count` | INTEGER | NOT NULL | 创建时写定，列表页免 COUNT 子查询 |
| `error_code` | VARCHAR(48) | NULL | 终态为 `FAILED` 时的错误码，取值见 [05-API规范与路由清单](./05-API规范与路由清单.md) |
| `error_message` | TEXT | NULL | 人类可读的失败原因 |
| `schedule_id` | VARCHAR(36) | FK `schedule.id` ON DELETE SET NULL | `source=scheduled` 时的来源 |
| `agent_session_id` | VARCHAR(36) | FK `agent_session.id` ON DELETE SET NULL | `source=agent` 时的来源会话 |
| `retry_of_id` | VARCHAR(36) | FK `pipeline.id` ON DELETE SET NULL | 由某条历史流水线重放而来 |
| `idempotency_key` | VARCHAR(64) | NULL, UNIQUE | 幂等提交去重，见 05 的幂等性章节 |
| `notify_on_finish` | BOOLEAN | NOT NULL, default `1` | 终态是否触发通知通道 |
| `created_at` | DATETIME | NOT NULL | 入队时间，即排序依据 |
| `started_at` | DATETIME | NULL | 转入 `RUNNING` 的时间 |
| `finished_at` | DATETIME | NULL | 进入终态的时间 |

`error_code` 复用 API 错误码的同一套枚举字符串，不另立一套内部码。这样前端拿到流水线详情后，用同一张码表渲染文案，也便于按错误码做聚合统计（"本周失败最多的原因是 `DEVICE_NOT_CONNECTED`"）。

三个来源字段（`schedule_id` / `agent_session_id` / `retry_of_id`）刻意拆成三列而不合并成一个多态的 `origin_id`。多态外键无法声明约束，也无法用 JOIN 直接取来源实体的名称，而列表页恰好需要显示"由『每日常规』定时触发"。

`core_epoch` 配合 `task.maa_task_id` 解决一个隐蔽问题：MaaCore 返回的 task id 是 `Asst` 实例内自增的小整数，子进程重启后会从头重复。带上世代号后，事后排查日志时能确定某个 `maa_task_id=3` 属于哪一次内核运行。运行期的回调匹配仍以 `PipelineRunner` 的内存映射为准，不查库。

| `started_at` | DATETIME | NULL | 收到 `TaskChainStart` 的时间 |
| `finished_at` | DATETIME | NULL | 收到 `TaskChainCompleted` / `TaskChainError` 的时间 |

`params` 与 `raw_params` 的分工值得说明。`params` 是**下发快照**——已注入全局渠道默认值、已剔除 `None`、与内核实际收到的 JSON 逐字节一致，排查"为什么内核没按我想的跑"时只看这一列。`raw_params` 是**客户端原文**，只记录用户显式设置过的字段，用于 `POST /api/pipelines/{id}/retry` 重放；重放时重新走一遍默认值注入，于是"上周提交的官服任务"在渠道默认值改成 B 服后会按新默认值跑，这是期望行为。

`task_name` 由服务端按 `type_name` 填充（`StartUp` → `开始唤醒`、`Fight` → `刷理智`，映射取自现有 `task.py` 各子类的 `task_name`）。现有 `Task.__init__` 校验 `task_name` 非空并允许调用方传值，实际上从未有人传过不同的值，属于无效自由度。

`(pipeline_id, order_index)` 与 `(pipeline_id, maa_task_id)` 都加唯一约束，后者允许 NULL（任务提交失败时没有内核 id）。

### 5.3 `log_entry` — 三路日志

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | 单调递增，兼作 WebSocket 续传游标 |
| `source` | VARCHAR(16) | NOT NULL | `LogSource` |
| `level` | VARCHAR(16) | NOT NULL | `LogLevel` |
| `content` | TEXT | NOT NULL | 已格式化的日志正文（中文） |
| `meta` | JSON | NULL | 结构化附加信息，见下 |
| `pipeline_id` | VARCHAR(36) | FK `pipeline.id` ON DELETE SET NULL | |
| `task_id` | VARCHAR(36) | FK `task.id` ON DELETE SET NULL | |
| `core_id` | VARCHAR(32) | NULL | 来自内核的日志才有值 |
| `created_at` | DATETIME | NOT NULL | **事件发生时间**，不是入库时间 |

`created_at` 取事件自身的时间戳而非 `INSERT` 时刻。`LogHub` 做批量刷盘，入库可能比事件晚几百毫秒；IPC 事件消息已经带了 `ts` 字段（见 [02-系统架构设计](./02-系统架构设计.md) 的事件消息定义），直接用它，否则前端看到的时间轴会被刷盘节奏抖动。

`meta` 按来源存不同结构，这正是选 JSON 列的原因：

- `maa_task`：`{"msg": 10001, "taskchain": "Fight", "what": "StageDrops", "details": {...}}` —— MaaCore 回调的原始 `msg` 与 `details`。保留原始体是为了以后补充文案映射时能从历史数据回溯，而不必重跑任务。
- `server`：`{"module": "services.pipeline_runner", "func": "_run_task", "lineno": 88, "exc": "Traceback..."}`
- `maacore_debug`：`{"raw": "[2026-09-16 11:30:00.123][INF][Px7f...] ...", "file": "asst.log", "offset": 1048576}`

**注意 `content` 里绝不放 base64 图像。** 现有 `pipeline.append_img_log()` 把整张截图的 base64 塞进日志列表，一次任务结束就是几百 KB 的字符串，落库后日志表会被图片撑爆、WebSocket 广播也会卡顿。重构后截图走 `screenshot` 表，日志里只放 `meta.screenshot_id`。

### 5.5 `schedule` — 定时任务

| `enabled` | BOOLEAN | NOT NULL, default `1` | |

| `priority` | INTEGER | NOT NULL, default `2` | 默认 `Priority.SCHEDULED` |
| `misfire_grace_seconds` | INTEGER | NOT NULL, default `300` | 错过触发点后的宽限期 |
| `catch_up` | BOOLEAN | NOT NULL, default `0` | 服务停机期间错过的是否补跑 |
| `skip_if_running` | BOOLEAN | NOT NULL, default `1` | 队列中已有本 schedule 的实例则跳过本次 |

| `updated_at` | DATETIME | NOT NULL | |

`template` 直接存提交请求体的 `tasks` 数组，不做任何预处理。这样定时触发时走的是和前端手动提交**完全相同**的校验与默认值注入路径，不会出现"手动能跑、定时报错"的分裂。

`skip_if_running` 保留了现有 `daily_task_scheduler.daily_art_task()` 里 `if task_scheduler.is_running(): return` 的行为，但语义更准确：现在检查的是"本 schedule 在队列里有没有未完成的实例"，而不是"整个系统是否忙"。系统忙时新流水线正常入队排队，这是队列化带来的改进。

现有 `resource/daily_task.json` 的 `weekday_task` 键沿用旧执行器的 Python `date.weekday()` 口径：`0=周一` 到 `6=周日`。新 schedule 的五段 cron 使用 POSIX 口径：`0=周日`、`1=周一` 到 `6=周六`。因此旧键 `"0"`（周一）必须迁移为 `cron = "0 7,19 * * 1"`，`"5"`（周六）迁移为 `... 6`，`"6"`（周日）迁移为 `... 0`；不能直接复制旧键。

历史迁移 `0002_migrate_daily_task_json.py` 曾直接复制星期索引。`0004_correct_daily_schedule_weekday.py` 修正这批数据，只修改名字严格为 `daily_task_weekday_<0..6>` 且 cron 仍等于 `0002` 默认值 `0 7,19 * * <旧索引>` 的记录。用户自建 schedule 和已经改过 cron 的记录不受影响，其他列（包括模板、时区、启用状态和优先级）保持原值。`0004` 的降级也只还原仍匹配修正后默认 cron 的行。源文件不存在时 `0002` 仍跳过，升级后原文件保留作为回滚依据。

### 5.6 `setting` — 可视化配置项

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `key` | VARCHAR(64) | PK | 点分命名，如 `adb.address`、`channel.client_type` |
| `value` | JSON | NOT NULL | 任意类型都包进 JSON，包括标量 |
| `updated_by` | VARCHAR(16) | NULL | `manual` / `agent` / `system` |
| `updated_at` | DATETIME | NOT NULL | |

只存**被显式覆盖过**的项。配置解析优先级为 环境变量 > `setting` 表 > `config.yaml` > 代码内默认值，与 [02-系统架构设计](./02-系统架构设计.md) 的启动顺序一致。表里没有某个 key 就意味着"用下层的值"，这比把所有默认值都灌进表里干净得多——升级后新增的默认值会自动生效，不需要数据迁移。

`value` 用 JSON 列而非 TEXT，是为了区分 `"25"`（字符串）与 `25`（整数）。`adb.screenshot_quality` 必须是整数才能传给 PIL，如果统一存字符串就得在读取侧维护一张类型表。

字段元信息（中文标签、类型、取值范围、是否敏感、热生效动作）**不进表**，定义在代码里的 `settings_schema.py`。理由是这些元信息随代码版本变化，放数据库会出现"代码升级了但表里还是旧 schema"的漂移；`GET /api/settings/schema` 直接从代码导出。敏感项（`llm.api_key`、`smtp.password`、`app.access_token`）读接口返回 `"***"`，写接口收到 `"***"` 或空字符串时视为"不变更"。

### 5.9 `agent_audit` — 全量工具调用审计

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | |
| `caller` | VARCHAR(16) | NOT NULL | `CallerType`：`mcp` / `internal` / `rest` |
| `caller_detail` | VARCHAR(128) | NULL | MCP session id、客户端 UA 或调用来源标识 |
| `tool_name` | VARCHAR(64) | NOT NULL | |
| `arguments` | JSON | NOT NULL | 调用参数，已裁剪 |
| `result_summary` | TEXT | NULL | 结果摘要，上限 2 KB |
| `result_ref` | JSON | NULL | 结果关联的实体 id：`{"pipeline_id":"...","screenshot_id":"..."}` |
| `status` | VARCHAR(16) | NOT NULL | `AuditStatus` |
| `error_code` | VARCHAR(48) | NULL | |
| `risk_level` | VARCHAR(16) | NOT NULL, default `"none"` | `PolicyEngine` 的判定结果 |
| `forced` | BOOLEAN | NOT NULL, default `0` | 流水线运行中带 `force=true` 强制介入 |
| `confirmation_id` | VARCHAR(36) | FK `confirmation.id` ON DELETE SET NULL | 本次调用**逐次确认**所对应的那条确认 |
| `authorized_by_id` | VARCHAR(36) | FK `confirmation.id` ON DELETE SET NULL | 本次调用凭**会话级授权**免确认执行时，指向授权那条确认 |
| `session_id` | VARCHAR(36) | FK `agent_session.id` ON DELETE SET NULL | 内置 agent 调用才有值 |

这张表是三个调用方的共同落点：REST 的 `POST /api/agent/tools/{name}/invoke`、MCP 的 tool call、内置 agent 的循环都写同一张表，前端审计页因此只需一个数据源。

**入库前必须裁剪 `arguments` 与 `result_summary`。** 截图工具的返回值是 base64 字符串，一张 1280×720 的 JPEG 编码后有几十万字符，原样落库会让审计表比日志表更早爆掉。约定：任何超过 1 KB 的字符串值替换为 `{"__truncated__": true, "len": 412300, "ref": "screenshot_id"}`。

`duration_ms` 包含人工确认的等待时间，因为审计关心的是"这次调用从发起到落地花了多久"。需要区分纯执行耗时时，用 `confirmation.resolved_at - confirmation.created_at` 相减。

`confirmation_id` 与 `authorized_by_id` **互斥**：一次调用要么走了逐次确认（前者有值），要么凭会话级授权免确认执行（后者有值），要么本来就不需要确认（两者皆空）。拆成两列而不用一列加标志，是为了让"这个授权窗口内一共执行了哪些操作"成为一次简单的 `WHERE authorized_by_id = ?` 查询 —— 这正是事后复盘原子操作序列的入口（见 [11-Agent模块设计 §4.3](./11-Agent模块设计.md)）。用一列加标志的话，同一个 `confirmation.id` 会同时表示"这次确认批准了这个调用"和"这次授权覆盖了这个调用"，聚合时必须时刻带上标志条件，容易漏。

### 5.10 `confirmation` — 人工确认请求

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | VARCHAR(36) | PK | |
| `action` | VARCHAR(64) | NOT NULL | 待确认的动作标识，通常是工具名如 `submit_pipeline` |
| `risk_level` | VARCHAR(16) | NOT NULL | `RiskLevel` |
| `reason` | TEXT | NOT NULL | 命中了哪条策略，直接展示给用户 |
| `payload` | JSON | NOT NULL | 待执行动作的完整参数，批准后原样执行 |
| `status` | VARCHAR(16) | NOT NULL, default `"pending"` | `ConfirmationStatus` |
| `requested_by` | VARCHAR(16) | NOT NULL | `CallerType` |
| `audit_id` | INTEGER | FK `agent_audit.id` ON DELETE SET NULL | |
| `resolved_by` | VARCHAR(32) | NULL | 处理方，单用户系统固定 `web`；超时则为 `system` |
| `resolved_reason` | TEXT | NULL | 拒绝原因 |
| `expires_at` | DATETIME | NOT NULL | 超时时刻，按 `risk_level` 分级（见下） |
| `created_at` | DATETIME | NOT NULL | |
| `resolved_at` | DATETIME | NULL | |

`payload` 存的是**待执行动作的完整参数**，不是引用。这样批准后不依赖发起方进程还活着——即使 MCP 客户端断开，已批准的动作仍可执行，或者反过来说，服务重启后可以扫出 `PENDING` 记录并一律置 `EXPIRED`，不会留下悬空的半执行状态。

会话级原子操作授权也是这张表的一条记录，`action` 取 `grant_atomic_ops`、`payload` 为 `{"session_id": "...", "window_seconds": 900}`，不为它单开一张表或加 `kind` 字段。它与普通确认的唯一差别是"执行"的含义——普通确认批准后执行 `payload` 描述的那个动作，授权确认批准后写 `agent_session.atomic_grant_*` 两个字段。这条记录同时充当授权的审计凭据：`agent_audit.authorized_by_id` 指向它，`expires_at` 保留原始的窗口计算依据。

**`expires_at` 按风险级别分级，而不是统一一个值。** 两类确认的等待场景完全不同：

| 确认类型 | 默认超时 | 理由 |
|---|---|---|
| 消耗类、破坏类 | 10 分钟 | 靠推送触达，用户要听见、解锁、点开应用、读完再决定。这类操作值得等 |
| 原子操作会话授权（`grant_atomic_ops`） | 120 秒 | 用户正在对话界面前主动让 agent 操作，此刻就在看屏幕 |

两个值都做成可配置。放长到 10 分钟的直接原因是推送的触达链条比想象的长，而 WebKit 忽略 `requireInteraction`（通知不常驻）让这个问题更严重 —— 平台约束的核实见 [09-前端重构方案 §13.2](./09-前端重构方案.md)。

超时靠**双保险**：内存中的 `asyncio.wait_for` 负责唤醒阻塞中的工具调用；一个每 10 秒跑一次的扫描任务把 `status='pending' AND expires_at < now()` 的记录批量置 `EXPIRED`，负责服务重启或内存态丢失的兜底。状态流转只允许 `PENDING → APPROVED / REJECTED / EXPIRED`，终态不可再变，重复批准由 `UPDATE ... WHERE status='pending'` 的影响行数判定。

10 分钟的窗口让扫描任务这一层从"兜底"变成"主力"——服务在 10 分钟内重启一次的概率远高于 2 分钟内，因此内存态丢失后仍能正确判定超时这件事，比原本更重要。

### 5.11 `update_record` — 三种热更新的历史

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|

| `from_version` | VARCHAR(64) | NULL | 更新前版本 |
| `to_version` | VARCHAR(64) | NULL | 目标版本 |

| `progress` | INTEGER | NOT NULL, default `0` | 0–100 |
| `bytes_total` | INTEGER | NULL | 下载总字节 |

| `triggered_by` | VARCHAR(16) | NOT NULL | `manual` / `agent` / `scheduled` |
| `created_at` | DATETIME | NOT NULL | |
| `started_at` | DATETIME | NULL | |
| `finished_at` | DATETIME | NULL | |

`channel` 是一个**按 `target` 分支解释**的列：

| `target` | `channel` 取值 | 说明 |
|---|---|---|
| `core` | `ReleaseChannel` | 实际只会写入 `stable`，其余两值见 [07-热更新方案 §2.6](./07-热更新方案.md) |
| `resource` | `ResourceChannel` | `ota`（通道 A）/ `repo`（通道 B）/ `all`（两条一起） |
| `game` | NULL | 游戏本体只有官服与 B 服之分，那是 `to_version` 的事 |

活动资源的两条通道**不拆进 `UpdateTarget`**，而是复用这一列。理由是 `target` 承担着"哪种更新"的语义并被部分唯一索引用来做并发互斥，拆成 `resource_ota` / `resource_repo` 会让两条通道变得可以并发执行——而 [07-热更新方案 §5.3](./07-热更新方案.md) 明确要求三种更新共用一把互斥锁，拆开反而要在别处把互斥补回来。用 `channel` 区分则天然沿用现有互斥：同一时刻只允许一条 `target='resource'` 的记录在跑，无论它更的是哪条通道。

代价是这一列的取值域不再单一，读取时必须先看 `target`。这在 SQLite 里无法用 CHECK 约束优雅表达（需要写成带 `CASE` 的复合条件），因此校验放在服务层的 Pydantic 模型里按 `target` 分发，与 `notify_channel.config` 的处理方式一致。

`from_version` → `to_version` 的版本变迁记录让"当前安装版本 vs 最新版本"的对比页有历史依据，也是游戏本体更新决策里明确要求的展示内容。`target='resource'` 且 `channel='repo'` 时，这两列存的是通道 B 的 `last_updated` 时间戳原值（形如 `2026-09-14 04:36:14.000`）而非语义化版本号；`channel='ota'` 时两列均为 NULL，因为通道 A 没有版本号概念，它的"版本"是 `ETag`，记在 `resource_asset` 表里（见 §5.13）。

同一 `target` 同时只允许一条进行中的记录，用**部分唯一索引**在数据库层强制：

```python
sa.Index(
    "uq_update_record_running_target",
    "target",
    unique=True,
    sqlite_where=sa.text("status = 'running'"),
)
```

这比在服务层查一次再插入可靠：并发两个 `POST /api/updates/core` 时，第二个会撞唯一约束，服务层捕获后转成 `409 UPDATE_ALREADY_RUNNING`。

`progress` 与 `phase` 会被高频更新（下载进度），必须**节流**：下载阶段每 500 ms 或每 1% 才写一次库，其余时间只走 WebSocket 广播。否则一次内核更新能产生几千次 UPDATE，白白抢占写锁。

### 5.13 `resource_asset` — 自定义资源与远端资源的版本基准

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | VARCHAR(36) | PK | |
| `kind` | VARCHAR(16) | NOT NULL | `ResourceAssetKind` |
| `name` | VARCHAR(64) | NOT NULL | |
| `description` | TEXT | NULL | |
| `content` | JSON | NULL | ≤ 64 KB 的内容直接入库 |
| `path` | VARCHAR(255) | NULL | 超过阈值则落文件，存相对 `resource/` 的路径 |
| `meta` | JSON | NULL | 关卡名、作业作者、方案数量等摘要信息 |
| `checksum` | VARCHAR(64) | NULL | 内容 SHA-256，去重与变更检测 |
| `enabled` | BOOLEAN | NOT NULL, default `1` | `custom_task` 是否参与增量资源注入 |
| `remote_version` | VARCHAR(64) | NULL | 远端版本基准，仅远端两类使用 |
| `etag` | VARCHAR(128) | NULL | 上次成功下载时的 `ETag`，仅 `ota_resource` 使用 |
| `last_modified` | VARCHAR(64) | NULL | 上次成功下载时的 `Last-Modified`，仅 `ota_resource` 使用 |
| `last_checked_at` | DATETIME | NULL | 上次向远端确认过版本的时间，仅远端两类使用 |
| `created_at` | DATETIME | NOT NULL | |
| `updated_at` | DATETIME | NOT NULL | |

唯一约束 `(kind, name)`。`content` 与 `path` 二选一（用 CHECK 约束表达 `content IS NOT NULL OR path IS NOT NULL`）：小作业直接入库省掉文件管理，大作业落文件避免单行过大。`checksum` 的用途是 `enabled` 的 `custom_task` 变更后判断是否需要重新触发 `LOAD_RESOURCE` 命令——内容没变就不必重载内核资源。

这张表原本只存用户侧资产（`copilot` / `infrast_plan` / `custom_task`），纳入活动资源的两条通道后同时承担**远端资源的版本基准**。两类行靠 `kind` 区分，共用一张表是因为它们回答的是同一个问题——"加载链上这一层现在是什么内容、什么时候来的"——而且前端的资源页需要把它们并列展示。

| `kind` | 行数 | `name` 示例 | `path` | 版本基准落在 |
|---|---|---|---|---|
| `ota_resource` | 每个清单条目一行 | `resource/tasks.json` | `<layers>/cache/` 下的相对路径 | `etag` + `last_modified` + `checksum` |
| `repo_resource` | 固定一行 | `MaaResource` | `<layers>/repo/` | `remote_version` |

两处 `<layers>` 均指 `resource/maa-layers/`，与 `<maa_path>` 平级而非嵌套在其中，理由见 [07-热更新方案 §3.7](./07-热更新方案.md)。

`checksum` 由 NOT NULL 放宽为 NULL。`ota_resource` 仍然必填（[07-热更新方案 §3.4](./07-热更新方案.md) 要求算一次内容 `sha256` 作为 `ETag` 不可信时的兜底），但 `repo_resource` 指向的是一棵 107 MB 的目录树，为它算整树哈希的成本远超收益——它的变更检测靠 `remote_version` 就够了。用 CHECK 约束表达"`kind='repo_resource'` 之外必须非空"在 SQLite 里可写但可读性差，放到服务层校验。

**`repo_resource` 这一行是通道 B 版本判定的唯一权威来源，不能改读磁盘上的 `version.json`。** 这不是洁癖：内核更新会把整个 MAA 目录替换成新解压的发行包，`<maa_path>/resource/version.json` 随之回退到发行包自带的旧值，而通道 B 落在 `<layers>/repo/` 里的那份不受更新影响仍是新值，两个文件长期不一致，读哪个都会误判。以本表记录为基准则完全不受内核更新影响。详见 [07-热更新方案 §2.5](./07-热更新方案.md) 与 [07-热更新方案 §3.3](./07-热更新方案.md)。

`last_checked_at` 与 `updated_at` 是两件事，不要合并：前者是"上次问过远端"，后者是"上次内容真的变了"。资源页要同时展示"最后更新于 3 天前"和"5 分钟前检查过，已是最新"，少一个都表达不出来。

远端两类行由 `UpdateService` 独占写入，用户接口不允许增删改；反过来 `enabled` 字段对它们无意义（加载链是否包含某一层取决于目录是否存在，见 [07-热更新方案 §3.5](./07-热更新方案.md)），恒为默认值 `1`。

## 6. 索引设计

索引不按"哪列看起来会被查"来加，而是先列全查询模式，再为每个模式挑一条索引。SQLite 的查询规划器**单表通常只用一条索引**，所以复合索引的列序要按「等值条件 → 范围条件 → 排序」排列，把过滤性最强的等值列放最前。

| 查询模式 | 出现位置 | 索引 |
|---|---|---|
| 取下一条待执行流水线：`core_id=? AND status='pending' ORDER BY priority, created_at LIMIT 1` | `PipelineRunner` 主循环，每轮一次 | `ix_pipeline_dequeue(core_id, status, priority, created_at)` |
| 流水线列表：可选 `status` / `source` 过滤，按 `created_at DESC` 分页 | 前端首页与历史页 | `ix_pipeline_status_created_at(status, created_at)`、`ix_pipeline_source_created_at(source, created_at)` |
| 当前运行中：`status='running'` | 状态轮询、冲突判定 | 复用 `ix_pipeline_dequeue` 前缀 |
| 幂等去重：`idempotency_key=?` | 提交接口 | `uq_pipeline_idempotency_key`（唯一） |
| 定时任务的历史实例：`schedule_id=? ORDER BY created_at DESC` | 定时任务详情页 | `ix_pipeline_schedule_id_created_at(schedule_id, created_at)` |
| 流水线的任务列表：`pipeline_id=? ORDER BY order_index` | 详情页、执行循环 | `uq_task_pipeline_order(pipeline_id, order_index)`（唯一，兼作索引） |
| 内核 task id 反查：`pipeline_id=? AND maa_task_id=?` | 事后排查 | `uq_task_pipeline_maa_task(pipeline_id, maa_task_id)`（唯一） |
| 日志分页：按 `source` + 可选 `level` + 时间范围，按 `id DESC` | 日志页三个标签 | `ix_log_entry_source_created_at(source, created_at)` |
| 日志续传：`id > ?` | WebSocket 重连补发 | 主键 |
| 流水线日志：`pipeline_id=? ORDER BY id` | 详情页日志区 | `ix_log_entry_pipeline_id_id(pipeline_id, id)` |
| 日志清理：`source=? AND created_at < ?` | 保留策略任务 | 复用 `ix_log_entry_source_created_at` |
| 截图清理与列表：`created_at <` / `pipeline_id=?` | 保留策略、详情页 | `ix_screenshot_created_at(created_at)`、`ix_screenshot_pipeline_id_created_at(pipeline_id, created_at)` |
| 装载定时任务：`enabled=1` | 启动与配置变更 | `ix_schedule_enabled_next_run_at(enabled, next_run_at)` |
| 待确认列表与超时扫描：`status='pending'`、`status='pending' AND expires_at < ?` | 前端卡片、超时任务 | `ix_confirmation_status_expires_at(status, expires_at)` |
| 审计查询：可选 `caller` / `tool_name` 过滤，按 `created_at DESC` | 审计页 | `ix_agent_audit_caller_created_at(caller, created_at)`、`ix_agent_audit_tool_name_created_at(tool_name, created_at)` |
| 会话消息：`session_id=? ORDER BY seq` | 会话加载、上下文重建 | `uq_agent_message_session_seq(session_id, seq)`（唯一） |
| 会话列表：`ORDER BY last_message_at DESC` | agent 页侧栏 | `ix_agent_session_last_message_at(last_message_at)` |
| 更新历史：`target=? ORDER BY created_at DESC` | 更新页 | `ix_update_record_target_created_at(target, created_at)` |
| 同 target 并发拦截：`target=? AND status='running'` | 更新接口 | `uq_update_record_running_target`（部分唯一） |
| 资源查询：`kind=? AND enabled=1` | 资源页、增量注入 | `ix_resource_asset_kind_enabled(kind, enabled)` |
| 远端版本基准读取：`kind=? AND name=?` | 更新检查，每次一到两行 | `uq_resource_asset_kind_name(kind, name)`（唯一，兼作索引） |
| API 调试台收藏列表：按 `updated_at DESC` | 调试台收藏面板 | `ix_api_snippet_updated_at(updated_at)` |

刻意**不加**的索引也值得记录。`status`、`source`、`level`、`kind` 这类低基数单列不建独立索引——SQLite 对选择性差的索引会直接放弃使用，白占空间还拖慢写入；它们只作为复合索引的首列出现。`log_entry.content` 不建全文索引：日志检索靠时间范围加来源收窄后在小结果集上 `LIKE`，FTS5 虚拟表会让写入成本翻倍，而这张表本来就是写多读少。

`log_entry`、`agent_message`、`agent_audit` 三张高频写表的索引总数都控制在 3 条以内。每条索引都要在 `INSERT` 时维护 B 树，日志表的索引数量直接决定落盘吞吐上限。

## 7. JSON 字段的写法

SQLModel 在需要指定具体 SQLAlchemy 列类型时必须用 `sa_column`：

```python
# maa_api/db/models.py
import uuid
from datetime import datetime
from typing import Any

from sqlalchemy import JSON, Column, DateTime, UniqueConstraint, text
from sqlmodel import Field, SQLModel

from maa_api.domain.enums import TaskStatus


class Task(SQLModel, table=True):
    __tablename__ = "task"

    id: str = Field(default_factory=lambda: str(uuid.uuid4()), primary_key=True, max_length=36)
    pipeline_id: str = Field(foreign_key="pipeline.id", ondelete="CASCADE", max_length=36)
    order_index: int
    type_name: str = Field(max_length=32)
    task_name: str = Field(max_length=32)

    # 下发给内核的参数原文
    params: dict[str, Any] = Field(
        default_factory=dict,
        sa_column=Column("params", JSON, nullable=False, server_default=text("'{}'")),
    )
    # 客户端原始提交，供重放
    raw_params: dict[str, Any] | None = Field(
        default=None,
        sa_column=Column("raw_params", JSON, nullable=True),
    )

    status: str = Field(default=TaskStatus.PENDING, max_length=16)
    retry_count: int = 0
    max_retries: int = 3
    maa_task_id: int | None = Field(default=None)
    created_at: datetime = Field(
        default_factory=utcnow,
        sa_column=Column("created_at", DateTime, nullable=False),
    )

    __table_args__ = (
        UniqueConstraint("pipeline_id", "order_index", name="uq_task_pipeline_order"),
        UniqueConstraint("pipeline_id", "maa_task_id", name="uq_task_pipeline_maa_task"),
    )
```

四个容易踩的坑：

**用了 `sa_column` 之后，`Field()` 上的列级参数全部失效。** `nullable`、`index`、`unique`、`default`、`max_length` 必须写进 `Column(...)`，写在 `Field()` 里会被静默忽略——这个失败模式没有任何报错，只表现为迁移生成的 DDL 少了约束。

**`Column` 实例不能被两个模型共用。** 想给多张表加同样的 `meta: JSON` 列时，必须写成工厂函数每次返回新实例，否则 SQLAlchemy 在第二次绑定时报 `Column object already assigned to Table`：

```python
def json_column(name: str, *, nullable: bool = True) -> Column:
    return Column(name, JSON, nullable=nullable)
```

**JSON 列的原地修改不会被 ORM 追踪。** `task.params["stage"] = "1-7"` 后 `commit()` 什么也不会发生，因为 SQLAlchemy 只比较对象引用。要么整体赋值 `task.params = {**task.params, "stage": "1-7"}`，要么在列类型上套 `MutableDict.as_mutable(JSON)`。本项目选**整体赋值**并在代码评审中把这条列为检查项：`MutableDict` 会给每个实例挂变更监听，在日志这种高频对象上是不必要的开销，而参数在落库后本来就不该再改。

**JSON 内部字段可以查但不该常查。** SQLite 内建 `json_extract`，SQLAlchemy 侧写作 `func.json_extract(Task.params, "$.stage") == "1-7"`。这是全表扫描，只适合排查场景。如果某个 JSON 内字段变成常用过滤条件（例如统计各关卡的刷取次数），正确做法是把它提升为独立列并加索引，而不是给 JSON 建表达式索引。

`alembic.ini` 放项目根，`script_location = maa_api/db/migrations`，版本文件名模板设为 `%%(rev)s_%%(slug)s` 并用四位序号手工递增，不用随机 hash——本项目是单人线性开发，序号让"第几个迁移"一目了然，也避免 `down_revision` 链在 review 时难以核对。

**约束命名约定必须在任何模型被导入之前设置。** SQLite 无法删除匿名约束，而 Alembic 的 batch 模式在重建表时需要按名字引用它们：

```python
# maa_api/db/models.py 顶部，先于所有表定义
from sqlalchemy import MetaData
from sqlmodel import SQLModel

SQLModel.metadata.naming_convention = {
    "ix": "ix_%(table_name)s_%(column_0_N_name)s",
    "uq": "uq_%(table_name)s_%(column_0_N_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
    "pk": "pk_%(table_name)s",
}
```

### 8.2 `env.py` 要点

```python
# maa_api/db/migrations/env.py
from alembic import context
from sqlalchemy import create_engine, pool
from sqlmodel import SQLModel

import maa_api.db.models  # noqa: F401  必须 import 以注册全部表到 metadata

from maa_api.db.session import SYNC_URL

target_metadata = SQLModel.metadata


def run_migrations_online() -> None:
    engine = create_engine(SYNC_URL, poolclass=pool.NullPool)
    with engine.connect() as conn:
        context.configure(
            connection=conn,
            target_metadata=target_metadata,
            render_as_batch=True,        # SQLite 必须：ALTER 走复制重建
            compare_type=True,
            compare_server_default=True,
        )
        with context.begin_transaction():
            context.run_migrations()
```

`render_as_batch=True` 是 SQLite 上最重要的一行。SQLite 的 `ALTER TABLE` 只支持加列、改表名、改列名，改类型、加约束、删列都不支持；batch 模式会自动展开成"建临时表 → 拷数据 → 删旧表 → 改名"的序列。忘了这行，第一次改列类型的迁移就会在生产库上失败。

Alembic 用**同步引擎**（`sqlite:///`）而非 aiosqlite。迁移是一次性的串行操作，异步驱动只带来复杂度；`async_engine_from_config` 那套写法在这里纯属负担。

`compare_type=True` 让自动生成能发现列类型变化，但不要盲信 `--autogenerate` 的产物：它检测不到索引重命名、检测不到 `sqlite_where` 的部分索引，生成的 batch 操作偶尔漏约束。每个迁移文件都要人工过一遍。

### 8.3 lifespan 里的自动迁移

按 [02-系统架构设计](./02-系统架构设计.md) 的启动顺序，迁移在第 2 步执行，早于 `LogHub` 与 `CoreSupervisor`。

```python
# maa_api/db/migrate.py
def _upgrade_head() -> None:
    cfg = Config("alembic.ini")
    cfg.set_main_option("script_location", "maa_api/db/migrations")
    cfg.set_main_option("sqlalchemy.url", SYNC_URL)
    command.upgrade(cfg, "head")


async def ensure_schema() -> None:
    DB_PATH.parent.mkdir(parents=True, exist_ok=True)
    if DB_PATH.exists() and _pending_revisions():
        _backup_database()          # resource/backup/maa_api.db.{ts}.bak
    await asyncio.to_thread(_upgrade_head)
```

四条纪律：

**迁移跑在线程池里。** `command.upgrade` 是同步阻塞调用，直接在 lifespan 的协程里跑会冻结事件循环；虽然此刻还没开始接受请求，但 uvicorn 的信号处理也会一起卡住，Ctrl-C 杀不掉。

**有待应用的迁移时先备份。** 用 `VACUUM INTO 'resource/backup/maa_api.db.{ts}.bak'` 而不是文件拷贝，前者能在 WAL 存在时拿到一致快照。只在确有待应用迁移时备份，否则每次重启都产生一份备份文件。备份保留最近 5 份。

**迁移失败必须中止启动。** 不要 `try/except` 后继续跑——schema 不匹配时服务能起来但每个请求都在报 `no such column`，比直接起不来更难排查。异常原样抛出，让 uvicorn 打印 traceback 后退出，同时在 stderr 打印备份文件路径。

**永远不要调用 `SQLModel.metadata.create_all()`。** 哪怕是首次启动建空库也走 `upgrade head`。混用两条建表路径会让 `alembic_version` 表与实际 schema 漂移：`create_all` 建出的是当前代码的最新结构，但版本表是空的，下一次启动会从第一个迁移开始重放，然后撞上"表已存在"。

## 9. 仓储层

仓储的职责边界是一句话：**把查询语句挡在服务层之外，不做业务决策**。服务层不出现 `select()`，仓储里不出现 `if 状态 == X then 发通知`。

```
maa_api/db/repositories/
├── base.py            BaseRepository：会话持有、分页封装
├── pipeline.py        PipelineRepository + TaskRepository
├── log.py             LogRepository + ScreenshotRepository
├── schedule.py        ScheduleRepository
├── setting.py         SettingRepository
├── agent.py           AgentSessionRepository + AgentMessageRepository
├── audit.py           AuditRepository + ConfirmationRepository
├── update.py          UpdateRepository
├── notify.py          NotifyChannelRepository
└── resource.py        ResourceAssetRepository
```

**事务归属**：仓储方法不自己 `commit()`，由调用方决定事务边界——一次流水线提交要在同一事务里写 `pipeline` 与全部 `task`，仓储如果各自提交就做不到原子。唯一例外是 `LogRepository.bulk_insert()` 与清理方法，它们自成事务，因为日志落盘与业务事务的成败无关（业务回滚了也不该丢掉解释失败原因的日志）。

**返回类型**：读方法返回 ORM 实例或轻量 dataclass，不返回 `Row` 或元组。分页统一返回 `Page[T]`，字段为 `items` / `total` / `page` / `size`，与 API 的分页响应体结构一致，避免在路由层再做一次转换。

典型方法签名：


三个方法的返回值设计需要解释。`claim_next()` 用**原子条件更新**领取流水线而不是"先查后改"：

```python
stmt = (
    update(Pipeline)
    .where(Pipeline.id == candidate_id, Pipeline.status == PipelineStatus.PENDING)
    .values(status=PipelineStatus.RUNNING, started_at=utcnow(), core_epoch=epoch)
)
if (await session.execute(stmt)).rowcount == 0:
    return None      # 被并发取走或已取消，重新选下一条
```

首版只有一个消费者，看起来不需要这道防护；但"取消流水线"是另一条并发写入路径，用户可能恰好在领取的瞬间点取消。`rowcount` 判定顺手把多消费者的扩展口留好了。

`mark_terminal()` 与 `resolve()` 都返回 `bool` 而非 `None`，表示"状态机是否接受了这次流转"。终态不可再变、待确认项不可重复批准这两条规则由 `WHERE` 子句在数据库层保证，返回 `False` 则服务层转成 `409`。

`expire_overdue()` 返回被置为过期的 id 列表而不是条数，因为服务层要据此广播 WebSocket 事件并唤醒对应的阻塞调用。

## 10. 数据保留与清理

### 10.1 体量估算

MaaCore 的回调密度是这个设计里最需要正视的约束。`SubTaskStart` 与 `SubTaskExtraInfo` 在刷理智时每关卡产生若干条，一条完整日常流水线（唤醒 → 基建 → 刷理智 → 公招 → 信用 → 奖励 → 关闭）大致产生 1000–3000 条 `maa_task` 日志；`maacore_debug` 更密，运行期每秒数条，半小时就有几千行。按每天两次日常估算，日志表每天增长 1–2 万行，单行含 `meta` JSON 平均约 250 字节，即 3–5 MB/天。不做清理的话一年就是 1–2 GB，SQLite 撑得住但查询与备份都会变得难受。

### 10.2 分级保留策略

三种来源的价值密度差别很大，因此分级处理而不是一刀切。

| 来源 | 落库级别 | 保留天数 | 条数上限 |
|---|---|---|---|
| `maa_task` | 全部 | 30 | 300,000 |
| `server` | `INFO` 及以上 | 7 | 200,000 |
| `maacore_debug` | **`WARNING` 及以上** | 3 | 50,000 |

`maacore_debug` 只落 `WARNING` 及以上是一个有意的削减。这一路日志在 MaaCore 自己的 `asst.log` 文件里已经有完整副本，把 `DEBUG`/`INFO` 再复制进数据库，换来的只是"能在网页上翻更久的历史"，代价是吃掉日志表一半以上的体量。方案是：实时推送全量（`LogHub` 直接转发给 WebSocket，前端调试时看得到每一行），落库只落警告与错误，需要翻更早的完整 debug 日志时由接口 tail 文件。落库阈值做成配置项 `log.persist_maacore_debug_level`，排查内核问题期间可以临时调到 `debug`。

两个维度同时生效，取更严格的一方：先按天数删，删完若仍超条数上限，按 `id` 升序继续删到上限以内。条数上限是为了防住"一次异常刷了几十万行"的突发场景——单靠天数拦不住突发。

### 10.3 流水线与截图

`pipeline` 保留 90 天或最近 500 条（先触发者生效）。删除时 `task` 随外键级联，`log_entry` 与 `screenshot` 的关联字段置 NULL 后由各自策略处理。被清理的流水线再被查询时返回 `404` 而不是 `410`——不保留墓碑记录，因为为了区分"从未存在"和"曾经存在"而维护一张墓碑表，收益不值得。

截图文件保留 7 天，同时受总大小上限约束（默认 512 MB）。超限时按 `created_at` 升序删文件并给记录打 `deleted_at`，记录本身随流水线的保留策略一起清理。这是 `deleted_at` 列存在的意义：流水线详情页仍然显示"此处有一张已过期的截图"，接口返回 `410 SCREENSHOT_EXPIRED`。

`resource/temp/screencap/` 下的 IPC 中转图保留 1 小时，与 [02-系统架构设计](./02-系统架构设计.md) 的约定一致。这批文件不进 `screenshot` 表，它们只是跨进程传图的临时载体；需要归档时由主进程另存到 `image/screenshot/` 并建记录。

`agent_audit` **不设保留上限**。它是审计，按定义要长期留存；单次调用一条记录，量级比日志小三个数量级，一年也就几万行。`agent_message` 随 `agent_session` 生命周期管理：手动删除会话时级联删除，另设"归档 90 天前的非活跃会话"为可选操作，默认不自动删。

### 10.4 清理任务的实现要点

清理逻辑集中在 `services/retention_service.py`，由 APScheduler 每天 04:00 触发，另在启动后 30 秒跑一次（覆盖长期停机后重启的场景）。

**分批删除，不要一条 DELETE 干完。** 删十万行的单条语句会长时间持有写锁，期间所有日志落盘都在 `busy_timeout` 上排队：

```python
while True:
    deleted = await repo.purge(source, before=cutoff, keep_max=limit)   # 内部 LIMIT 5000
    if deleted == 0:
        break
    await asyncio.sleep(0.05)      # 让出写锁给 LogHub 刷盘
```

SQLite 默认不支持 `DELETE ... LIMIT`（需要编译期开启 `SQLITE_ENABLE_UPDATE_DELETE_LIMIT`），所以仓储里写成子查询形式：`DELETE FROM log_entry WHERE id IN (SELECT id FROM log_entry WHERE source = :s AND created_at < :t ORDER BY id LIMIT 5000)`。

**空间回收靠增量 vacuum。** 因为初始迁移已设 `auto_vacuum=INCREMENTAL`，清理后执行 `PRAGMA incremental_vacuum(1000)` 归还部分页面，耗时可控且不需要独占锁。完整 `VACUUM` 需要重写整库并独占，只作为设置页里的手动维护操作提供，不进自动任务。

**日志写入侧同样需要节流。** `LogHub` 维护内存队列，攒够 200 条或超过 500 ms 才做一次 `add_all()` + `commit()`。批量插入比逐条快一个数量级，且大幅减少写锁争夺。队列同时充当 WebSocket 新连接的回填缓冲（保留最近 2000 条），细节见 [06-实时日志与WebSocket](./06-实时日志与WebSocket.md)。

## 11. 从现有内存模型的迁移

现有的 `TaskPipeline` 是一个进程内单例：`tasks` 列表、`logs` 列表、一个 `status` 字段，服务重启即全部丢失，且同时只能存在一条流水线（`task_scheduler.clear()` 会直接清空上一次的记录）。映射到新模型的对应关系如下。

`TaskPipeline.tasks` → `task` 表按 `pipeline_id` + `order_index` 组织。多条流水线从此可以共存于库中，前端能看到历史，队列也才有可能实现。

`TaskPipeline.logs`（`list[TaskPipelineLog]`，字段为 `log_type` / `log_level` / `content`）→ `log_entry` 表。`log_type` 的两个取值 `"text"` 与 `"img"` 被拆开处理：文本日志进 `log_entry`，图片日志（base64 内容）进 `screenshot` 表并在日志的 `meta.screenshot_id` 里引用。这是本次重构对日志模型最实质的改动。

`CallbackHandler.task_map`（内核 task id → 内部 task id 的进程内字典）→ 运行期仍是 `PipelineRunner` 的内存映射，同时把 `maa_task_id` 落到 `task` 表。内存映射是回调匹配的事实来源（快且在一次运行内绝对准确），DB 字段是事后排查的线索。

`resource/daily_task.json` → `schedule` 表，由 `0002_migrate_daily_task_json.py` 展开、再由 `0004_correct_daily_schedule_weekday.py` 修正旧 Python 星期索引到 POSIX cron 的偏移。`0004` 只更正仍处于默认值的迁移记录；文件不存在时 `0002` 跳过，迁移后原文件保留不删，作为回滚依据。星期口径详见 [§5.5](#55-schedule--定时任务)。

`config.yaml` 的各段 → 保持文件为**基础配置**，只有用户在设置页改过的项进 `setting` 表作为覆盖层。`smtp` 段额外生成一条 `notify_channel` 记录（`type=email`），因为通知配置从单一邮件扩展成了多通道，继续放在 `config.yaml` 里表达不了"多个通道各自订阅不同事件"。`app.access_token`、`app.maa_core_path`、`adb.path` 这三项标记为仅可从 `config.yaml` 或环境变量修改——它们在服务启动早期就要用到，放进数据库会产生"改错了就进不去设置页"的死锁。
