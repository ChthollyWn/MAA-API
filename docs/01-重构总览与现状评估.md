# 重构总览与现状评估

## 1. 动因

七项需求触发了这次重构：前端 UI 过时需重做、需要实时服务日志、需要三种热更新（MAA 内核 / 活动资源 / 游戏本体）、需要 ADB 连接重试、需要官服与 B 服渠道支持、需要开放 API 与在线调试页、需要 Agent 模块。

这七项里有五项无法在现有架构上增量实现：

热更新受阻于 native 库的加载方式。MaaCore 通过 `ctypes.CDLL` 加载进主进程，且 `Asst.__lib` 是进程级全局变量，覆盖磁盘文件对运行中的进程无效。

实时日志受阻于日志的存储位置。任务日志存在 `TaskPipeline.logs` 这个内存 list 里，`clear()` 一调就没了，服务日志只写文件，两者没有统一出口可供推送。

ADB 重试受阻于连接逻辑的分散。MaaCore 内部与 adbutils 各连一次，状态互不知情，且连接发生在模块 import 阶段。

开放 API 受阻于响应格式。所有接口一律返回 HTTP 200，业务码塞在 body 的 `code` 字段里，这个格式在 OpenAPI 与 agent 场景下无法表达错误语义。

Agent 受阻于并发模型。全局单个 `task_scheduler` 实例，运行中拒绝一切新提交，且没有队列概念，第二个调用方无处排队。

因此这是一次**重写而非改造**：后端执行层重写，`static/` 整体废弃，引入 SQLite 与子进程隔离。

## 2. 现状评估

### 2.1 技术栈

后端是 FastAPI + Poetry，Python 声明 `^3.11`（`scripts/start-maa-api.sh` 实际指向 3.13 的虚拟环境）。前端无构建工具，Vue 3 global build 加 Element Plus 从 unpkg CDN 直接引入。

关键依赖的实际版本（来自 `poetry.lock`）：

| 包 | 当前版本 | 说明 |
|---|---|---|
| fastapi | 0.95.2 | 落后多个大版本 |
| pydantic | **1.10.21** | **v1，不是 v2** |
| uvicorn | 0.22.0 | 落后 |
| adbutils | 2.8.6 | 可用 |
| apscheduler | 3.11.0 | 可用 |

pydantic 仍在 v1 是个容易被忽略但影响工作量的事实。现有代码的 `super().dict(*args, **kwargs)`（`task.py` 的 `to_dict`）、在 `__init__` 里 `super().__init__(**data)` 后直接赋值字段（`pipeline.py` 的 `TaskPipelineLog`）都是 v1 写法，v2 下行为不同或直接报错。重构需要连带完成 v1 到 v2 的迁移，这同时也是引入 SQLModel 的前提（SQLModel 与 pydantic v2 配套）。

本地 MaaCore 版本为 v6.17.5（macOS）与 v6.17.2 / v6.17.1（Linux），活动资源 `version.json` 显示最后更新于 2026-09-05。

### 2.2 架构问题

**启动期强耦合。** `maa_api/model/core/scheduler.py` 末尾是模块级 `task_scheduler = TaskScheduler()`，构造函数里调 `load_asst()`，而 `load_asst()` 依次做版本查询、下载更新、解压、加载资源、连接 ADB。这条链上任何一环失败（网络不通、镜像超时、模拟器没起来）都会让 import 失败，整个服务起不来。`scripts/start-maa-api.sh` 里那段最多重试 60 次的 ADB 等待循环，就是为了绕开这个问题而加在进程外的补丁。

**单实例且无队列。** 全局一个 MaaCore 实例，`_check_asst_running()` 在运行中直接抛异常拒绝新提交。定时任务撞上手动任务时靠 `if task_scheduler.is_running(): return` 静默放弃。没有排队概念，谁先到谁执行，后到的直接失败。

**状态全在内存。** `TaskPipeline` 是个 pydantic 模型，`tasks`、`status`、`logs` 都是内存字段。重启丢失全部执行历史，前端刷新看到的是当前进程的瞬时状态。

**截图以 base64 内嵌日志。** `pipeline.py` 的 `append_img_log` 把整张 JPEG 的 base64 塞进日志内容，前端通过 `GET /api/maa/pipeline` 全量拉取。一条流水线跑完累积十几张图，单次响应可达数 MB —— 决策要求移动端优先，这个做法在手机上不可用。

**轮询式任务等待。** `executor.py` 用 `while self._running and self.asst.running(): self._condition.wait(timeout=5)` 等任务完成。`running()` 反映的是整个内核是否在跑任务链而非某个具体任务，5 秒粒度也让状态更新有明显延迟。且没有超时兜底，一个卡住的任务会让流水线永久挂起。

**两套 ADB 连接。** `asst_manager.py` 里 MaaCore 通过 `asst.connect()` 连一次，`adb_service.py` 里 adbutils 又连一次，两者状态不同步。后者还在模块 import 时就读取了配置（`adb_address = Config.get_config("adb", "address")` 是模块级语句），配置改了不重启不生效。

### 2.3 代码缺陷清单

阅读代码时发现以下确切缺陷，重构时逐条消除。它们大多不影响主流程，但说明了对应功能路径从未被真正执行过。

**`ReclamationTask` 的参数字典用变量当键。** `model/core/task.py` 中：

```python
params = {
    enable: enable,        # 键应为字符串 "enable"
    theme: theme,
    mode: mode,
    ...
}
```

键位置用的是变量本身而非字符串字面量。当多个参数都是 `None` 时，字典会塌缩成 `{None: <最后一个值>}`。生息演算任务的参数从未正确传给内核。

**`TaskRequest` 的字段定义带尾随逗号。** `model/request/request.py` 中：

```python
tools_to_craft: Optional[list[str]] = None,    # 尾随逗号
increment_mode: Optional[int] = None,          # 尾随逗号
num_craft_batches: Optional[int] = None
```

类体里的尾随逗号会让默认值变成元组 `(None,)` 而非 `None`，与声明的类型不符。

**`TaskRequest.times` 重复定义。** 同一个类里 `times: Optional[int] = None` 出现两次（通用参数区与 Fight 参数区各一次），后者覆盖前者。

**`InfrastTask` 的参数名拼错。** 定义为 `failename`，而文档字符串写的是 `filename`，MAA 内核期望的键也是 `filename`。自定义基建换班方案（`mode=10000`）因此无法生效。

**`Award` 任务的默认值与文档矛盾。** `request.py` 里 `mail`、`recruit`、`orundum`、`mining`、`specialaccess` 全部默认 `True`，而 `task.py` 的文档字符串明确写这些默认为 `False`。实际行为是会去领取所有邮件与各种奖励。

**`InfrastTask.threshold` 的签名默认值与文档不符。** 函数签名是 `threshold: float = 0.5`，文档字符串写"默认 0.3"。已确认 0.3 是期望值，签名里的 0.5 是错的。新模型不设服务端默认值（`default=None`），把默认值的决定权交还内核，避免内核调整默认行为后服务端产生偏差；0.3 只作为前端表单的占位提示文案出现。

**`recruitment_time` 的类型声明在 JSON 层面不成立。** `request.py` 声明为 `dict[int, int]`，但 JSON 对象的键只能是字符串。该字段应为 `dict[str, int]`，键为 Tag 等级的字符串形式。

**枚举值硬编码在 Python 里会随内核版本过时。** 最典型的是 `Roguelike.theme`（当前硬编码 `Phantom` / `Mizuki` / `Sami` / `Sarkaz`），MAA 每次新增肉鸽主题都需要改代码。同类还有基建设施名、无人机用途、商店物品名。这些取值的事实来源是 MAA 的资源目录（`resource/tasks/` 下的定义文件），应当在启动时从资源读取并缓存，而非写死在模型里。

**`Asst.get_image` 的缓冲区写法无效。** `model/core/asst.py` 中 `buffer.value = b'\000' * size`，而 `ctypes.c_byte * size` 的实例没有 `value` 属性。该方法从未被成功调用过（项目实际截图走 adbutils）。

**两个方法漏了 `@staticmethod`。** `set_static_option` 与 `set_connection_extras` 定义时既无 `self` 也无装饰器，实例调用会把 `self` 当第一个参数。

**回调线程内抛异常。** `callback_handler.handle_task_status` 在 `task.type_name != taskchain` 时 `raise ResponseException(...)`。这个函数运行在 MaaCore 的 C 回调线程上，异常穿过 C 调用边界是未定义行为，可能直接崩掉内核。

**连接失败的回调事件名拼错，该日志从未触发过。** `callback_handler.py` 的 `connection_map` 里键是 `ConnectFaild`，而 MaaCore 实际发出的是 `ConnectFailed`（已核实内核二进制导出的字符串，且本地调试日志中该事件出现 68 次）。整张映射表里最关键的"模拟器连接失败"日志因此从未匹配成功，连接问题在界面上完全不可见 —— 这正是 ADB 连接故障难以排查的直接原因之一。

**`AsstConnect` 已被官方废弃。** `AsstCaller.h` 在该函数上方注明 "FIXME: 5.0 版本将废弃此接口"，而项目正在使用它。

**文件名拼写错误。** `maa_api/exception/excetpion_handler.py`（excetpion → exception）。

**CORS 配置组合无效。** `main.py` 里 `allow_origins=["*"]` 与 `allow_credentials=True` 同时设置，而 CORS 规范不允许凭据请求使用通配符来源，浏览器会拒绝该组合。

**使用了已废弃的启动钩子。** `@app.on_event("startup")` 在当前 FastAPI 版本已标记废弃，应改用 `lifespan`。

**鉴权只认 query 参数。** `dependence/auth.py` 的 `token_auth(token: str = "")` 只从 URL 查询参数取 token，无法用 header 传递。

### 2.4 前端问题

`static/index.html` 是 734 行单文件，所有任务表单以 `v-if="task.type_name === 'StartUp'"` 的形式平铺展开，且"查看"与"创建"两套表单各写一遍，同一个字段在文件里出现两次。新增一个任务类型需要改三处（查看区、创建区、`app.js` 的初始化数据）。

暴露的参数远少于内核支持的。以刷理智为例，`task.py` 的 `FightTask` 有 15 个参数，前端只有关卡、理智药、过期理智药、连战次数 4 个。企鹅数据汇报、掉落数量指定、节省理智碎石模式等都无法通过界面配置。

依赖 unpkg CDN 加载 Vue、Element Plus、axios。CDN 不可达时页面完全打不开，这对一个本该在局域网自给自足的工具是不合理的依赖。

### 2.5 已有但未合并的成果

`feat/0515` 分支（`ed4576c`，未合入 `dev`）已经实现了本次需求中的一部分：服务日志读取接口、MAA 内核 / 活动资源 / 游戏 APK 三种更新接口、多渠道 token 鉴权、配置模板与首启动检查、MaaCore 懒加载。

按决策，**不复用这些代码与结构**，从 `dev` 全新实现。但其中已验证的外部接口常量要沿用：官服 APK 下载直链、B 服 biligame 信息接口及其 `game_base_id`、两个渠道的包名、`dumpsys` 解析版本号的方式。详见 [07-热更新方案](./07-热更新方案.md)。

`feat/ws` 与 `feat/rec` 两个分支的名字暗示 WebSocket 与公招相关工作，但实际内容落后于 `dev`（停在 `53da0d6`），没有可复用成果。

## 3. 重构范围

### 3.1 做的事

后端执行层重写为主进程加 MaaCore 子进程的双进程架构；引入 SQLite 持久化流水线、日志、配置、定时任务、agent 会话与审计；API 全面改标准 HTTP 状态码与统一错误体；新增 WebSocket 实时推送；前端用 Vite + React 重写为移动优先的 PWA；实现三种热更新；统一 ADB 连接管理与四时机重试；账号渠道配置化；新增开放 API 调试台；新增 Agent 模块（MCP Server 加内置对话 agent）；定时任务重做为可视化 cron 配置；通知扩展为多通道；依赖升级（FastAPI 与 pydantic v2）。

### 3.2 不做的事

明确排除，避免范围蔓延：

不支持多设备或多账号并发。架构上为多子进程留了扩展口（见 [02-系统架构设计 §5.4](./02-系统架构设计.md)），但首版只跑一个子进程、绑一台设备、一个账号。

不支持官服与 B 服之外的区服。台服与国际服不在范围内。

不引入独立 OCR。画面理解依赖多模态模型看截图。

不做用户系统与多租户。鉴权仍是单个 `access_token`。

不改造 MaaCore 本身，不提交上游 PR。缺失的能力（滑动、独立 OCR）通过 ADB 或模型能力绕过。

不处理 git 历史中的明文密码。按决策仓库为私有，不做历史重写。

### 3.3 影响面

需要替换或删除的现有文件清单见 [02-系统架构设计 §9](./02-系统架构设计.md) 的映射表。简言之：`maa_api/` 下除 `asst.py`（迁移并补全）、`task.py`（保留任务定义与文档字符串）、`updater.py` 与 `downloader.py`（迁移）之外，其余模块基本重写；`static/` 全部删除。

配置文件 `config.yaml` 的结构会扩展（新增渠道默认值、LLM 配置、通知通道、重试参数等），但可视化设置页的配置项落库而非写回 YAML，两者的优先级关系见 [08-ADB连接与账号渠道](./08-ADB连接与账号渠道.md)。

## 4. 验收标准

功能性验收按需求逐项对应：

新前端在手机浏览器上可完成创建流水线、查看实时日志、触发三种热更新、调试 API 全部操作，并可添加到主屏。任务表单覆盖 `task.py` 中定义的全部参数，不再有界面无法配置的内核能力。

日志页能同时看到三路来源（MaaCore 回调、Python 服务、MaaCore debug），可按来源与级别过滤，新日志以 WebSocket 实时到达而非轮询。

内核热更新期间 HTTP 服务不中断，前端能看到内核状态在就绪、重启中、就绪之间流转，更新完成后队列自动继续。活动资源更新不重启子进程。游戏本体更新能显示当前安装版本与最新版本的对比。

模拟器未启动时服务能正常启动，前端显示设备未连接并提供重连入口；模拟器启动后自动连上无需重启服务；运行中断线能自动重连。

渠道默认为 B 服，单个任务可覆盖为官服，切换后包名相关功能（版本检测、APK 更新）随之切换。

API 调试台能在手机上构造并发起请求，看到标准 HTTP 状态码与结构化错误体，并能看到本次调用触发的服务端日志。

MCP Server 能被 Claude Desktop 或 Cursor 接入并成功调用工具；内置 agent 能通过自然语言完成提交流水线、诊断失败原因、卡死救援三个场景；高风险操作触发前端确认卡片，拒绝与超时都得到正确处理；全部工具调用可在审计页回溯。

非功能性验收：

MaaCore 子进程崩溃（可用故障注入模拟）后，主进程能在 20 秒内检测、落库、告警并重启，API 服务全程可用。

连续崩溃时退避生效，不出现重启风暴。

一条典型日常流水线（唤醒、基建、刷理智、公招、领奖、关闭）跑完后，执行历史、任务级状态、全部日志与截图在服务重启后仍可查询。

日志与截图有生效的保留策略，长期运行不会无限增长。

`FakeAsst` 替身能让执行层、日志汇聚、重试与超时逻辑在无内核无真机的环境下完成测试。

## 5. 主要风险

**子进程隔离的工程量被低估。** 这是范围内最大的一块重写，涉及执行层、回调处理、状态机、崩溃恢复。IPC 的边界情况（超时后迟到的结果、心跳与长命令的冲突、维护窗口与崩溃检测的互斥）容易漏。缓解方式是把内核层作为第一个里程碑单独完成并充分测试，再往上叠功能，见 [12-实施计划与里程碑](./12-实施计划与里程碑.md)。

**pydantic v1 到 v2 的迁移波及面广。** 所有模型定义、校验器、序列化调用都要改，且 SQLModel 与 FastAPI 的版本需要协调匹配。建议在里程碑早期一次性完成升级，而不是边写新代码边迁移。

**agent 的实际可用性未经验证。** 多模态模型识别明日方舟界面的准确率、tool-calling 的参数填写质量、原子操作的成功率全部未知。缓解方式是按 [11-Agent模块设计 §10](./11-Agent模块设计.md) 的顺序验证，从纯读场景（数据总结、失败诊断）开始，确认模型能力后再放开操作权限。

**PWA 在局域网 HTTP 下受限。** Service Worker 与推送通知要求安全上下文，局域网 IP 加 HTTP 不满足。这会影响"添加到主屏"与推送确认通知这两个体验点，解决方案与代价见 [09-前端重构方案](./09-前端重构方案.md)。

**官方 OTA 完整资源清单缺少权威依据。** MAA 的增量资源机制除 `tasks.json` 外还包含哪些文件，需要核实，核实结果与保守方案见 [07-热更新方案](./07-热更新方案.md)。

**游戏 APK 更新链路长且脆弱。** 下载数 GB、`adb install` 覆盖安装、官服无版本 API，每一环都可能失败。这项功能的完成度预期应低于其他功能，允许降级为"检测到新版本并提示"。
