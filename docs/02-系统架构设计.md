# 系统架构设计

## 1. 架构总览

重构后的 MAA-API 是**双进程**架构：一个 FastAPI 主进程，一个 MaaCore 子进程。二者通过 `multiprocessing.Queue` 通信。

```
┌─────────────────────────────────────────────────────────────────┐
│  主进程  uvicorn + FastAPI                        :8002          │
│                                                                   │
│  ┌──────────── 接入层 ────────────────────────────────────────┐  │
│  │ REST 路由    WebSocket /api/ws    MCP /mcp    静态文件托管  │  │
│  └──────────────────────────────────────────────────────────────┘  │
│                                                                   │
│  ┌──────────── 应用服务层 ────────────────────────────────────┐  │
│  │ TaskQueue      优先级任务队列，落库                          │  │
│  │ PipelineRunner 流水线执行、重试、状态机                      │  │
│  │ LogHub         三路日志汇聚 → WS 广播 + 落库                │  │
│  │ DeviceManager  ADB 连接状态机与四时机重试                    │  │
│  │ UpdateService  内核 / 资源 / 游戏三种更新                    │  │
│  │ ScheduleService APScheduler，配置落库                        │  │
│  │ NotifyService  邮件 / Webhook / Bark / 钉钉 / 企微           │  │
│  │ SettingService 配置读写与热生效                              │  │
│  │ ToolRegistry   Agent 工具注册表，REST/MCP/内置 agent 共用    │  │
│  │ PolicyEngine   高风险操作判定与人工确认编排                  │  │
│  │ AgentRuntime   内置 agent 的 tool-calling 循环               │  │
│  └──────────────────────────────────────────────────────────────┘  │
│                                                                   │
│  ┌──────────── 基础设施层 ────────────────────────────────────┐  │
│  │ SQLite (SQLModel + Alembic)      CoreSupervisor             │  │
│  └──────────────────────────────────────────────────────────────┘  │
└───────────────────────────┬───────────────────────────────────────┘
                            │  cmd_queue  ──────────►
                            │  ◄──────────  event_queue
┌───────────────────────────┴───────────────────────────────────────┐
│  MaaCore 子进程  core_worker                                      │
│                                                                   │
│  命令循环 ← cmd_queue        Asst 实例（ctypes → libMaaCore）    │
│  回调函数 → event_queue      心跳应答                             │
└───────────────────────────────────────────────────────────────────┘
                            │ ADB
                            ▼
                     模拟器 / 真机（明日方舟）
```

主进程**绝不加载** `libMaaCore`。所有涉及内核的操作都编码为命令投递给子进程。这条纪律是子进程隔离能成立的前提，一旦主进程里出现 `ctypes.CDLL(libMaaCore)`，内核热更新与崩溃隔离就同时失效。

## 2. 为什么是子进程隔离

当前代码在 `maa_api/model/core/asst.py` 中通过 `ctypes.CDLL` 把 `libMaaCore.dylib` 加载进进程，且 `Asst.__lib` 是类级别的进程全局变量。这带来三个问题，子进程隔离一次性解决全部：

**内核更新无法生效。** 下载新版覆盖磁盘上的库文件后，进程内存里映射的仍是旧库。`dlclose` 在有活跃线程和未释放句柄时行为未定义，MaaCore 也不保证支持重复加载。隔离后只需重启子进程，主进程与 HTTP 服务不受影响。

**内核崩溃拖垮整个服务。** MaaCore 是 C++ native 库，OpenCV / ONNX Runtime 的段错误会直接杀死宿主进程。隔离后崩溃只损失子进程，主进程可以捕获、落库、重启、告警。

**启动期阻塞。** 现在 `maa_api/model/core/scheduler.py` 在模块 import 阶段就执行 `load_asst()`，内含版本校验、下载、解压、ADB 连接，任一环节失败整个服务起不来。隔离后主进程秒起，子进程异步就绪。

代价是执行层需要重写，且 MaaCore 回调必须跨进程传回主进程。

## 3. IPC 协议

两条单向队列：`cmd_queue`（主 → 子）与 `event_queue`（子 → 主）。消息为纯 dict，只含可 pickle 的基础类型。

### 3.1 命令消息

```python
{
    "cmd_id": "uuid4",        # 用于匹配响应
    "type": "APPEND_TASK",    # 命令类型
    "payload": {...},         # 命令参数
}
```

| 命令类型 | payload | 说明 |
|---|---|---|
| `LOAD_RESOURCE` | `path`, `incremental_paths[]` | 加载 / 重载内核资源。增量层为**有序**列表，顺序即优先级 |
| `SET_INSTANCE_OPTION` | `key`, `value` | 触控方案、暂停下干员、ClientType 等 |
| `SET_STATIC_OPTION` | `key`, `value` | CPU / GPU OCR |
| `SET_CONNECTION_EXTRAS` | `name`, `extras` | 模拟器端 extras |
| `CONNECT` | `adb_path`, `address`, `config`, `block` | 走 `AsstAsyncConnect` |
| `CONNECTED` | — | 查询连接状态 |
| `APPEND_TASK` | `type_name`, `params` | 返回内核 task id |
| `SET_TASK_PARAMS` | `task_id`, `params` | 运行中改参数 |
| `START` / `STOP` / `RUNNING` | — | 任务链控制与状态 |
| `CLICK` | `x`, `y`, `block` | `AsstAsyncClick` |
| `SCREENCAP` | `block` | `AsstAsyncScreencap` |
| `GET_IMAGE` | `bgr`, `save_to` | 取图，见 3.3 |
| `BACK_TO_HOME` | — | 回游戏主界面 |
| `GET_UUID` | — | 设备唯一码 |
| `GET_TASKS_LIST` | — | 内核队列中的 task id 列表 |
| `GET_MAP_LEVEL_KEY` | `key` | 关卡名互查，实验性 |
| `GET_VERSION` | — | 内核版本号 |
| `PING` | `seq` | 心跳 |
| `SHUTDOWN` | `graceful` | 优雅退出 |

### 3.2 事件消息

```python
{
    "type": "CALLBACK",
    "ts": 1758000000.123,
    "payload": {...},
}
```

| 事件类型 | payload | 说明 |
|---|---|---|
| `READY` | `version`, `pid` | 子进程完成资源加载，可接受命令 |
| `CMD_RESULT` | `cmd_id`, `ok`, `data`, `error` | 命令执行结果 |
| `CALLBACK` | `msg`（int）, `details`（dict） | MaaCore 原始回调，未做任何解释 |
| `LOG` | `level`, `content` | 子进程自身的 Python 日志 |
| `PONG` | `seq` | 心跳应答 |
| `FATAL` | `error`, `traceback` | 子进程捕获到的不可恢复错误 |

`CALLBACK` 事件刻意保持原始形态：子进程只做 `json.loads` 和 `Message(msg)` 枚举转换，不翻译语义。回调到中文日志的映射（现在在 `callback_handler.py` 里的三张 dict）迁移到主进程，这样调整文案不必重启子进程。

### 3.3 截图数据的传递

1280×720×3 的 BGR 图像约 2.7 MB。走 `Queue` 需要 pickle 加管道往返，单次几十毫秒，agent 连续截图时会成为瓶颈。

因此 `GET_IMAGE` 采用**落盘传引用**：子进程从 `AsstGetImage` 拿到字节后，编码为 JPEG 写入 `resource/temp/screencap/{uuid}.jpg`，`CMD_RESULT` 只返回文件路径与图像元信息。主进程按需读取、转 base64 或生成临时 URL。临时目录由主进程定期清理（默认保留 1 小时）。

需要更高帧率时（例如 agent 的视觉循环）可改用 `multiprocessing.shared_memory` 共享一块固定大小缓冲区，`CMD_RESULT` 只回传 offset 与尺寸。这是预留优化项，首版不实现。

### 3.4 命令的同步语义

主进程侧由 `CoreClient` 封装：投递命令后在 `asyncio.Future` 上等待对应 `cmd_id` 的 `CMD_RESULT`，带超时。一个后台 asyncio 任务持续消费 `event_queue`，按 `cmd_id` 唤醒 Future，其余事件分派给 `LogHub` 与 `PipelineRunner`。

由于 `multiprocessing.Queue` 的 `get()` 是阻塞调用，消费循环跑在 `loop.run_in_executor` 的独立线程里，通过 `loop.call_soon_threadsafe` 把事件交回事件循环。

超时时长按命令类型区分：查询类 5 秒，`CONNECT` 60 秒，`LOAD_RESOURCE` 300 秒，`START` / `STOP` 30 秒。超时不代表子进程已死，仍需心跳判定。

`LOAD_RESOURCE` 的 300 秒是从原定的 120 秒上调的。原值是按"基础资源 + 一个 15 KB 的 OTA `tasks.json`"估的，而现在这条命令一次要跑完整条加载链——基础资源加上三个增量层，其中通道 B 的那层解压后有 107 MB（`Arknights-Tile-Pos/` 的 4203 个关卡 JSON 占大头），详见 [07-热更新方案 §3.3](./07-热更新方案.md)。**新的耗时尚未实测**，300 秒是留足余量的保守值而非测量结果；M7 验证合并语义时会顺带测出真实耗时，届时可以回调。

超时定得偏大的代价很低：这是一个正常情况下几秒内返回的命令，超时值只在真正卡死时才起作用，而卡死同时会被心跳判定捕获（见 [03-MaaCore内核层设计 §4](./03-MaaCore内核层设计.md)），不依赖这个超时兜底。反过来定得偏小则会在慢磁盘或容器环境上误杀一次正常的资源重载，代价大得多。

## 4. 子进程生命周期

`CoreSupervisor` 负责子进程的创建、监控、重启与关闭，状态机如下：

```
                  ┌──────────┐
                  │ STOPPED  │
                  └────┬─────┘
                       │ start()
                       ▼
                  ┌──────────┐   资源加载失败
                  │ STARTING ├──────────────┐
                  └────┬─────┘              │
                       │ READY 事件          ▼
                       ▼                ┌────────┐
                  ┌──────────┐          │ FAILED │
             ┌────┤  READY   │          └────────┘
             │    └────┬─────┘
    restart()│         │ 心跳超时 / 进程退出 / FATAL
             │         ▼
             │    ┌──────────┐
             │    │ CRASHED  │
             │    └────┬─────┘
             │         │ 自动重启
             ▼         ▼
        ┌──────────────────┐
        │   RESTARTING     │
        └──────────────────┘
```

**健康判定**：每 5 秒发 `PING`，连续 3 次未收到 `PONG`（15 秒）判定失联；同时轮询 `Process.is_alive()` 捕获进程级退出。两者任一触发即进入 `CRASHED`。

**崩溃处理**（按决策，自动重启 + 标记失败 + 告警）：

1. 当前运行中的流水线与任务标记为 `FAILED`，`error_code` 记为 `CORE_CRASHED`，落库
2. 队列中未开始的条目保持 `PENDING`，不丢弃
3. WebSocket 广播 `core_status` 事件，前端弹告警
4. 走通知通道推送
5. 重启子进程；重启成功后队列自动继续消费

**重启退避**：连续崩溃时退避 5s → 15s → 60s，累计 5 次失败后进入 `FAILED` 状态停止自动重启，等前端手动触发。避免坏资源导致的无限重启风暴。

**关机**：先发 `SHUTDOWN`，等待 10 秒；超时 `terminate()`，再超时 5 秒 `kill()`。

## 5. 任务队列与并发

三个来源会争夺唯一的 MaaCore 子进程：前端手动操作、agent 调用、定时任务。按决策采用**统一队列 + 优先级排序，不抢占**。

### 5.1 优先级

| 来源 | `source` | 优先级 |
|---|---|---|
| 前端手动 | `manual` | 0（最高） |
| Agent | `agent` | 1 |
| 定时任务 | `scheduled` | 2 |

同优先级按 `created_at` 先进先出。出队顺序即 `ORDER BY priority ASC, created_at ASC`。

**不抢占**意味着：正在执行的流水线不会被更高优先级的新提交打断。用户若想立刻插队，需显式调用停止接口终止当前流水线，再提交新的 —— 这个动作在前端是一个明确的按钮，不是隐式行为。

### 5.2 队列语义

队列以 SQLite 为唯一事实来源，`PipelineRunner` 是单消费者循环：

```
取下一条 PENDING 流水线（按优先级排序）
  → 置 RUNNING
  → 逐个任务：APPEND_TASK → START → 等回调直到完成/失败
      失败则按 max_retries 重试，间隔 retry_delay
  → 全部完成后置 COMPLETED / FAILED / CANCELLED
  → 触发通知
  → 回到队首
```

与当前 `executor.py` 的关键差异：状态每次变更都落库而非仅存内存；等待任务完成不再靠 `asst.running()` 轮询加 5 秒 `Condition.wait`，改为消费 `CALLBACK` 事件流中的 `TaskChainCompleted` / `TaskChainError` / `TaskChainStopped`，辅以超时兜底。

### 5.3 原子操作的并发

`click` / `swipe` / `screencap` / `back_to_home` 这些原子操作**不进队列**，直接投递命令。它们是即时动作，排队没有意义。

但当流水线正在运行时，原子操作会与内核的自动化行为冲突（agent 点一下，内核同时在点别处）。处理方式：

- 流水线运行中调用原子操作，返回 `409 PIPELINE_ALREADY_RUNNING`
- 请求带 `force=true` 时允许执行，但审计记录标记为强制介入
- agent 的"卡死脉救援"场景先停止流水线，再做原子操作，这是 agent 应遵循的操作序列，会写进 tool 描述

### 5.4 为单子进程留多实例扩展口

按决策首版只跑一个子进程，但接口层按多实例设计，避免未来重做：

- 内部所有内核调用经 `CoreRegistry.get(core_id)` 取 `CoreClient`，首版 `core_id` 恒为 `"default"`
- 数据库中 `pipeline` 表带 `core_id` 字段，首版恒为 `"default"`
- REST 路由预留 `?core_id=` 查询参数，缺省即 `default`
- `DeviceManager` 按 `core_id` 维护独立的连接状态

这样扩展到多设备时只需实现 `CoreRegistry` 的多实例管理与设备绑定配置，路由与数据模型不动。

## 7. 应用生命周期

用 `lifespan` 替代已废弃的 `@app.on_event("startup")`：

**启动顺序**

1. 加载配置（`config.yaml` → DB 覆盖项 → 环境变量）
2. 初始化数据库引擎，执行 Alembic 迁移到最新版本
3. 启动 `LogHub`，接入 Python logging handler 与 MaaCore debug 日志 tail
4. 启动 `CoreSupervisor`，**不阻塞等待** —— 子进程在后台走"校验版本 → 加载资源 → 连接设备"
5. 启动 `PipelineRunner` 消费循环
6. 启动 `DeviceManager` 的连接监控
7. 从 DB 装载定时任务，启动 APScheduler
8. 注册 ToolRegistry，挂载 MCP endpoint
9. 开始接受 HTTP 请求

第 4 步是与现状最大的行为差异：服务进入可用状态不再依赖内核就绪。此时 `GET /api/system/health` 会如实返回内核 `STARTING`、设备 `DISCONNECTED`，前端据此展示状态而非报错。

**关闭顺序**：停止接受新请求 → 停止 APScheduler → 取消 `PipelineRunner`（正在运行的流水线标记 `CANCELLED`）→ 关闭子进程 → 刷新日志缓冲落库 → 关闭数据库。

## 8. 数据流示例

### 8.1 前端提交流水线

```
POST /api/pipelines
  → 校验参数，套用全局渠道默认值
  → 落库：pipeline(status=PENDING, source=manual, priority=0) + tasks
  → 返回 202 + pipeline_id
PipelineRunner 取到该流水线
  → cmd APPEND_TASK → CMD_RESULT 返回内核 task id，记录映射
  → cmd START
子进程回调 TaskChainStart
  → event CALLBACK → 主进程翻译成中文日志
  → LogHub 落库 + WS 广播 → 前端日志页实时滚动
子进程回调 TaskChainCompleted
  → 任务置 COMPLETED 落库 → 截图存盘 → 进入下一任务
全部完成
  → pipeline 置 COMPLETED → NotifyService 推送 → WS 广播终态
```

### 8.2 Agent 调用需确认的操作

```
MCP tool call: submit_pipeline(tasks=[Fight(stage="1-7", stone=3)])
  → ToolRegistry 分发
  → PolicyEngine 判定：stone > 0 命中消耗类 → 需确认
  → 创建 confirmation(status=PENDING)，WS 广播 confirm_request
  → tool 调用阻塞等待（消耗类与破坏类默认 600s，原子操作授权 120s）
前端弹卡片 → 用户点准许
  → POST /api/confirmations/{id} {approved: true}
  → 唤醒等待中的 tool 调用
  → 正常提交流水线，返回 pipeline_id
  → 审计落库：调用方、工具、参数、确认结果、耗时
```

若超时未响应，confirmation 置 `EXPIRED`，tool 返回 `CONFIRMATION_EXPIRED` 错误。

### 8.3 内核热更新

```
POST /api/updates/core
  → 查询 api.maa.plus 最新版本，比对当前版本
  → 落库 update_record(status=RUNNING)
  → 下载到 resource/temp/，WS 广播下载进度
  → 等待队列空闲（或按请求参数强制中断当前流水线）
  → CoreSupervisor.stop()：SHUTDOWN → join
  → 解压覆盖到 MAA 目录
  → CoreSupervisor.start()：等 READY 事件
  → update_record(status=SUCCESS)，WS 广播完成
```

全程 HTTP 服务不中断，前端仅看到内核状态在 `READY → RESTARTING → READY` 之间流转。这正是选择子进程隔离换来的收益。
