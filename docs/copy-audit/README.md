# 用户可见文案盘点与 AI 腔诊断

本目录是「本项目用户可能看到的所有文本」的一次全量抽取结果，以及据此做的 AI 腔诊断。
抽取是脚本跑的，可重复；诊断分四面由四份独立报告给出，本文件是索引与结论。

> **改写已执行完毕**：结果、验证矩阵与遗留项见 [改写结果.md](./改写结果.md)；
> 写作者遵循的合同见 [规范-文案规范.md](./规范-文案规范.md)。
> 现在的规则命中数已作为 `scripts/copy_inventory.py --check` 的棘轮基线。

## 一、结论（先看这段）

**1. 界面文案基本没有典型 AI 腔，不必搞「去 AI 味运动」。**
2049 条界面文案里：`抱歉`/`感谢` 0 条、emoji 0 条、感叹号 0 条、破折号当冒号 0 条、
「不是…而是…」0 条、Markdown 粗体 0 条（唯一的 3 条 `***` 是凭据掩码）。

**2. 界面真正的问题是「工程师写给自己看」，共四类：**
- 开发笔记泄漏进用户可见字段：459 条后端 schema 标签里 77 条带「内核默认值 / 判别联合 discriminator /
  源码 / 旧文案」这类只对维护者有意义的词（内核默认值 53、discriminator 10、不支持运行中设置 8、
  源码 5、留空 5、本服务约定 3、已弃用 3），其中 20 条说明 ≥80 字、最长 174 字
  （`maa_api/domain/task.py`，直接渲染在任务表单的展开说明里）。
- 错误提示缺「你能做什么」：319 条 `api_error` 只有约 17% 给了下一步动作。
- 术语不统一：8 组（停止/取消/清空/移除、任务/流水线、删除/移除、通道/渠道…），涉及约 120 条。
- 英文与 JSON 兜底直接抛给用户：`web/src/api/errors.ts` 3 条英文、`web/src/realtime/client.ts` 4 条英文、
  `web/src/features/updates/types.ts:294` 兜底会 `JSON.stringify` 出一坨原始 JSON。

**3. AI 腔真正重的地方是「开发向书面」，比界面重一个量级。**

| | 界面源码 | 开发向 |
|---|---:|---:|
| 破折号 `——` | 0 | 132（源码注释 86 条独立计） |
| 粗体断言 `**` | 0 | 218（源码注释 213 条独立计） |
| 「A 而不是 B」对照腔 | 0 | 74（源码注释 86 条独立计） |

> 表中「开发向」那几栏主要来自后端 docstring——它们经 `/openapi.json` 暴露给 API 调用者，
> 所以同时出现在「用户可见」计数里；界面自身的命中是 **0**。

docs 正文（11985 行）补测：**2171 行含粗体、587 行含破折号、285 行含「A 而不是 B」**；
134 个模块 docstring 里 **56 个（41%）带里程碑号**（`M3-04`、`docs/05 §2`），写的是实施流水账。

**4. 对外 OpenAPI 文档是重灾区。** 路由 docstring 直接进 `/docs` 与内置 API 调试台，
里面有设计辩护、里程碑代号与实现取舍（`maa_api/api/routers/system.py:152`、`agent.py:702` 等）。

**5. Agent 的 AI 味来自提示词，不是来自模型。** `maa_api/agent/runtime.py:170` 的 1612 字
SYSTEM_PROMPT 全是行为约束，**没有一句输出风格约束**（不复述、不分点、不总结、不用 emoji 都没写），
模型只能退回训练默认人格。诊断-3 给了一版 1404 字的可直接替换草案（原 1612 字，−13%），
七项安全与工具约束逐条核对全部保留，删的只是文体、元指令和重复条款。

**6. 通知文案没问题。** 推送标题已经是「需要确认：在游戏画面点击（刷理智 · 源石 ×3）」这种人话。

## 五、病灶分类（合并四份报告，按危害排序）

1. **设计笔记进对外的位置**——OpenAPI docstring 写「为什么这么设计」、任务字段说明写「内核默认值
   False（源码 StartUpTask.cpp 的 `params.get(...)`）」。用户要的是「填什么会怎样」。
2. **破折号当冒号**——`A —— B`，中文里 `——` 是有标记性的停顿，每段一处就是翻译腔。改冒号/句号/括号。
3. **「A 而不是 B」自我辩护**——B 在正文里从没出现过时，否定它纯属多余（74 处开发向 + 285 行 docs）。
4. **加粗 + 小标题 + 表格三件套**——处处加粗等于不加粗；决策记录里的加粗结论该留，普通叙述不该有。
5. **绝对化规定腔**——契约上（fail loud、不得静默失败）该留，叙述里的「一律/绝不/务必」是虚张声势。
6. **docstring 写实施流水账**——41% 的模块 docstring 带里程碑号，回答的是「谁在哪个里程碑改的」，
   不是「为什么这么写」。
7. **错误提示缺对象与下一步**——`CoreClient 的异步方法必须在事件循环内调用（或在构造时传入 loop=）`
   会原样出现在网页错误提示里。
8. **术语不统一**——同一队列条目四种动词、同一个东西两个名字（任务/流水线、通道/渠道）。

## 六、改写规范（速查）

完整版见 [诊断-1 §三](./诊断-1-界面.md)、[诊断-2 §3](./诊断-2-对外消息.md)、
[诊断-4 §3](./诊断-4-文档与注释.md)。速查：

- **按钮**：动词 + 对象，2–6 字，不带「请/点击」；全站同一动作同一动词。
- **空状态**：首句「还没有 X」，第二句给怎么开始，≤30 字，带一个动作按钮。
- **错误提示**：`发生了什么 + 你能做什么`；不复述「失败」；兜底不许出现英文与 JSON；
  状态码排句中、一屏最多一个。
- **Toast**：「已 + 动词」，≤15 字，不加句号。
- **确认弹窗**：标题 = 动词 + 对象 + ？，描述 ≤40 字只写后果，不可撤销才写「无法撤销」。
- **字段说明**：只写「这个参数影响游戏里会发生什么」+「不填会怎样」；默认值写「默认开启/关闭」，
  不写「内核默认值 True（启用）」；源码考证移到注释或 docs。
- **注释与 docstring**：写「为什么」，不写「我按哪个里程碑改的」；模块 docstring ≤15 行；
  `——` 全篇 ≤3 处；不写「本模块/这里/下面这」。
- **禁止清单（可做 lint）**：`——`（非引述）、「而是」「才是」「而非」、「值得注意的是」、
  「综上所述」、「首先…其次」、`✅⚠️❌`、`**` 加粗断言（除非契约条款）。
- **保留不改**：`—` 作无值占位、`***` 凭据掩码、`「」` 中文引号、「正在加载…」、技术名词原文
  （token/JSON/cron/cURL/HTTP/WebSocket/OpenAPI/ADB/VAPID/Agent/Copilot）、确认弹窗的疑问句标题、
  决策记录里的加粗结论与表格、`operator-classes.md` 的「词条 —— 释义」词典体。

## 八、复现方式

```bash
.venv/bin/python scripts/copy_inventory.py     # 抽取 + 规则扫描 + 重建本目录清单
```

- 前端部分：`web/scripts/copy-inventory.mjs`（TypeScript AST，取 JSX 文本、JSX 属性、
  文案字段、toast/confirm/Error 调用，并识别纯英文散文；注释不是 AST 节点故不会混入）。
- 后端部分：`scripts/copy_inventory.py`（Python AST，按调用位置区分 `AppError` message、
  `MaaField(label=/description=)`、`logger.*()`、通知 `title=/body=`、路由 docstring 等）。
- 前端测试：`cd web && pnpm test --run`；后端：`.venv/bin/python -m pytest -q`。

## 九、已知局限（读清单前先看）

1. **docs 正文逐行统计**，不是逐处统计：`ai-tells-docs.md` 里「粗体 2171」指 2171 行含粗体。
2. **模板字符串按整条收**（`已取消「${name}」`），占位符是源码表达式原文，不是运行时文本。
3. `api.d.ts`、`task-types.fixture.json` 等生成物不计入前端清单（它们由后端 description 生成，
   改后端即改它们）。
4. 界面清单里保留了少量测试夹具字符串（`test-utils.tsx`）与 DOM id 模板（`${id}-error`），
   属于扫描器保守取值的噪声，诊断时已排除。
5. **知识库按行抽取**：跨行的 `**加粗**` 会被按行截断。当前 31 个内置条目里单行 `**` 数为奇数的行
   为 **0**，所以没有实际影响；批量改知识库前仍应先确认。
6. 诊断结论经抽查复核：诊断-3 自己推翻的 3 条（知识库加粗"损坏"、`check_confirmation` 缺中文名、
   媒体段字数）与诊断-1 的 schema 命中数（报告正文 89 / 结论 74，实测 **77**）已在本文件按实测值修正。
   诊断-3 顺带查出一处真问题：`maa_api/services/webpush_service.py:68-91` 有一份**平行于前端的
   `TOOL_LABELS`**，改工具名文案时两处必须同步（这也是 Agent 那一批的隐藏工作量）。
7. 未纳入扫描的表面：`static/`（构建产物）、`daily_task_template.json`（旧数据模板）、
   `config.template.yaml` 的注释、Dockerfile 与 `docs/14` 的正文（后者已被诊断-4 判为全仓最干净）。
8. **OpenAPI 覆盖已实测对齐**：拿 `app.openapi()` 与清单逐条比对，549 条中文字段里真实缺口为 **0**；
   剩下 251 条未进清单的是运行时拼接的 `「状态说明：ERROR_CODE」`（由 `_STATUS_MESSAGE`
   与错误码枚举生成，原料都已在清单内）。诊断-2 提到的「132 条模型/字段 description」
   已通过把 Pydantic 模型 docstring 归到 `openapi` 表面补齐（清单-2 因此从 766 涨到 832）。

## 十、待裁决

改写属于对外行为变更，动手前需要你定两件事：

1. **范围**：只做 B1（界面）？还是 B1+B2+B3（用户能直接感知的三批）？还是连 B4/B5（开发向书面）一起？
2. **风格基线**：诊断给的规范里有两处会改变现有习惯，需要你拍板——
   - 「界面文案统一不加句末句号」（现状 935 条无句号 / 330 条有句号，主要是说明类）；
   - 「错误提示保留 HTTP 状态码但排到句中」（现状多写在括号里或开头）。
