# 文案规范（改写合同）

本文件是改写期间所有写作者的唯一契约。与 [诊断-*](./README.md) 冲突时以本文件为准。
范围：界面文案、对外消息、Agent 提示词与工具描述、知识库、脚本输出、注释与 docstring。

## 一、总原则

1. **说人话，说必要的话。** 一句话能说完的不写两句；用户不需要知道实现。
2. **正文只留必要信息，解释挪进 `InfoHint`（小问号）。** 见第四节。
3. **只改文字，不改行为。** 占位符、分支、i18n 结构、错误码、字段名一律不动。
4. **改文案必须同步改断言它的测试。** 测试没跑过不算改完。

## 二、术语表（全站统一，不得各写各的）

| 概念 | 固定写法 | 不许写 |
|---|---|---|
| MaaCore 子进程 | 内核 | 核心、MaaCore 核心 |
| 一次完整执行（pipeline） | 流水线 | 任务（在指代 pipeline 时） |
| 流水线中的一步（task） | 任务 | 子任务、步骤 |
| 定时触发的配置（schedule） | 定时任务 | 计划任务、日程 |
| 通知投递目标 | 通道 | 渠道（指通知时） |
| 账号客户端类型（官服/B 服） | 客户端渠道 | 通道 |
| Agent 的一轮 | 会话 | 对话、聊天 |
| 人工确认记录 | 确认 | 批准、授权（作名词时） |
| 重试动作 | 重试 | 再试、重新尝试 |
| 数据获取 | 读取 | 拉取、获取（界面文案里） |
| 加入集合 | 添加 | 新增、创建 |
| 新建实体入口 | 新建 | 创建（按钮文案） |
| 删除已保存实体 | 删除 | 移除 |
| 从列表/任务链去掉一项 | 移除 | 删除 |
| 让运行中的流水线停下 | 停止 | 中断、终止 |

补充：`设置` 指界面里的设置项，`配置` 指 `config.yaml`／环境变量；`一键轮换` 是内核既有模式名，
属于游戏术语，不改。

## 三、句式规则

1. **按钮**：动词 + 对象，2–6 字，不带「请」「点击」。破坏性按钮必须带对象（「删除通道」而非「确认」）。
2. **Toast**：「已 + 动词」，≤15 字，单句不加句末句号。
3. **空状态**：首行「还没有 X」（否定式只用这一种），第二行给「怎么开始」，整体 ≤30 字，带一个动作。
4. **错误提示**：`发生了什么 + 你能做什么`。特定动作失败用「{动词}{对象}失败：{原因}」，
   不再套一层「操作失败：」。兜底路径不许出现英文、原始 JSON、内部类名与机制名。
5. **确认弹窗**：标题 = 动词 + 对象 + 「？」，描述 ≤40 字、只写后果不写机制；不可撤销才写「无法撤销」。
6. **句末句号**：单句文案（按钮、标签、Toast、标题、字段说明）**不加**句末句号；
   两句及以上的说明保留句末句号。
7. **HTTP 状态码**：保留但排在句中，一屏最多出现一个，例如「没有权限执行此操作（403）」。
8. **人称**：默认省略主语；需要时用「你」，不用「您」「用户」。

## 四、`InfoHint` 约定

解释性文字（为什么这样、有什么前提、机制说明）不铺在界面上，收进标题或字段旁的小问号：

```tsx
// 说明性文字 → hint（点击/悬浮/聚焦展开）
<Section title="执行顺序" hint="到点后从上到下依次执行，只保存改过的参数。">
// 计数、时间、状态这类一眼要看到的 → description（保持可见）
<Section title="截图" description={`${items.length} 张`}>
```

可用的入口：`Section` 的 `hint`、`Field` 的 `description`（字段说明保持可见，属必要信息）、
`InfoHint` 组件本身（`web/src/components/ui/info-hint.tsx`）。
判断标准：**删掉这句话，用户会不会做错事？** 会 → 留在明面上；不会 → 进 hint 或直接删。

## 五、禁止清单（改写时逐条自查）

- `——`（破折号当冒号/插入语）；真正需要停顿的地方全篇 ≤3 处。
- 「A 而不是 B」「而非」「才是」——除非 B 是读者真会误解的选项。
- 「值得注意的是」「需要说明的是」「综上所述」「总而言之」「首先…其次…最后」。
- 营销词：旨在、致力于、赋能、助力、打造、一站式、全方位、轻松、丝滑、极致、便捷、无忧。
- 客服腔：很抱歉、感谢您的、请您、敬请、温馨提示、小贴士。
- emoji 装饰（✅⚠️❌🚀 等）、感叹号。
- `**加粗断言**` 用在普通叙述里（决策记录的关键结论、契约条款除外）。
- 英文兜底文案（`Request failed with status 500`、`WebSocket send failed`…）。
- 把 `JSON.stringify` 的结果当文案；把内部类名（`CoreClient`、`event_queue`、`AsyncCallInfo`）、
  里程碑号（`M22`）、文档坐标（`docs/05 §2`）、源码文件名写进用户可见位置。
- 「本模块」「这里」「下面这」式自指（注释里同样禁止）。

## 六、保留不改

`—` 作无值占位；`***` 凭据掩码；`「」` 中文引号；「正在加载…」；技术名词原文
（token/JSON/cron/cURL/HTTP/WebSocket/OpenAPI/ADB/VAPID/Agent/Copilot）；确认弹窗的疑问句标题；
错误提示里的 HTTP 状态码；统计与时间格式（「共 N 条」「今天 09:00」）；决策记录里的加粗结论与表格；
`maa_api/agent/knowledge/builtin/operator-classes.md` 的「词条 —— 释义」词典体；
知识库里的字段名、工具名、星级符号。

## 七、各表面附加要求

- **界面**：`Section description` 里凡是解释性的句子，改成 `hint` 或删除；删除后信息仍有用的进 hint。
- **对外消息**：`AppError` 的 message 面向网页用户，补「你能做什么」；实现细节进 `details` 或注释。
- **OpenAPI**：`summary` 写「做什么」，`description` 只写调用者需要知道的契约（参数约束、状态码语义、
  幂等性）；设计取舍、里程碑、源码考证移到代码注释或 docs。
- **Agent 提示词/工具描述**：祈使句，写「什么时候用我」，不写参数形状；同一约束只写一次。
- **知识库**：保持给模型读的精度（字段名、工具名、数值、以游戏内为准），只清营销形容词、
  跨文件重复段落、一句话塞八个要点的长句。
- **注释与 docstring**：写「为什么」，不写「我在哪个里程碑改的」；模块 docstring ≤15 行。
- **脚本输出**：去掉 ✅⚠️❌ 与总结腔，用「通过／警告／失败」。
