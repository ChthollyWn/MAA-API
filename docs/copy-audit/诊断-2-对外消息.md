# AI 味诊断：后端对外消息（错误 / 日志 / OpenAPI / 通知）

诊断对象是 `docs/copy-audit/清单-2-对外消息.md` 的 674 条，另加清单未收录、但在 `/docs`
与 API 调试台里真实可见的 132 条模型与字段 `description`。计数口径见文末附录。

---

## 1. 结论

### 1.1 四个表面的 AI 味程度（重 → 轻）

| 排序 | 表面 | 条数 | 严重度 | 主要病灶 | 规则命中 |
|---|---|---:|---|---|---|
| 1 | `openapi` | 135（+132 漏收） | **高** | 把仓库内部设计笔记搬进对外契约：里程碑代号、`docs/NN §x`、ADR 编号、pydantic/settings 实现取舍、"为什么这么设计"的辩护段 | 13 个 operation ＋ 22 条字段描述 |
| 2 | `api_error` | 319 | **中高** | 86% 只报状态不给下一步；21 条泄漏内部实现；28 条实现态泄漏（"X 服务尚未启动"）；同一规则多种措辞 | 内部实现细节 21、实现态 28、英文整句 2、标点混排 3、绝对化 17 |
| 3 | `log` | 183 | **中** | 负面级别占 68%，其中 22 条是预期内降级仍记 warning；41 条夹带内核/进程黑话；1 条中英混排 | warning+error+exception 124、内部标识符 41、半角标点 7 |
| 4 | `notification` | 37 | **低** | 文案本身合格（标题 7 个事件名 + 16 条工具动作全是人话）；病灶在调用方：用内部工具名当标题、正文退化成 JSON | 2（VAPID / Web Push，属必要术语） |

**一句话**：AI 味不在"用户看得见的地方说得多"，而在"该说人话的地方在写设计文档"——
`openapi` 是重灾区，`api_error` 是数量重灾区，`log` 是级别与黑话问题，`notification` 基本没问题。

### 1.2 专项判断：错误 message 做到「说清发生了什么 + 用户能做什么」了吗

**只做到一半，而且是偏的那一半。**

- **"发生了什么"做到了，常常说得比用户需要的更细**：319 条里 54 条是「X 不存在」、28 条是
  「X 尚未启动」、40 余条是参数与取值校验，状态描述本身清楚。
- **"用户能做什么"基本没做到**：只有 46 条（14%）含「请…」指引，其余 273 条（86%）只描述状态。
  典型是一条命令都不给的失败：`maa_api/services/device_service.py:707`「MaaCore 截图失败」。
- **有一批把对象搞错了：对用户讲开发者的语言**。`maa_api/core/client.py:717`
  「CoreClient 的异步方法必须在事件循环内调用（或在构造时传入 loop=）」
  ——这句话会原样出现在网页的错误提示里，而用户既没有 loop 也不知道 CoreClient 是什么。
- **措辞不统一**：同一件事两种写法（设置项 2 种、分页参数 3 种），有的像给用户看
  （`maa_api/services/queue_service.py:150`「任务队列已暂停，请恢复队列后再提交」），
  有的像给提交者看的 commit message（`maa_api/services/pipeline_runner.py:1044`
  「流水线执行器发生内部错误」）。

结论：**给后续改写的靶子是"86% 缺下一步"，而不是"全部重写"**。建议优先修 21 条内部实现泄漏
与 28 条实现态泄漏，这两类改完，用户可见的错误质量会有台阶式变化。

## 2. `api_error`（319 条）

### 2.1 判据

1. **对象判据**：这句话是给"网页上的人"看的，还是给"读代码的人"看的？后者必须重写。
2. **完整性判据**：是否同时给出「发生了什么」与「你能做什么」。改不了、也等不到的情形，
   至少给「去哪儿看原因」。
3. **一致性判据**：同一条业务规则在不同端点上是否同一句话。
4. **术语判据**：`event_queue` / `AsyncCallInfo` / `core_id` / `model_fields_set` / supervisor /
   CAS 这类词，用户的世界里不存在。
5. **长度判据**：一条用户提示 ≤ 40 汉字、≤ 1 个分号；参数明细放 `details`。

## 3. `log`（183 条）

### 3.1 判据

日志页是给用户排障的（`web/src/features/logs/LogEntry.tsx` 会展示级别、时间、正文，
展开后显示 logger 名）。所以：

1. **级别判据**：ERROR = 功能已坏且需人工介入；WARNING = 用户这次操作受影响、服务已自动处理；
   INFO = 用户能感知的状态变化；DEBUG = 只有写代码的人看得懂。
2. **黑话判据**：`supervisor` / `dispatcher` / `event_queue` / `Future` / `CMD_RESULT` /
   `AsyncCallInfo` / `claim` / `pid=` / `seq=` 属于 DEBUG 或改写。
3. **影响判据**：负面日志必须写「影响是什么 + 已怎样处理」，只写"失败了"等于没写。
4. **一致性判据**：全中文、全角标点、句式统一为「对象 动作：结果」。

| 位置 | 原文 | 级别 | 改法 |

## 4. `openapi`（清单 135 条 + 实测漏收 132 条字段描述）

### 4.1 判据：什么该留在 description

`/docs` 是**接入者的契约面**，不是设计评审稿。逐项判据：

| 内容 | 判定 | 理由 |
|---|---|---|
| 免鉴权、幂等、副作用、状态码与 `error.code` | **保留** | 接入者据此刻画调用逻辑 |
| 字段语义、取值范围、单位、坐标系、默认值来源 | **保留** | 没有它就没法正确调用 |
| 扩展键（`x-label` / `x-risk` / `x-depends-on`）与枚举标签 | **保留** | 接入者要按它渲染表单 |
| "为什么这样设计"、方案对比、被否决的替代方案 | **移出** | 属设计文档，进模块 docstring 或 `docs/13` |
| `M22 规格 §3.4`、`docs/05 §5.3`、`ADR-04`、`M17 起` | **移出** | 接入者拿不到这些文档，编号只制造噪声 |
| pydantic / settings 表读法 / 索引约束 / 内核源码文件名 | **移出** | 实现细节，随重构漂移 |
| `**加粗**`、`——`、`而不是` 对照句 | **移出** | 装饰性强调，契约文本不需要修辞 |

### 4.2 实测的可见面（比清单更糟）

- 101 个 operation 里只有 **23 个**写了 `description`，其余 78 个只有一行 `summary`——
  长文全部挤在 10 个端点上：`GET /api/tasks/types`（486 字）、`POST /api/system/auth/cookie`
  （484 字）、`GET /api/system/health`（459 字）、`DELETE /api/system/auth/cookie`（339 字）、
  `POST /api/tasks/validate`（320 字）。
- 清单漏收的 132 条模型与字段 `description` 才是重灾区：**22 条命中规则**
  （反引号 13、`docs/NN §x` 7、`而不是` 5、`——` 5、绝对化 4、`**加粗**` 2），
  最长一条 360 字。
- 因为显式 `description=` 优先级更高，被挡住的 docstring 有 5 处
  （`system.py:165/229/269`、`tasks.py:257/329`），它们与上面的 description **讲同一件事、
  措辞不同**，长期必然漂移；真正漏进 `/docs` 的 docstring 只有 4 处，
  其中 `agent.py:702` 是内部说明（见下）。

## 6. 对外文案规范

### 6.1 错误 message（`error.message`）

**硬约束**：≤ 40 汉字；≤ 1 个分号；不含括号内的参数明细（放 `details`）；
不含 `exc` / 数据结构 / 内部类名；不出现英文整句；全角标点；句中不夹 `，请…。` 之外的从句。

**模板（三选一）**

| 模板 | 句式 | 适用 | 正例 |
|---|---|---|---|
| T1 用户可自行修复 | `{发生了什么}，请{怎么做}` | 参数错、队列暂停、未配置 | 任务队列已暂停，请恢复队列后再提交 |
| T2 用户改不了、等一下会好 | `{发生了什么}，请稍后重试` | 启动中、重连中、冷却中 | 设备正在自动重连，请稍后再试 |
| T3 用户改不了、也等不到 | `{发生了什么}；{去哪儿看}` | 内核崩溃、写盘失败、归档失败 | 截图归档失败，图片未写入审计记录；详情见日志页 |

**反例 → 正例**

- ✗ `CoreClient 的异步方法必须在事件循环内调用（或在构造时传入 loop=）`
  → ✓ `服务内部调用出错，请重试；若持续失败，请到日志页查看最近一条错误`
- ✗ `MaaCore 截图失败`
  → ✓ `用内核通道截屏失败，请确认设备已连接；若持续失败可改用 ADB 通道`
- ✗ `{label}取值无效`
  → ✓ `{label} 不是支持的取值，可选：{候选值}`
- ✗ `page 必须至少为 1，size 范围为 1 到 200`
  → ✓ `page 不能小于 1，size 需在 1–200 之间`

**实现约定**：高频文案抽到一处常量（如 `maa_api/domain/errors.py` 旁的 `MESSAGES` 表），
按 `ErrorCode` 分组；同一 `ErrorCode` 在不同路由必须复用同一句。§2.3 列出的 4 组重复文案先合并。

### 6.2 日志级别与措辞

| 级别 | 什么时候用 | 句式 | 例 |
|---|---|---|---|
| ERROR | 用户要的功能已坏，且需要人工介入 | `{对象}{发生了什么}；{下一步}` | 内核回滚失败，当前仍在使用原版本；请到更新页重试 |
| WARNING | 用户这次操作受影响，服务已自动处理 | `{对象}{发生了什么}，已{怎么处理}` | 设备连接中断，已启动自动重连（第 2 次） |
| INFO | 用户能感知的状态变化 | `{对象}{动作}：{结果}` | 流水线 a1b2 已提交，共 3 个任务 |
| DEBUG | 只对开发者有意义（`supervisor` / `event_queue` / `Future` / `pid` / `seq` / `CMD_RESULT`） | 自由 | — |

三条额外约定：全中文、全角标点（现有 7 处半角冒号/句号要改）；
占位符一律写成「字段名=值」，不要把裸 `%s` 留在句尾；同类事件句式固定，方便用户扫读。

### 6.3 OpenAPI `description` 该写什么、不该写什么

**写**：一句话说明这个端点做什么；鉴权与幂等要求；副作用；成功状态码与响应形态；
会出现的 `error.code` 及触发条件；字段的取值范围、单位、坐标系、默认值来源。

**不写**：`M\d+-\d+` / `M\d+ 规格` / `docs/NN §x` / `ADR-\d` / 仓库内 spec 路径；
pydantic / settings 表 / 索引 / 内核源码文件名的实现取舍；"为什么不用另一种设计"的辩护；
`**加粗**` 与 `——`；"不是错误——…"这类对照句。

**形式**：`description` ≤ 8 行；超过 8 行说明该讲的内容属于字段描述或设计文档；
每个字段的 `description` ≤ 60 汉字，超了先拆字段说明、再砍设计史。
显式 `description=` 与函数 docstring 二者只留一份内容（现在是两份、措辞不同）。

### 6.4 通知标题与正文

- **标题**：`{对象}：{结果}` 或 `{动作}（{影响}）`，≤ 18 汉字，禁止标识符。
  例：`任务执行完成：日常刷剿灭`、`需要确认：执行任务（刷理智 · 源石 ×3）`。
- **正文**：首行给结论，第二行给影响或下一步，之后才是明细；≤ 5 行、每行 ≤ 40 汉字。
  例：`3 项全部成功\n用时 12 分 30 秒`；失败时 `1/3 成功，1 项失败\n失败原因：设备未连接\n到流水线页查看详情`。
- **禁止**：把 payload JSON、`error_code`、trace id 当作正文；
  允许出现的唯一技术标识是用户自己起的名字（流水线标题、设备地址）。

## 8. 面向第三方接入者的文档口吻（`docs/14-开放API接入指南.md`）

这份文档整体质量高于代码内文案（有 Base URL、鉴权矩阵、可跑的 shell、WebSocket 协议表），

3. **§3 缺少可执行的重试判据**：只说了「按 `error.code` 决定是否提示、等待状态变化或修正参数」，
