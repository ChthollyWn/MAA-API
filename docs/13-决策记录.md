# 决策记录

## 1. 有实质权衡的决策

### ADR-01 · 前端选 Vite + React 而非 Next.js

讨论中曾考虑"改成纯 Next.js 前后端不分离"。否掉它的根本原因是后端搬不走：MaaCore 只提供 C API 与官方 Python 绑定，任务调度、ADB 操作、APK 安装全部依赖 Python，Node 里没有 MaaCore 绑定。因此 Next.js 不可能吃掉后端，只能做一层 BFF。

这让"不分离"只剩两种真实形态。静态导出（`output: 'export'`）确实能做到单进程单端口，但 Server Components、API Routes、middleware、SSR、ISR 全部失效，此时 Next.js 相对 Vite + React 的唯一增益是文件路由约定，代价是更重的工具链。独立 Node 服务加代理则把进程从一个变成两个、Docker 镜像要同时装 Node 与 Python，实质上比现在更"分离"；它唯一的实质收益是能把 `access_token` 藏进 httpOnly cookie。

决定性因素是 WebSocket。既然选了 WebSocket 推实时日志，而 Next.js App Router 没有原生 WebSocket 支持，独立 Node 服务方案要么自建 custom server 转发、要么让浏览器绕过代理直连后端（代理就失去意义）。加上移动端优先这一项 Next.js 也无加成，所以选 Vite + React：能达成单进程不分离，Tailwind 写移动端响应式最顺手。

### ADR-02 · MaaCore 用子进程隔离，而非同进程热替换

内核热更新有四种可能路径，选了工程量最大但唯一优雅的一种。

同进程 `dlclose` 加 `dlopen` 真热重载被否：`dlclose` 在有活跃线程和未释放句柄时行为未定义，MaaCore 也不保证支持重复加载，段错误风险高且无法测试覆盖。下载后自动重启整个服务进程可靠但 API 会中断，前端要处理重连，且正在进行的其他请求全部失败。只下载不重启、提示手动重启，等于没有实现"热"更新。

子进程隔离一次性解决了三个问题：内核更新只重启子进程、native 崩溃不再拖垮 API 服务、启动期不再被网络 IO 阻塞。代价是执行层需要重写、回调要跨进程传递。考虑到崩溃隔离与启动解耦这两项收益本身就是现有架构的痛点（`scheduler.py` 在 import 阶段连 ADB、失败则服务起不来），这个代价是值得付的。

### ADR-03 · IPC 用 multiprocessing Queue

候选还有子进程内跑轻量 HTTP 服务、Unix domain socket 加自定义协议、以及 ZeroMQ 或 gRPC。

选 Queue 的理由是同一代码库、同一依赖、对象直接传递，实现成本最低，且 `Queue` 的 pickle 序列化对纯 dict 消息完全够用。子进程内跑 HTTP 服务边界最清楚、未来能把内核挪到其他机器，但为单机双进程引入一整套 HTTP 栈属于过度设计。UDS 需要自定义消息分帧，ZeroMQ 与 gRPC 各多一个重依赖。

已知代价是截图这类大 payload 走 Queue 有性能开销（1280×720×3 约 2.7 MB，pickle 加管道往返数十毫秒），处理办法是落盘传引用，并预留 `shared_memory` 作为后续优化（见 [02-系统架构设计 §3.3](./02-系统架构设计.md)）。

### ADR-04 · 响应格式全面改标准 HTTP 状态码

现状是所有接口返回 HTTP 200，业务码在 body 的 `code` 字段（10200 / 10400 / 10401 / 50000）。这是一次破坏性变更，选它而非"新接口用新格式、旧接口保持兼容"。

理由是这次重构本身已经废弃了全部旧前端与旧接口路径，没有需要兼容的外部消费者；而保留两套格式会让错误处理、OpenAPI 文档、agent 的错误判断都要分叉。既然开放 API 是明确目标，就应该一次做对 —— agent 依赖 HTTP 语义判断成败，"一切都是 200"会让它无法区分成功与失败。

错误体选自定义结构 `{"error": {"code": "...", "message": "...", "details": {...}}}` 而非 FastAPI 默认的 `{"detail": "..."}` 或 RFC 9457 Problem Details。自定义结构的核心价值是那个可枚举的错误码字符串：agent 能据此做确定性分支（`CORE_NOT_READY` 该等待、`DEVICE_NOT_CONNECTED` 该重连、`CONFIRMATION_REJECTED` 不该重试），而人类可读的 `message` 做不到这一点。

### ADR-05 · 不复用 feat/0515 分支的代码

该分支已实现服务日志接口、三种更新接口、多渠道鉴权、配置模板与懒加载，看起来能省一大半后端工作。但它是在旧架构（同进程内核、内存状态、业务码响应）上写的，与子进程隔离、SQLite 持久化、标准状态码三项决策全部不兼容。迁移它的代码等于先理解再改写，成本不低于重写，还会带入旧架构的隐含假设。

但其中已验证的**外部接口常量**必须沿用：官服 APK 下载直链、B 服 biligame 接口及其 `game_base_id`、两个渠道的包名、`dumpsys` 解析版本号的正则。这些是有人花时间试出来的事实，重新查证只会浪费时间。

### ADR-06 · 鉴权维持单 token

选了单 `access_token` 加四渠道传递（Bearer / `X-Token` / query / cookie），否掉了 API Key 体系与限流。理由是单用户自用场景，多 key、命名、吊销、权限范围都是无人使用的复杂度。



### ADR-07 · Agent 的画面理解只用截图，不接 OCR

核实确认 MaaCore 的 OCR 没有独立 C API —— 内核内置 `libfastdeploy_ppocr`，但只能通过 `tasks.json` 的 task 定义间接触发，无法直接调用"识别这块区域的文字"。

因此 agent 要理解画面只有两条路：多模态模型看截图，或项目自己另接一个 OCR（PaddleOCR / RapidOCR）。选了前者，理由是不引入重依赖（OCR 模型文件与推理运行时体积可观），且多模态模型对"当前在什么界面"这类整体判断比 OCR 的文字碎片更有效。

代价是内置 agent 必须配置支持视觉的模型，纯文本模型只能做任务编排。这个约束会在设置页明确提示，并提供能力自检。另一个代价是识别准确率未经验证，因此 [12-实施计划与里程碑 §5](./12-实施计划与里程碑.md) 要求在 M11 阶段就手动验证模型对游戏界面的理解能力，而不是等到 M13。

### ADR-08 · 自定义任务开放到最强层级

允许 agent 通过增量资源机制注入自定义 `tasks.json` task 定义，这是 MAA 的底层任务 DSL（模板匹配、OCR、点击偏移、任务跳转）。这也是"应对 MAA 未适配的新活动"这个场景唯一的可行路径 —— 纯原子操作无法固化成可复用的能力。

风险是格式错误的 task 定义可能让 `AsstLoadResource` 失败，而资源加载失败意味着内核不可用，这是少数能真正搞坏服务的操作。因此配了四层防护：注入前 schema 校验、自定义资源与官方 OTA 缓存目录分离（便于一键清空）、加载失败自动回滚并重载、task 名强制带 `Custom_` 前缀（不允许覆盖官方定义）。

即便如此，这一层仍归入需人工确认的 `DANGEROUS`。曾考虑收紧为"只允许前端上传、agent 只能引用已有的自定义 task"，已确认不采纳 —— 见 §3 的对应条目。

### ADR-09 · 队列按优先级排序但不抢占

三个来源（前端手动、agent、定时任务）争夺唯一内核实例。选了统一队列加优先级排序，否掉了"正在跑就直接拒绝"（现状）、纯 FIFO、以及前端手动可抢占三种方案。

否掉现状是因为它让定时任务与 agent 在冲突时静默失败。否掉纯 FIFO 是因为人在界面前点按钮的期待与后台定时任务不同。否掉抢占是因为中途打断正在执行的 MAA 任务可能让游戏停在不确定的界面状态，恢复成本高且难以预测。

用户想立刻插队时需要显式停止当前流水线再提交，这是前端的一个明确按钮而非隐式行为。同时 `stop_pipeline` 被刻意设为 agent 免确认的工具，确保发现异常时能及时刹车。

### ADR-10 · 单子进程但按多实例设计接口

首版只跑一个 MaaCore 子进程、绑一台设备，维持"不允许多实例"的现有语义。但内核调用统一经 `CoreRegistry.get(core_id)`，`pipeline` 表带 `core_id` 字段，REST 路由预留 `?core_id=` 参数，`DeviceManager` 按 `core_id` 维护独立状态。

这么做的成本很低（多传一个恒为 `"default"` 的参数），收益是将来扩展到多设备或多账号并发时，路由层与数据模型不需要改动，只需实现 `CoreRegistry` 的多实例管理与设备绑定配置。相比之下，如果先写死单实例，多设备需求到来时数据库要加列、全部路由要改签名。

### ADR-11 · 原子操作改会话级授权，不逐次确认

原子操作（点击坐标、滑动、输入文本、按键）不属于"消耗类"或"破坏类"，但它们绕过 MAA 的全部识别与容错，点错位置可能触发任意游戏内操作。最初设计把它们归入需逐次确认。

否掉逐次确认是因为它让"卡死救援"这个核心场景不可用 —— agent 从未知界面复位可能需要连续几十次截图与点击，每次弹卡片等于让用户手动操作一遍。也否掉了完全免确认，因为那等于把无约束的屏幕控制权交给 LLM。

选定的方案是会话内首次尝试时弹一次授权确认，批准后该会话获得一个默认 15 分钟的窗口（可配，上限 60 分钟）。四条约束限制它的影响面：授权粒度是"会话加时间窗口"而非全局开关；只覆盖原子操作，消耗类与破坏类仍逐次确认；随时可撤销且前端常驻提示条显示剩余时间；审计不降级，每次操作照常落库并记录凭哪次授权执行。

授权状态落库而非只存内存，因为服务重启后不应悄悄延续一个用户以为早就结束的授权。详见 [11-Agent模块设计 §4.3](./11-Agent模块设计.md)。

### ADR-12 · 活动资源两条通道首版都做

核实推翻了"官方 OTA 不止 `tasks.json`"这个前提：`api.maa.plus` 的资源树对国服只有一个 `tasks.json`，而现有代码已经在拉它。这意味着只做通道 A 等于把现有功能重做一遍 UI，拿不到任何新资源，需求 3 的"活动资源热更新"会名存实亡。

因此首版同时实现通道 B（`MaaResource` 仓库），它才是 MAA 桌面客户端"资源更新"按钮背后的机制，含地图坐标、关卡表、公招数据与模板图。下载走 GitHub 仓库压缩包而非 Mirror 酱 —— 后者的版本查询免费但下载需要付费 CDK，不适合作为首版的硬依赖（它仍被用作 `raw.githubusercontent` 不可达时的版本查询兜底）。

代价是每次更新要拉一个全量包：实测压缩包 13.3 MiB、解压后 107 MB。因此先查 `version.json` 的 `last_updated` 再决定是否下载，无更新时的开销只有一次约 100 字节的 JSON 响应；镜像回退链与内核更新共用，含可配置的加速前缀。通道 B 标记为 `required=False`，失败时退回内核自带资源，功能不缺失只是滞后（实测滞后约 9 天）。

落点选了一个独立目录而非直接覆盖 `<maa_path>/resource/`。覆盖式落点更简单，官方给手动更新用户的指引也是这么做的，但它会被内核更新解压覆盖掉，每次升级内核都要重新同步一遍。代价是加载链从两层变四层，`LOAD_RESOURCE` 命令的签名必须从单个增量路径改为有序列表。

**这个独立目录连同另两个增量层一起放在 `<maa_path>` 之外**，落在 `resource/maa-layers/{repo,cache,custom}/`（与 `resource/lib/` 平级）。中间一版曾把三层放在 `<maa_path>` 下，沿用 MAA 官方 SDK 示例把 OTA 缓存写进 `<maa_path>/cache/` 的习惯，但那样内核更新的原子替换会连带清空三层——`repo/` 与 `cache/` 重下即可恢复，`custom/` 没有远端副本、属于永久丢失。补救方式是在替换后把三个目录从备份搬回新目录，但这给内核更新增加了一条必须成功的迁移步骤与对应回滚路径，迁移出错就静默丢数据。移出 `<maa_path>` 之后该故障类别整体消失，内核更新不需要任何迁移步骤，顺带也解开了 `<maa_path>/cache/avatars/`（内核自建的头像缓存）与通道 A 落点共用同一目录的纠缠。这样做不违反任何内核约束：`AsstLoadResource` 只接受一个路径并去读 `<path>/resource/`，增量层在磁盘上的位置自由，唯一的硬约束是基础资源必须是第一次调用（`ResDir` 由首次调用永久钉死）。代价是偏离官方示例的目录习惯，但路径本就由我们传入。

通道 B 的备份**只保留最近一份**（每份 107 MB，通道 A 的"保留 5 份"策略照搬会吃掉半个 G）。代价是只能回退一步：GitHub 的分支压缩包只给当前 HEAD，取更早的版本要按 commit 拉 `/archive/{sha}.zip`，首版不做。考虑到通道 B 同步的是数据文件而非会写坏行为的 task 定义，需要连退多版的场景很难构造。

合并语义已通过核对 `ResourceLoader` 源码确认（数据文件整文件替换、模板图按文件覆盖、增量目录允许残缺），但源码与本地内核未必同一构建线，仍列了三项待实测假设与退路。详见 [07-热更新方案 §3.3](./07-热更新方案.md)。

### ADR-13 · 首版就上 Tailscale Serve 作为 HTTPS 入口

PWA 的 Service Worker 与 Web Push 要求安全上下文，局域网 IP 加 HTTP 不满足。原方案是三段式递进，首版接受降级。

改为首版直接上第二段（Tailscale Serve），理由是降级形态下**推送不是"体验变差"而是"功能不存在"** —— 而 agent 的人工确认恰恰是最需要即时触达的事件，靠邮件兜底的延迟会让确认窗口形同虚设（相关的超时取舍见 ADR-14）。自签证书加手动信任被否（iOS 要装描述文件并在两处开关里启用），浏览器标志绕过被否（Android 上需要 root，而移动端是主场景）。

代价是每台访问设备要装 Tailscale 客户端并登录同一 tailnet。这同时是一项收益：不在 tailnet 内的设备连端口都摸不到，实际上比单 token 鉴权更强。

非安全上下文的分级降级仍然要实现，定位从"首版形态"改为"客户端未连通时的兜底"。详见 [09-前端重构方案 §12.4](./09-前端重构方案.md)。

### ADR-14 · 确认超时按风险分级，并为 Chromium 做推送按钮

原定确认超时统一 120 秒。这与推送触达的链条长度不匹配 —— 用户要听见、解锁手机、点开应用、读完卡片再决定，结果是高风险操作几乎总是超时自动拒绝。

改为分级：消耗类与破坏类默认 10 分钟，原子操作的会话授权保持 120 秒，两者可配置。否掉了统一放长（会让一个已经没人管的授权请求长时间挂着）与完全不设超时（agent 调用无限期挂起，避免调用无限期挂起）。

同时为 Chromium 平台做推送上的「准许 / 拒绝」按钮作为渐进增强，但**流程不以它为前提**：核实确认 WebKit 完全忽略 `actions`，iOS 与 macOS Safari 都不渲染按钮，且它还忽略 `requireInteraction`（通知不常驻）。两个平台共有的路径只有"点通知体 → 深链回卡片 → 应用内批准"。

这个决策连带暴露了一个鉴权冲突：从推送按钮批准要在 Service Worker 里发 `POST`，而 Service Worker 读不到 localStorage（非 window 上下文），同源自动携带的 cookie 又被 §3 的决策限制为不能用于写操作。解法是 token 增加一份 IndexedDB 副本供 Worker 读取并注入 `X-Token` 头，而不是给 cookie 开写操作特例 —— 开特例等于在最容易被忽略的路径上永久留一个 CSRF 口子。代价是三处存储的写入与清除必须同步，否则会出现"页面已登出但通知按钮还能批准操作"。详见 [09-前端重构方案 §13.2](./09-前端重构方案.md) 与 §10.1。

## 2. 其余决策速记

| 决策 | 选择与理由 |
|---|---|
| 移动端优先 | 实际使用场景是在手机上远程操作，底部 Tab 单手可达，桌面自适应即可 |
| PWA | 可添加到主屏、离屏缓存、推送确认通知。约束是需要安全上下文，见开放问题 |
| WebSocket 而非 SSE | 需要双向通道（确认响应、订阅管理），且 agent 事件推送可复用同一连接 |
| 三路日志全要 | 排查问题时任务日志、服务日志、内核 debug 日志缺一不可，分标签页展示 |
| 活动资源清单驱动 | 两条通道的获取方式不同（单文件条件请求 vs 仓库压缩包），显式清单让新增条目不必改代码，外服支持将来只需补条目 |
| 内核只用 stable | 挂机场景稳定性优先。内核是整个服务的地基，一个行为异常的预发布版本造成的排查成本远高于早几天适配新活动的收益。保留枚举与落库字段以便将来放开 |
| 生息演算修复后支持 | `ReclamationTask` 因参数字典把变量当成键而从未可用，在 M0 一并修掉，9 种任务类型全部支持 |
| 游戏更新带版本对比 | 没有版本对比就无法判断是否需要更新，只能盲目下载数 GB |
| ADB 四时机重试 | 启动等待、任务前预检、断线自动重连、手动重连各自解决不同失败模式 |
| ADB 失败不阻塞启动 | 配合内核懒加载，让服务可用性不依赖模拟器是否已启动 |
| 仅官服加 B 服 | 实际只用这两个，支持台服与国际服是无人使用的复杂度 |
| 渠道全局默认可覆盖 | 日常只用一个渠道，但保留单任务覆盖以应对特殊情况 |
| 单账号 | 无多账号需求，`account_name` 参数仍保留可用 |

## 3. 细化过程中浮现并已拍板的问题

这些问题在细化方案时浮现，不属于最初的决策范围，已逐项确认。记在这里是为了留下"为什么是这样"的依据。

**自定义 task 注入允许 agent 自主生成，但需确认。** 确认卡片展示完整 JSON。备选的"只允许前端上传、agent 只能引用已有的"被否，因为那会削掉"应对 MAA 未适配的新活动"这个目标场景的核心能力。已知的不足是长 JSON 在手机上审阅困难，缓解手段是 ADR-08 的四层防护（schema 校验、目录隔离、失败回滚、`Custom_` 名称前缀）而非事前人工审阅。详见 [11-Agent模块设计 §7.3](./11-Agent模块设计.md)。



**`AsstGetItemName` 不纳入。** macOS 版 `libMaaCore.dylib` 导出了这个符号，但头文件里完全没有声明，参数与返回语义只能靠逆向推测；且 Linux 版根本没导出它，纳入了在部署环境也用不上。掉落物品名称改从 MAA 资源目录的 `item_index.json` 读取。详见 [03-MaaCore内核层设计 §1.2](./03-MaaCore内核层设计.md)。

**cookie 渠道收窄，WebSocket 鉴权按客户端类型拆分。** 这两项都偏离了"四渠道等价"的原始决策，确认后实施。

cookie 只允许 `GET` / `HEAD` 与 WebSocket 升级，写操作必须走 header 或 query。需要说明的是 CSRF 风险本身已被 `SameSite=Lax` 挡住大半（跨站 POST 不携带 cookie），所以这层收窄属于深度防御而非必需 —— 采纳它的实际收益是让"写操作必须显式带凭据"成为一条简单且无例外的规则，不必依赖 cookie 属性配置正确。

WebSocket 方面，浏览器的 WebSocket API 无法自定义 header，只剩 query 与 cookie 两个选择。浏览器走 cookie（token 不进 URL，避开代理与日志记录），agent 与脚本走 query（无 cookie 容器，且实现简单）。详见 [05-API规范与路由清单](./05-API规范与路由清单.md) 与 [06-实时日志与WebSocket](./06-实时日志与WebSocket.md)。

**MaaCore debug 日志只落 `WARNING` 及以上。** 这一路密度极高（运行期每秒数条），且内核自己的 `asst.log` 里已有完整副本。全量经 WebSocket 实时推送保持不变，只是落库设阈值；需要翻更早的完整 debug 日志时由接口 tail 文件。阈值做成可调配置。这偏离了"三路全部落库"，确认后实施。详见 [04-数据模型与持久化](./04-数据模型与持久化.md) 的保留策略一节。

**内核命令超时返回 504 而非 502。** 区分的价值不只是语义精确：502 表示下游明确答复"办不成"，而 504 表示下游没答复、操作**可能已执行一半**，两者的正确处置不同 —— 504 后应当查状态而非重试，盲目重试可能把同一个任务提交两遍。因此前端的重试策略必须把 504 排除在自动重试之外（见 [09-前端重构方案 §10.3](./09-前端重构方案.md)），这是采纳 504 后连带的必要改动。

同一规则应用到 `LLM_TIMEOUT`（同样是上游未在时限内响应），也改为 504；`UPDATE_DOWNLOAD_FAILED` 保持 502，因为下载中断是传输层给了明确结果而非没答复。判断依据统一为"有没有收到答复"，不是"失败得有多严重"。详见 [05-API规范与路由清单 §2.4](./05-API规范与路由清单.md)。

## 4. 待补齐的契约缺口

这些是文档细化过程中暴露的接口契约缺口，不需要你拍板，但实现时必须补齐，否则对应功能不完整。

**缺少登出端点。** 如果 WebSocket 鉴权采用 cookie 方案，cookie 会被设为 HttpOnly（否则 XSS 可直接读取），而 HttpOnly cookie 前端 JavaScript 删不掉。结果是用户"登出"后 cookie 仍在，WebSocket 依然能连上。需要补一个由服务端清除 cookie 的端点（如 `DELETE /api/system/auth/cookie`）。

**`x-risk` 的 OpenAPI 扩展关键字尚未定义。** 参数 schema 需要标记哪些字段属于消耗类（`Fight.stone`、`Fight.medicine`、`Recruit.expedite`、`Mall.shopping`、`Roguelike.investment_enabled`），供前端在表单上给出醒目提示。这份清单必须与 agent 侧 `PolicyEngine` 的判定规则（见 [11-Agent模块设计 §4.1](./11-Agent模块设计.md)）共用同一处定义，否则会出现"前端不提示但 agent 要确认"或反之的不一致。

**`x-widget` 的取值集合需要扩充。** 几个结构化参数无法用基础控件表达：`Fight.drops` 是物品 id 到数量的映射、`Recruit.recruitment_time` 是 Tag 等级到分钟数的定长映射、`Infrast.facility` 是有序列表（顺序即换班顺序，不是普通多选）。需要追加 `item-count-map`、`duration-map`、`ordered-list` 三种控件类型，前端据此渲染专用编辑器。详见 [09-前端重构方案](./09-前端重构方案.md) 的动态表单一节。

## 5. 需要实测验证的假设

以下几条是文档里基于头文件、二进制符号或上游源码推断、但本地没有运行样本可以确证的设计前提。它们不阻塞开工，但必须在对应里程碑动手前用最小脚本跑一次，否则会照着错误的假设写实现。

**`AsyncCallInfo` 回调的载荷结构。** 迁移到 `AsstAsyncConnect` 的设计依赖这个回调来判定异步连接的最终结果，方案为它设计了两级 Future（外层等 `async_call_id` 返回、内层等回调送达结果）。但本地调试日志里没有这个回调的样本，`details` 里的字段名（`async_call_id` 与 `ret` 的实际键名与嵌套层级）只能从头文件推测。需要在 M1 动手前跑一个最小脚本，实际触发一次异步连接并打印原始回调 JSON。详见 [08-ADB连接与账号渠道](./08-ADB连接与账号渠道.md)。

**本地内核的构建来源。** 本地头文件带有 `ClientType` 相关注释而上游 `dev` 分支没有，加上 macOS 库导出了头文件未声明的 `AsstGetItemName`、而 Linux 库连 `AsstGetMapLevelKey` 都没导出，三条线索都指向本地库不是同一条发布线的构建产物（疑似 `dev-v2`）。这个结论的影响面超出单个 API：如果本地是非发布构建，那么文档里所有"某 API 可用"的判断都应改为运行期能力探测而非静态假设。方案已按平台探测加优雅降级来写（见 [03-MaaCore内核层设计 §1.2](./03-MaaCore内核层设计.md)），但建议在真机上核对一次内核版本号与构建信息。

以下四条是通道 B 带来的，都在 M7 动手前一并验证（见 [12-实施计划与里程碑](./12-实施计划与里程碑.md) M7），验证不通过时的退路是放弃独立目录方案、改为覆盖式落点。

**增量资源的合并语义在本地内核上成立。** 核对 `ResourceLoader` 源码得出三条结论：增量目录缺文件会被静默跳过而非判失败、数据文件是整文件替换、模板图按文件覆盖而非整目录替换。第三条最关键——若实际是整目录替换，加载通道 B 会让内核从 2464 张模板图掉到 1009 张，后果是大面积识别失败。但源码读的是发布线分支，而本地库疑似另一条构建线（见上一条）。验证方法：按完整链条加载后，确认一个只存在于通道 B 的 `Arknights-Tile-Pos` 条目能解析，同时确认一个通道 B 没有、只在内核自带 `template/` 里的模板仍可用。

**`TilePack` 重载时会清空既有条目。** 它把每个关卡的文件路径解析为"被加载的 `overview.json` 所在目录 + filename"并追加进列表。通道 B 的 `Arknights-Tile-Pos/` 实测是本地的严格超集，所以路径整体重定向本身安全；但若列表在重载时不清空，同一关卡会留下两条记录。

**重载后模板匹配缓存会失效。** `TemplResource` 有一个 revision 计数用于通知匹配器丢弃缓存，需要确认重载确实让它递增。否则运行中热重载会继续拿旧图做匹配，表现为"更新成功但行为没变"，且极难归因。

**整条加载链的重载耗时。** 只有通道 A 时是几百毫秒，加上 107 MB 的通道 B 目录后未知。[02-系统架构设计 §3.4](./02-系统架构设计.md) 把 `LOAD_RESOURCE` 的命令超时从 120 秒上调到 300 秒是按最坏情况留的余量，不是测量结果；同时 [03-MaaCore内核层设计 §4](./03-MaaCore内核层设计.md) 的心跳阈值在这条长命令执行期间需要放宽多少也取决于这个数。测出来后两处都可以回调。

## 7. 全部决策已确认

至此没有待你拍板的事项。§6 的默认值与下面两项在方案里都已定稿，只是取值可按实际使用回调。

**更新检查：每天自动一次，只检查不下载，有更新则通知；并保留手动「立即检查更新」入口。** 下载与安装始终手动触发。理由是"有更新"和"现在适合更新"是两件事 —— 内核更新要重启子进程、游戏包 1.8 GB 可能在移动网络下产生费用、通道 B 要下 107 MB，时机该由人定；而只做检查几乎没有代价。配套约束是通知要合并（三个目标一条）且同版本只通知一次，否则会连续多天收到同一条提醒而最终去关掉通知。检查失败只记日志不推送，手动检查的失败则必须在界面报错。详见 [07-热更新方案 §5.6](./07-热更新方案.md)。

**`InfrastTask.threshold` 以 0.3 为期望值**，现有代码签名里的 `0.5` 是错的。但新模型仍不设服务端默认值（`default=None`）：不传则由内核用自己的默认值，0.3 只作为 OpenAPI `description` 与前端占位提示里的说明文案。这样内核将来调整默认行为时服务端不会产生偏差。详见 [01-重构总览与现状评估](./01-重构总览与现状评估.md) 的缺陷清单。

## 8. 实施后的偏离、补充与待验证事项

### 8.1 实施偏离

**M6 · MAA 路径的在线修改与只读约束冲突，待拍板。** [12 的 M6](./12-实施计划与里程碑.md) 要求"改 MAA 路径重启子进程"，而 [04 §11](./04-数据模型与持久化.md) 与 [05 §4.13](./05-API规范与路由清单.md) 把 `app.maa_core_path` 定为只能由 `config.yaml` 或环境变量设置的只读项。实施按后者执行，设置 API 中该项只读（`maa_api/settings.py`）。是否开放在线修改仍待决定；若开放，需要补一条"修改后重启子进程"的热生效路径。

**已拍板（M14 开工前）：保持只读。** `app.maa_core_path` 继续只能由 `config.yaml` 或环境变量设置，在线修改保持 409/只读语义，不新增「保存后重启子进程」的热生效路径。这样 12 号文档 M6 的那句要求作废，[12](./12-实施计划与里程碑.md) 的 M6 条目按本裁决理解。理由：内核路径变更会同时影响已加载的资源层、正在排队的任务与 per-run Copilot 快照根目录，热改需要一条跨模块的迁移路径，而实际使用中换内核路径是低频操作，改配置重启服务足够。

**M10 · 手动 REST 的强制原子操作尚未接入 Agent 审计。** `force=true` 绕过流水线互斥时，`/api/device/*` 与 `/api/core/back_to_home` 的手动 REST 路径只写强制介入警告日志，不创建 `agent_audit` 记录；这不同于 [02 §5.3](./02-系统架构设计.md#53-原子操作的并发) 与 [05 §6.3](./05-API规范与路由清单.md#63-device) 早期方案中未区分调用渠道的审计表述。本文档据此限定为手动 REST 路径的现状；Agent 工具调用仍按 M11 的 Agent 工作流审计契约描述与实现。

### 8.5 M13 Task 4：core incident key 与启动恢复的代际隔离

`CoreSupervisor.generation` 每次服务进程启动会重置，因此 core incident 的持久 key 增加 lifespan 级 boot UUID：`core:<core_id>:<boot_uuid>:<generation>`。同一服务生命周期内按该 key 去重，进程重启后不会把新一代崩溃误判成旧事件。

数据库 `pipeline.core_epoch` 本身不包含 boot ID，idle crash 归并因此只查当前 PipelineRunner 在本次生命周期中记录的 CORE_CRASHED pipeline ID，并再次限定 core ID 与 generation。PipelineRunner 在开始 claim 查询前先登记当前代际；拿到 pipeline 后，在加载任务和提交事务前公布 claim ID/epoch 的普通值副本，避免 rollback 后访问过期 ORM 实例。claim 成功时将暂存的同代 crash 交给该 pipeline；claim body、commit 或 session context exit 失败时先尝试两次把可能已提交的 RUNNING claim 退回 PENDING。释放成功后，在 claim marker 清除后把暂存崩溃作为 idle core incident 处理；释放失败时终结该流水线，并保留 generation 到 pipeline 的 coalescing 关联，直到同代下一个 claim 或当前服务进程结束。claim 清理期间及 incident 现场生成前排队到事件循环的 core crash 会先把该流水线修正为 `CORE_CRASHED`，再以 `pipeline:<id>` 单一 key 生成诊断会话，避免初始上下文固化为领取错误或另建 core key。无 crash 而 claim 释放失败时同样终结为领取失败并创建 pipeline incident。若 callback 在 `_active` 创建前到达，会让该 pipeline 以 `CORE_CRASHED` 终结，避免 callback 顺序竞争创建两条 incident。已收到的 core crash 优先于同一窗口内的取消请求；若 FATAL 与取消、定时任务延迟或其他流水线终态提交并发，PipelineRunner 会把同一流水线修正为 `CORE_CRASHED`，再由 pipeline incident key 去重。进程启动恢复的旧 RUNNING pipeline 仍通过 pipeline incident key 处理，但不会被新 boot 的 idle core crash 查询误命中。

如果 `pipeline:<id>` 诊断已经开始后才收到同代际晚到 FATAL，PipelineRunner 仍更新原 pipeline，不影响新代际的 active pipeline；`AgentIncidentService` 在同一会话追加一条带 `pipeline:<id>:core:<generation>` 去重标记的现场更新和说明，不创建第二个会话或另一个 core key。会话详情、消息列表通过 `incident_context_updated` 事件刷新。

若 incident 创建时没有完整 LLM 配置，`agent_session.model` 使用 `unconfigured` 占位、`base_url` 置空并保存 assistant 错误说明。用户修复配置后继续该 incident session 时，用当前有效 model/base URL 填充并持久化占位；已有有效 model/base URL 快照不随设置变化而覆盖。

### 8.9 M14：Web Push 的实现方式与偏离

M14 交付 Web Push 全链路（VAPID 密钥、订阅 API、投递、Service Worker 的 `push` / `notificationclick`、设置页入口、确认卡片深链）。相对 [09 §13.1](./09-前端重构方案.md) 的方案有三处实施调整：

- **不用 `pywebpush`，改用既有直接依赖 `cryptography` 自实现。** 需要的原语（ECDH P-256、HKDF-SHA256、AES-128-GCM、ES256 签名）全部具备，而本机网络对 PyPI 不稳定（实测 pip 装包在 SSL/代理上反复失败），把新增运行时依赖做进安装步骤等于给构建加一个单点故障。正确性由 **RFC 8291 Appendix A 的官方向量**锁定：固定的 `as_private` / `ua_public` / `auth_secret` / `salt` 必须复现附录列出的全部中间值与最终 86 octet 头 + 密文。
- **HKDF 必须手写 extract / expand 两步。** `cryptography` 的 `HKDF.derive()` 是 RFC 5869 的 extract+expand 组合，而 RFC 8291 §3.4 的 `PRK_key = HMAC(auth_secret, ecdh_secret)` 与 `PRK = HMAC(salt, IKM)` 都是「只做 extract」的语义。用 `derive()` 替换会额外多做一次 expand：结果全错且**不抛任何异常**。测试里保留一条断言同时验证「官方向量通过」与「`derive()` 会得到不同的值」，去掉修复即变红。
- **Service Worker 从 `generateSW` 换成 `injectManifest` + 自写 `web/src/sw.ts`。** 生成的 Worker 没有 `push` 事件处理，而 Web Push 的通知完全依赖它（`userVisibleOnly: true` 要求每次推送都显示可见通知，否则订阅会被撤销）。因此 `vite.config.ts` 改用 `strategies: 'injectManifest'`，`navigateFallback` 与 denylist 语义由自写 Worker 用文件内常量复现（`frontend_smoke.py` 仍在断言产物里排除 `/api`、`/docs`、`/redoc`、`/openapi.json` 的导航）。预缓存改用 Cache API 自实现，同样不引入 Workbox 运行时依赖。

**一个只在构建产物里出现的缺陷，已修并加了守卫。** `injectManifest` 注入的清单 URL **不带前导斜杠**（`assets/foo.js`、`index.html`），而 `URL.pathname` 一定带；直接比较会让 `install` 里 `cache.addAll([])` 静默通过 —— 安装看起来成功、`caches.open` 不报错，只有真断网才发现什么都没缓存。修法是两边都归一化。守卫是 `web/scripts/sw_harness.mjs`：在 Node 里用最小 Cache API / fetch 替身**执行构建产物 `static/sw.js`**，断言 20 项行为（预缓存条数、URL 带前导斜杠、预缓存命中、API 导航不被接管、断网回退外壳、`push` 必须显示通知、损坏载荷降级、通知 tag 与 data）。它接进了 `pnpm build`，因为源码级单测覆盖不到注入后的清单。

**订阅注销按 endpoint 而不是主机名。** 列表接口出于凭据保护不回显 `endpoint` 全文（同一推送服务下多台设备主机名相同），所以新增 `POST /api/notifications/push-subscriptions/delete` 接受请求体里的 `endpoint` 精确注销；`endpoint` 不进 URL，避免出现在访问日志与浏览器历史里。

**测试环境的两个补充。** 一是 jsdom 没有可用的 IndexedDB（它挂了一个「存在但没有 `deleteDatabase`」的 stub），因此 `web/src/test/idb-shim.ts` 提供一个最小内存实现并在 `vitest.config.ts` 里作为 setup 加载 —— 目的是让 `src/lib/idb.ts` 的测试验证**真实键名**（`maa-api` / `auth` / `token`），而不是把整个 `indexedDB` mock 掉。二是 `ConfirmationsPanel` 现在用 `useSearchParams` 支持推送深链，既有用例需要包一层 `MemoryRouter`。

**顺带修掉的既有抖动。** `web/src/features/api-console/api-console.page.test.tsx` 的「移动端请求步骤」用例依赖 CodeMirror 250ms lint 防抖，却用默认 1s 的 `findBy` 超时；在基线分支 `refactor/v2` 上实测 3 次里失败 2 次。改为与该防抖相符的 5s 预算后连跑 4 次全绿。

**独立复审后的两处补正（同属 M14）：**

- **VAPID 密钥不再走设置 API。** 规格原写"其次为 SQLite 中经 `MAA_LLM_ENCRYPTION_KEY` 加密的私钥"，实现时它作为可写敏感项进了 `SETTING_KEYS`，于是私钥会以**明文 PEM** 落库（只有 `llm.api_key` 走了 Fernet），复审实测确认了这一点。改用更简单的方案：`notify.vapid_private_key` / `notify.vapid_subject` **从 `SETTING_KEYS` 与设置 schema 中移除**，只从 `config.yaml` 读。理由是这两个键本来就不适合走设置 API —— 多行 PEM 在设置页的单行输入框里回写会丢换行，而 `sensitive` 项读取只回 `***`，用户保存**任意其它字段**时前端会把 `***` 当新值提交、静默覆盖真实私钥。这也顺带满足"密钥必须稳定"这条硬要求：它只能由部署者显式编辑。§19 的"公私钥成对存储"同样未实现，改为由私钥导出公钥（少一处漂移源）。
- **通知标题改为用户看得懂的动作与影响。** 规格举的例子是「Agent 请求碎石 3 颗」，实现最初直接用了内部工具名与参数形态（如 `run_task`、`Fight.stone=3`），锁屏通知上等于没写。现在由 `maa_api/services/webpush_service.py` 的 `confirmation_title()` 映射：工具名走中文动作表（`click` → 「在游戏画面点击」、`submit_pipeline` → 「提交任务流水线」），影响范围复用 `RISK_FIELDS` + `TASK_LABELS` 渲染成「刷理智 · 源石 ×3」。认不出的工具名退回原值、**不编造**影响范围（误报消耗比不报更糟）。

**复审同时发现的其余问题**已一并处理：`focusOrOpen` 对未受控窗口的 `navigate()` 会抛 `TypeError`（规范如此），现在接住并退回 `openWindow`，否则点通知毫无反应；推送广播改为**并发 + 总预算**（原先串行、每订阅 10 秒超时，N 个不可达订阅会把确认调用拖成 10 秒 × N）；订阅登记的幂等 `200` 补进了 OpenAPI 声明；`sw_harness.mjs` 补上 `notificationclick` 的三条入口断言（`X-Token` 注入、approve/reject 极性、窗口复用与退回 `openWindow`、409 结果通知），复审用变异证明过这些路径此前**完全没有回归网**；harness 的失败呈现改为逐项标签（原先 waitUntil 拒绝会让整份报告只剩一句原始堆栈），并让预缓存替身校验每个 URL 在构建产物中确实存在。

**未完成（补充实测）**：真机（Android Chrome / iOS Safari）经 Tailscale 的实际送达、锁屏通知、Chromium action 按钮与深链回卡片，均依赖 M15 的 HTTPS 入口，按 §8.3 记为补充验证。

### 8.11 M14 补正：「有连接」不等于「用户在看」

[09 §13.1](./09-前端重构方案.md) 的前台层判断依据是 `document.visibilityState === 'visible'`，但实现最初把服务端的判断写成了「有没有活跃 WebSocket 连接」。两者在移动端并不等价：页面切到后台时被冻结，**WebSocket 往往仍然连着**（心跳只是暂停）。后果是确认请求到达时服务端认为「用户在看」而**不推送**，用户什么都收不到，确认只能等到超时自动拒绝 —— 恰好是推送要解决的那个场景。

补正做法：

- `ClientSession` 增加 `visible` 字段（默认 `True`，老客户端不发该消息时行为与之前一致）；
- 客户端在连接建立时与每次 `visibilitychange` 上报 `{"type": "visibility", "data": {"visible": bool}}`；
- `ConnectionManager.has_visible_client()` 取代「`bool(sessions)`」作为确认推送的判断依据，并要求会话未关闭。

测试：`tests/test_deployment.py` 覆盖「后台会话不阻止推送」「无会话为假」「已关闭会话不算可见」「visibility 消息更新状态」，前端 `src/realtime/client.test.ts` 覆盖连接时上报与切前后台重复上报。既有的订阅相关断言改为只看控制帧（排除每次订阅都会附带的 visibility 上报）。

### 8.13 默认模型标识修正与能力检查的失败原因、视觉探查修正

**问题。** Agent 页与设置页的能力自检固定显示「当前模型未通过 function calling 能力检查，无法进行 Agent 对话」，而实际原因与模型能力无关：`api.deepseek.com` 只接受 `deepseek-flash` 与 `deepseek-v4-pro`，仓库默认的 `deepseek-v4.1-flash`（`maa_api/settings.py` 的 `LLMSettings.model`、`config.template.yaml`、`config.yaml`）从来不是合法标识，探查请求被上游以 HTTP 400 `invalid_request_error` 拒绝。该错误码不在 `llm.py` 的已知上游码表内，`details` 里只有 `upstream_status`，于是 `_probe_capabilities` 落进「工具调用能力缺失」这一条分支，把配置错误报成了能力不足。

**修正。** 默认模型标识改为 `deepseek-flash`（[11 §8.1](./11-Agent模块设计.md)、[05 §6.15](./05-API规范与路由清单.md)、[docs/README](./README.md)、`README.md` 与 [12 的 M13](./12-实施计划与里程碑.md) 同步改写）。同时修掉「探查失败原因不可见」这个缺陷，因为它是本次误诊的直接原因：

- `invalid_request_error` 与 `invalid_api_key` 进入 `llm.py` 的已知上游码表，`details.upstream_code` 能给出稳定值。
- `details` 增加 `upstream_message`（上游 `error.message`，先按既有的凭据遮蔽规则脱敏，再截断到 300 字符）。`AppError.details` 会经 `app_error` 原样出接口与 SSE `error` 事件，所以脱敏在写入 `details` 之前完成；`tests/agent/test_llm.py` 固定「上游正文里的 API Key / `Authorization` 头不会回显」。
- `_probe_degraded_reason()` 在探查抛错时改用真实原因：`当前模型无法进行 Agent 对话：能力探查请求被上游拒绝（HTTP 400，invalid_request_error）；<已脱敏的上游原文>`。工具调用能力确实缺失（上游正常返回但没给出 `capability_probe` 调用）时仍报原来那句；视觉能力不足与「未配置 LLM」的文案不变。

**视觉探查的同源缺陷（重启后复验时发现并一并修掉）。** 探查用的测试图是 1×1 的 PNG，`api.deepseek.com` 以 `You have uploaded an unsupported image` 直接拒收（HTTP 400），而 `except AppError: vision = False` 把「图片无效」记成了「模型不支持图片输入」。结果是 `deepseek-flash` 明明能读图，能力自检却回 `vision_degraded`，截图与原子屏幕操作在 Agent 页被整体禁用。两处一起改：

- 测试图换成 64×64 纯蓝 PNG（`_VISION_PROBE_PNG`，132 字节）。实测 1×1、64×64、128×128 三档里只有 1×1 被拒；64×64 已能被正确识别为蓝色，没必要再传更大的图。
- 视觉判定改为「回答里出现 `blue`」（`_VISION_PROBE_MARKER`，配 `_VISION_PROBE_PROMPT` 要求一个词作答），不再只看有没有返回文本。这样 `deepseek-v4-pro` 那种「接受图片但回 *Unable to view image content*」的假通过会被判成不支持——该模型实测确实不具备图片输入能力，此前会被误记为 `vision: True`。探查请求本身失败（图片被拒、鉴权失败、超时）仍按不支持处理。
- 回归：`test_vision_probe_requires_the_model_to_actually_read_the_image`（答不出颜色的文本 + 上游 400 两种路径）与 `test_vision_probe_image_is_large_enough_for_the_upstream_to_accept`（断言 PNG 的 IHDR 为 64×64，防止改回 1×1）。用一个临时 `AgentRuntime` 直连上游复验：`{'tool_calling': True, 'vision': True, 'ready': True, 'status': 'ready'}`。

**顺带重构。** 遮蔽逻辑原来只长在 `runtime.py` 里，`llm.py` 要用就得重复一份或形成 `runtime ↔ llm` 循环导入，因此提取为 `maa_api/agent/redaction.py`（`redact_remote_data` 与四个私有常量原样搬移，`runtime.py` 改为导入并保留同名再导出），行为不变，既有脱敏测试全部保持通过。

**遗留。** 能力结果按 `(model, base_url)` 缓存在进程内存里，改完 `config.yaml` 必须重启服务才会重新探查。

### 8.14 品牌标换成插画，`favicon.svg` 改为 `favicon.png`

**改动。** 品牌标由 M16 画的「石墨底圆角方块 + 靛蓝单线 M」换成一张插画：`web/public/logo.webp`（512×512，带透明通道）成为画面的唯一来源，`scripts/generate_pwa_icons.py` 不再用 Pillow 画几何，改为把插画垫在品牌底色上再导出各尺寸。

由此产生的三处必须记录的偏离：

- **`favicon.svg` 删除，改为 `favicon.png`（64×64）。** 原来那个 SVG 是硬编码的 M 路径，插画是栅格图，无法继续用几何表达；把 PNG 塞进 SVG 的 `data:` URI 只是让文件名好看而体积更大，所以直接换文件类型，`web/index.html` 与 `vite.config.ts` 的 `includeAssets` 同步。旧文件名没有保留为兼容别名：图标只由浏览器与 manifest 按当前 HTML 取用，没有外部引用方。
- **底色由石墨 `#15181D` 改为暖白 `#F1ECE1`**（取自插画中画框内部），只出现在圆角外的四角与 maskable 的安全区。插画是暖色调，压在石墨黑上会显得脏。
- **PNG 量化为 256 色。** 真彩直存会把 512 图标推到 200KB 以上（原单线图标只有 19KB），而它要进 Service Worker 预缓存并成为设备上的桌面图标；256 色实测平均色差约 2.7/255，肉眼不可辨，体积降到约 1/5。maskable 的内容缩到 90% 安全区：实测 0.8 画面明显偏小、1.0 会把画框四角与玫瑰切掉，0.9 能让脸、双角与玫瑰都落在圆形安全区内。

**应用内品牌标同源。** `BrandMark` 改为渲染 `/logo.webp`（原来内联同一份 SVG 几何）。插画自带画框与透明留白，因此去掉了圆角容器；调用方传入的尺寸类与 `shadow-float` 落在 `<img>` 上，`SideNav`（28px）与登录页（56px）的布局未变。通知图标（`sw.ts` 的 `icon` / `badge`）继续指向 `pwa-192x192.png`，因此自动跟随新标。

**未验证。** 没有在真机/模拟器上确认主屏安装图标与 Android 圆形 maskable 裁切的最终观感（自动化只能验证文件存在与尺寸，见 §8.3 的补充实测口径）。`docs/09` §文件树与「图标」段、`docs/12` 的 M16 条目已同步改写；`docs/superpowers/` 下的 M16 计划、规格与台账保留当时的决策原貌，不回填。

### 8.15 思考模式模型的两个协议缺陷：tool 消息相邻性与 `reasoning_content`

**症状。** 自动诊断固定失败，用户只看到一句「自动诊断暂不可用（LLM_REQUEST_FAILED）：LLM 上游请求失败。故障记录已保存」，且在该会话里继续追问同样失败。日志里没有可用的上游原因——`run_incident` 的通用兜底分支把真实异常换成了硬编码文案（只有 `AppError` 分支会显示 `（码）：消息`），所以先要复现才能定位。两个缺陷叠加，都会让整个回合失败。

**缺陷一：截图破坏了 tool 消息的相邻性。** `get_screenshot` 的结果消息之后，`build_model_context` 会**另起一条 `user` 消息**装图片。OpenAI 协议要求 assistant 的 `tool_calls` 后面**紧跟**同样数量的 `tool` 消息，中间插任何消息都会被上游以 400 拒绝（`An assistant message with 'tool_calls' must be followed by tool messages`）。修法：把图片并进**那条 tool 消息**的多模态 `content`（文本 + `image_url`），顺序保持 `assistant(tool_calls) → tool…`。回归测试 `test_model_context_keeps_tool_replies_immediately_after_their_tool_calls` 直接断言相邻性——原来的测试只断言「tool 消息按序存在」，所以这条一直漏网。

**缺陷二（主因）：思考模式的 `reasoning_content` 被整个丢弃。** `deepseek-flash` 与 `deepseek-v4-pro` 都是思考模式：流式响应里带 `delta.reasoning_content`，而实测上游对历史的形状有硬要求——**历史里凡是后面不跟 user 消息的 assistant 消息都必须把思考内容原样回传**，否则 400（`The reasoning_content in the thinking mode must be passed back to the API`）。实测矩阵：纯 user → 200；`assistant(tool_calls) → tool` → 400；`…→tool→` 新的 user → 200；`…→tool→assistant(纯文本)` → 400；带（哪怕空串）`reasoning_content` 的各形态 → 200。自动诊断每一轮都以工具结果结尾，正好落在必错的那一格里。代码里此前**完全没有这个字段**（全仓库 grep 无命中），思考内容在流式解析时就被丢掉，无从回传。

**修法。** 按用户裁决「完整保留」：`_complete` 累积 `reasoning_content` 并随 assistant 消息落库（migration `0013_agent_message_reasoning` 加 `TEXT` 列，可空，既有行不受影响）、`_message_dict` 与上下文组装原样回传、`message_wire` 一并读出便于排查。不展示给用户。回归测试 `test_thinking_mode_reasoning_is_persisted_and_sent_back_on_the_next_request` 覆盖「增量分片拼接 → 落库 → 下一轮回传 → tool 消息仍紧跟」，并已验证把回传那段去掉即变红。

**顺带修掉的测试硬编码。** `tests/db/test_migrate.py` 的 `TABLES_ADDED_BY_HEAD` 是 `{"push_subscription"}` 写死的（0012 时代）。head 换成只加列的 0013 后，备份里本来就该有 `push_subscription`，这条断言反而误报。现改为用 AST 读 head 迁移脚本里的 `op.create_table`，换 head 不再需要手改。

**未覆盖。** 没有实测「思考内容被截断后上游是否仍接受」——本次是完整保留，不做截断；若日后要为省空间截断，需要重新验证。`docs/04` §5.8 已补该列；`docs/05` 的 agent 消息契约未改（该端点的响应体是通用 dict，OpenAPI 快照与前端生成物均无漂移）。

### 8.16 移除 tool-calling 步数上限、Markdown 表格渲染与 Agent 页高度

**移除步数上限（用户要求）。** 单轮不再限制模型迭代次数（原 `DEFAULT_MAX_ITERATIONS = 12`，改为 `None`）：一次故障排查要连着读几十轮日志与截图，按次数截断会把本该跑完的诊断切在半路。代价是「停不下来」不再由次数兜底，因此补上**原地打转检测**：连续三轮发出**完全相同**的工具调用（按名字与参数比对，不看每轮都会变的调用 id）就以 `finish_reason = "stuck_loop"` 正常结束并告知用户。真正兜底的仍是上下文裁剪（`max_context_chars`）与上游的上下文窗口报错。`max_iterations` 参数保留（正整数仍可限制，仅供测试与受限调用方），`max_steps` 因此只在显式设置时出现。测试：`test_tool_loop_has_no_step_limit_and_finishes_the_model_answer`（20 轮工具调用后仍继续请求模型）与 `test_tool_loop_stops_when_the_model_repeats_the_same_calls`（第 3 轮停下）。docs/04、docs/05、docs/11 同步改写。

**Markdown 表格渲染。** Agent 常用表格汇总状态，此前 `parseMarkdown` 不认表格，整块被当作段落，于是界面显示成一堆竖线与 `| --- |`。现在识别「表头行 + 分隔行 + 数据行」：行首行尾的 `|` 可省、缺列补空、多列截断，单元格仍是行内节点数组（粗体、行内代码、链接照常渲染）；只有表头与分隔行（流式中途）也成立，`rows` 为空，不丢内容。两个易错点写在代码注释里：分隔行 `--- | ---` 会被列表匹配器认成 `- ` 列表项，必须放行；无外框写法里末行可能不含 `|`，不能因为「这行没有竖线」就截断。渲染成真实 `<table>`，外层 `overflow-x-auto` 避免宽表把页面撑宽。回归测试含一条**真实回复**（`AssistantText.test.tsx` 的 `LIVE_TABLE_REPLY`）。

**Agent 页高度与外壳留白不一致。** 桌面布局给 `Page` 写的是 `h-[calc(100dvh-1.5rem)]`，漏了外壳 `main` 的底部留白里的 `--nav-offset`，于是整页比视口高出约 24px，出现「只有 Agent 页有整页纵向滚动条」的现象（对话区自己也在滚动，等于双滚动条）。现改用与日志页同一个口径：`h-[calc(100dvh_-_var(--nav-offset)_-_1.5rem)] min-h-[28rem]`，页面占满剩余高度、只有会话列表与对话区内部滚动。

### 8.17 M17：任务参数默认值与「预填即下发」

**起因与用户裁决（2026-09-28）。** 任务编辑器里 `启用本任务` 显示成「默认 + 滑块居中」，用户无法判断这是「空」还是「关」。用户裁决：① 所有任务参数，有默认值的都**按默认值显示并预填**；② 预填的值**随提交体显式下发**（所见即所提交），接受「MAA 将来改默认值我们不再自动跟随」；③ 默认值由后端逐字段补进 JSON Schema `default`；④ 范围只到任务参数，**不做**「日常预设模板」；⑤ 渠道字段（`client_type` / `server`）也预填当前全局默认并下发；⑥ 内核必填但无默认值的 `Recruit.select` / `confirm`、`Infrast.facility` 由本服务给默认值；⑦ `facility` 在界面上显示中文设施名。规格与计划见 `docs/superpowers/specs/2026-09-28-m17-task-param-defaults.md` 与 `docs/superpowers/plans/2026-09-28-m17-task-param-defaults.md`。

**默认值必须取证，不能照文档抄。** 三条独立证据链：MAA tag `v6.17.5` 源码（本仓捆绑的运行时版本）、同 tag 官方文档 `docs/zh-cn/protocol/integration.md` 的 `@default` 注解（英文版逐字段零差异）、以及**真内核实测**——`AsstAppendTask` 不需要连设备，返回 0 即 `set_params` 失败，因此新写的 `scripts/probe_task_defaults.py --model-defaults` 可以直接验证「前端会提交的这套全默认参数」能否被内核接受。三处文档与源码冲突一律以源码为准：`Recruit.skip_robot`（文档 `@default true`，源码是 `find` 且缺省不跳过）、`Recruit.set_time`（文档称仅 `times=0` 生效，源码两条路径都用）、`Roguelike.squad`/`roles`（文档写「指挥分队」/「取长补短」，源码是空串 = 内核自动选）。另有一处是本仓文档写错：**`StartUp.start_game_enabled` 的内核默认值是 `false`**（`StartUpTask.cpp:94`），原文案的「默认 True」是错的，随本次一并修正。

**这四类字段刻意不预填**（规格 §3.2）：语义是「无限」的（`Fight.times`、`Roguelike.starts_count`/`investments_count` 的内核默认是 `INT_MAX`，写进表单就是 `2147483647`；而 `Fight.times=0` 另有「跳过整个任务」的含义）；语义是「空 = 不启用」的空串字段（`stage`、`account_name`、`squad`、`penguin_id` 等，预填与不填无差别）；**条件默认值**随主题/模式变化的字段（`use_foldartal`、`check_collapsal_paradigms`、`difficulty`、`expected_collapsal_paradigms` 等，静态默认会在别的模式/主题下改掉内核行为，其中 `expected_collapsal_paradigms` 还会直接触发本服务的 422）；本服务校验器禁止「设了但不生效」的 `Recruit.expedite_times`。另有 `Roguelike.start_foldartal_list`：内核在 Sami 主题下遇到显式 `[]` 会让 `set_params` 失败，因此既不设默认也不能下发空数组。这些字段保持 M16 的「未设置」行为，界面标签从原来错写的「默认」改成「未设置」。

**顺带修掉三个既有缺陷。** 实测确认：`Recruit` 必须同时给 `select` 与 `confirm`、`Infrast` 必须给 `facility`、`StartUp` 必须给 `client_type`，缺任何一个内核都静默返回 0——也就是说 M17 之前，用户在公招/基建任务里「什么都不改」直接提交，拿到的是一个没有任何解释的 `502 CORE_COMMAND_FAILED`。现在前两者由本服务给默认值（`[1,4,5]` / `[2,3,4,5]` 取自旧前端 `createTasks` 的日常预设；`facility` 是七个设施按标准顺序），第三个由渠道默认值 overlay 提供。改完之后 `scripts/probe_task_defaults.py --model-defaults` 用真内核（v6.17.5，不连设备）逐个 append 全默认参数，九种任务类型全部拿到非 0 的 `task_id`（18–26）——这就是「预填即下发不会把内核打回 0」的直接证据；被拒的只剩刻意留缺的对照候选（`{}` 的 StartUp/Recruit/Infrast/Copilot）。

**`plan_index` 的连带效果。** 它现在有默认值 `0`，所以 `Infrast` 的自定义换班模式（`mode=10000`）在校验层面只剩 `filename` 是必填（原来 `filename` 与 `plan_index` 缺一不可），`tests/domain/test_task_models.py` 的合法/非法样本清单已相应调整。

**渠道字段的新代价。** `client_type` / `server` 在模型里仍是 `default=None`、仍由服务端按 `model_fields_set` 注入设置表里的全局默认值；变的只是 `GET /api/tasks/types` 会把**当前生效值**作为 schema `default` 暴露出来，前端据此预填并显式下发。于是 M17 之后**新建的流水线与定时任务不再跟随后续的渠道设置变更**（已经存过、没带这两个字段的记录仍然跟随，[05 §9](./05-API规范与路由清单.md) 已加限定）。设置保存后前端要失效任务类型目录的查询，否则 5 分钟 `staleTime` 内会预填旧值。

**其余接受的代价。** 参数快照冻结在建流水线时的默认值上，MAA 调整默认值不再自动影响已有流水线（用户已知情）；`Recruit.times` 的内核默认是 0，所以「什么都不改」的公招任务进去就出来——要真招募得自己改次数，这正是用户排除掉的「日常预设模板」要解决的问题；条件默认值字段在界面上仍是「滑块居中」的三态。

### 8.18 表格渲染的两处漏网，与「首轮收尾补会话标题」

**症状与取证（2026-09-28，同一会话）。** 8.16 交付的表格渲染仍有一部分表格原样显示成竖线加 `| --- |`。拿库里那条真实回复（会话 `e1ba2b83` 的 assistant 消息）直接过 `parseMarkdown`，得到的是**列表 + 段落**而不是表格——两个独立成因：① 表头 `| 字段 | 值 |` 同时符合 `LIST_ITEM` 的形状（`|` 是合法的无序列表标记），而列表判定排在表格之前，表头被列表匹配器先一步吃掉；② 表头紧贴在 `**新定时任务**` 后面、中间**没有空行**，段落收集循环又认不出「下一行是表格」。因此「带外框 + 紧凑分隔行 `|---|---|`」这种写法整块退化成原文，而单元测试里恰好全是「无外框」或「有空行」的样本，一直没覆盖到。修法是两处：判定「这一行是不是别的块」之前先 `stripTableFrame` 去掉行首外框竖线；段落收集循环在 `cursor > index` 时用 `matchTable(lines, cursor)` 断一次。回归测试用**该条回复的原文**（`AssistantText.test.tsx` 的 `LIVE_FRAMED_TABLE_REPLY`）加两条解析器用例锁住，不再只靠人造样本。

**会话标题（用户要求，2026-09-28）。** 用户提出：问完第一个问题、agent 正常回答之后，由 agent 快速总结一个标题并回填，总结完成之前统一用「新会话」占位。两处裁决由用户拍板：① 生成时机放在**首轮回答结束后、收流之前**（而不是后台异步），代价是「本轮完成」晚 1–3 秒，换来的是前端不需要为标题轮询；② **不做**手动重命名接口，只做自动标题。实现见 [11 §8.2](./11-Agent模块设计.md#82-tool-calling-循环)：一次不带工具的短调用、输入只取首条用户消息前 300 字、清洗引号与句末标点、按 24 字截断，落库后推 `session_title` 事件。三条边界刻意如此：标题跟着会话的 `model`/`base_url` 快照走；生成失败只记日志、绝不把成功的回答变成 `error`；已有标题的会话不再生成（所以每个会话最多一次，自动诊断会话本来就带标题）。

**测试口径的连带改动。** 多出的这次调用让 `tests/agent/test_runtime.py` 的假 LLM 会在队列空掉时收到一次「无工具」请求，于是：假 LLM 增补 `turns` 属性（按「第一条是 system」筛出真正的对话轮次，能力探测的两个探针请求与标题调用都不算），事件断言改用 `_turn_events`（过滤掉收尾的 `session_title`），并把「最后一次请求」这类断言从 `requests` 换成 `turns`。这些改动是口径调整、不是放宽断言：标题本身由 4 条新用例覆盖（生成并落库、只生成一次、失败不影响回合、`_clean_title` 的清洗与截断）。

**未覆盖。** 标题生成的**真实上游**表现没有实测：模型是否稳定遵守「不超过 12 字、只输出标题」、以及这次额外调用在思考模式模型（`deepseek-flash`）上的实际耗时，都还没有运行数据；当前只用 `_clean_title` 的清洗与截断兜底。另外「标题生成把这一轮完成时间推后 1–3 秒」的估计同样来自推断，不是实测。



### 8.19 流水线终态通知接线（docs/09 §13 的「保底层」落地）

**症状：通道配好了却收不到「任务完成」。** `pipeline_completed` / `pipeline_failed` 从 M6 起就写在 `NotifyEvent` 里、设置页也能勾选，但全仓库没有任何调用点——`send_event` 此前只有两处调用：`update_service` 的 `update_available` 与 agent 确认的 `confirmation_required`。`Pipeline.notify_on_finish` 存了库、回显给 API，同样无人读取。也就是说「任务完成后通知我」这个需求缺的是触发点，不是通道。

**触发点挂在唯一漏斗上。** `PipelineRunner._finish_pipeline()` 是运行中流水线终态的唯一入口（完成 / 失败 / 取消都汇到这里），而它调用的 `PipelineRepository.mark_terminal()` 用 `WHERE status IN (pending, running)` 保证终态不可再变、只在状态机真的接受了这次流转时返回 `changed=True`。通知就发在 `changed` 为真的那一次，重放同一个终态不会重发（回归：`test_replayed_terminal_write_notifies_once`）。这正是 `_finish_pipeline` 之外那几处 `mark_terminal` 直调要逐个过一遍的原因。

**另外两处不走漏斗的失败终态也补上了。** 逐个数过 `mark_terminal` 的全部调用点后，把「用户提交了任务却什么都没跑起来」的两条路一起接上，否则又会出现「配了通道却收不到」：① `_handle_device_unavailable()` 里手动 / agent 提交的流水线在设备预检就失败（`DEVICE_NOT_CONNECTED`；定时任务那里是延后 5 分钟重试，不是终态）；② `_record_failed_claim_error()` 里领取失败、无法释放的流水线（`INTERNAL_ERROR`）。两处同样按 `mark_terminal` 的返回值判断，重复调用不重发（回归：`test_device_precheck_failure_notifies_failed_pipeline`）。

**刻意不发的几处**（避免打扰与通知风暴）：`request_cancel()` 与批量取消（用户自己按了停止）、`_cancel_pipeline_rows()`（关服务时停止、运行中被取消）、`_recover_interrupted()`（服务重启把上次运行中的行回收为失败——重启是用户主动做的，且一次会命中多条）。

**内核崩溃抢占终态那条路单独处理，否则会先报完成再报失败。** 终态写入提交之后，`active.core_crashed` 可能已经把结果改判为崩溃，行会由 `_record_core_crash_terminal()` 改写为 `FAILED / CORE_CRASHED`。因此这条路上 `_finish_pipeline` 直接返回，通知交给真正改写成功的那一次发：`mark_core_crashed()` 的 `WHERE` 排除了已是 `FAILED + CORE_CRASHED` 的行，返回的 `rowcount` 恰好就是「这次真的改写了」，重复调用（例如 finally 里再补一次）不会命中（回归：`test_core_crash_preempting_a_completed_write_notifies_failure_once`，断言只投递一条 `pipeline_failed`）。

**不阻塞队列、不反噬终态。** 投递走后台任务（单个通道 10 秒超时 × N 个通道），队列消费者不等通知就领下一条流水线；`stop()` 与 incident 任务一样取消待发任务，所以关服务瞬间的终态通知可能丢，与既有后台诊断任务同一取舍。通道级异常由 `NotifyService` 逐通道记入 `last_status` / `last_error`，后台任务的未捕获异常只记日志，绝不回写流水线终态（回归：`test_notification_failure_does_not_break_the_terminal_write`）。

**顺带修掉一个静默吞异常的缺陷。** `_forget_incident_task()` 原来把 `task.exception()` 包在 `try/except` 里，而它是**返回**异常、不抛出，于是后台诊断任务失败时什么都不记（写新用例时先踩到：`caplog.text` 为空、断言失败）。两处回调（诊断与通知）都改为判返回值 + `logger.error(..., exc_info=...)`。

**文案与实测投递。** 标题写结果（「任务执行完成：睡前日常」/「任务执行失败」），正文是任务清单、成功/失败计数、耗时与失败原因，不出现内部标识符。用本地捕获服务器 + 真 `NotifyService` + webhook 通道实测：


`notify_on_finish=False` 的流水线不发（`test_notify_on_finish_false_suppresses_terminal_notification`）。docs/04 §5.1 与该字段、docs/09 §13「流水线终态交给多通道」原本只是纸面约定，现在落地，两处文档无需改动。

### 8.20 新增飞书通知通道（自定义机器人）

**起因与卡点。** 用户问「怎么加飞书通知」，而当时的答案是**配不出来**：飞书自定义机器人只接受 JSON 请求体（`{"msg_type":"text","content":{"text":"..."}}`，见[官方指南](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)），而通用 Webhook 通道的模板引擎只认 `{field}` 占位符、拒绝任何字面量花括号（§8.19 提到的那条限制）。实测一个 JSON 模板是**保存成功、发送必失败**，`last_error` 写 `body_template 只支持 {field} 形式的字段替换`——所以「填个 URL 就能用」对飞书不成立（ntfy 能用是因为它接受纯文本 POST）。relay 是可行但多一跳的绕法，飞书又与已有钉钉通道几乎同形，因此直接加第六种通道类型。

**加签是两套算法，不能照抄钉钉。** 这是本次最容易写错的地方，两者的差别是三处：飞书把 `"{timestamp}\n{secret}"` 当作 HMAC 的**密钥**、消息体为空，时间戳用**秒**，签名放在**请求体**里；钉钉把 secret 当密钥、`"{timestamp}\n{secret}"` 当消息体，时间戳用**毫秒**，签名拼在 **URL 查询参数**里。实现见 `notify_service._send_feishu()`，回归用例 `test_feishu_channel_signs_the_body_with_its_own_algorithm` 用官方算法独立复算签名并断言时间戳长度为 10（秒级），另断言**未填密钥时请求体不带 `timestamp`/`sign`**（带上会被飞书判为签名错误）。

**配置形状与校验。** `{"webhook","secret","at_user_ids":[]}`：`webhook` 与钉钉/企微一致强制 https、禁 userinfo；`secret` 选填；`at_user_ids` 每项渲染成 `<at user_id="…"></at>`（`all` 渲染成 `<at user_id="all">所有人</at>`）。用户 ID 会被原样拼进文本消息，所以校验拒绝含引号、尖括号或空白的值（`test_feishu_channel_rejects_non_https_and_unsafe_mention_ids`）——否则一个 `"` 就能破坏消息结构。脱敏沿用 `webhook` 键的既有规则：列表里回显 `https://open.feishu.cn/***`、`secret` 为 `***`。

**连带改动（通道类型是跨层枚举，一处加值要动五处）。** 后端 `NotifyChannelType.FEISHU` + `_FeishuConfig` + 发送分支；前端 `channel-config.ts` 的类型下拉与表单字段、`NotificationChannels.tsx` 的图标（`Bird`）；OpenAPI 快照（`NotifyChannelType` 是 schema 枚举）重生成后 `pnpm gen:api` 同步 `src/types/api.d.ts`；`tests/domain/test_enums.py` 的枚举全量断言；docs/04 §5.12 的三处清单与 README 决策表。

**补记：另有两处「五种通道」清单在首次提交时漏掉。** 提交后复核全仓库剩余命中，发现 docs/02 §1 的架构图与 docs/12 的 M14 交付项还写着旧清单。docs/12 是里程碑当时的范围快照（同段还有「M14 已交付」的历史表述），保留原文并就地标注交付时追加；docs/02 是现行架构图，直接改成六种。docs/04 §5.12 的正文「五种通道的字段集合完全不同」同样漏改（三处：枚举、正文、`config` 字段清单），一并修正——这类「跨层枚举加值」的清单散落在图上、表上和正文里，只按代码引用找会漏。

### 8.21 日志模块的两处实测修正：内核日志路径与回调载荷形状

**起因。** 用户报告两个现象：任务日志里有大量"未映射回调"，核心日志一直为空。只读排查（回放 `resource/maa-api/debug/asst.log` 的 8221 条真实回调 + `lsof` 看运行中的句柄）定位到两个独立根因，都不是运行期偶发。

**根因一：tailer 读的文件与内核写的文件不是同一个。** 服务在 `main.py` 把 `user_dir` 设为 `resource/maa-api` 交给 `AsstSetUserDir`，内核据此写 `resource/maa-api/debug/asst.log`；而 `log_wiring.resolve_core_log_path()` 从 `maa_core_path`（缺省 `resource/lib/maa/<平台>`）推导，指向 `resource/lib/maa/Darwin/debug/asst.log`。实测证据：API 进程持有前者的读句柄（mtime 停在 9-25），内核子进程写后者（40 MB 且在增长）。`source="core"` 一路因此从未产生过记录，连 `WARNING`/`ERROR` 都没有——与 docs/04 §10.2 的落库阈值无关（那条阈值只决定入不入库，实时推送是全量的）。

**裁决：把 `user_dir` 提成单一来源。** 新增 `maa_api.settings.core_user_dir()`，`main.py` 的 `boot_config["user_dir"]` 与 `resolve_core_log_path()` 都从它取值；内核目录不再参与日志路径推导，`resolve_core_log_path()` 也不再读 `maa_core_path`。没有为它加配置项——`user_dir` 是装配内部约定，不是运维需要调的东西，加键会与 docs/03「内核目录留空自动探测」的既有设计重复表达。改动影响对外行为（核心日志视图从空变有），记在此处。**原有测试对这个路径零覆盖**（`tests/` 里搜 `resolve_core_log_path` 无命中），所以补了 `tests/services/test_log_paths.py`，其中一个用例走 lifespan 的同一个入口 `start_core_debug_tailer()`，断言写进 `<user_dir>/debug/asst.log` 的行会以 `source="core"` 出现。

**根因二：`SubTaskStart`/`SubTaskError` 读错了载荷层级。** 翻译器从 `details.details.task` 取任务名，实测 v6.17.5 的 `details.details` 在 `SubTask*` 上恒为空（6815/6815），任务名在 `details.task`、ProcessTask 类型名在顶层 `subtask`、动作级步骤另有 `details.action`。后果是 `SUB_TASK_START_MAP` 的 22 条键**一次都不命中**，每个 `SubTaskStart` 退化成 `未映射回调 SubTaskStart.`（空名字）；`SubTaskError` 的载荷 `details` 为空、失败步骤只在顶层 `first` 数组里，于是永远产出 `子任务出错 []`。这是 docs/06 §3.3 与 §3.5 的纸面约定本身写错了层级，不是实现偏离文档。

**裁决：按键实际位置逐层回退取值**（`callback_translator._flatten`：`details.details.task` → `details.task` → 顶层 `subtask`），保留内层优先以兼容新旧内核。另按实测补 4 条映射：`ConnectionInfo` 的 `ScreencapCost`(413 次/会话) 与 `EmulatorFPS`(128 次)、`SubTaskExtraInfo` 的 `InfrastConfirmButton`/`ProductOfFacility`/`FightTimes`/`ExceededLimit` 等、`SUB_TASK_START_MAP` 的 `InfrastDormConfirmButton`（普通宿舍确认，与"二次确认"是两条不同任务定义，实测 99 次/会话）。

**降噪的裁决（改变对外行为，需知悉）。** `details` 带 `action` 键的 ProcessTask **动作级步骤不产记录**，实测这类占 `SubTask*` 回调的 6467/6815。理由：它们对使用者没有语义（`ClickSelf`/`Stop`/`DoNothing`），却会以数千条规模挤满 `log.ring_size`（默认 2000）的环形缓冲、把业务日志冲掉；docs/04 §10.1 给一条完整日常流水线的预算是 1000–3000 条。判定放在白名单命中**之后**，所以 `StartButton2` 这类同时带 `action` 的确认动作仍按 `INFO` 产出。

一并收紧了"未映射"的口径：未见过的**具名子任务**直接展示内核原名（`子任务开始：NewTaskAddedByMaa`），仍可检索定位；只有未知的**消息类型**与未知的 **`what`** 才落"未映射回调"兜底。这样"未映射"重新变回一个可信的告警信号，而不是日常噪音。

**实测口径（同一次会话，8221 条回调）。** 旧实现：7923 条记录，其中 4426 条"未映射回调"。新实现：1880 条（`INFO` 1362 / `DEBUG` 384 / `WARNING` 124 / `ERROR` 10），未映射 0 条。

**未做（用户明确留待后续）。** 日志页的历史查询（`GET /api/system/logs`）仍未把 `source` 与 `level` 下推到服务端——前端只发 `order`/`size`/`q`/`since`/`until`，来源与级别都在本地过滤。副作用是"核心"标签页只从**不分来源的最新 100 条**里筛，core 记录要恰好落进这一页才看得到。docs/09 §6.3 把这个行为写成了设计（"来源与级别**不进** REST 查询，在本地过滤"），所以改它要连文档一起改，单独一轮处理。

**验证。** `.venv/bin/python -m pytest -q`：1747 passed, 4 skipped。真实日志回放复核见上面的口径数字。

### 8.22 崩溃终态通知的重试缺陷，与三处漏改的通道清单

§8.19 落地后自查发现两处遗留，都属于「同一件事在多处表达、只改了一处」。

**`_record_core_crash_terminal()` 的重试会把「已改写」这件事覆盖掉。** `promoted` 原本在 `for _attempt in range(2)` 循环内每次迭代直接赋值，而这个循环存在的理由正是**提交的歧义失败**——`session.commit()` 可能真的落盘了、调用方却拿到异常（`except` 的注释写着 "retry context-exit/commit ambiguity once"）。于是重试时 `mark_core_crashed()` 的 `WHERE`（排除已是 `FAILED + CORE_CRASHED` 的行）只会返回 `False`，用 `False` 覆盖掉上一次的 `True`，那条流水线就永久不发终态通知——行已经是崩溃终态，后续任何调用都不会再返回 `True`，`finally` 里的补刀也救不回来。改为累积赋值 `... or ever_promoted`，语义是「本次调用是否曾经真正改写过」，与调用点要回答的问题一致；「重复调用不重发」的原有性质不变（第二次调用两次尝试都返回 `False`）。

**这条路的回归用例是本次唯一需要构造的测试难点。** 第一版用例让任务写入在 `mark_core_crashed()` 之后抛错，结果**打不到这个缺陷**：异常发生在 `session.commit()` 之前，事务连同 `mark_core_crashed` 的更新一起回滚，重试时行还是 `RUNNING`、`mark_core_crashed()` 照样返回 `True`，累积与覆盖两种写法都能过。真正的窗口只有当 commit 本身落盘而调用方仍拿到异常时才会打开，所以用例改为 monkeypatch `AsyncSession.commit`：先调用真 commit，再抛一次异常（`test_core_crash_retry_after_the_promotion_commit_still_notifies`）。**反证已做**：把实现改回覆盖写法，该用例失败在「只投递 0 条通知」；改回累积即通过。这类「失败点在提交前后决定缺陷可不可达」的构造，比测试本身更值得记下来。

**通道清单的三处漏改。** 提交后复核全仓库剩余命中，发现 docs/02 §1 的架构图、docs/12 的 M14 交付项、以及 docs/04 §5.12 的正文（「五种通道的字段集合完全不同」——同一小节的枚举与 `config` 字段清单当时改了，正文这句漏了）都还写着五种通道。docs/12 是里程碑当时的范围快照，保留原文并就地标注交付时追加；docs/02 与 docs/04 直接改成六种。教训是「跨层枚举加值」的清单散落在图上、表上和正文里，按代码引用去找会漏。

**验证。** `.venv/bin/python -m pytest`：1748 passed, 4 skipped（新增 1 项）。前端未受影响，`pnpm gen:api:check` / `pnpm typecheck` / `pnpm test --run` / `pnpm build` 均通过；`scripts/dump_openapi.py --check` 无变化。

### 8.23 M18：Agent 知识库、点击坐标系与两处运行时修复

规格与计划见 `docs/superpowers/specs/2026-09-29-m18-agent-knowledge.md` 与 `docs/superpowers/plans/2026-09-29-m18-agent-knowledge.md`。用户裁决（2026-09-29）定下路线与范围：账号资源查询按三步路线推进，本里程碑只做**第 1 步**（「我有多少合成玉」「我还有多少抽卡资源」两个例子端到端跑通）；知识库存数据库并在设置页编辑；MAA `Custom` 任务类型排在第 3 步；顺带修掉 `trigger_screencap` 让会话失效的缺陷；点击坐标统一为设备原始像素。

**一、四条行为变更（用户 2026-09-29 裁决，逐条记录）。**

1. **点击坐标统一为设备原始像素。** Agent 的 `click` 工具与 REST `/api/device/click` 收的都是与截图同一坐标系的设备像素，由 `DeviceManager.click` 在调 `AsstAsyncClick` 前按「高 / 720」折成 MaaCore 基准坐标。按原实现，调用方照截图坐标点击，在 2560×1440 设备上会点到两倍远的位置——这是本次要修的缺陷，不是偏好。`swipe` / `long_press` 本来就走 ADB 设备像素，新增的只是上界校验（分辨率未知时跳过；`click` 则必须知道分辨率，否则拒绝而不是盲点）。
2. **`trigger_screencap` 对内置 Agent 隐藏，并移出 `INCIDENT_ALLOWED_TOOLS`**（M13 规格里列过它）。隐藏只作用于模型可见的工具清单与模型发起的派发：注册表、`GET /api/agent/tools`、`POST /api/agent/tools/trigger_screencap/invoke` 照旧。理由见规格 §2：它的整帧 PNG 以 base64 文本进上下文（用户设备 2560×1440 的首页截图 4,865,068 字符，上限 `DEFAULT_MAX_CONTEXT_CHARS` 是 1,000,000），当轮就报 `LLM_CONTEXT_OVERFLOW`，而这轮工具调用属于受保护的最近完整轮次，同一会话之后每轮都报同一错误。
3. **`read_knowledge` 加入 `INCIDENT_ALLOWED_TOOLS`。** 诊断会话同样注入知识库索引，工具必须可用。
4. **只含 `wait_pipeline` 的批次不计入原地打转检测。** docs/11 §8.2 原来写的是「连续三轮相同调用即停止」，而等长任务连着等几次是正常节奏。docs/11 已按此改写。

**二、坐标系与错误声明（Task 1 的裁决）。**

- `/api/device/click` **留在 `atomic.py`**，只把调用目标从内核客户端换成 `DeviceManager.click`，不搬模块（路径、operationId、tag 不变，diff 最小）；`_device_manager` 按仓库既有风格在本地复制一份，不跨 router 导入私有函数。
- `click` 只按「分辨率是否已知」判定，不额外要求 `state == connected`（照规格字面）。代价是 `DEVICE_NOT_CONNECTED` 的触发面变大：设备连着但 `ResolutionGot` 还没到（或回调键位异常）时，REST/Agent 点击会 503，而不是像以前那样盲点。这是规格要的「宁拒绝不误点」。
- 换算用 Python `round(px × 720 / 高)`（照计划字面）。**已知差异**：Python 是银行家舍入，内核侧在恰好 `.5` 时可能差 1 个基准像素；现有证据（2560×1440 的整数倍坐标）区分不出舍入方式，真机核对若发现系统性偏移，应统一成与内核一致的那一种。
- REST 路由不加 docstring（FastAPI 会把 docstring 写进 OpenAPI `description`），改用行内注释；越界 `INVALID_PARAMETER` 的 `details` 形状自定：`{operation, x, y, resolution{width, height}}`。
- 既有用例 `test_operations_are_delegated_to_adb_and_core_substitutes` 补 `ResolutionGot` 前置，没有放宽断言。

**三、等待原语（Task 2 的裁决）。**

- 只含 `wait_pipeline` 的批次**既不计数也不重置** `last_signature` / `repeats`。若重置，「等一次、查一次」交替就能永远清空计数、绕过保险；保持不变时该序列里的 `get_pipeline` 批次仍在第 3 次触发 `stuck_loop`（有对照用例）。混合批次含任意别的工具时照旧计数。
- `wait_terminal` 每次轮询开**一次性短会话**（`get(with_tasks=True)` 后立即关闭），绝不使用调用方的 `ctx.db_session`——`_execute_and_record` 在整个 handler 期间持有它，等几分钟会把审计事务一起挂住。选轮询而不是事件订阅，是因为现有「事件」只是 WS 广播，没有 per-pipeline 的 future；`poll_seconds` 只作测试用关键字参数，线上恒为 1 秒。
- 超时返回最后读到的状态且**不算错误**（工具结果里没有 `error` 字段）；未知 id 立即抛 `PIPELINE_NOT_FOUND`，不等满超时。`timeout_seconds` 用 `float`（默认 300，`ge=5`、`le=600`），越界走既有的 `TOOL_ARGS_INVALID`。
- 没有把 `wait_pipeline` 加进诊断白名单：规格只要求 `read_knowledge` 加入。

**四、隐藏与状态摘要（Task 3 的裁决）。**

- 不可见检查排在 `allowed_tools` 检查**之前**：可见性是工具自身的全局属性，白名单是会话级策略；对诊断会话两种顺序都是 `TOOL_NOT_FOUND`，差别只在文案（现在是「内置 Agent 不提供该工具，请用 get_screenshot」）。伪造调用不进 ConfirmationService、不落审计。

### 8.25 M20：去掉自设的会话与上下文上限

规格见 `docs/superpowers/specs/2026-09-29-m20-uncapped-context.md`。用户裁决（2026-09-29）：「会话限制上下文限制以模型本身上上下文限制为准，不要自己设置上限。」这条裁决**取代 M18 §4.1/§4.3 里的两条知识库上限**与 M13 起的会话上下文裁剪口径；M18 与 M19 的规格作为里程碑当时的快照保留原文，冲突时以本节为准（[13 的既定规则](#8-实施后的偏离补充与待验证事项)）。

**一、动手前先确认「哪些才算自设上限」。** 全仓 `grep` 后只有两处属于本次范围：`runtime.py` 的 `DEFAULT_MAX_CONTEXT_CHARS = 1_000_000`（按字符数丢掉最早的完整轮次，裁不动就在本地抛 `LLM_CONTEXT_OVERFLOW`）、`knowledge/__init__.py` 的 `MAX_ENABLED_ENTRIES = 50` 与 `MAX_FULLTEXT_CHARS = 3_000`（超出 409）。**刻意保留**：字段长度上限（`title` 32 / `when_to_use` 120 / `body` 20,000——那是列宽与表单约束，不是上下文预算）、原地打转检测 `STUCK_REPEAT_LIMIT`、标题长度 `TITLE_MAX_CHARS`、分页 `size`。`max_iterations` 自 M13 起默认已经是「不设步数上限」。

**二、会话上下文：默认不裁，保留显式上限的能力。** `DEFAULT_MAX_CONTEXT_CHARS` 改为 `None`；`build_model_context` 在 `None` 时直接返回 `fixed + 全部历史`（跳过裁剪循环），显式传正整数时语义一字未改（仍保护最近一个完整工具轮次，仍抛 `LLM_CONTEXT_OVERFLOW`）。`AgentRuntime(max_context_chars=None)` 同上，构造校验改成「要么 `None`，要么 ≥ 1」。实测：40 轮 × 10 万字符（总 400 万字符）的历史在默认参数下逐条保留；显式传 200,000 时裁到 3 条。

**三、删掉上限就得删掉那个错误码。** `KNOWLEDGE_LIMIT_EXCEEDED` 一并删除：没有 `_check_limits()` 之后它再也抛不出来，留着就是假文档——本仓已有明文标准（M18 §8.23 记过「PUT 永不 404，声明它属于假文档」）。连带改动：`ErrorCode` 与 `ERROR_HTTP_STATUS` 少一个成员（条数注释 101/100 → 100/99）、`docs/05` §4.11 删一行且正文条数改 100、PUT 的 `error_responses` 去掉该码、`web/openapi.json` 与 `api.d.ts` 各少一行描述、`docs/14` 少一行，前端 `format.ts` 的文案映射与设置页的两个「x / 上限」计数器一并删除（页脚改成「已启用 N 条 · 术语表与用户档案正文合计 M 字」，不带分母）。

**四、补偿性改动：把上游的「上下文过长」翻译出来。** 本地不再预拦截之后，用户唯一能看出「窗口装不下」的地方就是上游的报错。`OpenAICompatibleClient` 现在按顺序判定 **429 → 上下文过长 → 其它 `LLM_REQUEST_FAILED`**，上下文过长映射成 `400 LLM_CONTEXT_OVERFLOW`（消息：「会话历史或知识库内容超出模型上下文长度，请开启新会话或缩短内容」），`details` 保留 `upstream_status` / `upstream_code` / `upstream_message`。识别同时看错误码（`context_length_exceeded`、`context_window_exceeded`、`string_above_max_length`）与措辞兜底（context length / maximum context / too many tokens / 上下文长度 等）。**已知边界**：表外措辞仍会落到通用 502；只映射建流前的非 2xx；判定完全外包给上游。

**五、行为变化与代价。** 以前超长会话会被本地悄悄丢掉最早的轮次继续跑，现在会一直带着完整历史直到模型窗口放不下，然后由上游拒绝——这是用户明确要的口径（宁可让模型决定，也不要把历史丢掉）。另一个后果是知识库可以无限加：索引每条一行、`glossary` / `profile` 全文每轮注入，加得太多会让**每一轮**都 400。当前内置量级是索引 1,892 字 + 全文段 2,438 字 ≈ 4.3 千字，离多数模型的窗口还很远。

**验证。** 后端 `.venv/bin/python -m pytest -o addopts= -q`：**1895 passed, 4 skipped**，退出码 0（比 M19 多 9 条，全是本次新增的行为断言：默认不裁 / 显式上限仍裁并抛 400 / 构造校验 / 上游上下文错误的 5 组参数化 / 知识库两条「不再被拒」）；`tests/agent tests/api tests/domain` 范围 961 passed。生成物：`scripts/dump_openapi.py --check`、`scripts/generate_api_guide.py --check`、`cd web && pnpm gen:api:check` 全部退出码 0。前端 `pnpm typecheck && pnpm test --run`（53 文件 / 540 项，比基线少 2 条：三条失效的上限用例合并成一条「不再拦截」回归）`&& pnpm build`（末行 `[sw_harness] SERVICE WORKER OK`）全部退出码 0。主 agent 另行实测：`DEFAULT_MAX_CONTEXT_CHARS is None`、400 万字符历史不丢轮次、`hasattr(ErrorCode, "KNOWLEDGE_LIMIT_EXCEEDED") is False`。

### 8.26 M21：Agent 主动提问与参数选择卡片

规格见 `docs/superpowers/specs/2026-09-29-m21-agent-question-card.md`，计划见 `docs/superpowers/plans/2026-09-29-m21-agent-question-card.md`。用户裁决（2026-09-29）：「让 agent 自己创建任务时，关于参数的选择，应该主动发送选择卡片，等待用户的选择后开始任务，不是让用户自己发消息回复。」同轮确认的三条边界：卡片只在**对话页内 + 本会话待答卡**（刷新/切页回来仍能看到，不动全局「待确认」面板与标题栏胶囊）；用户没回答时 **10 分钟后过期、直接结束本轮**；选项能力为**单选 + 多选**。

**一、动手前的事实。** 全仓没有「提问」概念：Agent 需要用户裁决参数时只能写在回复正文里，用户打字回复，模型再解析自然语言；`SYSTEM_PROMPT` 那句「不确定的参数要向用户询问，不要猜测」没有任何机制支撑。现成的阻塞式卡片只有人工确认链路（`ConfirmationService` → `confirmation` 表 → WS `confirm_request` → SSE `confirmation_required` → 对话内确认卡 → `POST /api/confirmations/{id}`），runtime 每 0.25 秒轮询确认状态，确认被拒/过期会以 `confirmation_resolved` 结束本轮。

**二、提问不复用确认链路（本次最大的架构裁决）。** 另起 `agent_question` 表、`QuestionService`（`maa_api/agent/questions.py`）与 `/api/agent/questions` 四个端点。理由有三：用户裁决要求提问**不**进全局待确认面板与胶囊，而复用 confirmation 会让它自动出现在列表、计数与推送里；语义也不同——确认是「授权一个已落库的高风险动作，批准后执行」，提问是「取一个答案后继续同一轮」，没有风险等级、没有授权窗口、也没有「拒绝后跳过同批后续调用」的语义；`confirmation` 表本身也表达不了「跳过」与「选项」。代价是一份与 `ConfirmationService` 同构的独立服务（落库先行 + 进程内 `asyncio.Event` 只做唤醒 + 重启清理）与一组自己的测试；好处是确认链路**一行未改**（`git diff --stat maa_api/agent/confirmation.py` 为空），风险面被隔离。

**三、时序与收尾口径。** 模型调用新工具 `ask_user`（group `interaction`、SAFE、`read_only=False`、`model_visible=True`，参数 `question` + `options[2..6]` + `multiple`）→ runtime 在 `_execute_tool_batch` 里拦截（不走 PolicyEngine、不落确认）→ `QuestionService.create()` 一个事务写 `agent_question`(pending) 与一条 `agent_audit`（`tool_name="ask_user"`）→ 广播 WS `question_request` → 发 SSE `question_required` → 挂起等待 → 用户点选 → `selection` 作为工具结果 `{"status":"answered","selected":[...]}` 回填成 tool 消息，**同一轮继续**。超时或用户点「跳过」时：先照常写出 tool 消息与 `tool_result`，再由 `_run_turn` 以 `finish_reason="question_unanswered"` 收尾——这是与 `confirmation_resolved` 同级的**正常终态**，不是错误。超时文案刻意**不带时长**（「提问超时未得到回答，本轮结束……」）：超时秒数可配置（`agent.question_timeout_seconds`，默认 600 秒），写死「10 分钟」会在改配置后失真，卡片上的倒计时由 `expires_at` 驱动。

**四、补了一个「跳过」动作（用户裁决之外的补充）。** 用户只说了超时，但提问挂起期间本轮 SSE 没有结束、输入栏发不出消息，没有跳过就要被卡满 10 分钟。跳过与超时共用同一条收尾路径（`question_unanswered`），后端多一个端点（`POST /api/agent/questions/{id}/skip`）与一个状态（`skipped`），审计记 `rejected` + 「用户跳过了提问」（**不写 `error_code`**：4 个新码里没有「跳过」，硬套会误导审计读者；确认链路的 `CONFIRMATION_REJECTED` 是另一回事）。若不需要，删掉端点与按钮即可，超时路径不受影响。

**五、审计与可见范围。** 每次提问写一条 `agent_audit`（pending → success/rejected/expired），`result_summary` 形如「用户选择：官服（Official）」——提问也是工具调用，审计页要能按 `ask_user` 筛出来，对话里的工具条与审计行通过 `audit_id` 对齐（wire 本身不带 `audit_id`，严格照规格的 12 个字段）。**不做** Web Push / 通知通道 / 全局面板计数：提问只出现在对话页。WS 新增 `question_request` / `question_resolved` 两个频道，作用仅是让前端失效待答查询（多标签页同步）；不加进 `WS` 的频道白名单，前端订阅会直接被拒。

**六、提示词与内置知识库。** `SYSTEM_PROMPT` 新增一段「需要用户裁决参数时」：候选之间选定（渠道、关卡、次数、是否碎石或用药、哪套基建方案）**必须**调 `ask_user` 发卡，不要在正文里让用户打字回复；选项最多 6 个、候选写进 label、问题正文不写答案；`selected` 就是裁决，拿到即照做、不再确认；跳过或超时后不要重发同一张卡；需要补一段文字或没有候选可列的开放式问题仍用正文提问。另外改了 4 条内置条目（`currency-sources`、`playbook-infrast-shift`、`playbook-promotion-planning`、`playbook-sanity-planning`）里「问用户是等还是稍后」「问用户是吃药、碎石还是等自然恢复」这类措辞，改成用 `ask_user` 发卡。**代价**：M19 的逐字一致性测试要求「规格 §4.6 的块 == 内置文件」，所以同步改了 M19 规格 §4.6 里这 4 个块（内容取自文件，不是手抄）。

### 8.27 M22：中断 Agent 正在执行的一轮

规格见 `docs/superpowers/specs/2026-09-29-m22-agent-interrupt.md`，计划见 `docs/superpowers/plans/2026-09-29-m22-agent-interrupt.md`。用户裁决（2026-09-29）：「agent 执行过程中，现在完全不能中断，需要加上中断功能。」同轮确认三条：①**只停 Agent 本轮**，游戏里已经跑起来的流水线继续；②**彻底撤回本轮在等、在跑的工具**（未批准的确认撤掉、等待中的工具结束），已入队的任务保留；③**刷新页面后仍能停**。

**一、被取代的决定。** M16 在 [§8.12](#812-m16前端-uiux-重构的偏离与记录) 与 docs/11 §8.5 写下「不做「停止生成」」，理由是 SSE 断开后 detached producer 仍在跑，纯前端的停止按钮只会断开显示、不会停止执行，容易误导用户。这条理由本身仍然成立——所以本次做的**不是**前端断流，而是真正的服务端中断：只有走新端点才会取消本轮，**断网/关页面仍旧不取消**（那条既有语义与它的测试都保留）。两者的区别在测试里有显式对照用例。

**二、中断的顺序是刻意的：先撤确认，再取消本轮。** `ConfirmationService._wait_and_execute` 醒来只认状态，用户批准就会执行，**与本轮是否还在等无关**——先取消本轮会让「取消期间被批准」变成一个真实的副作用。所以 `interrupt_turn` 先调 `abort_session_calls(session_id)` 把该会话仍 pending 的确认按**拒绝**语义终结（CAS `pending → rejected`、审计 `REJECTED`、广播 `confirm_resolved`、`event.set()`，worker 醒来看到非 approved 直接返回、永不执行），再 `task.cancel()`，等收尾完成后再撤一次（幂等）——覆盖「刚派发出去、行还没建好」的窗口。撤确认用拒绝而不是删记录：审计要能回答「这条确认后来怎么了」。

**三、在飞工具的三种处理。** ①**还没批准的确认** → 拒绝（见上）；②**正在执行的工具 worker**（普通工具，或已批准并已开始执行的确认）→ `task.cancel()`，`_execute_and_record` 捕获 `CancelledError` 把审计置 `FAILED` + 新错误码 `AGENT_TURN_INTERRUPTED`（409，只落在审计上）；③**挂起的提问** → `QuestionService.cancel_pending_for_session` CAS `pending → cancelled`（新增 `QuestionStatus.CANCELLED`）、审计 `REJECTED` + 「本轮已被中断，提问已取消」、广播 `question_resolved`。**没有新增 `AuditStatus.cancelled`**：`AuditStatus` 是对外契约，加枚举值要牵动迁移期语义与前端映射，`failed` + 明确的错误码已经能表达「没跑完，原因是被中断」。服务关闭时取消 worker 仍写 `SERVICE_UNAVAILABLE`（既有契约），靠 `abort_session_calls` 登记的 `_aborted_audits` 把两条语义分开。

**四、历史结构完整性是这次最大的坑。** assistant 的 `tool_calls` 消息先落库，tool 消息要等整批工具跑完才逐条落库。批次中途被中断就会留下「有 `tool_calls`、没有对应 tool 消息」的历史；M20 起历史不再按字符裁剪，下一轮请求会被上游以 400 拒绝。所以取消收尾必须为这批里**尚未落库**的调用补 tool 桩消息（`{"error": {"code": "AGENT_TURN_INTERRUPTED", …}}`），而且补之前要回库按 `tool_call_id` 去重（取消可能正好落在某条 tool 消息的落库过程中），桩消息必须**写在中断标记消息之前**（`tool` 消息要紧跟带 `tool_calls` 的 assistant 消息）。这一条在测试里用「批次中途中断 → 第二轮请求结构完整」精确覆盖。

**五、收尾与可观测性。** 已产出的部分助手文本 + 「本轮已被你中断。」落一条 `finish_reason="interrupted"` 的助手消息（用户读过的内容不会在刷新后消失，历史里也看得见中断点），随后发 SSE `interrupted` 与既有的 `message_end`，`_produce_turn` 的 finally 照旧释放会话锁并推 `_SSE_END`，所以**中断后立刻能发下一条消息**。`GET /api/agent/sessions/{id}` 新增 `turn_running`（直接读 `app.state.agent_runtime`，没有 runtime 时为 false，不为了这个字段现场构造 runtime），前端在 Agent 页开着时 10 秒轮询它，刷新/换设备后仍能按停止；**没有新增 WS 事件**——页面上已经有两组 10 秒轮询，多一个字段的收益不抵新增一个事件类型的契约面。取消收尾期间重复点停止不会二次 `cancel()`（第二次会打在收尾自己的写库 await 上，把落库与发事件打断，反而留下半截历史）。

**六、边界（如实写进文档，不粉饰）。** 中断**不碰流水线与队列**：不调 `stop_pipeline`、不取消任何已入队任务（用户裁决 §1）；**已批准且已在执行的工具可能已经产生副作用且无法回滚**——中断只保证「不再继续等它、不再有后续工具」，不自称可回滚；被动断开（断网/关页面）仍不取消本轮；一轮在「回答已结束、正在生成标题」的窗口里 `turn_running` 为 false，此时按停止返回 `interrupted=false`；无活动轮次时也会撤一次在飞调用（上一轮异常收场后挂着的确认/提问不该在这次「停止」之后复活），返回码仍是 `interrupted=false`。

**七、前端。** 流式期间发送按钮**原地**变「停止本轮」（`CircleStop` + `destructive-soft`，点击后进入 stopping 态），不必二次确认（停止是可恢复的）；顺手修掉一个既有 bug：主动 abort 后 `send()` 的 catch 因 `signal.aborted` 提前 return，把 `running` 永久留在 true（输入栏再也发不出消息）。会话详情 10 秒轮询让刷新后仍能停；`turn_running` 为真时发送也禁用（否则必吃 409）；`AGENT_SESSION_BUSY` 的文案改成「该会话仍有一轮在跑，可先停止它」；`interrupted` / `message_end` 两个 SSE 事件都要处理，否则输入栏会停在「Agent 正在处理…」。

**验证（主 agent 在收尾时亲自复跑）。** 后端 `.venv/bin/python -m pytest -q` → **1946 passed, 4 skipped**，退出码 0（比 M21 多 14 条，全是本次新增：中断时的流式收尾、等确认期间中断且之后批准不再执行、`wait_pipeline` 等待期中断（worker 取消 + 审计 `failed` + 新码）、提问挂起期中断、无活动轮次、批次中途中断后下一轮结构完整、`turn_running` 真假、被动断开对照）；`scripts/dump_openapi.py --check` 与 `scripts/generate_api_guide.py --check` 退出码 0；`scripts/agent_smoke.py` 与 `scripts/frontend_smoke.py` 末行均 `SMOKE OK`；`git diff --stat maa_api/scheduler maa_api/services/pipeline_runner.py` 为空（没碰流水线与队列语义）。前端 `pnpm gen:api:check`、`pnpm typecheck`、`pnpm test --run`（54 文件 / 558 项，新增 4 条）、`pnpm build`（末行 `[sw_harness] SERVICE WORKER OK`）全部退出码 0；新用例做过变异检验（拆掉 `interrupted` 处理、`turn_running` 恢复入口、`running:false`、409 文案会各自变红）。主 agent 另写独立探针（不经实现者测试夹具）：注册一个睡 60 秒的工具并让模型调用它 → 工具开始执行时 `interrupt_turn` → 断言 SSE 尾部是 `interrupted` + `message_end`、历史是 `user / assistant(tool_calls) / tool(桩) / assistant(interrupted)` 且每个 `tool_calls` 都有对应 tool 消息、审计 `failed` + `AGENT_TURN_INTERRUPTED`、重复中断返回 false、会话锁已释放、紧接着的第二轮正常收尾，末行 `PROBE OK`。

### 8.29 M23：会话里的图片与图表（媒体卡、任务留档截图）

用户裁决（2026-09-29）：「会话中，agent 应该有发送图片和 canvas 图表的能力。」同轮逐项确认八条：①对象是 MAA-API 内置 Agent 的对话页；②图片四类全要（agent 截的图直接可见、MAA 资源图、任务历史/日志里的既有截图、服务端渲染生成图）；③图表要结构化卡片、前端渲染、可交互并跟随主题；④图表用 **ECharts（canvas）**；⑤服务端渲染只做截图加工（裁剪/放大/标注框），不做图表 PNG；⑥**不做干员头像**（本地无图源），关卡地图改由本地 tile 数据渲染示意图；⑦补齐「任务历史里的截图」的**写入点**（流水线任务留档）；⑧任务失败自动截图挂日志一并做。规格 `docs/superpowers/specs/2026-09-29-m23-agent-media-cards.md`，计划 `docs/superpowers/plans/2026-09-29-m23-agent-media-cards.md`，分支 `m23-agent-media-cards`。

**一、媒体卡不新增任何结构，它只是工具结果的一部分。** 契约是 `result.media[]`（`image` / `item_icons` / `stage_map` / `chart` 四型），由 `maa_api/agent/media.py` 一处定义。卡片挂在 tool 消息上而不是消息表的新列上，于是：实时（SSE `tool_result`）与刷新后（历史消息）走**同一条渲染路径**、不需要新表/新端点/新错误码、审计天然记录了「agent 给用户看过什么」。代价是卡片不能独立于工具调用存在——这是刻意的：位置由调用顺序决定，本来就是对的。前端只认三种同源图片地址（`/api/images/<sha256>/(thumb|full)`、`/api/screenshots/<id>`、`/api/resources/items/icon?item_id=`），外域与 `data:` 一律丢卡；M23 之前落库的老 `get_screenshot` 结果没有 `media` 键，靠「工具名 + 四个字段」的兼容规则也渲染成图片卡。

**二、五个工具，全部靠声明 `SAFE` 免确认。** `send_screenshot`（已有截图：指定 id / 某条流水线最新一张 / 本会话最近一张）、`annotate_screenshot`（服务端加工）、`send_item_icons`（材料图标）、`send_stage_map`（关卡示意图）、`send_chart`（图表）。它们不进 `PolicyEngine` 的免确认白名单，而是走 `declared_risk is ToolRisk.SAFE` 那条既有分支——白名单是给「参数无关但风险特殊」的工具用的。只有 `annotate_screenshot` 是 `read_only=False`（它写文件与数据库行，因此与写操作串行），也只有它进 `SCREEN_TOOL_NAMES`：模型看不见画面就不可能圈对位置，视觉降级时要隐藏并拦截，**拦截文案按工具名生成**（不能把圈选说成「原子屏幕操作」）。「本会话最近一张」不能按 `trigger=agent` 取全局最近一张（`screenshot` 表没有 session 列），实现口径是**倒查本会话消息**里最后一条带 `screenshot_id` 的工具消息；REST 调用没有会话，必须显式给 `screenshot_id` 或 `pipeline_id`，否则 `INVALID_PARAMETER`。

**三、服务端渲染只做截图加工。** 固定顺序是**先画框 → 再裁剪 → 再放大**（放大图里框仍在原位）；坐标一律原图归一化值（0–1），参数上限 `boxes ≤ 16`、`label ≤ 32`、`zoom ∈ [1,8]`、放大后长边 ≤ 2048（剪裁块本身超限时有效倍数可以小于 1，输出有界优先）。输出**显式给质量 90**：`store_screenshot()` 不传 `quality` 时会落到 `adb.screenshot_quality`＝25，放大图会被二次压缩毁掉——这是有意的偏离，代价是这类图比普通截图大。标注文字用候选列表探测 CJK 字体，**一个都找不到就只画框**（label 仍在卡片图例里），不报错。加工结果照常落内容寻址存储并建一条 `Screenshot(trigger=agent)`；这是唯一在工具处理器内部 `commit` 的工具，安全性来自确认服务给处理器的是**独立会话**（`confirmation.py:984`），提交它不会牵动审计事务。

**四、关卡示意图用本地 tile 数据。** 索引是 `Arknights-Tile-Pos/overview.json`（4186 键的 dict，`filename` 100% 等于 `<键>.json`）；`code` 并不唯一（2133 个 code 里 944 个对应多关，`ISW-NO` 一个 code 对应 554 关），所以定位规则是 `stageId`/`levelId` 精确匹配优先 → 再按 `code` → 多命中按 `stageId` 字典序取第一并回报候选数 `candidates`。资源根按**内核真实加载链**查找：`<maa_path>/resource` + `maa-layers/{cache,custom}/resource`（后者覆盖前层）；`maa-layers/repo/` **不是**运行时增量层（它在资源更新时就被合并进 `<maa_path>/resource`）。单格是 3 字符码 `<地形><可部署><高度>`：地形 5 类（`#` 阻挡 / `~` 坑洞 / `w` 水域 / `!` 特殊机制 / `.` 普通地面，107 个 `tileKey` 全部显式成表并有夹具测试保证零遗漏），可部署与高度直接取 `buildableType` / `heightType`；**起点与终点不来自 `tileKey` 而来自 `isStart`/`isEnd` 布尔**（`tile_start` 只占 `isStart` 的 41%），单独出 `start`/`end` 坐标数组。`legend` 是**片段码**（1 字符只讲地形、2 字符只讲「可部署+高度」），与规格 §3.1 例子里 3 字符码的写法不同——这样图例能分别表达「出现了这类地形」与「出现了这种可部署组合」，前端按长度分派渲染。tile 行序**原样输出不翻转**，画面方向由前端一个常量（`BOTTOM_UP_ROWS`）负责，见「八、待验证」。

**五、干员头像不做，材料图标已有端点。** 本地没有任何干员立绘图源：MaaCore 的 `AvatarCacheManager` 只从战斗画面里识别头像（`load`/`set_avatar`），三个 `cache/avatars/` 目录都是空的。材料图标则早就有 `GET /api/resources/items` 与 `GET /api/resources/items/icon?item_id=`（`resource/template/items/` 480 张 PNG 来自 `item_index.json`），M23 只是让 agent 能用它。头像是否引入远端图源（PRTS/akhr 类）**留待裁决**：那要新增网络依赖、本地缓存、限流与离线降级。

**六、任务留档截图与失败日志附件。** 流水线任务进入 `completed` / `failed` / `skipped` / `crashed` 终态时留一张 `Screenshot(trigger=task_snapshot)`（带 `pipeline_id`/`task_id`），`cancelled` 不留；**`crashed` 是我加的**（规格只写了前三种）——内核崩在任务里正是最需要现场的情况。钩子只加在 `_execute_pipeline` 里 `_execute_task` 的唯一汇聚点（任务内部 20 处 return 一行未动），整段**失败即降级**：设备缺失、抓图异常、10 秒超时、落盘落库失败都只记 WARNING，绝不改写任务终态、不重试。`failed`/`skipped`/`crashed` 还会把这张图挂到日志上，做法是**新写一条 `source=task` 记录**而不是给既有失败日志补字段——既有那条记录在任务终态落库之前就已经 offer 了，且 `LogRecord` 一旦 offer 不可改；附件字段与前端 `logImage()` 认的形状对齐（`sha256` + `/api/images/<sha>/(thumb|full)`）。hub 通过 `bind_log_hub` **后置注入**（照 `bind_notify_service` 的范式），不给 `PipelineRunner.__init__` 加参数，因为 `app.state.pipeline_runner_factory` 是可替换钩子。附件与留档复用同一次截图（内容寻址天然去重，`screenshot` 只有一行）。

**七、图表用 ECharts，上限分两级。** 这推翻了 [09 §3.5](./09-前端重构方案.md) 记的 recharts 倾向（用户裁决 §4）。只经动态 import 进独立 chunk，按需注册 Line/Bar/Pie + Grid/Tooltip/Legend/Title + CanvasRenderer，不引 React 包装库、不加手动分包；主题色板是新增的 `--chart-1…--chart-6`（浅/深两套），运行时用 `getComputedStyle` 读并订阅主题变化重建。上限分两级：**字段级**超限（类目/系列/点数/长度/枚举/额外字段）走既有链路 → `TOOL_ARGS_INVALID`(422)；**语义级**越界（总点数 > 600、序列化 > 24 KB、NaN/Inf、`line`/`bar` 的 `len(values) != len(categories)`）→ `INVALID_PARAMETER`(400) 并在 message 里指明哪一项、实际多大。两级都要满足是因为 docs/04 §5.8 的 32 KB tool content 纪律**在代码里没有兜底**（仓储明确写成「调用方纪律」），产出方必须自己守住。前端永远提供「数据」折叠表格：它是无障碍兜底，也是 ECharts chunk 加载失败时的回退。

**八、模型上下文与提示词。** 媒体工具结果**落库不变**，回灌模型时压成一行占位（保留卡片类型与标题）；失败结果保留 `error` 原文，否则模型看不到越界原因、`INVALID_PARAMETER` 的自愈循环就断了。`get_screenshot` 的视觉回灌语义一行未改（仍然只把最新一张喂给多模态模型）。系统提示词新增一段（位置受既有段落顺序断言约束）：给用户看画面用 `send_screenshot`、说不清位置用 `annotate_screenshot`、数据分布用 `send_chart` 且**数据必须来自工具真实返回**、材料图标与关卡布局各有工具、**不要用 markdown 图片语法**、一次最多 8 张图与 6 个系列。
