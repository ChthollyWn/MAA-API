# 决策记录

## 1. 有实质权衡的决策

### ADR-01 · 前端选 Vite + React 而非 Next.js

讨论中曾考虑"改成纯 Next.js 前后端不分离"。否掉它的根本原因是后端搬不走：MaaCore 只提供 C API 与官方 Python 绑定，任务调度、ADB 操作、APK 安装全部依赖 Python，Node 里没有 MaaCore 绑定。因此 Next.js 不可能吃掉后端，只能做一层 BFF。

这让"不分离"只剩两种真实形态。静态导出（`output: 'export'`）确实能做到单进程单端口，但 Server Components、API Routes、middleware、SSR、ISR 全部失效，此时 Next.js 相对 Vite + React 的唯一增益是文件路由约定，代价是更重的工具链。独立 Node 服务加代理则把进程从一个变成两个、Docker 镜像要同时装 Node 与 Python，实质上比现在更"分离"；它唯一的实质收益是能把 `access_token` 藏进 httpOnly cookie。

决定性因素是 WebSocket。既然选了 WebSocket 推实时日志，而 Next.js App Router 没有原生 WebSocket 支持，独立 Node 服务方案要么自建 custom server 转发、要么让浏览器绕过代理直连后端（代理就失去意义）。加上移动端优先这一项 Next.js 也无加成，所以选 Vite + React：能达成单进程不分离，Tailwind 写移动端响应式最顺手。

### ADR-02 · MaaCore 用子进程隔离，而非同进程热替换

内核热更新有四种可能路径，选了工程量最大但唯一优雅的一种。

同进程 `dlclose` 加 `dlopen` 真热重载被否：`dlclose` 在有活跃线程和未释放句柄时行为未定义，MaaCore 也不保证支持重复加载，段错误风险高且无法测试覆盖。下载后自动重启整个服务进程可靠但 API 会中断，前端要处理重连，且正在进行的其他请求全部失败。只下载不重启、提示手动重启，等于没有实现"热"更新。

子进程隔离一次性解决了三个问题：内核更新只重启子进程、native 崩溃不再拖垮 API 服务、启动期不再被网络 IO 阻塞。代价是执行层需要重写、回调要跨进程传递。考虑到崩溃隔离与启动解耦这两项收益本身就是现有架构的痛点（`scheduler.py` 在 import 阶段连 ADB、失败则服务起不来），这个代价是值得付的。

### ADR-03 · IPC 用 multiprocessing Queue

候选还有子进程内跑轻量 HTTP 服务、Unix domain socket 加自定义协议、以及 ZeroMQ 或 gRPC。

选 Queue 的理由是同一代码库、同一依赖、对象直接传递，实现成本最低，且 `Queue` 的 pickle 序列化对纯 dict 消息完全够用。子进程内跑 HTTP 服务边界最清楚、未来能把内核挪到其他机器，但为单机双进程引入一整套 HTTP 栈属于过度设计。UDS 需要自定义消息分帧，ZeroMQ 与 gRPC 各多一个重依赖。

已知代价是截图这类大 payload 走 Queue 有性能开销（1280×720×3 约 2.7 MB，pickle 加管道往返数十毫秒），处理办法是落盘传引用，并预留 `shared_memory` 作为后续优化（见 [02-系统架构设计 §3.3](./02-系统架构设计.md)）。

### ADR-04 · 响应格式全面改标准 HTTP 状态码

现状是所有接口返回 HTTP 200，业务码在 body 的 `code` 字段（10200 / 10400 / 10401 / 50000）。这是一次破坏性变更，选它而非"新接口用新格式、旧接口保持兼容"。

理由是这次重构本身已经废弃了全部旧前端与旧接口路径，没有需要兼容的外部消费者；而保留两套格式会让错误处理、OpenAPI 文档、agent 的错误判断都要分叉。既然开放 API 是明确目标，就应该一次做对 —— agent 依赖 HTTP 语义判断成败，"一切都是 200"会让它无法区分成功与失败。

错误体选自定义结构 `{"error": {"code": "...", "message": "...", "details": {...}}}` 而非 FastAPI 默认的 `{"detail": "..."}` 或 RFC 9457 Problem Details。自定义结构的核心价值是那个可枚举的错误码字符串：agent 能据此做确定性分支（`CORE_NOT_READY` 该等待、`DEVICE_NOT_CONNECTED` 该重连、`CONFIRMATION_REJECTED` 不该重试），而人类可读的 `message` 做不到这一点。

### ADR-05 · 不复用 feat/0515 分支的代码

该分支已实现服务日志接口、三种更新接口、多渠道鉴权、配置模板与懒加载，看起来能省一大半后端工作。但它是在旧架构（同进程内核、内存状态、业务码响应）上写的，与子进程隔离、SQLite 持久化、标准状态码三项决策全部不兼容。迁移它的代码等于先理解再改写，成本不低于重写，还会带入旧架构的隐含假设。

但其中已验证的**外部接口常量**必须沿用：官服 APK 下载直链、B 服 biligame 接口及其 `game_base_id`、两个渠道的包名、`dumpsys` 解析版本号的正则。这些是有人花时间试出来的事实，重新查证只会浪费时间。

### ADR-06 · 鉴权维持单 token

选了单 `access_token` 加四渠道传递（Bearer / `X-Token` / query / cookie），否掉了 API Key 体系与限流。理由是单用户自用场景，多 key、命名、吊销、权限范围都是无人使用的复杂度。



### ADR-07 · Agent 的画面理解只用截图，不接 OCR

核实确认 MaaCore 的 OCR 没有独立 C API —— 内核内置 `libfastdeploy_ppocr`，但只能通过 `tasks.json` 的 task 定义间接触发，无法直接调用"识别这块区域的文字"。

因此 agent 要理解画面只有两条路：多模态模型看截图，或项目自己另接一个 OCR（PaddleOCR / RapidOCR）。选了前者，理由是不引入重依赖（OCR 模型文件与推理运行时体积可观），且多模态模型对"当前在什么界面"这类整体判断比 OCR 的文字碎片更有效。

代价是内置 agent 必须配置支持视觉的模型，纯文本模型只能做任务编排。这个约束会在设置页明确提示，并提供能力自检。另一个代价是识别准确率未经验证，因此 [12-实施计划与里程碑 §5](./12-实施计划与里程碑.md) 要求在 M11 阶段就手动验证模型对游戏界面的理解能力，而不是等到 M13。

### ADR-08 · 自定义任务开放到最强层级

允许 agent 通过增量资源机制注入自定义 `tasks.json` task 定义，这是 MAA 的底层任务 DSL（模板匹配、OCR、点击偏移、任务跳转）。这也是"应对 MAA 未适配的新活动"这个场景唯一的可行路径 —— 纯原子操作无法固化成可复用的能力。

风险是格式错误的 task 定义可能让 `AsstLoadResource` 失败，而资源加载失败意味着内核不可用，这是少数能真正搞坏服务的操作。因此配了四层防护：注入前 schema 校验、自定义资源与官方 OTA 缓存目录分离（便于一键清空）、加载失败自动回滚并重载、task 名强制带 `Custom_` 前缀（不允许覆盖官方定义）。

即便如此，这一层仍归入需人工确认的 `DANGEROUS`。曾考虑收紧为"只允许前端上传、agent 只能引用已有的自定义 task"，已确认不采纳 —— 见 §3 的对应条目。

### ADR-09 · 队列按优先级排序但不抢占

三个来源（前端手动、agent、定时任务）争夺唯一内核实例。选了统一队列加优先级排序，否掉了"正在跑就直接拒绝"（现状）、纯 FIFO、以及前端手动可抢占三种方案。

否掉现状是因为它让定时任务与 agent 在冲突时静默失败。否掉纯 FIFO 是因为人在界面前点按钮的期待与后台定时任务不同。否掉抢占是因为中途打断正在执行的 MAA 任务可能让游戏停在不确定的界面状态，恢复成本高且难以预测。

用户想立刻插队时需要显式停止当前流水线再提交，这是前端的一个明确按钮而非隐式行为。同时 `stop_pipeline` 被刻意设为 agent 免确认的工具，确保发现异常时能及时刹车。

### ADR-10 · 单子进程但按多实例设计接口

首版只跑一个 MaaCore 子进程、绑一台设备，维持"不允许多实例"的现有语义。但内核调用统一经 `CoreRegistry.get(core_id)`，`pipeline` 表带 `core_id` 字段，REST 路由预留 `?core_id=` 参数，`DeviceManager` 按 `core_id` 维护独立状态。

这么做的成本很低（多传一个恒为 `"default"` 的参数），收益是将来扩展到多设备或多账号并发时，路由层与数据模型不需要改动，只需实现 `CoreRegistry` 的多实例管理与设备绑定配置。相比之下，如果先写死单实例，多设备需求到来时数据库要加列、全部路由要改签名。

### ADR-11 · 原子操作改会话级授权，不逐次确认

原子操作（点击坐标、滑动、输入文本、按键）不属于"消耗类"或"破坏类"，但它们绕过 MAA 的全部识别与容错，点错位置可能触发任意游戏内操作。最初设计把它们归入需逐次确认。

否掉逐次确认是因为它让"卡死救援"这个核心场景不可用 —— agent 从未知界面复位可能需要连续几十次截图与点击，每次弹卡片等于让用户手动操作一遍。也否掉了完全免确认，因为那等于把无约束的屏幕控制权交给 LLM。

选定的方案是会话内首次尝试时弹一次授权确认，批准后该会话获得一个默认 15 分钟的窗口（可配，上限 60 分钟）。四条约束限制它的影响面：授权粒度是"会话加时间窗口"而非全局开关；只覆盖原子操作，消耗类与破坏类仍逐次确认；随时可撤销且前端常驻提示条显示剩余时间；审计不降级，每次操作照常落库并记录凭哪次授权执行。

授权状态落库而非只存内存，因为服务重启后不应悄悄延续一个用户以为早就结束的授权。详见 [11-Agent模块设计 §4.3](./11-Agent模块设计.md)。

### ADR-12 · 活动资源两条通道首版都做

核实推翻了"官方 OTA 不止 `tasks.json`"这个前提：`api.maa.plus` 的资源树对国服只有一个 `tasks.json`，而现有代码已经在拉它。这意味着只做通道 A 等于把现有功能重做一遍 UI，拿不到任何新资源，需求 3 的"活动资源热更新"会名存实亡。

因此首版同时实现通道 B（`MaaResource` 仓库），它才是 MAA 桌面客户端"资源更新"按钮背后的机制，含地图坐标、关卡表、公招数据与模板图。下载走 GitHub 仓库压缩包而非 Mirror 酱 —— 后者的版本查询免费但下载需要付费 CDK，不适合作为首版的硬依赖（它仍被用作 `raw.githubusercontent` 不可达时的版本查询兜底）。

代价是每次更新要拉一个全量包：实测压缩包 13.3 MiB、解压后 107 MB。因此先查 `version.json` 的 `last_updated` 再决定是否下载，无更新时的开销只有一次约 100 字节的 JSON 响应；镜像回退链与内核更新共用，含可配置的加速前缀。通道 B 标记为 `required=False`，失败时退回内核自带资源，功能不缺失只是滞后（实测滞后约 9 天）。

落点选了一个独立目录而非直接覆盖 `<maa_path>/resource/`。覆盖式落点更简单，官方给手动更新用户的指引也是这么做的，但它会被内核更新解压覆盖掉，每次升级内核都要重新同步一遍。代价是加载链从两层变四层，`LOAD_RESOURCE` 命令的签名必须从单个增量路径改为有序列表。

**这个独立目录连同另两个增量层一起放在 `<maa_path>` 之外**，落在 `resource/maa-layers/{repo,cache,custom}/`（与 `resource/lib/` 平级）。中间一版曾把三层放在 `<maa_path>` 下，沿用 MAA 官方 SDK 示例把 OTA 缓存写进 `<maa_path>/cache/` 的习惯，但那样内核更新的原子替换会连带清空三层——`repo/` 与 `cache/` 重下即可恢复，`custom/` 没有远端副本、属于永久丢失。补救方式是在替换后把三个目录从备份搬回新目录，但这给内核更新增加了一条必须成功的迁移步骤与对应回滚路径，迁移出错就静默丢数据。移出 `<maa_path>` 之后该故障类别整体消失，内核更新不需要任何迁移步骤，顺带也解开了 `<maa_path>/cache/avatars/`（内核自建的头像缓存）与通道 A 落点共用同一目录的纠缠。这样做不违反任何内核约束：`AsstLoadResource` 只接受一个路径并去读 `<path>/resource/`，增量层在磁盘上的位置自由，唯一的硬约束是基础资源必须是第一次调用（`ResDir` 由首次调用永久钉死）。代价是偏离官方示例的目录习惯，但路径本就由我们传入。

通道 B 的备份**只保留最近一份**（每份 107 MB，通道 A 的"保留 5 份"策略照搬会吃掉半个 G）。代价是只能回退一步：GitHub 的分支压缩包只给当前 HEAD，取更早的版本要按 commit 拉 `/archive/{sha}.zip`，首版不做。考虑到通道 B 同步的是数据文件而非会写坏行为的 task 定义，需要连退多版的场景很难构造。

合并语义已通过核对 `ResourceLoader` 源码确认（数据文件整文件替换、模板图按文件覆盖、增量目录允许残缺），但源码与本地内核未必同一构建线，仍列了三项待实测假设与退路。详见 [07-热更新方案 §3.3](./07-热更新方案.md)。

### ADR-13 · 首版就上 Tailscale Serve 作为 HTTPS 入口

PWA 的 Service Worker 与 Web Push 要求安全上下文，局域网 IP 加 HTTP 不满足。原方案是三段式递进，首版接受降级。

改为首版直接上第二段（Tailscale Serve），理由是降级形态下**推送不是"体验变差"而是"功能不存在"** —— 而 agent 的人工确认恰恰是最需要即时触达的事件，靠邮件兜底的延迟会让确认窗口形同虚设（相关的超时取舍见 ADR-14）。自签证书加手动信任被否（iOS 要装描述文件并在两处开关里启用），浏览器标志绕过被否（Android 上需要 root，而移动端是主场景）。

代价是每台访问设备要装 Tailscale 客户端并登录同一 tailnet。这同时是一项收益：不在 tailnet 内的设备连端口都摸不到，实际上比单 token 鉴权更强。

非安全上下文的分级降级仍然要实现，定位从"首版形态"改为"客户端未连通时的兜底"。详见 [09-前端重构方案 §12.4](./09-前端重构方案.md)。

### ADR-14 · 确认超时按风险分级，并为 Chromium 做推送按钮

原定确认超时统一 120 秒。这与推送触达的链条长度不匹配 —— 用户要听见、解锁手机、点开应用、读完卡片再决定，结果是高风险操作几乎总是超时自动拒绝。

改为分级：消耗类与破坏类默认 10 分钟，原子操作的会话授权保持 120 秒，两者可配置。否掉了统一放长（会让一个已经没人管的授权请求长时间挂着）与完全不设超时（agent 调用无限期挂起，避免调用无限期挂起）。

同时为 Chromium 平台做推送上的「准许 / 拒绝」按钮作为渐进增强，但**流程不以它为前提**：核实确认 WebKit 完全忽略 `actions`，iOS 与 macOS Safari 都不渲染按钮，且它还忽略 `requireInteraction`（通知不常驻）。两个平台共有的路径只有"点通知体 → 深链回卡片 → 应用内批准"。

这个决策连带暴露了一个鉴权冲突：从推送按钮批准要在 Service Worker 里发 `POST`，而 Service Worker 读不到 localStorage（非 window 上下文），同源自动携带的 cookie 又被 §3 的决策限制为不能用于写操作。解法是 token 增加一份 IndexedDB 副本供 Worker 读取并注入 `X-Token` 头，而不是给 cookie 开写操作特例 —— 开特例等于在最容易被忽略的路径上永久留一个 CSRF 口子。代价是三处存储的写入与清除必须同步，否则会出现"页面已登出但通知按钮还能批准操作"。详见 [09-前端重构方案 §13.2](./09-前端重构方案.md) 与 §10.1。

## 2. 其余决策速记

| 决策 | 选择与理由 |
|---|---|
| 移动端优先 | 实际使用场景是在手机上远程操作，底部 Tab 单手可达，桌面自适应即可 |
| PWA | 可添加到主屏、离屏缓存、推送确认通知。约束是需要安全上下文，见开放问题 |
| WebSocket 而非 SSE | 需要双向通道（确认响应、订阅管理），且 agent 事件推送可复用同一连接 |
| 三路日志全要 | 排查问题时任务日志、服务日志、内核 debug 日志缺一不可，分标签页展示 |
| 活动资源清单驱动 | 两条通道的获取方式不同（单文件条件请求 vs 仓库压缩包），显式清单让新增条目不必改代码，外服支持将来只需补条目 |
| 内核只用 stable | 挂机场景稳定性优先。内核是整个服务的地基，一个行为异常的预发布版本造成的排查成本远高于早几天适配新活动的收益。保留枚举与落库字段以便将来放开 |
| 生息演算修复后支持 | `ReclamationTask` 因参数字典把变量当成键而从未可用，在 M0 一并修掉，9 种任务类型全部支持 |
| 游戏更新带版本对比 | 没有版本对比就无法判断是否需要更新，只能盲目下载数 GB |
| ADB 四时机重试 | 启动等待、任务前预检、断线自动重连、手动重连各自解决不同失败模式 |
| ADB 失败不阻塞启动 | 配合内核懒加载，让服务可用性不依赖模拟器是否已启动 |
| 仅官服加 B 服 | 实际只用这两个，支持台服与国际服是无人使用的复杂度 |
| 渠道全局默认可覆盖 | 日常只用一个渠道，但保留单任务覆盖以应对特殊情况 |
| 单账号 | 无多账号需求，`account_name` 参数仍保留可用 |

## 3. 细化过程中浮现并已拍板的问题

这些问题在细化方案时浮现，不属于最初的决策范围，已逐项确认。记在这里是为了留下"为什么是这样"的依据。

**自定义 task 注入允许 agent 自主生成，但需确认。** 确认卡片展示完整 JSON。备选的"只允许前端上传、agent 只能引用已有的"被否，因为那会削掉"应对 MAA 未适配的新活动"这个目标场景的核心能力。已知的不足是长 JSON 在手机上审阅困难，缓解手段是 ADR-08 的四层防护（schema 校验、目录隔离、失败回滚、`Custom_` 名称前缀）而非事前人工审阅。详见 [11-Agent模块设计 §7.3](./11-Agent模块设计.md)。



**`AsstGetItemName` 不纳入。** macOS 版 `libMaaCore.dylib` 导出了这个符号，但头文件里完全没有声明，参数与返回语义只能靠逆向推测；且 Linux 版根本没导出它，纳入了在部署环境也用不上。掉落物品名称改从 MAA 资源目录的 `item_index.json` 读取。详见 [03-MaaCore内核层设计 §1.2](./03-MaaCore内核层设计.md)。

**cookie 渠道收窄，WebSocket 鉴权按客户端类型拆分。** 这两项都偏离了"四渠道等价"的原始决策，确认后实施。

cookie 只允许 `GET` / `HEAD` 与 WebSocket 升级，写操作必须走 header 或 query。需要说明的是 CSRF 风险本身已被 `SameSite=Lax` 挡住大半（跨站 POST 不携带 cookie），所以这层收窄属于深度防御而非必需 —— 采纳它的实际收益是让"写操作必须显式带凭据"成为一条简单且无例外的规则，不必依赖 cookie 属性配置正确。

WebSocket 方面，浏览器的 WebSocket API 无法自定义 header，只剩 query 与 cookie 两个选择。浏览器走 cookie（token 不进 URL，避开代理与日志记录），agent 与脚本走 query（无 cookie 容器，且实现简单）。详见 [05-API规范与路由清单](./05-API规范与路由清单.md) 与 [06-实时日志与WebSocket](./06-实时日志与WebSocket.md)。

**MaaCore debug 日志只落 `WARNING` 及以上。** 这一路密度极高（运行期每秒数条），且内核自己的 `asst.log` 里已有完整副本。全量经 WebSocket 实时推送保持不变，只是落库设阈值；需要翻更早的完整 debug 日志时由接口 tail 文件。阈值做成可调配置。这偏离了"三路全部落库"，确认后实施。详见 [04-数据模型与持久化](./04-数据模型与持久化.md) 的保留策略一节。

**内核命令超时返回 504 而非 502。** 区分的价值不只是语义精确：502 表示下游明确答复"办不成"，而 504 表示下游没答复、操作**可能已执行一半**，两者的正确处置不同 —— 504 后应当查状态而非重试，盲目重试可能把同一个任务提交两遍。因此前端的重试策略必须把 504 排除在自动重试之外（见 [09-前端重构方案 §10.3](./09-前端重构方案.md)），这是采纳 504 后连带的必要改动。

同一规则应用到 `LLM_TIMEOUT`（同样是上游未在时限内响应），也改为 504；`UPDATE_DOWNLOAD_FAILED` 保持 502，因为下载中断是传输层给了明确结果而非没答复。判断依据统一为"有没有收到答复"，不是"失败得有多严重"。详见 [05-API规范与路由清单 §2.4](./05-API规范与路由清单.md)。

## 4. 待补齐的契约缺口

这些是文档细化过程中暴露的接口契约缺口，不需要你拍板，但实现时必须补齐，否则对应功能不完整。

**缺少登出端点。** 如果 WebSocket 鉴权采用 cookie 方案，cookie 会被设为 HttpOnly（否则 XSS 可直接读取），而 HttpOnly cookie 前端 JavaScript 删不掉。结果是用户"登出"后 cookie 仍在，WebSocket 依然能连上。需要补一个由服务端清除 cookie 的端点（如 `DELETE /api/system/auth/cookie`）。

**`x-risk` 的 OpenAPI 扩展关键字尚未定义。** 参数 schema 需要标记哪些字段属于消耗类（`Fight.stone`、`Fight.medicine`、`Recruit.expedite`、`Mall.shopping`、`Roguelike.investment_enabled`），供前端在表单上给出醒目提示。这份清单必须与 agent 侧 `PolicyEngine` 的判定规则（见 [11-Agent模块设计 §4.1](./11-Agent模块设计.md)）共用同一处定义，否则会出现"前端不提示但 agent 要确认"或反之的不一致。

**`x-widget` 的取值集合需要扩充。** 几个结构化参数无法用基础控件表达：`Fight.drops` 是物品 id 到数量的映射、`Recruit.recruitment_time` 是 Tag 等级到分钟数的定长映射、`Infrast.facility` 是有序列表（顺序即换班顺序，不是普通多选）。需要追加 `item-count-map`、`duration-map`、`ordered-list` 三种控件类型，前端据此渲染专用编辑器。详见 [09-前端重构方案](./09-前端重构方案.md) 的动态表单一节。

## 5. 需要实测验证的假设

以下几条是文档里基于头文件、二进制符号或上游源码推断、但本地没有运行样本可以确证的设计前提。它们不阻塞开工，但必须在对应里程碑动手前用最小脚本跑一次，否则会照着错误的假设写实现。

**`AsyncCallInfo` 回调的载荷结构。** 迁移到 `AsstAsyncConnect` 的设计依赖这个回调来判定异步连接的最终结果，方案为它设计了两级 Future（外层等 `async_call_id` 返回、内层等回调送达结果）。但本地调试日志里没有这个回调的样本，`details` 里的字段名（`async_call_id` 与 `ret` 的实际键名与嵌套层级）只能从头文件推测。需要在 M1 动手前跑一个最小脚本，实际触发一次异步连接并打印原始回调 JSON。详见 [08-ADB连接与账号渠道](./08-ADB连接与账号渠道.md)。

**本地内核的构建来源。** 本地头文件带有 `ClientType` 相关注释而上游 `dev` 分支没有，加上 macOS 库导出了头文件未声明的 `AsstGetItemName`、而 Linux 库连 `AsstGetMapLevelKey` 都没导出，三条线索都指向本地库不是同一条发布线的构建产物（疑似 `dev-v2`）。这个结论的影响面超出单个 API：如果本地是非发布构建，那么文档里所有"某 API 可用"的判断都应改为运行期能力探测而非静态假设。方案已按平台探测加优雅降级来写（见 [03-MaaCore内核层设计 §1.2](./03-MaaCore内核层设计.md)），但建议在真机上核对一次内核版本号与构建信息。

以下四条是通道 B 带来的，都在 M7 动手前一并验证（见 [12-实施计划与里程碑](./12-实施计划与里程碑.md) M7），验证不通过时的退路是放弃独立目录方案、改为覆盖式落点。

**增量资源的合并语义在本地内核上成立。** 核对 `ResourceLoader` 源码得出三条结论：增量目录缺文件会被静默跳过而非判失败、数据文件是整文件替换、模板图按文件覆盖而非整目录替换。第三条最关键——若实际是整目录替换，加载通道 B 会让内核从 2464 张模板图掉到 1009 张，后果是大面积识别失败。但源码读的是发布线分支，而本地库疑似另一条构建线（见上一条）。验证方法：按完整链条加载后，确认一个只存在于通道 B 的 `Arknights-Tile-Pos` 条目能解析，同时确认一个通道 B 没有、只在内核自带 `template/` 里的模板仍可用。

**`TilePack` 重载时会清空既有条目。** 它把每个关卡的文件路径解析为"被加载的 `overview.json` 所在目录 + filename"并追加进列表。通道 B 的 `Arknights-Tile-Pos/` 实测是本地的严格超集，所以路径整体重定向本身安全；但若列表在重载时不清空，同一关卡会留下两条记录。

**重载后模板匹配缓存会失效。** `TemplResource` 有一个 revision 计数用于通知匹配器丢弃缓存，需要确认重载确实让它递增。否则运行中热重载会继续拿旧图做匹配，表现为"更新成功但行为没变"，且极难归因。

**整条加载链的重载耗时。** 只有通道 A 时是几百毫秒，加上 107 MB 的通道 B 目录后未知。[02-系统架构设计 §3.4](./02-系统架构设计.md) 把 `LOAD_RESOURCE` 的命令超时从 120 秒上调到 300 秒是按最坏情况留的余量，不是测量结果；同时 [03-MaaCore内核层设计 §4](./03-MaaCore内核层设计.md) 的心跳阈值在这条长命令执行期间需要放宽多少也取决于这个数。测出来后两处都可以回调。

## 7. 全部决策已确认

至此没有待你拍板的事项。§6 的默认值与下面两项在方案里都已定稿，只是取值可按实际使用回调。

**更新检查：每天自动一次，只检查不下载，有更新则通知；并保留手动「立即检查更新」入口。** 下载与安装始终手动触发。理由是"有更新"和"现在适合更新"是两件事 —— 内核更新要重启子进程、游戏包 1.8 GB 可能在移动网络下产生费用、通道 B 要下 107 MB，时机该由人定；而只做检查几乎没有代价。配套约束是通知要合并（三个目标一条）且同版本只通知一次，否则会连续多天收到同一条提醒而最终去关掉通知。检查失败只记日志不推送，手动检查的失败则必须在界面报错。详见 [07-热更新方案 §5.6](./07-热更新方案.md)。

**`InfrastTask.threshold` 以 0.3 为期望值**，现有代码签名里的 `0.5` 是错的。但新模型仍不设服务端默认值（`default=None`）：不传则由内核用自己的默认值，0.3 只作为 OpenAPI `description` 与前端占位提示里的说明文案。这样内核将来调整默认行为时服务端不会产生偏差。详见 [01-重构总览与现状评估](./01-重构总览与现状评估.md) 的缺陷清单。

## 8. 实施后的偏离、补充与待验证事项

### 8.1 实施偏离

**M6 · MAA 路径的在线修改与只读约束冲突，待拍板。** [12 的 M6](./12-实施计划与里程碑.md) 要求"改 MAA 路径重启子进程"，而 [04 §11](./04-数据模型与持久化.md) 与 [05 §4.13](./05-API规范与路由清单.md) 把 `app.maa_core_path` 定为只能由 `config.yaml` 或环境变量设置的只读项。实施按后者执行，设置 API 中该项只读（`maa_api/settings.py`）。是否开放在线修改仍待决定；若开放，需要补一条"修改后重启子进程"的热生效路径。

**已拍板（M14 开工前）：保持只读。** `app.maa_core_path` 继续只能由 `config.yaml` 或环境变量设置，在线修改保持 409/只读语义，不新增「保存后重启子进程」的热生效路径。这样 12 号文档 M6 的那句要求作废，[12](./12-实施计划与里程碑.md) 的 M6 条目按本裁决理解。理由：内核路径变更会同时影响已加载的资源层、正在排队的任务与 per-run Copilot 快照根目录，热改需要一条跨模块的迁移路径，而实际使用中换内核路径是低频操作，改配置重启服务足够。

**M10 · 手动 REST 的强制原子操作尚未接入 Agent 审计。** `force=true` 绕过流水线互斥时，`/api/device/*` 与 `/api/core/back_to_home` 的手动 REST 路径只写强制介入警告日志，不创建 `agent_audit` 记录；这不同于 [02 §5.3](./02-系统架构设计.md#53-原子操作的并发) 与 [05 §6.3](./05-API规范与路由清单.md#63-device) 早期方案中未区分调用渠道的审计表述。本文档据此限定为手动 REST 路径的现状；Agent 工具调用仍按 M11 的 Agent 工作流审计契约描述与实现。

### 8.5 M13 Task 4：core incident key 与启动恢复的代际隔离

`CoreSupervisor.generation` 每次服务进程启动会重置，因此 core incident 的持久 key 增加 lifespan 级 boot UUID：`core:<core_id>:<boot_uuid>:<generation>`。同一服务生命周期内按该 key 去重，进程重启后不会把新一代崩溃误判成旧事件。

数据库 `pipeline.core_epoch` 本身不包含 boot ID，idle crash 归并因此只查当前 PipelineRunner 在本次生命周期中记录的 CORE_CRASHED pipeline ID，并再次限定 core ID 与 generation。PipelineRunner 在开始 claim 查询前先登记当前代际；拿到 pipeline 后，在加载任务和提交事务前公布 claim ID/epoch 的普通值副本，避免 rollback 后访问过期 ORM 实例。claim 成功时将暂存的同代 crash 交给该 pipeline；claim body、commit 或 session context exit 失败时先尝试两次把可能已提交的 RUNNING claim 退回 PENDING。释放成功后，在 claim marker 清除后把暂存崩溃作为 idle core incident 处理；释放失败时终结该流水线，并保留 generation 到 pipeline 的 coalescing 关联，直到同代下一个 claim 或当前服务进程结束。claim 清理期间及 incident 现场生成前排队到事件循环的 core crash 会先把该流水线修正为 `CORE_CRASHED`，再以 `pipeline:<id>` 单一 key 生成诊断会话，避免初始上下文固化为领取错误或另建 core key。无 crash 而 claim 释放失败时同样终结为领取失败并创建 pipeline incident。若 callback 在 `_active` 创建前到达，会让该 pipeline 以 `CORE_CRASHED` 终结，避免 callback 顺序竞争创建两条 incident。已收到的 core crash 优先于同一窗口内的取消请求；若 FATAL 与取消、定时任务延迟或其他流水线终态提交并发，PipelineRunner 会把同一流水线修正为 `CORE_CRASHED`，再由 pipeline incident key 去重。进程启动恢复的旧 RUNNING pipeline 仍通过 pipeline incident key 处理，但不会被新 boot 的 idle core crash 查询误命中。

如果 `pipeline:<id>` 诊断已经开始后才收到同代际晚到 FATAL，PipelineRunner 仍更新原 pipeline，不影响新代际的 active pipeline；`AgentIncidentService` 在同一会话追加一条带 `pipeline:<id>:core:<generation>` 去重标记的现场更新和说明，不创建第二个会话或另一个 core key。会话详情、消息列表通过 `incident_context_updated` 事件刷新。

若 incident 创建时没有完整 LLM 配置，`agent_session.model` 使用 `unconfigured` 占位、`base_url` 置空并保存 assistant 错误说明。用户修复配置后继续该 incident session 时，用当前有效 model/base URL 填充并持久化占位；已有有效 model/base URL 快照不随设置变化而覆盖。

- **任务类型 fixture 与生产契约不一致（P3）。** `web/src/features/tasks/task-types.fixture.json` 的 Copilot 条目手写而成，缺 `required: ["asset_id"]`、把 `runtime_immutable` 写成 `[]`（真实为 `["asset_id"]`）、且没有 per-field 描述。「运行中不可修改 asset_id」与必填语义因此在 fixture 层完全没有覆盖。新增 `scripts/generate_task_types_fixture.py`（含 `--check`）从后端 schema 源生成该文件，测试改为直接使用 fixture 条目并断言这两个字段。
- **agent smoke 三处断言保真度（P3）。** 诊断等待条件 `message_count >= 3` 在普通文本回复路径不可达（该会话只有 user 现场 + assistant 结论两条），实测白等满 8 秒，改为「会话出现 + Fake LLM 已收满 4 次请求」；诊断工具集断言由「排除三个危险工具」改为与 `INCIDENT_ALLOWED_TOOLS` 的精确集合相等，否则 `click`/`swipe`/`restart_core`/`delete_schedule` 泄漏也测不出来；补 SSE 事件顺序断言（`message_start` → `text_delta` → `message_end` 首次出现位置递增）。
- **既有 flaky 用例（非本次引入）。** `tests/agent/test_confirmation_service.py::test_rest_sync_invocation_waits_for_resolution_and_broadcasts_approval_once` 用 20×1ms 轮询共享 `StaticPool` 单连接等待确认行，实测在基线 `34ab248` 上 6 次里失败 5 次，使 AGENTS.md 规定的发布门变成非确定红。改为等待确认落库后必然触发的 `confirm_request` 广播事件，随后连跑 8 次全绿。

仍待处理（本里程碑不再扩大范围，留作后续任务）：

- **`_refresh_existing_pipeline_context` 无超时地等 runtime turn 槽**（`agent/incidents.py`）：持 `pipeline:<id>` key lock 期间若该会话正有一轮在跑，`pipeline_failed` 会一直阻塞到槽位释放；同一 key 的后续诊断排队等它，另有极小窗口会与用户下一次发消息抢锁产生 409。建议加超时/退避，超时放弃补充现场并记 warning。
- **队列消费者缺少异常兜底**（`services/pipeline_runner.py`）：`_execute_pipeline` 的 finally 会调用可能抛异常 `_record_core_crash_terminal`，而 `_run_loop` 不保护它、`_worker` 也没有监管，异常会让消费队列的协程静默退出。属既有结构性问题，本次新增了一个抛出点。

- **Agent 页消息分页方向**：前端取 `page:1,size:200`，而服务端按 `seq ASC` 分页，拿到的是最旧的 200 条且没有「加载更早」入口；确认列表也只在全局前 100 条 pending 里前端过滤。长会话与多会话场景下会看不到最新回复或漏显确认卡片。
- **Agent 页能力自检成功后无反馈**（设置页已有 Badge），纯 UX 问题。

### 8.9 M14：Web Push 的实现方式与偏离

M14 交付 Web Push 全链路（VAPID 密钥、订阅 API、投递、Service Worker 的 `push` / `notificationclick`、设置页入口、确认卡片深链）。相对 [09 §13.1](./09-前端重构方案.md) 的方案有三处实施调整：

- **不用 `pywebpush`，改用既有直接依赖 `cryptography` 自实现。** 需要的原语（ECDH P-256、HKDF-SHA256、AES-128-GCM、ES256 签名）全部具备，而本机网络对 PyPI 不稳定（实测 pip 装包在 SSL/代理上反复失败），把新增运行时依赖做进安装步骤等于给构建加一个单点故障。正确性由 **RFC 8291 Appendix A 的官方向量**锁定：固定的 `as_private` / `ua_public` / `auth_secret` / `salt` 必须复现附录列出的全部中间值与最终 86 octet 头 + 密文。
- **HKDF 必须手写 extract / expand 两步。** `cryptography` 的 `HKDF.derive()` 是 RFC 5869 的 extract+expand 组合，而 RFC 8291 §3.4 的 `PRK_key = HMAC(auth_secret, ecdh_secret)` 与 `PRK = HMAC(salt, IKM)` 都是「只做 extract」的语义。用 `derive()` 替换会额外多做一次 expand：结果全错且**不抛任何异常**。测试里保留一条断言同时验证「官方向量通过」与「`derive()` 会得到不同的值」，去掉修复即变红。
- **Service Worker 从 `generateSW` 换成 `injectManifest` + 自写 `web/src/sw.ts`。** 生成的 Worker 没有 `push` 事件处理，而 Web Push 的通知完全依赖它（`userVisibleOnly: true` 要求每次推送都显示可见通知，否则订阅会被撤销）。因此 `vite.config.ts` 改用 `strategies: 'injectManifest'`，`navigateFallback` 与 denylist 语义由自写 Worker 用文件内常量复现（`frontend_smoke.py` 仍在断言产物里排除 `/api`、`/docs`、`/redoc`、`/openapi.json` 的导航）。预缓存改用 Cache API 自实现，同样不引入 Workbox 运行时依赖。

**一个只在构建产物里出现的缺陷，已修并加了守卫。** `injectManifest` 注入的清单 URL **不带前导斜杠**（`assets/foo.js`、`index.html`），而 `URL.pathname` 一定带；直接比较会让 `install` 里 `cache.addAll([])` 静默通过 —— 安装看起来成功、`caches.open` 不报错，只有真断网才发现什么都没缓存。修法是两边都归一化。守卫是 `web/scripts/sw_harness.mjs`：在 Node 里用最小 Cache API / fetch 替身**执行构建产物 `static/sw.js`**，断言 20 项行为（预缓存条数、URL 带前导斜杠、预缓存命中、API 导航不被接管、断网回退外壳、`push` 必须显示通知、损坏载荷降级、通知 tag 与 data）。它接进了 `pnpm build`，因为源码级单测覆盖不到注入后的清单。

**订阅注销按 endpoint 而不是主机名。** 列表接口出于凭据保护不回显 `endpoint` 全文（同一推送服务下多台设备主机名相同），所以新增 `POST /api/notifications/push-subscriptions/delete` 接受请求体里的 `endpoint` 精确注销；`endpoint` 不进 URL，避免出现在访问日志与浏览器历史里。

**测试环境的两个补充。** 一是 jsdom 没有可用的 IndexedDB（它挂了一个「存在但没有 `deleteDatabase`」的 stub），因此 `web/src/test/idb-shim.ts` 提供一个最小内存实现并在 `vitest.config.ts` 里作为 setup 加载 —— 目的是让 `src/lib/idb.ts` 的测试验证**真实键名**（`maa-api` / `auth` / `token`），而不是把整个 `indexedDB` mock 掉。二是 `ConfirmationsPanel` 现在用 `useSearchParams` 支持推送深链，既有用例需要包一层 `MemoryRouter`。

**顺带修掉的既有抖动。** `web/src/features/api-console/api-console.page.test.tsx` 的「移动端请求步骤」用例依赖 CodeMirror 250ms lint 防抖，却用默认 1s 的 `findBy` 超时；在基线分支 `refactor/v2` 上实测 3 次里失败 2 次。改为与该防抖相符的 5s 预算后连跑 4 次全绿。

**独立复审后的两处补正（同属 M14）：**

- **VAPID 密钥不再走设置 API。** 规格原写"其次为 SQLite 中经 `MAA_LLM_ENCRYPTION_KEY` 加密的私钥"，实现时它作为可写敏感项进了 `SETTING_KEYS`，于是私钥会以**明文 PEM** 落库（只有 `llm.api_key` 走了 Fernet），复审实测确认了这一点。改用更简单的方案：`notify.vapid_private_key` / `notify.vapid_subject` **从 `SETTING_KEYS` 与设置 schema 中移除**，只从 `config.yaml` 读。理由是这两个键本来就不适合走设置 API —— 多行 PEM 在设置页的单行输入框里回写会丢换行，而 `sensitive` 项读取只回 `***`，用户保存**任意其它字段**时前端会把 `***` 当新值提交、静默覆盖真实私钥。这也顺带满足"密钥必须稳定"这条硬要求：它只能由部署者显式编辑。§19 的"公私钥成对存储"同样未实现，改为由私钥导出公钥（少一处漂移源）。
- **通知标题改为用户看得懂的动作与影响。** 规格举的例子是「Agent 请求碎石 3 颗」，实现最初直接用了内部工具名与参数形态（如 `run_task`、`Fight.stone=3`），锁屏通知上等于没写。现在由 `maa_api/services/webpush_service.py` 的 `confirmation_title()` 映射：工具名走中文动作表（`click` → 「在游戏画面点击」、`submit_pipeline` → 「提交任务流水线」），影响范围复用 `RISK_FIELDS` + `TASK_LABELS` 渲染成「刷理智 · 源石 ×3」。认不出的工具名退回原值、**不编造**影响范围（误报消耗比不报更糟）。

**复审同时发现的其余问题**已一并处理：`focusOrOpen` 对未受控窗口的 `navigate()` 会抛 `TypeError`（规范如此），现在接住并退回 `openWindow`，否则点通知毫无反应；推送广播改为**并发 + 总预算**（原先串行、每订阅 10 秒超时，N 个不可达订阅会把确认调用拖成 10 秒 × N）；订阅登记的幂等 `200` 补进了 OpenAPI 声明；`sw_harness.mjs` 补上 `notificationclick` 的三条入口断言（`X-Token` 注入、approve/reject 极性、窗口复用与退回 `openWindow`、409 结果通知），复审用变异证明过这些路径此前**完全没有回归网**；harness 的失败呈现改为逐项标签（原先 waitUntil 拒绝会让整份报告只剩一句原始堆栈），并让预缓存替身校验每个 URL 在构建产物中确实存在。

**未完成（补充实测）**：真机（Android Chrome / iOS Safari）经 Tailscale 的实际送达、锁屏通知、Chromium action 按钮与深链回卡片，均依赖 M15 的 HTTPS 入口，按 §8.3 记为补充验证。

### 8.10 M15：Tailscale Serve 与部署配套

三项配套工作按 [09 §12.4](./09-前端重构方案.md) 落地，`Dockerfile` 与 `scripts/start-maa-api.sh` 一并收尾。

- **代理头信任范围成为配置项，默认只信任回环。** 新增 `deployment.forwarded_allow_ips`，由启动脚本读取后传给 uvicorn 的 `--forwarded-allow-ips`。**默认值刻意不是 `*`**：信任全部来源等于允许任何客户端伪造 `X-Forwarded-For` 与 `X-Forwarded-Proto`，既绕过按来源限流，也让 cookie 的 `Secure` 判定失真。多跳代理时按需追加地址。
- **cookie 的 `Secure` 按 `X-Forwarded-Proto` 判定。** 新增 `maa_api/util/http.py` 的 `request_is_https()`：优先看代理头（取最靠近客户端的第一个值），没有代理头时回落到连接 scheme。两个方向都必须能走通——只按连接判定会在 Tailscale 下永远不加 `Secure`；无条件加 `Secure` 会让局域网 HTTP 直连拿不到 cookie、WebSocket 握手失败。
- **浏览器来源白名单可配，且 HTTP CORS 与 WebSocket 校验共用同一份配置。** 新增 `deployment.cors_origins` 与 `deployment.cors_origin_regex`，作为既有「回环 + RFC1918」默认策略的**追加项**（不是替换，升级后局域网访问不会回退）。`api/ws.py` 的 `_trusted_cookie_origin` 同源读取这两个键：`*.ts.net` 里没有 IP 字面量，只配 HTTP 一半会出现「REST 正常、WebSocket 被 4403 拒绝」的半通状态。解析时先归一化结尾斜杠再校验，避免把配置里常见的 `https://host/` 误判成「带路径」而拒绝。
- **`Dockerfile` 与启动脚本。** 镜像已是多阶段构建（node 构建前端 → python 运行），本次只给 `CMD` 补上 `--forwarded-allow-ips 127.0.0.1` 并说明理由。`scripts/start-maa-api.sh` 重写为可移植版本：不再硬编码 poetry 虚拟环境路径（改用仓库内 `.venv`，可用 `MAA_PYTHON` 覆盖），按平台设置动态库搜索路径，并从配置读取代理头信任范围。用 `sh -n` 校验语法并实际启动验证过。
- **文档。** 新增 [15-部署指南](./15-部署指南.md)，把「每台访问设备都要装 Tailscale 客户端」放在第 0 节：它是唯一的用户侧前置条件，同时是访问控制手段（不在 tailnet 内的设备连端口都摸不到），因此 tailnet 的成员范围就是这个服务的暴露范围。

**未验证（补充实测）**：经 Tailscale 的真机访问与推送送达、Docker 镜像的实际构建。本机 tailscale 指向缺失的 App 可执行文件、Docker Engine 不可用，两者都无法在本环境验证，按 §8.3 记为补充实测。代码侧行为由 `tests/test_deployment.py`（代理头、cookie 的 `Secure`、来源白名单、可见性推送判断）与 `tests/test_vapid_settings.py`（VAPID 密钥只从 config.yaml 提供）覆盖。

### 8.11 M14 补正：「有连接」不等于「用户在看」

[09 §13.1](./09-前端重构方案.md) 的前台层判断依据是 `document.visibilityState === 'visible'`，但实现最初把服务端的判断写成了「有没有活跃 WebSocket 连接」。两者在移动端并不等价：页面切到后台时被冻结，**WebSocket 往往仍然连着**（心跳只是暂停）。后果是确认请求到达时服务端认为「用户在看」而**不推送**，用户什么都收不到，确认只能等到超时自动拒绝 —— 恰好是推送要解决的那个场景。

补正做法：

- `ClientSession` 增加 `visible` 字段（默认 `True`，老客户端不发该消息时行为与之前一致）；
- 客户端在连接建立时与每次 `visibilitychange` 上报 `{"type": "visibility", "data": {"visible": bool}}`；
- `ConnectionManager.has_visible_client()` 取代「`bool(sessions)`」作为确认推送的判断依据，并要求会话未关闭。

测试：`tests/test_deployment.py` 覆盖「后台会话不阻止推送」「无会话为假」「已关闭会话不算可见」「visibility 消息更新状态」，前端 `src/realtime/client.test.ts` 覆盖连接时上报与切前后台重复上报。既有的订阅相关断言改为只看控制帧（排除每次订阅都会附带的 visibility 上报）。

**视觉。**

- 配色改为石墨中性 + 靛蓝，深浅两套同等精调，令牌见 [09 §8.2](./09-前端重构方案.md)。默认主题从深色改为跟随系统（用户决定）；`index.html` 去掉了写死的 `class="dark"`，改由首帧前的内联脚本按存储值与系统偏好设置 `dark` class 与 `theme-color`。
- 图标重绘：品牌标是石墨底圆角方块上的一笔靛蓝单线「M」。`web/public/` 下的 favicon 与 PWA 图标改由 `scripts/generate_pwa_icons.py` 生成（Pillow 8 倍超采样，因为本机没有 rsvg / ImageMagick；支持 `--check`），文件名不变。
- manifest 的 `theme_color` / `background_color` 用石墨 `#0e1014`，与图标一致，安装后的启动画面过渡自然；页面里的 `<meta name="theme-color">` 随主题切换（浅 `#f6f7f9`、深 `#0e1014`）。
- iOS 的 `apple-mobile-web-app-status-bar-style` 从 `black-translucent` 改为 `default`：默认跟随系统后，浅色主题下 translucent 的白色状态栏文字会看不见。代价是如果某个 iOS 版本不按 `theme-color` 给状态栏着色，深色主题下顶部会是一条浅色状态栏（可读但不协调），列入下面的补充实测。

**交互。**

- 全局待确认挂在外壳上：`ConfirmationDock` 读取待确认列表并把数量写进 `stores/confirmations-ui.ts`；首页以外的页面在标题栏右侧显示「N 项待确认」胶囊，首页用横幅，点开都是同一个面板；未登录时 Dock 不发请求，避免 401 触发全局登出流程。规格原写的是 Tab 栏上方（桌面在右下角）的浮动胶囊，实施放进了标题栏。任何路由上的 `?confirm=<id>` 都会打开这个面板并定位到该条（M14 时只有首页处理这个深链）。
- 所有消耗类、破坏类确认改为应用内对话框（`ConfirmDialog`，`role="alertdialog"`，默认聚焦「取消」，按钮写明后果），源码中已没有 `window.confirm`。
- 触屏设备上文本输入获得焦点，或 `visualViewport` 缺口 ≥120px 时，隐藏底部 Tab，让输入区与操作栏贴近键盘；鼠标键盘设备不隐藏。新增 `--nav-offset`、`--nav-safe`、`--keyboard-inset` 三个布局变量，由外壳维护，贴底元素统一按它们避让 Tab 栏与虚拟键盘。
- PWA「新版本可用」提示从底部移到顶部并加「稍后」：在真实服务上发现它与页面主操作栏同位，挡住了「开始执行」。toast 同样放在顶部居中。
- 实时连接提示只在断开或重连中时出现在标题栏下方，首次连接中不提示，避免每次打开页面闪一条黄条。标题栏的返回按钮在应用内有上一页时后退，从深链直接打开时以 `replace` 跳到上级页面。

**明确不做「停止生成」。** SSE 断开后，后端这一轮仍在后台继续（`maa_api/agent/runtime.py` 的 detached producer）。纯前端的停止按钮只能断开显示、停不了执行，会让用户误以为操作已经中止；要做需要后端提供取消本轮的接口，不在纯前端的 M16 范围内。

**§8.7 遗留的处理。**

- 已修：Agent 页消息分页方向。现在先读第一页拿到 `total`，再读最后一页（每页 200 条），对话顶部的「加载更早的消息」读前一页；刷新只重读窗口的最后一页及之后新出现的页，跨页边界时不会漏掉本轮刚落库的消息，所以不破坏 §8.7「刷新完成后才丢弃实时副本」的防重复逻辑。
- 已修：Agent 页能力自检成功也有反馈（「模型能力正常」）。
- 已修：SSE `error` 事件改为可见。旧代码只写进从不渲染的 `turn.error`，流正常结束、实时副本清空后错误就看不到了；现在写入独立存放的本轮错误。普通回合出错时服务端不把错误落库成消息（`runtime.py` 的 `_produce_turn`），所以不会重复显示。
- 仍保留：待确认列表按全局前 100 条 pending 读取，再在前端按会话过滤。
- 仍保留：本轮的确认若在全局面板或推送里被处置，`turn.pendingConfirmation` 不会被清掉，流结束时这一轮会因「确认仍挂着」被保留，与历史重复显示。这属于受保护的合流逻辑，M16 没有动；建议后续在收到该工具调用的 `tool_result` 时清掉对应的 `pendingConfirmation`。
- §8.7 其余三条后端遗留（`_refresh_existing_pipeline_context` 无超时、队列消费者缺异常兜底、`mark_core_crashed` 的语义没有测试固定）不在纯前端范围，状态不变。

**用户可见的行为变化。**

- 流水线详情的关联日志改为最近 100 条（`order=desc&size=100`，再按时间正序显示），超出时说明「最近 100 条，共 N 条」。规格原文就是「最近 100 条」，旧实现取的是最早的 100 条。
- 无标题流水线的命名：历史列表不再为无标题的行逐条读详情（每页最多多出 20 个请求）。定时任务触发的显示定时任务名（共享的定时列表查询，一次请求），其余显示「来源 + 任务数」（如「手动任务 · 3 项」）；详情页仍用任务名组合。为此新建了共享查询 `features/schedules/queries.ts`（key `['schedules', 'list']`）：旧定时任务页在 `['schedules']` 下存数组、首页快捷面板存分页对象，同一个 key 两种形状会互相污染。
- 任务编辑器：`Fight.series`（连战次数）可以设置了 —— `x-widget: "select"` 而没有 `enum` 时从 `x-enum-labels` 推导选项，旧页面这里是空下拉；公招 Tag 等级（`Recruit.select` / `confirm`）改为 1–6 的可切换芯片，旧页面是自由文本；枚举只在不超过 3 个且标签不超过 6 个字时用分段控件；数字一律带步进与范围，去掉了滑块。
- 首页新增「停止任务」（`DELETE /api/pipelines/{id}`，先确认）与「查看详情」；运行状态从计划中的「状态芯片 + 详情面板」改为行内列表，少一次点击且信息不缺。
- 热更新的三个目标都走选项面板，以保留对所有目标生效的「允许强制中断」，面板的确认按钮就是确认步骤；有可用更新时状态芯片优先显示「可更新」（旧逻辑只要有错误就显示「检查失败」）；错误提示能显示 `{error: {message}}` 信封里的消息本身。
- 设置：`string[]` 字段（目前只有 `deployment.cors_origins`）用芯片输入并按数组提交；敏感项来源为默认值时显示「未配置」，其余显示「已配置，已脱敏」（服务端对敏感项一律返回 `***`，旧页面因此总显示已配置）；「清除本机 token」沿用旧行为，只清本机的 localStorage、内存与 IndexedDB，不注销 HttpOnly cookie，完整登出走「更多 › 退出登录」。
- API 调试台顺带修了五个页面层缺陷：从历史恢复后误进入「更新收藏」状态并拿历史 id 去 `PUT /api/snippets/{id}`；带路径参数的历史无法恢复；删除任意一条收藏都会清掉当前绑定；改自定义 header 名时每敲一个字丢一次焦点；历史里 status 0 显示为绿色。

**发现的后端缺陷（未修，超出纯前端范围）。**

- `SettingService._validate` 的类型检查表没有 `string[]`。`deployment.cors_origins`（`list[str]`）无论提交数组还是字符串，`PUT /api/settings` 都因 `KeyError('string[]')` 返回 500 `INTERNAL_ERROR`，同一次保存里的其他字段也不会写入（校验在写入之前）；「恢复默认」不走 `_validate`，可以用。旧前端同样存不进去。建议在类型表里加 `"string[]": lambda v: isinstance(v, list) and all(isinstance(s, str) for s in v)`。后端修好之前，在设置页保存这个字段会就地显示「保存失败」。
- `tests/api/test_push_subscriptions_router.py` 的 10 项在本机 `config.yaml` 设置了 `app.access_token` 后失败（401「缺少 access token」）：测试只 monkeypatch 了 `maa_api.settings.get_settings`，而 `maa_api/api/deps.py` 在导入时已经绑定了原函数，读到的是真实 token。基线提交上同样失败，与 M16 无关，本里程碑没有改后端测试。另外 `tests/core/test_crash_recovery.py::test_backoff_sequence_grows_then_failed_after_budget` 在并发构建负载下偶发超时，单独重跑通过，属时序敏感用例。

**测试环境。**

- vitest 的 `testTimeout` 设为 15 秒（`web/vitest.config.ts`）：API 调试台页面测试在 jsdom 里挂 CodeMirror，全量并行时要冷加载懒分块，还有 JSON 校验的防抖，单条会超过默认的 5 秒（§8.9 记录过它在基线上 3 次失败 2 次）。
- testing-library 的 `asyncUtilTimeout` 在 `web/src/test/setup.ts` 统一设为 5 秒：页面全部是懒加载分块，全量并行时冷加载会超过默认的 1 秒，多个文件的 `findBy*` 因此偶发超时。

**与规格或前文方案的其他差异（实施后核对）。**

- Agent 页只有「加载更早的消息」按钮，上滑到顶部不会自动加载（规格写两者都有）；日志页两者都有。
- 部分次要图标按钮用 36px 的 `icon-sm`（面板关闭、区块刷新、设备画面刷新、调试台响应抽屉的展开与全屏），`sm` 按钮为 40px，低于规格的 44px 触控目标，随下面的补充实测一起确认。
