# 实施计划与里程碑

## 1. 排序原则

三条原则决定了里程碑顺序：

**内核层优先。** 子进程隔离是所有功能的地基 —— 热更新、崩溃恢复、队列、agent 全都依赖它。它也是唯一涉及 native 库与跨进程边界的部分，风险最集中。放在最前面，一旦这里的方案有问题，后续所有工作都还没投入。

**数据层与 API 规范先于功能。** 表结构和错误码体系一旦定下来，功能开发就是填充；反过来先写功能再补持久化，会产生大量返工。

**每个里程碑结束时系统可运行。** 不接受"三个月后一次性能跑"的路径。每阶段都有明确的可交付状态，随时可以停下来评估。

工作量用相对规模标注（S / M / L / XL），不给日历时间，因为投入强度未知。

## 2. 里程碑

### M0 · 基线准备（M）

依赖升级与骨架搭建。这是唯一允许大面积触碰现有代码却不产生新功能的阶段。

- 升级 FastAPI 与 uvicorn 到当前版本，pydantic 从 1.10 迁移到 v2，引入 SQLModel、Alembic、aiosqlite、httpx
- 按 [02-系统架构设计 §6](./02-系统架构设计.md) 建立目录骨架，空模块先占位
- 修复 [01-重构总览与现状评估 §2.3](./01-重构总览与现状评估.md) 清单中不会随重写自然消失的缺陷：`asst.py` 的 `get_image` 缓冲区、两处漏掉的 `@staticmethod`、`InfrastTask` 的 `failename` 拼写、`ReclamationTask` 的字典键、`TaskRequest` 的尾随逗号与重复字段、`Award` 的默认值
- 定义 `AsstProtocol` 与 `FakeAsst` 替身，搭好 pytest 骨架
- `config.yaml` 加入 `.gitignore`，补 `config.template.yaml`（`config.yaml` 保留在本地，不再跟踪变更）

pydantic v1 到 v2 的迁移必须在这个阶段一次性做完。边写新代码边迁移会导致两种风格混杂，且 SQLModel 与 pydantic v2 配套，拖后会阻塞 M2。

**可交付状态**：服务能按现有功能正常启动运行，依赖已是新版本，测试框架就位。功能无变化。

### M1 · MaaCore 内核层（XL · 关键路径）

见 [03-MaaCore内核层设计](./03-MaaCore内核层设计.md)。

- `asst.py` 补全 8 个缺失 C API，迁移到 `AsstAsyncConnect`，补全 `InstanceOptionType`
- 实验性 API 的能力探测与降级（`AsstGetMapLevelKey` 仅 macOS 导出）
- IPC 协议定义：命令与事件的类型、payload 结构、序列化
- `core/worker.py` 子进程：启动序列、回调桥接、命令循环
- `CoreSupervisor`：状态机、心跳、崩溃检测、退避重启、维护窗口
- `CoreClient`：事件消费线程、`cmd_id` 到 Future 的映射、差异化超时、事件分派
- `CoreRegistry`：单实例实现，多实例扩展口
- 测试：IPC 契约测试（真实 Queue + 两端替身）、故障注入（`FakeAsst` 主动段错误退出）验证崩溃恢复全链路

这是整个计划里最重的一块，也是唯一建议不要压缩的一块。IPC 的边界情况容易漏：超时后迟到的 `CMD_RESULT`、长命令（`LOAD_RESOURCE`）执行期间的心跳误判、维护窗口与崩溃检测的互斥、`spawn` 模式下不可 pickle 的参数。这些都要在这个阶段用测试固化。

**可交付状态**：能用一个命令行脚本启动子进程、加载资源、连接设备、提交一个最短任务并收到回调；杀掉子进程能观察到自动重启。HTTP 服务尚未接入新内核层。

### M2 · 数据层（L）

见 [04-数据模型与持久化](./04-数据模型与持久化.md)。

- SQLModel 表定义
- Alembic 初始迁移，以及在 lifespan 里自动迁移到最新版本的机制
- 仓储层
- 日志与截图的保留策略及后台清理任务

清理任务要在这个阶段就做，而不是等日志表撑爆再补。MaaCore 回调相当密集，一条肉鸽流水线能产生数千条日志。

**可交付状态**：数据库可创建、可迁移、可读写，仓储层有单元测试覆盖。

### M3 · API 骨架（L）

见 [05-API规范与路由清单](./05-API规范与路由清单.md)。

- `lifespan` 装配替代废弃的 `on_event`，按 [02-系统架构设计 §7](./02-系统架构设计.md) 的启动顺序组织
- 统一错误体与异常处理器，错误码枚举
- 四渠道 token 鉴权
- 任务类型的 pydantic v2 discriminated union 模型，取代扁平的 `TaskRequest`
- `GET /api/tasks/types` 的 schema 导出（前端表单与 agent 共用）
- OpenAPI 元数据与 tag 分组
- 修正 CORS 配置

任务模型的参数说明必须从 `task.py` 的文档字符串完整迁移。这些说明是前端表单提示与 agent 参数填写质量的共同来源，是这个阶段最有价值也最容易偷工的部分。

**可交付状态**：新的 API 骨架可访问，`/docs` 可用且文档完整，鉴权生效，任务参数校验生效。业务端点尚未接内核。

### M4 · 日志与 WebSocket（L）

见 [06-实时日志与WebSocket](./06-实时日志与WebSocket.md)。

- `LogHub` 三路汇聚：MaaCore 回调翻译、Python logging handler、MaaCore debug 日志文件 tail
- 环形内存缓冲、攒批落库、背压策略
- WebSocket 端点与完整消息协议
- 连接管理、订阅过滤、断线补发
- 历史日志查询接口
- 截图改为存文件加引用，替代 base64 内嵌

回调文案映射表（现在 `callback_handler.py` 里那三张 dict）在这个阶段迁移，同时补上未处理的回调类型。

**可交付状态**：能用 `websocat` 之类的工具连上 WS 看到三路日志实时到达；日志可查历史、可过滤。

### M5 · 队列与执行器（L）

- `TaskQueue`：优先级排序，以数据库为事实来源
- `PipelineRunner`：单消费者循环、事件驱动的任务完成判定、重试、超时兜底
- 内核崩溃时的流水线状态处理与队列保留
- 原子操作与流水线运行的冲突处理（409 与 `force`）

任务完成判定从轮询 `running()` 改为消费回调事件，加超时兜底。超时阈值按任务类型配置 —— 肉鸽和生息演算的正常耗时远长于领奖励。

**可交付状态**：通过 API 提交流水线能完整执行到底，状态与日志全程落库，前端（尚未重写）可用 curl 验证全流程。至此后端核心功能闭环。

### M6 · 设备与渠道（M）

见 [08-ADB连接与账号渠道](./08-ADB连接与账号渠道.md)。

- `DeviceManager` 状态机，统一 MaaCore 与 adbutils 两条连接路径
- 四时机重试：启动等待（不阻塞启动）、任务前预检、断线自动重连、手动重连
- 设备扫描
- 渠道三层优先级注入，默认 B 服
- 设置读写与热生效（改 ADB 地址自动重连）。MAA 路径已拍板**保持只读**，不提供在线修改与热重启，见 [13-决策记录 §8.1](./13-决策记录.md)

`scripts/start-maa-api.sh` 里的 ADB 等待循环在这个阶段可以删掉，逻辑移入服务。

**可交付状态**：模拟器未启动时服务能正常启动并显示未连接；模拟器起来后自动连上；断线能自动恢复；设置可在线修改并生效。

### M7 · 热更新（XL）

见 [07-热更新方案](./07-热更新方案.md)。

- 通道 B 合并语义的**前置验证脚本**（见下）
- 内核更新：维护窗口、下载、原子替换与回滚、子进程重启。只做 stable 通道
- 三个增量层的目录落点定为 `resource/maa-layers/{repo,cache,custom}/`，与 `<maa_path>` 平级。**现有代码把 OTA 缓存写在 `<maa_path>/cache/`，这一步要连带改掉**，否则内核更新会清空它，见 [07 §3.7](./07-热更新方案.md)
- 活动资源通道 A：清单驱动、HTTP 条件请求、单文件原子落盘
- 活动资源通道 B：Mirror 酱查版本与 GitHub raw 回退、压缩包下载与镜像回退链、剥顶层目录解压、独立目录原子替换与回滚、磁盘预检
- 多层增量加载：`LOAD_RESOURCE` 命令改为有序路径列表并拆成多次调用，不重启子进程。实施改为覆盖合并，通道 B 更新需要重启子进程，见 [13-决策记录 §8.1](./13-决策记录.md)
- 游戏 APK 更新：版本对比、大文件下载与进度、`adb install`
- 更新记录落库、`resource_asset` 的远端版本基准落库、进度经 WS 上报、并发保护
- 每日自动检查更新（只检查不下载，通知合并且同版本只通知一次）与手动「立即检查」入口，见 [07 §5.6](./07-热更新方案.md)

体量从 L 上调为 XL。通道 B 不是"多一个下载地址"这么简单：它带来一条独立的版本判定链路（两级远端源 + 落库基准）、一套压缩包处理流程（下载、校验、剥目录、解压、原子替换、回滚）、加载链从两层变四层因而必须改 `LOAD_RESOURCE` 的命令签名，还牵出三个增量层的落点必须移出 `<maa_path>`（否则每次内核更新都会清空它们）。这几项里没有一项可以复用通道 A 的代码——通道 A 是"下载一个 15 KB 的 JSON 覆盖上去"，两者只有进度上报和落库是共用的。

游戏 APK 更新是三者中最脆弱的，允许完成度低于其他两项，必要时降级为"检测并提示"。如果这个阶段需要压缩，压这里，不要压通道 B 的回滚路径。

**通道 B 的合并语义必须在动手实现前验证**，三项待验假设、验证方法与退路见 [07 §3.3](./07-热更新方案.md)。做法与 §5 给 M1 定的方案验证前置一致：先写一个最小脚本按完整链条加载一次，确认模板图没被抹掉、新增关卡能解析、重载后模板缓存确实失效。这几小时的成本远低于"实现完才发现要改回覆盖式落点"——那会让上面一半的工作项作废。

**可交付状态**：三种更新均可从 API 触发；活动资源两条通道可单独或一起更新；内核更新期间 HTTP 服务不中断，且更新后自定义资源与已同步的活动资源仍在。

见 [09-前端重构方案](./09-前端重构方案.md)。

### M9 · 前端功能页（L）

- 任务页：schema 驱动的动态表单、队列、执行历史

动态表单是这个阶段的核心，它替代了旧前端 734 行硬编码，且让参数覆盖度问题一次性解决 —— 后端 schema 里有的参数界面上自动就有。

**可交付状态**：旧前端的全部功能在新前端可用，且参数覆盖度超过旧版。此时可以删除 `static/` 下的旧文件。

### M10 · 开放 API 调试台（M）

见 [10-开放API与调试台](./10-开放API与调试台.md)。

- 接口树、请求构造器、响应展示
- 请求历史与收藏、cURL 导出

### M11 · Agent 基座（L）

见 [11-Agent模块设计](./11-Agent模块设计.md) §3 到 §5、§7、§9。

- `ToolRegistry` 与已有应用服务可执行的工具实现
- `PolicyEngine` 风险判定
- 确认机制：落库、WS 广播、挂起等待、超时、内置 Agent 与 REST sync/async 调用的等待语义
- 原子操作的会话级授权：授权确认、窗口落库、到期与撤销 API；前端常驻授权提示条归 M13
- 审计落库与前端审计页
- 自定义资源：Copilot 作业、自定义 task 注入及其安全机制（schema 校验、独立目录、失败回滚、名称前缀）

工具实现全部经应用服务层，不直接碰 `CoreClient`。M11 交付 REST 工具调用、会话 CRUD / 消息只读查询 / 授权撤销 API、确认卡片与审计页；不挂载会话 `POST /messages`，不交付 LLM 循环。Copilot 执行当时缺少向 MaaCore 传递作业的调用契约，M13 Task 3 已纳入共享任务队列和 schedule 模板；Agent 上传后通过 `submit_pipeline` 提交，使用每次运行的安全快照，不能以普通 Fight 替代。M13 完成后，内置对话、LLM 循环、授权状态常驻 UI 与自动诊断均已交付。

**可交付状态**：当前已实现的工具可通过 REST 接口调用；高风险操作能触发前端确认卡片；会话授权可确认、撤销并审计；审计可回溯。Copilot 作业可校验上传、列出，并作为正式任务排队执行。

### M13 · 内置 Agent（L）

- OpenAI 兼容 LLM 客户端，`api_key` 加密存储，能力自检
- 默认 DeepSeek Flash（`deepseek-flash`）；`MAA_LLM_ENCRYPTION_KEY` 提供 SQLite API Key 加密主密钥
- tool-calling 循环、只读并发写串行、`max_iterations`
- 上下文管理：截图只留最近一张、状态摘要注入、历史截断、token 记录
- SSE 流式输出
- 前端对话界面：流式文本、工具调用轨迹可折叠、会话历史、等待确认状态、会话授权状态提示与撤销入口
- 故障自动诊断默认开启，可在设置页关闭；流水线失败与空闲内核崩溃按 incident key 去重，安全工具恢复沿用确认与审计机制
- Copilot 作业进入共享流水线与 schedule template；每次运行由应用服务生成独立私有快照，拒绝 symlink 源路径，并在流水线终态释放快照

**可交付状态**：内置 Agent 支持自然语言多轮对话、通过共享队列创建/执行流水线与定时任务、Copilot 原生执行、日志与故障诊断、安全恢复以及确认/审计。FakeAsst/Fake LLM 与 API/前端 smoke 验证通过；真实 DeepSeek 端点、MaaCore/设备、移动/桌面浏览器的人工验收作为补充验证，见 [13-决策记录 §8.3](./13-决策记录.md)。

### M22 · 中断 Agent 正在执行的一轮（M）

规格与计划见 `docs/superpowers/specs/2026-09-29-m22-agent-interrupt.md` 与 `docs/superpowers/plans/2026-09-29-m22-agent-interrupt.md`。用户裁决（2026-09-29）：「agent 执行过程中，现在完全不能中断，需要加上中断功能。」同轮确认三条：① 只停 Agent 本轮，**不碰流水线与队列**；② **彻底撤回本轮在等、在跑的工具**（未批准的确认撤掉、在跑的工具 worker 取消、挂起的提问置 `cancelled`），已经入队的任务保留；③ **刷新后仍能停**（后端记住本会话有没有一轮在跑）。这条需求同时取代了 M16 起「不做停止生成」的刻意决定——那时 SSE 断开后后端仍在 detached producer 里继续跑，纯前端的按钮只会断开显示，现在停止是真的中断后端执行。

- 后端：Runtime 会话级中断（`_active_turns` 为进程内真相源、`turn_running()`、`interrupt_turn()`）；取消分支的收尾是：把已产出的部分文本连同「本轮已被你中断。」落一条 `finish_reason="interrupted"` 的助手消息 → 补写本批未落库调用的 tool 桩消息（否则下一轮请求结构不合法）→ 推 SSE `interrupted` 再走既有 `message_end` → 释放会话锁；取消的调用不重试
- 后端：`ConfirmationService.abort_session_calls(session_id)`——仍 `pending` 的确认按「不批准」撤掉（CAS `rejected`、审计 `REJECTED`、广播、唤醒等待方，之后批准也不再执行），已批准或免确认的在跑工具取消 worker 并把审计置 `failed` + `AGENT_TURN_INTERRUPTED`；服务关闭取消 worker 仍旧写 `SERVICE_UNAVAILABLE`
- 后端：`QuestionService.cancel_pending_for_session(session_id)` 与新终态 `QuestionStatus.CANCELLED`（审计 `REJECTED` + 摘要「本轮已被中断，提问已取消」、广播 `question_resolved(reason="cancelled")`、唤醒等待方；卡片从待答列表消失）

## 5. 阶段性风险控制

**M1 的方案验证前置。** 在投入完整实现前，先写一个最小验证脚本：启动子进程、加载真实 MaaCore、提交一个任务、收到回调、杀掉子进程、观察重启。这个脚本能在几小时内验证子进程隔离方案是否成立，避免在错误方向上投入 XL 的工作量。

**agent 能力的早期验证。** 不要等到 M13 才发现模型看不懂游戏界面。建议在 M11 期间就用现有的截图接口手动喂给目标模型，验证它能否正确识别当前界面、读出理智数值、判断是否卡在弹窗。验证失败的话 agent 的第三层能力（原子操作）与"应对新活动"场景应当降级或移出范围。

**PWA 的 HTTPS 决策提前。** 这个决策影响部署方式，越晚做代价越大。建议在 M8 开始前就确定走哪条路径。

**范围冻结点。** M10 结束时开放 API 调试台可独立验收，是一个天然的验收与重新评估点。如果此时发现 agent 部分的实际价值低于预期，或模型能力验证不理想，可以在这里停下来；PWA 安装、离线缓存和推送仍待 M14。
