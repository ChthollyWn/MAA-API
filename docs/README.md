# MAA-API 重构方案

本目录是 MAA-API 全面重构的执行方案。**M0–M11、M13、M14、M15、M16、M17 已完成并合并进 `refactor/v2`**（M12 的 MCP Server 按 [13 §8.4](./13-决策记录.md) 移出范围，不交付）。

内核仍然是 [MaaAssistantArknights](https://github.com/MaaAssistantArknights/MaaAssistantArknights)（本地为 v6.17.x），重构范围覆盖后端架构、前端、热更新、开放 API 与新增的 Agent 模块。

本方案是**破坏性重构**而非渐进改造：后端执行层重写、`static/` 整体废弃、响应格式全面改标准 HTTP 状态码、引入 SQLite 持久化。基线为 `dev` 分支（`139c4bc`），不复用 `feat/0515` 的代码。

## 决策速查表

以下为讨论已确认的全部决策，是所有文档的单一事实来源。任何文档与本表冲突时以本表为准。实施后的偏离记录在 [13-决策记录 §8](./13-决策记录.md)，本表受影响的条目已加注。

### 需求 1 · 前端重构

| 项 | 决策 |
|---|---|
| 技术栈 | Vite + React + TypeScript + Tailwind CSS + shadcn/ui |
| 部署形态 | 单体。构建产物输出到 `static/`，FastAPI 单进程托管，单端口 8002 |
| 设备优先级 | **移动端优先**，桌面自适应 |
| 应用形态 | Web + PWA（添加到主屏、资源缓存、推送通知） |
| HTTPS 入口 | **首版即上 Tailscale Serve**，PWA 全部能力在首版可用。非安全上下文的分级降级仍要实现，作为客户端未连通时的兜底 |
| 导航结构 | 手机与平板用底部 Tab（首页、任务、日志、Agent、更多），宽度 ≥1024px 改为左侧栏；定时任务并入任务区，次级页面收进「更多」。**M16 实施，见 [13-决策记录 §8.12](./13-决策记录.md)** |
| 旧页面 | `static/index.html`、`static/daily.html`、`static/js/app.js`、`static/css/style.css` 全部废弃 |

### 需求 2 · 实时日志

| 项 | 决策 |
|---|---|
| 日志来源 | 三路全要：MaaCore 回调任务日志、Python 服务日志（logger + uvicorn）、MaaCore 自身 debug 日志 |
| 前端展现 | 按来源分标签页，支持按来源与级别过滤 |
| 传输方式 | WebSocket 推送 |
| 持久化 | 落 SQLite，支持历史查询 |

### 需求 3 · 热更新

| 项 | 决策 |
|---|---|
| MAA 内核 | **子进程隔离**。更新时只重启 MaaCore 子进程，API 服务全程不中断 |
| 活动资源 | 清单驱动，**两条通道首版都做**：通道 A 官方 OTA `tasks.json` 增量、通道 B `MaaResource` 仓库压缩包全量（地图坐标、关卡表、公招数据、模板图）。不依赖付费 CDK |
| 资源加载链 | 四层按序叠加：内核自带 → `repo/`（通道 B）→ `cache/`（通道 A）→ `custom/`（自定义）。后者覆盖前者，三个增量目录彼此隔离、可单独清空。**M7 实施改为覆盖合并，见 [13-决策记录 §8.1](./13-决策记录.md)** |
| 增量层落点 | 三个增量目录统一放在 `resource/maa-layers/`，**与 `<maa_path>` 平级而非嵌套其中**。内核更新替换整个 `<maa_path>`，放在外面就不需要迁移步骤，也不会丢掉没有远端副本的自定义资源 |
| 内核更新通道 | **只用 stable**，不暴露 beta / alpha。保留枚举与落库字段以便将来放开 |
| 更新检查 | 每天自动检查一次（默认 09:00，可配），**只检查不下载**，有更新则合并推一条通知且同版本只通知一次；另有手动「立即检查更新」入口。下载与安装始终手动触发 |
| 游戏本体 | 下载 APK + `adb install` 覆盖安装，并显示"当前安装版本 vs 最新版本"对比 |
| 外部接口常量 | 复用 `feat/0515` 已验证的常量（B 服 `game_base_id=101772`、官服直链、包名、`dumpsys` 解析方式），但不复用其代码结构 |

### 需求 4 · ADB 连接重试

| 项 | 决策 |
|---|---|
| 重试时机 | 四个全要：服务启动等待、任务执行前预检、运行中断线自动重连、前端手动重连 |
| 启动失败行为 | 服务照常启动，前端显示"设备未连接"并提供重连入口 |
| 连接 API | 从已废弃的 `AsstConnect` 迁移到 `AsstAsyncConnect` |

### 需求 5 · 账号渠道

| 项 | 决策 |
|---|---|
| 支持范围 | 仅官服（Official）+ B 服（Bilibili），**默认 B 服** |
| 配置粒度 | 全局默认配置，任务未显式指定时自动套用，允许单任务覆盖 |
| 多账号 | 不做，单账号 |

### 需求 6 · 开放 API

| 项 | 决策 |
|---|---|
| 调试页形态 | 自研调试面板集成进新前端（主题统一、自动带 token、保存请求历史），同时保留 FastAPI 原生 `/docs` 作为备用 |
| 鉴权 | 单 `access_token`，支持 Bearer / `X-Token` / query / cookie 四种传递方式 |
| 状态码 | **全面改用标准 HTTP 状态码**，废弃 `{code: 10200}` 业务码体系 |
| 错误体 | `{"error": {"code": "ADB_CONNECT_FAILED", "message": "...", "details": {...}}}`，错误码为可枚举字符串 |
| 任务参数默认值 | 字段带**真实内核默认值**（MAA v6.17.5，M17 取证后写进 JSON Schema `default`），默认值随下发快照显式下发；显式传 `null` 仍是「不下发、由内核决定」。逐字段依据与代价见 [13 §8.17](./13-决策记录.md) |

### 需求 7 · Agent 模块

| 项 | 决策 |
|---|---|
| 架构定位 | 前端内置对话式 Agent，用户以自然语言指挥 MAA |
| 内核 API 补全 | `asst.py` 缺失的 8 个 C API 全部补全，并迁移到 `AsstAsyncConnect` |
| 原子操作范围 | MaaCore 原生（click / screencap / back_to_home）+ ADB 补充（swipe / 长按 / 输入文本 / 按键）。**不开放任意 `adb shell`** |
| 视觉输入 | 截图 tool 返回 base64 或临时 URL，由多模态模型自行判断。不额外接 OCR |
| 自定义任务 | 最大范围：组合现有任务类型 + Copilot 作业 JSON + 自定义基建方案 + 增量资源注入自定义 `tasks.json` task 定义 |
| 需人工确认 | 消耗类（碎石、理智药、加急许可、商店购物、源石锭投资）+ 破坏类（清空基建方案、卸载重装游戏、重装内核、修改全局配置） |
| 原子操作确认 | **会话级授权**：首次弹一次确认，批准后该会话 15 分钟内免确认（时长可配，上限 60 分钟）。只覆盖原子操作，消耗类与破坏类仍逐次确认；可随时撤销，审计不降级 |
| 故障自动诊断 | M13 默认开启；流水线终态失败和空闲内核崩溃按持久 incident key 各至多诊断一次，可在设置页关闭。运行中内核崩溃合并到该流水线诊断会话 |
| 会话授权适用范围 | 只有带有效会话的内置 `internal` 调用可复用授权；REST 调用没有内置会话，原子操作逐次确认。服务重启或会话关闭、切换、删除时撤销 |
| 明确免确认的操作 | `stop_pipeline`、`trigger_screencap`、`back_to_home`、已校验并保存的 `upload_copilot`、`delete_schedule`；其余原子操作走上述授权/逐次确认规则 |
| 确认渠道 | 前端经 WebSocket 收到待确认事件并弹卡片，超时自动拒绝 |
| 确认超时 | 按风险分级：消耗类与破坏类 10 分钟，原子操作会话授权 120 秒，均可配置。Chromium 平台额外做推送上的「准许 / 拒绝」按钮（iOS 不支持，属渐进增强） |
| 并发策略 | 统一任务队列 + 优先级排序（前端手动 > agent > 定时），不抢占，前端可见排队情况 |
| 调用语义 | 异步提交返回 `task_id` 与同步阻塞等结果两种都提供 |
| 审计 | 全量落库（调用方、时间、参数、结果、耗时），前端有审计页可回溯 |
| LLM 接入 | 统一 OpenAI 兼容端点（`base_url` + `api_key` + `model`），默认 DeepSeek Flash（`deepseek-flash`）；API Key 由 `MAA_LLM_ENCRYPTION_KEY` 加密存储，兼容其他 OpenAI 兼容服务 |
| 会话存储 | 落 SQLite：多轮历史、工具调用轨迹、token 消耗 |
| Agent 知识库 | 内置只读条目随代码发布（`maa_api/agent/knowledge/builtin/`，M24 起 32 条，事实以 PRTS 为准并随代码离线可用），数据库只存用户改动与自定义条目；索引、术语表与用户档案按 kind 注入 system 消息（M19 测得约 4.3 千字），索引之后另插一行「当期活动」（M24：现读本机活动资源、≤ 120 字、读不到就不插），`read_knowledge` 读全文，`get_activity_stages` 查当期活动与关卡代号（新组 `activity`；M25 起改为 PRTS 优先、外服与不可用时退回本机），设置页「Agent 知识库」可编辑、停用与恢复默认；**条目数与全文段都不设上限**（M20）；M25 起另有实时检索层（见下一行）。见 [13 §8.23](./13-决策记录.md)、[13 §8.24](./13-决策记录.md)、[13 §8.25](./13-决策记录.md)、[13 §8.38](./13-决策记录.md)、[13 §8.40](./13-决策记录.md) |
| 上下文与上限 | **不设自设的会话/上下文上限**（M20）：会话历史整段发给模型，装不下时由上游拒绝并映射成 `400 LLM_CONTEXT_OVERFLOW`；知识库不设条目数与字数上限。保留的约束只有字段长度与原地打转检测。见 [13 §8.25](./13-决策记录.md) |
| Agent 提问 | **与确认并列的独立链路**（M21）：需要用户在若干候选之间裁决参数（渠道、关卡、次数策略）时调 `ask_user` 发一张选择卡并挂起本轮，选择以工具结果回填、同一轮继续；没有风险等级、不授权任何操作，因此**不占「待确认」计数**，卡片只在本会话的对话页内（不进全局面板、不进标题栏胶囊，也不做 Web Push）。用户没回答就结束本轮：默认 10 分钟超时或点「跳过」，两者都以 `finish_reason=question_unanswered` 收尾；等待时长可配（`agent.question_timeout_seconds`，默认 600 秒）。见 [13 §8.26](./13-决策记录.md) |
| 中断本轮 | **中断是真的中断**（M22）：执行期间输入栏的发送按钮原地变「停止本轮」，`POST /api/agent/sessions/{id}/interrupt`（幂等）停掉 LLM 流、撤回本轮在等与在跑的工具（未批准的确认直接撤掉、之后批准也不再执行；已批准或免确认的工具取消 worker 并落 `failed` + `AGENT_TURN_INTERRUPTED`；挂起的提问置 `cancelled`），补 tool 桩消息、落一条 `finish_reason=interrupted` 的助手消息后释放会话锁；刷新或换设备后由会话详情的 `turn_running` 恢复停止入口。**只停 Agent 本轮，不碰流水线与队列**；**已批准并已在执行的工具可能已经产生副作用且无法回滚**。断网 / 关页面这类被动断开仍旧不取消本轮。见 [13 §8.27](./13-决策记录.md) |
| 会话内媒体与任务留档 | **Agent 能把画面与数据递给用户**（M23）：工具结果里的 `result.media[]` 承载四种卡（图片 / 材料图标 / 关卡示意图 / 图表），卡片挂在 tool 消息上，所以实时（SSE `tool_result`）与刷新后（历史消息）走同一条渲染路径，**没有新表、新端点、新错误码**。`media` 组五个工具（`send_screenshot` / `annotate_screenshot` / `send_item_icons` / `send_stage_map` / `send_chart`）全部声明 `SAFE` 走 `declared_risk` 分支免确认（不进白名单）；前端只认三种同源图片地址（`/api/images/<sha256>/thumb` 与 `/full`、`/api/screenshots/<id>`、`/api/resources/items/icon?item_id=`），外域与 `data:` 一律丢卡。图表用 **ECharts（canvas）** 渲染、可交互并跟随主题，另带「数据」折叠表兜底。流水线任务进入 `completed` / `failed` / `skipped` / `crashed` 时留一张 `task_snapshot` 截图（`cancelled` 不留），失败 / 跳过 / 崩溃另挂日志附件。**干员头像不做**（本地无图源）留待裁决。见 [13 §8.29](./13-决策记录.md) |
| 外部数据源与检索 | **以 PRTS 为事实源**（M25，用户裁决 R1–R3）：允许联网，但只限白名单域名的只读接口（`prts.wiki` 的 `action=query` / `ask` / `cargoquery` / `opensearch` 与 `parse&prop=sections`），按需实时拉取、进程内 TTL 缓存（不落盘）、有超时与响应上限，返回内容一律当不可信数据。工具结果带来源信封（来源名、页面链接、抓取时间、`cached` / `stale`），前端在工具卡上渲染来源标签、回答里要写明出处；PRTS 不可用或外服时退回本机 MAA 资源包并标 `source=resource`，取不到的字段进 `unavailable`、不凭记忆补全。新配置段 `sources`（设置页「外部数据源」）管总开关、缓存时长、内存上限、每分钟请求上限与是否走系统代理；REST 只开 `GET /api/sources/status` 与 `DELETE /api/sources/cache`，**不做 PRTS 代理**（Q25）。工具：`get_stage`、`search_prts`、`get_prts_page` 与改造后的 `get_activity_stages`（国服优先 PRTS、在开的多个活动全部列出）。R1–R3 与 Q1–Q49 见 [规格 §1.2](./superpowers/specs/2026-10-09-m25-prts-knowledge.md)，实施与偏离见 [13 §8.40](./13-决策记录.md) |
| 消耗类判定的口径 | **按内核实际会收到的参数判定**（M25 修 D1、Q43）：`_consumption_reasons` 对提交类工具用含默认值的完整任务定义、对 `set_task_params` 用「现有参数 + 本次修改」合并后的结果，取不到现有参数时 fail closed。对外影响：提交 Mall（默认购物）与 Roguelike（默认投资）今后会弹确认，显式 `false` 不弹；`Fight` 的计数字段默认 0 不受影响。见 [13 §8.40](./13-决策记录.md) |
| 里程碑边界 | M11 交付 REST 工具基座、确认与审计、会话只读 API；M13 已交付 LLM 循环、SSE 消息、Agent UI 与自动诊断。Copilot 通过共享任务队列和 schedule template，以每次运行的私有快照传给 MaaCore；Agent 上传后经 `submit_pipeline` 提交，不以普通 Fight 替代 |

Agent 的目标场景（全选）：自然语言变任务、出错自动诊断、卡死脉救援、应对 MAA 未适配的新活动、账号资源查询、读历史数据生成报告。

### 跨领域决策

| 项 | 决策 |
|---|---|
| 持久化 | 引入 SQLite。流水线历史、日志、配置、定时任务、agent 会话、审计全部落库 |
| ORM 与迁移 | SQLModel + Alembic |
| MaaCore 子进程 IPC | Python `multiprocessing` + `Queue` / `Pipe` |
| 子进程数量 | 先实现单个（维持"不允许多实例"语义），但接口与路由层按多子进程设计，留好扩展口 |
| 子进程崩溃处理 | 自动重启子进程，当前流水线标记失败并落库，前端告警 |
| 定时任务 | 保留并重做为前端"定时任务"模块，可视化配置执行时间与任务组合，配置落 SQLite |
| 通知 | 扩展为多通道：邮件 + Webhook + Bark / 钉钉 / 企微 / 飞书，设置页可开关与配置 |
| 流水线终态通知 | 完成 / 失败各推一条（含设备预检失败与领取失败）；用户取消与服务重启回收不推。逐条流水线由 `notify_on_finish` 控制，是否送达由通道的 `events` 订阅决定。见 [13 §8.19](./13-决策记录.md) |

## 关键技术约束

这些约束来自对本地 MaaCore v6.17.x 的 `AsstCaller.h` 与导出符号的核实，会限定方案的能力上限。

**MaaCore 只有点击，没有滑动。** C API 中只有 `AsstAsyncClick`，不存在 swipe、长按、输入文本、按键事件。所有滑动类操作必须走 ADB（`adbutils`）。

**MaaCore 的 OCR 没有独立 C API。** 内核内置 OCR（`libfastdeploy_ppocr`），但只能通过 `tasks.json` 的 task 定义间接触发，无法直接调用"识别这块区域的文字"。因此 agent 的画面理解只能依赖多模态模型看截图。

**`AsstConnect` 已被官方标记废弃。** 头文件注明 "FIXME: 5.0 版本将废弃此接口"，而当前代码正在使用它。必须迁移到 `AsstAsyncConnect`。

**`AsstGetMapLevelKey` 是实验性 API。** 位于 `AsstCallerExtra.h`，官方明确标注"不属于受支持的公共 API，可能随时变更或移除"。封装时必须隔离并提供优雅降级。

**ctypes 加载的 native 库无法在同进程内安全替换。** 这是选择子进程隔离架构的根本原因，详见 [03-MaaCore内核层设计](./03-MaaCore内核层设计.md)。

**PWA 的 Service Worker 与推送需要安全上下文。** 局域网 HTTP 访问（如 `http://192.168.1.x:8002`）下 Service Worker 不可用，只有 `localhost` 或 HTTPS 例外。这是首版就采用 Tailscale Serve 的原因；它同时带来三项配套要求（uvicorn 信任代理头、cookie `Secure` 按 `X-Forwarded-Proto` 判定、CORS 与 WS origin 白名单可配），详见 [09-前端重构方案 §12.4](./09-前端重构方案.md)。

**WebKit 忽略通知的 `actions` 与 `requireInteraction`。** iOS 与 macOS Safari 都不渲染推送通知上的按钮，通知也不常驻。因此「不打开应用就批准确认」只在 Chromium 上成立，两个平台共有的路径是"点通知体 → 深链回卡片 → 应用内批准"。被忽略的选项静默失效，没有异常也没有控制台警告。详见 [09-前端重构方案 §13.2](./09-前端重构方案.md)。

**Service Worker 访问不到 localStorage。** 它不是 window 上下文，而 localStorage 是同步 API。这导致从推送按钮批准确认时 Worker 拿不到 token，又不能退回用 cookie（写操作被禁），所以 token 需要额外写一份到 IndexedDB。三处存储的清除必须同步。

**官方 OTA 通道对国服只有一个 `tasks.json`。** 核实 `api.maa.plus/MaaAssistantArknights/api/resource/` 的目录索引后发现整棵树只有 6 个 `tasks.json`（国服 1 个、四个外服各 1 个、iOS platform_diff 1 个），没有其他文件类型——现有代码拉取的那一个文件已经是这条通道的全部内容。这推翻了"OTA 不止 `tasks.json`"的原始假设，也是决定首版必须纳入通道 B（`MaaResource` 仓库）的直接原因：只做通道 A 等于把现有功能重做一遍 UI，拿不到任何新资源。详见 [07-热更新方案 §3](./07-热更新方案.md)。

**增量资源的合并语义只到源码核对为止，未在本地内核上实跑。** 核对 `ResourceLoader` 得出三条结论：增量目录缺文件会被静默跳过、数据文件是整文件替换、模板图按文件覆盖而非整目录替换。第三条最要紧——若实际是整目录替换，加载通道 B 会让内核的模板图从 2464 张掉到 1009 张。但源码读的是发布线分支而本地库疑似另一条构建线（见下条），M7 动手前必须先验证。退路是放弃独立目录方案、改为按官方指引覆盖 `<maa_path>/resource/`，代价是每次内核更新后都要重新同步。详见 [07-热更新方案 §3.3](./07-热更新方案.md)。M7 实施时已按这条退路改为覆盖合并，见 [13-决策记录 §8.1](./13-决策记录.md)。

**通道 B 的落点不能直接覆盖 `<maa_path>/resource/`，这连带改动了两处既有设计。** 内核更新会把整个 MAA 目录替换成新解压的发行包，覆盖式落点每次升级内核都会被抹掉。改用独立目录后加载链从两层变四层，于是 `LOAD_RESOURCE` 命令的签名必须从单个增量路径改成有序列表（[02-系统架构设计 §3.1](./02-系统架构设计.md)、[03-MaaCore内核层设计 §7](./03-MaaCore内核层设计.md)）。同时三个增量目录（含现有代码写在 `<maa_path>/cache/` 的 OTA 缓存）要一并移到 `resource/maa-layers/`，与 `<maa_path>` 平级（[07-热更新方案 §3.7](./07-热更新方案.md)）——留在 `<maa_path>` 里就必须给内核更新加一条迁移步骤，而迁移出错会清空没有远端副本的自定义资源。

**本地内核疑似 `dev-v2` 构建线。** 本地头文件带有 `ClientType` 相关注释而上游 `dev` 分支没有，加上 macOS 库导出了头文件未声明的 `AsstGetItemName`，判断本地不是发布版构建。这个结论会影响其他 API 的可用性判断，建议在真机上验证一次。
