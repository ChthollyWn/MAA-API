## 实测结论

### W1 计划生命周期（§7.7）

- `async def preview(self, *, name, targets, run_times, context=None) -> dict[str, Any]`（`maa_api/services/account/plans.py:289`）返回键固定为 `today_tasks` / `daily_template` / `medicine{"today":0,"stone":0,"expiring_medicine":999}` / `days_estimated` / `total_sanity` / `stages` / `conflicts` / `unobtainable` / `notes`，全部是纯 JSON 值（确认服务要把它原样落库）。**卡片与提交共用同一套任务构造函数**（`build_today_tasks` / `build_daily_template`），所以卡片里的 `Fight` 次数与关卡就是将来真跑的。
- `MAX_FIGHT_RUNS = 20` 从死常量变成真切分规则：`split_fight_runs(runs, *, limit)`（`plans.py:70`），30 次 → 20 + 10，今天的流水线与每日模板同口径。
- 进度重算：`refresh()` → `_replan()` → `_update_schedule()`，规划入口是新抽的 `UpgradePlanner.plan_needs(needs, *, server=None, display=None)`（`maa_api/services/account/planner.py:1051`），与 `plan()` 共用 `_solve`（`planner.py:1119`）——**只走「材料 → 候选关卡 → 线性规划」，不重算目标增量、不再扣一次仓库**。成功写 `progress` 的 `stages`/`total_sanity`/`days_estimated`/`replanned_at`/`closed_dropped` 并 pop 旧的 `replan_error`，失败只写 `progress["replan_error"]` 并保留旧场次。
- 关卡关闭自动剔除的判据是掉率表的在开关卡（`_load_rates(include_closed=False)`），不引入新的「活动结束时间」数据源；与上次 `progress.stages` 比对后消失的关卡代号记进 `closed_dropped`。
- 删除定时任务同步取消：`ScheduleService.bind_delete_hook(hook)`（`schedule_service.py:243`，异常只 warning）+ `delete()` 末尾 `:422` 调用；`UpgradePlanService.on_schedule_deleted(schedule_id)`（`plans.py:532`）只改 `status=active` 且同 id 的计划；计划自己删任务（`_finish`/`cancel`）期间用 `_suppress_schedule_delete` 计数抑制，否则刚完成的计划会被钩子改回 cancelled。
- **顺带修掉的真 bug**：`_conflicting_schedules()` 原来对真实 `SchedulePage`（pydantic 行没有 `.get`）恒抛异常又被吞掉，`conflicts` 永远是空；现在用 `_page_items`/`_row_field` 兼容 dict 与 pydantic。因此「与现有定时任务争抢理智」从**从未生效**变成真有值——规格 §7.7 明文要求的行为变化。
- 冒烟（`scripts/account_smoke.py`）末段断言：`[3] 养成计划启动：今天的流水线 ['Fight','Depot']｜每日 0 8,20 * * *｜总理智 18`、`[4] 进度重算：剩余 {'扭转醇': 5}｜每日任务 Fight [7] 次`、`[5] 模拟完成：计划 completed｜定时任务 0 条｜通知 upgrade_plan_finished`、`[6] 计划列表 1 条｜取消后状态 cancelled`、`[7] 删除定时任务：schedule-1 → 计划 cancelled｜已完成计划仍是 completed`、末行 `SMOKE OK`。

### 装配顺序缺陷（M27 起就存在，本轮修）

- `maa_api/main.py` 的 lifespan 里 `UpgradePlanService` 比 `ScheduleService` 早构造约 300 行，构造参数 `schedule_service=app.state.schedule_service if hasattr(...) else None` 恒为 `None` → **真实启动时每日定时任务根本不会建**，冲突检查也恒为空；M27 的冒烟自己直接构造服务，所以从未暴露。
- 修法：计划服务加 `bind_schedule_service()`（与 `bind_finish_hook` 同款的后置绑定）；在 `ScheduleService` 创建之后接线，并接 `ScheduleService.bind_delete_hook(upgrade_plans.on_schedule_deleted)`；`PolicyEngine(...)` 处补 `plan_preview=upgrade_plans.preview`。
- `tests/api/test_upgrade_plan_wiring.py` 启动真实 lifespan 后断言三件事：`plans._schedule_service is schedules`、`schedules._delete_hook == plans.on_schedule_deleted`、`confirmation_service.policy.plan_preview == plans.preview`。**负向对照**：去掉 `main.py` 的三处接线后该用例必红（`1 failed, 1 passed`），还原后 `2 passed`。

### W2 计划 REST 与确认 payload

- 三条端点（`maa_api/api/routers/account.py:339` 起，全部 `require_auth`）：`GET /api/account/upgrade-plans`（可选 `status`，`Literal["active","completed","cancelled"]`，非法值 422；返回 `{"items","total"}`）、`GET /api/account/upgrade-plans/{plan_id}`、`DELETE /api/account/upgrade-plans/{plan_id}`（等价 `cancel_upgrade_plan`）。服务层没有 `get_plan`，单条 = `list_plans()` 过滤（形状与列表项天然一致；副作用是 GET 也会刷新进度，已写进 docs/05 §6.21）。`_plan_service` 先取 `upgrade_plan_service` 再取 `account_upgrade_plan_service`，都缺则 503 `SERVICE_UNAVAILABLE`。错误码复用既有的 `UPGRADE_PLAN_NOT_FOUND`，不新造码。
- `PolicyEngine.__init__(*, atomic_grant_minutes=..., plan_preview: PlanPreviewProvider | None = None)`：非 callable 抛 `TypeError("plan_preview must be a callable")`；`start_upgrade_plan` 的 payload 有 `preview` 时把 `conflicts` 合成**一条** reason「与现有定时任务争抢理智：<名字>（<id>）」（条目缺字段降级、全缺跳过），取不到时只放 `preview_error`（`str(exc)[:200]`）。**四条降级路径**（未注入提供者 / 参数不齐 / 提供者抛异常 / 返回值不是 Mapping）**都不拦确认**，`risk` 仍是 `NONE`、仍是每次确认。

### 门禁与运维

- **并发跑测试会造假红**：W1/W2/W4/W6 各自的全量运行出现过 5–10 个失败，两次之间失败集合还会换岗，全部落在没人改过的 app 级测试上（CORS 参数化、lifespan 迁移、`test_device_lifecycle` 的 greenlet）。写者停止后单独复跑这些文件全绿，最终全量只留两条已知真资源用例。另外 W2 用 `git archive HEAD` 到 `/tmp` 的「纯净副本也失败」实验不成立：`config.yaml` 是未跟踪且被忽略的本地配置，归档里没有它。**结论：验收必须在所有写者停止后独占复跑。**
