# M39 · 练度扫描分两类（全量左滑遍历 / 单个点名）

来源：用户 2026-10-11 原话（m00039）：「扫描任务分为两类，一类是全量扫描，一类是单个干员扫描。全量扫描任务逻辑为，起手 → 进干员列表 → 选择第一行第一个干员 → 点击查看练度详情并扫描 → 下一步不返回干员列表，直接向左滑动屏幕，会直接显示下一个干员的练度详情，这样可以直接遍历所有干员的练度详情页，直到滑动数次没有变动，即最后一个干员；单个干员扫描沿用现在的逻辑，打开干员列表，依次扫描格子里的干员名称，直到找到对应的干员，然后点击详情扫描。」计划见 [`docs/superpowers/plans/2026-10-11-m39-full-scan.md`](../plans/2026-10-11-m39-full-scan.md)。

M36 当时明确把全量扫描排除在首版之外（`docs/12`：「全量 384 人一轮 10–60 min，首版不做」），本轮把它补上。数据模型、写回口径、识别记录、取消与并发语义**全部沿用 M36/M37/M38**，只加一类编排。

## 1. 目标与用户决策

1. `POST /api/account/training-scan` 多一个 `mode`：`single`（默认，点名找人，现状）与 `full`（全量，详情页左滑遍历）。
2. 全量的推进方式按用户描述：进列表 → 点第一行第一格 → 读详情 → **不返回列表**，直接左滑读下一张详情，直到滑不动。屏内连续左滑这一段完全照用户描述实现。
3. 一处**必须偏离**用户描述的裁决（记台账，见 §5 与 `docs/13` §8）：详情页上的干员名字是美术字，内核 OCR 读不出来（M36 实测 score 0.166，回「画」），所以「一路不返回地滑下去」时**没有任何身份来源**，读到的读数会写到错误的人头上。做法改成**每屏 16 人先读一遍列表卡名认人，再在这一屏里连续左滑把 16 张详情扫完，然后回列表翻下一页**。屏内 15 次连续左滑一字不差地按用户描述走；整轮 24 屏只多出 24 次「返回 + 翻页」。这是「结果正确」与「步骤字面一致」之间的取舍，选前者。
4. 单个干员扫描（`mode=single`）**行为零变化**：名单来源、逐屏读卡名找人、点开、读详情、回列表、翻屏、`limit`/`deferred`/`unresolved` 口径全部照旧。

## 2. 事实基础（2026-10-11 真机实测）

探针：`scripts/probe_full_scan.py`（M39 新增，复用 `scripts/probe_training_scan.py` 的 plumbing）。设备 2560×1440（`127.0.0.1:5555`），MaaCore v6.18.0，游戏账号 384 名干员。

### 2.1 详情页左滑的姿势（唯一可行的一种）

详情页左右两侧是面板（左侧属性 / 信赖值，右侧技能 / 模组 / 职业栏），**只有起点落在立绘区域才会换人**：

| 变体 | 起点 → 终点（内核 1280×720） | 平均灰度差 | frac(>25) | 结果 |
| --- | --- | --- | --- | --- |
| mid / edge / slow / low（起点在右侧面板 x=1080/1220） | (1080,350)→(100,350) 等 | 0.00–0.05 | 0.000 | 不动 |
| **center** | **(650,400)→(250,400)** | **24.20** | 0.243 | 换人 |
| centerhigh | (700,250)→(200,250) | 28.33 | 0.304 | 换人 |
| centerlong | (760,430)→(120,430) | 40.54 | 0.363 | 换人 |
| centerback（反方向，起点在立绘） | (400,400)→(800,400) | — | — | 换到上一位 |
| prev / centerprev（起点落在左侧面板） | (100,350)→(1080,350) | 0.02 | 0.000 | 不动 |

形状与列表翻屏同款：`algorithm: JustReturn` + `action: Swipe` + `specificRect`/`rectMove` + `specialParams: [400,1,37,1]`。换人后画面在 0.9 s 内稳定（划后 +0.9 s 与 +1.7 s 两帧 mean=0.00）。

**禁区**：起点落在内核 x ≥ 1100（设备 2200+）会拖到右侧**职业筛选栏**——探针里 `edge` 变体一划就把筛选栏拉开并选中了「医疗」，列表被过滤、栅格整体左移约 140 设备像素，卡名 OCR 此后只回单字碎片。滑动起点必须留在立绘上。

### 2.2 车厢顺序 = **列优先**（本轮最关键的事实）

列表一屏 8 列 × 2 行，详情页左滑的顺序**不是**按行，而是按列：

```
点 top0(风笛) → 滑 1 次 可露希尔(bottom0) → 滑 2 次 凛御银灰(top1) → 滑 3 次 琴柳(bottom1) → …
```

即滑第 i 次（i 从 0 起）落在 `column = i // 2`、`row = top if i % 2 == 0 else bottom`。所以「点第一格 + 连续左滑 15 次」正好覆盖这一屏的 16 个人，与行优先的卡名读数按上表下标重排即可对齐。

### 2.3 列表位置保持（每屏回列表认人的前提）

读一屏卡名 → 点 top0 → 左滑 3 次 → 按返回 → **再读这一屏卡名，与滑动前逐格一致**。详情页左滑不会带动列表滚动，所以「回列表」不会丢位置。另：内核 `EnterBox`（`OperBoxBegin`）**必须从主界面跑**，在列表页跑会耗到 90 秒超时。

### 2.4 「划不动 / 翻不动」的像素信号

| 场景 | 平均灰度差 | frac(>25) |
| --- | --- | --- |
| 详情页划不动（第一个干员上反着划） | 0.02 | 0.000 |
| 详情页换人（顺划一次） | 24.20–48.57 | 0.243–0.548 |
| 列表翻页成功 | 41.92–67.53 | 0.482–0.661 |
| 列表翻不动（已经在最后一屏） | 0.05 | 0.000 |

⇒ 判据取 **平均灰度差 ≥ 2.0** 为「画面动了」，与噪声（0.02–0.05）和真实变化（24+）之间各有约两个数量级的余量。取平均灰度差而不是 frac(>25)：前者对半透明面板的细微变化更钝，代价只是阈值要重新标。

### 2.5 卡名漏检是固定存在的

干净基线（主界面 → `EnterBox`）一屏读到 14/16：`bottom0`（可露希尔）与 `bottom3`（丰川祥子）漏检、「余」被读成「手」。M36 记的是「每屏约 3/16 读不出」。**漏检的格子照样要滑过去**（车厢不会等人），只是不能写库。

### 2.6 身份只能来自列表卡名

详情页左下角有名字（拉丁名 + 美术字），但都是美术字，M36 实测 `OperBoxNameOCR` 回「画」score 0.166。这是 §1.3 那条偏离的全部原因。

### 2.7 工具边界：adb 注入的拖拽对游戏无效

`adb shell input swipe / draganddrop / motionevent`（分多次进程注入）在这台设备上对游戏画面**完全无效**（mean 0.02–0.06），点击有效。滑动标定只能用内核 `action: Swipe` 注入。另：`asst.get_image()` 在「只跑 `Swipe`/`JustReturn` 节点」的轮次里回的是**缓存帧**（5 张 md5 相同且与当场 adb 截图不同），所以探针取实时帧走 `adb exec-out screencap`；生产侧 `_detail_scan` 是在详情链（带识别节点）之后取图，那一帧是新鲜的。

## 3. 范围

### 3.1 本里程碑

- `mode` 参数（HTTP / Agent 工具 / 前端）与全量编排 `_scan_full`。
- 全量：屏内左滑遍历、列优先身份对齐、三条收尾判据、防错位（划不动检测 + 重试）。
- 新内核节点：详情页左滑节点 `SwipeNextDetail`（起点在内核 (650,400)）。
- 状态与文档：`snapshot()` 多 `mode` 与 `screens`，`docs/05`、`docs/09`、`docs/12`、`docs/13` §8、OpenAPI 快照与前端类型。

### 3.2 不做

- 不改单个扫描的任何行为与口径。
- 不做「只扫未识别/过期的人」的名单瘦身（M38 已记在案，另开里程碑）。
- 不做全量的断点续扫（中途取消后重跑＝从头滑，已经写库的读数保留）。
- 不改任务并发模型：全量同样是一轮独占设备。
- 不动 `docs/13` §8.51 那条「刷新识别不单独给入口」的裁决：全量扫描是同一张卡片上的第二种跑法，不新增页面入口。

## 4. 设计

### 4.1 两类任务的接口形状

服务层新增 `TrainingScanMode(StrEnum)`：`single`（默认）/ `full`。请求体 `TrainingScanRequest` 多一个 `mode` 字段；`full` 时 `limit` / `char_ids` / `include_plan_targets` **被忽略**（全量就是全表，不设名单），文档里写明；响应（POST 与 GET）多 `mode`，GET 另多 `screens`（已读屏数），`full` 的 `total` 恒为 `null`（全量的总数要滑到底才知道，UI 的「已读 x」不带 `/ y` 已经能表达）。

`full` 时 POST 返回 `targets=[]`、`deferred=[]`、`unresolved=[]`（`unresolved` 只在跑的过程中积累：卡名读出来但目录里没有的）。

### 4.2 全量扫描的编排

```
起手 StartUp → 进列表 EnterBox
screen = 0, prev_names = None
loop:
    names = 读一屏 16 格卡名（行优先）           # 6.6 s/屏（taskDelay=100）
    screen == 0 且一个名字都没有 → CORE_COMMAND_FAILED（画面不是列表，M37 §4.4 口径）
    screen > 0 且（names 为空 或 与 prev_names 有交集） → 翻不动/没有更多，收尾
    screen > 0 且 screen >= FULL_SCAN_MAX_SCREENS → 收尾（跑飞保护）
    # 屏内 16 张
    cur = 详情链(ClickCell(top,0))               # 第 0 张：点开 + 读详情
    记第 0 张 ← names[(top,0)]
    for i in 1..15:
        划一次（SwipeNextDetail）
        nxt = 详情链()                            # 第 i 张：只读详情
        while 画面没动(nxt.image, cur.image):      # 划不动 = 到头了，或一次偶发
            if 已经重试 FULL_SWIPE_RETRIES 次 → 收尾（名单到底）
            划一次；nxt = 详情链()
        记第 i 张 ← names[cell_of(i)]             # cell_of(i): column=i//2, row=top/bottom
        cur = nxt
    回列表 BACK；翻下一页 SwipeNextPage
    prev_names = names; screen += 1
```

`cell_of(i)`＝§2.2 的列优先下标。**先动后记**：只有确认画面真的换了人（或第 0 张的点开）才把读到的读数写到 `names[cell_of(i)]` 名下，划不动时绝不落到下一个人头上。

### 4.3 身份对齐、漏检与防错位

- 身份 = 列表卡名 → `char_id`（干员目录 `_name_index`；同名多形态不猜）。卡名没读出来的格子：这一张照滑，但**不写库**，记进 `skipped`（原因「这一张的卡名没读出来」）。
- 卡名读出来但目录里没有（`battle_data.json` 过期）：记进 `unresolved`，不写。
- `char_id` 不在账号表（账号表过期/未识别）：走 `apply_detail_scan` 现有的 `None` 分支，记进 `mismatched`。
- 防错位靠两条：①「划不动」不给身份（见 §4.2 的 while）；② 重试仍划不动则整轮收尾，不再猜。偶发划空的代价是这一屏后半段没扫到（记 `skipped`），不是把读数写错人。
- 一次滑动只前进一张：真机 3 次滑动 = 3 个人（§2.2），节点 `maxTimes=1`、`next=[Done]` 只执行一次手势。

### 4.4 收尾判据（四条，命中任意一条即结束）

1. **屏内左滑连续 `FULL_SWIPE_RETRIES + 1` 次画面不动**：已经到最后一名干员（车厢到底）。
2. **新一屏读到的卡名全是老面孔**（`seen` 集合，跨整轮累计）：列表没再往前。用「见过没有」而不是像素比对，是因为翻页后本来就要读卡名，白得一个判据；同一个干员不会在一屏里出现两次，所以「没有新面孔」＝「还在原屏」。
3. **`FULL_SCAN_MAX_SCREENS` 上限**：跑飞保护。
4. **整屏卡名在干员目录里一个都对不上 → 硬失败**：画面已经不在干员列表页（真机跑飞那次，此后每屏读到的都是主界面碎片）。

前三条命中时结束于 `succeeded`（**正常完成**，不是失败）；第四条是 `failed`（画面状态未知，宁可停下来报错，也不继续空转）。

**落地时的偏离与实测修正（2026-10-11）**：
1. 判据 2 起初写成「与**上一屏**重名 ≥ 上一屏全部」（`len(shared) >= len(names)`），真机整轮跑飞时暴露它兜不住：画面漂到主界面之后，每屏读到的碎片都在变，这条永远不成立，一轮白转 26 屏。改成跨整轮累计的 `seen`：新一屏一个没见过的名字都没有就收尾。
2. 每屏扫完**必须先 `_best_effort_back()` 回列表**再翻页：详情页上的翻页手势落在右侧面板上纹丝不动（§2.1），漏了这一步第二屏必然读不到卡名、整轮提前收尾。**例外**：第一格没点开详情页那一屏（`:attr:`_ScreenOutcome.SKIP`）**不能**按返回键——画面还停在列表上，按返回会直接退出干员列表。
3. `submission()` / 快照里的 `total`：全量扫描是 `None`（没有名单），不是 `0`——`0` 会让页面把「没有名单」和「一个人没扫」混起来。
4. 第一格「点开」要验一下到底开没开：点开前后各抓一帧比像素（`frame_changed`），再看详情读数有没有拿到东西（`skill_level`/`elite`）；两样都说没开就重试一次（`FULL_CLICK_RETRIES = 1`），还是没开就**跳过这一屏**继续翻页。点空一次的真实代价是：后面 15 次左滑把列表当详情页滑，最后那次返回直接退回主界面，整轮从第 7 屏起空转到第 33 屏（见台账）。

### 4.5 内核节点（`maa_api/services/account/scan_tasks.py`）

新增一个导航节点，形状照抄 `SwipeNextPage`，只换坐标：

```
SwipeNextDetail = {algorithm: JustReturn, action: Swipe,
                   specificRect: DETAIL_SWIPE_FROM = (650, 400, 100, 100),
                   rectMove:     DETAIL_SWIPE_TO   = (250, 400, 100, 100),
                   specialParams: SWIPE_PARAMS = [400, 1, 37, 1],
                   postDelay: DETAIL_SWIPE_POST_DELAY = 900,
                   maxTimes: 1, next: [Done], exceededNext: [Done]}
```

`postDelay` 取 900（比翻屏的 800 多 100 ms）：换人后 0.9 s 画面才稳（§2.1），这一步后面紧跟的详情链会在 `postDelay` 之后立刻截图，留一点余量。

**落地时的偏离（2026-10-11，真机验收逼出来的）**：左滑节点**不并进**详情链，而是单独一条流水线，后面再单独提交一次详情链（`_run_step(SWIPE_NEXT_DETAIL)` + `_detail_scan()`）。原写法（左滑当详情链的 `lead`，省一次 app 往返，M38 对「点开」就是这么做的）在真机上让每张卡片白跑一次重试——并链时链尾 `_grab_image()` 拿到的那一帧永远跟上一张比不出变化（`frame_changed` 回 `False`），只有拆开走第一次就成（`pipeline` 表 12 张卡片 12 次重试、8.4 s/张 vs 拆开后 ≈5 s/张）。

### 4.6 写回与识别记录

完全沿用：`apply_detail_scan`（`skill_level` / `masteries` / `modules`，精英化 <2 不提交后两列）、`record_training_scan` 一轮一条。全量写库人数可能很大（384 行），单条 UPDATE 走既有事务口径，不新增批量路径。

### 4.7 API / Agent 工具 / 前端

- `POST /api/account/training-scan`：body 多 `mode`；描述里写清 `full` 忽略名单参数、`total` 为 `null`、可能跑很久、取消语义不变。
- `GET`：返回多 `mode` 与 `screens`。
- Agent 工具 `scan_operator_training`：多一个 `mode` 参数（`single` / `full`），描述里点明全量会占设备很久、只在用户明确要「全量 / 全部干员」时用。
- 前端 `TrainingScanCard`：开始按钮拆成「开始扫描」（点名，现状）与「开始全量扫描」；卡片显示 `mode` 标签、全量时进度写「已读 x（第 n 屏）」，`total` 为 `null` 时不画比例条（现有 `scannedText` 已经这么处理）。

### 4.8 失败、取消与并发

- 并发锁、409、`SUBMIT_STARTED_TIMEOUT_SECONDS`、按步取消全部沿用。
- 取消/失败时把设备留在列表页：屏内左滑过程中的取消发生在步与步之间，收尾照跑一次 `BACK`（尽力而为）。
- 单张详情读失败：记 `skipped` 继续滑，不影响这一屏其它人（与 M36 单格失败同口径）。
- 一屏读卡名失败（整屏空）在第一屏是硬失败（画面不对），在第 ≥2 屏是正常收尾（判据 2）。

### 4.9 性能预算

一屏：读卡名 ≈ 6.6 s（taskDelay=100） + 16 张详情（每张 ≈ 4 s：左滑 1.3 s + 详情链 2.7 s） + 返回 2.4 s + 翻页 2.6 s ≈ **75–100 s/屏**；24 屏 ≈ **30–40 min**（与 M36 说的 10–60 min 同量级）。全量只写库不新增资源开销；`screens` 与 `message` 每屏更新一次，前端 5 s 轮询足够。

## 5. 兼容与风险

- **`mode` 是新增可选字段，默认 `single`**：老调用方（前端旧版本、Agent、开放 API 使用者）行为不变。
- 最大风险是**身份错位**（读数写到错的人头上）：靠「先动后记 + 划不动不记 + 重试仍不动就收尾」三道闸门挡住；真机验收里专门看一遍「读到的专精/模组与游戏界面对得上」（抽查 3 人）。
- 二次风险是**中途划空**（偶发）：代价是这一屏后半段没扫到（进 `skipped`），可重跑；不会写脏数据。
- 列表被人为筛选（职业筛选栏）或排序被改：全量按当前列表顺序走，身份仍然对齐（身份来自当屏卡名），不额外校验；`EnterBox` 会把排序带回「等级」。
- 回退：`mode` 默认值改回只认 `single`，或前端摘掉「开始全量扫描」按钮；服务层的 `_scan_full` 与一个节点是全部新增面。
