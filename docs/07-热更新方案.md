> 本文档定义 MAA 内核、活动资源、游戏本体三种更新的完整流程与共同机制。决策依据见 [README 决策速查表](./README.md#决策速查表)，架构位置见 [02-系统架构设计](./02-系统架构设计.md)。

# 热更新方案

## 1. 三种更新的本质差异

三个更新目标看起来同属"更新"，但技术性质完全不同，混为一谈会做出错误的设计。

| 目标 | 更新对象 | 是否需重启子进程 | 量级 |
|---|---|---|---|
| MAA 内核 | native 库文件（`libMaaCore.dylib` 等） | **必须** | 约 190 MB |
| 活动资源 | 内核读取的 JSON 数据 | 不需要 | 约 15 KB |
| 游戏本体 | 设备上的 APK | 不涉及子进程 | 约 1.8 GB |

**内核必须重启子进程**，因为 ctypes 加载的 native 库无法在同进程内安全替换（见 [README 关键技术约束](./README.md#关键技术约束)）。这正是选择子进程隔离架构的根本原因，收益在此兑现：更新时 API 服务全程不中断。

**活动资源不需要重启**，因为它是内核读取的**数据**而非映射的**代码**。`AsstLoadResource` 可重复调用，后加载的增量资源覆盖同名定义。这个区别是理解整套热更新方案的关键。

**游戏本体与我们的进程无关**，它是设备侧的事。难点不在流程而在量级——1.8 GB 的下载需要断点续传、进度上报、磁盘检查与完整性校验，每一环出错都意味着用户要重来一遍。

全文用到两个路径简写，它们在磁盘上**平级**，这一点贯穿内核更新与资源更新两节：

| 简写 | 实际路径 | 谁写它 |
|---|---|---|
| `<maa_path>` | `resource/lib/maa/{platform}/` | 内核更新流程整体替换 |
| `<layers>` | `resource/maa-layers/` | 三个增量资源层，内核更新不触碰 |

把 `<layers>` 放在 `<maa_path>` 之外是一项决策而非巧合，完整理由见 §3.7。

## 2. MAA 内核更新

### 2.1 版本查询

版本信息来自 `https://api.maa.plus/MaaAssistantArknights/api/version/summary.json`，返回三个发布通道：

```json
{
  "alpha":  { "version": "v6.18.0-beta.1.d017.g7e5de9b3c1",
              "detail": "https://api.maa.plus/MaaAssistantArknights/api/version/alpha.json" },
  "beta":   { "version": "v6.18.0-beta.1",
              "detail": "https://api.maa.plus/MaaAssistantArknights/api/version/beta.json" },
  "stable": { "version": "v6.17.5",
              "detail": "https://api.maa.plus/MaaAssistantArknights/api/version/stable.json" }
}
```

现有 `updater.py` 的 `Version` 枚举（`Nightly` / `Beta` / `Stable`）与 `map_version_type()` 的映射关系（`Nightly → alpha`、`Beta → beta`、`Stable → stable`）保留，改名为更贴合上游术语的 `ReleaseChannel`。

需要注意的是**旧域名 `ota.maa.plus` 已于 2025-11-29 停止解析**，官方要求迁移到 `api.maa.plus`。现有代码的 `Mirrors = ["https://api.maa.plus"]` 已经是正确的，但 `updater.py` 里遗留的示例注释仍写着旧域名，迁移时一并清理，避免后来者照着注释写错。

`summary.json` 当前还额外返回了 `version/alpha.json`、`version/beta.json`、`version/stable.json` 三个同名键（值只含 `version` 字段）。现有代码按 `response_data[version_type]` 取值不受影响，但新实现解析时要按白名单取 `alpha` / `beta` / `stable` 三个键，不要遍历全部键。

**当前版本号**从内核自身取。现有做法是 `Asst.load()` 后调 `Asst().get_version()`——这在重构后**不可行**，因为主进程绝不加载 `libMaaCore`（[02-系统架构设计 §1](./02-系统架构设计.md) 的纪律）。改为通过 IPC 的 `GET_VERSION` 命令向子进程查询，结果缓存在 `CoreSupervisor` 里（子进程 `READY` 事件的 payload 已经带了 `version`，直接用即可，无需额外往返）。

子进程未就绪时（`STARTING` / `CRASHED` / `FAILED`）拿不到版本号。此时降级从磁盘推断：读 MAA 目录下的 `resource/version.json`，或从安装目录里残留的发行包文件名解析。两者都失败则展示"未知"，且**允许**执行更新——内核起不来恰恰可能是需要更新或重装的场景，不能因为读不到版本号就禁用更新入口。

### 2.2 平台与架构匹配

`detail` 指向的 `stable.json` 结构为 `{"version": "...", "details": {...}}`，其中 `details.assets` 是发行资产数组：

```json
{
  "name": "MAA-v6.17.5-macos-runtime-universal.zip",
  "size": 193765923,
  "browser_download_url": "https://github.com/MaaAssistantArknights/MaaAssistantArknights/releases/download/v6.17.5/MAA-v6.17.5-macos-runtime-universal.zip",
  "mirrors": []
}
```

现有 `updater.py` 的平台判定逻辑正确，保留：

| `platform.system()` | `platform.machine()` | 目标标识 |
|---|---|---|
| `Darwin` | 任意 | `macos-runtime-universal` |
| `Linux` | `aarch64` | `linux-aarch64` |
| `Linux` | 其他 | `linux-x86_64` |
| `Windows` | `AMD64` / `x86_64` | `win-x64` |
| `Windows` | 其他 | `win-arm64` |

匹配正则也保留 `^MAA-.*-{platform}\.(zip|tar\.gz)$`。这个正则做对了两件容易忽略的事：实测 v6.17.5 的 62 个资产里，Linux 同时提供 `.tar.gz` 与 `.AppImage`、macOS 同时提供 `-runtime-universal.zip` 与 `-universal.dmg`，扩展名白名单恰好排除了 AppImage 与 dmg 这两种我们无法直接解压使用的格式。

不过有三点需要在重构时修正。

**资产列表存在重名条目。** 实测 `MAA-v6.17.5-macos-universal.dmg` 与 `MAA-v6.17.5-win-x64.zip` 各出现两次。现有代码用 `for` 循环遇到第一个匹配就 `return`，行为上没错但是隐式的。新实现应显式收集全部匹配项，按 `size` 一致性校验后取第一个，若出现 `size` 不同的同名资产则记 `WARNING` 日志——那意味着上游数据有问题，值得知道。

**`mirrors` 字段实测为空数组。** 现有代码注释里假设它包含 `s3.maa-org.net`、`agent.imgg.dev` 等镜像，实际上代码已经把这段注释掉了并只用 GitHub 直链。当前上游确实不再下发镜像列表，所以只有 GitHub 一个源。这对国内网络是明确的痛点，处置方式见 §2.3。

**`MAAComponent-OTA-*` 增量包只有 win-x64。** 资产列表里有大量形如 `MAAComponent-OTA-v6.17.4_v6.17.5-win-x64.zip` 的小体积增量包（5 MB 级，相比全量 273 MB），但**仅 Windows x64 提供**。macOS 与 Linux 只能走全量下载。本项目部署在 macOS 与 Linux，因此不实现增量包逻辑，只做全量——但要在代码注释里写明原因，避免后来者以为是遗漏。

### 2.3 下载与镜像

由于 `mirrors` 为空，唯一下载源是 `browser_download_url` 指向的 GitHub Releases。190 MB 从 GitHub 直连在国内可能极慢甚至失败，必须有应对。

三层策略，按顺序尝试：

1. **系统代理**。`config.yaml` 已有 `app.proxy` 配置项，现有 `HttpUtils` 也已把它应用到所有请求。这是首选，也是对用户最透明的方式
2. **用户自定义镜像前缀**。设置页新增一个可选的"下载加速前缀"配置，形如 `https://ghproxy.example.com/`，拼在 GitHub URL 前。不内置任何具体的第三方加速服务地址——这类服务寿命短、可用性不稳定，硬编码进代码等于埋雷
3. **上游 `mirrors` 字段**。虽然当前为空，解析逻辑仍要实现并优先使用。上游哪天恢复下发镜像，我们自动受益

三层都失败则报 `UPDATE_DOWNLOAD_FAILED` 错误，前端展示完整的下载地址供用户手动下载，并提供"从本地文件安装"的入口（上传已下载好的压缩包）。这个兜底很重要——网络问题是我们无法在代码里解决的，给用户一条出路比反复重试有价值。

下载器复用 `util/downloader.py`（从 `model/util/downloader.py` 迁移并增加进度回调）。现有 `Downloader` 类有分片并发下载的实现，但 `file_download()` 实际调用的是 `download_file_no_chunk()` 单线程路径，分片逻辑处于未使用状态。重构时**保留单线程流式下载**作为默认实现，理由是分片并发对单一 GitHub 源意义不大（瓶颈在链路而非并发数），而分片代码里的重试与合并逻辑复杂度高、缺乏测试覆盖。断点续传的需求由 §4.3 的通用下载器统一提供。

现有 `downloader.py` 用 `tqdm` 打印进度条到控制台，重构后改为回调：

```python
async def download(url: str, dest: Path, *,
                   on_progress: Callable[[int, int], None] | None = None,
                   resume: bool = True) -> Path:
    """流式下载。on_progress(downloaded, total) 由调用方节流后转成 WS 消息。"""
```

`tqdm` 依赖可以移除。

### 2.4 完整流程

```
POST /api/updates/core  { channel: "stable", force_interrupt: false }
  │
  ├─ ① 并发保护：取更新互斥锁，已有更新在跑则 409 UPDATE_ALREADY_RUNNING
  ├─ ② 落库 update_record(target=core, status=RUNNING)
  ├─ ③ 查询 summary.json → 目标版本；对比当前版本
  │     相同且非强制 → 置 SKIPPED 返回
  ├─ ④ 解析 detail.json → 匹配平台资产 → 得到 url / size
  ├─ ⑤ 磁盘空间检查：需要 size × 3 的可用空间（压缩包 + 解压临时目录 + 备份）
  │     不足 → 置 FAILED，错误码 UPDATE_DISK_INSUFFICIENT
  ├─ ⑥ 下载到 resource/temp/core-update/{version}/{filename}
  │     WS 广播 update_progress(phase=downloading)
  ├─ ⑦ 校验：文件大小与 assets.size 一致
  │     WS 广播 update_progress(phase=verifying)
  ├─ ⑧ 解压到临时目录 resource/temp/core-update/{version}/extracted/
  │     校验关键文件存在（见 §2.5）
  ├─ ⑨ 等待队列空闲（WS 广播 phase=waiting_idle）
  │     force_interrupt=true 则直接停止当前流水线
  ├─ ⑩ 进入维护窗口 CoreSupervisor.acquire_maintenance()
  ├─ ⑪ CoreSupervisor.stop()：SHUTDOWN → join
  ├─ ⑫ 备份现有目录 → 原子替换（见 §2.5）
  │     WS 广播 update_progress(phase=applying)
  ├─ ⑬ CoreSupervisor.start()，等 READY 事件（超时 120s）
  │     WS 广播 update_progress(phase=restarting)
  ├─ ⑭ 校验新版本号与预期一致；重新下发 CONNECT
  ├─ ⑮ 退出维护窗口，PipelineRunner 恢复消费
  └─ ⑯ 落库 SUCCESS，清理临时目录，WS 广播 phase=done
```

第 ⑩ 步的维护窗口是必需的（见 [03-MaaCore内核层设计 §4.3](./03-MaaCore内核层设计.md)）。没有它，第 ⑪ 步主动停止子进程会被崩溃检测判定为故障并触发自动重启，与更新流程正面冲突。

第 ⑨ 步的"等待队列空闲"有超时（默认 30 分钟）。肉鸽任务可能跑几小时，让更新无限期等下去不合理。超时后按请求参数决定：`force_interrupt=false` 时放弃更新并置 `FAILED`（错误码 `UPDATE_QUEUE_BUSY_TIMEOUT`），前端提示用户稍后再试或勾选强制中断。

### 2.5 原子性与回滚

直接把压缩包解压覆盖到 MAA 目录是现有 `updater.py` 的做法，风险在于：解压到一半失败会留下新旧文件混杂的目录，内核既起不来也退不回去。必须改为"先在旁边准备好，再整体切换"。

目录布局：

```
resource/
├── lib/maa/
│   ├── Darwin/                  # <maa_path>，当前使用
│   └── Darwin.backup/           # 上一版本备份，更新成功后保留一份
├── maa-layers/                  # <layers>，内核更新不触碰（见 §3.7）
│   ├── repo/                    #   通道 B
│   ├── cache/                   #   通道 A
│   └── custom/                  #   自定义资源
└── temp/core-update/
    └── v6.17.5/
        ├── MAA-v6.17.5-macos-runtime-universal.zip
        └── extracted/           # 解压后校验通过的完整目录
```

`maa-layers/` 与 `lib/` 平级是这个布局的关键：替换只发生在 `lib/maa/` 内部，增量层在替换的作用域之外。

替换流程：

```python
def apply_core_update(staged: Path, target: Path, backup: Path) -> None:
    """三步重命名。每一步都是同文件系统内的 rename，接近原子。"""
    if backup.exists():
        shutil.rmtree(backup)
    if target.exists():
        target.rename(backup)          # ① 现有版本让位
    try:
        staged.rename(target)          # ② 新版本就位
    except Exception:
        if backup.exists() and not target.exists():
            backup.rename(target)      # ③ 失败立即回滚
        raise
```

关键点是**临时目录必须与目标目录在同一个文件系统上**，否则 `rename` 会退化成跨设备复制，既不原子又很慢。因此临时目录选在 `resource/temp/` 而非系统 `/tmp`——前者与 `resource/lib/` 同在项目目录下。

**这个替换整体吞掉 `<maa_path>`，所以三个增量层一个都不能放在它下面。** `repo/`、`cache/`、`custom/` 统一落在 `<layers>`（即 `resource/maa-layers/`，见 §3.7），与 `resource/lib/` 平级而非嵌套。发行包里只有 `resource/`，若增量层在 `<maa_path>` 内，② 一旦完成，通道 A 的 OTA 缓存、通道 B 的 107 MB 同步、以及用户全部的自定义 task 会一起消失，其中 `custom/` 没有远端副本、属于永久丢失。放在外面之后，内核更新不需要任何迁移步骤，也就没有"迁移失败导致静默丢数据"这条故障路径——这是选择这个布局的首要理由。

由此内核更新对增量层唯一的实际影响是：通道 B 的版本基准必须落库、不能只读磁盘上的 `version.json`（见 §3.3）。内核更新把 `<maa_path>/resource/version.json` 换成了发行包自带的值，而 `<layers>/repo/resource/version.json` 不受影响仍是同步时的值，两个文件长期不一致。以落库记录为准就不受这个影响。

解压后、替换前的校验清单（缺任一项即判定包损坏，放弃更新且不动现有目录）：

- 平台对应的主库文件存在且非空：macOS `libMaaCore.dylib`、Linux `libMaaCore.so`、Windows `MaaCore.dll`
- `resource/` 目录存在，且其下 `tasks/`、`template/`、`config.json` 齐全
- `resource/version.json` 可正常解析为 JSON

注意现有 `updater.py` 有一段"解压后若存在同名子目录则把内容逐个 `shutil.move` 上来"的逻辑——不同平台的发行包目录结构不一致（有的压缩包根目录直接是文件，有的套了一层 `MAA-vX.Y.Z-platform/`）。这个归一化逻辑要保留，但移到临时目录里完成，校验通过后才整体替换。

**回滚**分两个层次。更新过程中失败走上面代码里的 ③，自动回退，用户无感。更新成功但新版本有问题（内核起不来、任务跑不通）时，提供 `POST /api/updates/core/rollback` 接口，把 `Darwin.backup` 换回来并重启子进程。备份只保留最近一个版本——保留多个的收益很低而磁盘占用是每份 190 MB。

### 2.6 只使用 stable 通道

**已拍板：只使用 stable，不向界面暴露 beta / alpha 选项。** 挂机场景下稳定性优先——内核是整个服务的地基，一个行为异常的预发布版本造成的排查成本远高于早几天适配新活动带来的收益。

实现上仍保留 `ReleaseChannel` 枚举与 `channel` 参数（§2.1 已说明现有 `Version` 枚举的映射关系），只是：

- `POST /api/updates/core` 的 `channel` 参数默认且仅接受 `stable`，传其他值返回 `400 INVALID_PARAMETER`
- 设置页不提供通道选择控件
- 解析 `summary.json` 时仍按白名单取三个键，只是只消费 `stable`

保留枚举而不删掉，是因为将来若要放开只需去掉参数校验与加一个前端控件，不必回头改数据模型与落库结构。`update_record` 表的 `channel` 字段照常记录实际使用的通道，历史数据在放开后仍然可比。

供将来放开时参考，`alpha` 通道的版本号形如 `v6.18.0-beta.1.d017.g7e5de9b3c1`（带 commit 距离与短哈希），是每日构建，稳定性无保证；界面上应标为"每日构建（不推荐）"而非直译的 "alpha"。

## 3. 活动资源更新

### 3.1 官方 OTA 清单的核实结果

这项决策最初的表述是"对齐官方完整 OTA 清单，不止 `tasks.json`"。为了确定"不止"具体指哪些文件，对 `https://api.maa.plus/MaaAssistantArknights/api/resource/` 做了逐层枚举（该路径开放 nginx 目录索引，可直接读到完整文件列表），实测结果如下：

```
/MaaAssistantArknights/api/resource/
├── tasks.json                                     15 KB
├── global/
│   ├── YoStarEN/resource/tasks.json              548 B
│   ├── YoStarJP/resource/tasks.json             1588 B
│   ├── YoStarKR/resource/tasks.json              544 B
│   └── txwy/resource/tasks.json                  456 B
└── platform_diff/
    └── iOS/resource/tasks.json                    95 B
```

**这棵树里的全部内容就是 6 个 `tasks.json`，没有别的文件类型。** 其中 `global/` 下四个是外服（美服、日服、韩服、台服）增量，`platform_diff/iOS/` 是 iOS 端差异。本项目按决策只支持官服与 B 服（均为国服），因此**只有根目录的 `tasks.json` 与我们相关**。

结论有点出人意料：现有 `asst_manager.py` 拉取的那一个 `tasks.json`，**已经是国服场景下官方 OTA 清单的全部内容**。"不止 tasks.json"这个假设对这条通道不成立。

### 3.2 但存在第二条资源更新通道

MAA 的资源更新实际上有两条彼此独立的通道，上面查的是其中一条。

**通道 A：`api.maa.plus` 的 OTA `tasks.json`**。这是 MAA 官方 Python SDK（`src/Python/sample.py`）示例中使用的方式，下载到 `<layers>/cache/resource/tasks.json`（官方示例落在 `<maa_path>/cache/`，我们移出了 `<maa_path>`，理由见 §3.7）后以增量方式加载。内容是**当期活动的 task 定义**——实测当前 47 个顶层键，全部是 `SR-*`（活动关卡）与 `BlackFlowTemporary@*`（活动玩法流程）这类条目。它解决的是"内核版本没变，但游戏开了新活动"的场景。

**通道 B：`MaaResource` 仓库**。这是 MAA 桌面客户端"设置 → 软件更新 → 资源更新"按钮背后的机制。仓库地址 `https://github.com/MaaAssistantArknights/MaaResource`，README 自述为"同步 MaaAssistantArknights 中与 MaaCore 版本无关，需要动态更新的文件（如新活动地图、公招数据等）"。

实测该仓库 `resource/` 目录包含：

```
Arknights-Tile-Pos/     地图格子坐标
battle_data.json        干员战斗数据
global/                 外服资源
infrast.json            基建配置
item_index.json         物品索引
recruitment.json        公招数据
stages.json             关卡表
template/               模板图
version.json            资源版本基准
```

**它明确不包含 `tasks/`、`tasks.json`、`config.json`、`ocr_config.json`**（这几个路径实测返回 404）。这与通道 A 正好互补：task 定义与内核版本强绑定，走 OTA 增量；数据类文件与内核版本无关，走仓库全量同步。仓库根目录还有一个只含 `.gitignore` 的空 `cache/` 目录，正是给通道 A 的 `tasks.json` 预留的落点，两条通道的布局设计上是配套的。

资源版本以 `resource/version.json` 的 `last_updated` 字段为基准。实测对比：

| 来源 | `last_updated` |
|---|---|
| 本地 MAA v6.17.5 自带 | `2026-09-05 11:08:36.000` |
| `MaaResource` 仓库当前 | `2026-09-14 04:36:14.000` |

也就是说内核自带的资源确实会滞后于仓库，通道 B 有实际价值。

MAA 客户端获取通道 B 更新时优先走 Mirror 酱（`https://mirrorchyan.com/api/resources/MaaResource/latest`），不可用或未配置 CDK 时回退到 GitHub 仓库压缩包。实测不带 CDK 调用该接口可以正常**查询版本**：

```json
{
  "code": 0,
  "msg": "current resource latest version is 2026-09-14 04:36:14.000",
  "data": { "version_name": "2026-09-14 04:36:14.000", "version_number": 290,
            "channel": "stable", "release_note": "月行水上" }
}
```

但响应里没有 `url` 字段——**下载需要付费 CDK**。这意味着通道 B 对我们只有"免费查版本、自己想办法下载"的价值。

### 3.3 方案：两条通道首版都启用

> **实施说明（M7）**：本节的独立目录多层加载方案无法在本地验证 `TilePack` 重载与模板缓存失效，实施按本节预留的退路改为覆盖合并，通道 B 更新需要重启子进程，见 [13-决策记录 §8.1](./13-决策记录.md)。

**已拍板：首版同时实现通道 A 与通道 B，通道 B 走 GitHub 仓库压缩包（不依赖付费 CDK）。** 理由是通道 A 单独拿不到任何新东西——§3.1 已经查明国服的 OTA 树只有那一个 `tasks.json`，而现有代码已经在拉它，只做通道 A 等于把现有功能重做一遍 UI。真正让"活动资源热更新"成为新能力的是通道 B 带来的地图坐标、关卡表、公招数据与模板图。

两条通道的职责边界是清晰互补的，这决定了它们可以共用一套下载与重载流程，只在"取什么"上不同：

| | 通道 A（OTA） | 通道 B（MaaResource） |
|---|---|---|
| 内容 | 当期活动的 task 定义 | 与内核版本无关的数据文件与模板图 |
| 粒度 | 单文件增量 | 仓库全量 |
| 体积 | 15 KB | 下载 13 MB，解压后 107 MB（实测见下） |
| 版本基准 | HTTP `ETag` / `Last-Modified`（见 §3.4） | `resource/version.json` 的 `last_updated` |
| 落点 | `<layers>/cache/resource/tasks.json` | `<layers>/repo/resource/`（与 `cache/` 同级，理由见下） |
| 失败影响 | 新活动关卡识别不了 | 退回内核自带资源，功能不缺失只是滞后 |

**因此通道 B 标记为 `required=False`。** 它失败时内核自带的那份资源仍然可用（只是滞后，实测滞后约 9 天），而通道 A 失败意味着新活动完全跑不了。这个差异要反映到失败处理上：通道 B 失败只告警不回滚整次更新。

清单定义为显式配置，`source` 字段区分两条通道的获取方式：

```python
class ResourceSource(StrEnum):
    OTA = "ota"                  # 单文件 HTTP GET，条件请求判新旧
    GIT_ARCHIVE = "git_archive"  # 仓库压缩包，version.json 判新旧

@dataclass(frozen=True)
class ResourceItem:
    key: str                     # 稳定标识，用于落库与前端展示
    source: ResourceSource
    url: str                     # 远端地址
    dest: str                    # 相对 <layers> 的落点
    required: bool               # 失败是否阻断整次更新
    client_types: tuple[str, ...] | None   # None 表示所有渠道都需要
    subdir: str | None = None    # 仅 GIT_ARCHIVE：压缩包内要提取的子目录

RESOURCE_MANIFEST: tuple[ResourceItem, ...] = (
    ResourceItem(
        key="cn_tasks",
        source=ResourceSource.OTA,
        url="https://api.maa.plus/MaaAssistantArknights/api/resource/tasks.json",
        dest="cache/resource/tasks.json",
        required=True,
        client_types=("Official", "Bilibili"),
    ),
    ResourceItem(
        key="maa_resource",
        source=ResourceSource.GIT_ARCHIVE,
        url="https://github.com/MaaAssistantArknights/MaaResource/archive/refs/heads/main.zip",
        dest="repo",
        required=False,
        client_types=None,
        subdir="MaaResource-main/resource",
    ),
)
```

`client_types` 字段让渠道切换能联动资源清单——虽然官服与 B 服共用同一份国服资源，但结构上留好了口子。渠道相关的联动见 [08-ADB连接与账号渠道](./08-ADB连接与账号渠道.md)。外服支持将来只需往元组里补 `global/*` 条目。

#### 通道 B 的实测体量

实测下载并解压了一次 `main.zip`（2026-09-16），数据如下，后面的下载与磁盘策略都基于它：

| 项 | 实测值 |
|---|---|
| 压缩包 | 13,916,116 字节（约 13.3 MiB） |
| 解压后 | 约 107 MB，5254 个条目 |
| `Arknights-Tile-Pos/` | 93 MB，4203 个文件 |
| `template/` | 12 MB，1009 个文件，**只有 `infrast/` 与 `items/` 两个子目录** |
| 其余 JSON 合计 | 约 2 MB |

再把它与本地内核 v6.17.5 自带的 `resource/` 逐文件比对，真实差异只有三处：`battle_data.json`、`version.json`、以及 `Arknights-Tile-Pos/`（16 个新增关卡文件加一个改动的 `overview.json`）。`infrast.json`、`item_index.json`、`recruitment.json`、`stages.json` 与 `template/` 下全部 1009 个文件**逐字节相同**。

也就是说通道 B 这次用 13 MB 的下载换来 17 个文件的更新。这个比例决定了两件事。一是**必须先比版本再决定下不下载**，绝不能每次检查更新都拉全量包。二是"按文件增量拉取"（用 GitHub API 逐文件比对 blob sha）是一个明确的后续优化方向，但首版不做——它要为 5254 个文件维护一份索引并发起大量小请求，在国内网络下未必比一个 13 MB 的包更快，复杂度却高得多。

顺带修正一个直觉误差：体积大头不是模板图而是 `Arknights-Tile-Pos/` 的关卡格子坐标（93 MB 对 12 MB）。它们是高度可压缩的 JSON，所以压缩包只有 13 MB 却能解压出 107 MB——**磁盘预检要按解压后的体积算，不能按压缩包大小算**。

#### 通道 B 的版本判定

**先查版本再决定是否下载**，否则每次检查更新都要拉 13 MB。基准是 `resource/version.json` 的 `last_updated` 字段。远端有两个免费来源：

1. Mirror 酱的 `https://mirrorchyan.com/api/resources/MaaResource/latest`，取 `data.version_name`。§3.2 实测不带 CDK 可以正常查版本，**只能查不能下**
2. `https://raw.githubusercontent.com/MaaAssistantArknights/MaaResource/main/resource/version.json`，取 `last_updated`

**首选第 1 条**，因为它是一个几百字节的 JSON 接口，专为版本查询设计，且多给了 `release_note`（实测值如"月行水上"）可以展示在前端版本面板上。实测两个来源当前返回同一个值（`2026-09-14 04:36:14.000`），可以互相印证。

第 2 条是 Mirror 酱不可用时的回退。它的好处是与实际要下载的压缩包严格同源——Mirror 酱毕竟是第三方镜像服务，理论上可能滞后于仓库。两者都取不到时报 `UPDATE_MANIFEST_UNAVAILABLE`，不要在拿不到远端版本的情况下盲目下载。注意这种情况按 §5.1 记 `FAILED` 而不是 `SKIPPED`——`SKIPPED` 的语义是"已确认是最新所以没动作"，而这里是"根本没查到"，两者混同会让前端的"最后更新时间"把一次失败显示成一次成功的免更新检查。

**本地基准必须从 `resource_asset` 表读，不能去读磁盘上的 `version.json`。** 这一点看起来绕，但磁盘上那两个候选文件都不可靠：

- `<maa_path>/resource/version.json` 是**内核自带**的那份，通道 B 从不写它（我们不覆盖 `resource/`，理由见下）。一次内核更新会把它换成新发行包里的值，而那个值与我们同步到哪一版毫无关系——既可能比我们旧，也可能比我们新
- `<layers>/repo/resource/version.json` 是通道 B 自己落盘的那份，内核更新碰不到它（§3.7 的布局保证了这点），但它仍不适合当基准：它只在压缩包里存在才有值，而"文件不存在"同时对应"从没同步过"和"同步过但这一版的包里没带 `version.json`"两种情况，无法区分

数据库里的基准不受这两种情况影响，且能区分"从没同步过"与"同步过且已经是最新"。字段设计见 [04-数据模型与持久化 §5.13](./04-数据模型与持久化.md)。落盘后要以**压缩包里实际的 `last_updated`** 回写基准，而不是查询时拿到的值——GitHub 的分支压缩包是实时打包的，下载期间分支有新提交时拿到的会更新，记错了会导致下次判断出错。

#### 通道 B 的下载

下载源与镜像回退**复用 §2.3 为内核更新定的那一套**，不另起一套配置：先走 `app.proxy` 系统代理，再走设置页里的"下载加速前缀"（拼在 GitHub URL 前），同样不内置任何第三方加速服务地址。§2.3 的第三层（上游 `mirrors` 字段）对通道 B 不适用——GitHub 仓库压缩包没有这个概念，所以通道 B 只有两层。

两层都失败时的处置也照抄 §2.3：报 `UPDATE_DOWNLOAD_FAILED`，前端展示完整下载地址并提供"从本地文件安装"的入口。这个兜底对通道 B 比对内核更新还合适——官方 issue #10033 给手动更新用户的指引本来就是"自己下载这个压缩包"，用户上传下来的包和我们自己下的是同一个文件。

**GitHub codeload 不支持断点续传。** 实测对压缩包地址发 `Range: bytes=0-1023`，返回的是 `200` 加完整的 `content-length: 13916116`，不是 `206`，响应头里也没有 `accept-ranges`。这正是 §4.3 强调"必须检查续传请求的返回码是不是 206"的场景：不检查就按 `ab` 模式追加写入，会把文件写坏且校验不一定拦得住。

因此通道 B **不做断点续传，中断即整包重来**。13 MB 的重下成本可以接受，1.8 GB 的游戏 APK 不行，两者策略不同的原因就在这里。重试按 §5.4 的规则：网络层由下载器自身指数退避重试最多 3 次，流程级失败（校验不过、解压失败）不自动重试。

进度上报复用 §5.2 的 `update_progress` 消息，`target=resource`，节流规则（每 500 ms 或每 1% 取先到者）不变。好消息是普通 GET 会返回准确的 `Content-Length`，百分比可以正常算；**但不要用 `HEAD` 预探体积**，实测 codeload 对 `HEAD` 不返回 `content-length`，拿不到总长就只能报不确定进度。

磁盘预检按**解压后**的体积算，不是压缩包大小。当前需求约 230 MB（解压产物 107 MB + 旧版本备份 107 MB + 压缩包 13 MB），空间不足报 `UPDATE_DISK_INSUFFICIENT`。这个数字要做成可配置常量并留出余量——它会随仓库增长而变化，且无法从响应头推出来，硬编码一个刚好够用的值迟早会失效。

#### 通道 B 的落点与加载链

**压缩包顶层是 `MaaResource-main/`，要提取的只是它下面的 `resource/` 子目录**（实测；顶层还有 `cache/`，但里面只有一个 `.gitignore`，丢弃不用）。提取后要重新拼出 `resource/` 这一层，因为 `AsstLoadResource(path)` 的约定是去读 `<path>/resource/`。写错这一层会导致加载静默无效——内核找不到 `resource/` 时不报错，只是什么都不加载。

**不能把它覆盖到 `<maa_path>/resource/`**，尽管官方 issue #10033 给手动更新用户的指引正是这么做的。区别在于我们有内核热更新而手动用户没有：§2.5 的内核更新会把整个目录 `rename` 成 `.backup` 再把新解压的发行包换上来，覆盖进 `resource/` 的通道 B 内容会随之整体消失，本地基准退回内核自带的旧值，形成"每次内核更新都要重下一遍"的循环。

同理它也**不落在 `<maa_path>` 下的任何位置**，而是与另两个增量层一起放到 `<layers>`（`resource/maa-layers/`，与 `resource/lib/` 平级）。理由与上一段相同且更强：只要在 `<maa_path>` 之内，内核更新的整体替换就会连带清空它，区别仅在于是否需要补一条迁移步骤来抢救。完整取舍见 §3.7。

```
resource/lib/maa/{platform}/resource/   内核自带基础资源，只由内核更新流程写
resource/maa-layers/repo/               通道 B：MaaResource 仓库同步
resource/maa-layers/cache/              通道 A：官方 OTA
resource/maa-layers/custom/             用户与 agent 自定义
```

完整加载链是**四次按序调用**，每次只传一个路径：

| 序 | 传给 `AsstLoadResource` 的路径 | 实际读取 | 内容 |
|---|---|---|---|
| ① | `<maa_path>` | `<maa_path>/resource/` | 内核自带基础资源 |
| ② | `<layers>/repo` | `<layers>/repo/resource/` | 通道 B 的数据文件与模板图 |
| ③ | `<layers>/cache` | `<layers>/cache/resource/` | 通道 A 的活动 task 定义 |
| ④ | `<layers>/custom` | `<layers>/custom/resource/` | 用户与 agent 的自定义 task |

**① 必须排在第一个**，有两个层次的理由。浅的一层是 §3.5 的合并语义：后加载覆盖先加载，基础资源在前才对。深的一层是核对 `AsstLoadResource` 实现后发现的——它内部对 `ResDir`（内核的资源根目录）只在其为空时设置一次，也就是由**第一次调用**永久钉死。第一次若传了增量目录，内核的资源根就指向那个残缺目录，后续一切按路径解析的查找都会错，且不报错。这条约束与增量层放在磁盘何处无关：`ResDir` 由 ① 传入的 `<maa_path>` 钉死，②③④ 只是叠加文件，路径可以任意。②③④ 的相对顺序理由见 §3.7。

落盘本身用"解压到临时目录再整体替换"，与 §2.5 的原子性策略一致，临时目录同样选在 `resource/temp/` 以保证与目标同文件系统（跨设备 `rename` 会退化成复制，107 MB 的复制既不原子也很慢）：

```
下载到 resource/temp/resource-update/{version}/main.zip
  → 校验：zipfile.testzip() 通过，且顶层目录为 MaaResource-main/
  → 解压 MaaResource-main/resource/ 到 .../staged/resource/
  → 校验 staged/resource/version.json 可解析，读出实际 last_updated
  → 原子替换（三步 rename，同 §2.5）：
        <layers>/repo  → <layers>/repo.backup
        .../staged     → <layers>/repo
  → 以实际 last_updated 回写 resource_asset 基准
  → 置 pending_reload 标志（见 §3.6）
```

#### 通道 B 的合并语义

§3.5 给出的是 **task 定义**的合并规则。通道 B 里一个 task 定义都没有，它给的是 `stages.json` 这类数据文件和 `template/` 下的图片，合并语义与 task 不同，必须分开说清楚。

核对 `ResourceLoader` 的实现（`src/MaaCore/Config/ResourceLoader.cpp` 与同目录的头文件）后可以确认三件事：

**增量目录允许残缺。** 内部的 `load_resource<T>(p)` 在 `p` 不存在时直接返回当前的"已加载"标志，而基础资源加载成功后该标志为真。所以增量目录里没有的文件被静默跳过而不是判为失败——这正是 `cache/` 只放一个 `tasks.json` 也能加载成功的机制；通道 B 不含 `tasks/`、`config.json`、`onnx/`、`PaddleOCR/`，同理不会报错。

**数据文件是整文件替换。** `stages.json`、`battle_data.json`、`recruitment.json`、`infrast.json`、`item_index.json` 走的是"整体解析进对应配置单例"的路径，没有 task 那样的按字段合并。这对通道 B 是正确语义：实测仓库里的 `stages.json` 与 `recruitment.json` 和本地内核自带的**逐字节相同**，说明仓库同步的是主仓的完整文件而非差分片段，整体替换不会丢内容。

**模板图是按文件覆盖，不是整目录替换。** `TemplResource::load(dir)` 为传入目录建一份"相对路径 → 绝对路径"索引，再对当前需要的模板名逐个查找并写进一张**跨调用累积**的表；本次没找到但此前已登记过的条目保持不变。所以后加载的目录只覆盖它确实提供的那些模板。

最后一条尤其关键，因为通道 B 的 `template/` 只有 1009 个文件而本地内核的 `template/` 有 2464 个。如果语义是整目录替换，加载通道 B 会让内核丢掉 1455 张模板图，后果是大面积识别失败。这个数字差实际上不构成问题，但原因比"按文件覆盖"更细：

- 顶层 `template/` 只在增量目录存在 `tasks/` 或 `tasks.json` 时才会被扫描——源码里 task 定义与 `template/` 是绑在同一次调用里的。通道 B 不含 tasks，所以它的 `template/` **不会**经这条路径加载
- 但通道 B 的 `template/` 实测只有 `infrast/` 与 `items/` 两个子目录，而这两个子目录分别由 `infrast.json` 与 `item_index.json` 的加载各自带上（源码里这一段的注释原文就是"OTA 配置（路径固定，勿修改）"），通道 B 恰好把这两个 JSON 也一起提供了
- 实测这 1009 个文件与本地对应子目录的文件集合**完全一致**，通道 B 在 `template/` 上是一份等价镜像而不是子集

也就是说通道 B 提供的每个文件都恰好落在 `ResourceLoader` 会去读的位置上，既没有"提供了但加载不到"的死角，也没有"该保留却被抹掉"的缺口。这个吻合不是巧合——源码里那段注释直接把这批路径称作 OTA 配置，通道 B 本来就是照着它组织的。

**以上结论来自源码核对，没有在本地内核上实跑过**，因此按 [13-决策记录 §5](./13-决策记录.md) 的惯例记为需要实测验证的假设，M7 动手前用最小脚本跑一次：

1. **合并语义在本地内核上成立。** 源码读的是发布线分支，而本地库疑似 `dev-v2` 构建线（见 [13-决策记录 §5](./13-决策记录.md)），两者的 `ResourceLoader` 未必一致。验证方法：按完整链条加载后，确认一个只存在于通道 B 新增关卡里的 `Arknights-Tile-Pos` 条目能被解析，同时确认一个只存在于内核自带 `template/`、通道 B 没有的模板（如 `template/Award/` 下任一张）仍然可用
2. **`TilePack` 重载时是否清空既有条目。** 它把每个关卡的文件路径解析为"被加载的 `overview.json` 所在目录 + filename"，并追加进一个列表。加载通道 B 的 `overview.json` 后全部 4203 个关卡文件都会改从 `<layers>/repo/resource/Arknights-Tile-Pos/` 取——实测该目录是本地的**严格超集**（本地有的它全有，另多 16 个），所以路径重定向本身安全；但若列表在重载时不清空，同一关卡会出现两条记录
3. **重载后模板缓存是否失效。** `TemplResource` 有一个 revision 计数用于通知匹配器缓存失效，需要确认重载确实让它递增，否则运行中重载会继续拿旧图做匹配

三条都不成立时的退路是放弃独立目录方案，改为按官方 issue #10033 的手动更新方式把文件覆盖进 `<maa_path>/resource/`。那条路径正确性有保证，代价是每次内核更新后都要重新覆盖一遍，且失去"一键清空通道 B 回到内核自带状态"的能力。

顺带一提，通道 B 的 `global/` 子树（约 1 MB，四个外服）对本项目无用——本项目只支持国服，内核只在按外服 `ClientType` 加载时才会读它。原样保留即可，不值得为省 1 MB 在解压时做过滤。

#### 通道 B 的失败与回滚

备份策略见 §5.5，这里说流程。通道 B 的每一步失败都不应该影响已经能用的内核自带资源：

| 失败点 | 处置 |
|---|---|
| 查不到远端版本 | 落 `FAILED`，报 `UPDATE_MANIFEST_UNAVAILABLE`，不动磁盘 |
| 下载失败 | 删 `.part` 文件，报 `UPDATE_DOWNLOAD_FAILED`，不动磁盘 |
| zip 校验或顶层目录名不符 | 报 `UPDATE_EXTRACT_FAILED`，不动磁盘 |
| 解压或 `version.json` 解析失败 | 清理 `staged/`，报 `UPDATE_EXTRACT_FAILED`，不动磁盘 |
| 原子替换中途失败 | 按 §2.5 的三步 rename 立即把 `repo.backup` 换回来；回滚也失败则报 `UPDATE_ROLLBACK_FAILED` |
| 替换成功但 `LOAD_RESOURCE` 失败 | 把 `repo.backup` 换回来并**重新下发一次完整加载链**，报 `RESOURCE_LOAD_FAILED` |

前五行都是"没碰目标目录"，天然安全。真正需要设计的是最后一行：资源已经换上去了，但内核加载不了。此时必须换回旧目录并重载，否则内核停在"新资源加载失败"的状态上，比更新前更糟。这与 [03-MaaCore内核层设计 §7](./03-MaaCore内核层设计.md) 给自定义 task 注入定的"加载失败自动回滚并重载"是同一条路径，实现上应共用。

因为通道 B 的 `required=False`，`channel='all'` 这一次更新的成败按通道 A 的结果判定：A 成功 B 失败仍记 `SUCCESS`，B 的错误写进 `update_record.log`，前端版本面板据此把通道 B 单独标为"更新失败"；A 失败则整次记 `FAILED`。只更通道 B（`channel='repo'`）时没有这层豁免，失败就是失败，`error_code` 照实写。这样"一键更新"不会因为可选通道出问题就整体标红，而用户明确只点了通道 B 时又能拿到真实结果。

### 3.4 条件请求与版本判定

两条通道的版本判定机制完全不同，分开说。

**通道 A** 没有独立的版本号接口，但 `api.maa.plus` 的响应头支持标准 HTTP 缓存校验。实测：

```
HTTP/2 200
content-length: 15358
last-modified: Fri, 11 Sep 2026 10:09:45 GMT
etag: "6aa3d369-3bfe"
```

带 `If-None-Match` 或 `If-Modified-Since` 重新请求均返回 **304**。这直接给出了"有没有更新"的判定方式，不需要下载全文再比对内容哈希：

```python
async def check_item(item: ResourceItem, cached: CachedMeta | None) -> CheckResult:
    headers = {}
    if cached:
        if cached.etag:
            headers["If-None-Match"] = cached.etag
        if cached.last_modified:
            headers["If-Modified-Since"] = cached.last_modified
    resp = await http.get(item.url, headers=headers)
    if resp.status_code == 304:
        return CheckResult(changed=False)
    resp.raise_for_status()
    return CheckResult(changed=True, body=resp.content,
                       etag=resp.headers.get("ETag"),
                       last_modified=resp.headers.get("Last-Modified"))
```

每个清单条目的 `etag` / `last_modified` / 内容 `sha256` / 落盘时间记录在数据库的资源元信息表里，同时作为前端"最后更新时间"的展示来源。

**不能只信 ETag。** 反代或 CDN 可能不透传，所以落盘前仍要算一次内容 `sha256` 并与已记录的比对，相同则视为无变化（跳过重载）。这层双保险的成本对 15 KB 的文件可以忽略。

写盘用"先写临时文件再 `rename`"，避免下载中断留下半截 JSON——那会让内核加载资源时报错甚至崩溃。写盘前还要做一次 `json.loads()` 语法校验，不合法直接判定为服务端问题并放弃本次更新。

**通道 B 不走 HTTP 条件请求**，判定方式在 §3.3 已经展开，这里只说它与通道 A 的差别，避免实现时套错模型：

| | 通道 A | 通道 B |
|---|---|---|
| 判定依据 | `ETag` / `Last-Modified` 响应头 | `version.json` 的 `last_updated` 字段值 |
| 判定时机 | 与下载同一次请求（304 即无更新） | 下载前的独立轻量请求 |
| 本地基准来源 | 落库的 `etag` / `last_modified` | 落库的 `last_updated`，**不读磁盘** |
| 无更新时的代价 | 一次 304，零字节 | 一次 JSON 请求，约 100 字节 |

通道 A 能把"判定"和"下载"合并成一次请求是因为它只有 15 KB，服务端给 200 就顺手收了。通道 B 的包是 13 MB，必须先问清楚再决定下不下载，所以判定和下载是两次独立请求。这也意味着通道 B 存在一个通道 A 没有的竞态：查版本到下载之间仓库若恰好又推了新 commit，下到的包会比查到的版本更新。这不是错误（内容只会更新不会更旧），但落库时要以**解压后实际读到的** `version.json` 为准，而不是以查版本阶段拿到的值为准，否则数据库记录会比磁盘落后一拍、下次检查出现幽灵更新。

通道 A 的"不能只信 ETag"那层 `sha256` 双保险对通道 B 不适用——`last_updated` 是仓库内容的一部分而非 CDN 生成的头，不存在反代不透传的问题。

### 3.5 重载：与内核更新的本质区别

活动资源更新完落盘后，只需向子进程下发一条 `LOAD_RESOURCE` 命令：

```python
await core_client.load_resource(
    path=maa_path,                 # ① 基础资源，见 §3.3 为什么必须单列且排第一
    incremental_paths=[            # ②③④ 有序，后者覆盖前者
        layers_path / "repo",      # 通道 B：数据文件与模板图
        layers_path / "cache",     # 通道 A：活动 task 定义
        layers_path / "custom",    # 用户与 agent 的自定义 task
    ],
)
```

增量层是一个**有序列表而非单个路径**。原设计的 `incremental_path` 只能装一个，早在 §3.7 要求同时加载 `cache/` 与 `custom/` 时就已经不够用了，纳入通道 B 只是让这个缺陷更明显。`AsstLoadResource` 的 C 签名是 `(const char* path) -> bool`，一次只吃一个路径，多层靠**按序多次调用**实现，拆分方式与失败处理见 [03-MaaCore内核层设计 §7](./03-MaaCore内核层设计.md)。

**不重启子进程，不中断任何连接。** 这与内核更新需要停进程、换文件、起进程、等 READY 形成鲜明对比。

> **实施说明（M7）**：这一条只对通道 A 成立。通道 B 改为覆盖合并后，更新需要在队列空闲时重启一次子进程，见 [13-决策记录 §8.1](./13-决策记录.md)。

耗时在只有通道 A 时是几百毫秒。纳入通道 B 后加载链多了一层 107 MB 的目录，且每次重载都要把整条链从头走一遍，**实际耗时需要重新实测**（标注为需实测验证的假设，见 [13-决策记录 §5](./13-决策记录.md)）。即便退化到数秒，它与内核更新的分钟级停机仍不是一个量级，结论不变——但 [02-系统架构设计](./02-系统架构设计.md) 里 `LOAD_RESOURCE` 的命令超时要按最坏情况留余量。

根本原因在 §1 已经说过：资源是内核**读取的数据**，库是进程**映射的代码**。`AsstLoadResource` 被设计为可重复调用，后加载的定义按同名字段合并覆盖先加载的（MAA 的任务协议文档对多文件任务的合并规则有明确定义：无 `baseTask` 字段则继承并覆盖同名任务的字段，有 `baseTask` 则整体替换，`"baseTask": "#none"` 显式断开继承）。加载顺序必须固定为**基础资源 → 增量资源**，顺序颠倒会让基础资源反过来覆盖活动定义。

### 3.6 重载的时机约束

**不能在任务执行中途重载。** 正在执行的任务可能已经读取了部分旧定义，重载后续步骤读到新定义，会出现半新半旧的行为——具体表现从"任务卡在某个界面"到"点错按钮"都有可能，且极难排查。

因此 `LOAD_RESOURCE` 下发前必须确认内核空闲。三种处理方式，按请求参数选择：

| 模式 | 行为 |
|---|---|
| `wait`（默认） | 资源已落盘，重载推迟到当前流水线结束后由 `PipelineRunner` 在取下一条前执行 |
| `force` | 立即停止当前流水线（置 `CANCELLED`），重载后恢复队列消费 |
| `defer` | 只落盘不重载，下次子进程启动时自然生效 |

`wait` 是默认值，因为活动资源更新不紧急——新活动的 task 定义晚生效几十分钟没有实际影响，而打断一局肉鸽的代价是真实的。通道 B 更是如此：它同步的是地图格子坐标、关卡表这类数据文件，滞后几小时也不影响正在跑的任务。

**两条通道共用同一个待重载标志和同一次重载。** 因为 `LOAD_RESOURCE` 下发的是整条加载链（§3.5），无论这次更新动的是 `cache/` 还是 `repo/` 还是两个都动，重载动作完全相同。所以一次"两条通道都有更新"的检查只会产生一次重载，不需要按通道分别置位。

实现上引入一个"待重载"标志：资源落盘后置位，`PipelineRunner` 在每次取新流水线之前检查该标志，置位则先执行重载再取任务。这个检查点天然处于空闲时刻，不需要额外的锁。

```
资源落盘 → 置 pending_reload 标志 → WS 广播 "资源已下载，将在空闲时生效"
PipelineRunner 循环顶部
  → if pending_reload and not core.running():
        await core.load_resource(...)
        clear pending_reload
        WS 广播 update_progress(target=resource, phase=done)
  → 取下一条 PENDING 流水线
```

服务启动时的加载路径也统一到这里：子进程启动序列里按 §3.5 的顺序加载本地已有的整条链（基础 → `repo/` → `cache/` → `custom/`，见 [03-MaaCore内核层设计 §3.1](./03-MaaCore内核层设计.md)），缺哪层跳过哪层，不做任何网络请求。网络侧的检查更新由主进程的 `UpdateService` 在启动后异步执行，检查到有更新则走上面的落盘 + 待重载流程。这个拆分让启动不再被网络 IO 阻塞——现有 `asst_manager.load_asst()` 把下载与加载揉在一起，网络不通时整个服务起不来。

### 3.7 自定义资源的隔离

agent 可以注入自定义 task 定义（见 [11-Agent模块设计](./11-Agent模块设计.md)），走的是同一个 `AsstLoadResource` 机制。三个增量层**必须彼此分离到不同目录**，且**全部放在 `<maa_path>` 之外**：

```
resource/lib/maa/{platform}/resource/   内核自带基础资源，由内核更新流程整体替换
resource/maa-layers/repo/resource/      通道 B 仓库同步，由 UpdateService 管理，可整体清空重下
resource/maa-layers/cache/resource/     通道 A 的 OTA tasks.json，由 UpdateService 管理
resource/maa-layers/custom/resource/    用户与 agent 的自定义资源，永不被更新流程触碰
```

`<maa_path>` 指 `resource/lib/maa/{platform}/`，下文用 `<layers>` 指 `resource/maa-layers/`。两者在 `resource/` 下平级，这是**刻意的**：内核更新替换的是整个 `<maa_path>`，把增量层放在它之外，更新流程就在结构上不可能碰到它们。

加载顺序为 基础 → `repo/` → `cache/` → `custom/`，自定义定义优先级最高。

这个顺序不是随意排的。通道 B 在通道 A 之前，因为 B 是数据类文件的全量同步、A 是当期活动的 task 增量，让 A 能覆盖 B 才符合"增量优先级更高"的语义；反过来会让全量同步覆盖掉活动定义。当前两条通道的文件集合其实不重叠（通道 B 实测不含任何 task 定义），这个顺序在今天不产生实际差异，但把它定死能保证仓库将来开始下发 tasks 时不会突然改变行为。而 `custom/` 必须在最后，否则 agent 注入的自定义 task 会被官方资源覆盖，自定义能力形同虚设。

层间分离的价值在于出问题时可以一键清空 `custom/` 回到官方状态，而不会连带丢失活动资源；反过来 OTA 更新也不会意外抹掉用户辛苦调的自定义 task。通道 B 独占一个与 `cache/` 平级的目录而不是塞进 `cache/` 里，有两个额外理由：它是体积最大（107 MB）也最可能需要整体重下的一层，独立出来才能单独清空；而 §5.5 给 `cache/` 定的是"体积极小、保留最近 5 份"的备份策略，把 107 MB 混进去会让那条策略直接失效。

**为什么整个 `<layers>` 在 `<maa_path>` 之外。** 曾经的设计是把三层放在 `<maa_path>` 下（`<maa_path>/cache/` 是 MAA 官方 SDK 示例的习惯落点），但这会引出一个严重缺陷：§2.5 的原子替换把整个 `<maa_path>` 换成新解压的发行包，而发行包里只有 `resource/`，于是每次内核更新都会连带清空三个增量层——`repo/` 和 `cache/` 重下一次就回来了，`custom/` 里的东西没有远端副本，是**永久丢失**。补救办法是在替换后把三个目录从备份搬回新目录，但那等于给内核更新增加一条必须成功的迁移步骤和对应的回滚路径，迁移一旦出错就静默丢数据。移到 `<maa_path>` 之外后这类故障不存在，`AsstLoadResource` 也不要求增量层与基础资源同级——它只接受一个路径并去读 `<path>/resource/`，路径在磁盘上的位置完全自由（约束只有一条：基础资源必须是**第一次**调用，见 §3.5）。

顺带解决的还有一处目录冲突：`<maa_path>/cache/avatars/` 是**内核自己**的干员头像缓存落点（内核按"用户目录 + `cache/avatars`"拼出来并自动创建）。旧布局下它与我们的通道 A 缓存挤在同一个 `cache/` 目录里，清空和备份都要特意绕开它；新布局下两者根本不在一处，`<layers>/cache/` 里只有我们自己的东西。

## 4. 游戏本体更新

### 4.1 版本信息的两条路径

官服与 B 服的能力不对等，这是设计的出发点。

**已安装版本**两服相同，通过 `adb shell dumpsys package <包名>` 解析，包名映射为：

| 渠道 | 包名 |
|---|---|
| Official | `com.hypergryph.arknights` |
| Bilibili | `com.hypergryph.arknights.bilibili` |

解析沿用 `feat/0515` 已验证的方式：先判断输出里是否含 `Package [<包名>]` 确认已安装，再用两个正则取值。

```python
INSTALLED_RE = re.compile(r"versionName=(.*)")
UPDATED_RE = re.compile(r"lastUpdateTime=(.*)")
```

取 `group(1).strip()`。未安装时返回明确的"未安装"状态而非"未知"，两者在前端的展示与可执行操作不同（未安装时按钮文案应为"安装"而非"更新"）。

**最新版本**两服差别很大。

B 服有可查的接口 `https://line1-h5-pc-api.biligame.com/game/detail/gameinfo?game_base_id=101772`，`code == 0` 时 `data` 里有一批有用的字段（实测值）：

| 字段 | 实测值 | 用途 |
|---|---|---|
| `android_pkg_ver` | `190` | B 服自己的包序号，非 versionName |
| `android_pkg_size` | `1901392256` | 包体字节数，用于磁盘预检 |
| `android_sign` | `b0863e6e628700fc2df73ba1499600cb` | 32 位十六进制，疑似 MD5，用于完整性校验 |
| `android_pkg_name` | `com.hypergryph.arknights.bilibili` | 与我们的常量交叉验证 |
| `android_download_link` | `https://pkg.biligame.com/games/mrfz_2.7.71_20260824_022945_16353.apk` | 主下载源 |
| `android_download_link2` | `https://pkgdl.biligame.net/games/mrfz_...apk` | 备用源 |
| `summary` | `SideStory「月行水上」活动开启` | 活动公告 |

**`feat/0515` 的 `apk_info.py` 把 `summary` 当成版本号返回，这是错的。** `summary` 是活动公告文案，与版本毫无关系。重构时不要沿用这个字段。

真正能与 `dumpsys` 的 `versionName` 对比的是**下载链接文件名里的版本段**：`mrfz_2.7.71_20260824_022945_16353.apk` 中的 `2.7.71` 就是 versionName 格式。解析：

```python
BILI_APK_VER_RE = re.compile(r"mrfz_(?P<ver>\d+(?:\.\d+)+)_(?P<date>\d{8})_")
```

这是从 URL 约定推断出来的，不是官方承诺的接口契约——B 服改文件命名规则就会失效。因此实现上必须能优雅降级：正则不匹配时退回用 `android_pkg_ver` 展示，并明确标注"无法与已安装版本直接对比"。

官服**只有下载直链 `https://ak.hypergryph.com/downloads/android_lastest`，没有任何版本号接口**。实测该地址 302 跳转到 `https://launcher.hypergryph.com/game/latest/...`，最终落到 CDN，响应头里没有版本信息，URL 路径里也没有（`feat/0515` 用 `os.path.basename(parsed.path)` 取文件名会得到无意义的 `1`，这是另一个要避开的坑）。

### 4.2 官服的版本对比降级方案

拿不到远端版本号，但拿得到**远端包的指纹**。实测对直链发 `Range: bytes=0-0` 请求（`HEAD` 被拒，返回 405）：

```
HTTP/2 206
content-type: application/vnd.android.package-archive
content-range: bytes 0-0/1882311496
etag: "BE459408D7BBA73A9FDD08CE8BCCA119-400"
last-modified: Mon, 31 Aug 2026 04:36:15 GMT
```

由此得到三个可用信号：**总大小** 1882311496 字节（约 1.75 GiB）、**ETag**、**Last-Modified**。

降级展示逻辑：

```
官服版本面板
  当前版本：2.7.71（来自 dumpsys versionName）
  安装时间：2026-08-25 10:33:12（来自 dumpsys lastUpdateTime）
  最新版本：官服未提供版本接口
  远端包更新时间：2026-08-31 04:36:15（来自 Last-Modified）
  远端包大小：1.75 GB
  判定：远端包更新时间晚于本地安装时间 → 可能有新版本
```

"远端包更新时间 vs 本地安装时间"是一个**启发式判断而非精确比对**，界面上必须如实说明。它会有两类误差：热更新（游戏内下载资源不重装 APK）会让本地 `lastUpdateTime` 显得过旧；用户重装同一版本会让它显得过新。因此官服的更新按钮永远可点（不像 B 服能在版本一致时禁用），文案为"下载并安装最新版"而非"更新到 x.y.z"。

ETag 作为辅助：把上次下载成功时的 ETag 记在数据库里，与当前 ETag 相同则几乎可以确定远端包没变，此时在界面上提示"远端包自上次下载后未变化"。注意这个 ETag 形如 `"BE459408D7BBA73A9FDD08CE8BCCA119-400"`，末尾的 `-400` 是 S3 分片上传的分片数标记，**它不是整个文件的 MD5**，不能当作完整性校验的期望值使用。

### 4.3 下载

1.8 GB 的下载必须做好四件事。

**进度上报。** 经 WebSocket 的 `update_progress` 消息（结构见 [06-实时日志与WebSocket §7.3](./06-实时日志与WebSocket.md)）。节流为每 500 ms 或每 1% 推一次取先到者——不节流的话 8 KB 一个 chunk 会产生二十多万条消息。除了百分比还要报瞬时速度与 ETA，用户在等一个小时的下载时这两个数字比百分比更有意义。

**断点续传。** 两个源都实测支持 Range 请求（官服返回 206，B 服的 `pkg.biligame.com` 为常规 CDN）。实现上记录已下载字节数，重试时带 `Range: bytes={downloaded}-`：

```python
async def download_resumable(url: str, dest: Path, *, expected_size: int,
                             on_progress) -> None:
    part = dest.with_suffix(dest.suffix + ".part")
    downloaded = part.stat().st_size if part.exists() else 0
    if downloaded >= expected_size:
        part.rename(dest)
        return

    headers = {"Range": f"bytes={downloaded}-"} if downloaded else {}
    headers["User-Agent"] = BROWSER_UA
    async with http.stream("GET", url, headers=headers, follow_redirects=True) as resp:
        if downloaded and resp.status_code != 206:
            # 服务端忽略了 Range，只能从头来
            downloaded = 0
            part.unlink(missing_ok=True)
        resp.raise_for_status()
        mode = "ab" if downloaded else "wb"
        with part.open(mode) as f:
            async for chunk in resp.aiter_bytes(1 << 20):
                f.write(chunk)
                downloaded += len(chunk)
                on_progress(downloaded, expected_size)
    part.rename(dest)
```

必须检查续传请求的返回码是不是 206——服务端忽略 `Range` 直接返回 200 全量时，追加写入会把文件写坏。这个检查在现有 `downloader.py` 的分片实现里是有的（`if response.status_code == 206`），但单线程路径没有，重构时补上。

`User-Agent` 要设成浏览器串。`feat/0515` 的实现里已经这么做了，保留——部分 CDN 对非浏览器 UA 有限流或直接拒绝。

**磁盘空间检查。** 下载前用 `shutil.disk_usage()` 检查目标分区，要求可用空间大于 `expected_size × 1.2`。APK 不需要解压，1.2 倍余量用于 `.part` 与最终文件在 `rename` 前短暂共存以及文件系统开销。空间不足直接报 `UPDATE_DISK_INSUFFICIENT` 并在错误详情里给出需要多少、还剩多少——这个信息能让用户自己解决问题。

`expected_size` 的来源：B 服取 `android_pkg_size`，官服取 `Range: bytes=0-0` 探测到的 `Content-Range` 总长。两者都拿不到时（接口变更）跳过预检并记 `WARNING`，不要因为拿不到大小就拒绝下载。

**完整性校验。** 分三层，可用哪层用哪层：

1. **大小一致**。最基本的一层，两服都能做。`.part` 文件大小必须精确等于 `expected_size`
2. **MD5 比对**。B 服的 `android_sign` 是 32 位十六进制，格式上符合 MD5。**这是从字段格式推断的，未经实际下载验证**（验证需要完整下载 1.8 GB）。实现上做成"若 MD5 匹配则通过；若不匹配则记 `WARNING` 并继续，不阻断安装"，等实际运行中收集到足够样本再决定是否改为强制。官服的 ETag 因为带 `-400` 分片标记而不可用于此层
3. **APK 结构校验**。用 `zipfile.ZipFile(path).testzip()` 确认是完整的 zip，且包含 `AndroidManifest.xml`。这层能拦住绝大多数截断与损坏，且不依赖任何外部承诺的哈希值。成本是读一遍文件，对 1.8 GB 约几秒，可以接受

第 3 层是实际的主力校验手段，务必实现。

### 4.4 安装

用 adbutils 的 `device.install()`（底层即 `adb install -r`）。几个必须处理的点。

**签名一致性。** Android 要求覆盖安装的 APK 签名与已安装应用一致，否则失败并返回 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`。这在渠道切换时是**必然会遇到**的：官服包与 B 服包签名不同且包名也不同，所以它们其实是两个独立应用，可以共存，不存在覆盖冲突。真正会触发签名错误的是同渠道但来源不同的包（例如用户之前装的是第三方渠道包）。处置方式是捕获该错误码，明确提示"已安装的应用签名与官方包不一致，需要先卸载再安装（会丢失本地缓存，账号数据在云端不受影响）"，并提供一个需人工确认的卸载重装入口——按 [README 决策速查表](./README.md#决策速查表)，卸载重装游戏属于破坏类操作。

**存储空间。** 设备侧也要空间，而且需要的比 APK 本身多（安装过程中系统会解压 dex、生成 odex）。安装前检查：

```python
out = device.shell("df /data")   # 解析可用块数
```

要求设备可用空间大于 APK 大小的 2 倍。不足时报错并给出具体数字。`INSTALL_FAILED_INSUFFICIENT_STORAGE` 是这类失败的错误码。

**安装超时。** 1.8 GB 的 APK 从推送到设备再到安装完成，在模拟器上可能要几分钟。adbutils 的默认超时远小于此，必须显式放大：

```python
device.install(apk_path, nolaunch=True, uninstall=False, flags=["-r", "-d"])
```

超时设置为 20 分钟。同时在这期间持续推送 `update_progress(phase="applying")` 心跳消息，否则前端会以为卡死。`adb install` 本身不提供进度，只能报一个不确定进度的状态。

**失败原因解析。** `adb install` 的输出里带 `Failure [INSTALL_FAILED_XXX]`，把它解析出来映射成中文提示比透传原文有用得多：

| 错误码 | 提示 |
|---|---|
| `INSTALL_FAILED_INSUFFICIENT_STORAGE` | 设备存储空间不足 |
| `INSTALL_FAILED_UPDATE_INCOMPATIBLE` | 已安装应用的签名不一致，需先卸载 |
| `INSTALL_FAILED_VERSION_DOWNGRADE` | 目标版本低于已安装版本，需加 `-d` 参数或先卸载 |
| `INSTALL_FAILED_INVALID_APK` | APK 文件损坏，请重新下载 |
| `INSTALL_PARSE_FAILED_NO_CERTIFICATES` | APK 未签名或签名损坏 |

未识别的错误码原样展示并附上完整输出，别吞掉。

**安装前要先关闭游戏。** 覆盖安装运行中的应用，Android 会强制杀掉进程，游戏可能来不及保存本地状态。而且如果 MaaCore 此刻正在操作游戏，会产生难以理解的行为。流程上：

```
① 等待队列空闲（与内核更新共用同一套等待逻辑）
② 通过 DeviceManager 停止游戏：adb shell am force-stop <包名>
③ 安装
④ 安装后不自动启动游戏（install 时带 nolaunch）
```

第 ② 步的包名取决于当前渠道配置，这是渠道联动的一个点，见 [08-ADB连接与账号渠道](./08-ADB连接与账号渠道.md)。

**安装后需要重新确认设备连接。** 安装本身不会断开 ADB 连接，但实践中大体积安装可能让模拟器短暂无响应，且部分模拟器在安装后会重启 ART 服务。稳妥做法是安装完成后：

```
① DeviceManager 主动做一次连接健康检查（adb shell echo ok）
② 不健康则走标准重连流程（见 08 文档的四时机重试）
③ 重新读取 dumpsys 获取新的 versionName 与 lastUpdateTime
④ WS 广播新的版本信息，前端面板刷新
```

第 ③ 步同时也是**安装成功的最终确认**——`adb install` 返回成功但版本号没变的情况虽然罕见但存在，以 `dumpsys` 的实际结果为准。

## 5. 三种更新的共同机制

### 5.1 更新记录落库

所有更新走同一张 `update_record` 表，字段设计见 [04-数据模型与持久化](./04-数据模型与持久化.md)，这里约定语义。

关键字段：`id`、`target`（`core` / `resource` / `game`）、`status`、`from_version`、`to_version`、`channel`、`caller`（`manual` / `agent` / `scheduled`）、`started_at`、`finished_at`、`error_code`、`error_message`、`bytes_total`、`bytes_downloaded`、`detail`（JSON，存清单条目级明细等）。

`status` 状态机：

```
PENDING → RUNNING → SUCCESS
                  → FAILED      （可从此状态发起重试）
                  → CANCELLED   （用户中止）
        → SKIPPED               （已是最新，未执行任何操作）
```

`SKIPPED` 单独一档而非算作 `SUCCESS`，这样"上次真正更新是什么时候"这个问题可以直接查出来，前端的"最后更新时间"展示才准确。

每次更新都落一条记录，包括检查后发现无更新的情况。这让"检查更新"本身也可追溯——用户反馈"明明有新版本却没检测到"时，能看到当时查到的版本号是什么。

### 5.2 进度上报

统一经 WebSocket 的 `update_progress` 消息，`update_id` 对应 `update_record.id`。消息结构与 `phase` 取值见 [06-实时日志与WebSocket §7.3](./06-实时日志与WebSocket.md)。

三种更新的 `phase` 序列不同：

| target | phase 序列 |
|---|---|
| `core` | `checking` → `downloading` → `verifying` → `waiting_idle` → `applying` → `restarting` → `done` |
| `resource` | `checking` → `downloading` → `verifying` → `waiting_idle` → `applying` → `done` |
| `game` | `checking` → `downloading` → `verifying` → `waiting_idle` → `applying` → `done` |

前端用统一的进度条组件渲染，`phase` 决定文案，`percent` 只在 `downloading` 阶段有意义（其余阶段为不确定进度）。

除了 WebSocket，进度也写进 `update_record` 的 `bytes_downloaded` 字段（节流为每 5 秒一次写库）。这样前端刷新页面或换设备打开时能恢复出当前进度，不必依赖 WebSocket 连接的连续性。

### 5.3 并发保护

**同一时间只允许一个更新任务。** 一个进程内的 `asyncio.Lock` 不够——需要在拿不到锁时立刻返回错误而不是排队等待：

```python
class UpdateService:
    def __init__(self):
        self._lock = asyncio.Lock()
        self._current: UpdateRecord | None = None

    @asynccontextmanager
    async def _exclusive(self, record: UpdateRecord):
        if self._lock.locked():
            raise DomainError(
                "UPDATE_ALREADY_RUNNING",
                f"已有更新任务正在执行：{self._current.target}",
                details={"update_id": self._current.id,
                         "target": self._current.target,
                         "phase": self._current.phase},
            )
        async with self._lock:
            self._current = record
            try:
                yield
            finally:
                self._current = None
```

`UPDATE_ALREADY_RUNNING` 对应 HTTP `409 Conflict`。错误详情里带上正在执行的更新信息，前端据此直接跳到那个更新的进度界面而不是只弹一个"请稍后"。

为什么三种更新共用一把锁而非各自一把：内核更新会重启子进程，资源更新要下发 `LOAD_RESOURCE`，游戏更新要停游戏并占用 ADB——三者两两之间都有冲突。共用一把锁最简单也最安全。

**服务重启后的残留记录。** 进程被杀时可能留下 `RUNNING` 状态的记录。启动时扫描并把它们置为 `FAILED`（`error_code` 为 `UPDATE_INTERRUPTED`），否则锁的状态与数据库不一致，前端会一直显示"更新中"。这个清理放在 `lifespan` 的启动阶段，紧跟数据库迁移之后。

### 5.4 失败重试与人工重试入口

**自动重试只在网络层。** HTTP 请求与下载分片失败时由下载器自身重试（指数退避，最多 3 次）。流程级的失败**不自动重试**——解压失败、校验不通过、安装被拒，重试同样的动作大概率还是同样的结果，而每次重试都要重新下载几百 MB 到几 GB。

**人工重试入口**为 `POST /api/updates/{update_id}/retry`。它基于原记录的参数创建一条新的 `update_record`（而不是复用旧记录），这样重试历史完整可见。

重试时的**断点复用**是必须的：已下载完成且校验通过的文件保留在 `resource/temp/` 下，重试时先检查是否已有可用文件（按大小与哈希判定），有则直接跳到后续步骤。对游戏 APK 这尤其重要——因为安装失败而重新下载 1.8 GB 是不可接受的。

临时文件的保留期设为 7 天，由清理任务处理。用户明确取消更新时立即删除对应的临时文件。

### 5.5 更新前的自动备份

三个目标的备份策略不同，因为可恢复性不同。

**内核**：按 §2.5 的方案，替换前把现有目录 `rename` 成 `.backup`。这是完整备份，代价是 190 MB 磁盘。只保留最近一个版本。

**活动资源（通道 A）**：备份 `<layers>/cache/` 到 `<layers>/cache.backup/`。体积极小（15 KB 级），可以保留最近 5 次，便于在"新活动资源有 bug"时快速往回退几个版本。不必再像旧布局那样排除内核自建的 `cache/avatars/`——头像缓存落在 `<maa_path>/cache/` 下，与 `<layers>/cache/` 已经不在一处（见 §3.7）。

**活动资源（通道 B）**：替换前把 `<layers>/repo/` 整体 `rename` 成 `<layers>/repo.backup/`，**只保留最近一份**（已拍板）。不照搬通道 A 的"保留 5 份"是因为每份 107 MB，5 份就吃掉半个 G。代价是只能回退一步：GitHub 的分支压缩包只给当前 HEAD，再往前的版本要按 commit 拉 `/archive/{sha}.zip`，首版不做这件事。考虑到通道 B 的内容是从主仓同步的数据文件（不是会写坏行为的 task 定义），需要连退几个版本的场景很难构造，这个取舍可以接受。

**游戏 APK**：**不备份**。一是 1.8 GB 备份的磁盘代价太高，二是从设备上拉回旧 APK（`adb pull` 已安装应用的 base.apk）本身就需要几分钟且未必成功，三是旧版本客户端通常连不上服务器，回滚没有实际意义。取而代之的是在更新记录里保存更新前的 `versionName` 与 `lastUpdateTime`，至少让用户知道自己原来是什么版本。

配置类的备份不在此列——`config.yaml` 与数据库的备份属于设置模块的职责。

### 5.6 定时检查与手动检查

**已拍板：每天自动检查一次，只检查不下载，有更新则通知；同时保留手动触发入口。** 三种更新的**下载与安装始终是手动触发**，自动化只到"告诉你有新版本"为止。

理由是这三种更新的代价差异很大，而"有更新"和"现在适合更新"是两件事。内核更新要重启子进程、游戏更新要下 1.8 GB 且可能在移动网络下产生费用、通道 B 要下 107 MB —— 这些都该由你在知情的前提下决定时机。反过来只做检查几乎没有代价：几个轻量 HTTP 请求，拿到的是一条通知。

```
ScheduleService 每日触发（默认 09:00，可在设置页改）
  → 调用与 GET /api/updates/status?refresh=true 相同的查询逻辑
  → 回写 resource_asset.last_checked_at 与各目标的远端版本
  → 若任一目标 has_update 为真：
       WS 广播 update_available 事件（前端版本面板出现红点）
       经 NotifyService 推送一条通知（汇总三个目标，不是发三条）
  → 全部无更新则静默，不产生通知也不写 update_record
```

几个设计要点：

**检查不写 `update_record`。** 那张表记录的是"做过哪些更新"，把每天一次的检查写进去会让更新历史被无内容的记录淹没。检查结果落在 `resource_asset` 的 `last_checked_at` 与远端版本字段上（见 [04-数据模型与持久化](./04-数据模型与持久化.md)），内核与游戏这两个没有对应表行的目标则只存进内存缓存 —— 它们的"上次检查时间"对用户的价值仅限于界面上显示一句"5 分钟前检查过"。

**通知要合并且要防重复。** 三个目标汇总成一条通知，否则一次检查最多发三条。更重要的是**同一个版本只通知一次**：把已通知过的版本号记下来，下次检查若远端版本没变就不再推送。否则你会连续 14 天每天收到同一条"MaaCore v6.18.0 可用"，很快就会去关掉通知。

**检查失败不通知。** 网络不通、GitHub 不可达这类失败只记服务日志，不推送。自动检查是后台行为，用户没有主动发起，为它的失败去打扰用户不合理 —— 而手动点「立即检查更新」的失败必须在界面上明确报错，因为那是用户在等结果。

**与定时任务共用调度器但独占一个 job。** 它不进任务队列（[02-系统架构设计](./02-系统架构设计.md) 的优先级队列只管 MAA 任务），因为它不碰内核也不碰设备，与流水线执行完全无关，没有互斥需求。检查期间用户照常可以跑任务。

## 6. 与 Agent 的衔接

按 [README 决策速查表](./README.md#决策速查表)，"重装内核"属于破坏类操作，需要人工确认。三种更新对 agent 的开放程度按风险分级：

| 操作 | 风险 | 需人工确认 |
|---|---|---|
| 查询版本信息 | 无 | 否 |
| 更新活动资源 | 低 | 否 |
| 更新 MAA 内核（stable 通道） | 中 | 否 |
| 更新 MAA 内核（beta / alpha 通道） | 中高 | **是** |
| 重装 MAA 内核（清空目录重下） | 高 | **是** |
| 更新游戏本体 | 中高 | **是** |
| 卸载重装游戏 | 高 | **是** |
| 带 `force_interrupt=true` 的任意更新 | 高 | **是** |

活动资源更新不需要确认，因为它可回滚、体积小、且是 agent"应对 MAA 未适配的新活动"场景的必要前置动作，每次都要人确认会让这个场景变得很难用。

内核 stable 更新不需要确认的理由是它有完整的回滚机制且不消耗游戏内资源。但**带强制中断的更新必须确认**——它会打断用户正在跑的任务，这个代价用户应当知情。

游戏更新需要确认的理由是流量与时间成本：1.8 GB 的下载在移动网络下可能产生实际费用，而 agent 无从判断用户的网络环境。

确认流程走 `PolicyEngine` 与 `confirmation` 机制，WebSocket 事件结构见 [06-实时日志与WebSocket §7.3](./06-实时日志与WebSocket.md) 的 `confirm_request`，编排细节见 [11-Agent模块设计](./11-Agent模块设计.md)。确认卡片的 `summary` 字段应包含具体代价，例如"将下载约 1.8 GB，预计耗时 15 分钟，期间无法执行任务"——让用户在有信息的前提下决策。

所有更新调用无论是否需要确认都**全量落审计表**：调用方、时间、参数、确认结果、耗时、最终状态。

## 7. 前端版本面板

面板是三张并列的卡片（移动端纵向堆叠），每张对应一个更新目标。

**共同字段**：当前版本、最新版本、更新时间、状态徽标、操作按钮。

**MAA 内核卡片**：

```
MAA 内核                                    [最新]
当前版本    v6.17.5
最新版本    v6.17.5（stable 通道）
更新时间    2026-09-16 10:25
                                    [检查更新] [切换通道]
```

有更新时徽标变为"可更新"，按钮变为"更新到 v6.18.0"。通道切换在这张卡片的次级菜单里，切到非 stable 时卡片顶部出现黄色警示条。子进程未就绪时当前版本展示为"未知（内核未就绪）"，更新按钮**保持可用**。

**活动资源卡片**：

```
活动资源                                    [有更新]
资源版本    2026-09-11 18:09（按远端 Last-Modified）
上次检查    2026-09-16 14:02
生效状态    已下载，将在任务空闲后生效
                                    [立即检查] [立即生效]
```

"生效状态"这一行是内核卡片没有的，对应 §3.6 的 `pending_reload` 标志。"立即生效"按钮在有待重载资源且内核正在跑任务时出现，点击等同于 `force` 模式（会打断当前流水线），因此需要二次确认。

**游戏本体卡片**（官服，展示降级形态）：

```
明日方舟（官服）                            [可能有更新]
已安装      2.7.71
安装时间    2026-08-25 10:33
远端包      1.75 GB，更新于 2026-08-31 04:36
            官服未提供版本号接口，以上为包体更新时间
                                    [下载并安装]
```

**游戏本体卡片**（B 服，展示完整形态）：

```
明日方舟（B 服）                            [最新]
已安装      2.7.71
安装时间    2026-08-25 10:33
最新版本    2.7.71（B 服包序号 190）
包体大小    1.77 GB
                                    [重新安装]
```

两服卡片的差异是有意保留的——把官服的不确定性如实呈现给用户，比伪造一个看起来精确实则猜测的版本号更负责任。

**更新进行中**时卡片切换为进度形态，展示 `phase` 文案、进度条、速度、ETA 与取消按钮。取消对 `downloading` 阶段有效（删除 `.part` 文件或保留供续传，由用户选择），对 `applying` 阶段无效（按钮置灰，文案说明"正在应用更新，无法取消"）。

**更新历史**在面板底部折叠展示，取自 `update_record` 表，每行是时间、目标、版本变化、结果。失败的记录可展开看错误详情并提供重试按钮。

版本信息的获取接口为 `GET /api/updates/status`，一次返回三个目标的完整状态。这个接口涉及多次外部网络请求（`summary.json`、Mirror 酱或 GitHub raw 的 `version.json`、biligame 接口、直链探测）与一次 ADB 调用，耗时可能到几秒，因此：结果缓存 5 分钟；各来源并发查询；任一来源失败不影响其余（该项返回"查询失败"而非整个接口 500）。前端首次加载时先展示缓存值再后台刷新。

面板顶部有一个**「立即检查更新」按钮**，对应 `GET /api/updates/status?refresh=true` —— 绕过 5 分钟缓存强制重查。它与下面 §5.6 的每日自动检查是同一套查询逻辑的两个入口，区别只在于要不要用缓存。按钮在请求期间置为 loading 并禁用，避免连点打出多次外部请求。

## 8. 待确认的开放问题

**"对齐官方完整 OTA 清单"指的是哪条通道——已拍板。** §3.1 与 §3.2 的枚举结果表明这句话可以指两件不同的事：通道 A（`api.maa.plus` 的 OTA 树，整棵只有 6 个 `tasks.json`，国服就 1 个，现有代码已全覆盖）或通道 B（`MaaResource` 仓库，桌面端"资源更新"按钮背后的机制，含数据文件与模板图但不含任何 task 定义）。**决定首版两条通道都启用**，通道 B 走 GitHub 全量压缩包下载（Mirror 酱的免费接口只能查版本、拿不到下载地址，`url` 字段需要付费 CDK）。方案见 §3.3。此条不再需要人工拍板，保留在此是为了记录两条通道的差别与选择理由。

**通道 B 的合并语义在本地内核上是否成立——需实测。** §3.3 已通过核对 `ResourceLoader` 源码确认了三条结论（增量目录允许残缺、数据文件整文件替换、模板图按文件覆盖而非整目录替换），但源码读的是发布线分支而本地库疑似另一条构建线。§3.3 末尾列了三项需要用最小脚本验证的假设与验证不通过时的退路，M7 动手前必须先跑这一步。

**B 服 `android_sign` 是否为 APK 文件的 MD5。** 字段格式（32 位十六进制）符合 MD5，但未经实际验证——验证需要完整下载 1.8 GB 并计算哈希。首版按 §4.3 的方案实现为"匹配则通过，不匹配只告警"。建议首次真实更新后人工核对一次，确认后再改为强制校验。

**B 服 APK 文件名的版本段格式是否稳定。** §4.1 的正则依赖 `mrfz_<version>_<date>_` 这个命名约定，这是观察得出的规律而非官方契约。需要在多个版本迭代后观察其稳定性。

**官服直链的 302 目标是否会变。** 实测 `ak.hypergryph.com/downloads/android_lastest` 跳到 `launcher.hypergryph.com/game/latest/GzD1CpaWgmSq1wew/1/1`，路径里的 `GzD1CpaWgmSq1wew` 看起来是某种固定标识。实现上只请求入口直链并跟随重定向，不硬编码中间地址——但需要留意官服若改为需要签名参数或反爬校验，这条路径会整体失效。届时的备选是引导用户手动下载后上传。

**内核更新的磁盘余量系数。** §2.4 第 ⑤ 步按 `size × 3` 估算（压缩包 + 解压 + 备份）。macOS 包解压后约 300 MB 而压缩包 190 MB，3 倍略有富余但不算浪费。实际部署环境（尤其是容器）的磁盘配额需要确认，必要时把系数做成可配置。

**每日自动检查的时刻默认值。** §5.6 定的是每天 09:00，可在设置页改。这个时刻本身没有技术依据，取的是"早上起来就能看到有没有更新"。若你的作息不同，改设置即可，不影响实现。
