# 12 实施路线与里程碑

v3 分六个阶段、36 个里程碑（M63–M98）。当前要执行的是 M63–M85，spec 在 [specs/](./specs/README.md)。P4、P5（M86–M98）的稿在 [specs/todo/](./specs/todo/README.md)，标为 TODO，不是执行规格。顺序不调整，除非 [13 §8](./13-决策记录.md) 记了偏离。

## 1. 阶段总览

```mermaid
flowchart LR
    P0["P0 地基 M63–M68"] --> P1["P1 骨架 M69–M73"]
    P1 --> P2["P2 Worker 内核 M74–M80"]

    P3 --> P4["P4 领域亮点 M86–M90"]
```

| P5 扩展 | MCP Client、Hooks、代码沙箱、高级检索与知识图谱、经验沉淀、代理团队与 DAG、人格与语音、版本化与 A/B |

## 3. 分支、提交与 tag

- 每个里程碑从 `dev` 拉一个短英文名分支，名字取 spec 文件名去掉 `mNN-` 前缀，例如 `agentspec-harness`。
- 小步提交，提交信息格式 `<类型>(m<N>): <中文摘要>`，类型用 `feat`、`fix`、`docs`、`test`、`refactor`、`chore`。
- 完成后 `git merge --no-ff` 回 `dev`，合并信息 `merge: <标题>（M<N>，见 docs/v3/13 §8.x 或「无偏离」）`；打 tag `v3-m<N>`。
- 默认不推送；用户明确要求时才推。发布时把 `dev` 合入 `master`（AGENTS.md）。
- 不用 worktree。

## 4. 每个里程碑的完成标准

一个里程碑只有在下面各项都满足时才算完成。主 agent 必须亲自重跑第 2–7 项，不以实现者的报告为准。

1. spec 的每个任务都完成，§0 的前置检查与 §7 的验收命令全部通过。
2. 后端全量测试：`.venv/bin/python -m pytest -q > /tmp/pytest.log 2>&1; echo $?`，看 `tail -n 30 /tmp/pytest.log`。与本分支起点的 `dev` 相比不新增失败；起点已有的失败记进台账。
3. 改了接口：先 `.venv/bin/python scripts/dump_openapi.py`，再 `cd web && pnpm gen:api`，然后 `.venv/bin/python scripts/dump_openapi.py --check` 与 `pnpm gen:api:check` 通过；现行路由清单与错误码表测试通过。
4. 改了前端：`cd web && pnpm install --frozen-lockfile && pnpm gen:api:check && pnpm typecheck && pnpm test --run && pnpm build`，然后 `.venv/bin/python scripts/frontend_smoke.py`，末行 `SMOKE OK`。
5. 冒烟：M65 起每个动 `maa_api/agent/` 的里程碑跑 `.venv/bin/python scripts/agent_smoke.py`；M73 起再跑 `.venv/bin/python scripts/orchestrator_smoke.py`；简报相关改动另跑 `.venv/bin/python scripts/brief_smoke.py`。末行都是 `SMOKE OK`。
6. 评测：M68 起跑 `.venv/bin/python scripts/agent_eval.py --suite regression --mode replay`，全部通过；改了提示词或代理定义的里程碑另跑 `--suite capability --mode replay`，通过率不低于台账里上一个里程碑记录的基线。
7. `git diff --check` 干净；M64 起 `.venv/bin/python scripts/check_doc_links.py` 输出 `BROKEN 0`。
8. 文档同步：受影响的 v3 文档（02–11）、`docs/v3/14-现行接口清单.md`、`config.template.yaml`；与 spec 不一致的地方记进 13 §8。
9. 台账：`docs/v3/ledgers/<spec 文件名>.md`，包括做了什么、验证证据（命令与结果）、「Rulings I made」（自行裁决的实现细节）、遗留问题。
10. 合并与 tag（§3）。

依赖真机、模拟器或真实内核的检查（`scripts/core_smoke.py`、真机会话复盘）不作为硬性验证，只作补充，结果记进台账。

## 5. 执行者工作流

执行者（不论能力强弱）对每个里程碑都按这个顺序做：

1. 读 spec 全文；读 spec「相关文档」一节列出的 02–11 小节。只做 `docs/v3/specs/` 根目录下的里程碑。`specs/todo/` 标了 TODO，跳过。不通读 v2 的大文档（v2/13 有 600 多 KB），需要时用 `rg` 查具体小节。
2. `git checkout dev`，`git checkout -b <分支名>`。
3. 跑 spec §0 的前置检查。任何一条不符合预期，停下来报告，不要继续。
4. 按 spec §5 的任务顺序做。每个任务做完立即跑它写明的验证命令；失败就修到通过，不跳过、不注释掉测试。
5. 测试、构建、diff 这类长输出重定向到文件，只看尾部与退出码。
6. 遇到 spec §10「停下来问」列出的情形，停下来问；遇到 spec 没写到的实现细节，按最小改动原则自行决定，记进台账的「Rulings I made」。
7. 做完 §4 的完成标准，写台账，合并，打 tag。

## 6. 风险与回滚

| 风险 | 对策 |
|---|---|
| runtime 拆分引入回归（M65） | M65 只搬代码、不改行为；v2 的 `tests/agent/` 全部保持通过；`legacy_chat` 的录制回放先由 16 场景行为对齐 golden（`tests/agent/harness/test_harness_parity.py`）承担，M68 再迁成评测用例 |
| 迁移出错丢数据 | 启动迁移前 v2 已有 `VACUUM INTO` 备份（保留 5 份）；每条迁移有升级与降级测试 |
| 多代理并发烧钱 | `worker.max_concurrent`、预算三级上限、成本页（M67、M68） |
| 主动工作扰民或误操作 | 默认 observe；推断委托风险上限 none；注意力纪律写进共用提示词（M70） |
| IM 通道泄露确认能力 | 一次性码绑定身份；破坏类确认默认只能在 Web 批准（M85） |
| 设备争用 | 租约硬互斥 + 队列领取闸门 + 人工抢占（M71） |
| 后期 spec 与代码漂移 | 每份 spec 的前置检查列出它依赖的名字；不符合就停下来校准 spec |

回滚：每个里程碑是一次 `--no-ff` 合并，可以整体 `git revert -m 1 <merge>`；带迁移的里程碑回滚时先执行降级（`alembic downgrade <上一 revision>`），降级不可逆的迁移在 spec 里写明。
