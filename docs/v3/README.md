# MAA-API v3：SuperAgent 改造方案

> 状态：**v3 路线（M63–M86）已全部完成（2026-11-09）**；P1 基础、P2 能力层、P3 主动性/后台与 P4 的界面导航图都已合入 dev 并打 `v3-m63` … `v3-m86` tag。
> v2（M0–M62）的方案、记录与现行系统文档在 [../v2/](../v2/README.md)，自 M64 起冻结只读。

v3 把 MAA-API 从「带一个对话式 Agent 的自动化服务」改成「以 Agent 为主」的服务：用户面对的是一个常驻的**总控**，总控把工作拆成**工单**交给隔离的 **Worker** 去做，Worker 内部跑一套带中间件、压缩、技能与记忆的运行时；设备同一时刻只归一个代理用，所有消耗类与破坏类操作仍然逐次确认。

外层拓扑参照 DeepSeek Harness 团队的 Super-agent 设计（Router/Worker 双层、事件驱动、面向人的交互、计算与状态分离、Watchdog），Worker 内部参照字节 DeerFlow 2.0 的 SuperAgent harness（中间件链、摘要压缩、Skills、记忆、子代理）。两者的区别与取舍见 [01 §3](./01-总览与范围.md)。

## 决策速查表

下表是 v3 的单一事实来源。其他 v3 文档与本表冲突时以本表为准；实施中的偏离记在 [13 §8](./13-决策记录.md)，本表受影响的条目同步加注。

### 方向与范围

| 项 | 决策 |
|---|---|
| 主线 | MAA-API 升级为 Agent 大脑；10-30 的 Android 单机 App 讨论稿暂缓，执行后端保留抽象，以后 Android 作为客户端或远程执行端接入 |
| 架构理念 | 混合：外层 DeepSeek Super-agent（总控 + Worker、事件驱动、注意力纪律、Watchdog），Worker 内部 DeerFlow 式内核（中间件链、摘要压缩、Skills、记忆、子代理） |
| 实现路线 | Python 自研，在现有 runtime 上重构，不引入 LLM 框架（LangGraph、DeerFlow、DSH 都不作依赖） |
| 产品形态 | 两步走：P1 先做 Agent 优先的指挥台，P3 起做自主运营 |
| 节奏 | 开 v3，在 `dev` 上分阶段推进，Agent 层允许破坏性重写；v2 会话数据保留在库里，只读查看器与 4 个只读端点已删除（2026-11-09，见 [13 §8.175](./13-决策记录.md)）；阶段顺序 P0 到 P5 不调整 |
| 设备与账号 | 继续单账号、单设备、单内核（多账号多设备不做） |
| 不做的功能 | 多账号多设备、截图视觉缓存、多 Provider 原生适配、MCP Server（维持 M12 决定）、A2A、权限模式、演练模式 |

### 总控、工单与 Worker

| 项 | 决策 |
|---|---|
| 总控 | 一个常驻、连续的总控会话，跨 Web 与 IM 共用上下文；用轻模型；不碰设备 |
| 总控的工具 | 只读速查（状态、队列、设备、知识、账号摘要）+ 工单工具 + `ask_user` + 免确认的 `stop_pipeline`；动设备、多步骤、要查资料的一律建工单 |
| 工单 | 一份授权工作，带一份不可变的**委托**（来源、范围、显式/推断、风险上限）；扩大范围必须新开工单 |
| Worker | 每个工单一个、相互隔离、用强模型；由代理定义（AgentSpec）声明提示词、工具、模型、风险上限 |
| 汇报 | Worker 每轮以 `report` 收尾：progress / waiting / ready / blocked / failed / dropped；只有 waiting、ready、blocked、failed 转给总控 |
| 用户介入 | 用户可以在工单里直接给 Worker 发消息，消息直通该 Worker，总控收到摘要 |
| 子代理 | Worker 可以委派子代理（情报、导航、验证、侦察）；只读子代理可并行；深度上限 2；推翻 M48 的「只读、深度 1」 |
| 设备租约 | 每台设备容量 1 的硬互斥；写设备的工具必须持有租约；人工操作（前端手动提交、REST 原子操作、停止）可以抢占 |
| 确认冒泡 | 子代理与 Worker 发起的确认、提问冒泡到总控会话与全局确认面板，标明来自哪个工单、哪个代理；确认分级与审计口径不变 |

### 运行时与模型

| 项 | 决策 |
|---|---|
| 代理定义 | `maa_api/agent/specs/builtin/*.md`，YAML frontmatter + 正文提示词；运行记录 spec 版本哈希 |
| 运行树 | 新表 `agent_run`；会话锁、中断状态、心跳落库；服务重启后未完成的运行标为中断并附恢复提示 |
| 中间件 | 统一的 before_model / after_model / wrap_tool 接口，顺序见 05 §5；v2 的特判（提问、卡死检测、确认）都改成中间件 |
| 模型配置 | 按角色（总控、Worker、子代理、摘要、标题、事件研判、记忆、视觉、embedding）选模型档案；档案存表，默认档案仍是现有 `llm.*` |
| 结构化输出 | 汇报、计划、记忆抽取、研判结果都用 JSON Schema 约束并本地校验，失败重试一次 |
| 成本 | 逐次调用记成本账本，拆出缓存命中；会话、单次运行、每日三级预算与告警 |
| 前缀缓存 | 系统提示与工具声明保持稳定，状态快照与时间放到最后；每个代理的工具集固定 |
| 步数上限 | 总控与 Worker 仍不设步数上限（沿用 v2 §8.16）；子代理设上限 |

### 上下文、知识与记忆

| 项 | 决策 |
|---|---|
| 预算口径 | 按 token 和模型窗口计算（替代 40 万有效字符常量），token 用校准过的估算，不引入 tokenizer 依赖 |
| 摘要压缩 | 达到窗口的 75% 自动压缩，`/compact` 手动压缩；检查点落库；压缩前确定性保存工单、委托、计划、已加载技能 |
| 工具结果清理 | 可重新获取的旧工具结果换成占位，保留调用记录 |
| RAG | SQLite FTS5（trigram 分词）+ 向量（BLOB + numpy 余弦）+ RRF 融合；embedding 远端与本地 ONNX 都支持、设置里切换，没有向量时退回全文检索；推翻 docs/v2/11 §6.7 |
| 语料 | 内置与用户知识、MAA 官方文档、PRTS 页面（运行时抓取，只存本地，不进仓库）、拆包数据、作业站作业、历史工单与故障 |
| Skills | `SKILL.md` 渐进披露：常驻只放名字和描述，用到才加载正文并激活工具子集；playbook 类知识条目迁成技能 |
| 长期记忆 | 语义、情景、程序三类；会后抽取，用户确认后入库，按预算注入 |

### 主动性、通道与安全

| 项 | 决策 |
|---|---|
| 事件 | 流水线、内核、设备、定时、系统事件与 IM 消息统一进事件表；先规则准入，再由便宜模型研判 |
| 主动工作 | 每条事件规则 off / observe / auto 三档，默认 observe（只记录「本来会做什么」）；v2 的失败自动诊断迁成一条默认 auto 的内置规则 |
| 推断委托 | 主动建的工单风险上限为「无需确认」，需要消耗或破坏时只能请用户另起显式工单 |
| Watchdog | 主系统之外的定时巡检；先只记录，验证可靠后开启有限自愈 |
| IM 通道 | 首批飞书、QQ 官方机器人、钉钉、Telegram；一次性码绑定身份；破坏类确认默认只能在 Web 端批准 |
| 沙箱 | 可插拔：macOS 默认 Seatbelt 受限子进程，可切 Docker；任何情况下都不开放 `adb shell` |
| 注意力纪律 | 接单确认一次，执行中安静，只在有结果、要决策、做不完时开口；一次只问一个结构化问题；指挥台只列需要人处理的事 |

## 给执行者的约定

- **一次只做一个里程碑**，只做该 spec 列出的事。spec 的「停下来问」一节列出的情形出现时，停下来问，不要自己发挥。
- **先跑 spec 的前置检查**。前置检查失败说明前面的里程碑没按 spec 落地，或者 spec 已经过时，两种情况都先报告。
- **名字以契约为准**：表名、列名、端点、事件名、错误码、配置键、工具名、模块路径以 02–05 为准；spec 与 02–05 冲突时以 02–05 为准，并在台账里记下冲突。
- **v2 文档只读**。代码注释与测试里形如 `docs/13 §8.x`、`docs/05 §6` 的引用，指的是 `docs/v2/` 下同名文件。
- **偏离要记录**：实现与 spec 不一致时，在同一任务内更新受影响的 v3 文档，并在 [13 §8](./13-决策记录.md) 补一条。
- **术语**：界面与文档遵守 [文案规范](../copy-audit/规范-文案规范.md)；v3 新术语见 [01 §8](./01-总览与范围.md)。
