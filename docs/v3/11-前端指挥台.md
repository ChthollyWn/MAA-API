# 11 前端指挥台

本文定义 v3 前端：信息架构与路由、指挥台首页、工单页、收件箱事件卡片、SSE v3 与 WebSocket 的消费、各管理页、移动端布局与文案要点。v2 的设计系统、页面框架、移动优先规范、WebSocket 客户端与鉴权处理全部沿用（[v2/09 §6、§8–§10](../v2/09-前端重构方案.md)），本文只写 v3 新增与改动的部分。

组件文件、props、query key 与测试用例名写在各里程碑的 spec 里：指挥台、工单页与代理定义页见 [M72](./specs/m72-console-frontend.md)，产物与生成式 UI 见 [M90](./specs/todo/m90-artifacts-genui.md)（TODO），语音见 [M97](./specs/todo/m97-persona-voice.md)（TODO）。端点、事件与字段名以 [04](./04-接口与事件协议.md) 为准。

## 1. 原则

1. **注意力纪律落在界面上**。指挥台只列需要人处理的事：等你确认、等你回答、等你批准的计划、卡住或在等你的工单、待审核的记忆与观察记录、严重的 Watchdog 告警。设备、内核、队列这类健康状态不占指挥台的位置，移到「更多 › 运行状态」；它们出了问题由 Watchdog（M83）告警进「待你处理」。
2. **一个连续的总控会话**。没有会话列表，也没有「新建会话」。指挥台上只有一个总控会话，Web 与 IM（M85）说的话都进它；「重新开始」把当前会话归档，归档的会话留在库里，不再有查看入口（旧会话只读查看器已于 2026-11-09 删除，见 [13 §8.175](./13-决策记录.md)）。
3. **工单是工作单元**。用户想看某件事办得怎样，就去这件事的工单：汇报、Worker 的消息、子代理的过程、每一轮的运行都在工单页里。工单页里发的消息直通该 Worker。
4. **复用 v2 组件**。确认卡 `ConfirmationCard`、提问卡 `QuestionCard`、工具条 `ToolCallBar`、媒体卡 `MediaCards`、输入栏 `Composer`、Markdown 渲染、消息分页窗口（`features/agent/messages.ts`）、滚动跟随（`use-conversation-scroll.ts`）都沿用。实时副本与历史去重的做法沿用 v2 M59 的思路，判据从「消息 id 边界」换成「运行 id」（§6.2）。
5. **只读优先的管理页**。代理定义、运行追踪、成本、Watchdog 告警这类页面以查看为主；能改的（技能、事件规则、IM 通道绑定、MCP、Hooks、工作流）都在各自页面里显式保存，改动经后端校验。
6. **移动优先**。375px 宽单列可用；桌面（≥ 1024px）多一列侧栏。所有贴底元素沿用 `--nav-offset`、`--keyboard-inset`、`--nav-safe` 三个变量（v2/09 §8.1）。

## 3. 指挥台首页 `/`

### 3.1 三块与布局

指挥台由三块组成：

| 块 | 内容 | 桌面（≥ 1024px） | 手机 |
|---|---|---|---|
| 待你处理 | 需要人处理的事，§3.2 | 右侧栏上部，直接渲染卡片 | 标题栏下吸顶的一行「N 件事等你处理」，点开是底部面板；没有待处理时整行不出现 |
| 总控会话 | 总控的消息流与输入栏，§3.3 | 左侧主列，消息区自己滚动，输入栏在卡片底部 | 整页滚动，输入栏贴在 Tab 栏上方 |
| 进行中的工单 | `status=open` 的工单，§3.4 | 右侧栏下部 | 「待你处理」那一行下面一条横向滚动的胶囊；没有进行中的工单时不出现 |

标题栏不显示「N 项待确认」胶囊（`hideConfirmationEntry`），因为「待你处理」已经列出全部确认。标题栏的操作菜单「指挥台操作」有两项：重新开始会话、运行状态。

### 3.2 待你处理

数据来源组合如下。每个来源一个查询，合并、去重、排序由纯函数 `buildAttentionItems` 完成（M72 建立，后续里程碑往里加来源）。

| 来源 | 接口 | 进入条件 | 呈现 | 里程碑 |
|---|---|---|---|---|
| 确认 | `GET /api/confirmations?status=pending`（与全局待确认面板共用 `pendingConfirmationsQuery` 的缓存） | 全部待确认 | 来源行 + `ConfirmationCard` | M72 |
| 提问 | `GET /api/agent/questions?status=pending` | 全部待答 | 来源行 + `QuestionCard` | M72 |
| 工单 | `GET /api/agent/tickets?status=waiting&status=blocked` | 它的 `human_action` 指向的确认或提问不在上面两类里，且它不是任何已列确认、提问的来源工单 | 工单卡：标题、状态、`human_action.prompt`、「打开工单」 | M72 |
| 计划待批准 | 经工单：Worker 出计划后汇报 waiting，`human_action.type=decision`，`ref_id` 指向一份 `awaiting_approval` 的计划 | 计划的 id 等于工单 `human_action.ref_id` | 计划卡：标题、步骤，就地「批准计划」「退回计划」；同一工单不再出工单卡 | M75、计划批准补丁 |
| Watchdog 告警 | `GET /api/agent/watchdog/alerts`，只取未解决且 `severity=critical` 的 | 全部 | 告警卡：消息、对象、时间、「标记已处理」 | M83 |
| 记忆提议 | `GET /api/agent/memories?status=proposed` | 至少 1 条 | 汇总成一行「N 条记忆待审核」，点开去 `/more/memories?status=proposed` | M79 |
| 观察记录 | `GET /api/agent/observations?reviewed=false` | 至少 1 条 | 汇总成一行「N 条观察记录待审阅」，点开去 `/more/triggers`（待审阅分页签） | M81 |

排序：确认（按过期时间升序）→ 提问（按过期时间升序）→ Watchdog 告警（按时间降序）→ 受阻工单 → 计划待批准 → 等你处理的工单（都按更新时间降序）→ 记忆汇总行 → 观察记录汇总行。

来源行写明谁在等：有 `origin.ticket_id` 时是「来自工单「标题」· 代理中文名」，代理中文名取自 `GET /api/agent/specs` 的 `title`；没有 origin 时按调用方写「来自 REST 调用」或「来自后台运行」。计划卡的来源行写法相同，代理名取工单 `kind` 对应的定义 `title`。来源行里的工单标题可点，打开该工单；计划卡另带「打开工单」。

几条边界：

- 总控会话的实时副本里正挂着的确认卡、提问卡，不在「待你处理」里重复出现（按 id 排除）。
- 全局待确认面板 `ConfirmationDock` 与标题栏胶囊仍只算确认，口径与 v2/09 §6.6 相同；提问进「待你处理」，不进全局面板。
- 计划待批准以计划卡代替同一工单的工单卡；计划刚批准或退回、Worker 还没汇报清 `human_action` 时，该工单暂不出工单卡，避免出现一张点了就 409 的死卡。计划读取失败（详情里没有 Worker 会话、计划接口报错或计划为空）时回落到工单卡。
- 处理掉一张卡后它立刻从列表消失：确认靠 `confirm_resolved` 与本地失效，提问靠 `question_resolved` 与本地摘除缓存（沿用 v2 的 `resolveQuestion` 做法）；计划卡靠审批响应写回计划缓存与工单失效。审批失败时列表顶部显示「处理计划失败：原因」；计划已不在待批准（409）时计划卡消失，其他失败保留卡片可重试，手机上面板在错误清除前不自动收起。

### 3.3 总控会话

消息来自 `GET /api/agent/orchestrator/messages`，分页读取方式与 v2 消息窗口相同（先读第一页拿 `total`，再读最后一页，「加载更早的消息」向前翻）。总控会话本身来自 `GET /api/agent/orchestrator`（10 秒轮询，另由 WS 失效），它给出 `session_id` 与 `turn_running`。

消息的渲染：

| 消息 | 渲染 |
|---|---|
| `role=user` 且 `inbox_id` 为空（或 `inbox_kind=user_message`） | 用户气泡；正文末尾的【引用】段（§7.2）拆出来，折叠成「引用 N 项」 |
| `role=user` 且 `inbox_id` 非空 | 事件卡片（§5） |
| `role=assistant` | Markdown 正文；`tool_calls` 拆成工具条 |
| `role=tool` | 并进对应的工具条，媒体卡渲染在工具条外（v2 M23 口径） |
| `create_ticket`、`send_to_ticket`、`get_ticket`、`cancel_ticket` 的结果 | 工具条下方多一个工单胶囊「工单「标题」」，点开工单页 |

发送走 `POST /api/agent/orchestrator/messages`，返回 SSE v3 流（§6.1）。总控忙的时候也能发：本地已有一条流在读时，第二条消息只提交、不读流，作为「排队中」的气泡显示，等它进了历史再消失；回复经 WS 失效刷新出来。输入栏的发送按钮在「有一轮在跑且草稿为空」时变成「停止本轮」（`POST /api/agent/orchestrator/interrupt`），有草稿时仍是发送。

状态行（输入栏上方）的优先级：正在停止本轮 > 本地这一轮在跑（等确认 > 等回答 > 总控正在处理）> 本轮已停止 > 总控正在处理收到的消息（`turn_running` 为真但本地没有流）。

重新开始：`POST /api/agent/orchestrator/reset`，先弹确认框；409 `RUN_ALREADY_ACTIVE` 时就地提示先停止本轮。历史为空时显示三条快捷开场（「把日常做了」「设备连上了吗」「上次那条流水线为什么失败」），点选只填进输入栏，不直接发送。

### 3.4 进行中的工单

`GET /api/agent/tickets?status=open&page=1&size=20`。每行：状态点、标题、Worker 的中文名、最近一次汇报的摘要（一行截断）；持有设备租约的那一行多一个「占用设备」徽章（比对 `GET /api/agent/device-lease` 的 `lease.ticket_id`）。底部「全部工单」去 `/tickets`。等你处理与受阻的工单只出现在「待你处理」里，不在这一块重复。

## 4. 工单

### 4.1 工单列表 `/tickets`

吸顶工具条是分段控件「进行中 / 已结束 / 全部」，分别对应 `status=open,waiting,blocked`、`status=done,failed,cancelled` 与不传；选择写进 `?status=`。列表 `GET /api/agent/tickets`，每页 20 条，按 `total` 判断「加载更多」（v2 历史列表的口径）。每行：状态徽章、标题、Worker 中文名、来源（你发起、事件、目标、Watchdog、系统）、最近汇报摘要（两行截断）、更新时间。

### 4.2 工单详情 `/tickets/:ticketId`

数据：`GET /api/agent/tickets/{ticket_id}`（`TicketDetail`，10 秒轮询，WS 失效）、`GET /api/agent/tickets/{ticket_id}/messages?include_subagents=true`、`GET /api/agent/tickets/{ticket_id}/reports`、`GET /api/agent/runs?ticket_id=…&root_only=true`、`GET /api/agent/device-lease`。

| 部分 | 内容 | 里程碑 |
|---|---|---|
| 概要卡 | 状态、Worker 中文名、来源、创建与更新时间、最近汇报摘要；waiting 或 blocked 时突出 `human_action.prompt`，类型为 confirmation、question 的就地渲染对应的确认卡、提问卡 | M72 |
| 委托 | 范围原文、强度（你明确要求的、系统推断的）、风险上限、发起方、时间；默认折叠 | M72 |
| 租约指示 | 本工单持有设备时显示「正在使用设备」、用途与剩余时间，带「释放设备」（`DELETE /api/agent/device-lease`，先确认）；设备被别的工单占用时显示「设备正被工单「标题」使用」；都没有时不显示 | M72 |
| Worker 消息 | 渲染规则同 §3.3；`delegate` 工具条下嵌套子代理的过程（§4.3） | M72 |
| 发消息 | `POST /api/agent/tickets/{ticket_id}/messages`，SSE v3；工单已结束时输入栏换成提示「工单已结束，不能再发消息」 | M72 |
| 汇报时间线 | 新的在上：状态、摘要、需要你做的事、`details` 里的流水线 id 链到流水线详情；分页「加载更多」 | M72 |
| 活动树 | 根运行列表，展开读 `GET /api/agent/runs/{run_id}` 的 children 树（深度 ≤ 3）：代理、种类、状态、终止原因、步数、token（含缓存命中）、成本、时长；每个节点链到 `/more/runs/:runId` | M72 |
| 计划面板 | 当前计划与待办（`GET /api/agent/sessions/{worker_session_id}/plan`），待批准时显示「批准计划」「驳回」（`approve_plan`）；SSE `plan_updated` 与 WS `plan_updated` 更新它。指挥台「待你处理」是计划批准的主入口，本面板保留为状态展示与第二入口 | M75、计划批准补丁 |
| 产物 | 工单里生成的产物链接；`create_view` 的视图卡就地渲染（M90） | M75、M90 |
| 团队消息 | 代理团队的消息（`list_team_messages`） | M96 |

操作菜单：停止本轮（`interrupt_ticket`）、取消工单（`cancel_ticket`，先确认）、查看运行追踪（`/more/runs?ticket_id=`）。已结束的工单只留最后一项。

桌面两列：左列 Worker 消息与输入栏，右侧栏依次是概要卡、租约指示、汇报时间线、活动树、委托（M75 起计划面板插在概要卡之后）。手机上标题栏下吸顶状态行（状态徽章与租约指示）和分段控件「消息 / 汇报 / 活动」：「消息」顶部是概要卡，下面是消息流，输入栏贴底；「汇报」是委托与汇报时间线；「活动」是活动树。

### 4.3 子代理嵌套

子代理的消息在它自己的会话里，`include_subagents=true` 时随工单消息一起返回，`session_id` 不等于 Worker 会话。前端按 `run_id` 把它们分组，挂到 `result.run_id` 等于该组的 `delegate` 工具条下面，折叠成「子代理过程（情报员，N 条消息）」。实时流里，`subagent_start` 按（父运行、代理名、任务原文）匹配同一运行里第一条还没配对的 `delegate` 调用，之后带该子运行 `run_id` 的事件都画在这条工具条下面；`delegate` 的结果回来时以结果里的 `run_id` 为准重新配对。配不上的子运行画在父运行末尾。

## 5. 收件箱消息与事件卡片

### 6.2 实时副本与历史去重

本轮实时副本在屏时，历史里同一批内容要让位，否则任何一次历史刷新都会让本轮显示两遍。v3 的判据：

- 看到了 `run_start` 的运行（完整观察），历史里它产生的非用户消息全部隐藏。
- 接入时已在进行、没看到 `run_start` 的运行（部分观察），只隐藏 id 大于发送时历史最后一条消息 id 的非用户消息。
- 用户消息从不按运行隐藏。本地先画一个乐观气泡，历史里出现「id 更大、`role=user`、不是收件箱消息、去掉【引用】段后正文相同」的消息时，乐观气泡消失。
- 流结束后先失效并等待历史重读完成，再丢弃实时副本；还挂着确认卡或提问卡的一轮保留到卡片处理完（v2 M59 口径）。
- 工单页换工单时，旧工单的实时副本立即丢弃（layout effect，绘制前清掉）。

## 10. 移动端布局

- 指挥台：标题栏「指挥台」；吸顶工具条从上到下是「待你处理」汇总行与进行中工单的胶囊条，两者为空时都不渲染，工具条高度随之归零。消息区跟随整页滚动，「回到底部」浮在输入栏上方（v2 口径）。输入栏 `docked`，贴在 Tab 栏上方，键盘弹出时 Tab 栏隐藏、输入栏贴键盘（v2/09 §8.4）。命令面板与提及面板从输入栏上方升起，最高 50dvh，内部滚动。
