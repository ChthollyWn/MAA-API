# v3 规格（spec）

每个里程碑一份 spec，文件名 `mNN-<英文短名>.md`。spec 写到「能力一般的执行者照着做就能完成」的粒度：路径、类名、函数签名、表结构、端点、事件、配置键、测试用例名、验证命令都写死，不写「适当」「等」「视情况」。

清单与依赖见 [12 §2](../12-实施路线与里程碑.md)；共享名字以 [02](../02-系统架构.md)–[05](../05-运行时与代理定义.md) 为准。M63–M90 的 spec 在本目录。M91–M98 在 [todo/](./todo/README.md)，先搁置。

## 1. 给执行者的规则

1. 一次只做一个里程碑，只做本 spec 写到的事。执行队列是 M63–M90。`todo/` 里只剩 M91–M98，标了 TODO，不要开工。
2. 开工前跑 §0 前置检查；任何一条不符合预期，停下来报告。
3. 按 §5 的任务顺序做，每个任务做完立即跑它的验证命令，失败修到通过；不跳过、不删测试、不加 `skip`。
4. 名字以 02–05 为准；spec 与 02–05 冲突时以 02–05 为准，在台账里记下冲突。
5. 不新增 spec 没写的依赖、表、端点、错误码、配置键、工具。确实需要时停下来问。
6. 不改 `docs/v2/` 下的文件（M63 的路径任务除外）。
7. 长输出重定向到文件，只看尾部与退出码，例如 `.venv/bin/python -m pytest -q > /tmp/pytest.log 2>&1; echo $?; tail -n 30 /tmp/pytest.log`。
8. `python` 不在 PATH，一律用 `.venv/bin/python`；macOS 没有 `timeout` 命令（docs/ENVIRONMENT.md）。
9. 遇到 §10「停下来问」的情形就停；spec 没写到的实现细节按最小改动自行决定，写进台账的「Rulings I made」。
10. 完成标准见 [12 §4](../12-实施路线与里程碑.md)。

## 4. 设计
### 4.1 数据模型
表与列（引用 03 的小节，并给出 SQLModel 类的完整代码）；迁移文件名与 upgrade/downgrade 的完整步骤；数据迁移的 SQL。
### 4.2 模块与文件
每个新建或修改的文件：路径、职责、类与函数签名（Python 代码块，带类型标注与 docstring 要点）。
### 4.3 接口
端点（方法、路径、函数名、请求与响应模型的完整字段、状态码、错误码）；SSE/WS 事件的完整 payload 示例（JSON）。
### 4.4 配置项
键、类型、默认、范围、分组、是否 config-only、`_FIELDS` 元数据、`config.template.yaml` 片段。
### 4.5 行为与算法
伪代码、状态机、并发与边界情况（每条边界情况写「输入 → 期望行为」）。
### 4.6 前端
路由、组件文件、状态、请求与 query key、界面文案（遵守文案规范）。没有前端改动写「无」。
### 4.7 提示词与代理定义
新增或修改的代理定义全文（frontmatter + 正文），或写「无」。

## 3. 写 spec 的规则（给写作者）

- 每个任务的工作量控制在一个执行者一到两小时内；任务之间写范围尽量不重叠。
- 引用既有代码写「路径 + 符号名 + 约行号」，例如 `maa_api/agent/runtime.py` 的 `AgentRuntime._run_turn_body`（约 1250 行）；行号会漂移，符号名用来 `rg` 定位。
- 新代码给出完整签名；关键逻辑给伪代码；不把整段实现写进 spec。
- 测试写到用例名与断言要点；用 v2 的测试设施：同步函数里 `asyncio.run(...)`（不装 pytest-asyncio）、`tests/fakes/fake_llm.py` 的 `FakeLLM`、`tests/api/conftest.py` 的 `make_client` 等。
- 每条命令都能直接复制执行；写出期望输出（或期望退出码）。
- 用到 02–05 没有的名字时，在 spec 末尾加一节「需要补进契约的名字」，列出名字与用途，由主 agent 合并进 02–05；不要直接改 02–05。
- 文案遵守 [文案规范](../../copy-audit/规范-文案规范.md)：不用破折号当冒号、不用营销词与客服腔、不用感叹号与 emoji。
