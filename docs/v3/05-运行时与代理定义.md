# 05 运行时与代理定义

本文定义代理定义（AgentSpec）的格式、内置代理名单、AgentLoop 的契约、中间件接口与顺序、工具定义的扩展字段、汇报与委派契约。代码位置见 [02 §4](./02-系统架构.md)。

## 1. 代理定义（AgentSpec）

### 1.1 文件格式

内置代理定义放在 `maa_api/agent/specs/builtin/<name>.md`：YAML frontmatter + 正文。正文就是该代理的系统提示词（祈使句，写「什么时候做什么」，不写参数形状，遵守文案规范 §七）。

```markdown
---
name: daily_ops
title: 执行官
kind: worker
description: 提交并盯住流水线：日常、刷图、基建、公招这类内核任务。
model_role: worker
tools: [get_system_status, submit_pipeline, wait_pipeline, get_pipeline, report, delegate]
deferred_groups: []
device: exclusive
risk_ceiling: consume
max_steps: 0
delegates: [navigator, verifier]
verify_before_ready: true
skills: []
output_schema: null
budget: {max_cost_per_run: 0}
version: 1
---
你负责……（提示词正文）
```

### 1.2 字段

| 字段 | 类型 | 必填 | 规则 |
|---|---|---|---|
| `name` | str | 是 | `^[a-z][a-z0-9_]{1,31}$`，与文件名一致，全局唯一 |
| `title` | str | 是 | 中文短名，≤ 8 字，界面与汇报里显示 |
| `kind` | enum | 是 | `orchestrator`、`worker`、`subagent`、`background` |
| `description` | str | 是 | ≤ 120 字；总控据此挑选 Worker 种类，子代理据此被委派 |
| `model_role` | enum | 是 | `ModelRole` 之一（03 §13） |
| `tools` | list[str] | 是 | 精确工具名；加载时逐个校验存在于 `ToolRegistry`，不存在就启动失败 |
| `deferred_groups` | list[str] | 否 | 按需开启的工具组（v2 M57 机制）；只有 `legacy_chat` 与 `general` 用 |
| `device` | enum | 是 | `none`、`read`、`exclusive`：该代理可用的最高设备级别；工具的 `device` 高于它就不进工具集 |
| `risk_ceiling` | enum | 是 | `none`、`consume`、`destructive`：本代理能发起的最高风险；与委托的上限取较低者（09 §2） |
| `max_steps` | int | 是 | 0 表示不设上限；`kind=subagent` 必须大于 0 |
| `delegates` | list[str] | 否 | 可委派的子代理名；只有 `kind=worker` 能有 |
| `verify_before_ready` | bool | 否 | 默认 false；只有 `kind=worker` 能为 true，其他种类写 true 时启动失败（M87）。true 表示 `report(status=ready)` 前先过完成闸门（§4.1） |
| `skills` | list[str] | 否 | 预加载的技能 id（M78 起生效） |
| `output_schema` | str? | 否 | 结构化输出的 schema 名（§8）；子代理与后台代理必填 |
| `budget.max_cost_per_run` | float | 否 | 0 表示沿用 `budget.per_run_cost_limit` |
| `version` | int | 是 | 人工递增，改提示词时 +1 |

加载规则（`AgentSpecRegistry.load()`，M65）：

- 启动时读 `builtin/*.md`，任何一条校验失败都抛异常、中止启动（内置定义坏了属于代码错误）。
- 版本哈希 `spec_version` = 文件字节的 sha256 前 12 位，写进每次运行的 `agent_run.spec_version`。
- 额外的一致性规则：`orchestrator` 种类至多一个（M70 起恰好一个），且 `device=none`；`subagent` 不能有 `delegates`；`delegates` 里的名字必须是 `kind=subagent` 的定义；`tools` 里不能出现 `device` 高于定义 `device` 的工具。
- M98 之前只有内置定义；M98 起可以在库里存覆盖版本（`agent_spec_version`）。

## 2. 运行时组成

```
AgentLoop(chain, transcript, call_model, tool_schemas, registry).run(ctx)
  ├─ 中间件链（§5）
  ├─ 模型调用：ModelRouter.client_for(spec.model_role)（M67 前沿用 v2 的 client_factory）
  ├─ 工具执行：toolexec.execute_batch → 每个调用经过 wrap_tool 链 → ConfirmationService.invoke
  └─ 事件：RunEventBus.emit(RunEvent) → SSE 流 / WS agent_run / Trace
```

spec、会话、运行 id 都在 `RunContext` 里；`AgentLoop` 只拿可替换的五个依赖（链、历史读写、模型调用、工具声明、工具注册表），M65 的 v2 门面与侦察各自传入自己的实现。

### 2.1 核心类型（`maa_api/agent/harness/context.py`）

| 类型 | 字段 |
|---|---|
| `RunContext` | `run_id`、`root_run_id`、`parent_run_id`、`session_id`、`ticket_id`、`spec: AgentSpec`、`caller=CallerType.INTERNAL`、`app`（取 `app.state` 服务）、`request`（兼容 v2 handler 用的 `ctx.request.app.state`；后台运行用一个只带 `app` 的替身）、`emit`、`cancel_event: asyncio.Event`、`state: dict`（中间件私有状态，键用中间件名前缀）、`steps: int`、`inbox_items: list`；M65 另加 `interrupted_now`（回调，转调门面的中断判定）、`allowed_tools`、`vision_enabled`、`parallel_tools`、`draft`、`pending_stop` 与 `stop_after_batch(reason, text)` |
| `ModelRequest` | `messages: list[dict]`（OpenAI 格式）、`tools: list[dict]`、`profile`（M67）、`response_format: dict \| None`、`estimated_tokens: int`、`meta: dict` |
| `ModelResponse` | `text`、`reasoning`、`usage: Usage`、`upstream_finish_reason`、`latency_ms`、`raw_tool_calls: list[dict]`（M65；`ToolCall` 由循环用 `parse_tool_call` 解析出来）、`model: str \| None`、`response_id: str \| None`（M68，供 `llm.chat` span 记响应信息） |
| `ToolCall` | `id`、`name`、`raw_arguments: str`、`arguments: dict \| None`（`execute_batch` 解析前是 `None`，因为 v2 先落 assistant 消息再解析参数） |
| `ToolOutcome` | `status`（`ok`、`error`、`awaiting`、`rejected`、`expired`、`skipped`）、`result: dict \| None`、`error: {code, message, details} \| None`、`audit_id`、`message_id`、`stop_run: bool`、`stop_reason: str \| None`、`stop_text: str \| None`、`content: str \| None`、`body()`（落库与事件用的响应体） |
| `RunOutcome` | `status`、`finish_reason`、`final_text`、`report_id`、`usage`；M66 之前 `status` 是字符串 |

### 2.2 AgentLoop 算法

```
run.start()                                     # 发起方调用 RunService.start；AgentLoop 不调用（M66）
for mw in chain: await mw.on_run_start(ctx)
while True:
    if ctx.cancel_event.is_set(): finish('interrupted')
    req = base_request(ctx)                     # 历史 + 系统提示 + 工具声明
    for mw in chain: req = await mw.before_model(ctx, req)
    resp = await model.stream(req, on_text=emit text_delta)
    for mw in reversed(chain): resp = await mw.after_model(ctx, resp)
    persist assistant message（含 tool_calls、reasoning）
    if not resp.tool_calls: finish(resp 终止原因或 'stop')
    outcomes = await toolexec.execute_batch(ctx, resp.tool_calls)   # 只读工具并发；含写工具则串行；遇 rejected 跳过余下调用
    persist tool messages（每个调用一条，配对不拆）
    stop = select_stop(outcomes, ctx.pending_stop)
    if stop is not None: finish(stop.reason)
    ctx.steps += 1
    if spec.max_steps and ctx.steps >= spec.max_steps: finish('max_steps')
for mw in reversed(chain): await mw.on_run_end(ctx, outcome)
run.finish(outcome)                             # 发起方调用 RunService.finish；AgentLoop 不调用（M66）
```

- `select_stop` 的优先级（M65 细化）：没答成的提问取最后一个 → 确认被拒或过期取第一个 → 其余 `stop_run` 按位置取第一个 → `ctx.stop_after_batch()` 预约的结束。
- 每一步从数据库重读历史（v2 做法），保证中断、回溯之后的一致性。
- 被中断时补齐未配对的 tool 桩消息（v2 `_TurnDraft` 的做法），再落一条 `finish_reason='interrupted'` 的助手消息。
- 模型调用失败的重试与错误映射沿用 v2 `OpenAICompatibleClient`（还没吐出 chunk 时最多重试 3 次，429 看 Retry-After）。

### 2.3 运行状态与终止原因

运行状态（`AgentRunStatus`）：`running` → `waiting_human`（等确认或提问）→ `running` → `succeeded` / `failed` / `interrupted` / `cancelled`。

`finish_reason` 取值（新运行）：

| 值 | 含义 | 运行状态 |
|---|---|---|
| `stop` | 模型给出最终回答 | succeeded |
| `report_submitted` | Worker 提交了汇报 | succeeded |
| `question_unanswered` | 提问被跳过或被收尾取消（提问没有超时） | succeeded |
| `confirmation_rejected` | 确认被拒 | succeeded |
| `confirmation_expired` | 确认超时 | succeeded |
| `stuck_loop` | 连续 3 批相同调用（v2 `STUCK_REPEAT_LIMIT=2`） | failed |
| `max_steps` | 达到定义的步数上限 | succeeded |
| `budget_exceeded` | 超出成本预算 | failed |
| `context_overflow` | 压缩后仍装不下 | failed |
| `interrupted` | 用户中断或 Watchdog 中断 | interrupted |
| `cancelled` | 工单被取消 | cancelled |
| `lease_preempted` | 设备被用户接管且本轮无法继续 | succeeded |
| `error` | 其他异常 | failed |
| `recovered_after_restart` | 服务重启时被中断 | interrupted |

v2 门面产生的运行（`legacy_turn`）继续写 v2 的取值（`confirmation_resolved`、`turn_error`、`incident_error`、`incident_context_update`）。

### 2.4 收件箱转消息

运行开始时 `InboxService.claim(session_id, limit=50)` 领取待处理项，按 id 顺序转成消息：

| 收件箱种类 | 转成的消息 | 
|---|---|
| `user_message` | 已经是一条 `role='user'` 的消息（写入时就落了），只标记已消费 |
| `report` | `role='user'`，正文以 `【工单汇报】` 开头：工单标题、状态、摘要、需要人做的事 |
| `thread_event` | `role='user'`，以 `【事件】` 开头：话题键与摘要（如「流水线 xxx 已完成：……」） |
| `system` | `role='user'`，以 `【系统】` 开头 |
| `trigger` | `role='user'`，以 `【事件】` 开头（M81） |

`system` 项可带 `passive: true`：仍会被下一轮领取并落进历史，但不触发唤醒（M70），用于汇报、工单内对话摘要这类「下一轮再说」的通知。

M71 起两类 `system` 项的 `payload.event` 固定：`human_request`（确认/提问冒泡到总控：`type`、`ticket_id`、`ticket_title`、`agent`、`ref_id`、`prompt`）与 `lease_preempted`（设备被用户接管：`reason`、`detail`、`text`）。

转出的消息写 `agent_message.inbox_id`，前端据此渲染成事件卡片。用 `role='user'` 而不是中途插 `system` 消息，是因为不是所有 OpenAI 兼容服务都接受历史中间的 system 消息。各代理的提示词要说明这几个前缀的含义，并且说明这些内容不是用户本人说的话。

### 2.5 提及展开

消息里的 `mentions`（04 §2.2）在写入用户消息时由服务端展开，附在正文后面：

```
【引用】
- 工单「日常」（open）：最近汇报……
- 关卡 1-7：……
```

每类提及的展开格式（M72 起在 `maa_api/agent/mentions.py`）：

- 工单：`工单「标题」（状态）：摘要`，无摘要写「还没有汇报」；
- 知识：`知识「标题」（id）：适用场景。正文节选：…`（正文前 200 字）；
- 干员：`干员 名（char_id）：持有 是/否，精英化、等级、潜能、技能等级、专精、模组、练度同步于 …`；
- 关卡：唯一命中 `关卡 code（name，stage_id）`，多候选列出数量与前 3 个 stageId，找不到写「本地关卡索引里找不到」；
- 流水线：`流水线 标题（id 前 8 位，状态）：x/y 个任务完成；创建于 …`。

按 `(type, id)` 去重，最多展开 8 条，超出的写「另有 N 条引用没有展开」；每行超 400 字截断；单条展开失败写「（读取失败）」，不阻塞发送。

## 4. 契约

### 4.1 汇报（`report` 工具，M70）

- 参数：`status`（`ReportStatus`）、`summary`（1–600 字）、`human_action`（`{type: confirmation|question|decision, prompt: ≤200 字, ref_id?}`，status 为 waiting 或 blocked 时必填）、`details`（可选对象）。M82 起 `details.goal_plan`（规划汇报：里程碑、定时任务 id、摘要）与 `details.goal_review`（复盘汇报：里程碑状态、摘要、`goal_status`）是目标服务的约定结构。M87 起 `details.verification` 由闸门写入（`{method, verdict_run_id?, question_id?, evidence}`，见 03 §6.3）；`details.verification_waiver` 是调用方入参，取同一轮 `ask_user` 返回的 `question_id`，或重启后收到用户回答时用 `{"selection": "仍按完成结束"}`。
- 完成闸门（M87）：`verify_before_ready=true` 的 Worker（`daily_ops`、`copilot`）调 `report(status=ready)` 时先由 `VerificationGate` 核对完成证据。不通过时不写 `ticket_report`、工单状态不变、本批不以 `report_submitted` 结束，运行继续；工具返回 `{accepted: false, reason, message, evidence, delegate}`，`delegate` 键总是存在（没有可委派时为 `null`），`reason` 取 `verification_required`、`verification_failed`、`verification_exhausted`、`waiver_invalid`。
- 确认载荷（M87）：工单会话里的 `grant_copilot_attempts` 确认 `payload` 多一个 `max_attempts`（int，1–10，等于当时的 `copilot_loop.max_iterations`）；没有工单的会话不带这个键。
- `report` 必须是一批工具调用的最后一个；AgentLoop 处理完这一批就以 `report_submitted` 结束本轮。被闸门拒绝的 `ready` 是例外：不结束运行、不写汇报，见上一条。
- 状态映射：progress→`open`、waiting→`waiting`、ready→`done`、blocked→`blocked`、failed→`failed`、dropped→`cancelled`。
- 转发：waiting、ready、blocked、failed 写进总控收件箱（`kind='report'`）；dropped 只在工单来源为 `user` 时转发；progress 不转发。
- Worker 一轮结束却没有调用 `report`：`ReportMiddleware` 在 `on_run_end` 自动补一条汇报。运行失败（error、stuck_loop、budget_exceeded、context_overflow）补 `blocked` 并转发总控，摘要「这一轮运行没有完成：{原因}。」；其余补 progress（不转发），摘要取最终回答的前 600 字（为空时写「本轮没有输出」）。

### 4.2 委派（`delegate` 工具，M70）

- 参数：`agent`（必须在调用者定义的 `delegates` 里，否则 `DELEGATION_NOT_ALLOWED`）、`task`（1–2000 字）、`context`（可选，≤ 4000 字，父代理认为子代理需要知道的事实）。
- 执行：新建 `agent_session(kind='subagent', parent_session_id=父会话, ticket_id=同一工单)` 与子运行（`parent_run_id=父运行`）；子代理只看到 `task` 与 `context`，看不到父会话历史。
- 输出：子代理以 `output_schema` 约束的 JSON 结束；`subagent_report` 的形状是 `{summary ≤1500 字, findings: [{title, detail, evidence: [str]}], uncertainties: [str], artifacts: [artifact_id]}`。解析失败重试一次，仍失败时把最后一段文本当 `summary`、其余为空，并标 `degraded=true`。
- 回传：返回值就是上面的 JSON 加 `run_id`、`steps_used`；子代理的消息只留在子会话里。
- 并行：同一批里的多个 `delegate`，被委派的代理 `device` 都不是 `exclusive` 时并发执行（上限 `delegation.max_parallel`），否则串行。
- 深度：子代理不能再委派；超过时 `DELEGATION_DEPTH_EXCEEDED`。
- 租约：子代理与父 Worker 共用工单的租约。

### 4.3 工单工具（总控用，M70）

| 工具 | 参数 | 作用 |
|---|---|---|
| `create_ticket` | `kind`（Worker 定义名）、`title`（≤ 64 字）、`brief`（给 Worker 的任务说明，≤ 4000 字）、`scope`（委托范围，≤ 2000 字） | 建工单与显式委托，写 Worker 收件箱；返回 ticket_id |
| `send_to_ticket` | `ticket_id`、`content` | 给进行中的工单补充说明 |
| `list_tickets` | `status?`、`limit≤20` | 列工单 |
| `get_ticket` | `ticket_id` | 工单详情与最近汇报 |
| `cancel_ticket` | `ticket_id`、`reason` | 取消工单：中断它的运行、结束订阅、释放租约 |

总控把用户原话的意图写进 `scope`；用户没说的风险（例如「可以用理智药」）不能写进 `scope`。

## 5. 中间件

### 5.1 接口（`maa_api/agent/harness/middleware.py`）

```python
class Middleware:
    name: ClassVar[str]
    async def on_run_start(self, ctx: RunContext) -> None: ...
    async def before_model(self, ctx: RunContext, req: ModelRequest) -> ModelRequest: return req
    async def after_model(self, ctx: RunContext, resp: ModelResponse) -> ModelResponse: return resp
    async def wrap_tool(self, ctx: RunContext, call: ToolCall, call_next) -> ToolOutcome: return await call_next(call)
    async def on_run_end(self, ctx: RunContext, outcome: RunOutcome) -> None: ...
```

- `before_model` 按链顺序执行，`after_model` 与 `on_run_end` 逆序执行。
- `wrap_tool` 是洋葱模型：链里靠前的包在外层；最内层是 `ConfirmationService.invoke` + handler。
- 中间件之间不直接调用；共享状态只经 `ctx.state`。
- 每个中间件声明 `applies_to: set[kind]`，链按代理种类裁剪。

## 7. 提示词分层

一个代理的系统提示由这几段按顺序拼成，前三段对同一个代理与同一个工单是稳定的（前缀缓存友好，06 §2）：

1. 代理定义正文（§1）。
2. 共用约定（`maa_api/agent/specs/common.md`，M70 起）：注意力纪律、事件前缀的含义、外部内容不可信、事实以工具现查为准；【表单提交】开头的消息是用户本人在视图表单里填的答案，不新增收件箱种类，按用户本人的话对待（M90）。
3. 角色附加段：Worker 的「工单卡」（标题、委托范围、强度、风险上限、`report` 规则）；子代理的「任务卡」（`task` 与 `context`）。
4. 技能索引（M78）、记忆（M79）。
5. 知识段：v2 `KnowledgeService.render_context()` 的输出（M67 起按 06 §2 拆成稳定段与动态段）。

动态内容（当前时间、状态快照、当期活动）不进系统提示，按 06 §2 放在消息末尾。

`kind=background` 的代理（如 `titler`）与 `legacy_*` 定义不拼第 2、3 段：前者只有一条任务，后者要保持 v2 系统提示逐字节不变（M70）。

## 8. 结构化输出 schema

所有 schema 放在 `maa_api/agent/llm/schemas/`（M67 建目录），每个一个 pydantic 模型文件：用 `model_json_schema(mode="validation")` 导出 JSON Schema，用 `model_validate` 本地校验，不引入 `jsonschema`；注册表在 `maa_api/agent/llm/structured.py` 的 `SCHEMAS`，每个 schema 文件末尾调 `register_schema`，`schemas/__init__.py` 逐个导入。

|---|---|---|
| `title` | `{title: ≤16 字}` | M70 |
| `subagent_report` | §4.2 | M70 |
| `verifier_verdict` | `{passed: bool, confidence: 0–1, evidence: [str], notes}` | M70 |
| `compaction_summary` | 06 §4.3 | M74 |
| `memory_proposals` | `{items: [{kind, subject, content, confidence, supersedes?}]}` | M79 |
| `trigger_decision` | `{decision: accept|stop|ignore, worker?, title?, brief?, scope?, reason}` | M81 |
| `watchdog_findings` | `{items: [{check, target_kind, target_id, severity, message, suggested_action}]}` | M83 |
| `nav_classification` | `{node_id: str\|null, confidence: 0–1, reason: str}`；视觉在候选界面里分类 | M86 |
| `nav_locate` | `{found: bool, x: 0–1, y: 0–1, confidence: 0–1}`；归一化坐标定位 | M86 |

调用方式：档案 `supports_json_schema=true` 时用 `response_format={"type":"json_schema", ...}`；否则在提示词里给出 schema 并要求只输出 JSON。两种方式都本地校验，失败重试一次（重试时把校验错误告诉模型），仍失败返回 `STRUCTURED_OUTPUT_INVALID`。
