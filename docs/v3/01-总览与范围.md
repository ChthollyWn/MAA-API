# 01 总览与范围

## 1. 背景

v2（M0–M62）交付了一个可用的单代理 Agent：84 个工具（模型可见 83）、风险分级与确认、会话级原子操作授权、`ask_user` 提问、中断、媒体卡片、全量审计、34 条内置知识、PRTS 与企鹅物流等外部检索、只读侦察子代理（M48）、失败自动诊断、三级丢弃式上下文裁剪。安全与工具这一侧已经是工程级的。

缺的是编排与上下文这一侧：

- 一个会话一个循环一个模型，`maa_api/agent/runtime.py` 约 3000 行，会话锁、中断状态、能力探查缓存都在进程内存里，服务一重启就丢。
- 上下文只靠丢弃控制，没有摘要压缩；预算按字符而不是 token 与模型窗口；带当前时间的状态摘要排在历史之前，每轮第一次请求都打不中前缀缓存。
- 知识库只有「索引注入 + 按 id 读全文」，没有检索；没有跨会话记忆。
- 子代理只有 M48 侦察一种，只读、深度 1、同步阻塞，过程不留痕；没有通用委派。
- 用户要自己管理会话；系统不会主动做事，只有失败诊断一条自动链路。
- 没有 trace、成本统计和评测集，模型行为的回归靠人工实机复盘。

## 2. 目标

v3 要做到 DeepSeek Super-agent 文章里的四个特征，并补齐工程级 harness：

| 特征 | 在 MAA-API 里的含义 | 主要承载 |
|---|---|---|
| 连续 | 用户感觉始终只有一个代理：Web、IM 里说的话进同一个总控会话；总控记得之前定下的事 | 总控会话、摘要压缩、长期记忆（M70、M74、M79、M85） |
| 高效 | 多件事并行推进，Worker 跑着也能接新指令；查资料、分析可以并行，设备操作排队 | 工单与 Worker、子代理并行、设备租约（M69–M71） |
| 主动 | 持续观察流水线、内核、设备、定时、活动等事件，值得处理时主动推进，不值得时保持安静 | 事件规则、observe/auto、目标、每日简报（M81–M84） |
| 持久 | 运行落库可恢复；卡住、跑偏、内核假死能被发现并处理 | 运行树、心跳、恢复、Watchdog（M66、M83） |

工程目标：

- 每个代理的提示词、工具、模型、风险上限由代理定义声明，可审阅、可版本化、可评测。
- 每次模型调用、工具调用、检索、确认都有 span；成本逐次入账并拆出缓存命中。
- 改提示词或换模型之前先跑离线评测，回归不降级。

## 3. 两种 SuperAgent 理念与取舍

| 维度 | DeepSeek Super-agent（2026-10-31） | DeerFlow 2.0 SuperAgent | v3 取用 |
|---|---|---|---|
| 要解决的问题 | 人的注意力是瓶颈，用户不该管理会话 | 单个代理怎么把长任务做完 | 两者都要：外层管多任务与打扰，内层管单任务质量 |
| 结构 | 常驻 Router（轻模型、不干活）+ 每个工单一个长期 Worker | Lead Agent 自己推理与执行，子代理是一次性 `task` 调用 | 总控 = Router；Worker = 工单；Worker 内部可以开一次性子代理 |
| 并发 | 多工单真并行，全双工 | 一轮内的子代理扇出 | 多工单并行 + Worker 内子代理扇出；设备操作用租约串行 |
| 触发 | 事件驱动，两级过滤，主动工作先 observe | 用户消息驱动 | 事件驱动，沿用 observe 默认 |
| 与人交互 | 确认一次、执行中安静、一次一问、面板只列待处理 | 常规对话 + Clarification 中间件 | 注意力纪律作为顶层原则；`ask_user` 承担一次一问 |
| 上下文 | Inline & Spill、按 ID 链式召回；不谈历史压缩 | 摘要压缩、记忆注入、技能按需加载、token 预算 | 两者合并：外置与续读 + 摘要压缩 + 记忆 + 技能 |
| 可靠性 | 计算/状态/环境分离、外部 Watchdog、发件箱 | LangGraph 检查点 | 状态全部落库、Watchdog、发件箱（M85） |
| 执行环境 | 环境留在原地，端侧只执行 | 沙箱（本地/Docker/K8s，含 bash） | 设备就是环境；代码沙箱只跑 Python，不开 shell 与 `adb shell` |
| 实现 | 研究原型，DSH（TypeScript 插件框架）的 bundle | Python，LangGraph + LangChain | 自研 Python，不引入框架 |

不采用的部分与理由：

- **Router 分片、跨 Source 身份映射、多机 BYOM、A2A**：单用户单设备的场景用不上。
- **DeerFlow 的 bash 子代理与宿主机命令**：与「不开放任意 `adb shell`」冲突。
- **以 DSH 或 DeerFlow 为大脑、MAA-API 退为工具服务**：确认、提问、中断、审计与运行时及前端 SSE 深度耦合，换框架等于重接一遍；本机加依赖也受阻。

## 5. 设计原则

1. **注意力纪律**。接单确认一次；执行中保持安静；只在有结果、需要决策或做不完时开口；一次只问一个结构化问题；指挥台只列需要人处理的事，健康状态不占位置。
2. **红线不变**。不开放任意 `adb shell`；消耗类与破坏类操作逐次确认，原子操作只走「会话 + 时间窗」授权；审计不降级；外部内容一律当不可信数据；上下文与委托都不等于确认。
3. **单设备硬互斥**。并行只用于不占设备的工作；动设备必须持有租约；人工操作可以抢占代理。
4. **状态外置**。工单、委托、计划、目标、确认、压缩摘要、记忆、产物都落库；模型上下文只放当前需要的部分。
5. **复用优先**。`ToolRegistry`、`PolicyEngine`、`ConfirmationService`、`QuestionService`、审计、外部数据源、`FakeLLM` 原样保留；`runtime.py` 拆分重构，不推倒重来。
6. **fail closed**。拿不到参数就按高风险处理；拿不到租约就报忙；结构化输出校验失败就重试一次再报错，不猜。
7. **每阶段可用**。每个里程碑结束时系统可以正常使用；破坏性改动只在 spec 明确写出的地方发生。

## 7. 非目标

- 不改 MaaCore 子进程架构、IPC 协议与任务队列语义（v2 docs/02、docs/03）。
- 不改流水线、定时任务、更新、账号数据、作业资源这些业务域的既有接口语义，除非某个 spec 明确写出。
- 不做多用户与权限体系：仍是单 token 鉴权。
- 不做云端部署形态；仍是本机单进程 + SQLite。

## 8. 术语表

文档、界面、提示词统一使用下表写法。v2 术语（内核、流水线、任务、定时任务、通道、客户端渠道、会话、确认等）继续遵守 [文案规范 §二](../copy-audit/规范-文案规范.md)。

| 概念 | 中文写法 | 代码名 | 说明 |
|---|---|---|---|
| Router | 总控 | `orchestrator` | 常驻的总控会话及其代理。代码不用 `router`，避免与 FastAPI 路由混淆 |
| Worker | Worker（执行代理） | `worker` | 一个工单对应的代理 |
| 子代理 | 子代理 | `subagent` | Worker 委派的一次性代理 |
| 后台代理 | 后台代理 | `background` | 没有用户会话的内部代理：事件研判、记忆整理、摘要、Watchdog |
| AgentSpec | 代理定义 | `AgentSpec` | 一个代理的提示词、工具、模型、风险上限 |
| Ticket | 工单 | `ticket` | 一份授权工作 |
| Mandate | 委托 | `mandate` | 工单的来源与授权范围，不可变。不要写成「授权」，「确认」另有所指 |
| Report | 汇报 | `report` | Worker 每轮结束时的状态与摘要 |
| Run | 运行 | `agent_run` | 一次代理调用（总控一轮、Worker 一轮、一次子代理、一次研判…） |
| Trigger | 事件 | `agent_trigger` | 进入系统的一条事件（消息、流水线结束、崩溃、定时…） |
| Thread | 话题 | `thread_key` | 一串相关事件的键，例如一条流水线、一个 IM 会话、一个工单 |
| Subscription | 订阅 | `thread_subscription` | 工单对话题的订阅；订阅话题的后续事件直通该 Worker |
| Source | 事件源 | `source` | 事件来自哪里：web、im_feishu、pipeline、core… |
| Lease | 设备租约 | `device_lease` | 设备的独占使用权，容量 1 |
| Observation | 观察记录 | `trigger_observation` | observe 模式下「本来会做什么」的记录 |
| Checkpoint | 压缩检查点 | `compaction_checkpoint` | 摘要压缩的结果 |
| Artifact | 产物 | `artifact` | 笔记、外置的大输出、报告、图表、表单 |
| Skill | 技能 | `skill` | 一份按需加载的做事方法 |
| Memory | 记忆 | `memory_item` | 跨会话保留的事实、经历、套路 |
| Goal | 目标 | `goal` | 长程目标，拆成里程碑执行 |
| IM channel | IM 通道 | `channel` | 双向的即时通讯接入。按文案规范，「渠道」只指客户端渠道 |
| Outbox | 发件箱 | `outbox` | 所有外发消息先入库再投递 |

## 9. v3 整体验收

- P1 结束：用户在指挥台与总控说话，总控建工单、Worker 执行、确认冒泡、汇报回到总控；服务重启后能恢复；v2 的全部业务能力不回退。M73 起失败诊断也走工单（`diagnose`），不再起 v2 诊断会话。
- P2 结束：长会话靠压缩维持在窗口内；知识检索带出处；技能与记忆生效。
- P3 结束：失败诊断、每日简报等主动工作按规则运行；IM 里能对话与批准确认；Watchdog 能发现卡死。
- P4、P5 结束：各功能按各自 spec 的验收标准通过。
- 全程：后端测试、OpenAPI 快照、前端门禁、相关冒烟全部通过；评测集通过率不低于上一个里程碑的基线。
