# 10 可观测与评测

本文定义运行追踪（span 模型、属性键、与运行树的关系、可选的 OTLP 导出）、成本的可观测面、离线评测体系（场景、录制文件、假世界、判分器、结果与基线），以及版本化与 A/B 的指标。表结构见 [03 §5、§12](./03-数据模型.md)，端点与配置见 [04](./04-接口与事件协议.md)，中间件顺序见 [05 §5](./05-运行时与代理定义.md)。实现分在两个里程碑：[M68](./specs/m68-trace-evals.md) 建底座，[M98](./specs/todo/m98-versioning-ab.md) 加版本与 A/B（M98 仍是 TODO，不在当前执行队列）。

## 1. 目标

1. 每次运行、每次模型调用、每次工具调用都有 span，能回答「这一轮做了什么、慢在哪、花了多少、哪一步出错」。
2. 追踪不拖慢运行：span 在内存里攒批，由后台任务写库；写库或导出失败只记日志，不影响运行结果。
3. span 只存元数据。消息正文、推理内容、工具参数与结果仍在 `agent_message`、`agent_audit` 里，追踪表与导出都不带它们。
4. 属性键对齐 OpenTelemetry GenAI 语义约定，本项目特有的概念用 `maa.*` 前缀；接 Langfuse、Phoenix 只需填一个地址。
5. 改提示词、换模型、动运行时之前，先用离线评测确认行为不回退：regression 套件每个里程碑都跑且必须全过，capability 套件的通过率不低于台账里的基线。
6. 回放模式完全离线、结果确定；只有录制与实测两种模式需要真实的模型 key。
7. 代理定义的新版本要先过评测才能启用；A/B 实验按工单分组，用完成率、成本、耗时、人工干预次数比较两个版本。

## 2. span 模型与属性键

### 2.1 写入规则

- 一个 span 是 `trace_span` 的一行（03 §5.1）。`trace_id` 等于根运行的 `root_run_id`，`span_id` 是 16 位小写十六进制随机数，`parent_span_id` 指向同一条 trace 里的上级 span。
- span 在结束时整行写入，开始时不落库。进行中的 span 只在进程内存里；运行是否还在进行，以 `agent_run.status` 为准。
- 开始时间取墙上时钟（naive UTC），时长取单调时钟，`ended_at = started_at + duration_ms`。
- 只记录运行内部发生的事。REST 直接调用的检索、工具等没有运行的操作不记 span。
- `trace.enabled=false` 时不记任何 span（热生效）；已写的数据不受影响，按 `trace.retention_days` 照常清理。
- 写入路径：`SpanRecorder` 把结束的 span 放进内存队列，后台任务每 0.5 秒或攒满 200 条写一批。队列上限 10000 条，满了丢弃新来的并计数；写库失败的批次下一轮重试，连续失败 3 次丢弃。运行的关键路径上没有数据库写入。
- `status` 只有 `ok`、`error` 两个值。工具被拒绝、确认过期、提问没人答属于人的决定，记 `ok` 并在属性里写明结果；`error` 只表示出错：模型调用抛错、工具返回错误、运行以失败结束。

### 2.3 属性值的限制

- 值只允许字符串、整数、浮点、布尔与字符串列表（最多 16 项）；`None` 不写。
- 字符串超过 256 字截断并以「…」结尾；每个 span 最多 48 个属性，超出的按写入顺序丢弃。
- 不写入属性的内容：消息与推理正文、提示词、工具参数与结果、用户原话、API key、`base_url` 的路径与查询串。`maa.policy.reason` 这类短理由可以写，同样受 256 字限制。

## 3. 运行树与 trace 的关系

### 3.1 对应关系

- 运行树是 `agent_run` 的父子关系（`parent_run_id`、`root_run_id`，03 §3.2）；trace 是 `trace_id` 相同的全部 span。一棵运行树对应一条 trace。
- 每个运行恰好产生一个 `agent.run` span，`run_id` 列指向该运行；运行内部的 span 都带同一个 `run_id`。
- 根运行的 `agent.run` 没有上级 span。子运行的 `agent.run` 的上级是父运行里发起它的那个 span：委派时是 `delegate.subagent`，压缩时是 `compaction.summarize`，在中间件钩子里直接起的运行（例如标题生成）挂在父运行的 `agent.run` 下。

### 3.2 上级 span 怎么定

`SpanRecorder` 用一个 `contextvars.ContextVar` 记当前 span：`agent.run` 开始时设为自己，工具调用期间设为该工具的 span，结束时复原。asyncio 新建任务会复制当前上下文，所以在工具调用里起的子运行自然拿到正确的上级。规则：

- 当前 span 属于别的 trace 时不当上级。例如总控的 `create_ticket` 写收件箱后，Worker 的运行在另一个任务里开始，它从上下文里继承到的总控 span 被忽略，Worker 运行自成一条 trace。
- 哪些运行同属一条 trace：子代理、在父运行调用栈内触发的压缩与标题生成，这些运行的 `parent_run_id` 指向父运行。哪些运行自成一条 trace：收件箱唤醒的总控与 Worker 每一轮、事件研判、Watchdog 巡检、会话结束后的记忆整理。
- 跨 trace 的因果（总控建单后 Worker 开工、汇报回到总控）不靠 span 表达，靠工单与收件箱：`agent_run.ticket_id`、`agent_inbox.consumed_run_id`。

### 3.3 查询与展示

- `GET /api/agent/runs/{run_id}/spans` 按 `run_id` 找到根运行，返回整条 trace 的 span（按开始时间排序，最多 5000 条，超出时 `truncated=true`）。前端高亮 `run_id` 等于当前运行的那部分。
- 工单页的活动树（M72）列出带该 `ticket_id` 的根运行，展开用 `GET /api/agent/runs/{run_id}` 的子运行树，点进去看 trace。一个工单通常对应多条 trace，每轮一条。
- 运行追踪页的瀑布图按 `parent_span_id` 缩进；上级不在结果里的 span 当作顶层画，并标「上级没有记录」。

### 3.4 缺口

- 服务重启时进行中的 span 都在内存里，会丢；被 `RunRecovery` 标为中断的运行没有 `agent.run` span，它已经结束的子 span 在瀑布图里成为顶层。
- span 超过 `trace.retention_days`（默认 14 天）被清理，`agent_run` 与 `cost_ledger` 保留更久（03 §14），所以老运行只有运行树与成本，没有瀑布图。

## 4. 成本账本与预算的可观测面

### 4.1 三处数据与一致性

| 数据 | 粒度 | 保留 | 用途 |
|---|---|---|---|
| `cost_ledger`（M67） | 每次模型调用一行 | 365 天 | 成本页的汇总、预算判断 |
| `agent_run` 的 token 与 `cost_micros`（M66、M67） | 每次运行累计 | 不自动删除 | 运行列表、工单成本、A/B 指标 |
| `llm.chat` span 的 `gen_ai.usage.*`、`maa.usage.*`、`maa.cost.*` | 每次模型调用 | 14 天 | 瀑布图里看哪一步贵 |

同一运行在 span 还没清理时满足：`Σ cost_ledger.cost_micros（run_id）= agent_run.cost_micros = Σ llm.chat 的 maa.cost.micros`，三种 token 同理。M68 用测试钉住这条等式。

### 4.2 缓存命中

- 命中率 = `cached_tokens / prompt_tokens`，逐次调用、逐运行、逐分组都能算。
- 前缀缓存布局（06 §2）做得对时，同一代理连续几次调用的命中率应当很高；命中率突然下降，说明系统提示、工具声明或它们的顺序变了，先查最近改动的代理定义与工具描述。
- 成本页按代理与模型列出命中率，瀑布图里每个 `llm.chat` 显示本次命中的 token。

### 4.3 预算

- 三个设置（04 §6）：`budget.daily_cost_limit`、`budget.per_run_cost_limit`、`budget.warn_ratio`；代理定义的 `budget.max_cost_per_run` 优先于单次上限。
- 预算只按人民币统计（M67 的 `BUDGET_CURRENCY`）。`BudgetMiddleware` 在每次模型调用前检查，超出时运行以 `budget_exceeded` 结束，运行状态 `failed`，`agent.run` 的 `error.type` 为 `budget_exceeded`；花费达到 `warn_ratio` 时广播一次 `agent_event` 的 `budget_warning`。
- 成本页的「今日」卡片显示今日的人民币成本与每日上限，达到 `warn_ratio` 时变成警告色；运行详情显示本运行成本与它适用的单次上限。上限为 0 表示不限，界面上写「不限」。

### 4.4 币种

成本一律存为币种的百万分之一（`cost_micros`）与币种代码。成本页显示 `summarize_costs` 返回的 `currency`；导出到 Langfuse 时只有币种是 USD 才写它识别的成本字段（§5.3）。

## 5. 可选 OTLP 导出

### 5.1 开关与依赖

- 两个 config-only 设置（04 §6）：`trace.otlp_endpoint` 填完整的 traces 地址（以 `/v1/traces` 结尾），空表示不导出；`trace.otlp_headers` 写成 `k=v,k=v`，每项按第一个 `=` 拆开（Basic 认证的 base64 末尾常带 `=`），值里的逗号写成 `%2C`。改了要重启服务。
- 依赖做成 extra `otlp`：`opentelemetry-sdk` 与 `opentelemetry-exporter-otlp-proto-http`。选 HTTP/protobuf：Langfuse 只收 HTTP（JSON 或 protobuf），Phoenix 的 HTTP 入口收 protobuf；gRPC 导出器依赖体积很大的 `grpcio`，两个后端也用不上。
- 配了地址却没装 extra 时，启动日志写一条警告，导出关闭，追踪照常写库。

### 5.2 导出什么、怎么映射

- 写库成功的每一批 span 原样再交给导出队列，内容与库里一致，不补正文。导出在独立的后台任务里进行，不占写库任务。
- id：trace id 取根运行 UUID 去掉连字符的 32 位十六进制，span id 原样。resource 属性 `service.name=maa-api`、`service.version` 取服务版本。
- 导出时补的键：`gen_ai.provider.name`（等于 `gen_ai.system`）；`langfuse.observation.type` 与 `openinference.span.kind`，按下表；`agent.run` 上补 `session.id`（有工单写 `maa.ticket.id`，否则写 `gen_ai.conversation.id`）；根运行的 `agent.run` 再补 `langfuse.trace.name`（代理定义 `name`）。

| span | 导出名 | OTLP SpanKind | `langfuse.observation.type` | `openinference.span.kind` |
|---|---|---|---|---|
| `agent.run` | `invoke_agent {gen_ai.agent.name}` | INTERNAL | `agent` | `AGENT` |
| `llm.chat` | `chat {gen_ai.request.model}` | CLIENT | `generation` | `LLM` |
| `llm.embed` | `embeddings {gen_ai.request.model}` | CLIENT | `embedding` | `EMBEDDING` |
| `tool.execute` | `execute_tool {gen_ai.tool.name}` | INTERNAL | `tool` | `TOOL` |
| `delegate.subagent` | `execute_tool {gen_ai.tool.name}` | INTERNAL | `tool` | `TOOL` |
| `retrieval.search` | `retrieval.search` | INTERNAL | `retriever` | `RETRIEVER` |
| `policy.*` | 原名 | INTERNAL | `guardrail` | `GUARDRAIL` |
| 其余 | 原名 | INTERNAL | `span` | `CHAIN` |

- `status=error` 导出为 OTLP 的 ERROR，描述取 `error.type`；`ok` 导出为 UNSET。

### 5.3 接 Langfuse

1. 装 extra `otlp`（安装命令见 16-部署指南 §12；Docker 镜像用 `--build-arg MAA_EXTRAS="otlp"` 构建）。
2. 在 Langfuse 项目设置里拿到 public key 与 secret key，算 `AUTH=$(printf '%s' 'pk-lf-…:sk-lf-…' | base64)`。
3. `config.yaml`：

   ```yaml
   trace:
     otlp_endpoint: https://cloud.langfuse.com/api/public/otel/v1/traces
     otlp_headers: "Authorization=Basic <AUTH>,x-langfuse-ingestion-version=4"
   ```

   美区写 `https://us.cloud.langfuse.com/api/public/otel/v1/traces`；自建（Langfuse v3.22 起）写 `http://<主机>:3000/api/public/otel/v1/traces`。`x-langfuse-ingestion-version=4` 让数据实时出现，不带它可能延迟十分钟左右。
4. 重启后在 Langfuse 里按 session 看：同一工单的每轮运行归在一个 session 下。成本字段 `gen_ai.usage.cost` 在 Langfuse 里按美元理解，所以只在币种为 USD 时写；其他币种的成本在属性里的 `maa.cost.*` 能看到。

### 5.4 接 Phoenix

1. 本机起一个：`docker run -p 6006:6006 arizephoenix/phoenix:latest`（Docker Desktop 的 CLI 不在 PATH 时用完整路径，见 docs/ENVIRONMENT.md）。
2. `config.yaml` 写 `trace.otlp_endpoint: http://127.0.0.1:6006/v1/traces`；Phoenix 开了认证时 `otlp_headers` 写 `Authorization=Bearer <API key>`。
3. Phoenix 15.10 起在入库时把 `gen_ai.*` 转成它的 OpenInference 字段；更早的版本靠导出时补的 `openinference.span.kind` 区分模型、工具与代理。

### 5.5 失败处理与隐私

- 导出队列上限 10000 条，满了丢最旧的；单批超时 10 秒，失败的批次下一轮再试一次，仍失败就丢弃并计数。导出警告一分钟最多一条日志。
- 导出的内容不含正文，但包含模型名、工具名、工单与运行 id、时长与成本。只配自己掌控或信任的地址。

## 6. 评测体系

### 6.1 组成

```
maa_api/agent/evals/        scenario.py（场景 schema 与加载）、cassette.py（录制文件与模型传输层）、
                            graders.py（判分器）、runner.py（逐例执行、结果写出）
scripts/agent_eval.py       命令行入口
tests/fakes/fake_core.py    假内核、假设备、假流水线执行器（基于 FakeAsst）
tests/evals/environment.py  假世界：生产 create_app() + lifespan + 临时目录
tests/evals/scenarios/      场景 YAML
tests/evals/cassettes/      录制文件 JSONL
tests/evals/fixtures/       外部来源的响应夹具
resource/evals/             结果（不进版本库）
```

评测走生产装配：每个用例用 `create_app()` 起一个完整的应用与 lifespan，数据库、配置、资源目录都在临时目录里；只替换内核、设备、外部数据源与模型这四个边界。

### 6.2 套件

| 套件 | 测什么 | 判分器 | 闸门 |
|---|---|---|---|
| `regression` | 运行时、工具、策略、确认、中断这些确定的行为：给定模型输出，系统必须怎么反应 | 不允许 `llm_judge` | 每个里程碑跑，必须 100% 通过 |
| `capability` | 模型在真实情境里会不会做对：来自实机复盘的教训 | 四种都可以 | 通过率不低于台账里上一个里程碑的基线 |

### 6.3 模式

| 模式 | 模型应答从哪来 | 出网 | 写录制文件 | 结果确定 | 需要 key | 用途 |
|---|---|---|---|---|---|---|
| `replay` | 录制文件 | 否 | 否 | 是 | 否 | 每个里程碑的闸门 |
| `record` | 真实模型 | 只访问模型 | 用例通过时写 | 否 | 是 | 新建或刷新录制文件 |
| `live` | 真实模型 | 只访问模型 | 否 | 否 | 是 | 测提示词与模型的真实能力；M98 的激活闸门 |

外部数据源在三种模式下都走夹具，不访问真实网站。capability 套件在 replay 下回放的是录制时的模型轨迹，它守住的是「系统对这条真实轨迹的处理」；提示词改了之后要知道新提示词好不好，用 `live` 或重新 `record`。

### 6.4 场景 YAML

一个文件一个场景，文件名主干等于 `id`。字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | str | 是 | `^[a-z0-9][a-z0-9-]{2,63}$` |
| `title` | str | 是 | ≤ 40 字 |
| `suite` | enum | 是 | `regression`、`capability` |
| `agent` | str | 是 | 被评测的代理定义 `name`；M98 按它挑场景 |
| `source` | str | 否 | 出处，例如 `docs/v2/13 §8.81` |
| `tags` | list[str] | 否 | |
| `entry.kind` | enum | 是 | `legacy_session`（v2 会话入口，M68）、`orchestrator`、`ticket`（M70 实现驱动） |
| `entry.worker`、`entry.title`、`entry.brief`、`entry.scope` | str | `ticket` 必填 | 直接建工单时的 Worker 定义名、标题、任务说明与委托范围 |
| `settings` | map | 否 | 点分配置键到值，只能用 `SETTING_KEYS` 里的键 |
| `world.core_script` | enum | 否 | FakeAsst 剧本：`success`（默认）、`failure`、`stuck`、`disconnect` |
| `world.device_connected` | bool | 否 | 默认 true |

| `world.seed.pipelines` | list | 否 | 预置的流水线：`{title, status, minutes_ago, error_code, error_message, tasks: [{type_name, status, params, error_code, error_message}], logs: [{task, level, content}]}` |

| `turns[].human.confirmations` | enum | 否 | 确认卡出现时怎么办：`approve`、`reject`（默认）、`ignore`（等它过期） |
| `turns[].human.questions` | enum 或对象 | 否 | `ignore`（默认）、`skip`、`{answer: [选项]}` |

### 6.5 录制文件

JSONL，第一行是头，之后每行一次模型调用：

```json
{"type": "header", "format": 1, "scenario": "legacy-daily-submit", "source": "handwritten", "recorded_at": "2026-11-02T08:00:00Z", "model": "eval-model", "agent": "legacy_chat", "spec_version": null, "notes": "手写的理想轨迹"}
{"type": "call", "channel": "agent", "reply": {"tool_calls": [{"id": "c1", "name": "submit_pipeline", "arguments": {"title": "日常", "tasks": [{"name": "StartUp", "start_game_enabled": true}, {"name": "Fight", "stage": "1-7"}]}}], "usage": {"prompt_tokens": 1800, "completion_tokens": 60, "cached_tokens": 1536}}}
{"type": "call", "channel": "agent", "reply": {"tool_calls": [{"id": "c2", "name": "wait_pipeline", "arguments": {"pipeline_id": "{{result:c1:pipeline_id}}", "timeout_seconds": 60}}]}}
{"type": "call", "channel": "agent", "reply": {"text": "日常做完了：理智清到 1-7，奖励已领取。"}}
```

- 应答有两种写法：手写用 `reply`（`text`、`reasoning`、`tool_calls`、`finish_reason`、`usage`，加载时展开成 OpenAI 流式分片）；录制的用 `chunks`（上游原始分片）。模拟上游错误写 `error: {status, headers, body}`。
- `channel`：`agent` 是代理的调用，按顺序逐条消费，必须全部用完；`aux` 是不带工具、也不以 system 开头的请求（会话标题等），有录制就按顺序用，没有就回一句固定文字；`probe` 是能力探查，没有录制时自动应答；`judge` 是 `llm_judge` 的评审调用。
- 占位符 `{{result:<tool_call_id>:<字段路径>}}` 在回放时换成该次工具结果里的值，用来引用流水线 id 这类每次都不同的值。录制时，参数里的 UUID 如果出现在之前的工具结果里，自动改写成占位符。
- 录制的调用另带 `request` 指纹：`model`、`roles`（消息角色序列）、`tool_call_ids`（请求末尾的 tool 消息对应的 id）、`tools_sha`、`system_sha`（工具名列表与系统提示的 sha256 前 12 位）。
- 回放时的检查：请求以 tool 消息结尾时，这些消息的 `tool_call_id` 集合必须等于上一条 `agent` 应答的 tool call id 集合，否则本例出错；调用次数超过录制的、或者录制的没用完，本例出错；`tools_sha`、`system_sha` 与录制时不同只记警告，加 `--strict` 时算出错。
- 录制文件不存请求正文、请求头与 key。`record` 模式只在用例通过时覆盖 `tests/evals/cassettes/<id>.jsonl`；不通过的录制写到结果目录，命名 `<id>.failed.jsonl`，供排查。

### 6.6 假世界

- 内核：`tests/fakes/fake_core.py` 的 `FakeCoreClient` 包一个 `tests/fakes/fake_asst.py` 的 `FakeAsst`，按 `world.core_script` 选剧本。`success` 立即完成；`failure` 发 `TaskChainError`；`stuck` 只发开始、一直不结束；`disconnect` 发断开。真实的 `PipelineRunner`、队列与审计照常工作。
- 设备：`FakeDeviceManager` 按 `world.device_connected` 报告连接状态；截图返回按 `world.screen` 画的 1280×720 图（纯色底加英文标签，例如 `ANDROID DESKTOP`），点击只记录坐标。
- 外部数据源：进程内默认的 `ExternalClient` 换成带 `httpx.MockTransport` 的实例，按 `world.http` 回夹具；没匹配上的请求按连接失败处理，工具返回「来源不可用」的结果。
- 预置数据：`world.seed` 在 lifespan 启动后、第一轮之前直接写库。
- 模型：lifespan 之后把 `app.state.agent_runtime.client_factory` 换成一个经评测传输层发请求的 `OpenAICompatibleClient`（v2 冒烟脚本的做法）；M67 的模型路由经 `client_factory_provider` 读同一个工厂，旧会话、总控、Worker 与能力探查的请求都走它。传输层在回放时读录制文件，录制与实测时转发给真实模型并计数。以后新增的模型客户端（例如 M76 的 embedding）也要能经这个工厂或同样的传输层注入，否则评测无法离线。

### 6.7 判分器

一个场景可以有多个判分器；每个判分器的结果是 `passed`、`failed`、`skipped` 或 `error`。用例通过的条件：没有 `failed` 与 `error`，并且至少一个 `passed`。

| 判分器 | 字段 | 判什么 |
|---|---|---|
| `tool_sequence` | `match`（`subsequence` 默认、`exact`）、`steps[]`（`tool`、`args`、`status`（`ok`、`error`）、`error_code`、`next`）、`forbid[]`、`max_calls{}`、`min_calls{}` | 工具调用的顺序与参数。`subsequence` 要求各步按顺序出现，`next: true` 要求紧跟上一步；`exact` 要求全部调用逐一对应 |
| `outcome_state` | `runs`、`pipelines`、`confirmations`、`questions`、`messages`、`model_calls`、`requests`、`spans` | 运行结束后的系统状态：运行状态与终止原因、流水线与任务、确认与提问的结局、消息配对（`orphan_tool_calls`）、模型调用次数、发给模型的请求形状（如带推理内容的历史消息条数）、记下的 span 名字 |
| `text_contains` | `target`（`final` 默认、`all`）、`all_of`、`any_of`、`none_of`、`ignore_case`（默认 true） | 回复文字。`final` 是最后一轮最后一条有正文的助手消息，`all` 是全部助手正文 |
| `llm_judge` | `rubric`（≤ 2000 字）、`pass_score`（0–1，默认 0.7） | 让评审模型按评分标准打分，输出 `{score, passed, reasons}` 并本地校验。回放时用录制的 `judge` 应答，没有就记 `skipped`；regression 套件不能用 |

`args` 与 `outcome_state` 的期望值按同一套规则匹配：

| 写法 | 含义 |
|---|---|
| 标量 | 相等 |
| 对象 | 期望里的每个键都匹配；实际值可以有多余的键 |
| 列表 | 按顺序的子序列 |
| `{absent: true}` | 这个键不存在 |
| `{not: 期望}` | 不匹配括号里的期望时算匹配 |
| `{re: "…"}`、`{contains: "…"}` | 正则搜索、子串 |
| `{gte: n}`、`{lte: n}`、`{gt: n}`、`{lt: n}`、`{in: [...]}` | 数值比较、取值之一 |
| `{len: 期望}` | 列表或字符串的长度匹配期望 |
| `{first: 期望}`、`{last: 期望}`、`{any: 期望}`、`{all: 期望}` | 首个、末个、任一、全部元素匹配 |

只含一个键、键名是上表运算符的对象按运算符处理，其余对象按普通对象匹配。期望对象里的键在实际值里不存在时，只有 `{absent: true}` 与 `{not: …}` 算匹配；例如 `timeout_seconds: {not: {gt: 120}}` 在模型没传这个参数（取默认 120）时也通过。

### 6.8 结果与基线

- 一次评测写一个目录 `resource/evals/<id>/`：`result.json`（汇总）、`cases/<场景 id>-<第几次>.json`（每例的消息、工具调用、事件、span 与判分细节），并在 `resource/evals/index.jsonl` 追加一行摘要。`<id>` 形如 `20261102-081530-regression-replay-3f2a`。
- `result.json` 的字段：`format`、`id`、`suite`、`mode`、`started_at`、`finished_at`、`git`（`commit`、`dirty`）、`model`、`repeat`、`filters`、`target`、`baseline`（M98 填）、`variants`（每个变体的汇总）、`summary`（`total`、`passed`、`failed`、`error`、`skipped`、`pass_rate`、`model_calls`、三种 token、`cost_micros`、`currency`、`duration_ms`）、`cases[]`。
- 通过率 = passed /（passed + failed + error），跳过的不计。
- 命令行退出码：0 通过；1 有用例不通过或低于 `--min-pass-rate`；2 参数错误；3 环境错误（例如 `record`、`live` 缺 key）。末行通过时是 `EVAL OK`，否则 `EVAL FAIL`。
- 基线记在台账：每个里程碑的台账写 `regression` 与 `capability` 两个套件在 replay 下的通过率与结果 id；capability 有 live 结果时一并记下模型名与通过率。

### 6.9 什么时候跑、怎么加场景

- 12 §4 第 6 条：M68 起每个里程碑跑 `--suite regression --mode replay`；改了提示词或代理定义的里程碑另跑 `--suite capability --mode replay`，有 key 时再跑一次 `live` 记进台账。
- 一个场景只测一件事；regression 场景描述系统的确定行为，用手写录制文件；capability 场景来自实机会话，`source` 写明出处，先手写理想轨迹，有 key 时用 `record` 换成真实轨迹。
- `legacy_session` 入口依赖 v2 会话的发消息路径，M72 删除它之前，这些场景要迁到 `ticket` 入口（M72 或 M73 的 spec 负责）。

## 7. A/B 与版本化的指标（M98）

### 7.1 版本与激活闸门

- 每个代理定义的每个版本是 `agent_spec_version` 的一行（03 §12）：`version` 是内容 sha256 的前 12 位，与 `agent_run.spec_version` 同一口径。内置文件的当前内容在启动时同步成 `source=builtin` 的行；在代理定义页编辑后保存的是 `source=override`、`status=candidate` 的行。
- 激活一个从没启用过的覆盖版本前，必须有它的 capability 评测结果：`live` 或 `record` 模式，用 `scripts/agent_eval.py --spec <name>@<version>` 跑（同一次评测里自动把当前启用的版本当基线一起跑），候选版本的通过率不低于当前版本，并且这期间当前版本没有换过、候选内容没有改过。服务端从 `resource/evals/index.jsonl` 找这份结果，不在服务进程里跑评测。
- 回滚不需要评测：曾经启用过的版本，以及代码里当前的内置版本，可以直接激活。
- 没有任何 capability 场景的代理定义不能激活覆盖版本。

### 7.2 分组

- 只有 `kind=worker` 的代理定义能做实验，按工单分组；`versions.ab_enabled=false` 时不分组，也不能新建实验。
- 一个代理定义同时最多一个进行中的实验。A 组是建实验时启用的版本，B 组是候选版本；候选版本要先过 §7.1 的闸门。
- 建工单时按 `sha256("<实验 id>:<工单 id>")` 的前 8 位十六进制换算成 [0, 1) 的数，小于 `ratio` 分到 B 组，否则 A 组。分组写进 `ticket.experiment_id` 与 `ticket.variant`，工单结束前不变，实验停止后也不变。
- 该工单的 Worker 每一轮都用分到的版本；子代理不受影响。`agent.run` span 带 `maa.experiment.id` 与 `maa.experiment.variant`。

### 7.3 指标

只统计已结束（`done`、`failed`、`cancelled`）的工单，按组计算：

| 指标 | 定义 | 来源 |
|---|---|---|
| 工单数 | 分到该组的工单，另列已结束的数量 | `ticket.experiment_id`、`variant` |
| 完成率 | `done` / 已结束，附 95% Wilson 区间 | `ticket.status` |
| 平均成本 | 每个工单名下全部运行（含子代理运行）的 `cost_micros` 之和，再取均值 | `agent_run.ticket_id` |
| 耗时 | `ended_at - created_at` 的中位数与 P90 | `ticket` |
| 人工干预次数 | 每个工单的提问数、用户在工单里发的消息数、被用户停止的运行数之和，再取均值 | `agent_question.origin_ticket_id`、`agent_inbox`（`kind=user_message`、`thread_key=ticket:<id>`）、`agent_run.finish_reason=interrupted` |
| 确认次数 | 每个工单的确认数均值；消耗类与破坏类操作本来就要逐次确认，单独列出，不算进人工干预 | `confirmation.origin_ticket_id` |
| 运行失败 | 按 `finish_reason` 分组的失败运行数 | `agent_run.status=failed` |

运行中的实验每次读取时现算；停止时把当时的结果写进 `ab_experiment.metrics` 作为快照。成本涉及多个币种时成本类指标为空，界面写「币种不一致，不比较成本」。

### 7.4 判读

- Wilson 区间：p = 完成数 / n，z = 1.96，中心 (p + z²/2n) / (1 + z²/n)，半宽 z·√(p(1−p)/n + z²/4n²) / (1 + z²/n)。
- 每组已结束的工单少于 20 个时，对比页标「样本不足，先别下结论」。
- 系统不自动判胜负。停止实验时由用户选「保留当前版本」或「改用候选版本」，后者等于激活 B 组版本，因为它已经过了闸门而且实验期间不允许换版本。

### 7.5 回滚与清理

- 激活新版本后效果不好，在版本列表里激活上一个启用过的版本即可回滚；正在跑的工单下一轮起改用新的启用版本，参加实验的工单除外。
- 启动时覆盖版本校验失败（例如它引用的工具在新代码里没有了），自动退回内置版本，该覆盖版本标为 `retired`，日志写明原因。
- `agent_spec_version` 与 `ab_experiment` 不自动删除。
