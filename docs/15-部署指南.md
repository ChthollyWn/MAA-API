# 部署指南

> 本文记录 MAA-API 的实际部署形态：单进程 FastAPI 托管前端构建产物，HTTPS 入口由 Tailscale Serve 提供。决策依据见 [13-决策记录 §ADR-13](./13-决策记录.md) 与 [09-前端重构方案 §12](./09-前端重构方案.md)。

## 0. 先做这一步：每台访问设备都要装 Tailscale 客户端

**这是唯一的用户侧前置条件，不能省。** 服务本身跑在 `127.0.0.1:8002`，只有登录了同一 tailnet 的设备才能访问。不在 tailnet 里的设备连端口都摸不到。

这一步同时是访问控制手段：它比单 `access_token` 鉴权更强，因为设备在拿到 TCP 连接之前就被拒了。反过来，**任何拿到 tailnet 内一台设备的人都能打开这个控制台**，所以 tailnet 的成员范围就是这个服务的暴露范围。

为什么不用自签证书或局域网 HTTP：Service Worker、Push API、Notification API 都要求**安全上下文**，`http://192.168.x.x:8002` 不是安全上下文，Web Push 在那下面不是"体验降级"而是"功能不存在"。详见 [09 §12.1](./09-前端重构方案.md)。

## 1. 起服务

### 本机（开发/单机）

```bash
./scripts/start-maa-api.sh
```

脚本会：定位仓库根、设置 MaaCore 动态库搜索路径（macOS `DYLD_LIBRARY_PATH` / Linux `LD_LIBRARY_PATH`）、从配置读取代理头信任范围，然后用仓库内的 `.venv` 启动 uvicorn。可用环境变量覆盖：`MAA_PYTHON`、`MAA_HOST`、`MAA_PORT`。

ADB 等待逻辑在 M6 已内移到服务里，脚本不再做这件事。

需要**登录即起、退出即拉起**（挂机跑定时任务时是常态）就用 launchd，别用 `nohup` 或 tmux：

```bash
./scripts/maa-api-service.sh install   # 安装 LaunchAgent 并启动
./scripts/maa-api-service.sh status    # 加载状态、PID、端口、日志位置
./scripts/maa-api-service.sh logs -f   # 跟随日志
./scripts/maa-api-service.sh reload    # 改完 config.yaml 重启生效
./scripts/maa-api-service.sh disable   # 彻底停用（stop 会被 KeepAlive 拉回来）
```

停服语义见 [README](../README.md) 的「macOS 开机自启（LaunchAgent）」一节：`KeepAlive` 让"停止"与"停用"必须分开表达。**同一个 8002 端口与 SQLite 库只能有一个实例**，launchd 与 Docker 二选一。

### Docker

```bash
docker build -t maa-api .
docker run -d --name maa-api -p 127.0.0.1:8002:8002 \
  -v "$PWD/config.yaml:/app/config.yaml:ro" \
  -v "$PWD/resource:/app/resource" \
  maa-api
```

镜像已经是多阶段构建（node 构建前端 → python 运行），运行镜像里没有 Node 工具链。`CMD` 带了 `--forwarded-allow-ips 127.0.0.1`，理由见下一节。

## 2. 配上 HTTPS 入口（Tailscale Serve）

在跑 MAA-API 的机器上执行一条命令：

```bash
tailscale serve --bg https / http://127.0.0.1:8002
```

之后从 tailnet 内任意设备访问 `https://<主机名>.<tailnet>.ts.net`。证书由 Tailscale 自动签发与续期，不需要任何证书维护。

### 配套配置（三项，缺一会得到"页面能开但某处悄悄坏掉"）

**第一项：让 uvicorn 信任代理头。** `tailscale serve` 是反向代理：浏览器到它是 HTTPS，而它到 uvicorn 是到 `127.0.0.1` 的明文 HTTP。所以到 FastAPI 的请求里 `X-Forwarded-Proto: https`，但连接本身是 HTTP。

```yaml
deployment:
  # 默认就是 127.0.0.1。不要写 "*"。
  forwarded_allow_ips: 127.0.0.1
```

`*` 会让任何客户端都能伪造 `X-Forwarded-For` 与 `X-Forwarded-Proto`：既绕过按来源限流，也让下面 cookie 的 `Secure` 判定失真。多跳代理时按需追加地址而不是放宽成通配。

**第二项：把 `*.ts.net` 域名加进浏览器来源白名单。** 这个域名取决于 tailnet 名与主机名，部署时才知道，所以是配置项：

```yaml
deployment:
  cors_origins:
    - https://maa-api.example-tailnet.ts.net
  # 或者用正则，省得主机名变了要改配置
  # cors_origin_regex: 'https://[a-z0-9-]+\.example-tailnet\.ts\.net'
```

HTTP CORS 与 WebSocket 握手校验**用同一份配置**。只配一半会出现「REST 请求正常、WebSocket 连接被 4403 拒绝」这种半通状态。

**第三项：确认 cookie 的 `Secure` 判定生效。** `POST /api/system/auth/cookie` 按 `X-Forwarded-Proto` 决定是否给 `maa_token` 加 `Secure`（实现见 `maa_api/util/http.py`）。判定必须按实际协议而不是按部署形态猜：

- 只按连接判定 → 在 Tailscale 下永远不加 `Secure`，cookie 在 HTTPS 站点上失去保护；
- 无条件加 `Secure` → 局域网 HTTP 直连时浏览器拒收 cookie，WebSocket 握手拿不到凭据。

这一项不需要配置，但要确认第一项做对了，否则判定拿不到正确的协议值。

## 3. Web Push（PWA 推送通知）

推送让「需要你立刻决策」的操作能送到锁屏，并在通知上直接处置。它要求 HTTPS、已把应用添加到主屏、且用户授权过通知。

**生成密钥对（只需要做一次）：**

```bash
.venv/bin/python scripts/generate_vapid_keys.py
```

把输出粘进 `config.yaml` 的 `notify` 段，然后重启服务。

**私钥必须保持稳定。** 浏览器在订阅时把公钥绑进订阅，推送服务用它校验签名。换密钥等于让所有已建立的订阅从那一刻起静默投递失败——订阅还在、用户却收不到任何通知、也没有任何报错。这正是密钥由脚本显式生成、而不是服务启动时自动生成的原因。

**验收路径**：手机用 `https://<主机名>.<tailnet>.ts.net` 打开 → 添加到主屏 → 在应用内进「更多 › 设置 › 通知」（`/more/settings/notifications`）→ 点「启用推送通知」（权限申请必须由真实用户手势触发，iOS 会忽略非手势请求）。之后让服务产生一条需要人工确认的操作，把应用切到后台，应当收到通知；点通知体回到应用，全局待确认面板会自动打开并定位到这条确认（深链 `/?confirm=<id>`），或（仅 Chromium）用通知上的「准许 / 拒绝」按钮直接处置。

WebKit（iOS / macOS Safari）**不渲染**通知上的按钮，也不支持常驻通知，这是平台限制而非缺陷：被忽略的选项静默失效，没有异常也没有控制台警告。两个平台共有的路径是「点通知体 → 深链回卡片 → 应用内批准」。详见 [09 §13.2](./09-前端重构方案.md)。

## 4. 反向代理的其它选择

想完全不依赖第三方控制平面时，可以把 Tailscale Serve 换成 Caddy + DNS-01 挑战：反代 `127.0.0.1:8002` 并配置 DNS 提供商插件。上面三项配套工作（信任代理头、来源白名单可配、本文档）对它同样适用，**切换过去不需要改代码**——把 `deployment.cors_origins` 换成自己的域名即可。

## 5. 故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 手机打不开页面 | 设备没装客户端或没登录同一 tailnet | 装 Tailscale 并登录；这是设计上的访问控制 |
| 页面能开，但 WebSocket 连不上（日志见 `untrusted_origin`） | `deployment.cors_origins` 没放行 `*.ts.net` 域名 | 按上面第二项配置后重启 |
| 登录页、「更多」页或「设置 › 通知」显示「当前通过 HTTP 访问」 | 访问的是 `http://` 地址 | 改用 `https://<主机名>.<tailnet>.ts.net` |
| 「设置 › 通知」的 Web 推送只有说明、没有「启用推送通知」按钮 | 非安全上下文 | 同上；能力探测是显式的，不靠 try-catch 吞异常 |
| 启用推送报「服务端尚未配置 VAPID 密钥」 | `notify.vapid_private_key` 为空或不可解析 | 运行密钥生成脚本并重启 |
| 某个浏览器突然收不到推送 | 该订阅被推送服务注销（404/410），已被标记失效 | 「设置 › 通知」的「已登记的设备」里会显示「已失效」，在该设备上重新启用推送 |
| 登录后 WebSocket 仍失败 | cookie 没拿到 | 检查 `deployment.forwarded_allow_ips` 是否信任了实际代理地址 |

## 7. 出站请求与域名清单（防火墙与代理）

服务需要主动访问的域名分三组，出站规则放行到这些主机的 `443`（邮件通道另有用户自己的 SMTP 主机）：

| 主机 | 用途 | 控制方式 |
|---|---|---|
| `api.maa.plus` | 内核与活动资源的版本检查、OTA `tasks.json`（通道 A）、内核更新详情 | `updates.*` |
| `github.com`、`raw.githubusercontent.com`、`mirrorchyan.com` | 内核更新包与 `MaaResource` 压缩包（通道 B）、Mirror 酱的版本查询；下载失败时按上游返回的 `mirrors` 列表依次回退 | `updates.download_prefix`、资源更新的选源与上游返回的镜像列表 |
| `ak.hypergryph.com`、`line1-h5-pc-api.biligame.com` | 游戏本体的最新版本与下载（官服 / B 服） | 游戏更新（M7） |
| Bark / 邮件 / Webhook / 钉钉 / 企微 / 飞书 | 通知投递。Bark 默认 `api.day.app`（可换自建 server），其余是各自配置里的地址 | `notify.*` |
| `prts.wiki` | **M25 起**：PRTS 的只读检索（`/api.php` 的 `action=query` / `ask` / `cargoquery` / `opensearch` 与 `parse&prop=sections`） | `sources.*` |
| `penguin-stats.io`、`penguin-stats.cn` | **M26 起**：企鹅物流的掉率查询（`/PenguinStats/api/v2/result/matrix`、`/stages`、`/items`、`/period`）。两个主机的数据一致，默认走 `.io`，请求失败一次后自动改试 `.cn`；数据许可 CC BY-NC 4.0 | `sources.penguin_enabled`、`sources.penguin_host` |

外部数据源这一组（M25 起）与更新、通知两组分开，规则更严：只发 `GET`，主机与路径按来源白名单复核，请求有连接 / 读取超时、响应上限、每分钟令牌桶、429 冷却与连续失败熔断（[11 §6.6](./11-Agent模块设计.md)）。部署在只允许特定出站的环境里时，放行 `prts.wiki:443` 与 `penguin-stats.io:443` 即可（只放行 `.io` 时 `.cn` 的自动改试会失败，掉率按不可用处理）；把 `sources.enabled`、`sources.prts_enabled` 或 `sources.penguin_enabled` 关掉，对应的外部查询就不再发出站请求（当期活动与关卡退回本机资源包，干员退回本机 `battle_data.json` 的部分字段，敌人与掉率如实报查不到；没有本机兜底的查询返回 `503 EXTERNAL_SOURCE_DISABLED`）。

代理：`sources.use_proxy` 为 `true` 且 `app.proxy` 非空时，外部数据源请求走系统代理；改代理设置会重建出站客户端，不需要重启服务。更新与通知两组仍按各自的既有口径走 `app.proxy`。

后续里程碑会往这张表里加：`prts.maa.plus`（M29）、`fastly.jsdelivr.net` / `cdn.jsdelivr.net` / `api.github.com`（M29，拆包关卡数据的镜像与兜底）。
