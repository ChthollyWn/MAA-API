# M14 PWA 与打磨 · Web Push 交付规格

## 目标

在 M13 已交付的内置 Agent 与确认机制之上，补齐 M14 的两项能力：一是 **Web Push 即时触达**（前端关闭、锁屏也能收到人工确认请求，并能从通知深链或按钮直接处置）；二是**安全上下文分级降级**的显式化，保证 Tailscale Serve 未连通、用局域网 IP 直连时应用完整可用而不是满屏报错。

多通道通知（邮件 / Webhook / Bark / 钉钉 / 企微）与骨架屏、虚拟滚动等打磨项在 M9 已落地，不在本里程碑范围内。

## 范围与依赖边界

- 本里程碑交付 **Web Push 全链路**：VAPID 密钥、订阅 API、推送发送、Service Worker 的 `push` / `notificationclick`、设置页启用入口、确认卡片的深链处理。
- **HTTPS 入口本身归 M15。** 推送能力在 `http://192.168.x.x:8002` 下必然不可用，这是浏览器约束而非代码缺陷；本里程碑的验收在 `https://<host>.<tailnet>.ts.net` 或同机 `localhost` 上做，真机验收按 [09 §12.4](../09-前端重构方案.md) 与 M15 交叉执行。
- CORS 与 WebSocket 的 origin 白名单可配（含 `*.ts.net`）归 M15；本里程碑只保证现有白名单策略下推送链路自洽。

## 已确认的产品行为

### 密钥与配置

- VAPID 密钥对**只从 `config.yaml` / 环境变量读**，不进入设置 API，也不落 SQLite（实施补正，见 [13 §8.9](../13-决策记录.md)）：多行 PEM 在设置页单行输入框里回写会丢换行，而 `sensitive` 项读取只回 `***`，用户保存任意其它字段时前端会把 `***` 当新值提交并静默覆盖真实私钥。公钥由私钥导出，不单独存储。
- 提供 `scripts/generate_vapid_keys.py` 一次性生成密钥对并打印可直接粘贴进 `config.yaml` 的内容。**不在服务启动时自动生成**：启动时随机生成会让每次重启都换掉密钥，已存在的订阅会全部失效且用户无从知晓。
- 私钥属于凭据，适用既有脱敏规则：设置 API 只返回 `***`、不进日志、不进模型上下文。

### 订阅

- `POST /api/notifications/push-subscriptions` 接受浏览器 `PushSubscription.toJSON()` 的形状（`endpoint`、`keys.p256dh`、`keys.auth`），返回 201 与 `Location`。同一 `endpoint` 重复提交为幂等更新（返回 200），不产生重复行。
- `GET /api/notifications/push-subscriptions` 返回订阅列表，只暴露 `id`、`endpoint_host`、`created_at`、`last_success_at`，**不回显 `endpoint` 全文、`p256dh`、`auth`**——它们与凭据同级。
- `DELETE /api/notifications/push-subscriptions/{id}` 删除订阅，204。
- 发送时收到 404 / 410 表示订阅已失效，服务端删除该行并记录日志，不做无限重试。
- 写入前校验 `endpoint` 必须是 `https` 绝对 URL，`p256dh` 必须是 65 字节未压缩 P-256 点，`auth` 必须是 16 字节；不满足返回 `PUSH_SUBSCRIPTION_INVALID`（422）。校验 P-256 点时须确认该点在曲线上且不是无穷远点（[RFC 8291 §7](../README.md)）。

### 发送

- 传输层自行实现，**不引入 `pywebpush`**：`cryptography` 已是直接依赖，具备了 ECDH P-256、HKDF-SHA256、AES-128-GCM 与 ES256 签名的全部原语；本机网络对 PyPI 不稳定，新增运行时依赖会同时把安装步骤变成构建的单点故障。
- 单条推送严格按 [RFC 8291](https://www.rfc-editor.org/rfc/rfc8291.txt) 与 [RFC 8188](https://www.rfc-editor.org/rfc/rfc8188.txt) 加密：单记录 `aes128gcm`，86 octet 头（salt 16 + rs 4 + idlen 1 + keyid 65），`rs = 4096`，明文追加 `0x02` 填充分隔符。
- **派生必须手写 HKDF 的 extract 与 expand 两步，不能用 `cryptography` 的 `HKDF.derive()`。** `derive()` 是 RFC 5869 的 extract+expand 组合，当 HKDF 被当作「只做 extract」使用时（本方案里 `PRK_key = HMAC(auth_secret, ecdh_secret)` 与 `PRK = HMAC(salt, IKM)` 两步）会额外多做一次 expand，结果全错且不会报错。已用官方向量实测确认：`HKDF(...).derive(ecdh)` 得到的值与 RFC 的 `PRK_key` 不一致，改用显式 `hmac.new(salt, ikm, sha256)` + 手写 expand 后全部匹配。详见下方「验收 · 自动化」。
- 请求头：`Content-Encoding: aes128gcm`、`TTL`、`Authorization: vapid t=<JWT>, k=<公钥>`、`Content-Type: application/octet-stream`。JWT 用 ES256，`aud` 取 `endpoint` 的 origin，`sub` 取配置的 `mailto:` 联络地址（缺省 `mailto:admin@example.com`），`exp` 为 12 小时。
- 明文上限 3993 octet（[RFC 8291 §4](https://www.rfc-editor.org/rfc/rfc8291.txt)）。超限时按 `tag` 合并语义截断 `body` 而不是让加密失败。
- 推送发送失败**不得**影响确认流程本身：确认照常落库、照常等待、照常超时。推送只是触达手段。广播**并发 + 总预算**（默认 12 秒），不能随订阅数线性增长 —— 确认的创建路径会 await 它。
- 通知标题必须是用户看得懂的动作与影响（如「提交任务流水线（刷理智 · 源石 ×3）」），**不得**出现 `run_task` / `Fight.stone=3` 这类内部标识符：用户是从锁屏点进来的。认不出的操作退回工具名，但不编造影响范围。

### 触达协同（docs/09 §13.1 的三级递进）

1. WebSocket 推 `confirm_request`；前端在线（`document.visibilityState === 'visible'`）时只出应用内卡片 + toast + 震动。
2. 后端在创建确认时检查**当前是否有活跃 WebSocket 连接**；没有活跃连接且有可用订阅时，立即发 Web Push。通知内容按「Apple 卡片优先」设计：完整信息写进 `title` / `body`，`tag` 用 `confirm:<id>` 做同类合并，`data` 携带 `confirmationId` 与深链 `url`。
   - `title` / `body` 必须包含操作内容与消耗量（如「Agent 请求碎石 3 颗」），且**不得**包含 token、API Key、绝对路径等敏感内容。
3. 没有可用订阅时（HTTP 部署 / 未安装 / 未授权）维持现状：由已配置的 Bark / 钉钉等通道兜底，消息体带可点击深链。

### Service Worker

- `push` 事件必须调用 `showNotification()`（`userVisibleOnly: true` 是浏览器强制的，静默处理会让订阅被撤销）。
- `notificationclick` 处理三种入口：`action === 'approve'` / `'reject'`（Chromium 渐进增强），以及 `action === ''`（点通知体本身，iOS 只走这条）。
- 从 action 按钮处置确认时，`fetch` 必须从 IndexedDB 取 token 注入 `X-Token`——Service Worker 不是 window 上下文，读不到 localStorage，而写操作不能靠同源 cookie 通过鉴权。
- `focusOrOpen` 先用 `clients.matchAll()` 找到已打开的窗口并 `focus()` + 导航，找不到才 `clients.openWindow()`；直接用 `openWindow` 会在应用已开着时再开一个。
- 处置结果必须回一条简短结果通知（「已准许：碎石 3 颗」/「操作已过期，未执行」）。失败分支不能省：确认可能已在此期间超时，静默失败会让用户以为批准成功。

### 分级降级（docs/09 §12.4 第一层）

- `PWA_AVAILABLE = window.isSecureContext && 'serviceWorker' in navigator`，`PUSH_AVAILABLE = PWA_AVAILABLE && 'PushManager' in window`。不要在非安全上下文里调用 `register()` 再用 try-catch 吞异常。
- 非安全上下文下：设置页整块隐藏推送配置，显示既有 `PwaSecurityNotice` 说明；首页确认卡片不受影响，照常通过 WebSocket 工作。
- 权限申请只能由真实用户手势触发（设置页的「启用推送通知」按钮）。**不得**在页面加载时自动调用 `Notification.requestPermission()`：iOS 会直接忽略非手势请求，Chromium 会记为一次被动拒绝并影响后续提示。

### 前端交互

- 设置页推送区块：当前权限状态（未询问 / 已允许 / 已拒绝 / 不支持）、启用按钮、失效原因说明、已订阅设备列表与注销入口。
- 首页确认卡片支持 `?confirm=<id>` 深链：加载后自动展开该确认并滚动到可见位置；关闭卡片时清除查询参数，避免刷新后反复弹出已处置的确认。

## 数据模型

新增 `push_subscription` 表（Alembic forward-only migration）：

| 列 | 说明 |
|---|---|
| `id` | 主键 |
| `endpoint` | 订阅端点全文，唯一 |
| `endpoint_host` | 从 endpoint 解析出的主机名，用于列表展示 |
| `p256dh` | Base64url 的客户端公钥 |
| `auth` | Base64url 的认证密钥 |
| `user_agent` | 可选，便于用户辨认设备 |
| `created_at` / `updated_at` | 时间戳 |
| `last_success_at` | 最近一次发送成功时间，可空 |
| `disabled_at` | 被判定失效的时间，可空；有值表示不再发送 |

`endpoint` 建唯一索引。失效订阅保留行并置 `disabled_at`（而不是删除），以便用户看到「某设备订阅已失效」并重新启用。

## API 契约

| 方法 | 路径 | 成功码 | 错误 |
|---|---|---|---|
| GET | `/api/notifications/vapid-public-key` | 200 | `PUSH_NOT_CONFIGURED`（503，未配置密钥） |
| GET | `/api/notifications/push-subscriptions` | 200 | — |
| POST | `/api/notifications/push-subscriptions` | 201 / 200（幂等更新） | `PUSH_SUBSCRIPTION_INVALID`（422） |
| DELETE | `/api/notifications/push-subscriptions/{id}` | 204 | `PUSH_SUBSCRIPTION_NOT_FOUND`（404） |

新错误码 `PUSH_NOT_CONFIGURED`、`PUSH_SUBSCRIPTION_INVALID`、`PUSH_SUBSCRIPTION_NOT_FOUND` 必须同步进 `docs/05` 的错误码表、`docs/14` 生成指南与各 endpoint 的 OpenAPI response 声明。

## 验收

### 自动化

- **RFC 8291 Appendix A 官方向量**：用固定的 `as_private` / `ua_public` / `auth_secret` / `salt` 复现该附录列出的中间值（`ecdh_secret`、`PRK_key`、`IKM`、`PRK`、`CEK`、`NONCE`）与最终 86 octet 头 + 密文（`DGv6ra1nlYgDCS1FRnbzlwAAEABBBP4z…`）。这是本里程碑唯一的独立加密正确性证据，不能只用自实现的解密来验证自实现的加密。
- VAPID JWT：用公钥验签成功、`aud` 等于 endpoint origin、`exp` 在未来、`sub` 为 `mailto:`。
- 订阅 API：形状校验（非 https endpoint、错误的 p256dh 长度、非 16 字节 auth、不在曲线上的点）、重复 endpoint 幂等、列表不泄露密钥字段、删除 404。
- 触达协同：无活跃 WS 连接 + 有订阅 → 触达推送；有活跃 WS 连接 → 不推送；无订阅 → 走通道兜底且不报错；推送失败不影响确认落库与超时。
- 失效处理：发送收到 410 → 置 `disabled_at` 且后续发送跳过该行。
- 前端：`PUSH_AVAILABLE` 在非安全上下文为 false 且渲染降级说明；`notificationclick` 的三种入口分支；action 处置从 IndexedDB 取 token；`?confirm=<id>` 深链展开卡片。

### 补充验证（不阻塞本里程碑，记录证据）

- 真机（Android Chrome / iOS Safari）经 Tailscale 的实际送达、action 按钮渲染与深链回卡片。
- 锁屏状态下的送达与点击。
- 这些项依赖 M15 的 HTTPS 入口，按 [docs/13 §8.3](../13-决策记录.md) 记入补充实测。

## 风险

- **加密实现是安全敏感代码**，唯一可靠的把关是官方向量测试；回退方案是抄 RFC 示例而不是「自己再看一遍」。
- **iOS 的 `actions` 与 `requireInteraction` 被静默忽略**，所以流程正确性不能以按钮为前提，深链路径必须独立可用。
- **VAPID 私钥轮换会让全部订阅失效**，所以密钥必须来自显式配置而非启动时生成；误配时应在设置页给出可诊断的提示而不是静默失败。
