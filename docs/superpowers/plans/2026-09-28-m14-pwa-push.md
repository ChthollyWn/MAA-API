## Task 1 · Web Push 加密原语（RFC 8291 / 8188）（已完成）

**产物**：`maa_api/services/webpush_crypto.py` + `tests/services/test_webpush_crypto.py`

- 先写 **RFC 8291 Appendix A 官方向量**测试并确认 RED：用固定的 `as_private` / `ua_public` / `auth_secret` / `salt` 复现 `ecdh_secret`、`PRK_key`、`IKM`、`PRK`、`CEK`、`NONCE` 与最终 86 octet 头 + 密文 `DGv6ra1nlYgDCS1FRnbzlwAAEABBBP4z…`。
- 实现 `encrypt_push_message(payload: bytes, *, ua_public: bytes, auth_secret: bytes, as_private: EcPrivateKey, salt: bytes | None = None) -> bytes`，返回可直接作为请求体的 `header + ciphertext`。
- **必须手写 HKDF extract/expand**：`PRK_key = HMAC(auth_secret, ecdh_secret)`、`PRK = HMAC(salt, IKM)` 两步是「只 extract」语义，`cryptography` 的 `HKDF.derive()` 会额外多做一次 expand，结果静默全错。已实测确认该陷阱，测试里保留一条断言锁住它。
- 校验入口：`ua_public` 必须是 65 字节 `0x04` 开头的未压缩点且落在 P-256 上、不是无穷远点；`auth_secret` 必须 16 字节。不满足抛领域异常而不是静默。
- 明文超过 3993 octet 时抛错（调用方负责按 `tag` 截断 body）。
- 运行：`.venv/bin/python -m pytest -q tests/services/test_webpush_crypto.py`；提交 `feat(notify): add RFC 8291 push encryption`。

## Task 3 · 推送发送与三级触达协同（已完成）

**产物**：`maa_api/services/webpush_service.py`（含 VAPID JWT 与发送）、`ConfirmationService` 的推送钩子。

- 先写失败测试并确认 RED：VAPID JWT 可被公钥验签、`aud` 等于 endpoint origin、`exp` 在未来、`sub` 为 `mailto:`；发送请求头含 `Content-Encoding: aes128gcm`、`TTL`、`Authorization: vapid t=…, k=…`；410/404 响应把该行置 `disabled_at` 且后续发送跳过；发送异常不冒泡到确认流程；超长 body 被截断而不是加密失败。
- 实现 VAPID JWT（ES256，`exp` 12 小时）与单条推送发送（httpx，超时与重试边界）。
- 在 `ConfirmationService._create_confirmation` 的 `broadcast("confirm_request", event)` 之后挂钩：**仅当当前没有活跃 WebSocket 会话**（`ConnectionManager.sessions` 为空）且有可用订阅时才推送。有活跃连接时不推送（用户就在看页面）。
- 通知内容按「Apple 卡片优先」：完整操作与消耗量写进 `title` / `body`，`tag` 用 `confirm:<id>`，`data` 带 `confirmationId` 与深链 `url`；**不得**含 token、API Key、绝对路径。chromium `actions` 只是附加项。
- 无订阅时维持现状：已配置的 Bark/钉钉等通道照旧发深链兜底，且推送缺失不报错。
- 运行：`.venv/bin/python -m pytest -q tests/services/test_webpush_service.py tests/agent/test_confirmation_push.py`；提交 `feat(notify): push confirmations when no client is connected`。

## Task 4 · 前端推送链路与深链确认（已完成）
