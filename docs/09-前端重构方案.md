> 这份方案定义前端从零重写的工程结构、技术依赖、页面规划与构建集成。技术选型已定稿，只讲怎么落地。决策依据见 [README 决策速查表](./README.md#决策速查表)，模块边界与数据流以 [02-系统架构设计](./02-系统架构设计.md) 为准。

# 前端重构方案

## 1. 范围与前提

现有 `static/` 下的四个文件全部废弃：`index.html`（734 行，Vue 3 global build + Element Plus 从 unpkg CDN 加载，无构建工具，8 种任务的表单用 `v-if="task.type_name === 'StartUp'"` 硬编码堆在一起）、`daily.html`、`js/app.js`、`css/style.css`。新前端是独立的 Vite 工程，源码在 `web/`，构建产物落到 `static/`，由 FastAPI 单进程在 8002 端口托管。

技术栈已定：Vite + React + TypeScript + Tailwind CSS + shadcn/ui。形态是 Web + PWA，移动端优先、桌面自适应。导航在手机与平板上用底部 Tab 栏，宽度 ≥1024px 时换成左侧栏（M16，见 [§6](#6-页面与路由规划)）。

三条贯穿全文的设计前提：

所有依赖打进 bundle，不留任何 CDN 外链。旧前端从 unpkg 拉 Vue、Element Plus、axios，这意味着内网无外网出口时页面直接白屏。新前端离线可用是硬要求。

后端不再有模板渲染。`router/template.py` 里两个返回 `FileResponse` 的路由一并废弃，SPA 的所有路径由前端路由处理，后端只负责把 `index.html` 交出去（见 [§5](#5-后端托管配置变更)）。

表单不再硬编码。任务参数的权威来源是后端 `GET /api/tasks/types` 返回的参数 schema，前端按 schema 生成控件（见 [§7](#7-任务表单的-schema-驱动生成)）。

`components/ui/` 的原语清单：`Button`、`Input`、`Textarea`、`Label`、`NativeSelect`、`Switch` / `SwitchRow`、`SegmentedControl`、`Chip` / `RemovableChip`、`Field`、`ListGroup` / `ListItem`、`Section`、`Disclosure`、`Badge` / `StatusDot`、`Progress`、`Skeleton`、`LoadingState` / `EmptyState` / `ErrorState` / `Spinner`、`InlineAlert`、`ResponsiveSheet`、`ConfirmDialog` 与 `useConfirm`、`ActionSheet` / `ActionMenu`、`StickyActionBar`、`ImageViewer`、`Toaster` 与 `toast`。M16 按本项目的设计令牌与触控尺寸重写了这一层，底层仍是 Radix 原语（Dialog、AlertDialog、Switch、ToggleGroup、Label、Slot）；它不再是「CLI 生成后不改」的代码。形态与用法见 [§7.3](#73-schema-到控件的映射规则) 与 [§8](#8-移动优先的设计规范)。

`features/` 与 `routes/` 的边界：`routes/` 放页面级组装与布局；取数与业务 hooks 放在 `features/`，这样同一份逻辑能被不同页面复用（例如首页的「运行定时任务」与任务区的定时列表共用 `features/schedules/queries.ts`）。Agent、Agent 审计、API 调试台与设置的页面组件直接放在各自的 feature 目录里，由路由表懒加载。`components/` 放跨业务域的通用件，一旦某个组件只被一个 feature 用，就应该搬进那个 feature。

`static/` 不再有手写文件，全部由 `vite build` 生成，加入 `.gitignore`（见 [§14](#14-构建与部署集成)）。

## 3. 依赖清单与选型理由

版本为 2026 年 9 月核实到的当前稳定版，写进 `package.json` 时用 `^` 允许小版本升级。

### 3.1 构建与语言

| 包 | 版本 | 用途 |
|---|---|---|
| `vite` | ^8.3.0 | 构建工具与 dev server |
| `@vitejs/plugin-react` | ^6.1.1 | React 支持与 Fast Refresh |
| `typescript` | ^6.0 | 类型检查 |
| `react` / `react-dom` | ^19.3.0 | UI 运行时 |

Vite 是唯一必须的构建工具选择，理由不在于它比 webpack 快，而在于三件本项目直接依赖的能力：`server.proxy` 能把开发期的 `/api` 与 WebSocket 一起转发到 8002，省掉前后端分离时的 CORS 配置；`build.outDir` 可以直接指向仓库外的 `../static`，产物无需二次拷贝；生态里有 `vite-plugin-pwa` 这类成熟插件把 Workbox 的配置复杂度收进插件选项。

Vite 8 有两个变化会影响写法：打包器从 Rollup 换成了 Rolldown，`build.rollupOptions` 已改名 `build.rolldownOptions`（旧名仍被兼容层自动转换但已废弃），`output.manualChunks` 的对象形式被移除、函数形式废弃，手动分包改用 `output.codeSplitting.groups`；JS 转换与压缩从 esbuild 换成 Oxc，CSS 压缩换成 Lightning CSS。另外 `build.target` 默认值对应的 Safari 下限是 16.4，恰好与 iOS Web Push 的最低版本一致，不需要额外调低。

`@vitejs/plugin-react` 是唯一该用的 React 插件。`@vitejs/plugin-react-oxc` 已废弃，其 Oxc 能力合并回了官方插件，在 Vite 8 下会自动启用 Oxc 版 Fast Refresh。React Compiler 目前是实验特性（需额外安装 `oxc-transform-react` 并传 `compiler: true`），首版不开。

### 3.2 UI 与样式

| 包 | 版本 | 用途 |
|---|---|---|
| `tailwindcss` | ^4.3 | 样式 |
| `@tailwindcss/vite` | ^4.3 | Tailwind 的 Vite 插件 |
| `shadcn`（CLI，仅 devDependency 或 npx 调用） | latest | 组件生成 |
| `@radix-ui/react-dialog`、`react-alert-dialog`、`react-switch`、`react-toggle-group`、`react-label`、`react-slot` | 按需引入 | 组件层的无样式原语 |
| `sonner` | 随 Toaster 组件引入 | toast |
| `lucide-react` | 随 shadcn/ui init 安装 | 图标 |
| `class-variance-authority` / `clsx` / `tailwind-merge` | 随 shadcn/ui init 安装 | 变体与类名合并 |

表中标「随…安装」的几项最初由 `shadcn` CLI 在 `init` 与 `add` 时按组件实现所需的版本追加，避免人工锁的版本与组件源码不匹配。M16 重写组件层时，新增的 Dialog、AlertDialog、Switch、ToggleGroup 四个 Radix 原语直接 `pnpm add`，同时去掉了不再使用的 `@radix-ui/react-tabs`。项目从未引入 `vaul`：底部面板由基于 Radix Dialog 的 `ResponsiveSheet` 实现（见 [§7.3](#73-schema-到控件的映射规则)）。

Tailwind v4 必须用 `@tailwindcss/vite` 插件，且版本不能低于 4.2.2：4.2.2 之前的 `@tailwindcss/vite` 的 peer 范围不包含 Vite 8，安装会报冲突。v4 没有 `tailwind.config.js`，所有设计令牌写在 CSS 的 `@theme` 块里，入口是 `@import "tailwindcss"`（v3 的 `@tailwind base/components/utilities` 三行在 v4 是错的）。

选 Tailwind 的核心原因是移动端需要大量非常规布局：安全区内边距、底部抽屉的把手区、日志行的密排版、设备截图的自适应容器。这些用原子类现场组合比覆盖组件库的 CSS 变量更直接。

shadcn/ui 不是 npm 依赖，而是用 CLI 把组件源码写进 `src/components/ui/`。这个模式对本项目是净收益：组件代码在仓库里，改一个控件的移动端表现不必和上游 API 抗争；底层是 Radix 原语，键盘导航、焦点陷阱、ARIA 属性已经做对，自己写这些是纯浪费。初始化用 `npx shadcn@latest init`（Tailwind v4 项目下 `components.json` 的 `tailwind.config` 留空，`tailwind.css` 指向 `src/index.css`）。M16 起组件层按 [§8](#8-移动优先的设计规范) 的设计令牌手写维护，不再使用 CLI 的 Drawer、Tabs、Select、Slider、Form 组件：弹层统一为 `ResponsiveSheet`，下拉用原生 `<select>`，数字用步进输入，理由见 [§7.3](#73-schema-到控件的映射规则)。

需要注意 shadcn CLI v4 开始支持 `--base radix | baseui` 两套原语，按决策表明确使用 Radix，初始化时显式指定，避免默认值变化导致组件 API 漂移。`toast` 组件已废弃，统一用 `sonner`。

`lucide-react` 是 shadcn/ui 的默认图标库，按需 tree-shake，不额外引入第二套图标。

### 3.3 路由与状态

| 包 | 版本 | 用途 |
|---|---|---|
| `react-router` | ^7.18 | 路由 |
| `@tanstack/react-query` | ^5.101 | 服务端状态 |
| `zustand` | ^5.0 | 本地状态 |

React Router v7 用 library 模式（`createBrowserRouter` + `RouterProvider`），不用它的 framework 模式：后者会引入自己的构建流程和服务端渲染约定，和「静态产物交给 FastAPI 托管」的部署形态冲突。从 v7 起 `react-router-dom` 只是对 `react-router` 的重导出，新代码直接依赖 `react-router`。

TanStack Query 负责一切来自后端的数据。它解决的是本项目里一个具体且高频的问题：同一份状态（流水线进度、设备连接态、内核版本）要在首页、任务页、更多页同时显示，还要被 WebSocket 推送更新。手写 `useEffect` + `useState` 的做法在旧前端已经能看到后果：`app.js` 里每个接口都重复一遍 `axios.then/catch/$notify`，共 7 处结构相同的样板，且没有任何缓存与去重。Query 的 `queryKey` 提供了一个天然的「按 key 精准失效」的入口，正好接 WebSocket 事件（见 [§9.5](#95-与-tanstack-query-缓存的协作)）。

Zustand 只用于确实不属于服务端的状态：token 与登录态、主题、待确认数量与全局面板开关、编排器的内存草稿、日志的内存环形缓冲。选它是因为不需要 action/reducer 的仪式感；也因为日志缓冲每秒可能更新几十次，Context 的整树重渲染会直接卡死长列表，而 Zustand 的选择器订阅只重渲染真正读了那块状态的组件。

### 3.4 表单与校验

原方案用 `react-hook-form` + `zod` + `@hookform/resolvers`，实施中没有引入（`web/package.json` 从未包含这三个包，M16 同步文档时更正）。

任务表单是本次重构技术难度最高的一块：11 种任务类型（M27 起加 `OperBox` / `Depot`，`OperBox` 已于 M47 随干员识别通道删除，见 [13 §8.70](./13-决策记录.md)）、单个类型最多三十多个参数、大量参数之间有依赖。实际做法是一套不依赖表单库的纯函数引擎（`features/tasks/form/`，见 [§7.5](#75-表单引擎schema-默认值与草稿物化)）：草稿在新建/复制/从模板加载时物化 schema 里的默认值（M17 起，见 §7.5），提交时序列化的就是这份草稿；一次只编辑一个任务（编辑器面板），不存在「同一页挂 5 个任务表单」的重渲染压力。客户端校验保持很轻：数字显示范围、步进结果夹在范围内，复杂结构的 JSON 必须能解析才写入；其余以服务端 422 为准并映射回字段（[§10.3](#103-错误状态码的前端处理)）。API 调试台的 JSON body 实时校验用 `ajv`（见 10 号文档）。

### 3.5 长列表与图表

| 包 | 版本 | 用途 |
|---|---|---|
| `@tanstack/react-virtual` | ^3.14 | 虚拟滚动 |
| `react-zoom-pan-pinch` | ^4.0 | 设备截图的捏合缩放（仍未引入，见下） |
| `echarts` | ^6.1 | 结构化图表卡（只经动态 import 加载） |

虚拟滚动在日志页是必需项。三路日志汇聚后，一次完整的日常流水线能产生上千行，其中夹杂 base64 截图。旧前端的 `v-for` 全量渲染在移动端会直接白屏。`@tanstack/react-virtual` 是 headless 的，只给 `useVirtualizer` 返回的位置计算，DOM 完全自己写，这对「日志行高度不固定、图片行明显更高」的场景是必要的（需要 `measureElement` 做动态测量）。

`react-zoom-pan-pinch` 用于首页设备截图的双指缩放与拖动（`TransformWrapper` / `TransformComponent`）。手写 pointer 事件处理双指手势、边界约束、惯性，是典型的「看起来简单做起来两周」的活。

图表用 ECharts 6.1（canvas），这条推翻了原方案的 recharts 倾向。原方案的取舍是「shadcn/ui 的 Chart 组件基于 recharts，主题令牌能直接复用」，但这个前提在本项目不成立：M23 起图表的主要形态是 agent 在会话里发的结构化图表卡（折线 / 柱状 / 饼图，见 [§6.4](#64-agent-agent)），要求可交互并跟随主题，这是用户的直接裁决（[13 §8.29](./13-决策记录.md)）；ECharts 的 canvas 渲染加按需注册，也让「只在真的出现图表时才付这份体积」成为可实现的路径。代价与随之而来的约束一起接下：

- 只经动态 import 进独立 chunk。`features/agent/chart/EChartSurface.tsx` 里对 `echarts/core`、`echarts/charts`、`echarts/components`、`echarts/renderers` 四路 `import()`：会话里真的出现图表卡才会加载；按需注册 `Line` / `Bar` / `Pie` + `Grid` / `Tooltip` / `Legend` / `Title` + `CanvasRenderer`，不引任何 React 包装库。
- 图表不写死颜色。新增主题色板 `--chart-1…--chart-6`（浅 / 深两套，见 [§8.2](#82-色彩令牌与主题)），运行时用 `getComputedStyle` 从 `:root` 读，并订阅主题变化后重建 option，暗色切换与「跟随系统」都不必各画一份颜色表。
- 如实记体积与预缓存。图表路径实际会拉到的 9 个 chunk 合计约 1.06 MB raw / 355 KB gzip，明显高于原估算（150–200 KB gzip），原因是 ECharts 6 的 `echarts/charts` chunk 会静态带上 `parseGeoJson` / `graphic` / `customGraphicKeyframeAnimation` 等（即使只注册三种图）。这些 chunk 没有任何静态引用，页面首屏不受影响；但 PWA 的预缓存会一并缓存它们（`injectManifest.globPatterns` 覆盖全部 `**/*.js`，见 [§11.2](#112-service-worker-缓存策略)）：「懒加载」对页面 JS 成立，对 Service Worker 预缓存不成立。要不要把这些 chunk 移出预缓存（换更小的安装体积，代价是首次看图表要联网）留待裁决。

实施现状：`react-zoom-pan-pinch` 仍未引入（设备画面与各类截图点开后由全屏查看器 `ImageViewer` 显示原图）；图表也没有走 recharts：`echarts@^6.1.0` 已随 M23 进入 `web/package.json` 的 `dependencies`，目前只被 agent 会话的图表卡使用，掉落统计页仍未做。

## 4. Vite 配置要点

```ts
// web/vite.config.ts
import path from 'node:path'
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'
import tailwindcss from '@tailwindcss/vite'
import { VitePWA } from 'vite-plugin-pwa'

const API_TARGET = process.env.MAA_API_TARGET ?? 'http://127.0.0.1:8002'

export default defineConfig({
  base: '/',
  resolve: {
    alias: { '@': path.resolve(import.meta.dirname, 'src') },
  },
  plugins: [react(), tailwindcss(), VitePWA({ /* 见 §11 */ })],

  server: {
    host: true,          // 监听 0.0.0.0，手机连同一 Wi-Fi 才能访问 dev server
    port: 5173,
    proxy: {
      // ws: true 让 /api/ws 的 Upgrade 请求也走同一条代理规则
      '/api': { target: API_TARGET, changeOrigin: true, ws: true },
      '/openapi.json': { target: API_TARGET, changeOrigin: true },
      '/docs': { target: API_TARGET, changeOrigin: true },
      '/redoc': { target: API_TARGET, changeOrigin: true },
    },
  },

  build: {
    outDir: path.resolve(import.meta.dirname, '../static'),
    emptyOutDir: true,   // outDir 在 root 之外，不显式置 true 则 Vite 拒绝清空
    sourcemap: true,
    rolldownOptions: {
      output: {
        entryFileNames: 'assets/[name]-[hash].js',
        chunkFileNames: 'assets/[name]-[hash].js',
        assetFileNames: 'assets/[name]-[hash][extname]',
      },
    },
  },
})
```

`base: '/'` 因为前端就挂在站点根路径。如果将来要挂到 `/app` 之类的前缀下，`base` 与 React Router 的 `basename`、PWA manifest 的 `scope`/`start_url`、Workbox 的 `navigateFallback` 四处必须同步改，所以现在不留这个口子。

`outDir` 与 `emptyOutDir`。`outDir` 指向仓库根的 `static/`，`emptyOutDir: true` 确保每次构建清掉上一轮的哈希文件（否则 `static/` 会无限堆积历史 chunk）。由于 `outDir` 在 Vite root 之外，不显式声明 `emptyOutDir` 时 Vite 会拒绝清空并打印警告，这是必须显式写的原因。旧前端遗留的 `favicon.ico`、`js/`、`css/` 需要一次性手工删除，新的静态资源放 `web/public/`。

dev server 代理。`'/api'` 规则加 `ws: true`，HTTP 请求与 `/api/ws` 的 WebSocket 升级共用一条规则，前端代码里 WebSocket 的 URL 写成相对路径（由 `location` 推导），开发与生产完全一致，不需要环境判断。`/openapi.json` 与 `/docs` 也要代理，否则 API 调试台在开发期拉不到契约。`MAA_API_TARGET` 环境变量留给「后端跑在另一台机器上」的调试场景。

产物命名与缓存策略。所有 JS/CSS/字体/图片带内容哈希落在 `assets/` 下，`index.html` 与 `sw.js` 不带哈希。对应的后端响应头策略（见 [§5.3](#53-缓存响应头)）是 `assets/*` 长期 immutable、`index.html` 与 `sw.js` 必须 `no-cache`。这个分工是 SPA 更新能生效的前提：浏览器每次导航都重新取 `index.html`，从里面读到新的哈希文件名，旧文件因为哈希不同不会被误用。

不加手动分包。原方案打算显式分组两块「大且非首屏必需」的依赖（CodeMirror 与图表库），实际两处都没有落地：`web/vite.config.ts` 里根本没有 `codeSplitting` 配置，`static/assets/` 下的 `JsonEditor-*.js`（API 调试台的编辑器，`LazyJsonEditor.tsx` 用 `lazy(() => import(...))`）与 `charts-*.js`（agent 图表卡的 ECharts，见 [§3.5](#35-长列表与图表)）都是 Rolldown 按动态 `import()` 边界自动切出来的 chunk。图表侧不补规则的理由很直接：`EChartSurface` 只在真的出现图表卡时才 `import()`，自动分包已经给出了想要的效果，再写一条 `test: /echarts|zrender/` 只是在依赖升级后多一个会静默失效的点。真要手工分组时，写法是 Vite 8 的 `codeSplitting.groups`，不是已被移除的 `manualChunks` 对象形式。

`sourcemap: true` 在生产构建也开。这是私有部署的内部工具，产物不公开，source map 换来的线上问题排查能力远大于几百 KB 的额外磁盘占用。若介意，改 `'hidden'`（生成文件但不在 JS 里引用）。

## 5. 后端托管配置变更

### 5.1 现状

```python
# maa_api/main.py（现状）
app.mount("/static", StaticFiles(directory=STATIC_PATH), name="static")
```

```python
# maa_api/router/template.py（现状）
@router.get("/", dependencies=[Depends(token_auth)])
async def index():
    return FileResponse(STATIC_PATH / "index.html")

@router.get("/daily", dependencies=[Depends(token_auth)])
async def daily():
    return FileResponse(STATIC_PATH / "daily.html")
```

这套「每个页面一条路由」的做法对 SPA 不成立：前端有十几个路径（`/tasks/schedules/new`、`/logs/core`、`/more/settings/device`…），且路径会随功能增加而变化，不可能在后端逐个登记。

### 5.2 新方案：`app.frontend()`

FastAPI 0.138.0 起提供了正好解决这件事的原语：

```python
# maa_api/main.py（新）
app = FastAPI(
    title="MAA-API",
    openapi_tags=OPENAPI_TAGS,     # 见 10 号文档
    lifespan=lifespan,
)

# 1. 先注册所有 API 路由与 WebSocket
for router in API_ROUTERS:
    app.include_router(router, prefix="/api")
app.include_router(ws_router)                  # /api/ws

# 2. 最后交出前端静态产物
app.frontend("/", directory=STATIC_PATH, fallback="index.html", check_dir=False)
```

需要把 `pyproject.toml` 里的 `fastapi = "^0.95.0"` 提到 `^0.138`。

`app.frontend()` 的语义解决了「catch-all 会吞掉一切」这个老问题，关键在于它不是一条注册在路由表里的 catch-all 路由，而是一个仅在所有正常路由都没匹配上之后才生效的兜底。由此得到三条我们需要的保证：

- `/api/*`、`/api/ws`、`/docs`、`/redoc`、`/openapi.json` 都是正常的 path operation 或 mount，优先级高于前端，不会被吞掉。即使 API 路由自己抛 404，返回的也是 API 的 JSON 错误体。
- `fallback="index.html"` 只对 `GET` / `HEAD` 且 `Accept` 头里显式包含 `text/html` 或 `application/xhtml+xml` 的请求生效，也就是浏览器的导航请求。缺失的 `.js` / `.css` / `.png` 仍然正常返回 404，不会拿到一份 HTML 导致「MIME type mismatch」这类难查的错误。
- `POST` / `PUT` 打到只能匹配前端兜底的路径时返回 404，不会被误当成页面请求。

因为注册顺序不影响优先级，写在最后只是为了阅读时一眼看出层次。`check_dir=False` 是必须的：`static/` 由前端构建生成，后端进程可能在前端还没构建时就创建了 app 对象（开发期尤其如此），默认的 `check_dir="auto"` 在非 development 环境会直接抛错。

`fallback` 的默认值是 `"auto"`（目录里有 `404.html` 就用它、否则用 `index.html`），对我们的 SPA 而言显式写 `"index.html"` 更清晰，也避免将来误放一个 `404.html` 导致客户端路由失效。

### 5.3 缓存响应头

`app.frontend()` 不负责按路径区分缓存策略，需要一个窄中间件补上：

```python
@app.middleware("http")
async def frontend_cache_headers(request: Request, call_next):
    response = await call_next(request)
    path = request.url.path
    if path.startswith("/assets/"):
        # 文件名带内容哈希，可以永久缓存
        response.headers["Cache-Control"] = "public, max-age=31536000, immutable"
    elif path == "/" or path.endswith((".html", "/sw.js", "/manifest.webmanifest")):
        # 入口与 Service Worker 必须每次校验，否则新版本永远发布不出去
        response.headers["Cache-Control"] = "no-cache"
    return response
```

`sw.js` 的 `no-cache` 是硬要求。浏览器对 Service Worker 脚本本身有更新检查机制，但如果 HTTP 层给了长缓存，更新检查会拿到缓存副本，导致用户长期停在旧版本外壳上。旧外壳引用的是已经被 `emptyOutDir` 删掉的哈希文件名，表现为白屏。

### 5.4 若后端锁在低版本 FastAPI

作为备选（不推荐，仅在无法升级 FastAPI 时使用），手写兜底路由。要点是：必须注册在所有 API 路由之后、必须显式排除保留前缀、必须做路径穿越校验、必须只对 HTML 导航请求返回 `index.html`。

```python
RESERVED_PREFIXES = ("/api", "/docs", "/redoc", "/openapi.json")
STATIC_ROOT = STATIC_PATH.resolve()

app.mount("/assets", StaticFiles(directory=STATIC_ROOT / "assets"), name="assets")

@app.get("/{spa_path:path}", include_in_schema=False)
async def spa_fallback(spa_path: str, request: Request):
    if request.url.path.startswith(RESERVED_PREFIXES):
        raise HTTPException(status_code=404)

    candidate = (STATIC_ROOT / spa_path).resolve()
    if candidate.is_relative_to(STATIC_ROOT) and candidate.is_file():
        return FileResponse(candidate)

    accept = request.headers.get("accept", "")
    if "text/html" not in accept and "application/xhtml+xml" not in accept:
        raise HTTPException(status_code=404)

    return FileResponse(STATIC_ROOT / "index.html", headers={"Cache-Control": "no-cache"})
```

`candidate.is_relative_to(STATIC_ROOT)` 这一行不能省。少了它，`GET /../../config.yaml` 就能读到仓库外的任意文件。这也是优先选用 `app.frontend()` 的一个理由：这类安全细节交给框架比自己写更可靠。

### 5.5 前端页面是否需要鉴权

旧方案在 `/` 和 `/daily` 上挂了 `Depends(token_auth)`，这对 SPA 是错的设计：应用外壳本身不含任何敏感数据，把它锁住只会让「打开页面 → 输入 token」这个正常流程变成「必须先在 URL 上带 token 才能看到输入 token 的界面」，正是旧前端 `getToken()` 从 query string 读取、每个跳转都要手工拼 `?token=` 的根源。

新方案：`index.html` 与 `assets/*` 公开，所有 `/api/*` 鉴权。未登录用户能拿到外壳，外壳发现没有 token 就渲染 token 录入页。数据一行都拿不到。鉴权细节见 [§10](#10-鉴权在前端的处理)。

移动端一屏内要回答「现在能不能用、正在干什么、有没有事等我」。首页只呈现「此刻」，自上而下五块；桌面分两列，左列是前四块，右列是设备画面。

待确认横幅。有待确认项时显示「N 项操作等待你确认」，点开全局待确认面板（[§6.6](#66-全局待确认)）。确认有超时且超时自动拒绝（消耗类与破坏类默认 10 分钟，原子操作会话授权 120 秒，见 [§13.2](#132-确认超时与推送触达的矛盾)），所以横幅放在最上面。首页的标题栏不再重复显示待确认入口。

当前任务。标题、状态、进度条（`role="progressbar"`，按已完成数 / 总数）与正在执行的步骤；「全部步骤」可展开看每步的名称、耗时与状态。运行中可「停止任务」（确认后 `DELETE /api/pipelines/{id}`），「查看详情」进入流水线详情页。数据来源 `GET /api/pipelines/current`（无运行中时返回 `{"pipeline": null}`，不是 404，前端据此渲染空态而不必把 404 当正常情况处理），由 `pipeline_status` 与 `task_status` 事件驱动更新。

快捷操作。两块磁贴：「新建任务」进入 `/tasks`；「运行定时任务」打开面板，列出定时任务与时间摘要，确认后 `POST /api/schedules/{id}/run`。

运行状态。一个列表组，设备、内核、服务、队列各一行，行内直接显示状态（圆点 + 文字）与关键信息：设备地址、重试进度与最近错误（见 [08-ADB连接与账号渠道](./08-ADB连接与账号渠道.md)）；内核状态（`stopped` / `starting` / `ready` / `crashed` / `restarting` / `failed`，对应 [02 §4](./02-系统架构设计.md) 的状态机）、PID 与世代；服务版本与运行时长；队列的待处理与运行中计数，点这一行进入 `/tasks/queue`。设备断开或不可用时列表下方出现提示与「重新连接设备」（`POST /api/device/reconnect`）；health 读取失败时显示错误与「重试连接」。几层分开展示，因为它们的故障处置动作完全不同：内核 `crashed` 要看崩溃原因、设备断开要点重连、服务异常要看日志。M16 计划里它是「状态芯片 + 详情面板」，实施时改为行内列表：少一次点击，信息不缺。数据来源 `GET /api/system/health`，由 WebSocket 的 `core_status` / `device_status` 事件推送更新，不轮询。

`GET /api/system/health` 是免鉴权端点（[05 §6.1](./05-API规范与路由清单.md)），且返回 `auth_enabled`。前端因此可以在用户还没输入 token 时就拿到它，用于两件事：判断这个实例是否开启了鉴权（未开启就跳过登录页直接进应用），以及在 token 无效时仍能显示「服务是活着的，只是你没登录」。

设备画面。16:9 卡片，右上角是刷新按钮，点图片全屏查看。数据来源 `GET /api/device/screenshot?backend=adb&format=jpeg&size=mobile`（[05 §6.3](./05-API规范与路由清单.md)），不归档。刷新策略：流水线运行中每 5 秒自动刷新，空闲时只手动刷新。这比旧前端「进页面截一次、之后全靠手点刷新」实用，也比无条件高频轮询省电。

### 6.2 任务 `/tasks`

四个子视图共用标题栏下吸顶的分段导航（新建 / 队列 / 历史 / 定时），不占 Tab 位；切换写入浏览器历史，可前进后退。新建、队列、历史是三条平级路由，指向同一个懒加载页面、按路径决定视图；流水线详情与定时任务编辑器是子页面，不显示分段导航。定时任务并入任务区是用户在 M16 的决定（[13 §8.12](./13-决策记录.md)）：它提交的同样是流水线，编辑器复用编排器的任务列表，编排器的「存为定时」也能直接跳过去。

新建（编排器）`/tasks`。12 种任务类型的 schema 驱动编辑，完整方案见 [§7](#7-任务表单的-schema-驱动生成)。顶部是可选的流水线名称。任务列表每个任务一行：类型图标、中文名、参数摘要（从与默认值不同的字段生成，如「1-7 · 理智药 2」；全默认显示「使用默认参数」）与错误角标；点整行打开任务编辑器（手机全屏、桌面右侧面板），行右侧的「更多操作」提供上移、下移、复制、删除（删除需确认）。MAA 的任务链顺序有语义（`StartUp` 必须在前、`CloseDown` 必须在后），所以顺序必须能调；原方案的拖拽没有采用，改为上移 / 下移。「添加任务」打开类型面板：12 种任务类型各带图标与一句说明，点选即加入并直接打开编辑器，上限 32 个。编排中的草稿存在内存 store 里，切到队列再回来不会丢。底部吸附操作栏：主按钮「开始执行（N 项）」，次按钮「存为定时」。

提交先 `POST /api/tasks/validate`，通过后 `POST /api/pipelines`（带 `Idempotency-Key`）。有 `x-risk` 字段被改动时先弹确认，逐行列出消耗项；422 的字段错误落到对应任务行的角标与编辑器里的字段，就地提示「第 N 个任务有 K 处错误」并可一键打开出错的任务；504 时查询 `/api/pipelines/current`，重试复用同一个 key。成功后 toast，并就地提供「查看队列」。「存为定时」跳到 `/tasks/schedules/new`，通过 `location.state.composerPrefill = { name, template }` 带上名称与任务模板（形状同 `POST /api/pipelines` 的 `tasks`），不做 validate 与风险确认，编排器保留自己的草稿。

队列 `/tasks/queue`。顶部状态行显示运行中与待执行计数，以及「暂停队列 / 恢复队列」。当前运行项置顶（标题、来源、开始时间），可「停止」（确认）。待执行列表按服务端顺序列出标题、来源、优先级（「0（最高）」「1（普通）」「2（最低）」，对应前端手动 / agent / 定时，见 [02 §5.1](./02-系统架构设计.md)）与状态，点行进入详情；行内「更多操作」有「取消」与「停止当前并执行此条」。因为决策是「不抢占」，插队必须是显式动作：先 `PATCH /api/queue/{id}` 把目标优先级设为 0，再取消当前流水线；确认文案写明当前流水线会被取消，且不能保证目标紧接着执行。这正是 02 号文档要求的「明确的按钮，不是隐式行为」。「刷新队列」与「清空待执行」（确认框写明条数）在待执行区块的标题行。队列每 5 秒轮询。

历史 `/tasks/history`。列表行显示状态、标题、开始时间、耗时与任务数，底部「加载更多」，点行进入详情页。数据来源 `GET /api/pipelines?page=&size=`，用 `useInfiniteQuery`，依据 `{items, total, page, size}` 信封里的 `total` 判断是否还有下一页（[05 §3.2](./05-API规范与路由清单.md) 规定分页参数固定为 `page` 从 1 开始、`size` 默认 20 上限 200，越界返回 `400 INVALID_PAGINATION` 而不静默钳制，所以前端不能盲目递增页码，必须按 `total` 停止）。列表接口不带任务明细，所以无标题的流水线不逐条读详情取任务名：定时任务触发的显示定时任务名（复用共享的定时列表查询，一次请求），其余显示「来源 + 任务数」（如「手动任务 · 3 项」）；详情页再用任务名组合。

流水线详情 `/tasks/history/:pipelineId`。概要（状态、优先级、来源、创建 / 开始 / 结束时间、错误）、每个任务的结果、关联日志（最近 100 条，可跳到日志页）、截图网格（进入视野才加载，点开全屏）；运行中或等待中每 5 秒刷新。底部操作栏：运行中或等待中可「取消」，失败或已取消可「重试」，重试成功后以 `replace` 跳到新流水线的详情。深链直接打开详情，不要求该流水线在历史列表的当前页。

定时 `/tasks/schedules`。列表行：名称、启用开关（行内直接 `PATCH {enabled}`，失败回滚并就地说明）、时间摘要（如「周一至周五 04:00」，无法可视化时显示原始 cron）、下次执行、最近结果（含 skipped 与错误）、任务数；行内「更多操作」有「立即运行」「编辑」「删除」，运行与删除需确认。旧 `daily_task.json` 的迁移说明收在列表下方。编辑器是整页（`/tasks/schedules/new`、`/tasks/schedules/:scheduleId`）：名称；星期芯片（一至日，另有「每天」「工作日」「周末」快捷选择）；时间（原生 `type="time"`）；「高级」折叠区里的时区；无法可视化的 cron 显示为原始表达式输入框并说明将原样保存，可「改为按星期设置」；任务列表复用编排器组件；底部操作栏「保存」（新建 `POST`、编辑 `PUT`）；页面菜单「立即运行」「删除」。原来写死为 2 的优先级控件去掉了，改为一行说明「定时任务以最低优先级排队」。409 名称冲突时就地标出名称框，编辑器保持打开；有未保存改动时离开会被拦截。星期 + 时间与 POSIX cron 的互转沿用 `schedule-time.ts`，模板按白名单序列化（Copilot 只保留 `asset_id` 与 `formation`，不带作业内容），见 [§15.4](#154-按星期配置的任务组合)。

### 6.3 日志 `/logs`

来源用吸顶工具条上的分段控件切换：全部、任务、服务、核心，分别对应 `/logs`、`/logs/task`（MaaCore 回调任务日志）、`/logs/service`（Python 服务日志，含 uvicorn）、`/logs/core`（MaaCore 自身 debug 日志），即 [06-实时日志与WebSocket](./06-实时日志与WebSocket.md) 定义的三路汇聚。工具条上还有搜索框与「筛选」按钮（有生效条件时显示数量）。筛选面板里是级别多选芯片（全部、DEBUG、INFO、WARNING、ERROR、CRITICAL）与时间范围（「最近 15 分钟」「最近 1 小时」「今天」或自定义起止），改动立即生效；生效的条件以芯片显示在工具条下方，可逐个移除或「清除全部」。列表占满剩余高度，页面本身不滚动，只有列表滚动。

取数是双通道的。历史走 `GET /api/system/logs` 的游标分页，最新优先（`order=desc`，每页 100 条），滚到顶部或点「加载更早日志」时带 `before_id` 读更早的一页；关键词防抖后作为 `q`、时间范围作为 `since` / `until` 交给服务端。来源与级别不进 REST 查询，在本地过滤，多个级别之间是「或」。实时部分走 WebSocket 推送，追加到 `stores/log-buffer.ts` 的环形缓冲，与历史按 `id` 合并去重。环形缓冲每路上限 2000 行，超出丢弃最早的，否则挂机一夜后内存会被日志吃光。日志订阅只在日志页挂载期间开启，卸载时关闭。

日志端点是全项目唯一支持游标的地方：[05 §3.2](./05-API规范与路由清单.md) 规定 `after_id` / `before_id` 游标与 `page` 互斥，同时传两者返回 `400 INVALID_PAGINATION`。日志页只用游标，不要顺手带上 `page`。

补漏与截断。页面记住上次看到的日志 id，再次进入时用 `after_id` 升序补读期间漏掉的记录。实时连接报告历史被截断时，列表里出现「加载缺失历史日志」按钮，用 after / before 两个边界补齐缺口（[§9.4](#94-断线期间的消息补偿)）。

自动吸底要有条件。只有当用户已经在底部附近（距底部不超过 48px）时才自动跟随最新，否则保持位置，并在底部显示「N 条新日志」胶囊；离开底部但没有新日志时显示「回到底部」。无条件吸底会让「往上翻看刚才那条报错」变成不可能。来源、级别、关键词或时间范围一变，列表回到最新一条，新日志计数清零。

行与截图。每行是等宽时间、级别色条与级别文字、来源、两行截断的内容；点行展开全文、完整时间与记录器，并可「复制」。带截图的行显示缩略图（`<img loading="lazy">`，地址限定为本服务的 `/api/images/<sha256>/thumb`），点开全屏查看器再加载 `/full` 原图。旧前端把完整 base64 塞进 JSON 响应，一条日志几百 KB，这是它在移动端不可用的主因之一。长列表用 `@tanstack/react-virtual` 虚拟滚动。

### 6.4 Agent `/agent`

手机上是全高对话，桌面是左侧会话栏 + 右侧对话区。当前会话用 `?session_id=` 表示，没有 `/agent/:sessionId` 这样的路径。标题栏显示当前会话标题，右侧是「会话列表」按钮（手机上打开会话面板）与「Agent 操作」菜单（检查模型能力、新建会话）。会话列表每行显示标题、自动诊断徽章、消息数、模型与更新时间，删除收在行内「更多操作」里并需确认。当前会话的模型与 token 累计显示在对话顶部。

流式输出。回复经 SSE 增量推送（协议见 [11-Agent模块设计 §8.2](./11-Agent模块设计.md)），文字与工具调用按到达顺序显示在「本轮」里。流结束后等历史刷新完成再丢弃这份实时副本，避免同一轮显示两次（[13 §8.7](./13-决策记录.md)）。

工具调用轨迹。每次 tool call 渲染为可折叠的紧凑条：中文动作名与工具原名、状态（执行中、等待确认、已完成、失败）、展开后的参数与结果 JSON；历史里的调用与它的结果合成一条。这是 agent 模块最重要的可观测性：出错时用户需要看到「它到底调了什么」。

媒体卡（M23）。Agent 从此可以把画面与数据直接发给用户：工具结果里的 `media[]` 渲染成四型卡片：图片（agent 截的图、任务历史与日志里的既有截图、服务端加工后的图）、物品图标（一格里一张材料图标）、关卡示意图（本地 tile 数据画的网格，起点 / 终点与图例单独标注）、图表（折线 / 柱状 / 饼图，ECharts canvas，可交互并跟随主题）。卡片挂在 tool 消息上，实时（SSE `tool_result`）与刷新后（历史消息）走同一条渲染路径，没有新表也没有新端点。四条渲染纪律：

- 卡片渲染在工具条的折叠区之外。工具条默认是收起的紧凑条，卡片放进 `<details>` 里就等于看不见；`ToolCallBar` 在 `<details>` 之前渲染 `MediaCards`，展开工具条只是看参数与结果 JSON。
- 大图走既有 `ImageViewer`。缩略图懒加载，点开才取原图，在全屏查看器里看，不新做一套看图组件。预览按缩略图的自然尺寸显示（`w-fit` + 长边 320 px，与后端 `_THUMBNAIL_EDGE` 对齐，窄屏仍自适应），不拉满卡片宽度：把 320 px 的缩略图铺到 600+ px 等于放大数倍，视网膜屏上就是糊的（收尾修复的经过见 [13 §8.29](./13-决策记录.md)）；卡片下方也不再显示原图尺寸。
- 取图统一走 `api` 客户端（`X-Token`）拿 blob，不依赖 cookie。共用 hook 是 `components/ui/use-authed-image.ts`：`IntersectionObserver` 懒加载、取到 blob 后 `URL.createObjectURL`、卸载或换图时 `revokeObjectURL`。流水线详情的 `PipelineScreenshots` 也改用这同一支 hook，行为不变；它和媒体卡都不能退回裸 `<img src>`（那只能靠 cookie，见 [§10.4](#104-websocket-与图片的特殊处理)）。前端只认三种同源图片地址（`/api/images/<sha256>/(thumb|full)`、`/api/screenshots/<id>`、`/api/resources/items/icon?item_id=`），外域与 `data:` 一概丢卡。
- `get_screenshot` 的图不是卡片，是工具卡内的附件（M23 收尾）。只有五个 `send_*` 工具产生会话级媒体卡；agent 自己观察画面用的 `get_screenshot` 结果由 `media.ts` 的 `toolScreenshotAttachment()` 从 `screenshot_id` / `sha256` / `thumb_url` / `full_url` 解析成附件，渲染在该次工具调用 `<details>` 展开区里的「附件」一节（缩略图 + 点击看原图），因此连续截图不会在会话里刷屏。只有用户明确要求看画面时才由 `send_screenshot` / `annotate_screenshot` 发到会话里（口径见 [11 §5.5](./11-Agent模块设计.md)、[13 §8.29](./13-决策记录.md)）。
- 图表的「数据」折叠表永远在。它是无障碍路径（读屏与键盘用户拿到的是一张真表格，列是系列、行是类目、带 `scope`），也是 ECharts chunk 加载失败时的兜底：加载失败时该表自动展开并提示「图表加载失败，已改用数据表」。图表永远不是唯一的信息来源。

确认、授权与输入。等待确认时对话内出现确认卡（批准并继续 / 拒绝）；会话授权条随标题栏吸顶，显示剩余时间与「撤销」。**作业授权卡（M29）**：`action=grant_copilot_attempts` 的确认卡换成专用视图——尝试次数（1–10 的下拉，默认 3）、成功标准（三星 / 通关，默认三星）、是否允许助战补位（开关，默认允许）三项可改，**有效期只展示**（由 `payload.window_seconds` 或 `window_minutes` 换算成分钟，缺失时写「服务端配置的时长」）；批准时这三项作为 `overrides` 随 `POST /api/confirmations/{id}` 一起提交，拒绝不带。**作业授权条**与屏幕操作授权条并列吸顶，显示授权的关卡、剩余次数（`剩余 n/m 次`）、剩余时间与「撤销」（`DELETE /api/agent/sessions/{id}/copilot-grant`）；数据来自会话详情的 `copilot_grant`（与 `atomic_grant` 并列），WS 的 `copilot_grant_changed` 只用来失效会话详情查询。输入栏固定在底部，随内容增高（约 6 行封顶），通过 `visualViewport` 避让虚拟键盘；桌面 Enter 发送、Shift+Enter 换行，触屏设备 Enter 换行、用发送按钮发送。

提问卡（M21）。Agent 需要用户在若干候选之间裁决时（走哪个渠道、刷哪个关卡、次数与吃药策略）不再写在正文里等用户打字回复，而是发一张选择卡，本轮挂起等答案：

- 本轮卡。固定渲染在本轮的工具条下方，附着在触发它的那次 `ask_user` 调用上。选项形态由工具参数的 `multiple` 决定：单选是一组互斥按钮（再点一次可取消选择），多选可以勾多项；没有选中时「提交」保持禁用，另有「跳过」。卡片按后端的 `expires_at` 每秒倒计时，到期后整卡禁用并显示「提问已超时，本轮已结束」。倒计时读的是落库的过期时刻，刷新或切页回来重算仍然对得上；时间戳缺失或读不出来时不做本地超时，终态交给后端（宁可晚一点结束，也不要凭坏时间戳禁掉一张还能答的卡）。提交或跳过成功后立刻清掉本轮卡，后端接着推 `tool_result` 与后续文本，同一轮继续往下跑；跳过与超时则本轮结束（收尾文案由后端的 `text_delta` 给出，前端不自己拼）。提问卡也纳入「保留本轮」的收尾条件：SSE 中途断开时这一轮不会连同还能答的卡片一起被丢掉。
- 本会话待答卡。刷新页面或切走再回来时，未回答的提问仍然在：`GET /api/agent/questions?session_id=…&status=pending`（10 秒轮询，与 pending confirmations 同节奏）拿本会话的待答列表，渲染在本轮之后。已在本轮展示过的 `question_id` 不重复渲染，去重与确认卡是同一套判断。在别处已经答掉或已不存在的提问（`409` / `404`）就地转成「这次提问已经结束」，不弹红错，重试没有意义。
- 多标签页同步。WS 的 `question_request` / `question_resolved` 只用来失效待答查询（沿用 query-bridge，与确认的 `confirm_request` / `confirm_resolved` 同一口径，协议见 [06 §7.3](./06-实时日志与WebSocket.md#73-服务端推送消息)），因此一个标签页答掉之后，另一个标签页的待答卡随之消失；重连后的 `subscribed` 也失效一次，补上断线期间漏掉的终态。
- 输入栏状态行。等待提问时显示「请先回答上方的问题」。三种状态并存的优先级是确认 > 提问 > 「Agent 正在处理…」：确认挡住的是一次真实操作，先处理它。
- 边界：不进全局面板、不进标题栏胶囊。提问没有风险等级、不授权任何操作（[11-Agent模块设计 §5.3](./11-Agent模块设计.md)），把它算进「N 项待确认」会让这个数字失去意义，也不为它做 Web Push 与深链。它只在本会话的对话页内可见，详见 [§6.6](#66-全局待确认) 的对照。

停止本轮（M22）。流式期间发送按钮原地变成「停止本轮」（`CircleStop`、`destructive-soft`，`aria-label="停止本轮"`）：点击后按钮进入 stopping 态（spinner + 禁用，标题「正在停止本轮…」），请求 `POST /api/agent/sessions/{id}/interrupt`，成功后本轮立刻收尾、输入栏恢复可用，不必等连接关闭。刷新或切页回来、本地已经没有流式副本时，只要会话详情的 `turn_running` 为真，状态行显示「本轮仍在后台执行」并给出同一个停止按钮：会话详情查询在 Agent 页开着时按 10 秒轮询（与待确认、待答同节奏），所以换标签页或换设备停掉的那一轮也能在 10 秒内反映到本页。状态行的优先级因此是：正在停止本轮 > 本轮运行中（确认 > 提问 > 处理中）> 本轮已停止 > 本轮仍在后台执行 > 正在提交确认。发送被 409 挡下时文案是「该会话仍有一轮在跑，可先停止它」；`turn_running` 为真时发送按钮本身就保持停止形态（此时发送必然吃 409，先给停止入口）。SSE 的 `interrupted` 事件把本轮标记为已中断（撤下挂起的确认卡与提问卡，不当错误弹出），随后的 `message_end` 直接把本轮置为结束，状态行与输入栏不必再等连接关闭。

停止是主动动作，被动断开仍旧不取消本轮。只有点这个按钮（或直接调中断端点）才会取消本轮：断网、关页面、切标签页造成的 SSE 被动断开不取消后端正在执行的那一轮，它会继续跑完；这一点与 M16 的既定语义一致（[11-Agent模块设计 §8.5](./11-Agent模块设计.md#85-对话界面m16)），两条路径在测试里显式区分。中断也不碰流水线与队列（要停在跑的流水线仍走显式的停止入口），而已经批准并已在执行的工具可能已经产生副作用且无法回滚：界面只把它的工具条显示为「未返回结果」，不做「已回滚」的暗示。

会话历史。落 SQLite（决策表），包含多轮历史、工具调用轨迹、token 消耗。消息先读第一页拿到 `total`，再读最后一页（每页 200 条）；点对话顶部的「加载更早的消息」读前一页，插入后保持阅读位置。界面细节与取舍见 [11-Agent模块设计 §8.5](./11-Agent模块设计.md)。

### 6.5 更多 `/more`

一个分组列表页：运维（热更新、Agent 审计、API 调试台）、系统（设置）、外观（浅色 / 深色 / 跟随系统的分段控件）、账户（「退出登录」，确认后执行，见 [§10.1](#101-token-的录入与存储)）、关于（服务版本、实时连接状态）；非安全上下文时底部附一条说明（[§12.4](#124-部署路径)）。M16 把主题切换与退出登录从全局顶栏移到「更多」页，标题栏只留标题与页面操作。桌面上这些次级入口同时直接列在侧边栏里。「更多」不做二级 Tab，就是一个朴素的分组列表：移动端的设置类入口用列表比用宫格好找。

设置拆成索引与分区。索引是 iOS 式分组列表：「此设备」下是外观、访问令牌，「服务」下是设备与渠道、LLM 与 Agent、Agent 知识库、通知、更新与日志、应用与部署；「其他」只在 schema 出现未映射的分组时列出。服务端分区由设置 schema 驱动，与 schema `group` 的映射是：`设备`、`渠道` → `device`；`LLM`、`Agent` → `agent`；`更新`、`日志` → `maintenance`；`应用`、`部署` → `system`；未知分组 → `other`。`appearance`（主题）与 `access`（替换或清除本机 token）是纯前端分区；`notifications` 包含 Web 推送与通知通道（通道按类型填写表单，保留「以 JSON 编辑」）；`agent` 分区顶部是「检查模型能力」。字段下方小字标注生效方式（立即生效 / 保存后重连设备 / 需重启服务）与来源（默认值 / 配置文件 / 数据库覆盖），不显示原始 key。每个分区独立保存（只提交改动过且非只读的字段），「恢复默认」确认后清除本分区的数据库覆盖，有未保存改动时离开会被拦截。

「Agent 知识库」分区（M18，M20 去掉上限）。路径 `/more/settings/knowledge`，排在「LLM 与 Agent」之后，scope 为 server，但不走设置 schema（内容是条目，不是键值对），用专用组件实现：列表按类型（`playbook`、`screen`、`rule`、`glossary`、`profile`）分组，每行显示标题、id、来源徽标（内置 / 已修改 / 自定义，由接口的 `source` + `modified` 推出）与启用开关（切换即发 `PUT`），顶部是「新建」；页脚只报「已启用 N 条 · 术语表与用户档案正文合计 M 字」，不带分母（[13 §8.25](./13-决策记录.md)：不设自设上限）。编辑页是整页（`/more/settings/knowledge/new`、`/more/settings/knowledge/:entryId`），形态与定时任务编辑器相同，字段依次为标识（仅新建时可填）、类型（内置条目不可改）、标题、什么时候用、正文（等宽字体、随内容增高）、启用；页面显示各字段的字数与上限（`title` 32 字、`when_to_use` 120 字、`body` 20,000 字，那是列宽约束），并预览这条在索引里的样子（`- <id>｜<title>：<when_to_use>`）。已修改的内置条目提供「恢复默认」、自定义条目提供「删除」，都要二次确认（`DELETE`）；后端返回 `409 KNOWLEDGE_BUILTIN_READONLY` 或 `422` 时就地给出可读文案。移动优先，遵循 §8。

**森空岛绑定与练度同步卡片（M42，取代 M36 的练度扫描卡片）**。干员页识别状态条旁一张卡（**2026-10-14 起桌面端与状态条双列并排、移动端堆叠；标题行由 `Section` 换成自绘 `h2` + `InfoHint`**），三种形态：**未绑定**显示二维码（后端零依赖编码器出的内联 SVG，`<img src="data:image/svg+xml;…">`，不走 `dangerouslySetInnerHTML`）＋剩余有效期倒计时＋按响应的 `poll_interval_ms` 轮询 `GET /api/skland/login/qrcode/{session_id}`（四态：等待扫码 / 成功 / 已失效 / 失败），另有「手动输入 cred」抽屉做兜底；`key_configured=false` 时不画码，直接提示先在 `config.yaml` 配 `skland.credential_key`。**已绑定**显示账号昵称与角色、上次同步时间与摘要，按钮「同步练度」走 `POST /api/skland/sync`（同步执行、按钮 loading，几秒返回）与「解绑」（二次确认）。练度写入后每个字段的来源标成 `skland`（卡片上就是那枚「森空岛」徽章），**M47 起这是账号干员数据的唯一写入路径**。卡片不再占设备、不再有全量扫描与身份计数（M39/M40 的两颗按钮与 `screens`/`realigned`/`unverified` 随扫描线退役），口径见 [13 §8.61](./13-决策记录.md)、[13 §8.62](./13-决策记录.md)。

「作业」页（M29，规格 §9.10、Q49）。入口在「更多」（桌面侧边栏同样直接列出），路径 `/more/copilots`，主导航保持 5 项。顶部是搜索框（标题 / 关卡 / 说明，300 ms 防抖；服务端在 `name`、`description` 与 `meta` 的 JSON 里匹配）与来源筛选（全部 / 用户上传 / 作业站 / AI 生成，在已取回的列表里筛——列表端点只支持 `q`），列表分页加载（每页 50 份，端点按资源 `name` 升序返回，不做按时间的排序；行内显示创建时间与跑过几次）。每行显示：标题、来源徽标、关卡（代号或 `stage_name`）、是否「已保留」、创建时间与跑过几次、**版本链**（沿 `parent_id` 还原，父版本不在已取回的页里时显示「不在本页 · <短 id>」占位，不假装它是第一版）、以及每个版本的**尝试结果徽标**（结果 + 判定方，「模型判定」加粗、不计次的标「（不计次）」，`title` 里给时间与证据）。操作有四个：查看 JSON（详情端点按需取，等宽字体只读面板）、下载（浏览器下载作业 JSON 文件）、保留 / 取消保留（写 `meta.retain`，被保留的不会被每日清理删掉）、删除（二次确认）。作业站来源的行在末尾给「作业站原帖」外链（`https://prts.maa.plus/copilot/<id>`，只对 `SOURCE_LINK_HOSTS` 里的主机生成外链），行内给出的 `siteId` 在链接不可用时退成纯文字。页面上另有一句说明：成功的作业与自己上传的不会被自动清理，AI 生成的失败草稿 7 天后会被清理，想留下就点「保留」——与后端的五条清理条件同一口径（[13 §8.44](./13-决策记录.md) 九）。

### 6.6 全局待确认

待确认面板挂在外壳上（`features/confirmations/ConfirmationDock.tsx`），任何页面都能打开：

- 入口。首页以外的页面，有待确认项时标题栏右侧出现「N 项待确认」胶囊；首页用横幅代替（§6.1）。没有待确认项时不显示入口。数量由外壳里的 Dock 查询后写入 `stores/confirmations-ui.ts`，标题栏与首页只读这个 store，页面单独渲染时不会多发请求；未登录时 Dock 不发请求，避免 401 触发全局登出流程。
- 面板。手机上从底部升起，桌面是居中对话框。每条确认显示标题（工具名，或「授权会话操作游戏界面」）、触发原因、由载荷 `expires_at` 本地计算的倒计时（到期显示「已过期」并禁用按钮）、调用方、可折叠的「查看操作参数」JSON，以及「批准」「拒绝」（`POST /api/confirmations/{id}` 传 `{approved}`）。会话授权类另外显示目标会话与授权时长。最后一条处理完后面板自动收起。
- 深链。任何路由上的 `?confirm=<id>` 都会自动打开面板，高亮并滚动到该条；处置后或关闭面板时清掉参数；目标已处理或已过期时提示一次「这条待确认操作已经处理或已过期」。这个格式由后端推送与 Service Worker 写死（[§13.1](#131-人工确认的触达设计)）。
- 竞态。处置返回 409 时提示已处理并刷新列表；WS 的 `confirm_request`、`confirm_resolved`、`subscribed` 都会触发重新读取（沿用 query-bridge）。

Agent 页另有对话内的确认卡，只列出本会话的待确认项，见 [11-Agent模块设计 §5.2](./11-Agent模块设计.md)。

提问（`agent_question`）不进这个面板。它不是确认：没有风险等级、不授权任何操作，因此既不进这个面板、也不进标题栏胶囊，更没有 Web Push 与深链（[11 §5.3](./11-Agent模块设计.md)）。提问卡只出现在对话页本会话范围内，见 [§6.4](#64-agent-agent)。把它算进「N 项待确认」会让这个数字失去意义：用户点开面板看到的会是一张没有风险、批准了也不发生任何事的卡。

## 7. 任务表单的 schema 驱动生成

### 7.1 为什么必须 schema 驱动

旧前端在 `index.html` 里把 7 种任务的表单写了两遍（一遍只读展示、一遍可编辑创建），`daily.html` 里又写了第三遍。三份副本已经漂移：`index.html` 的 `Infrast` 只读视图缺了「无人机用途」和「源石碎片自动补货」两个字段，而创建视图和 `daily.html` 里有。更根本的问题是 `task.py` 里定义的参数远多于表单暴露的：`Fight` 有 13 个参数，表单只有 4 个；`Roguelike` 与 `Reclamation` 两种任务类型压根没有表单。

结论：表单必须由后端的参数定义单点生成。后端加一个参数，前端自动出现一个控件。

### 7.2 schema 契约

契约由 [05 §8](./05-API规范与路由清单.md) 定义，前端不要自己发明一套描述符格式。要点是：返回的不是自定义的参数数组，而是 Pydantic 直出的标准 JSON Schema，中文元信息挂在 `x-` 前缀的自定义关键字上（JSON Schema 规范要求校验器忽略未知关键字，所以 schema 仍然能直接喂给任何标准校验器）。

```jsonc
{
  "items": [
    {
      "name": "Fight",
      "label": "刷理智",
      "description": "刷指定关卡，支持理智药与碎石",
      "runtime_immutable": ["stage"],
      "groups": ["基础", "资源消耗", "账号", "数据上报", "高级"],
      "schema": {
        "type": "object",
        "properties": {
          "series": {
            "anyOf": [{ "type": "integer", "maximum": 6, "minimum": -1 }, { "type": "null" }],
            "default": null,
            "description": "连战次数。-1 禁用切换，0 自动选择最大可用次数",
            "x-label": "连战次数",
            "x-group": "基础",
            "x-widget": "select",
            "x-enum-labels": { "-1": "禁用切换", "0": "自动选择最大可用次数", "1": "1 次" }
          },
          "expedite_times": {
            "type": "integer",
            "x-label": "加急次数",
            "x-depends-on": { "expedite": true }
          }
        },
        "additionalProperties": false
      }
    }
  ],
  "total": 12, "page": 1, "size": 12
}
```

前端消费这份 schema 时有四个必须处理对的细节。

`anyOf: [{...}, {"type": "null"}]` 是可选字段的常规形态，不是特例。Pydantic 对 `int | None` 就是这么导出的。渲染前先做一次归一化：从 `anyOf` / `oneOf` 里剔掉 `{"type": "null"}` 分支，记下 `nullable: true`，再用剩下的唯一分支去查控件映射表。如果剔完还剩多个分支（真正的联合类型），退化为只读 JSON 编辑器并在开发环境打警告。目前 `task.py` 没有这种字段，但留个兜底比运行时白屏好。

`runtime_immutable` 是类型级的字段名数组（如 `["stage"]`），对应 `task.py` 文档字符串里反复出现的「不支持运行中设置」。编辑一个正在运行的流水线时，名字在这个数组里的控件置灰并给出提示。

`groups` 是有序的中文字符串数组，直接作为折叠面板的分区标题，字段靠自己的 `x-group` 归位。顺序即渲染顺序，前端不要重排。没有 `x-group` 的字段归入最后一个分区。`Fight` 有 13 个参数，`Roguelike` 在 M28 对齐上游 v6.18.0 后有 36 个，不分组平铺在手机上完全不可用，所以分组是必需的。

`x-enum-labels` 处理「数值有特殊语义」的情况。`series` 的 `-1` 是禁用、`0` 是自动，不是「比 1 小的次数」。注意它的 key 在 JSON 里必然是字符串（JSON 对象的 key 只能是字符串），而字段值是整数，查表时要 `String(value)`。

取值范围走 JSON Schema 原生关键字（`minimum` / `maximum` 来自 `ge` / `le`，`enum` 来自 `Literal`，`minItems` / `maxItems`），前端直接据此做客户端校验，不必解析自定义字段。`description` 取 `Field(description=...)`，内容摘自 `task.py` 的文档字符串，作为表单项的提示文案：那些说明（「剿灭作战必须输入 Annihilation」「仅在 use_support 为 True 时有效」）是本项目最有价值的领域知识。

跨字段依赖由 `x-depends-on` 承载，形态是「字段名 → 期望值」的对象（如 `{ "expedite": true }`），多个键之间是「与」的关系。`task.py` 里这类约束极多：`penguin_id` 仅在 `report_to_penguin` 为真时有效、`filename` 与 `plan_index` 仅在 `Infrast.mode == 10000` 时有效、`Roguelike` 的一大批参数仅在 `theme == "Sami"` 或特定 `mode` 下有效。前端据此禁用该控件并显示依赖提示：禁用比隐藏好，因为用户能看到「还有个选项，但需要先开某个开关」，隐藏会让人以为功能不存在。

按 05 的约定，客户端校验只是体验优化，服务端的 `model_validator` 仍是最终防线。前端不需要为了「本地校验绝对准确」去实现复杂的条件校验，把明显的错误挡住即可，剩下的交给 422 响应（见 §10.3 的错误呈现）。

有一个 05 尚未覆盖、需要补上的关键字：`x-risk`。用于标记会消耗资源的参数（`stone`、`medicine`、`expiring_medicine`、`expedite`、`shopping`、`investment_enabled`），前端在这些控件旁加醒目提示色，并在提交流水线前若任一 risk 参数非零就弹一次汇总确认。这与 agent 侧 `PolicyEngine` 的人工确认（[11-Agent模块设计](./11-Agent模块设计.md)）应当是同一套风险清单的两个出口，不该各维护一份。建议把 `x-risk` 加入 [05 §8.2](./05-API规范与路由清单.md) 的关键字表。

### 7.3 schema 到控件的映射规则

映射的输入是 §7.2 归一化之后的字段描述（剔除 null 分支、解析出 `x-widget`）。判定写在 `features/tasks/form/schema.ts` 的 `resolveWidget`，控件在 `features/tasks/editor/`。M16 起的原则是一个字段只有一个控件：去掉了原方案里的滑块，也不再为选择类控件单独弹抽屉。按下表自上而下取第一条匹配：

| 归一化后的 schema 特征 | 控件 |
|---|---|
| `Copilot.asset_id` | 作业选择：列出已保存的 Copilot 作业（名称 · 关卡），只存 `asset_id` |
| 剔除 null 后仍有多个分支的联合类型，或识别不了的结构 | JSON 文本框，内容能解析时才写入草稿 |
| `x-widget: "item-count-map"` / `"duration-map"` | 掉落物、公招时长的专用控件（§7.4） |
| `type: object`，`properties` 固定 | 嵌套分组，每个 key 递归套用本表 |
| `type: object`，无 `properties` | 键值编辑器，改键时保持顺序与输入焦点 |
| `type: array`，元素是对象（如 `Roguelike.core_char_list`） | JSON 文本框（M28）：`ListControl` 按 `String(item)` 渲染会显示 `[object Object]`，所以元素 schema 是对象时退回 JSON，内容能解析时才写入草稿 |
| `type: array` + `x-widget: "tags"` | 元素有可选值（`enum`，或不超过 12 个值的整数范围，如公招 Tag 等级 1–6）时是可切换芯片；否则是芯片 + 输入框，回车添加（输入法组字时的回车不算） |
| `type: array` + `x-widget: "ordered-list"` | 有序列表：添加、上移、下移、移除（§7.4） |
| 其余 `type: array` | 自由列表 |
| 有选项（`enum`；`x-widget: "select"` 而没有 `enum` 时从 `x-enum-labels` 推导） | 不超过 3 个且每个标签不超过 6 个字时用分段控件（`SegmentedControl`），否则用原生下拉（`NativeSelect`） |
| `type: boolean` 或 `x-widget: "switch"` | 开关（`Switch`） |
| `type: integer` / `number` | 数字框 + −/+ 步进，旁边显示范围 |
| `type: string` | 单行文本；`x-widget: "textarea"` 或 `maxLength > 120` 时多行 |

几条决定形态的取舍：

- 分段还是下拉，看选项数与标签长度。分段控件在 375px 宽下只放得下 3 个短标签：`Recruit.extra_tags_mode`、`Infrast.mode`、`Reclamation.mode` 选项少但标签长，会落到下拉。原方案靠 `x-widget: "select"` 强制下拉（`Fight.series` 的 `x-enum-labels` 文案很长），现在前端直接看标签长度；`select` 只在 schema 没给 `enum` 时用来从 `x-enum-labels` 推导选项。M16 之前渲染的是空下拉，连战次数根本设不了。
- 下拉用原生 `<select>`。手机上调出系统自带的选择器（iOS 是底部滚轮），不需要为它另做底部抽屉；桌面上是普通下拉。
- 数字不用滑块。`medicine`（0~100）用滑块选不准「3」，小范围字段用步进同样顺手。步长取 `multipleOf`，否则整数 1、小数 0.05；步进结果夹在范围内并按步长取整，手输的值不夹取，交给服务端校验。
- 取值有限的整数数组用芯片。公招的 `select` / `confirm` 是 1–6 的可切换芯片，M16 之前是自由文本输入。

编辑器里每个字段的交互规则：

- 标签在上、控件在下；说明文字默认一行截断，点「展开说明」看全文；错误信息紧贴控件（`aria-invalid` + `role="alert"`）。
- 有默认值的字段按默认值预填并标「默认」（必填字段标「必填」）；改动后标签旁出现圆点，并出现「恢复默认」：把该字段写回默认值（没有默认值的字段则从草稿里删掉，回到不提交的状态）。没有已知默认值的字段（四类，见 [§7.5](#75-表单引擎schema-默认值与草稿物化)）保持空白并标「未设置」；其中布尔字段的开关滑块居中，表示交给内核。
- 「明确留空」收进字段的「更多」菜单，只在 schema 允许 null 时出现；选中后提交 `null`，控件显示「已设为空」。
- 按 `groups` 分组：第一组展开，其余折叠，折叠头显示「已修改 N 项」；有错误的分组自动展开，打开编辑器时滚动到第一个出错的字段。
- `x-depends-on` 未满足时控件禁用（不隐藏）并说明依赖哪个字段；`runtime_immutable` 字段在编辑运行中的流水线时标注「运行中不可修改」；带 `x-risk` 的字段标注「消耗资源」。

设置页（`features/settings/`）按同样的原则映射设置 schema，阈值略有不同：分段控件允许 12 个字符以内的标签且要求当前值在选项里；整数数组与字符串数组都用芯片输入；敏感字段是初始为空的 password 输入，留空不提交。

弹层形态。所有弹层都是同一个 `ResponsiveSheet`：宽度 < 1024px 时从底部升起（按内容高度，最高 90dvh，顶部有抓手，内容可滚动，底部可放固定操作区）或铺满全屏；≥ 1024px 时是居中对话框或右侧面板。原方案要求所有选择类控件改用底部抽屉，M16 改为原生下拉与行内控件，弹层只用于一组操作或一整块内容：类型面板、筛选面板、选项面板、详情，以及行内「更多操作」的 `ActionSheet`。消耗类与破坏类操作都用 `ConfirmDialog`（`role="alertdialog"`，标题说清动作，按钮文案写明后果，默认聚焦「取消」），不再使用 `window.confirm`。

编辑单个任务的整套参数在面板里，不跳页。手机全屏、桌面右侧面板；标题是任务类型，副标题是类型说明的第一段，右上角只有「完成」。跳页编辑会丢失「我正在配一条流水线」的上下文。

### 7.4 复杂参数的具体处理

这四个是 `task.py` 里结构最复杂的参数，必须逐个给方案，否则实现时只能瞎猜。

[05 §8.2](./05-API规范与路由清单.md) 列出的 `x-widget` 取值是 `select` / `stepper` / `switch` / `tags` / `textarea`，覆盖不了这几个结构化参数。因此追加三个取值：`item-count-map`、`duration-map`、`ordered-list`。这三个需要同步进 05 的关键字表，否则后端不会产出、前端也就拿不到。

`Fight.drops`：物品 ID → 数量的字典。`task.py` 注明 key 参考 `resource/item_index.json`。让用户手填 item_id 不可行，那是 `30013` 这样的数字。方案是后端新增 `GET /api/resources/items`，读取 MAA 资源目录下的 `item_index.json` 派生出 `[{ item_id, name, icon_url }]` 并缓存（资源热更新后失效重载）。前端控件是行内搜索框 + 已选列表：按中文名或 ID 搜索，有输入时才列出结果（最多 8 条），点选后加入已选列表，每个物品带数量框与删除按钮；物品目录读取失败或为空时，退回为手动输入物品 ID。提交时组装成 `{ "30013": 5 }`。控件顶部常驻一行提示「任一物品达到指定数量即停止任务」，因为「或的关系」不符合直觉。

`Recruit.recruitment_time`：Tag 等级 → 招募时限（分钟）的字典。key 是固定的（等级 ≥ 3，即 3/4/5/6），默认值全为 540，即 09:00。所以这不是自由键值对，而是定长表单：三到四行，每行「4 星 Tag」配一个时长选择器。时长输入不用原生 `<input type="time">`（它在各浏览器表现差异大，且表达的是时刻），每行是「时」「分」两个数字框。默认显示 09:00，改动后按分钟提交（09:00 即 `540`）；字段级的「恢复默认」删除整个映射，行内不再单独提供恢复。schema 用 `properties` 固定 key 表达：

```jsonc
{
  "type": "object",
  "x-label": "希望招募时限",
  "x-widget": "duration-map",
  "properties": {
    "3": { "type": "integer", "default": 540, "x-label": "3 星 Tag", "x-unit": "minute" },
    "4": { "type": "integer", "default": 540, "x-label": "4 星 Tag", "x-unit": "minute" },
    "5": { "type": "integer", "default": 540, "x-label": "5 星 Tag", "x-unit": "minute" }
  },
  "additionalProperties": false
}
```

`Infrast.facility`：有序的设施列表。`task.py` 明确标注「（有序）」，数组顺序就是换班顺序，不只是「换哪些」。旧前端用 `el-select multiple` 是错的：多选框的顺序由点击顺序决定，用户完全感知不到，也无法调整。方案是一个两段列表：上面是已启用的设施，按顺序成行，每行有上移、下移、移除；下面是其余设施，点选即追加到已启用的末尾。原方案的长按拖拽没有做，只保留上移 / 下移按钮。schema 标记 `x-widget: "ordered-list"` 触发这个控件。M28（D4）起候选多出**加工站**（`Processing`）与**训练室**（`Training`）两项，共 9 项；默认值仍是七个设施（`Mfg`/`Trade`/`Power`/`Control`/`Reception`/`Office`/`Dorm`），所以控件显示的是「已启用 7 项 + 可选 2 项」。中文名与内核键的对应挂在数组元素的 `x-enum-labels` 上（§7.2 最后一段）。

`Mall.buy_first` / `blacklist`：中文商品名数组，无固定枚举。旧前端硬编码了两个选项（「招聘许可」「龙门币」），而 `task.py` 的注释还提到「加急许可」「家具零件」。商品列表会随游戏更新变化，不该写死。方案是可输入的标签编辑器：已选项显示为可移除的芯片，输入框回车或点「添加」追加新值。原方案的预置候选与拖拽调序没有做：`buy_first` 的顺序有语义，目前只能按添加顺序排列，要调整只能删掉重加（见 [13 §8.12](./13-决策记录.md)）。

另外 `Roguelike.expected_collapsal_paradigms` 同属这一类（默认值 `["目空一些", "睁眼瞎", "图像损坏", "一抹黑"]`），用同一个控件。

M28 给 `Roguelike` 对齐上游 v6.18.0 后补的两类嵌套结构，都按已有的通用规则处理，不新增专用控件：

- `Roguelike.core_char_list`（开局干员顺位，`[{name, use_support}]`）是**元素为对象的数组**，落进上面映射表新加的那一行：JSON 文本框，能解析才写入草稿，解析失败显示「JSON 格式尚未完整或无效。」（`editor.test.tsx` 的 D5 用例覆盖了写入与报错两条路径）。
- `Roguelike.collectible_mode_start_list`（凹开局的期望奖励，`{hot_water, shield, …}`）是 `properties` 固定的对象，直接走「嵌套分组」：九个奖励各渲染成一个开关（`hot_water` / `shield` / `ingot` / `hope` / `random` / `key` / `dice` / `ideas` / `ticket`，中文名来自各自的 `x-label`），改一项只写这一项，不动其它键。

新参数里的条件字段沿用 `x-depends-on`：`collectible_mode_*` 只在 `mode=4`、`investment_with_more_score` 只在 `mode=1`、`monthly_squad_*` 只在 `mode=6`、`deep_exploration_auto_iterate` 只在 `mode=7`、`blackflow_strategy` 只在 `theme=BlackFlow`、`blackflow_cultivation_target` 还要 `blackflow_strategy=baby_animal`。依赖未满足时控件禁用（不隐藏）并显示「需先将「模式」设为「刷源石锭」」这样的说明；服务端的 `model_validator` 仍会拦一遍，前端禁用只是提前告知。

`task-types.fixture.json` 由 `scripts/generate_task_types_fixture.py` 从后端 schema 生成，M28 随新一轮 schema 重新生成：补齐了 M27 漏掉的 `OperBox` / `Depot`（本节此前「10 种任务类型」的说法已按 12 种改正），现在与 `GET /api/tasks/types` 的 11 种一致（M47 起少一个 `OperBox`：干员数据只来自森空岛同步）；编排器与编辑器的测试也按 12 种断言。

### 7.5 表单引擎：schema 默认值与草稿物化

原方案从 schema 生成 Zod 再交给 React Hook Form，实施没有采用（[§3.4](#34-表单与校验)）。表单逻辑是 `features/tasks/form/` 里的一组纯函数，由 M16 从旧任务页中抽出并补齐单测，编排器与定时任务编辑器共用：

| 模块 | 职责 |
|---|---|
| `schema.ts` | §7.2 的归一化（剥 null 分支、解析 `$ref`、识别复杂结构）、分组、控件判定（§7.3）、`x-depends-on` 判定与依赖说明、默认值与必填、`materializeDefaults()`（M17） |
| `values.ts` | 草稿读写：设置字段、恢复默认（写回默认值，没有默认值时从草稿删除）、明确留空（写入 `null`）、字段状态（默认 / 未设置 / 已修改 / 已设为空）、按分组计数、数组项移动 |
| `serialize.ts` | 把草稿序列化为提交体；`x-risk` 字段非零时生成逐行的风险摘要，供提交前确认 |
| `errors.ts` | 把 422 的两种 `details` 形态（`details.field` 与 pydantic `loc`）映射成「任务 → 字段 → 消息」 |
| `summary.ts` | 从与默认值不同的字段生成任务行的参数摘要 |

M17 起：有默认值就按默认值显示并预填。服务端模型现在带真实的内核默认值（`default=`，来源与逐字段表见 [13 §8.17](./13-决策记录.md)），前端在新建、复制、从模板加载三种入口调用 `materializeDefaults()` 把「有 `default` 且未设置」的字段写进草稿，于是控件直接显示具体值、任务行摘要只在用户改过时才变化、提交体带上这些值（所见即所提交）。

这条与 M16 之前的「草稿只存改动过的字段」正好相反，是一处知情的取舍：好处是用户不用猜「空控件到底是关还是没设」，也让 `Recruit.select`/`Infrast.facility` 这类内核必填但无默认值的参数不再必现 502；代价是 MAA 将来调整某个参数的默认值时我们不再自动跟随：参数快照会冻结在建流水线时的值，要跟随就得改 schema 并重新保存流水线。用户 2026-09-28 裁决接受该代价（[13 §8.17](./13-决策记录.md)）。

没有默认值的四类字段（语义是「无限」、语义是「空 = 不启用」、条件默认值随主题/模式变化、本服务校验器禁止「设了但不生效」）保持 M16 的行为：不进草稿、控件显示为空并标「未设置」，由内核在缺省时自行决定。字段状态因此有五档：默认（等于 schema `default`）、未设置（无默认值且未填）、已修改（与默认值不同）、已设为空（显式 `null`，唯一会提交 `null` 的途径）、必填（schema 要求且未填）。

`additionalProperties: false` 在前端不需要对应处理：表单的字段集合本来就是从同一份 schema 生成的，不可能出现多余键。它的价值在服务端：拼错参数名会被 422 拒掉而不是静默忽略。

## 8. 移动优先的设计规范

本节是 M16 设计系统的落地约定：令牌写在 `web/src/index.css`，原语在 `components/ui/`，外壳在 `components/layout/`。原则是手机优先：先保证 375px 宽下单列可用，再用 `sm:` / `lg:` 增强；界面只用令牌，不写死色值、不用 Tailwind 调色板颜色。

### 8.1 安全区适配

`index.html` 的 viewport 必须带 `viewport-fit=cover`，否则 iPhone 上页面不会延伸到刘海与圆角区域，`env(safe-area-inset-*)` 全部返回 0。`interactive-widget=resizes-content` 让 Android Chrome 在虚拟键盘弹出时缩小布局视口，贴底元素自然落在键盘上方；iOS 不认这个参数，由外壳写入的 `--keyboard-inset` 补上（[§8.4](#84-触摸目标布局与虚拟键盘)）。

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover, interactive-widget=resizes-content" />
<meta name="apple-mobile-web-app-capable" content="yes" />
<meta name="apple-mobile-web-app-status-bar-style" content="default" />
<!-- 首帧脚本按当前主题改写为 #f6f7f9 或 #0e1014，见 §8.2 -->
<meta name="theme-color" content="#0e1014" />
```

iOS 状态栏样式为什么是 `default` 而不是 `black-translucent`，见 [§11.1](#111-manifest-与视觉)。

Tailwind v4 不内置安全区工具类，用 `@utility` 自定义；贴底布局用外壳维护的三个 CSS 变量：

```css
/* src/index.css（节选） */
@custom-variant dark (&:where(.dark, .dark *));

@utility pt-safe { padding-top: env(safe-area-inset-top, 0px); }
@utility pb-safe { padding-bottom: env(safe-area-inset-bottom, 0px); }
@utility px-safe {
  padding-left: env(safe-area-inset-left, 0px);
  padding-right: env(safe-area-inset-right, 0px);
}

:root {
  --tabbar-height: 3.5rem;
  /* 底部 Tab 栏上沿到视口底部的距离 */
  --nav-offset: calc(var(--tabbar-height) + env(safe-area-inset-bottom, 0px));
  /* Tab 栏不显示时，贴底元素需要自己让出的安全区 */
  --nav-safe: 0px;
  /* iOS 虚拟键盘遮住的高度，由外壳根据 visualViewport 写入 */
  --keyboard-inset: 0px;
}
:root[data-tabbar="hidden"] {
  --nav-offset: 0px;
  --nav-safe: env(safe-area-inset-bottom, 0px);
}
@media (min-width: 1024px) {
  :root, :root[data-tabbar="hidden"] { --nav-offset: 0px; --nav-safe: 0px; }
}
```

底部 Tab 栏 `fixed bottom-0`，内容区高 56px，外层 `pb-safe`。外壳的 `main` 下内边距是 `calc(var(--nav-offset) + 1.5rem)`，最后一条内容不会被 Tab 栏盖住。所有贴底元素（页面主操作栏 `StickyActionBar`、Agent 输入栏、调试台的发送栏与响应抽屉）都用 `bottom: calc(var(--nav-offset) + var(--keyboard-inset))` 定位，底部内边距再加 `--nav-safe`：Tab 栏在时贴在它上面；键盘弹出、Tab 栏隐藏时贴在键盘上面，并自己让出 home indicator；桌面上两者都是 0。页面不必各自计算这些距离。全屏容器高度用 `dvh`：移动端 Safari 的 `100vh` 不随地址栏收缩变化，会导致底部内容被裁掉。

### 8.2 色彩令牌与主题

配色是石墨中性 + 靛蓝，深浅两套同等精调。令牌以 CSS 变量定义：浅色写在 `:root`，深色写在 `:root.dark`，经 `@theme inline` 映射为 Tailwind 颜色（`card` → `--surface`，`muted` / `secondary` / `accent` → `--surface-2`，`popover` → `--surface-raised`，`input` → `--border-strong`）。

| 变量 | 浅色 | 深色 | 用途 |
|---|---|---|---|
| `--background` | `#F6F7F9` | `#0E1014` | 页面底色 |
| `--surface` | `#FFFFFF` | `#15181D` | 卡片、列表组、面板 |
| `--surface-2` | `#EEF0F3` | `#1C2027` | 次级填充：输入框底、分段控件底、悬停 |
| `--surface-raised` | `#FFFFFF` | `#1A1D23` | 浮层 |
| `--surface-active` | `#FFFFFF` | `#2B303A` | 分段控件的选中项 |
| `--border` / `--border-strong` | `#E2E5EA` / `#CDD1D8` | `#272C35` / `#363C47` | 分隔线；输入框描边 |
| `--foreground` | `#14161B` | `#E7E9EE` | 正文 |
| `--muted-foreground` | `#646A76` | `#959BA7` | 次要文字 |
| `--primary` / `--primary-hover` | `#4F5BD5` / `#4450C8` | `#5A66E8` / `#6672EE` | 主按钮底、选中态底 |
| `--primary-foreground` | `#FFFFFF` | `#FFFFFF` | 主色上的文字 |
| `--primary-soft` | `#ECEEFD` | `#1F2340` | 主色浅底（选中行、信息提示） |
| `--primary-text` | `#4350C8` | `#9AA3F7` | 链接、选中的图标与文字 |
| `--success` / `--success-soft` | `#1F8A5B` / `#E6F4EC` | `#3FB67F` / `#14281F` | 成功 |
| `--warning` / `--warning-soft` | `#A86A12` / `#FBF1DF` | `#D9A441` / `#2B2314` | 警告、待确认 |
| `--danger` / `--danger-soft` | `#C8413B` / `#FBEAE9` | `#EB6A64` / `#2E1818` | 危险、失败 |
| `--ring` | `#4F5BD5` | `#9AA3F7` | 焦点环 |
| `--chart-1` … `--chart-6` | `#4F5BD5` / `#D98C1F` / `#8B93A1` / `#2F9BD6` / `#A55BD6` / `#2FA87A` | `#7B86F0` / `#E8B256` / `#A8B0BD` / `#5CC0F0` / `#C98CF0` / `#54D3A0` | 图表色板（M23）：最多 6 个系列 |

- 正文与次要文字对背景的对比度都不低于 4.5:1，主色按钮上的白字同样不低于 4.5:1。
- 状态色只用于状态本身（芯片、图标、进度），不做大面积底色；颜色之外同时用文字或图标表达状态。深色主题的警告用琥珀色、危险用降饱和的红，避免在深底上刺眼。
- 日志级别：DEBUG 用次要文字色，INFO 用主色文字，WARNING 用警告色，ERROR 与 CRITICAL 用危险色，行首是同色的级别色条。
- 图表色板（`--chart-1…--chart-6`）与语义状态色是两套：前者只负责「同一张图里六个系列互相可辨」，不表达状态，深浅两套同序号可互换；图表组件从 `:root` 读它，不自己写死颜色（见 [§3.5](#35-长列表与图表)）。
- 过渡期保留的旧颜色别名（`positive`、`negative`、`destructive` 等）已在 M16 收尾时从 `index.css` 删除。

主题。默认跟随系统，可在「更多」页与「设置 › 外观」切换浅色、深色、跟随系统，选择存 localStorage `maa-api-theme`。默认改为跟随系统是 M16 的用户决定（此前默认深色）：两套主题同等精调，夜间场景由系统的深色模式或手动选择覆盖。深色用 `@custom-variant dark (&:where(.dark, .dark *))` 的 class 切换，因为要提供手动覆盖；选择「跟随系统」时 `stores/ui.ts` 监听系统偏好变化并实时切换。

首帧闪烁（FOUC）必须避免：`index.html` 的 `<head>` 里内联一小段脚本，在 React 挂载前按已存的选择与系统偏好给 `<html>` 设 `dark` class、`color-scheme` 与 `<meta name="theme-color">`（浅 `#f6f7f9`、深 `#0e1014`）。这组颜色在 `index.html` 与 `stores/ui.ts` 各写了一份，改一处必须同步另一处。manifest 的颜色固定为石墨 `#0e1014`，见 [§11.1](#111-manifest-与视觉)。

### 8.3 字体、字号、圆角与动效

- 字体。系统字体栈，不打包字体文件、不引外链：`-apple-system, BlinkMacSystemFont, "SF Pro Text", "PingFang SC", "HarmonyOS Sans SC", "MiSans", "Noto Sans SC", "Microsoft YaHei", system-ui, sans-serif`；等宽 `"SF Mono", "JetBrains Mono", ui-monospace, Menlo, Monaco, Consolas, monospace`。两组字体栈写在 `:root` 的 `--app-font-sans` / `--app-font-mono` 上，再由 `@theme inline` 引用：inline 主题变量不保证输出到 `:root`，toast 等内联样式需要能解析的 CSS 变量。
- 字号阶梯。12（标注）/ 13（次要，`text-footnote`）/ 15（正文，`text-body`）/ 17（区块标题与子页标题，`text-headline`）/ 20（一级页面标题，`text-title`）。输入控件取 16px，避免 iOS 聚焦时自动缩放页面。时间、计数、版本号用 `tabular-nums`。`cn()` 用 `extendTailwindMerge` 注册了这些自定义字号（以及阴影、动画）：否则 tailwind-merge 会把 `text-footnote` 当成文字颜色，与 `text-muted-foreground` 合并时吞掉字号。
- 间距与圆角。4px 栅格；页面左右内边距手机 16px、平板 24px、桌面 32px。圆角：卡片与列表组 12px，输入框与按钮 10px，芯片与胶囊全圆角，底部面板顶部 16px。
- 层次。浅色主题的卡片用极轻阴影（`0 1px 2px rgb(16 18 24 / 0.05)`），深色主题只用描边；浮层用更重的 `shadow-float`。不做卡片套卡片：一个页面区块最多一层容器，区块内部用分隔线或留白。
- 动效。淡入与对话框 180ms `ease-out`，底部面板上滑与右侧面板滑入 260ms（`cubic-bezier(0.32, 0.72, 0, 1)`），收起 140–200ms `ease-in`；芯片与开关只做状态过渡。`prefers-reduced-motion: reduce` 时去掉动效。
- 图标与品牌。图标用 lucide，常用尺寸 16 / 18 / 20。品牌标是石墨底圆角方块上的一笔靛蓝单线「M」，界面里的 `BrandMark` 与 PWA 图标同源（[§11.1](#111-manifest-与视觉)）。

### 8.4 触摸目标、布局与虚拟键盘

可点击元素的目标尺寸是 44×44 CSS px：`Button` 默认高 44px（`min-h-11`）、`lg` 48px，图标按钮 `size-11`，所有图标按钮都有 `aria-label`。`sm`（40px）与 `icon-sm`（36px）是例外：后者目前用在面板关闭、区块刷新、设备画面刷新、调试台响应抽屉的展开与全屏这类次要图标按钮上，低于 44px 的目标，列入真机补充实测的关注点（[13 §8.12](./13-决策记录.md)）。

列表行不低于 48px（`ListItem` 为 56px），整行可点时右侧显示箭头；行内次要操作收进「更多操作」（`ActionMenu`）。相邻可点元素之间留出间隙：开关与删除按钮挨在一起是误触高发区。

页面级表单的主操作放在底部吸附的 `StickyActionBar`：手机上固定在 Tab 栏之上并随键盘上移，桌面吸附在内容列底部、靠右对齐。有未保存改动时，离开页面前用应用内确认框拦截（`lib/use-unsaved-changes.tsx`：路由跳转用 `useBlocker`，关闭或刷新页面用 `beforeunload`）。

虚拟键盘。外壳的 `use-virtual-keyboard.ts` 在触屏设备上跟踪键盘：文本输入框获得焦点，或 `visualViewport` 与布局视口的高度差 ≥ 120px（排除地址栏收起这类小幅变化）时视为键盘弹出，在 `<html>` 上写 `data-tabbar="hidden"` 并撤下底部 Tab 栏，让输入区与操作栏贴近键盘；同时把 iOS 键盘遮住的高度写进 `--keyboard-inset`。焦点在两个输入框之间移动时会先失焦再聚焦，失焦后的更新延迟 60ms，避免 Tab 栏闪一下。鼠标键盘设备不隐藏 Tab 栏。

### 8.5 加载、反馈与刷新

- 加载。已知布局的区域用 `Skeleton` 占位，尺寸与真实内容一致，避免内容到位时的布局跳动；其余用行内加载提示（`LoadingState`，`role="status"`）。首页各块独立加载，任一块慢不阻塞其余。
- 空状态与出错。空状态说明原因并给出下一步操作（`EmptyState`）；出错给「重试」（`ErrorState`，`role="alert"`）。
- 成功用 toast。sonner，放在顶部居中，约 2.6 秒自动消失，手机底部已被 Tab 栏与操作栏占用。
- 需要用户处理的错误就地显示。在触发位置附近用 `InlineAlert`（danger / warning 为 `role="alert"`），并给出重试或下一步入口，不用 toast。
- 确认。消耗类、破坏类操作用 `ConfirmDialog`，按钮文案写明后果（例如「清空 3 条待执行」）。
- 刷新。不做下拉刷新（原方案的自绘 `PullToRefresh` 没有实现）。实时数据靠 WebSocket 推送（[§9.5](#95-与-tanstack-query-缓存的协作)），队列与进行中的流水线另有 5 秒轮询；需要手动刷新的列表在区块标题行放刷新按钮。
- 加载更多用显式入口。历史列表底部是「加载更多」，审计是上一页 / 下一页与页码，Agent 对话顶部是「加载更早的消息」；日志列表滚到顶部时自动读更早的一页，顶部同时保留「加载更早日志」按钮。原方案在历史列表底部用 `IntersectionObserver` 自动翻页，没有采用。

### 8.6 断网与后端不可用的降级

几种故障要区分对待，因为用户的下一步动作不同：

后端不可达（请求超时或连接被拒）。网络通但服务挂了（uvicorn 没起、端口错、容器重启中）。路由守卫读 `GET /api/system/health` 失败时，页面显示「无法连接到 MAA-API：…」的错误、「重试」与「重新输入 token」。

实时连接断开。页面照常可读，标题栏下方出现一行细提示（[§9.1](#91-连接状态机)），说明数据可能不是最新；WebSocket 客户端同时进入重连退避。

浏览器离线。没有单独的离线横幅。TanStack Query 的 `networkMode` 保持默认 `'online'`，请求会挂起等待网络恢复，再自动重放；Service Worker 让已缓存的应用外壳在断网时仍能打开（[§11.2](#112-service-worker-缓存策略)）。

后端在但内核或设备不可用（`GET /api/system/health` 返回内核 `starting` / `crashed` / `failed`，或设备未连接）。这是正常状态：[02 §7](./02-系统架构设计.md) 明确规定服务进入可用状态不依赖内核就绪。所以页面完整渲染，首页的运行状态如实显示内核与设备状态，设备断开或不可用时给出提示与「重新连接设备」。旧前端在这种情况下会直接报错，让人以为服务坏了。

原方案设想的统一判定 hook（`useServiceAvailability()`）、离线横幅，以及「需要内核的操作按钮一律置灰」都没有实现。

## 9. WebSocket 客户端封装

单个 WebSocket 连接承载全部实时推送，端点 `GET /api/ws`（[02 §1](./02-系统架构设计.md)）。封装在 `src/realtime/client.ts`，对外暴露一个单例。**协议本身由 [06-实时日志与WebSocket](./06-实时日志与WebSocket.md) 定义，本节只讲客户端侧的可靠性实现，不重新定义帧格式。**

实现前需要先记住三条来自 06 的约定，它们直接决定客户端代码怎么写：消息信封是 `{type, ts, data}`（载荷字段叫 `data`，不是 `payload`；请求/响应类帧额外带 `req_id` 用于配对）；订阅是显式的，连接建立后要发 `subscribe` 声明频道，可用频道为 `log` / `pipeline_status` / `task_status` / `core_status` / `device_status` 以及更新进度与待确认事件；`log` 频道支持 `log_filter` 在服务端做过滤，前端**不要**订阅全量日志再在本地筛：06 实测 `TRC` 占 62%、`WRN` 占 30%，服务端过滤能从源头削掉九成以上的流量，这对移动网络是决定性的。

### 9.1 连接状态机

```
CONNECTING ──open──> OPEN ──close/error──> RECONNECTING ──达到上限──> OFFLINE
                      ^                          │
                      └──────────open────────────┘
```

状态放 Zustand，全局可读。`RECONNECTING` 与 `OFFLINE` 时，页面标题栏下方显示一行细提示（「正在重连实时服务（第 3 次）」「实时连接已断开，页面数据可能不是最新」），连接正常时不占空间；首次连接中（`CONNECTING`）不提示，避免每次打开页面闪一条黄条（M16）。桌面侧边栏底部与「更多 › 关于」另外常驻显示连接状态。界面上没有手动重试按钮，`OFFLINE` 之后的恢复依赖 §9.2 的前台重连。

### 9.2 自动重连与指数退避

退避序列按 [06 §7.5](./06-实时日志与WebSocket.md)：1s → 2s → 4s → 8s → 最大 30s，带 ±20% 抖动。抖动是必要的：内核重启时前端可能同时开了手机和电脑两个页面，固定间隔会让它们同步重连，在服务刚起来的瞬间形成小尖峰。

关闭原因决定重连行为，退避策略要分情况：

| 关闭信号 | 客户端动作 |
|---|---|
| `server_shutdown` 消息 + close `1001` | 首次重连间隔固定 3s，之后正常退避 |
| close `1011`（服务端发送队列满） | 正常退避，且必须带 `last_seen_id` 补拉 |
| close `4401`（token 无效） | **不重连**，清 token 跳登录页 |
| close `4403`（仅凭 cookie 但来源不可信） | **不重连**，提示改用 header 鉴权 |
| close `4429`（超出频率限制） | 退避但起始间隔抬到 30s |

`4401` / `4403` 这两个必须硬编码成「不重连」。鉴权失败是确定性错误，重连只会在服务端日志里刷出一串失败握手，且掩盖真正的问题。close `1011` 的语义值得特别注意：按 06 §6，它表示「本连接的服务端发送队列满了，你消费太慢」，服务端主动断开以保护其他连接。客户端此时不该激进重连，而应先把积压的渲染任务清掉（§9.5 的节流就是为此）再连回来。

连续失败 10 次后进入 `OFFLINE` 停止自动重连，等用户手动点重试或页面重新获得焦点（`visibilitychange` 且 `document.visibilityState === 'visible'`）时立刻重置退避并重连。移动端浏览器在后台会冻结页面并静默断开连接，切回前台立即重连比继续退避体验好得多。

### 9.3 心跳

不能只依赖 TCP 层：移动网络切换（Wi-Fi ↔ 蜂窝）或 NAT 超时会导致连接「看起来还在」但实际已死，`onclose` 不触发。

06 §8 规定的是**双向**心跳，客户端侧的义务是每 30 秒发一帧应用层 `ping`，服务端原样回带 `t` 供计算 RTT：

```jsonc
// 客户端 →
{ "type": "ping", "req_id": "r-4", "data": { "t": 1758000009.000 } }
// 服务端 ←
{ "type": "pong", "req_id": "r-4", "ts": 1758000009.010, "data": { "t": 1758000009.000 } }
```

注意 `t` 是**秒**为单位的浮点时间戳（不是毫秒整数），算 RTT 时要 `(Date.now() / 1000) - t`。

30 秒这个间隔不是随便定的：服务端在「超过 90 秒无任何客户端消息」时会关闭连接，30 秒给了两次丢包的容错余量。客户端侧的死连接检测同样取 90 秒：维护一个 `lastFrameAt`，任何收到的帧（包括服务端每 30 秒的协议级 ping）都刷新它，一个 5 秒周期的检查器发现 `Date.now() - lastFrameAt > 90_000` 就主动 `ws.close()` 走重连流程。两侧用同一个阈值，行为可预测。

RTT 值不要只是算出来丢掉：把它显示在设置页的连接诊断区，并在超过 1 秒时给状态栏加一个「连接较慢」提示。这是用户判断「是我网差还是服务卡」的唯一线索。

页面隐藏时（`document.hidden`）停止发送心跳并容忍连接断开，不浪费电量。这样做会触发服务端 90 秒超时关闭，是预期行为，切回前台时按 §9.2 立即重连并按 §9.4 补发。如果部署在 nginx 反代之后，06 §8 提醒 `proxy_read_timeout` 需大于心跳间隔（建议 120s），否则 nginx 会先于应用超时断开；这条在 §12 的反代方案里要一并配上。

### 9.4 断线期间的消息补偿

日志在断线期间会丢失，而仅靠重连后全量刷新 query 无法恢复它：日志是流，不是快照。状态类事件不需要补偿（重连后重取一次快照即可），所以补偿机制只服务于 `log` 频道。

机制由 [06 §7.4](./06-实时日志与WebSocket.md) 定义：客户端**持久化** `last_seen_id`（最后收到的日志 `id`），重连时带上，服务端从环形缓冲补发 `id > last_seen_id` 的记录。有两条容易写错的细节：

`last_seen_id` 可以走握手 query（`?last_seen_id=1234`）或首个 `subscribe` 消息的字段，但**只在首次 `subscribe` 时生效**，后续再发 `subscribe` 改订阅不会重新触发补发。所以客户端的补发请求必须和「连接建立后的第一次订阅」合成一个动作，不能先订阅再补发。

补发结果在 `subscribed` 响应里告知，不是单独的帧：

```jsonc
{ "type": "subscribed", "req_id": "r-1",
  "data": { "channels": ["log", "pipeline_status"], "backfilled": 32, "truncated": false } }
```

`truncated: true` 表示缺口超出了服务端缓冲容量，补发不完整。此时**不要静默跳过**，要在日志列表对应位置插入一条「存在未加载的历史日志，点击加载」的分隔提示，点击后走 `GET /api/system/logs?after_id=<last_seen_id>` 的游标查询补齐更早的部分。这是 06 明确要求的呈现方式，也是用户判断「日志是真的没有还是没加载出来」的唯一依据。

`last_seen_id` 要存 localStorage：移动端页面被系统回收后重新打开，内存态全丢，只有持久化的游标能让补发继续生效。同时客户端按 `id` 去重（丢弃 `id <= lastSeenId` 的帧），因为补发窗口与新事件可能重叠。

### 9.5 与 TanStack Query 缓存的协作

**核心原则：按事件类型精准失效，不做全量刷新。** `queryClient.invalidateQueries()` 不带参数会失效整个缓存，在一个每秒可能收到几十条事件的连接上这等于持续全量重取。

`realtime/query-bridge.ts` 维护一张路由表，把事件类型映射到处置动作：

事件类型名取 [06 §7.3](./06-实时日志与WebSocket.md) 的规范值，不要另起别名：一旦前端用了自己的命名，`types/realtime.ts` 就得维护一张翻译表，而这张表会在后端加事件时静默失配。

```ts
type Handler = (ev: ServerEvent, qc: QueryClient) => void

export const routes: Record<ServerEvent['type'], Handler> = {
  // 载荷自带完整新状态 → 直接打补丁，零网络往返、零闪烁
  core_status:     (ev, qc) => qc.setQueryData(keys.systemHealth(), (old) =>
                                old && { ...old, core: ev.data }),
  device_status:   (ev, qc) => qc.setQueryData(keys.systemHealth(), (old) =>
                                old && { ...old, device: ev.data }),
  pipeline_status: (ev, qc) => {
    qc.setQueryData(keys.pipelineCurrent(), (old) =>
      isTerminal(ev.data.status) ? { pipeline: null } : { pipeline: ev.data })
    if (isTerminal(ev.data.status)) {
      qc.invalidateQueries({ queryKey: keys.pipelineList(), refetchType: 'active' })
      qc.invalidateQueries({ queryKey: keys.queue() })
    }
  },
  task_status:     (ev, qc) => patchTaskInCurrent(qc, ev.data),

  // 只是「某物变了」的信号 → 失效对应 key
  confirm_request: (_, qc) => qc.invalidateQueries({ queryKey: keys.confirmations() }),
  confirm_resolved:(_, qc) => qc.invalidateQueries({ queryKey: keys.confirmations() }),
  update_progress: (ev, qc) => qc.setQueryData(keys.updateJob(ev.data.update_id), ev.data),

  // 高频流式数据 → 完全不进 Query 缓存
  log:             (ev) => useLogBuffer.getState().append(ev.data),
  agent_event:     (ev) => useAgentStream.getState().apply(ev.data),
}
```

`pipeline_status` 的处理方式值得说明：06 把「进度更新」和「进入终态」合并成同一个事件类型，靠 `status` 字段区分（`pending` / `running` / `completed` / `failed` / `cancelled`）。所以客户端不能假设有一个独立的「完成」事件，必须自己判断终态并据此把 `pipelines/current` 置空、失效历史列表与队列。把这个判断集中在路由表里，页面组件就不需要关心。

三条选择准则：

**事件载荷是否包含完整的新状态。** 是则用 `setQueryData` 直接写缓存，零网络往返、零闪烁。`core_status` / `device_status` / `pipeline_status` 都属于这类，后端应当刻意把它们设计成自包含的。

**只是变更信号则 `invalidateQueries`，并带 `refetchType: 'active'`。** 默认行为只重取活跃观察者，但显式写出来是为了表明意图：用户在日志页时，队列 query 只标脏不重取，切回任务页才发请求。

**高频流式数据不进 Query 缓存。** 日志行和 agent 的 token 增量走 Zustand 环形缓冲。Query 的定位是「服务端资源的快照」，把每秒几十条的追加流塞进去会触发大量订阅者重渲染，而且这些数据本来就不需要缓存失效语义。

另外加一层节流：同一个 `queryKey` 前缀在 250ms 窗口内的多次失效合并成一次。流水线执行时 `task_status` 与 `pipeline_status` 往往连着来，合并后省掉一半请求。实现上用一个 `Map<string, timeoutId>` 做尾部防抖。

这层节流同时是对 close `1011`（服务端队列满则断开）的防御。06 §6 的策略是「慢客户端的代价由它自己承担」：如果前端每收一帧就同步触发一轮重渲染与重取，在日志高峰期就会真的消费不过来而被踢掉。日志行的写入也要批量：`useLogBuffer.append` 内部用 `requestAnimationFrame` 合并同一帧内的多次追加，一次性 `set` 到 store。

## 10. 鉴权在前端的处理

后端是单个 `access_token`，支持 Bearer / `X-Token` / query / cookie 四种传递方式（[README 决策表](./README.md#决策速查表)）。四种方式各有不得不用的场景。

### 10.1 token 的录入与存储

没有用户名密码，登录页 `/login` 就是一个 token 输入框（`type="password"` + 明文切换按钮）。

[05 §6.1](./05-API规范与路由清单.md) 没有专门的「校验 token」端点，所以登录流程复用现有的两个：先读免鉴权的 `GET /api/system/health` 拿 `auth_enabled`，若为 `false` 直接跳过登录页；否则用户输入 token 后带上它调 `POST /api/system/auth/cookie`，返回 `204` 即 token 有效（返回 `401 UNAUTHORIZED` 即无效），同时这一步顺带把 WebSocket 需要的 cookie 也拿到了。一次请求同时完成校验与换 cookie，不必再加端点。

存储位置：localStorage + 后端下发 HttpOnly cookie + IndexedDB，三处。前两处服务于页面上下文，第三处专门服务于 Service Worker，理由见后文。

localStorage 存 token 的风险是 XSS：任何注入的脚本都能读走它。必须承认这个风险，然后论证在本项目里它是可接受的：前端没有任何用户生成内容的富文本渲染路径（日志用纯文本渲染，不用 `dangerouslySetInnerHTML`）；所有依赖打进 bundle，没有 CDN 外链，不存在第三方脚本被投毒的通道；部署形态是私有内网单用户。在这个威胁模型下，XSS 的前置条件基本等于「攻击者已经能改前端代码」，此时 token 存哪都一样。

反过来，如果只用 HttpOnly cookie 而不存 localStorage，就得为「同一个 token 要同时用于 fetch、WebSocket、`<img src>`」这三种场景各自配置 CORS 与 `credentials`，且在跨主机调试（dev server 在 5173、后端在 8002）时 cookie 的 `SameSite` 会成为持续的摩擦点。

结论是双写：localStorage 作为前端可读的主副本（用于请求拦截器注入 header）；同时 `POST /api/system/auth/cookie` 成功时后端下发 `maa_token` 的 `HttpOnly; SameSite=Lax` cookie（[05 §5](./05-API规范与路由清单.md)，HTTPS 下追加 `Secure`），这份 cookie 专门服务于无法自定义请求头的场景。

双写不会放大 CSRF 风险，因为 05 对 cookie 渠道加了一条硬限制：仅凭 cookie 鉴权的请求只允许 `GET`、`HEAD` 与 WebSocket 升级，写方法若 token 只来自 cookie 直接返回 `403 FORBIDDEN`。前端的写请求本来就带 `X-Token` 头，不受影响。这条限制的实际效果是：即使用户在别的网站被诱导对本服务发起 `POST`，浏览器自动附带的 cookie 也不足以让它通过。

第三处存储：IndexedDB，供 Service Worker 使用。这一处是被推送通知的「准许 / 拒绝」按钮逼出来的（[§13.2](#132-确认超时与推送触达的矛盾)）。点击通知的 action 时，处理逻辑跑在 Service Worker 的 `notificationclick` 事件里，此时页面可能根本没打开。而 Service Worker 不是 window 上下文，访问不到 localStorage：那是个同步 API，Worker 环境里不存在。

于是出现一个两难：Service Worker 要发 `POST /api/confirmations/{id}`，但它读不到 localStorage 里的 token；同源 fetch 会自动带上 cookie，可 cookie 按上面那条硬限制不能用于写操作。

解法是把 token 也写一份进 IndexedDB（Service Worker 可以访问），由 Worker 读出来放进 `X-Token` 头：

```ts
// src/pwa/sw-auth.ts —— 在 Service Worker 里读 token
async function readToken(): Promise<string | null> {
  const db = await openDB('maa-api', 1)
  return db.get('auth', 'token')
}
```

这样"写操作必须显式带凭据"这条规则保持无例外，不必为推送场景给 cookie 开特例：开了特例就等于把 CSRF 防护上的一个口子永久留在那里，而且是留在一个最容易被忽略的路径上。

三处存储的写入与清除必须同步，否则会出现"页面已登出但通知按钮还能批准操作"这种最坏情况。登出时要清四样：localStorage、Zustand、IndexedDB，以及让后端清 cookie。05 当前没有列出登出端点，实现时需要补一个（`DELETE /api/system/auth/cookie` 最贴合现有命名），否则 HttpOnly cookie 前端删不掉，登出后 WebSocket 仍能连上。这是需要回填到 05 路由清单的一处缺口。

### 10.2 请求拦截器注入

用 `openapi-fetch` 的中间件统一注入，不在每个调用点手写 header：

```ts
// src/api/client.ts
import createClient, { type Middleware } from 'openapi-fetch'
import type { paths } from '@/types/api'

const auth: Middleware = {
  async onRequest({ request }) {
    const token = useAuth.getState().token
    if (token) request.headers.set('X-Token', token)           // 渠道 2，05 指定给 SPA
    request.headers.set('X-Request-Id', crypto.randomUUID())  // 用于与实时日志联动，见 10 号文档
    return request
  },
  async onResponse({ response }) {
    if (response.status === 401) useAuth.getState().onUnauthorized()
    return response
  },
}

export const api = createClient<paths>({ baseUrl: '/' })
api.use(auth)
```

用 `X-Token`，这是 [05 §5](./05-API规范与路由清单.md) 的渠道分工：渠道 1（`Authorization: Bearer`）留给脚本与 `curl`，渠道 2（`X-Token`）指派给前端 SPA 的 fetch 封装。两者服务端都接受、优先级也只差一位，分开用的收益在排查问题时：看一眼请求头就知道这次调用来自浏览器还是来自 agent，不必去比对 `User-Agent`。

### 10.3 错误状态码的前端处理

`onUnauthorized()` 做三件事：清 localStorage 与 Zustand 里的 token、把 `location.pathname + search` 存为 `returnTo`、`navigate('/login')`。同时断开 WebSocket 并阻止重连（否则会在退避循环里反复失败）。

要区分 401 与 403。401 是「token 无效或缺失」，跳登录页；403 是「身份有效但动作被策略拒绝」，在触发位置就地提示、不跳转，已保存的 token 保留（M16 起需要用户处理的错误就地显示，不用 toast，见 §8.5）。403 在单 token 模型下是会真实出现的，[05 §4](./05-API规范与路由清单.md) 列了两种触发条件：非同源请求试图仅凭 cookie 执行写操作。后者正是前端可能踩到的：如果 `X-Token` 头因为某个中间件被剥掉，写请求会退化成 cookie-only 而收到 403。所以 403 的提示文案要能指向这个原因（如登录页的「服务拒绝了此认证请求」）。

422 是第三类，需要单独处理：它来自 Pydantic 的参数校验，是任务表单提交的主要失败形态。响应体按 [05 §3](./05-API规范与路由清单.md) 的统一错误信封 `{"error": {"code", "message", "details"}}`，`details` 里带字段级的错误位置。前端用 `features/tasks/form/errors.ts` 把它映射回对应任务与字段：任务行显示错误角标，就地提示「第 N 个任务有 K 处错误」并可一键打开出错的任务，编辑器里错误紧贴控件、打开时滚动到第一个出错的字段。这是 §7 的 schema 驱动表单能正确闭环的关键一环。

重试策略要按状态码细分，不能笼统地"4xx 不重试、5xx 重试"。TanStack Query 的默认 `retry: 3` 会让一个失效 token 打出四次请求，在 uvicorn 日志里刷出一堆 401。在 `QueryClient` 的 `defaultOptions.queries.retry` 里写一个函数：

```ts
retry: (failureCount, error) => {
  if (failureCount >= 3) return false
  const status = (error as ApiError).status
  if (status === undefined) return true    // 网络错误，重试
  if (status === 504) return false         // 下游未应答，操作可能已执行
  return status >= 500                     // 其余 5xx 重试，4xx 一律不重试
}
```

504 必须排除在重试之外，这是它与其他 5xx 的关键区别。按 [05 §2.4](./05-API规范与路由清单.md)，504 表示下游没有应答，而命令可能已经投递并正在执行，自动重试会把同一个任务提交两遍。504 的正确处置是查状态而非重试，所以前端收到 504 时应当主动刷新相关查询（如 `GET /api/pipelines/current`）并提示"内核未在预期时间内响应，正在确认当前状态"。

对写操作（`useMutation`）则不自动重试，无论什么状态码：提交任务、触发更新这类动作重复执行的后果比多等一次严重得多。需要重试时由用户显式点按钮。

### 10.4 WebSocket 与图片的特殊处理

WebSocket 的浏览器 API 不支持自定义请求头。`new WebSocket(url)` 只能传 URL 和子协议，没有 header 参数，这是 WHATWG 规范的限制，没有变通办法。因此 WS 只能用渠道 3（query）或渠道 4（cookie），这也正是这两个渠道存在的原因。

有一处文档分歧：[05 §5](./05-API规范与路由清单.md) 推荐先换 cookie 再连（「token 不出现在 URL 里」），而 [06 §7.2](./06-实时日志与WebSocket.md) 写的是「首选 query 参数」。两者的取舍出发点不同，按客户端类型分开就不矛盾了。据此规定：

浏览器（SPA 前端）走 cookie。登录时已经调过 `POST /api/system/auth/cookie`（§10.1），cookie 已在。`new WebSocket('/api/ws')` 不带任何 token 参数，握手作为普通 HTTP GET 自动携带 cookie。好处是 token 不进 uvicorn 的 access log、不进浏览器 history、不会在截图或分享链接时泄露。

非浏览器客户端走 query。agent、脚本、`wscat` 这类客户端没有 cookie jar，`?token=xxx` 是唯一可行的方式，06 的「首选 query」针对的就是它们。这部分不属于本前端的实现范围，但接入说明要写清楚（见 [10-开放API与调试台](./10-开放API与调试台.md) 的接入指南章节）。

前端仍要保留 query 兜底路径，用于一个具体场景：跨主机开发时 dev server（5173）与后端（8002）不同源，`SameSite=Lax` 的 cookie 在 WebSocket 握手时不一定带上。选择逻辑是「先试不带 token 的 URL，握手被 close `4401` 拒绝后再回退到带 query 的 URL」，而不是无条件带 query。启用兜底时必须配套：后端把 `token` 查询参数从 access log 脱敏（06 §7.2 同样要求这一点），前端不把带 token 的 URL 写进任何日志或错误上报。

还有一个易踩的坑：`4403`（仅凭 cookie 但来源不可信）在跨源开发时可能被触发，此时不要退回 query 重试，而应提示开发者配 dev server 代理（§4 的 `server.proxy` 让前后端同源，从根上避开这个问题）。

第三种方案是「连接后第一帧发 auth 消息」，后端在 `accept()` 之后等第一帧再决定是否继续。它的问题是 `accept()` 必须先发生，未鉴权的连接会短暂占用服务端资源，且无法用标准的 HTTP 401 拒绝。列为备选，不作为首版实现。

`<img src>` 同样不能带 header。日志页的截图缩略图就是 `<img>` 加载的（`<img loading="lazy">` + `/api/images/<sha256>/thumb`），它依赖 cookie；首页的设备截图走 `fetch`（`credentials: 'same-origin'`）取 blob 再 `createObjectURL`，同样依赖 cookie。M23 起 Agent 媒体卡与流水线详情截图改走第三条路：`api` 客户端带 `X-Token` 取 blob（`components/ui/use-authed-image.ts`），完全不依赖 cookie。新代码优先用后者：它不要求用户先换过 cookie，也不会因为 `SameSite=Lax` 在跨源开发时失效。如果要让 `log_entry` 里的缩略图也完全不依赖 cookie，后端可以为图片资源提供一次性短时 URL（响应体里返回带签名与过期时间的 query），前端把这个 URL 直接给 `<img src>`；这种做法更严格但增加一次往返，日志页暂时保持 cookie 方案。

需要注意 Service Worker 不要缓存任何带 token 的请求。Workbox 的 `runtimeCaching` 规则里排除掉 URL 含 `token=` 的请求，否则 token 会被写进 Cache Storage，退出登录后仍留在磁盘上。

## 11. PWA 方案

### 11.1 manifest 与视觉

```ts
// web/vite.config.ts（节选）
VitePWA({
  registerType: 'prompt',          // 不静默更新，由用户确认后刷新
  injectRegister: false,           // 注册由 components/pwa/PwaUpdatePrompt.tsx 自己做
  strategies: 'injectManifest',    // 自写 src/sw.ts（M14，见 13 §8.9）
  srcDir: 'src',
  filename: 'sw.ts',
  injectManifest: {
    globPatterns: ['**/*.{css,html,ico,png,svg,webmanifest,js}'],
    maximumFileSizeToCacheInBytes: 3 * 1024 * 1024,
  },
  includeAssets: ['favicon.svg', 'apple-touch-icon.png', 'pwa-192x192.png', 'pwa-512x512.png', 'pwa-maskable-512x512.png'],
  manifest: {
    name: 'MAA-API 控制台',
    short_name: 'MAA-API',
    description: '明日方舟自动化服务控制台',
    theme_color: '#0e1014',
    background_color: '#0e1014',
    display: 'standalone',
    orientation: 'any',
    start_url: '/',
    scope: '/',
    icons: [
      { src: '/pwa-192x192.png', sizes: '192x192', type: 'image/png' },
      { src: '/pwa-512x512.png', sizes: '512x512', type: 'image/png' },
      { src: '/pwa-maskable-512x512.png', sizes: '512x512', type: 'image/png', purpose: 'maskable' },
    ],
  },
})
```

Chromium 系的安装门槛要求 manifest 至少包含 `name` 或 `short_name`、`start_url`、`display`、以及 192px 与 512px 两个图标，且 `prefer_related_applications` 不为真。上面的配置满足。`purpose: 'maskable'` 的那张图是给 Android 自适应图标用的，缺了它图标在部分启动器上会被套一个白底方框。`display: 'standalone'` 让启动后没有浏览器地址栏。`start_url` 是 `/`，`scripts/frontend_smoke.py` 会检查它与图标文件；原方案的 `?src=pwa` 流量标记与 `shortcuts` 没有采用。

颜色。manifest 的 `theme_color` 与 `background_color` 固定为石墨 `#0e1014`，与石墨底的图标一致，安装后的启动画面过渡自然。页面里的 `<meta name="theme-color">` 则随当前主题实时切换（浅 `#f6f7f9`、深 `#0e1014`，见 [§8.2](#82-色彩令牌与主题)）。

图标。`web/public/` 下的 favicon 与 PWA 图标由 `scripts/generate_pwa_icons.py` 从品牌插画 `web/public/logo.webp`（512×512，带透明通道）生成：`favicon.png`（64×64）、`apple-touch-icon.png`（180×180）、`pwa-192x192.png`、`pwa-512x512.png`、`pwa-maskable-512x512.png`。插画是画面的唯一来源，脚本只做合成与缩放：把插画垫在品牌底色（暖白 `#F1ECE1`，取自画框内部）上、按需加圆角、再量化为 256 色 PNG（真彩直存会让 512 图标超过 200KB，而它要进 Service Worker 预缓存；量化后平均色差约 2.7/255）。`any` 用途的图标带透明圆角；apple-touch 与 maskable 是满幅方块、由系统自行裁切，maskable 的内容缩到 90% 安全区（实测 0.8 太小、1.0 会切掉画框四角与玫瑰）。应用内的品牌标读同一张插画（`BrandMark` 渲染 `/logo.webp`），不再单独维护一份几何。`--check` 只比较生成结果与已提交文件是否一致，不写盘。

iOS 状态栏。`apple-mobile-web-app-status-bar-style` 用 `default`，不用原方案的 `black-translucent`：默认主题改为跟随系统后，浅色主题下 `black-translucent` 的白色状态栏文字会看不见。代价是，如果某个 iOS 版本不按 `theme-color` 给状态栏着色，深色主题下顶部会是一条浅色状态栏（可读但不协调）；这一点要在真机上确认（[13 §8.12](./13-决策记录.md)）。

iOS 还需要 `<meta name="apple-mobile-web-app-capable" content="yes">` 与 `<link rel="apple-touch-icon" href="/apple-touch-icon.png">` 作为兼容兜底，都在 `index.html` 里，见 [§8.1](#81-安全区适配)。

### 11.2 Service Worker 缓存策略

原方案用 Workbox 的 `generateSW` 配 `runtimeCaching`；M14 为了处理 `push` 事件改为 `injectManifest` + 自写的 `src/sw.ts`，预缓存也用 Cache API 自己实现，不引入 Workbox 运行时（[13 §8.9](./13-决策记录.md)）。缓存行为只有两条：

- 预缓存应用外壳。构建时把产物清单注入 `self.__WB_MANIFEST`，`install` 时用 Cache API 预缓存全部条目；缓存名取清单的指纹，`activate` 时清掉旧版本的缓存。预缓存命中的静态资源缓存优先。注入的清单 URL 不带前导斜杠，而 `URL.pathname` 一定带，两边都要归一化，否则预缓存会静默为空；守卫是在 Node 里执行构建产物的 `web/scripts/sw_harness.mjs`，接在 `pnpm build` 之后。清单由 `injectManifest.globPatterns` 的 `**/*.js` 决定，所以动态 import 切出来的 chunk 也在预缓存里，包括 agent 图表卡那批约 1.06 MB raw / 355 KB gzip 的 ECharts chunk（[§3.5](#35-长列表与图表)），「出现图表才加载」对 Service Worker 的安装阶段不成立。
- 导航离线回退。导航请求先走网络，断网时回退到缓存的 `/index.html`。`/api`、`/docs`、`/redoc`、`/openapi.json` 在导航 denylist 里，永远打到网络，否则一个失败的 API 请求会被当成页面请求返回 `index.html`。denylist 对 `url.pathname` 做匹配，所以带 `^` 锚定的正则是正确的。

所有 `/api/*` 请求都不缓存。原方案给 `/api/tasks/types`（离线时仍能渲染表单）与截图配的运行时缓存没有实现。

`install` 里不自行 `skipWaiting`：新 SW 装好后进入 waiting 状态，不主动接管已打开的页面，等用户在更新提示里点「立即更新」才发 `SKIP_WAITING`（[§11.4](#114-更新提示)）。这避免了「用户正在填表单时页面被新版本资源替换」。

### 11.3 安装引导

实施现状：安装引导卡片还没有实现（`web/src` 里没有 `beforeinstallprompt` 处理，也没有 iOS 引导卡片），列为待办，见 [13 §8.12](./13-决策记录.md)。目前 Android / 桌面 Chromium 靠浏览器自带的安装入口；iOS 需要用户自己从分享菜单「添加到主屏幕」，非安全上下文下的推送说明会提示这一步。下面是原方案，实现时照此执行。

Android / 桌面 Chromium 有 `beforeinstallprompt` 事件。监听并存下 event 对象，在合适时机（用户已经用过两次、不在首次访问）显示一张「安装到主屏」卡片，点击时调 `event.prompt()`。不要在页面加载时立刻弹，那是最容易被无脑关掉的时机。

iOS / iPadOS 没有 `beforeinstallprompt`，也没有任何编程式安装 API。只能引导用户手动操作。检测条件是「UA 判定为 iOS」且 `navigator.standalone !== true`（已安装时该值为 `true`），满足则显示一张图示卡片：「点击底部分享按钮 → 添加到主屏幕」，配一张标注了分享图标位置的插图。这是 iOS 上唯一可行的做法。

引导卡片的关闭状态要持久化（localStorage 记一个 `installPromptDismissedAt`），7 天内不再显示。

### 11.4 更新提示

`components/pwa/PwaUpdatePrompt.tsx`（挂在 `App.tsx`）自己完成注册与更新检测，不用 `useRegisterSW`：

- 只在生产构建、安全上下文且浏览器支持 Service Worker 时注册 `/sw.js`，否则直接跳过（不是 try-catch 吞异常，而是根本不调用，见 [§12.4](#124-部署路径)）。注册成功后立即 `registration.update()` 检查一次更新。
- 新 Worker 装好并进入 waiting 状态、且页面已被旧 Worker 控制时，显示「MAA-API 有新版本可用」与「稍后」「立即更新」。「立即更新」向 waiting Worker 发 `SKIP_WAITING`，等 `controllerchange` 后刷新页面；「稍后」只关掉本次提示。
- 提示是浮在顶部的一条（手机在安全区下方居中，桌面在右上角），不做成 Modal：新版本可用不是紧急事件，不该打断当前操作。M16 起它从底部移到顶部，因为真实服务上发现它与页面主操作栏同位，挡住了「开始执行」。

后端每次部署新前端产物后，`index.html`（`no-cache`）会立刻变，SW 的预缓存清单随之变化，用户在下一次打开页面时收到提示。原方案每小时 `registration.update()` 一次的定时轮询没有实现：安装到主屏、连续几天不重新导航的 PWA 会长期停在旧版本，直到下次重新打开。

## 12. PWA 的安全上下文约束与部署路径

这是整份方案里唯一一个「技术上无法用代码绕过」的约束，必须在动工前就定好部署形态。

### 12.1 约束事实

Service Worker、Push API、Notification API 都要求安全上下文（secure context）。安全上下文的判定只认两类来源：HTTPS，以及 `localhost` / `127.0.0.1`（含任意端口，无需 TLS）的特例。

局域网 HTTP 地址，比如 `http://192.168.1.50:8002`，不是安全上下文。在这个地址下：

- `navigator.serviceWorker.register()` 直接失败，`window.isSecureContext === false`
- Chromium 的安装门槛明确要求 HTTPS 或 `localhost` / 回环地址，不满足则不会出现安装提示、不生成 WebAPK
- Push API 与 `Notification.requestPermission()` 不可用
- `getUserMedia` 等其他强能力同样不可用（本项目不涉及，但同源）

注意 `localhost` 特例只对同一台设备成立。手机上的 `localhost` 指手机自己，不是运行 MAA-API 的那台机器。所以「桌面上一切正常」完全不能说明手机上也正常，这是最容易踩的坑。

### 12.2 降级矩阵

| 能力 | `http://192.168.x.x:8002` | `http://localhost:8002`（同机） | HTTPS |
|---|---|---|---|
| 应用正常使用（页面、API、WebSocket） | 可用 | 可用 | 可用 |
| iOS「添加到主屏幕」+ standalone 显示 | **可用** | 可用 | 可用 |
| Android / 桌面 Chromium 安装提示 | 不可用 | 可用 | 可用 |
| Service Worker（离线外壳、资源缓存） | 不可用 | 可用 | 可用 |
| Web Push 推送通知 | 不可用 | 名义可用但无实际意义 | 可用 |

一个反直觉的事实值得强调：iOS 的「添加到主屏幕」在纯 HTTP 下是可以用的。它是用户手动触发的操作，不受安装门槛限制，会读取 manifest 并按 `display: standalone` 启动、使用 `apple-touch-icon` 作为图标。所以「HTTP 下能不能添加到主屏」的答案是：iOS 能，得到一个没有浏览器界面的独立图标应用；Android 不能得到系统级安装（只能存一个普通书签）。

但推送通知在 HTTP 下必然失效，无论哪个平台。iOS 的 Web Push 要求三个条件同时成立：站点是 HTTPS、PWA 已通过分享菜单添加到主屏、在已安装的应用内由用户手势触发 `Notification.requestPermission()`。Safari 标签页内即使在 HTTPS 下也无法订阅。所以 HTTP 下推送不是「体验降级」而是「功能不存在」。

### 12.3 可选方案与代价

自签证书 + 手动信任。用 `mkcert` 建一个本地 CA 并为 LAN IP 签证书，把 CA 根证书装到每台要访问的设备上。代价：iOS 需要下载配置描述文件、在「设置 → 通用 → VPN与设备管理」安装，再去「关于本机 → 证书信任设置」里手动开启完全信任，这是两个不同位置的两步操作，非技术用户几乎不可能自己完成；每台新设备都要重做；证书有效期到了要全部重来（mkcert 默认签 2 年多）。适合单人单设备，不适合多设备。

反向代理终结 TLS。前面放一个 Caddy 或 Nginx，用自有域名 + Let's Encrypt。如果域名解析到公网 IP 则用 HTTP-01 挑战，但那意味着服务要暴露到公网，与私有部署的前提冲突。更好的做法是 DNS-01 挑战 + 内网 DNS 解析：向 Let's Encrypt 用 DNS 挑战申请 `maa.example.com` 的真实证书（不需要服务可被公网访问），同时在路由器或本地 DNS 上把这个域名解析到 LAN IP。代价：需要一个自有域名、需要 DNS 服务商的 API token 配给 Caddy、需要能配置内网 DNS（有些运营商光猫不支持）。技术上最干净，前置条件最多。

内网组网工具带证书。Tailscale 的 `tailscale serve` 会给设备分配 `*.ts.net` 的域名并自动签发受信证书，一条命令就能把本地 8002 端口暴露为 HTTPS。代价：需要每台访问设备都装 Tailscale 客户端并登录同一账号；流量走 WireGuard 隧道（同网段下通常仍是直连，不经中转，延迟影响可忽略）；依赖一个第三方服务的控制平面。好处是顺带解决了「不在家时也能访问」和「IP 变化后地址失效」两个问题。

Chrome 的 `unsafely-treat-insecure-origin-as-secure` 标志。把指定 origin 强制当作安全上下文。桌面 Chrome 可以通过 `chrome://flags/#unsafely-treat-insecure-origin-as-secure` 或 `--unsafely-treat-insecure-origin-as-secure="http://192.168.1.50:8002" --user-data-dir=/tmp/xxx` 启用。但在 Android 上这个命令行标志需要 root 或开发者模式的设备，普通手机用不了，而移动端恰恰是本项目的主场景。所以这个方案对我们基本无效，只在桌面临时调试时有点用。

Chrome DevTools 的端口转发。Android 手机用 USB 连电脑，在 `chrome://inspect` 里配端口转发，手机上的 `localhost:8002` 映射到电脑能访问的地址，从而落进 `localhost` 特例。这是开发期验证 Service Worker 与推送逻辑的最便捷办法，但要插着线，不能作为日常使用方式。

### 12.4 部署路径

已拍板：首版就上 Tailscale Serve（下面的第二层），不接受 PWA 能力缺失的降级形态。这意味着 PWA 的全部能力（离线外壳、安装为独立应用、Web Push 确认通知）在首版就是可用的，`M14` 的验收标准按「真机上能收到推送并点击深链回确认卡片」来定。

第一层的分级降级仍然要实现，但定位从"首版形态"变成"防御性兜底"：Tailscale 客户端没连上、或用户临时用局域网 IP 直连时，应用要正常工作，不出白屏与满屏报错。

第一层（无论如何都要实现，零成本）：按安全上下文分级降级。应用不假设自己运行在安全上下文里。`components/pwa/PwaUpdatePrompt.tsx` 在 `!window.isSecureContext` 时直接跳过 SW 注册（不是 try-catch 吞异常，而是根本不调用，避免控制台刷错误）。「设置 › 通知」里的 Web 推送只显示说明、不渲染订阅控件：点不动的按钮只会让人以为坏了。说明文案是「当前通过 HTTP 访问，Service Worker 离线缓存、Android 安装提示与推送通知不可用。配置 HTTPS 后自动启用。」，M16 起只出现在登录页、「更多」页底部与推送设置里，不再每页常驻。这一层保证「什么都没配」时应用完整可用，只是少了 PWA 能力。

```ts
// src/pwa/push.ts
export const PWA_AVAILABLE = window.isSecureContext && 'serviceWorker' in navigator
export const PUSH_AVAILABLE = PWA_AVAILABLE && 'PushManager' in window
```

第二层（首版采用）：Tailscale Serve。在跑 MAA-API 的机器上执行一条命令，访问 `https://<主机名>.<tailnet>.ts.net`：

```bash
tailscale serve --bg https / http://127.0.0.1:8002
```

选它的理由是它同时解决了三个问题：受信证书（PWA 全部能力解锁）、稳定地址（不再受 DHCP 影响）、外网可达（不在家也能看挂机状态）；代价只是每台访问设备装一个客户端并登录同一账号。证书由 Tailscale 自动签发与续期，不需要任何证书维护。

首版采用它带来三项必须落地的配套工作，都归到 `M15`：

后端要信任代理头。`tailscale serve` 是反向代理，请求到达 FastAPI 时 `X-Forwarded-Proto` 为 `https` 但连接本身是到 `127.0.0.1` 的 HTTP。cookie 的 `Secure` 属性判定（[§10 鉴权在前端的处理](#10-鉴权在前端的处理)提到 HTTPS 下追加 `Secure`）如果按连接本身判定就永远不会加上。需要给 uvicorn 配 `--forwarded-allow-ips=127.0.0.1` 并让下发 cookie 的代码按 `X-Forwarded-Proto` 判定，否则 `Secure` cookie 在 Tailscale 下反而失效。

CORS 与 WebSocket 的 origin 白名单要包含 `*.ts.net` 域名。这个域名在部署时才确定（取决于 tailnet 名与主机名），所以必须是配置项，这也顺带修掉了现有代码 `allow_origins=["*"]` 配 `allow_credentials=True` 的错误组合（见 [01-重构总览与现状评估](./01-重构总览与现状评估.md)）。

文档要写清「装客户端」这一步不可省。它是唯一的用户侧前置条件，且未登录同一 tailnet 的设备完全访问不到。部署文档里要把这一步放在最前面，并说明它同时是访问控制手段：不在 tailnet 内的设备连端口都摸不到，这实际上比单 token 鉴权更强。

第三层（有域名与 DNS 控制权时）：Caddy + DNS-01。想完全不依赖第三方控制平面，或者要给多个服务统一做 TLS 入口时的长期形态。Caddyfile 大致是反代 `127.0.0.1:8002` 并配置 DNS 提供商插件。首版不做，但上面那三项配套工作（信任代理头、origin 白名单可配、部署文档）对它同样适用，所以切换过去时不需要改代码。

开发期用同机 `localhost:8002`（或 dev server 的 `localhost:5173` 配代理）来验证 SW 行为，需要在真机上验证时用 Chrome DevTools 的端口转发。不推荐 mkcert（多设备维护成本高）与 Chrome 标志（Android 上要 root，等于不可用）。

## 13. 通知能力的分工

三条触达通道，职责不重叠。

后端多通道通知（邮件 / Webhook / Bark / 钉钉 / 企微）是保底层。它不依赖前端在线、不依赖安全上下文、不依赖用户授权过通知权限。因此把「必须送达」的事件交给它：流水线终态（完成 / 失败）、内核崩溃告警、热更新完成、定时任务执行结果。这是 `NotifyService` 的职责（[02 §1](./02-系统架构设计.md)），通道开关与配置在设置页。

PWA Web Push 是即时层（M14 已交付）。优势是前端完全关闭时也能把通知送到锁屏，且点击能直接深链回具体页面。劣势是前置条件多（HTTPS、已安装、已授权），必然有一部分用户/场景拿不到。因此它承载「需要用户立刻决策」的事件，主要就是 agent 的人工确认请求。**M29 起用途放宽一条**：作业研究结束（`copilot_research_finished`，Q48）也走浏览器推送，与 M27 的养成计划完成通知同一口径；这条放宽记在 [13 §8.9 的旁注与 §8.44](./13-决策记录.md) 九（该事件的发送接线仍是遗留，见 §8.44 十、7）。设置页的通知通道事件清单同步加上「作业研究结束」，与后端 `NotifyEvent` 的取值一一对应。

WebSocket + 应用内提示是前台层。用户正看着页面时，不该收到系统通知（重复且干扰）。通过 WS 推送 → 任何页面的标题栏出现「N 项待确认」、首页出现横幅，点开是全局待确认面板（[§6.6](#66-全局待确认)）。原方案的 toast 与 `navigator.vibrate` 震动反馈没有实现。判断依据是 `document.visibilityState === 'visible'`（服务端侧的判断见 [13 §8.11](./13-决策记录.md)）。

### 13.1 人工确认的触达设计

人工确认是三条通道唯一需要协同的场景。[README 决策表](./README.md#决策速查表)规定确认渠道是「前端经 WebSocket 收到待确认事件并弹卡片，超时自动拒绝」，但如果用户此刻没开页面，这个确认必然超时。所以实际是一个三级递进：

1. WebSocket 推 `confirm_request`。前端在线 → 待确认数量刷新，标题栏的「N 项待确认」或首页横幅出现，点开全局待确认面板处置。
2. 同时后端检查：若没有正在查看页面的客户端（M14 补正后按页面可见性判断，见 [13 §8.11](./13-决策记录.md)），立即走 Web Push 推送。通知标题写清操作内容（「Agent 请求碎石 3 颗」），`data` 里带 confirmation id；点击通知的 `notificationclick` 处理器打开 `/?confirm=<id>`，全局待确认面板自动打开并定位到这一条（M16 起任何路由上的 `?confirm=` 都生效，见 [§6.6](#66-全局待确认)）。
3. 若没有可用的 push 订阅（HTTP 部署 / 未安装 / 未授权），退到 Bark 或钉钉，消息体里带一个可点击的深链（`https://<host>/?confirm=<id>`）。

第 2 步的技术要点：Web Push 的 `userVisibleOnly: true` 是强制的（浏览器要求每次 push 都必须显示一个可见通知），所以 SW 的 `push` 事件处理器里必须调用 `showNotification()`，不能静默处理。

后端侧需要：VAPID 密钥对（生成一次，公钥下发给前端作为 `applicationServerKey`，私钥存配置）、`push_subscription` 表存 `endpoint` / `p256dh` / `auth` 三个字段、以及发送端。订阅在 `pwa/push.ts` 里完成：

实施时的两处调整（M14，见 [13 §8.9](./13-决策记录.md)）：发送端不用 `pywebpush`，而是用已有直接依赖 `cryptography` 自行实现 RFC 8291 / 8188 加密与 RFC 8292 的 ES256 JWT：本机网络对 PyPI 不稳定，把安装步骤变成构建的单点故障不划算；加密正确性由 RFC 8291 Appendix A 的官方向量锁定。另外 Service Worker 从 `generateSW` 换成 `injectManifest` + 自写的 `web/src/sw.ts`，因为生成的 Worker 没有 `push` 事件处理，而 Web Push 的通知完全依赖它；预缓存改用 Cache API 自实现，同样不引入 Workbox 运行时依赖。

```ts
const reg = await navigator.serviceWorker.ready
const sub = await reg.pushManager.subscribe({
  userVisibleOnly: true,                       // 必需，浏览器强制
  applicationServerKey: vapidPublicKey,        // 从 GET /api/notify/vapid-public-key 取
})
await api.POST('/api/notify/push-subscriptions', { body: sub.toJSON() })
```

权限申请必须由真实用户手势触发（「设置 › 通知」`/more/settings/notifications` 里的「启用推送通知」按钮），不能在页面加载时自动调 `Notification.requestPermission()`：iOS 会直接忽略非手势触发的请求，Chromium 会记一次「被动拒绝」影响后续提示。

### 13.2 确认超时与推送触达的矛盾

确认超时原定统一 120 秒（[02 §8.2](./02-系统架构设计.md)），这与推送触达之间有矛盾：推送从后端发出，到用户听见、解锁手机、点开应用、读完卡片再决定，120 秒往往不够。结果是 agent 的高风险操作几乎总是超时自动拒绝，确认机制形同虚设。

已拍板：超时按风险级别分级。消耗类与破坏类默认 10 分钟，原子操作的会话授权保持 120 秒，两者都可配置。分级的理由是这两类等待场景不同：前者靠推送触达，值得等；后者触发时用户正在对话界面前主动让 agent 动手，此刻就在看屏幕，放长反而会让一个已经没人管的授权请求挂在那里。

同时已拍板：为 Chromium 平台做推送上的「准许 / 拒绝」按钮，作为渐进增强。成本不高，Android 上能省掉打开应用这一步。但流程不能以它为前提：下面的核实结果说明 Apple 平台完全不渲染这些按钮。

「在推送上放准许 / 拒绝按钮」这条路在 Apple 平台上不通。核实了 WebKit 的通知能力边界，结论是它对 Web Push 的支持范围远小于 Chromium：

| 通知选项 | Chromium（桌面 / Android） | WebKit（macOS / iOS） |
|---|---|---|
| `actions`（按钮） | 渲染，最多 2 个 | **忽略** |
| `requireInteraction`（常驻不自动消失） | 桌面端生效 | **忽略** |
| `image`、`icon`、`badge` | 渲染 | 忽略，只用应用自身图标 |
| `title`、`body`、`tag`、`data` | 生效 | 生效 |
| `notificationclick` 事件 | 正常触发 | 正常触发 |

被忽略的选项静默失效，不抛异常也不打控制台警告，所以本地调试时很容易误以为生效了。

这带来两个后果。其一，iOS 上唯一可行的响应路径是「点通知体 → 深链回确认卡片 → 在应用内批准」，中间多了打开应用这一步。其二，`requireInteraction` 被忽略意味着通知会自动消失，用户如果当时没看到，等回过神来通知已经不在通知中心显眼处了。

因此稳妥的做法是把超时放长，不在通知上直接响应。具体放多长、以及要不要为 Android 额外做 action 按钮，是接下来要做的取舍。

实现上通知本身要按「Apple 卡片优先」设计：把完整信息（要执行什么操作、涉及多少消耗）写进 `title` 与 `body`，用 `tag` 做同类合并，用 `data.url` 承载深链目标，这样它在两个平台上都读得通。Chromium 上的 `actions` 属于渐进增强，不能作为流程的前提。

`notificationclick` 要同时处理三种入口，其中「点通知体」是两个平台共有的路径：

```ts
self.addEventListener('notificationclick', (event) => {
  event.notification.close()
  const { confirmationId, url } = event.notification.data
  // action 为空字符串 = 点了通知体本身（iOS 只会走到这里）
  if (event.action === 'approve' || event.action === 'reject') {
    event.waitUntil(resolveConfirmation(confirmationId, event.action === 'approve'))
  } else {
    event.waitUntil(focusOrOpen(url))   // 深链回确认卡片
  }
})
```

三个细节容易写错。`event.action` 在点击通知体时是空字符串而非 `undefined`，所以分支要按具体 action 值判断而不是判空。`resolveConfirmation` 的 fetch 必须从 IndexedDB 取 token 注入 `X-Token` 头（原因见 [§10.1](#101-token-的录入与存储)），同源自动携带的 cookie 不足以通过写操作的鉴权。而 `focusOrOpen` 要先用 `clients.matchAll()` 查有没有已打开的窗口并 `focus()` 加导航，直接 `clients.openWindow()` 会在应用已经开着时又开一个。

从 action 按钮批准后要给用户一个结果反馈，否则他不知道到底生效了没有：在 `resolveConfirmation` 的成功与失败分支里各 `showNotification()` 一条简短结果通知（「已准许：碎石 3 颗」／「操作已过期，未执行」）。失败分支尤其不能省：确认可能在这期间已经超时，静默失败会让用户以为批准成功了。

## 14. 构建与部署集成

### 14.1 Dockerfile 改多阶段构建

现有 Dockerfile 是单阶段 `python:3.11.9-slim` + poetry，没有前端构建步骤（旧前端不需要构建）。新方案加一个 node 阶段：

```dockerfile
# ---------- 阶段 1：构建前端 ----------
FROM node:22-slim AS web

WORKDIR /web
# 先只拷依赖清单，让 npm ci 的层能被缓存
COPY web/package.json web/pnpm-lock.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile

COPY web/ ./
RUN pnpm build          # 产物落在 /web/../static，即 /static

# ---------- 阶段 2：运行时 ----------
FROM python:3.11.9-slim

WORKDIR /app

RUN apt-get update && apt-get install -y --no-install-recommends \
      curl adb libatomic1 \
    && rm -rf /var/lib/apt/lists/*

COPY pyproject.toml poetry.lock ./
RUN pip install --no-cache-dir poetry -i https://mirrors.aliyun.com/pypi/simple/ \
    && poetry install --no-root --only main

COPY maa_api/ ./maa_api/
COPY scripts/ ./scripts/
COPY config.yaml ./
# 只把前端产物拷过来，node 与 node_modules 不进最终镜像
COPY --from=web /static ./static

EXPOSE 8002

CMD ["poetry", "run", "uvicorn", "maa_api.main:app", "--host", "0.0.0.0", "--port", "8002"]
```

三个要点：`web/` 阶段的 `vite build` 的 `outDir` 是 `../static`，在容器里就是 `/static`（因为 `WORKDIR /web`），第二阶段用 `COPY --from=web /static` 取；依赖清单单独一层拷贝，改业务代码时不触发重装依赖；最终镜像不含 Node.js。

另外现有 Dockerfile 缺了 `COPY` 应用代码的步骤（依赖挂载卷运行），新版本显式拷进去。`poetry install --only main` 排除开发依赖。

### 14.2 本地开发流程

两个进程同时跑，两个终端：

```bash
# 终端 1：后端。--reload 监听 maa_api/ 的改动
poetry run uvicorn maa_api.main:app --host 0.0.0.0 --port 8002 --reload

# 终端 2：前端 dev server，带 HMR
cd web && pnpm dev
```

开发时访问 5173（dev server），不是 8002。dev server 把 `/api`、`/openapi.json`、`/docs` 代理到 8002，WebSocket 也一并转发（`ws: true`），所以前端代码里所有 URL 都写相对路径，开发与生产零差异。手机上调试时访问 `http://<电脑 LAN IP>:5173`（`server.host: true` 已开启外部访问）。

后端此时 `static/` 可能是空的或过期的，不影响开发：开发期没人访问 8002 的页面。`app.frontend(..., check_dir=False)` 保证后端在 `static/` 不存在时也能启动。

验证生产构建时跑一次 `pnpm build` 然后直接访问 8002，这一步在合并前必须做：dev server 与生产产物在路由兜底、SW 注册、资源路径上的行为是不同的，只在 5173 上测过的改动可能在 8002 上挂掉。

`scripts/start-maa-api.sh` 按 [02 §6](./02-系统架构设计.md) 的规划简化（ADB 等待逻辑移入服务），不承担前端构建职责。

### 14.3 `static/` 加入 `.gitignore`

```gitignore
# 前端构建产物
/static/
```

理由：产物是可重现的派生物，入库会让每次前端改动产生几十个哈希文件名变化的二进制 diff，PR 无法审查，仓库体积持续膨胀。

三件配套动作：

一次性删除现有 `static/` 下的所有文件并从 git 索引移除（`git rm -r --cached static/`）。旧的 `index.html`、`daily.html`、`js/app.js`、`css/style.css`、`favicon.ico` 全部废弃，`favicon.ico` 之类需要保留的静态资源移到 `web/public/`。

部署文档必须写明构建是必需步骤。克隆仓库后直接跑 uvicorn 会得到一个没有前端的服务（API 正常、访问 `/` 返回 404）。Docker 路径下多阶段构建自动处理了；裸机部署要在文档里明确写出 `cd web && pnpm install && pnpm build`。

Docker 镜像作为分发产物。不入库产物的代价是「拿到源码不等于拿到可运行的应用」，用发布镜像补上：镜像里已经含构建好的 `static/`。

### 14.4 CI 的可选做法

不是必需项，但如果加，最小有用的形态是一个 PR 检查：

```yaml
# 概念示意，非完整配置
- pnpm install --frozen-lockfile
- pnpm typecheck          # tsc --noEmit
- pnpm lint
- pnpm gen:api:check      # 校验 api.d.ts 与 openapi.json 一致（见 10 号文档 §6.1）
- pnpm build              # 构建必须能过
```

`pnpm gen:api:check` 是其中最有价值的一条：它会在「后端改了接口但没同步类型」时让 CI 变红，不必等到运行时才发现。

镜像构建可以做，但对私有部署项目收益有限：除非有多台机器要部署，否则本地 `docker build` 就够。

### 15.4 按星期配置的任务组合

`static/daily.html` 的数据结构是本次迁移信息量最大的一块。它的形态是：

```jsonc
{
  "enable": true,                       // 定时任务总开关
  "task_dict": {                        // 命名的任务组合库
    "日常": [ /* task 对象数组 */ ],
    "剿灭": [ /* ... */ ],
    "周本": [ /* ... */ ]
  },
  "weekday_task": {                     // 星期 → 组合名
    "0": "日常",   // 周一
    "1": "日常",   // 周二
    "2": "剿灭",   // 周三
    "3": "日常",
    "4": "日常",
    "5": "周本",
    "6": "周本"    // 周日
  }
}
```

对应接口是 `GET/PUT /api/maa/daily` 与 `POST /api/maa/daily/execute`。

注意索引约定：`"0"` 是周一，`"6"` 是周日，这与 JavaScript `Date.getDay()`（0 = 周日）和 Python `datetime.weekday()`（0 = 周一）中的后者一致。迁移时若弄错这个偏移，所有人的定时任务会整体错一天，而且这种错误在测试里很难发现（要跨周才显形）。新的定时任务模块应当在数据库里用明确的字段名（`weekday` 且注明 1=周一 或直接存 cron 表达式）。

「命名的任务组合库 + 星期到组合的映射」这个两层模型要保留。它比「每天独立配一套任务」好用得多：改一次「日常」组合，五天的配置同时生效。新模块在此基础上扩展：

- 首页的快捷入口直接复用定时任务，避免同一套配置维护两遍：M16 的首页「运行定时任务」列出定时任务并立即运行，不另设「快捷启动」收藏

实施现状（与上面的两层模型不同）：每个定时任务各自保存名称、cron、时区与任务模板，没有可被多个定时共享的命名组合库；一天多条定时、上次执行结果与下次触发时间都已实现（[§6.2](#62-任务-tasks) 的「定时」）。
- `weekday_task` 的单一映射升级为支持 cron 表达式（决策表要求「可视化配置执行时间」，旧实现只能按星期、执行时刻写在后端配置里不可改）
- 一天可以有多条定时（早上跑日常、晚上跑剿灭），旧模型每天只能一条
- 每条定时记录上次执行结果与下次触发时间，旧版本完全没有可观测性

迁移路径：写一个一次性脚本读 `config.yaml` 里的旧 `daily` 配置，把 `task_dict` 转成新的任务组合记录、`weekday_task` 转成 7 条（或按去重后的组合数）cron 定时记录。这个脚本属于 [04-数据模型与持久化](./04-数据模型与持久化.md) 的数据迁移范畴。

### 15.6 在核对 `task.py` 时发现的问题

逐个任务类型核对参数时发现以下几处，需要在重构后端 `domain/task.py` 时一并处理，一并记录以免遗漏：

`InfrastTask` 的 `failename` 是 `filename` 的拼写错误。构造函数参数名写作 `failename`，但文档字符串里写的是 `filename`，MaaCore 期望的键名也是 `filename`。当前这个参数实际上完全不生效：传进去的键是 `failename`，内核不认。自定义基建方案（`mode == 10000`）因此从未真正可用。

`InfrastTask.threshold` 的默认值与文档不符。代码里是 `threshold: float = 0.5`，文档字符串写「默认 0.3」。已确认以 0.3 为期望值，签名里的 0.5 是错的。前端表单不硬编码这个值，而是把 0.3 作为占位提示文案展示（「留空则使用内核默认值 0.3」）。请求体里该字段为 `None` 时不传给内核，由内核用自己的默认值，理由见 [05 §7.2](./05-API规范与路由清单.md)。

`ReclamationTask` 的 `params` 字典构造方式是错的。它写的是 `{enable: enable, theme: theme, ...}`：用变量作为 key。这会让字典的键变成参数值本身（`None` 或传入值），产出的 params 完全不可用。这是 `Reclamation` 任务从未被前端暴露、因此错误一直没被发现的直接后果。其 `theme` 的文档字符串也写着「默认为 1」，但取值是 `"Fire"` / `"Tales"` 字符串。

`Roguelike.theme` 的可选值可能已过时。`task.py` 列了 `Phantom` / `Mizuki` / `Sami` / `Sarkaz` 四个，但本地 MaaCore 是 v6.17.x，其间官方可能已新增主题。这类会随内核版本变化的枚举不该在 Python 里写死：建议 `GET /api/tasks/types` 在返回 schema 时，对这类枚举从 MaaCore 资源目录的 `tasks.json` 动态派生，资源热更新后自动跟上。这也是把 schema 放后端生成的又一个理由。

任务类型的数量口径需要统一。`task.py` 里有 9 个 `Task` 子类，这份方案按 9 种覆盖。若「8 种」的口径来自排除 `Reclamation`（因其实现有上述缺陷），需要明确是修好它还是正式不支持：这影响前端是否要为它生成表单。
