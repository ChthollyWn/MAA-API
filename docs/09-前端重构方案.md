# 前端重构方案

## 1. 范围与前提

现有 `static/` 下的四个文件全部废弃：`index.html`（734 行，Vue 3 global build + Element Plus 从 unpkg CDN 加载，无构建工具，8 种任务的表单用 `v-if="task.type_name === 'StartUp'"` 硬编码堆在一起）、`daily.html`、`js/app.js`、`css/style.css`。新前端是独立的 Vite 工程，源码在 `web/`，构建产物落到 `static/`，由 FastAPI 单进程在 8002 端口托管。

技术栈已定：**Vite + React + TypeScript + Tailwind CSS + shadcn/ui**。形态是 **Web + PWA**，**移动端优先**、桌面自适应，导航用**底部 Tab 栏**。

三条贯穿全文的设计前提：

**所有依赖打进 bundle，不留任何 CDN 外链。** 旧前端从 unpkg 拉 Vue、Element Plus、axios，这意味着内网无外网出口时页面直接白屏。新前端离线可用是硬要求。

**后端不再有模板渲染。** `router/template.py` 里两个返回 `FileResponse` 的路由一并废弃，SPA 的所有路径由前端路由处理，后端只负责把 `index.html` 交出去（见 [§5](#5-后端托管配置变更)）。

**表单不再硬编码。** 任务参数的权威来源是后端 `GET /api/tasks/types` 返回的参数 schema，前端按 schema 生成控件（见 [§7](#7-任务表单的-schema-驱动生成)）。

`static/` 不再有手写文件，全部由 `vite build` 生成，加入 `.gitignore`（见 [§14](#14-构建与部署集成)）。

## 3. 依赖清单与选型理由

版本为 2026 年 9 月核实到的当前稳定版，写进 `package.json` 时用 `^` 允许小版本升级。

### 3.1 构建与语言

| 包 | 版本 | 用途 |
|---|---|---|
| `vite` | ^8.3.0 | 构建工具与 dev server |
| `@vitejs/plugin-react` | ^6.1.1 | React 支持与 Fast Refresh |
| `typescript` | ^6.0 | 类型检查 |
| `react` / `react-dom` | ^19.3.0 | UI 运行时 |

Vite 是唯一必须的构建工具选择，理由不在于它比 webpack 快，而在于三件本项目直接依赖的能力：`server.proxy` 能把开发期的 `/api`、`/mcp` 与 WebSocket 一起转发到 8002，省掉前后端分离时的 CORS 配置；`build.outDir` 可以直接指向仓库外的 `../static`，产物无需二次拷贝；生态里有 `vite-plugin-pwa` 这类成熟插件把 Workbox 的配置复杂度收进插件选项。

Vite 8 的两个变化会影响写法，必须注意：**打包器从 Rollup 换成了 Rolldown**，`build.rollupOptions` 已改名 `build.rolldownOptions`（旧名仍被兼容层自动转换但已废弃），`output.manualChunks` 的对象形式被移除、函数形式废弃，手动分包改用 `output.codeSplitting.groups`；**JS 转换与压缩从 esbuild 换成 Oxc**，CSS 压缩换成 Lightning CSS。另外 `build.target` 默认值对应的 Safari 下限是 16.4，恰好与 iOS Web Push 的最低版本一致，不需要额外调低。

`@vitejs/plugin-react` 是唯一该用的 React 插件。`@vitejs/plugin-react-oxc` 已废弃，其 Oxc 能力合并回了官方插件，在 Vite 8 下会自动启用 Oxc 版 Fast Refresh。React Compiler 目前是实验特性（需额外安装 `oxc-transform-react` 并传 `compiler: true`），首版不开。

### 3.2 UI 与样式

| 包 | 版本 | 用途 |
|---|---|---|
| `tailwindcss` | ^4.3 | 样式 |
| `@tailwindcss/vite` | ^4.3 | Tailwind 的 Vite 插件 |
| `shadcn`（CLI，仅 devDependency 或 npx 调用） | latest | 组件生成 |
| `@radix-ui/*` | 随组件按需引入 | shadcn/ui 底层无样式原语 |
| `vaul` | 随 Drawer 组件引入 | 底部抽屉 |
| `sonner` | 随 Toaster 组件引入 | toast |
| `lucide-react` | 随 shadcn/ui init 安装 | 图标 |
| `class-variance-authority` / `clsx` / `tailwind-merge` | 随 shadcn/ui init 安装 | 变体与类名合并 |

表中标「随…安装」的几项不手工写进 `package.json`，由 `shadcn` CLI 在 `init` 与 `add` 时按当前组件实现所需的版本自动追加，避免人工锁的版本与组件源码不匹配。

Tailwind v4 必须用 `@tailwindcss/vite` 插件而非 PostCSS 路线，且版本不能低于 4.2.2 —— 4.2.2 之前的 `@tailwindcss/vite` 的 peer 范围不包含 Vite 8，安装会报冲突。v4 没有 `tailwind.config.js`，所有设计令牌写在 CSS 的 `@theme` 块里，入口是 `@import "tailwindcss"`（v3 的 `@tailwind base/components/utilities` 三行在 v4 是错的）。

选 Tailwind 而非组件库自带样式体系，核心原因是移动端需要大量非常规布局：安全区内边距、底部抽屉的把手区、日志行的密排版、设备截图的自适应容器。这些用原子类现场组合比覆盖组件库的 CSS 变量更直接。

shadcn/ui 不是 npm 依赖，而是用 CLI 把组件源码写进 `src/components/ui/`。这个模式对本项目是净收益：组件代码在仓库里，改一个控件的移动端表现不必和上游 API 抗争；底层是 Radix 原语，键盘导航、焦点陷阱、ARIA 属性已经做对，自己写这些是纯浪费。初始化用 `npx shadcn@latest init`（Tailwind v4 项目下 `components.json` 的 `tailwind.config` 留空，`tailwind.css` 指向 `src/index.css`），组件按需 `npx shadcn@latest add drawer dialog tabs form select switch slider ...`。

需要注意 shadcn CLI v4 开始支持 `--base radix | baseui` 两套原语，本方案按决策表明确使用 **Radix**，初始化时显式指定，避免默认值变化导致组件 API 漂移。`toast` 组件已废弃，统一用 `sonner`。

`lucide-react` 是 shadcn/ui 的默认图标库，按需 tree-shake，不额外引入第二套图标。

### 3.3 路由与状态

| 包 | 版本 | 用途 |
|---|---|---|
| `react-router` | ^7.18 | 路由 |
| `@tanstack/react-query` | ^5.101 | 服务端状态 |
| `zustand` | ^5.0 | 本地状态 |

React Router v7 用 library 模式（`createBrowserRouter` + `RouterProvider`），不用它的 framework 模式 —— 后者会引入自己的构建流程和服务端渲染约定，和「静态产物交给 FastAPI 托管」的部署形态冲突。从 v7 起 `react-router-dom` 只是对 `react-router` 的重导出，新代码直接依赖 `react-router`。

TanStack Query 负责一切来自后端的数据。它解决的是本项目里一个具体且高频的问题：同一份状态（流水线进度、设备连接态、内核版本）要在首页、任务页、更多页同时显示，还要被 WebSocket 推送更新。手写 `useEffect` + `useState` 的做法在旧前端已经能看到后果 —— `app.js` 里每个接口都重复一遍 `axios.then/catch/$notify`，共 7 处结构相同的样板，且没有任何缓存与去重。Query 的 `queryKey` 提供了一个天然的「按 key 精准失效」的入口，正好接 WebSocket 事件（见 [§9.5](#95-与-tanstack-query-缓存的协作)）。

Zustand 只用于确实不属于服务端的状态：token 与登录态、主题、抽屉栈、日志的内存环形缓冲。选它而非 Redux 是因为不需要 action/reducer 的仪式感；选它而非纯 Context 是因为日志缓冲每秒可能更新几十次，Context 的整树重渲染会直接卡死长列表，而 Zustand 的选择器订阅只重渲染真正读了那块状态的组件。

### 3.4 表单与校验

| 包 | 版本 | 用途 |
|---|---|---|
| `react-hook-form` | ^7.87 | 表单状态 |
| `zod` | ^4.5 | 校验 schema |
| `@hookform/resolvers` | ^5.7 | 两者桥接 |

任务表单是本次重构技术难度最高的一块：9 种任务类型、单个类型最多 24 个参数、大量参数之间有可见性依赖。React Hook Form 的非受控模式让「一个页面上同时挂 5 个任务的表单」不会因为某个数字输入框的每次击键触发整页重渲染。Zod 负责把后端 schema 的 `minimum` / `maximum` / `enum` 转成运行时校验（见 `lib/schema-to-zod.ts`），配合 `@hookform/resolvers/zod` 在提交前拦住非法值，而不是等后端返回 422。注意 `@hookform/resolvers` 5.x 的 peer 同时支持 Zod 3 与 4，本项目固定用 Zod 4。

### 3.5 长列表与图表

| 包 | 版本 | 用途 |
|---|---|---|
| `@tanstack/react-virtual` | ^3.14 | 虚拟滚动 |
| `react-zoom-pan-pinch` | ^4.0 | 设备截图的捏合缩放 |
| `recharts` + `react-is` | ^3.10 | 掉落统计图表（可选） |

虚拟滚动在日志页是必需项而非优化项。三路日志汇聚后，一次完整的日常流水线能产生上千行，其中夹杂 base64 截图。旧前端的 `v-for` 全量渲染在移动端会直接白屏。`@tanstack/react-virtual` 是 headless 的，只给 `useVirtualizer` 返回的位置计算，DOM 完全自己写，这对「日志行高度不固定、图片行明显更高」的场景是必要的（需要 `measureElement` 做动态测量）。

`react-zoom-pan-pinch` 用于首页设备截图的双指缩放与拖动（`TransformWrapper` / `TransformComponent`）。手写 pointer 事件处理双指手势、边界约束、惯性，是典型的「看起来简单做起来两周」的活。

图表标记为可选：掉落统计不是首版必需功能。如果做，用 `recharts` 而非 ECharts —— shadcn/ui 的 Chart 组件就是基于 recharts 的封装，主题令牌能直接复用；ECharts 体积大且样式体系独立。注意 recharts 3.x 要求同时安装 `react-is` 且版本需与 React 对齐。

### 3.6 PWA 与类型生成

| 包 | 版本 | 用途 |
|---|---|---|
| `vite-plugin-pwa` | ^1.3.0 | manifest 注入 + Service Worker 生成 |
| `workbox-window` / `workbox-build` | ^7.4.1 | 由插件间接依赖，需显式声明以锁版本 |
| `openapi-typescript` | ^7.13 | 从 OpenAPI 生成 TS 类型 |
| `openapi-fetch` | ^0.17 | 类型安全的 fetch 封装 |

`vite-plugin-pwa` 1.3.0 是第一个 peer 范围包含 Vite 8 的版本，1.2.x 及更早会报 peer 冲突。它把 Workbox 的 `generateSW` 流程包成插件选项，省掉手写 `workbox-config.js` 和额外构建步骤，同时提供 `virtual:pwa-register/react` 这个虚拟模块导出 `useRegisterSW`，直接拿到 `needRefresh` 与 `updateServiceWorker`，更新提示的 UI 不必自己盯 `ServiceWorkerRegistration` 的事件。

`openapi-typescript` 与 `openapi-fetch` 的生成流程、产物是否入库、后端改接口后的同步规则，全部在 [10-开放API与调试台](./10-开放API与调试台.md) 里定义，此处不重复。

### 3.7 API 调试台的额外依赖

| 包 | 版本 | 用途 |
|---|---|---|
| `@uiw/react-codemirror` | ^4.25 | 请求 body 的 JSON 编辑器 |
| `@codemirror/lang-json` | ^6 | JSON 语法与折叠 |

## 4. Vite 配置要点

```ts
// web/vite.config.ts
import path from 'node:path'
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'
import tailwindcss from '@tailwindcss/vite'
import { VitePWA } from 'vite-plugin-pwa'

const API_TARGET = process.env.MAA_API_TARGET ?? 'http://127.0.0.1:8002'

export default defineConfig({
  base: '/',
  resolve: {
    alias: { '@': path.resolve(import.meta.dirname, 'src') },
  },
  plugins: [react(), tailwindcss(), VitePWA({ /* 见 §11 */ })],

  server: {
    host: true,          // 监听 0.0.0.0，手机连同一 Wi-Fi 才能访问 dev server
    port: 5173,
    proxy: {
      // ws: true 让 /api/ws 的 Upgrade 请求也走同一条代理规则
      '/api': { target: API_TARGET, changeOrigin: true, ws: true },
      '/mcp': { target: API_TARGET, changeOrigin: true },
      '/openapi.json': { target: API_TARGET, changeOrigin: true },
      '/docs': { target: API_TARGET, changeOrigin: true },
      '/redoc': { target: API_TARGET, changeOrigin: true },
    },
  },

  build: {
    outDir: path.resolve(import.meta.dirname, '../static'),
    emptyOutDir: true,   // outDir 在 root 之外，不显式置 true 则 Vite 拒绝清空
    sourcemap: true,
    rolldownOptions: {
      output: {
        entryFileNames: 'assets/[name]-[hash].js',
        chunkFileNames: 'assets/[name]-[hash].js',
        assetFileNames: 'assets/[name]-[hash][extname]',
        codeSplitting: {
          groups: [
            { name: 'vendor-editor', test: /node_modules[\\/](@codemirror|@uiw|@lezer)/ },
            { name: 'vendor-charts', test: /node_modules[\\/](recharts|d3-|victory-)/ },
          ],
        },
      },
    },
  },
})
```

**`base: '/'`** 因为前端就挂在站点根路径。如果将来要挂到 `/app` 之类的前缀下，`base` 与 React Router 的 `basename`、PWA manifest 的 `scope`/`start_url`、Workbox 的 `navigateFallback` 四处必须同步改，所以现在不留这个口子。

**`outDir` 与 `emptyOutDir`。** `outDir` 指向仓库根的 `static/`，`emptyOutDir: true` 确保每次构建清掉上一轮的哈希文件（否则 `static/` 会无限堆积历史 chunk）。由于 `outDir` 在 Vite root 之外，不显式声明 `emptyOutDir` 时 Vite 会拒绝清空并打印警告，这是必须显式写的原因。旧前端遗留的 `favicon.ico`、`js/`、`css/` 需要一次性手工删除，新的静态资源放 `web/public/`。

**dev server 代理。** `'/api'` 规则加 `ws: true`，HTTP 请求与 `/api/ws` 的 WebSocket 升级共用一条规则，前端代码里 WebSocket 的 URL 写成相对路径（由 `location` 推导），开发与生产完全一致，不需要环境判断。`/openapi.json` 与 `/docs` 也要代理，否则 API 调试台在开发期拉不到契约。`MAA_API_TARGET` 环境变量留给「后端跑在另一台机器上」的调试场景。

**产物命名与缓存策略。** 所有 JS/CSS/字体/图片带内容哈希落在 `assets/` 下，`index.html` 与 `sw.js` 不带哈希。对应的后端响应头策略（见 [§5.3](#53-缓存响应头)）是 `assets/*` 长期 immutable、`index.html` 与 `sw.js` 必须 `no-cache`。这个分工是 SPA 更新能生效的前提：浏览器每次导航都重新取 `index.html`，从里面读到新的哈希文件名，旧文件因为哈希不同不会被误用。

**手动分包。** 只对两块「大且非首屏必需」的依赖显式分组：CodeMirror（只有 API 调试台用）与图表库（只有统计页用）。其余交给 Rolldown 自动分包，不要过度干预 —— 手写分组规则在依赖升级后会静默失效。注意这里用的是 Vite 8 的 `codeSplitting.groups`，不是已被移除的 `manualChunks` 对象形式。

**`sourcemap: true`** 在生产构建也开。这是私有部署的内部工具，产物不公开，source map 换来的线上问题排查能力远大于几百 KB 的额外磁盘占用。若介意，改 `'hidden'`（生成文件但不在 JS 里引用）。

## 5. 后端托管配置变更

### 5.1 现状

```python
# maa_api/main.py（现状）
app.mount("/static", StaticFiles(directory=STATIC_PATH), name="static")
```

```python
# maa_api/router/template.py（现状）
@router.get("/", dependencies=[Depends(token_auth)])
async def index():
    return FileResponse(STATIC_PATH / "index.html")

@router.get("/daily", dependencies=[Depends(token_auth)])
async def daily():
    return FileResponse(STATIC_PATH / "daily.html")
```

这套「每个页面一条路由」的做法对 SPA 不成立：前端有十几个路径（`/tasks/new`、`/logs/core`、`/more/settings`…），且路径会随功能增加而变化，不可能在后端逐个登记。

### 5.2 新方案：`app.frontend()`

FastAPI 0.138.0 起提供了正好解决这件事的原语：

```python
# maa_api/main.py（新）
app = FastAPI(
    title="MAA-API",
    openapi_tags=OPENAPI_TAGS,     # 见 10 号文档
    lifespan=lifespan,
)

# 1. 先注册所有 API 路由与 WebSocket
for router in API_ROUTERS:
    app.include_router(router, prefix="/api")
app.include_router(ws_router)                  # /api/ws

# 2. 再挂 MCP 的 ASGI 子应用
app.mount("/mcp", mcp_app)

# 3. 最后交出前端静态产物
app.frontend("/", directory=STATIC_PATH, fallback="index.html", check_dir=False)
```

需要把 `pyproject.toml` 里的 `fastapi = "^0.95.0"` 提到 `^0.138`。

`app.frontend()` 的语义解决了「catch-all 会吞掉一切」这个老问题，关键在于它**不是**一条注册在路由表里的 catch-all 路由，而是一个仅在**所有正常路由都没匹配上之后**才生效的兜底。由此得到三条我们需要的保证：

- `/api/*`、`/api/ws`、`/docs`、`/redoc`、`/openapi.json` 都是正常的 path operation 或 mount，优先级高于前端，不会被吞掉。即使 API 路由自己抛 404，返回的也是 API 的 JSON 错误体而不是 `index.html`。
- `fallback="index.html"` 只对 `GET` / `HEAD` 且 `Accept` 头里显式包含 `text/html` 或 `application/xhtml+xml` 的请求生效 —— 也就是浏览器的导航请求。缺失的 `.js` / `.css` / `.png` 仍然正常返回 404，不会拿到一份 HTML 导致「MIME type mismatch」这类难查的错误。
- `POST` / `PUT` 打到只能匹配前端兜底的路径时返回 404，不会被误当成页面请求。

因为注册顺序不影响优先级，写在最后只是为了阅读时一眼看出层次。`check_dir=False` 是必须的：`static/` 由前端构建生成，后端进程可能在前端还没构建时就创建了 app 对象（开发期尤其如此），默认的 `check_dir="auto"` 在非 development 环境会直接抛错。

`fallback` 的默认值是 `"auto"`（目录里有 `404.html` 就用它、否则用 `index.html`），对我们的 SPA 而言显式写 `"index.html"` 更清晰，也避免将来误放一个 `404.html` 导致客户端路由失效。

### 5.3 缓存响应头

`app.frontend()` 不负责按路径区分缓存策略，需要一个窄中间件补上：

```python
@app.middleware("http")
async def frontend_cache_headers(request: Request, call_next):
    response = await call_next(request)
    path = request.url.path
    if path.startswith("/assets/"):
        # 文件名带内容哈希，可以永久缓存
        response.headers["Cache-Control"] = "public, max-age=31536000, immutable"
    elif path == "/" or path.endswith((".html", "/sw.js", "/manifest.webmanifest")):
        # 入口与 Service Worker 必须每次校验，否则新版本永远发布不出去
        response.headers["Cache-Control"] = "no-cache"
    return response
```

`sw.js` 的 `no-cache` 是硬要求。浏览器对 Service Worker 脚本本身有更新检查机制，但如果 HTTP 层给了长缓存，更新检查会拿到缓存副本，导致用户长期停在旧版本外壳上 —— 而旧外壳引用的是已经被 `emptyOutDir` 删掉的哈希文件名，表现为白屏。

### 5.4 若后端锁在低版本 FastAPI

作为备选（不推荐，仅在无法升级 FastAPI 时使用），手写兜底路由。要点是：必须注册在所有 API 路由之后、必须显式排除保留前缀、必须做路径穿越校验、必须只对 HTML 导航请求返回 `index.html`。

```python
RESERVED_PREFIXES = ("/api", "/mcp", "/docs", "/redoc", "/openapi.json")
STATIC_ROOT = STATIC_PATH.resolve()

app.mount("/assets", StaticFiles(directory=STATIC_ROOT / "assets"), name="assets")

@app.get("/{spa_path:path}", include_in_schema=False)
async def spa_fallback(spa_path: str, request: Request):
    if request.url.path.startswith(RESERVED_PREFIXES):
        raise HTTPException(status_code=404)

    candidate = (STATIC_ROOT / spa_path).resolve()
    if candidate.is_relative_to(STATIC_ROOT) and candidate.is_file():
        return FileResponse(candidate)

    accept = request.headers.get("accept", "")
    if "text/html" not in accept and "application/xhtml+xml" not in accept:
        raise HTTPException(status_code=404)

    return FileResponse(STATIC_ROOT / "index.html", headers={"Cache-Control": "no-cache"})
```

`candidate.is_relative_to(STATIC_ROOT)` 这一行不能省。少了它，`GET /../../config.yaml` 就能读到仓库外的任意文件。这也是优先选用 `app.frontend()` 的一个理由 —— 这类安全细节交给框架比自己写更可靠。

### 5.5 前端页面是否需要鉴权

旧方案在 `/` 和 `/daily` 上挂了 `Depends(token_auth)`，这对 SPA 是错的设计：应用外壳本身不含任何敏感数据，把它锁住只会让「打开页面 → 输入 token」这个正常流程变成「必须先在 URL 上带 token 才能看到输入 token 的界面」，正是旧前端 `getToken()` 从 query string 读取、每个跳转都要手工拼 `?token=` 的根源。

新方案：**`index.html` 与 `assets/*` 公开，所有 `/api/*` 鉴权。** 未登录用户能拿到外壳，外壳发现没有 token 就渲染 token 录入页。数据一行都拿不到。鉴权细节见 [§10](#10-鉴权在前端的处理)。

底部 Tab 五个主入口，次级页面收进「更多」。

| Tab | 路径 | 图标语义 |
|---|---|---|
| 首页 | `/` | 仪表盘 |
| 任务 | `/tasks` | 列表 |
| 日志 | `/logs` | 终端 |
| Agent | `/agent` | 对话 |
| 更多 | `/more` | 九宫格 |

路由表用 `createBrowserRouter`，除首页外全部 `lazy` 加载。`/agent`、`/more/api-console`、`/more/audit` 是明确的按需页面，让它们进首屏 bundle 没有意义。

### 6.1 首页 / 仪表盘 `/`

移动端一屏内要回答「现在能不能用、正在干什么、有没有事等我」。自上而下五块：

**设备截图。** 首屏最大的视觉元素。数据来源 `GET /api/device/screenshot`（[05 §6.3](./05-API规范与路由清单.md)），默认 `backend=adb`、不归档。用 `react-zoom-pan-pinch` 包一层支持双指缩放与拖动看细节。刷新策略：默认不轮询，提供手动刷新按钮；流水线运行中时按 5 秒轮询（`refetchInterval`），流水线结束自动停。这比旧前端「进页面截一次、之后全靠手点刷新」实用，也比无条件高频轮询省电。

**三层状态卡。** 内核（`stopped` / `starting` / `ready` / `crashed` / `restarting` / `failed`，对应 [02 §4](./02-系统架构设计.md) 的状态机，线上传输用小写形式）、设备（连接状态与 ADB 地址，见 [08-ADB连接与账号渠道](./08-ADB连接与账号渠道.md)）、服务（版本、运行时长、队列深度）。三层分开展示而非合成一个「健康/不健康」，因为这三者的故障处置动作完全不同：内核 `crashed` 要看崩溃原因、设备断开要点重连、服务异常要看日志。数据来源 `GET /api/system/health`，由 WebSocket 的 `core_status` / `device_status` 事件推送更新，不轮询。

`GET /api/system/health` 是**免鉴权**端点（[05 §6.1](./05-API规范与路由清单.md)），且返回 `auth_enabled`。前端因此可以在用户还没输入 token 时就拿到它，用于两件事：判断这个实例是否开启了鉴权（未开启就跳过登录页直接进应用），以及在 token 无效时仍能显示「服务是活着的，只是你没登录」而不是一个笼统的错误页。

**当前流水线进度。** 任务链的逐项状态与耗时，当前任务高亮。数据来源 `GET /api/pipelines/current`（无运行中时返回 `{"pipeline": null}`，不是 404，前端据此渲染空态而不必把 404 当正常情况处理），由 `pipeline_status` 与 `task_status` 事件驱动更新。

**待人工确认卡片。** agent 触发高风险操作时（[README 决策表](./README.md#决策速查表)列举的消耗类与破坏类），WebSocket 推 `confirm_request`，这里立刻出现一张卡片，显示 `title` / `summary` / `caller` / `params`、以及由载荷里的 `expires_at` 本地倒计时算出的剩余秒数（不必等服务端通知，也不会因为推送延迟而显示错误的剩余时间）。准许或拒绝调 `POST /api/confirmations/{id}` 传 `{approved, reason?}`。服务端在超时或被处置后另发 `confirm_resolved` 关闭卡片。有待确认项时该卡片置顶并配合震动反馈，因为它有超时且超时自动拒绝（消耗类与破坏类默认 10 分钟，原子操作会话授权 120 秒，见 [§13.2](#132-确认超时与推送触达的矛盾)）。详见 [11-Agent模块设计](./11-Agent模块设计.md)。

**快捷启动。** 从「收藏的任务组合」里一键提交。收藏的数据结构与定时任务共用（见 [§15.4](#154-按星期配置的任务组合)），避免用户为同一套日常配置两遍。

### 6.2 任务 `/tasks`

三个子视图，顶部分段控件切换，不占 Tab 位：

**创建 / 编辑流水线** `/tasks/new`、`/tasks/:id/edit`。9 种任务类型的动态表单，完整方案见 [§7](#7-任务表单的-schema-驱动生成)。交互骨架是：任务类型列表（每行一个开关 + 已配置摘要），点行标题打开底部抽屉编辑该任务参数，抽屉里是 schema 生成的表单。任务顺序可拖拽调整 —— 这一点旧前端没有，但 MAA 的任务链顺序有语义（`StartUp` 必须在前、`CloseDown` 必须在后），必须能调。

**队列** `/tasks/queue`。展示 `PENDING` 条目的排队顺序，标注每条的来源与优先级（前端手动 0 / agent 1 / 定时 2，见 [02 §5.1](./02-系统架构设计.md)）。因为决策是「不抢占」，用户想插队必须显式停止当前流水线，所以这里要有一个明确的「停止当前并执行此条」按钮，并在点击时弹确认说明「当前流水线会被标记为已取消」。这正是 02 号文档要求的「明确的按钮，不是隐式行为」。

**历史** `/tasks/history`。分页的流水线历史列表，点进去是详情（任务逐项结果、耗时、关联日志、截图）。数据来源 `GET /api/pipelines?status=&source=&page=&size=`，用 `useInfiniteQuery`，`getNextPageParam` 依据 `{items, total, page, size}` 信封里的 `total` 与已加载条数判断是否还有下一页（[05 §3.2](./05-API规范与路由清单.md) 规定分页参数固定为 `page` 从 1 开始、`size` 默认 20 上限 200，越界返回 `400 INVALID_PAGINATION` 而不静默钳制，所以前端不能盲目递增页码，必须按 `total` 停止）。

### 6.3 日志 `/logs`

三路来源分标签页，路径分别是 `/logs/task`（MaaCore 回调任务日志）、`/logs/service`（Python 服务日志，含 uvicorn）、`/logs/core`（MaaCore 自身 debug 日志），对应 [06-实时日志与WebSocket](./06-实时日志与WebSocket.md) 定义的三路汇聚。

单个标签页的结构：顶部过滤条（级别多选、关键词、时间范围）+ 虚拟滚动列表 + 底部「跳到最新」浮动按钮。

**取数是双通道的。** 历史部分走 `GET /api/system/logs?source[]=&level[]=&after_id=&size=` 的游标分页（`useInfiniteQuery`，向上滚动加载更早）；实时部分走 WebSocket 推送，追加到 `stores/log-buffer.ts` 的环形缓冲。两者在渲染层拼接：`[...历史(倒序), ...实时]`。环形缓冲每路上限 2000 行，超出丢弃最早的 —— 这是必须的，否则挂机一夜后内存会被日志吃光。

日志端点是全项目唯一支持游标的地方：[05 §3.2](./05-API规范与路由清单.md) 规定 `after_id` 与 `page` **互斥**，同时传两者返回 `400 INVALID_PAGINATION`。日志页只用 `after_id`，不要顺手带上 `page`。

**自动吸底要有条件。** 只有当用户当前已经在底部附近（`scrollTop + clientHeight >= scrollHeight - 48`）时才自动滚到最新，否则保持位置并在底部显示「N 条新日志」的浮动按钮。无条件吸底会让「往上翻看刚才那条报错」变成不可能。

**截图行懒加载。** 日志条目有 `text` 与 `img` 两种类型（旧前端的 `log.log_type`）。`img` 行不内联 base64，而是渲染 `<img loading="lazy">` 指向后端的截图 URL，并请求缩略图尺寸（`?w=320`）；点击才打开全屏查看器加载原图。旧前端把完整 base64 塞进 JSON 响应，一条日志几百 KB，这是它在移动端不可用的主因之一。

### 6.4 Agent `/agent`

对话界面。会话列表（`/agent`）与单会话（`/agent/:sessionId`）。

**流式输出。** LLM 的回复走 SSE 或 WebSocket 增量推送（协议见 [11-Agent模块设计](./11-Agent模块设计.md)），前端逐 token 追加。要点：流式期间不要对每个 token 触发 React 重渲染整条消息树，用局部状态累积、按 ~60ms 节流提交。

**工具调用轨迹可视化。** agent 每次 tool call 渲染一张可折叠卡片：工具名、入参（JSON 折叠视图）、耗时、结果摘要、是否触发了人工确认。这是 agent 模块最重要的可观测性 —— 出错时用户需要看到「它到底调了什么」。卡片里若包含 `pipeline_id`，提供跳转到 `/tasks/history/:id` 的链接；若包含截图，内联缩略图。

**会话历史。** 落 SQLite（决策表），包含多轮历史、工具调用轨迹、token 消耗。会话列表页显示每个会话的 token 总量与最后活动时间。

### 6.5 更多 `/more`

一个分组列表页，每项跳到子页面：

| 子页 | 路径 | 内容 |
|---|---|---|
| 热更新 | `/more/updates` | 内核 / 活动资源 / 游戏本体三种更新，当前版本 vs 最新版本对比，下载进度（WS 推送）。见 [07-热更新方案](./07-热更新方案.md) |
| 定时任务 | `/more/schedules` | 可视化配置执行时间与任务组合，承接旧 `daily.html` 的按星期配置逻辑。见 [§15.4](#154-按星期配置的任务组合) |
| API 调试台 | `/more/api-console` | 自研调试面板。见 [10-开放API与调试台](./10-开放API与调试台.md) |
| 审计记录 | `/more/audit` | agent 与 API 调用的全量审计回溯 |
| 设置 | `/more/settings` | ADB 地址、MAA 路径、账号渠道默认值、通知通道、LLM 接入、token 管理。改后热生效 |

「更多」不做二级 Tab，就是一个朴素的分组列表 —— 移动端的设置类入口用列表比用宫格好找。

## 7. 任务表单的 schema 驱动生成

### 7.1 为什么必须 schema 驱动

旧前端在 `index.html` 里把 7 种任务的表单写了**两遍**（一遍只读展示、一遍可编辑创建），`daily.html` 里又写了第三遍。三份副本已经漂移：`index.html` 的 `Infrast` 只读视图缺了「无人机用途」和「源石碎片自动补货」两个字段，而创建视图和 `daily.html` 里有。更根本的问题是 `task.py` 里定义的参数远多于表单暴露的 —— `Fight` 有 13 个参数，表单只有 4 个；`Roguelike` 与 `Reclamation` 两种任务类型压根没有表单。

结论：表单必须由后端的参数定义单点生成。后端加一个参数，前端自动出现一个控件。

### 7.2 schema 契约

契约由 [05 §8](./05-API规范与路由清单.md) 定义，前端**不要自己发明一套描述符格式**。要点是：返回的不是自定义的参数数组，而是 Pydantic 直出的**标准 JSON Schema**，中文元信息挂在 `x-` 前缀的自定义关键字上（JSON Schema 规范要求校验器忽略未知关键字，所以 schema 仍然能直接喂给任何标准校验器）。

```jsonc
{
  "items": [
    {
      "name": "Fight",
      "label": "刷理智",
      "description": "刷指定关卡，支持理智药与碎石",
      "runtime_immutable": ["stage"],
      "groups": ["基础", "资源消耗", "账号", "数据上报", "高级"],
      "schema": {
        "type": "object",
        "properties": {
          "series": {
            "anyOf": [{ "type": "integer", "maximum": 6, "minimum": -1 }, { "type": "null" }],
            "default": null,
            "description": "连战次数。-1 禁用切换，0 自动选择最大可用次数",
            "x-label": "连战次数",
            "x-group": "基础",
            "x-widget": "select",
            "x-enum-labels": { "-1": "禁用切换", "0": "自动选择最大可用次数", "1": "1 次" }
          },
          "expedite_times": {
            "type": "integer",
            "x-label": "加急次数",
            "x-depends-on": { "expedite": true }
          }
        },
        "additionalProperties": false
      }
    }
  ],
  "total": 9, "page": 1, "size": 9
}
```

前端消费这份 schema 时有四个必须处理对的细节。

**`anyOf: [{...}, {"type": "null"}]` 是可选字段的常规形态**，不是特例。Pydantic 对 `int | None` 就是这么导出的。渲染前先做一次归一化：从 `anyOf` / `oneOf` 里剔掉 `{"type": "null"}` 分支，记下 `nullable: true`，再用剩下的唯一分支去查控件映射表。如果剔完还剩多个分支（真正的联合类型），退化为只读 JSON 编辑器并在开发环境打警告 —— 目前 `task.py` 没有这种字段，但留个兜底比运行时白屏好。

**`runtime_immutable` 在类型层而非字段层。** 它是一个字段名数组（如 `["stage"]`），对应 `task.py` 文档字符串里反复出现的「不支持运行中设置」。编辑一个正在运行的流水线时，名字在这个数组里的控件置灰并给出提示，而不是让用户改完再被后端拒绝。

**`groups` 是有序的中文字符串数组**，直接作为折叠面板的分区标题，字段靠自己的 `x-group` 归位。顺序即渲染顺序，前端不要重排。没有 `x-group` 的字段归入最后一个分区。`Fight` 有 13 个参数、`Roguelike` 有 23 个，不分组平铺在手机上完全不可用，所以分组是必需的而非装饰。

**`x-enum-labels` 处理「数值有特殊语义」的情况。** `series` 的 `-1` 是禁用、`0` 是自动，不是「比 1 小的次数」。注意它的 key 在 JSON 里必然是字符串（JSON 对象的 key 只能是字符串），而字段值是整数，查表时要 `String(value)`。

取值范围走 JSON Schema 原生关键字（`minimum` / `maximum` 来自 `ge` / `le`，`enum` 来自 `Literal`，`minItems` / `maxItems`），前端直接据此做客户端校验，不必解析自定义字段。`description` 取 `Field(description=...)`，内容摘自 `task.py` 的文档字符串，作为表单项的提示文案 —— 那些说明（「剿灭作战必须输入 Annihilation」「仅在 use_support 为 True 时有效」）是本项目最有价值的领域知识。

跨字段依赖由 `x-depends-on` 承载，形态是「字段名 → 期望值」的对象（如 `{ "expedite": true }`），多个键之间是「与」的关系。`task.py` 里这类约束极多：`penguin_id` 仅在 `report_to_penguin` 为真时有效、`filename` 与 `plan_index` 仅在 `Infrast.mode == 10000` 时有效、`Roguelike` 的一大批参数仅在 `theme == "Sami"` 或特定 `mode` 下有效。前端据此**禁用**（而非隐藏）该控件并显示依赖提示 —— 禁用比隐藏好，因为用户能看到「这里还有个选项，但需要先开某个开关」，隐藏会让人以为功能不存在。

按 05 的约定，客户端校验只是体验优化，服务端的 `model_validator` 仍是最终防线。前端不需要为了「本地校验绝对准确」去实现复杂的条件校验，把明显的错误挡住即可，剩下的交给 422 响应（见 §10.3 的错误呈现）。

有一个 05 尚未覆盖、需要补上的关键字：**`x-risk`**。用于标记会消耗资源的参数（`stone`、`medicine`、`expiring_medicine`、`expedite`、`shopping`、`investment_enabled`），前端在这些控件旁加醒目提示色，并在提交流水线前若任一 risk 参数非零就弹一次汇总确认。这与 agent 侧 `PolicyEngine` 的人工确认（[11-Agent模块设计](./11-Agent模块设计.md)）应当是同一套风险清单的两个出口，不该各维护一份。建议把 `x-risk` 加入 [05 §8.2](./05-API规范与路由清单.md) 的关键字表。

### 7.3 schema 到控件的映射规则

映射的输入是 §7.2 归一化之后的字段描述（剔除 null 分支、解析出 `x-widget`）。`x-widget` 存在时优先级最高，直接决定控件；不存在时按下表从类型与约束推断。

| 归一化后的 schema 特征 | 控件 | shadcn/ui 组件 |
|---|---|---|
| `x-widget: "switch"` 或 `type: boolean` | 开关 | `Switch` |
| `x-widget: "select"` 或有 `enum` 且选项 > 4 | 下拉 | `Select` |
| 有 `enum` 且选项 ≤ 4 | 分段选择 | `ToggleGroup type=single` |
| `x-widget: "stepper"` | 步进数字输入 | `Input type=number` + 加减按钮 |
| `x-widget: "tags"` | 可输入的标签编辑器 | `Command` 组合框 + `Badge` 列表 |
| `x-widget: "textarea"` | 多行文本 | `Textarea` |
| `type: integer`，`maximum - minimum <= 12` | 滑块 + 当前值标签 | `Slider` |
| `type: integer`，跨度 > 12 或无上界 | 步进数字输入 | `Input type=number` + 加减按钮 |
| `type: number`，`[0, 1]` | 百分比滑块，`step: 0.05` | `Slider` |
| `type: string`，无 `enum` | 单行文本 | `Input` |
| `type: array`，`items` 有 `enum` | 多选 | `ToggleGroup type=multiple`；选项多时改抽屉内 `Checkbox` 列表 |
| `type: object`，`properties` 固定 | 定长分组表单 | 每个 key 一行，递归套用本表 |
| `type: object`，无 `properties` | 键值编辑器 | 自绘（见 §7.4） |

注意 `x-widget: "select"` 会覆盖「选项 ≤ 4 用分段选择」的推断 —— `Fight.series` 在 05 的示例里显式标了 `select`，因为它的 `x-enum-labels` 文案很长（「自动选择最大可用次数」），塞不进分段按钮。这正是 `x-widget` 存在的意义：后端知道文案长度，前端只知道类型。

两条尺寸相关的判断依据：滑块阈值定在跨度 12，是因为 `Recruit.extra_tags_mode`（0~2）用滑块手感好，而 `medicine`（0~100）用滑块无法精确选到「3」；选项数阈值定在 4，是因为移动端 `ToggleGroup` 一行放得下 4 个 44px 的按钮，第 5 个就要换行或横向滚动，此时下拉更干净。

移动端的控件形态有两条强制规则：

**任何需要展开选择的控件都用底部抽屉，不用居中 Modal。** `Select`、多选列表、物品选择器、时间选择器全部替换为 `Drawer`（shadcn/ui 的 Drawer 基于 `vaul`，从底部推起、支持下拉关闭）。原因是单手持握时屏幕下半部分才是拇指可达区域，居中 Modal 的确认按钮往往正好落在最难点到的位置；而且软键盘弹出时居中 Modal 会被顶出可视区。

shadcn/ui 文档里的 Responsive Dialog 模式正好是我们要的：同一个组件在桌面渲染 `Dialog`、在移动端渲染 `Drawer`。用 `useMediaQuery('(min-width: 768px)')` 切换，包一个 `ResponsiveSheet` 组件，业务代码只用它。

**编辑单个任务的整套参数也在抽屉里，不跳页。** 抽屉高度 `85dvh`，内部独立滚动，底部固定「保存 / 取消」操作条并带安全区内边距。跳页编辑会丢失「我正在配一条流水线」的上下文。

### 7.4 复杂参数的具体处理

这四个是 `task.py` 里结构最复杂的参数，必须逐个给方案，否则实现时只能瞎猜。

[05 §8.2](./05-API规范与路由清单.md) 列出的 `x-widget` 取值是 `select` / `stepper` / `switch` / `tags` / `textarea`，覆盖不了这几个结构化参数。本节因此追加三个取值：`item-count-map`、`duration-map`、`ordered-list`。这三个需要同步进 05 的关键字表，否则后端不会产出、前端也就拿不到。

**`Fight.drops`：物品 ID → 数量的字典。** `task.py` 注明 key 参考 `resource/item_index.json`。让用户手填 item_id 不可行 —— 那是 `30013` 这样的数字。方案是后端新增 `GET /api/resources/items`，读取 MAA 资源目录下的 `item_index.json` 派生出 `[{ item_id, name, icon_url }]` 并缓存（资源热更新后失效重载）。前端控件是「已选行列表 + 添加按钮」：点添加打开抽屉，抽屉里是 `Command` 组合框按中文名搜索（带图标），选中后在列表追加一行（图标 + 名称 + 数量步进器 + 删除）。提交时组装成 `{ "30013": 5 }`。控件顶部常驻一行提示「任一物品达到数量即停止任务」，因为「或的关系」不符合直觉。

**`Recruit.recruitment_time`：Tag 等级 → 招募时限（分钟）的字典。** key 是固定的（等级 ≥ 3，即 3/4/5/6），默认值全为 540，即 09:00。所以这不是自由键值对，而是定长表单：三到四行，每行「4 星 Tag」配一个时长选择器。时长选择器不用原生 `<input type="time">`（它在各浏览器表现差异大且语义是时刻而非时长），改用抽屉内的两列滚轮（小时 / 分钟）。UI 层显示 `09:00`，提交时换算成 `540`。换算函数放 `lib/format.ts`，不要散落在组件里。schema 用 `properties` 固定 key 表达：

```jsonc
{
  "type": "object",
  "x-label": "希望招募时限",
  "x-widget": "duration-map",
  "properties": {
    "3": { "type": "integer", "default": 540, "x-label": "3 星 Tag", "x-unit": "minute" },
    "4": { "type": "integer", "default": 540, "x-label": "4 星 Tag", "x-unit": "minute" },
    "5": { "type": "integer", "default": 540, "x-label": "5 星 Tag", "x-unit": "minute" }
  },
  "additionalProperties": false
}
```

**`Infrast.facility`：有序的设施列表。** `task.py` 明确标注「（有序）」—— 数组顺序就是换班顺序，而不仅是「换哪些」。旧前端用 `el-select multiple` 是错的：多选框的顺序由点击顺序决定，用户完全感知不到，也无法调整。方案是一个两段列表：上半「已启用」，每行可拖拽调序并显示序号；下半「未启用」，点击加入已启用的末尾。拖拽在移动端用长按触发（`touch-action: none` + pointer 事件），并提供上移/下移按钮作为无障碍兜底。schema 标记 `x-widget: "ordered-list"` 触发这个控件。

**`Mall.buy_first` / `blacklist`：中文商品名数组，无固定枚举。** 旧前端硬编码了两个选项（「招聘许可」「龙门币」），而 `task.py` 的注释还提到「加急许可」「家具零件」。商品列表会随游戏更新变化，不该写死。方案是可输入的标签编辑器：预置常用项作为快捷候选（招聘许可、龙门币、加急许可、家具零件、碳素、技巧概要），同时允许自由输入新值。已选项渲染为可删除的 `Badge`，支持拖拽调整优先级（`buy_first` 的顺序有语义）。

另外 `Roguelike.expected_collapsal_paradigms` 同属这一类（默认值 `["目空一些", "睁眼瞎", "图像损坏", "一抹黑"]`），用同一个控件，预置候选就是这四项。

### 7.5 schema → Zod → React Hook Form

表单校验不手写，从 schema 生成：

输入是 JSON Schema 的单个 property 节点，先做 §7.2 说的 null 分支归一化，再按类型建 Zod：

```ts
// src/lib/schema-to-zod.ts
/** 剥掉 Pydantic 对 Optional 字段产生的 anyOf null 分支 */
function unwrapNullable(node: JsonSchema): { inner: JsonSchema; nullable: boolean } {
  const branches = node.anyOf ?? node.oneOf
  if (!branches) return { inner: node, nullable: false }
  const nonNull = branches.filter((b) => b.type !== 'null')
  return { inner: nonNull.length === 1 ? { ...node, ...nonNull[0] } : node, nullable: nonNull.length < branches.length }
}

export function fieldToZod(node: JsonSchema): z.ZodTypeAny {
  const { inner } = unwrapNullable(node)
  let s: z.ZodTypeAny
  if (inner.enum) {
    s = z.enum(inner.enum.map(String) as [string, ...string[]])
  } else switch (inner.type) {
    case 'boolean': s = z.boolean(); break
    case 'integer':
    case 'number': {
      let n = inner.type === 'integer' ? z.number().int() : z.number()
      if (inner.minimum !== undefined) n = n.min(inner.minimum)
      if (inner.maximum !== undefined) n = n.max(inner.maximum)
      s = n
      break
    }
    case 'array':   s = z.array(fieldToZod(inner.items!)); break
    case 'object':  s = inner.properties
      ? z.object(mapValues(inner.properties, fieldToZod))
      : z.record(z.string(), z.unknown())
      break
    default:        s = z.string()
  }
  // 后端把所有参数都当可选（缺省时套用内核默认值），前端不能强制必填
  return s.optional().nullable()
}
```

`additionalProperties: false` 不需要在 Zod 侧对应 `.strict()`—— 表单的字段集合本来就是从同一份 schema 生成的，不可能出现多余键。它的价值在服务端：拼错参数名会被 422 拒掉而不是静默忽略。

一个必须遵守的约定：**参数缺省与显式设为默认值是两种不同的语义**。`task.py` 的 `Task.__init__` 会过滤掉 `None`（`self.params = {k: v for k, v in self.params.items() if v is not None}`），未传的参数由 MaaCore 使用自己的默认值。所以表单提交时，未被用户改动过的字段不应该带上 —— 否则「MAA 更新后改了某参数默认值」这件事就永远影响不到我们。实现上用 RHF 的 `formState.dirtyFields` 过滤提交载荷，只发用户实际改过的字段。

## 8. 移动优先的设计规范

### 8.1 安全区适配

`index.html` 的 viewport 必须带 `viewport-fit=cover`，否则 iPhone 上页面不会延伸到刘海与圆角区域，`env(safe-area-inset-*)` 全部返回 0：

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover" />
<meta name="apple-mobile-web-app-capable" content="yes" />
<meta name="apple-mobile-web-app-status-bar-style" content="black-translucent" />
<meta name="theme-color" content="#0b0f19" />
```

Tailwind v4 不内置安全区工具类，用 `@utility` 自定义：

```css
/* src/index.css */
@import "tailwindcss";

@custom-variant dark (&:where(.dark, .dark *));

@utility pt-safe { padding-top: env(safe-area-inset-top, 0px); }
@utility pb-safe { padding-bottom: env(safe-area-inset-bottom, 0px); }
@utility px-safe {
  padding-left: env(safe-area-inset-left, 0px);
  padding-right: env(safe-area-inset-right, 0px);
}
/* 底部 Tab 栏：内容区固定 56px + home indicator 高度 */
@utility h-tabbar { height: calc(3.5rem + env(safe-area-inset-bottom, 0px)); }
```

底部 Tab 栏的实现要点：`fixed bottom-0`，容器用 `h-tabbar pb-safe`，图标与文字在上方的 56px 内垂直居中。页面主体加 `pb-[calc(3.5rem+env(safe-area-inset-bottom))]` 的下内边距，避免最后一条内容被 Tab 栏盖住。`h-dvh` 而非 `h-screen` 作为全屏容器高度 —— 移动端 Safari 的 `100vh` 不随地址栏收缩变化，会导致底部内容被裁掉。

底部固定的操作条（抽屉的保存按钮、日志页的过滤条）同样需要 `pb-safe`，否则在 iPhone 上按钮会压在 home indicator 上，既难点又容易触发系统手势。

### 8.2 触摸目标与间距

所有可点击元素最小 44×44 CSS px。shadcn/ui 的默认按钮尺寸（`h-9`，36px）在移动端不够，在 `components/ui/button.tsx` 的 `size` 变体里加一档 `mobile: 'h-11 px-4'` 并设为移动端默认。图标按钮用 `size-11` 而非 `size-9`。

列表行的可点区域要覆盖整行（`block w-full text-left`）而不只是文字部分。相邻可点元素之间留至少 8px 间隙 —— 开关与删除按钮挨在一起是误触高发区。

### 8.3 加载与刷新

**骨架屏，不用 spinner。** 已知布局的区域（状态卡、列表行、截图容器）用 `Skeleton` 占位，尺寸与真实内容一致，避免内容到位时的布局跳动。首页三块内容独立加载，任一块慢不阻塞其余（三个独立 `useQuery`，不用 `useQueries` 等齐）。

**下拉刷新。** 移动端用户的第一反应是下拉，必须支持。实现用一个自绘的 `PullToRefresh` 容器：监听 `touchstart`/`touchmove`，仅当 `scrollTop === 0` 且向下拖动超过 64px 时触发，触发动作是 `queryClient.invalidateQueries({ queryKey: [当前页面的 key 前缀] })`。不要引入第三方下拉刷新库 —— 它们普遍和 iOS 的橡皮筋效果打架，自己写反而可控。日志页不做下拉刷新（下拉是加载更早历史），改用顶部的手动刷新按钮。

**列表加载更多用自动触发。** 历史列表滚到底部时用 `IntersectionObserver` 自动 `fetchNextPage`，不放「加载更多」按钮。

### 8.4 深色模式

夜间使用是主要场景（挂机脚本通常在睡前配置）。深色是**默认**主题，不是可选项。用 `@custom-variant dark (&:where(.dark, .dark *))` 的 class 切换模式而非 `prefers-color-scheme` 媒体查询，因为要提供手动覆盖。三态：跟随系统 / 强制浅色 / 强制深色，存 `stores/ui.ts` 并持久化到 localStorage。

首屏闪白（FOUC）必须避免：在 `index.html` 的 `<head>` 里内联一小段脚本，在 React 挂载前从 localStorage 读偏好并给 `<html>` 加 `class="dark"`。同时 `manifest` 与 `<meta name="theme-color">` 用深色值，让 PWA 启动画面与系统状态栏一致。

深色模式下日志页的级别配色需要单独调：`warning` 用琥珀色而非黄色（黄色在深底上刺眼）、`error` 用降饱和的红色。旧前端的映射（`info`→info、`warning`→warning、`error`→danger）保留语义，换具体色值。

### 8.5 断网与后端不可用的降级

三种故障要区分对待，因为用户的下一步动作不同：

**浏览器离线**（`navigator.onLine === false` 或 `online`/`offline` 事件）。顶部出现一条常驻的离线横幅。已缓存的应用外壳与 schema 可以继续浏览，所有写操作按钮置灰。TanStack Query 的 `networkMode` 保持默认 `'online'`，请求会被暂停而非失败，恢复网络后自动重放。

**后端不可达**（请求超时或连接被拒）。这和离线不同 —— 网络通但服务挂了（uvicorn 没起、端口错、容器重启中）。展示一个全屏的 `ErrorState`：说明「无法连接到 MAA-API 服务」、显示当前尝试的 base URL、提供重试按钮，并附一行排查提示（检查服务是否运行、地址是否正确）。WebSocket 客户端同时进入重连退避，状态栏显示重连倒计时。

**后端在但内核不可用**（`GET /api/system/health` 返回内核 `STARTING` / `CRASHED` / `FAILED`，或设备 `DISCONNECTED`）。这是**正常状态**而不是错误 —— [02 §7](./02-系统架构设计.md) 明确规定服务进入可用状态不依赖内核就绪。所以页面完整渲染，只是：状态卡如实显示内核与设备状态；所有需要内核的操作（提交流水线、原子操作、截图）按钮置灰并在旁边说明原因与修复入口（「设备未连接 · 重新连接」）。旧前端在这种情况下会直接报错，让人以为服务坏了。

三者共用一个 `useServiceAvailability()` hook 返回判定结果，页面据此选择渲染分支，不要在每个组件里各自判断。

## 9. WebSocket 客户端封装

单个 WebSocket 连接承载全部实时推送，端点 `GET /api/ws`（[02 §1](./02-系统架构设计.md)）。封装在 `src/realtime/client.ts`，对外暴露一个单例。**协议本身由 [06-实时日志与WebSocket](./06-实时日志与WebSocket.md) 定义，本节只讲客户端侧的可靠性实现，不重新定义帧格式。**

实现前需要先记住三条来自 06 的约定，它们直接决定客户端代码怎么写：消息信封是 `{type, ts, data}`（载荷字段叫 `data`，不是 `payload`；请求/响应类帧额外带 `req_id` 用于配对）；订阅是显式的，连接建立后要发 `subscribe` 声明频道，可用频道为 `log` / `pipeline_status` / `task_status` / `core_status` / `device_status` 以及更新进度与待确认事件；`log` 频道支持 `log_filter` 在服务端做过滤，前端**不要**订阅全量日志再在本地筛 —— 06 实测 `TRC` 占 62%、`WRN` 占 30%，服务端过滤能从源头削掉九成以上的流量，这对移动网络是决定性的。

### 9.1 连接状态机

```
CONNECTING ──open──> OPEN ──close/error──> RECONNECTING ──达到上限──> OFFLINE
                      ^                          │
                      └──────────open────────────┘
```

状态放 Zustand，全局可读。`OPEN` 之外的状态在顶部显示细条状态栏（`RECONNECTING` 显示「正在重连…（第 3 次）」，`OFFLINE` 显示「实时连接已断开 · 重试」）。

### 9.2 自动重连与指数退避

退避序列按 [06 §7.5](./06-实时日志与WebSocket.md)：1s → 2s → 4s → 8s → 最大 30s，带 ±20% 抖动。抖动是必要的：内核重启时前端可能同时开了手机和电脑两个页面，固定间隔会让它们同步重连，在服务刚起来的瞬间形成小尖峰。

关闭原因决定重连行为，不能一律退避：

| 关闭信号 | 客户端动作 |
|---|---|
| `server_shutdown` 消息 + close `1001` | 首次重连间隔固定 3s，之后正常退避 |
| close `1011`（服务端发送队列满） | 正常退避，且必须带 `last_seen_id` 补拉 |
| close `4401`（token 无效） | **不重连**，清 token 跳登录页 |
| close `4403`（仅凭 cookie 但来源不可信） | **不重连**，提示改用 header 鉴权 |
| close `4429`（超出频率限制） | 退避但起始间隔抬到 30s |

`4401` / `4403` 这两个必须硬编码成「不重连」。鉴权失败是确定性错误，重连只会在服务端日志里刷出一串失败握手，且掩盖真正的问题。close `1011` 的语义值得特别注意：按 06 §6，它表示「本连接的服务端发送队列满了，你消费太慢」，服务端主动断开以保护其他连接。客户端此时不该激进重连，而应先把积压的渲染任务清掉（§9.5 的节流就是为此）再连回来。

连续失败 10 次后进入 `OFFLINE` 停止自动重连，等用户手动点重试或页面重新获得焦点（`visibilitychange` 且 `document.visibilityState === 'visible'`）时立刻重置退避并重连。移动端浏览器在后台会冻结页面并静默断开连接，切回前台立即重连比继续退避体验好得多。

### 9.3 心跳

不能只依赖 TCP 层 —— 移动网络切换（Wi-Fi ↔ 蜂窝）或 NAT 超时会导致连接「看起来还在」但实际已死，`onclose` 不触发。

06 §8 规定的是**双向**心跳，客户端侧的义务是每 30 秒发一帧应用层 `ping`，服务端原样回带 `t` 供计算 RTT：

```jsonc
// 客户端 →
{ "type": "ping", "req_id": "r-4", "data": { "t": 1758000009.000 } }
// 服务端 ←
{ "type": "pong", "req_id": "r-4", "ts": 1758000009.010, "data": { "t": 1758000009.000 } }
```

注意 `t` 是**秒**为单位的浮点时间戳（不是毫秒整数），算 RTT 时要 `(Date.now() / 1000) - t`。

30 秒这个间隔不是随便定的：服务端在「超过 90 秒无任何客户端消息」时会关闭连接，30 秒给了两次丢包的容错余量。客户端侧的死连接检测同样取 90 秒 —— 维护一个 `lastFrameAt`，任何收到的帧（包括服务端每 30 秒的协议级 ping）都刷新它，一个 5 秒周期的检查器发现 `Date.now() - lastFrameAt > 90_000` 就主动 `ws.close()` 走重连流程。两侧用同一个阈值，行为可预测。

RTT 值不要只是算出来丢掉：把它显示在设置页的连接诊断区，并在超过 1 秒时给状态栏加一个「连接较慢」提示。这是用户判断「是我网差还是服务卡」的唯一线索。

页面隐藏时（`document.hidden`）停止发送心跳并容忍连接断开，不浪费电量。这样做会触发服务端 90 秒超时关闭，是预期行为 —— 切回前台时按 §9.2 立即重连并按 §9.4 补发。如果部署在 nginx 反代之后，06 §8 提醒 `proxy_read_timeout` 需大于心跳间隔（建议 120s），否则 nginx 会先于应用超时断开；这条在 §12 的反代方案里要一并配上。

### 9.4 断线期间的消息补偿

日志在断线期间会丢失，而仅靠重连后全量刷新 query 无法恢复它 —— 日志是流，不是快照。状态类事件不需要补偿（重连后重取一次快照即可），所以补偿机制只服务于 `log` 频道。

机制由 [06 §7.4](./06-实时日志与WebSocket.md) 定义：客户端**持久化** `last_seen_id`（最后收到的日志 `id`），重连时带上，服务端从环形缓冲补发 `id > last_seen_id` 的记录。有两条容易写错的细节：

`last_seen_id` 可以走握手 query（`?last_seen_id=1234`）或首个 `subscribe` 消息的字段，但**只在首次 `subscribe` 时生效**，后续再发 `subscribe` 改订阅不会重新触发补发。所以客户端的补发请求必须和「连接建立后的第一次订阅」合成一个动作，不能先订阅再补发。

补发结果在 `subscribed` 响应里告知，不是单独的帧：

```jsonc
{ "type": "subscribed", "req_id": "r-1",
  "data": { "channels": ["log", "pipeline_status"], "backfilled": 32, "truncated": false } }
```

`truncated: true` 表示缺口超出了服务端缓冲容量，补发不完整。此时**不要静默跳过**，要在日志列表对应位置插入一条「存在未加载的历史日志，点击加载」的分隔提示，点击后走 `GET /api/system/logs?after_id=<last_seen_id>` 的游标查询补齐更早的部分。这是 06 明确要求的呈现方式，也是用户判断「日志是真的没有还是没加载出来」的唯一依据。

`last_seen_id` 要存 localStorage 而非仅在内存 —— 移动端页面被系统回收后重新打开，内存态全丢，只有持久化的游标能让补发继续生效。同时客户端按 `id` 去重（丢弃 `id <= lastSeenId` 的帧），因为补发窗口与新事件可能重叠。

### 9.5 与 TanStack Query 缓存的协作

**核心原则：按事件类型精准失效，不做全量刷新。** `queryClient.invalidateQueries()` 不带参数会失效整个缓存，在一个每秒可能收到几十条事件的连接上这等于持续全量重取。

`realtime/query-bridge.ts` 维护一张路由表，把事件类型映射到处置动作：

事件类型名一律取 [06 §7.3](./06-实时日志与WebSocket.md) 的规范值，不要另起别名 —— 一旦前端用了自己的命名，`types/realtime.ts` 就得维护一张翻译表，而这张表会在后端加事件时静默失配。

```ts
type Handler = (ev: ServerEvent, qc: QueryClient) => void

export const routes: Record<ServerEvent['type'], Handler> = {
  // 载荷自带完整新状态 → 直接打补丁，零网络往返、零闪烁
  core_status:     (ev, qc) => qc.setQueryData(keys.systemHealth(), (old) =>
                                old && { ...old, core: ev.data }),
  device_status:   (ev, qc) => qc.setQueryData(keys.systemHealth(), (old) =>
                                old && { ...old, device: ev.data }),
  pipeline_status: (ev, qc) => {
    qc.setQueryData(keys.pipelineCurrent(), (old) =>
      isTerminal(ev.data.status) ? { pipeline: null } : { pipeline: ev.data })
    if (isTerminal(ev.data.status)) {
      qc.invalidateQueries({ queryKey: keys.pipelineList(), refetchType: 'active' })
      qc.invalidateQueries({ queryKey: keys.queue() })
    }
  },
  task_status:     (ev, qc) => patchTaskInCurrent(qc, ev.data),

  // 只是「某物变了」的信号 → 失效对应 key
  confirm_request: (_, qc) => qc.invalidateQueries({ queryKey: keys.confirmations() }),
  confirm_resolved:(_, qc) => qc.invalidateQueries({ queryKey: keys.confirmations() }),
  update_progress: (ev, qc) => qc.setQueryData(keys.updateJob(ev.data.update_id), ev.data),

  // 高频流式数据 → 完全不进 Query 缓存
  log:             (ev) => useLogBuffer.getState().append(ev.data),
  agent_event:     (ev) => useAgentStream.getState().apply(ev.data),
}
```

`pipeline_status` 的处理方式值得说明：06 把「进度更新」和「进入终态」合并成同一个事件类型，靠 `status` 字段区分（`pending` / `running` / `completed` / `failed` / `cancelled`）。所以客户端不能假设有一个独立的「完成」事件，必须自己判断终态并据此把 `pipelines/current` 置空、失效历史列表与队列。把这个判断集中在路由表里，页面组件就不需要关心。

三条选择准则：

**事件载荷是否包含完整的新状态。** 是则用 `setQueryData` 直接写缓存，零网络往返、零闪烁。`core_status` / `device_status` / `pipeline_status` 都属于这类，后端应当刻意把它们设计成自包含的。

**只是变更信号则 `invalidateQueries`，并带 `refetchType: 'active'`。** 默认行为只重取活跃观察者，但显式写出来是为了表明意图：用户在日志页时，队列 query 只标脏不重取，切回任务页才发请求。

**高频流式数据不进 Query 缓存。** 日志行和 agent 的 token 增量走 Zustand 环形缓冲。Query 的定位是「服务端资源的快照」，把每秒几十条的追加流塞进去会触发大量订阅者重渲染，而且这些数据本来就不需要缓存失效语义。

另外加一层节流：同一个 `queryKey` 前缀在 250ms 窗口内的多次失效合并成一次。流水线执行时 `task_status` 与 `pipeline_status` 往往连着来，合并后省掉一半请求。实现上用一个 `Map<string, timeoutId>` 做尾部防抖。

这层节流同时是对 close `1011`（服务端队列满则断开）的防御。06 §6 的策略是「慢客户端的代价由它自己承担」—— 如果前端每收一帧就同步触发一轮重渲染与重取，在日志高峰期就会真的消费不过来而被踢掉。日志行的写入也要批量：`useLogBuffer.append` 内部用 `requestAnimationFrame` 合并同一帧内的多次追加，一次性 `set` 到 store，而不是每行一次。

## 10. 鉴权在前端的处理

后端是单个 `access_token`，支持 Bearer / `X-Token` / query / cookie 四种传递方式（[README 决策表](./README.md#决策速查表)）。这四种不是并列的备选，而是各有其不得不用的场景。

### 10.1 token 的录入与存储

没有用户名密码，登录页 `/login` 就是一个 token 输入框（`type="password"` + 明文切换按钮）。

[05 §6.1](./05-API规范与路由清单.md) 没有专门的「校验 token」端点，所以登录流程复用现有的两个：先读免鉴权的 `GET /api/system/health` 拿 `auth_enabled`，若为 `false` 直接跳过登录页；否则用户输入 token 后带上它调 `POST /api/system/auth/cookie`，返回 `204` 即 token 有效（返回 `401 UNAUTHORIZED` 即无效），同时这一步顺带把 WebSocket 需要的 cookie 也拿到了。一次请求同时完成校验与换 cookie，不必再加端点。

**存储位置：localStorage + 后端下发 HttpOnly cookie + IndexedDB，三处。** 前两处服务于页面上下文，第三处专门服务于 Service Worker —— 理由见本节末尾。

localStorage 存 token 的风险是 XSS —— 任何注入的脚本都能读走它。必须承认这个风险，然后论证在本项目里它是可接受的：前端没有任何用户生成内容的富文本渲染路径（日志用纯文本渲染，不用 `dangerouslySetInnerHTML`）；所有依赖打进 bundle，没有 CDN 外链，不存在第三方脚本被投毒的通道；部署形态是私有内网单用户。在这个威胁模型下，XSS 的前置条件基本等于「攻击者已经能改前端代码」，此时 token 存哪都一样。

反过来，如果只用 HttpOnly cookie 而不存 localStorage，就得为「同一个 token 要同时用于 fetch、WebSocket、`<img src>`」这三种场景各自配置 CORS 与 `credentials`，且在跨主机调试（dev server 在 5173、后端在 8002）时 cookie 的 `SameSite` 会成为持续的摩擦点。

结论是双写：localStorage 作为前端可读的主副本（用于请求拦截器注入 header）；同时 `POST /api/system/auth/cookie` 成功时后端下发 `maa_token` 的 `HttpOnly; SameSite=Lax` cookie（[05 §5](./05-API规范与路由清单.md)，HTTPS 下追加 `Secure`），这份 cookie 专门服务于**无法自定义请求头的场景**。

双写不会放大 CSRF 风险，因为 05 对 cookie 渠道加了一条硬限制：**仅凭 cookie 鉴权的请求只允许 `GET`、`HEAD` 与 WebSocket 升级**，写方法若 token 只来自 cookie 直接返回 `403 FORBIDDEN`。前端的写请求本来就带 `X-Token` 头，不受影响。这条限制的实际效果是：即使用户在别的网站被诱导对本服务发起 `POST`，浏览器自动附带的 cookie 也不足以让它通过。

**第三处存储：IndexedDB，供 Service Worker 使用。** 这一处是被推送通知的「准许 / 拒绝」按钮逼出来的（[§13.2](#132-确认超时与推送触达的矛盾)）。点击通知的 action 时，处理逻辑跑在 Service Worker 的 `notificationclick` 事件里，此时页面可能根本没打开。而 Service Worker **不是 window 上下文，访问不到 localStorage** —— 那是个同步 API，Worker 环境里不存在。

于是出现一个两难：Service Worker 要发 `POST /api/confirmations/{id}`，但它读不到 localStorage 里的 token；同源 fetch 会自动带上 cookie，可 cookie 按上面那条硬限制不能用于写操作。

解法是把 token 也写一份进 IndexedDB（Service Worker 可以访问），由 Worker 读出来放进 `X-Token` 头：

```ts
// src/pwa/sw-auth.ts —— 在 Service Worker 里读 token
async function readToken(): Promise<string | null> {
  const db = await openDB('maa-api', 1)
  return db.get('auth', 'token')
}
```

这样"写操作必须显式带凭据"这条规则保持无例外，不必为推送场景给 cookie 开特例 —— 开了特例就等于把 CSRF 防护上的一个口子永久留在那里，而且是留在一个最容易被忽略的路径上。

三处存储的写入与清除必须同步，否则会出现"页面已登出但通知按钮还能批准操作"这种最坏情况。登出时要清四样：localStorage、Zustand、IndexedDB，以及让后端清 cookie。05 当前没有列出登出端点，实现时需要补一个（`DELETE /api/system/auth/cookie` 最贴合现有命名）——否则 HttpOnly cookie 前端删不掉，登出后 WebSocket 仍能连上。这是需要回填到 05 路由清单的一处缺口。

### 10.2 请求拦截器注入

用 `openapi-fetch` 的中间件统一注入，不在每个调用点手写 header：

```ts
// src/api/client.ts
import createClient, { type Middleware } from 'openapi-fetch'
import type { paths } from '@/types/api'

const auth: Middleware = {
  async onRequest({ request }) {
    const token = useAuth.getState().token
    if (token) request.headers.set('X-Token', token)           // 渠道 2，05 指定给 SPA
    request.headers.set('X-Request-Id', crypto.randomUUID())  // 用于与实时日志联动，见 10 号文档
    return request
  },
  async onResponse({ response }) {
    if (response.status === 401) useAuth.getState().onUnauthorized()
    return response
  },
}

export const api = createClient<paths>({ baseUrl: '/' })
api.use(auth)
```

用 `X-Token` 而非 `Authorization: Bearer`，这是 [05 §5](./05-API规范与路由清单.md) 的渠道分工：渠道 1（`Authorization: Bearer`）留给 MCP 客户端、脚本与 `curl`，渠道 2（`X-Token`）明确指派给前端 SPA 的 fetch 封装。两者服务端都接受、优先级也只差一位，分开用的收益在排查问题时：看一眼请求头就知道这次调用来自浏览器还是来自 agent，不必去比对 `User-Agent`。

### 10.3 错误状态码的前端处理

`onUnauthorized()` 做三件事：清 localStorage 与 Zustand 里的 token、把 `location.pathname + search` 存为 `returnTo`、`navigate('/login')`。同时断开 WebSocket 并阻止重连（否则会在退避循环里反复失败）。

要区分 401 与 403。401 是「token 无效或缺失」，跳登录页；403 是「身份有效但动作被策略拒绝」，只弹 toast 不跳转。403 在单 token 模型下是会真实出现的，[05 §4](./05-API规范与路由清单.md) 列了两种触发条件：MCP 只读工具集调用了写操作，以及非同源请求试图仅凭 cookie 执行写操作。后者正是前端可能踩到的 —— 如果 `X-Token` 头因为某个中间件被剥掉，写请求会退化成 cookie-only 而收到 403。所以 403 的 toast 文案要能指向这个原因（「请求缺少鉴权头，请重新登录」），而不是笼统的「权限不足」。

422 是第三类，需要单独处理：它来自 Pydantic 的参数校验，是任务表单提交的主要失败形态。响应体按 [05 §3](./05-API规范与路由清单.md) 的统一错误信封 `{"error": {"code", "message", "details"}}`，`details` 里带字段级的错误位置。前端要把它映射回 React Hook Form 的字段错误（`setError(fieldPath, { message })`）并滚动到第一个出错的控件，而不是弹一个通用 toast 让用户自己找。这是 §7 的 schema 驱动表单能正确闭环的关键一环。

**重试策略要按状态码细分，不能笼统地"4xx 不重试、5xx 重试"。** TanStack Query 的默认 `retry: 3` 会让一个失效 token 打出四次请求，在 uvicorn 日志里刷出一堆 401。在 `QueryClient` 的 `defaultOptions.queries.retry` 里写一个函数：

```ts
retry: (failureCount, error) => {
  if (failureCount >= 3) return false
  const status = (error as ApiError).status
  if (status === undefined) return true    // 网络错误，重试
  if (status === 504) return false         // 下游未应答，操作可能已执行
  return status >= 500                     // 其余 5xx 重试，4xx 一律不重试
}
```

**504 必须排除在重试之外**，这是它与其他 5xx 的关键区别。按 [05 §2.4](./05-API规范与路由清单.md)，504 表示下游没有应答，而命令**可能已经投递并正在执行**——自动重试会把同一个任务提交两遍。504 的正确处置是查状态而非重试，所以前端收到 504 时应当主动刷新相关查询（如 `GET /api/pipelines/current`）并提示"内核未在预期时间内响应，正在确认当前状态"，而不是静默重试。

对**写操作**（`useMutation`）则一律不自动重试，无论什么状态码 —— 提交任务、触发更新这类动作重复执行的后果比多等一次严重得多。需要重试时由用户显式点按钮。

### 10.4 WebSocket 与图片的特殊处理

**WebSocket 的浏览器 API 不支持自定义请求头。** `new WebSocket(url)` 只能传 URL 和子协议，没有 header 参数 —— 这是 WHATWG 规范的限制，没有变通办法。因此 WS 只能用渠道 3（query）或渠道 4（cookie），这也正是这两个渠道存在的原因。

这里有一处需要注意的文档分歧：[05 §5](./05-API规范与路由清单.md) 推荐先换 cookie 再连（「token 不出现在 URL 里」），而 [06 §7.2](./06-实时日志与WebSocket.md) 写的是「首选 query 参数」。两者的取舍出发点不同，按客户端类型分开就不矛盾了，**本方案据此规定**：

**浏览器（本前端）走 cookie。** 登录时已经调过 `POST /api/system/auth/cookie`（§10.1），cookie 已在。`new WebSocket('/api/ws')` 不带任何 token 参数，握手作为普通 HTTP GET 自动携带 cookie。好处是 token 不进 uvicorn 的 access log、不进浏览器 history、不会在截图或分享链接时泄露。

**非浏览器客户端走 query。** agent、脚本、`wscat` 这类客户端没有 cookie jar，`?token=xxx` 是唯一可行的方式，06 的「首选 query」针对的就是它们。这部分不属于本前端的实现范围，但接入说明要写清楚（见 [10-开放API与调试台](./10-开放API与调试台.md) 的接入指南章节）。

前端仍要保留 query 兜底路径，用于一个具体场景：跨主机开发时 dev server（5173）与后端（8002）不同源，`SameSite=Lax` 的 cookie 在 WebSocket 握手时不一定带上。选择逻辑是「先试不带 token 的 URL，握手被 close `4401` 拒绝后再回退到带 query 的 URL」，而不是无条件带 query。启用兜底时必须配套：后端把 `token` 查询参数从 access log 脱敏（06 §7.2 同样要求这一点），前端不把带 token 的 URL 写进任何日志或错误上报。

还有一个易踩的坑：`4403`（仅凭 cookie 但来源不可信）在跨源开发时可能被触发，此时**不要**退回 query 重试，而应提示开发者配 dev server 代理（§4 的 `server.proxy` 让前后端同源，从根上避开这个问题）。

第三种方案是「连接后第一帧发 auth 消息」，后端在 `accept()` 之后等第一帧再决定是否继续。它的问题是 `accept()` 必须先发生，未鉴权的连接会短暂占用服务端资源，且无法用标准的 HTTP 401 拒绝。列为备选，不作为首版实现。

**`<img src>` 同样不能带 header。** 首页的设备截图与日志里的截图都是 `<img>` 加载的。方案与 WebSocket 一致：依赖 cookie。如果要完全不依赖 cookie，后端可以为图片资源提供一次性短时 URL（响应体里返回带签名与过期时间的 query），前端把这个 URL 直接给 `<img src>`。这种做法更严格但增加一次往返，首版用 cookie，把签名 URL 记为备选。

需要注意 **Service Worker 不要缓存任何带 token 的请求**。Workbox 的 `runtimeCaching` 规则里排除掉 URL 含 `token=` 的请求，否则 token 会被写进 Cache Storage，退出登录后仍留在磁盘上。

### 11.2 Service Worker 缓存策略

```ts
workbox: {
  // 应用外壳预缓存：构建产物里的这些类型全部进 precache manifest
  globPatterns: ['**/*.{js,css,html,ico,png,svg,webp,woff2}'],

  navigateFallback: '/index.html',
  // 这些前缀的请求不能被导航兜底接管，否则 API 的 404 会拿到一份 HTML
  navigateFallbackDenylist: [
    /^\/api\//, /^\/mcp/, /^\/docs/, /^\/redoc/, /^\/openapi\.json/,
  ],

  cleanupOutdatedCaches: true,
  clientsClaim: false,     // 配合 registerType: 'prompt'，不抢占已打开的页面

  runtimeCaching: [
    {
      // 任务类型 schema 变化极少，短缓存能让离线时表单仍可渲染
      // 注意：Workbox 用完整 URL 匹配，正则不要用 ^ 锚定路径
      urlPattern: /\/api\/tasks\/types$/,
      handler: 'StaleWhileRevalidate',
      options: {
        cacheName: 'maa-task-schema',
        expiration: { maxEntries: 4, maxAgeSeconds: 60 * 60 * 24 },
        cacheableResponse: { statuses: [200] },
      },
    },
    {
      // 截图是不变的历史快照，缓存能让翻看历史日志不重复下载
      urlPattern: /\/api\/screenshots\/.+\.(?:jpg|jpeg|png|webp)$/,
      handler: 'CacheFirst',
      options: {
        cacheName: 'maa-screenshots',
        expiration: { maxEntries: 60, maxAgeSeconds: 60 * 60 },
        cacheableResponse: { statuses: [200] },
      },
    },
  ],
}
```

**其余 `/api/*` 一律不缓存。** 不需要显式写 `NetworkOnly` 规则 —— 没有 `runtimeCaching` 规则匹配的请求本来就直接走网络。关键是 `navigateFallbackDenylist` 必须把 API 前缀排除，否则一个失败的 API 请求会被导航兜底当成页面请求返回 `index.html`。

一个容易踩的不对称：`navigateFallbackDenylist` 是对 `url.pathname` 做匹配，所以 `/^\/api\//` 这种带 `^` 的正则是正确的；而 `runtimeCaching[].urlPattern` 是对**完整 URL**（含协议与主机）做匹配，同样写 `^\/api\/` 永远匹配不上。这两处的写法差异必须记住，写错时的表现是「缓存规则静默失效」，很难发现。

`clientsClaim: false` 与 `registerType: 'prompt'` 配套：新 SW 装好后进入 waiting 状态，不主动接管已打开的页面，等用户点「刷新」才 `skipWaiting`。这避免了「用户正在填表单时页面被新版本资源替换」。

### 11.3 安装引导

**Android / 桌面 Chromium** 有 `beforeinstallprompt` 事件。监听并存下 event 对象，在合适时机（用户已经用过两次、不在首次访问）显示一张「安装到主屏」卡片，点击时调 `event.prompt()`。不要在页面加载时立刻弹 —— 那是最容易被无脑关掉的时机。

**iOS / iPadOS 没有 `beforeinstallprompt`，也没有任何编程式安装 API。** 只能引导用户手动操作。检测条件是「UA 判定为 iOS」且 `navigator.standalone !== true`（已安装时该值为 `true`），满足则显示一张图示卡片：「点击底部分享按钮 → 添加到主屏幕」，配一张标注了分享图标位置的插图。这是 iOS 上唯一可行的做法。

引导卡片的关闭状态要持久化（localStorage 记一个 `installPromptDismissedAt`），7 天内不再显示。

### 11.4 更新提示

```tsx
// src/pwa/register.tsx
import { useRegisterSW } from 'virtual:pwa-register/react'

export function ServiceWorkerUpdatePrompt() {
  const {
    needRefresh: [needRefresh, setNeedRefresh],
    updateServiceWorker,
  } = useRegisterSW({
    onRegisteredSW(url, registration) {
      // 每小时主动检查一次更新；长期挂在主屏上的 PWA 不会自己重新导航
      if (registration) setInterval(() => registration.update(), 60 * 60 * 1000)
    },
  })

  if (!needRefresh) return null
  return (
    <UpdateBanner
      onConfirm={() => updateServiceWorker(true)}   // true = 刷新页面
      onDismiss={() => setNeedRefresh(false)}
    />
  )
}
```

提示用顶部横幅而非 Modal：新版本可用不是紧急事件，不该打断当前操作。横幅可关闭，关掉后下次 SW 检查到更新会再出现。

`registration.update()` 的定时轮询是必要的：安装到主屏的 PWA 可能连续几天不重新导航，仅靠 SW 自身的更新检查时机会长期停在旧版本。

后端每次部署新前端产物后，`index.html`（`no-cache`）会立刻变，SW 的 precache manifest 随之变化，用户在下一次打开或下一次定时检查时收到提示。

## 12. PWA 的安全上下文约束与部署路径

这是本方案里唯一一个「技术上无法用代码绕过」的约束，必须在动工前就定好部署形态。

### 12.1 约束事实

Service Worker、Push API、Notification API 都要求**安全上下文**（secure context）。安全上下文的判定只认两类来源：HTTPS，以及 `localhost` / `127.0.0.1`（含任意端口，无需 TLS）的特例。

局域网 HTTP 地址，比如 `http://192.168.1.50:8002`，**不是**安全上下文。在这个地址下：

- `navigator.serviceWorker.register()` 直接失败，`window.isSecureContext === false`
- Chromium 的安装门槛明确要求 HTTPS 或 `localhost` / 回环地址，不满足则不会出现安装提示、不生成 WebAPK
- Push API 与 `Notification.requestPermission()` 不可用
- `getUserMedia` 等其他强能力同样不可用（本项目不涉及，但同源）

注意 `localhost` 特例只对**同一台设备**成立。手机上的 `localhost` 指手机自己，不是运行 MAA-API 的那台机器。所以「桌面上一切正常」完全不能说明手机上也正常，这是最容易踩的坑。

### 12.2 降级矩阵

| 能力 | `http://192.168.x.x:8002` | `http://localhost:8002`（同机） | HTTPS |
|---|---|---|---|
| 应用正常使用（页面、API、WebSocket） | 可用 | 可用 | 可用 |
| iOS「添加到主屏幕」+ standalone 显示 | **可用** | 可用 | 可用 |
| Android / 桌面 Chromium 安装提示 | 不可用 | 可用 | 可用 |
| Service Worker（离线外壳、资源缓存） | 不可用 | 可用 | 可用 |
| Web Push 推送通知 | 不可用 | 名义可用但无实际意义 | 可用 |

一个反直觉的事实值得强调：**iOS 的「添加到主屏幕」在纯 HTTP 下是可以用的**。它是用户手动触发的操作，不受安装门槛限制，会读取 manifest 并按 `display: standalone` 启动、使用 `apple-touch-icon` 作为图标。所以「HTTP 下能不能添加到主屏」的答案是：iOS 能，得到一个没有浏览器界面的独立图标应用；Android 不能得到系统级安装（只能存一个普通书签）。

但**推送通知在 HTTP 下必然失效，无论哪个平台**。iOS 的 Web Push 要求三个条件同时成立：站点是 HTTPS、PWA 已通过分享菜单添加到主屏、在已安装的应用内由用户手势触发 `Notification.requestPermission()`。Safari 标签页内即使在 HTTPS 下也无法订阅。所以 HTTP 下推送不是「体验降级」而是「功能不存在」。

### 12.3 可选方案与代价

**自签证书 + 手动信任。** 用 `mkcert` 建一个本地 CA 并为 LAN IP 签证书，把 CA 根证书装到每台要访问的设备上。代价：iOS 需要下载配置描述文件、在「设置 → 通用 → VPN与设备管理」安装，再去「关于本机 → 证书信任设置」里手动开启完全信任，这是两个不同位置的两步操作，非技术用户几乎不可能自己完成；每台新设备都要重做；证书有效期到了要全部重来（mkcert 默认签 2 年多）。适合单人单设备，不适合多设备。

**反向代理终结 TLS。** 前面放一个 Caddy 或 Nginx，用自有域名 + Let's Encrypt。如果域名解析到公网 IP 则用 HTTP-01 挑战，但那意味着服务要暴露到公网，与私有部署的前提冲突。更好的做法是**DNS-01 挑战 + 内网 DNS 解析**：向 Let's Encrypt 用 DNS 挑战申请 `maa.example.com` 的真实证书（不需要服务可被公网访问），同时在路由器或本地 DNS 上把这个域名解析到 LAN IP。代价：需要一个自有域名、需要 DNS 服务商的 API token 配给 Caddy、需要能配置内网 DNS（有些运营商光猫不支持）。技术上最干净，前置条件最多。

**内网组网工具带证书。** Tailscale 的 `tailscale serve` 会给设备分配 `*.ts.net` 的域名并自动签发受信证书，一条命令就能把本地 8002 端口暴露为 HTTPS。代价：需要每台访问设备都装 Tailscale 客户端并登录同一账号；流量走 WireGuard 隧道（同网段下通常仍是直连，不经中转，延迟影响可忽略）；依赖一个第三方服务的控制平面。好处是顺带解决了「不在家时也能访问」和「IP 变化后地址失效」两个问题。

**Chrome 的 `unsafely-treat-insecure-origin-as-secure` 标志。** 把指定 origin 强制当作安全上下文。桌面 Chrome 可以通过 `chrome://flags/#unsafely-treat-insecure-origin-as-secure` 或 `--unsafely-treat-insecure-origin-as-secure="http://192.168.1.50:8002" --user-data-dir=/tmp/xxx` 启用。**但在 Android 上这个命令行标志需要 root 或开发者模式的设备**，普通手机用不了 —— 而移动端恰恰是本项目的主场景。所以这个方案对我们基本无效，只在桌面临时调试时有点用。

**Chrome DevTools 的端口转发。** Android 手机用 USB 连电脑，在 `chrome://inspect` 里配端口转发，手机上的 `localhost:8002` 映射到电脑能访问的地址，从而落进 `localhost` 特例。这是开发期验证 Service Worker 与推送逻辑的最便捷办法，但要插着线，不能作为日常使用方式。

### 12.4 部署路径

**已拍板：首版就上 Tailscale Serve（下面的第二层），不接受 PWA 能力缺失的降级形态。** 这意味着 PWA 的全部能力（离线外壳、安装为独立应用、Web Push 确认通知）在首版就是可用的，`M14` 的验收标准按「真机上能收到推送并点击深链回确认卡片」来定，而不是「HTTP 下功能不报错」。

第一层的分级降级**仍然要实现**，但定位从"首版形态"变成"防御性兜底"：Tailscale 客户端没连上、或用户临时用局域网 IP 直连时，应用要正常工作而不是白屏或满屏报错。

**第一层（无论如何都要实现，零成本）：按安全上下文分级降级。** 应用不假设自己运行在安全上下文里。`pwa/register.tsx` 在 `!window.isSecureContext` 时直接跳过 SW 注册（不是 try-catch 吞异常，而是根本不调用，避免控制台刷错误），`pwa/install.tsx` 与推送相关的设置项整块隐藏，设置页里出现一条说明：「当前通过 HTTP 访问，离线缓存与推送通知不可用。配置 HTTPS 后自动启用。」这一层保证「什么都没配」时应用完整可用，只是少了 PWA 能力。

```ts
// src/pwa/register.tsx
export const PWA_AVAILABLE = window.isSecureContext && 'serviceWorker' in navigator
export const PUSH_AVAILABLE = PWA_AVAILABLE && 'PushManager' in window
```

**第二层（首版采用）：Tailscale Serve。** 在跑 MAA-API 的机器上执行一条命令，访问 `https://<主机名>.<tailnet>.ts.net`：

```bash
tailscale serve --bg https / http://127.0.0.1:8002
```

选它的理由是它同时解决了三个问题 —— 受信证书（PWA 全部能力解锁）、稳定地址（不再受 DHCP 影响）、外网可达（不在家也能看挂机状态）——而代价只是每台访问设备装一个客户端并登录同一账号。证书由 Tailscale 自动签发与续期，不需要任何证书维护。

首版采用它带来三项必须落地的配套工作，都归到 `M15`：

**后端要信任代理头。** `tailscale serve` 是反向代理，请求到达 FastAPI 时 `X-Forwarded-Proto` 为 `https` 但连接本身是到 `127.0.0.1` 的 HTTP。cookie 的 `Secure` 属性判定（[§10 鉴权在前端的处理](#10-鉴权在前端的处理)提到 HTTPS 下追加 `Secure`）如果按连接本身判定就永远不会加上。需要给 uvicorn 配 `--forwarded-allow-ips=127.0.0.1` 并让下发 cookie 的代码按 `X-Forwarded-Proto` 判定，否则 `Secure` cookie 在 Tailscale 下反而失效。

**CORS 与 WebSocket 的 origin 白名单要包含 `*.ts.net` 域名。** 这个域名在部署时才确定（取决于 tailnet 名与主机名），所以必须是配置项而非硬编码 —— 这也顺带修掉了现有代码 `allow_origins=["*"]` 配 `allow_credentials=True` 的错误组合（见 [01-重构总览与现状评估](./01-重构总览与现状评估.md)）。

**文档要写清「装客户端」这一步不可省。** 它是唯一的用户侧前置条件，且未登录同一 tailnet 的设备完全访问不到。部署文档里要把这一步放在最前面，并说明它同时是访问控制手段——不在 tailnet 内的设备连端口都摸不到，这实际上比单 token 鉴权更强。

**第三层（有域名与 DNS 控制权时）：Caddy + DNS-01。** 想完全不依赖第三方控制平面，或者要给多个服务统一做 TLS 入口时的长期形态。Caddyfile 大致是反代 `127.0.0.1:8002` 并配置 DNS 提供商插件。首版不做，但上面那三项配套工作（信任代理头、origin 白名单可配、部署文档）对它同样适用，所以切换过去时不需要改代码。

**开发期**用同机 `localhost:8002`（或 dev server 的 `localhost:5173` 配代理）来验证 SW 行为，需要在真机上验证时用 Chrome DevTools 的端口转发。**不推荐** mkcert（多设备维护成本高）与 Chrome 标志（Android 上要 root，等于不可用）。

## 13. 通知能力的分工

三条触达通道，职责不重叠。

**后端多通道通知（邮件 / Webhook / Bark / 钉钉 / 企微）是保底层。** 它不依赖前端在线、不依赖安全上下文、不依赖用户授权过通知权限。因此把「必须送达」的事件交给它：流水线终态（完成 / 失败）、内核崩溃告警、热更新完成、定时任务执行结果。这是 `NotifyService` 的职责（[02 §1](./02-系统架构设计.md)），通道开关与配置在设置页。

**PWA Web Push 是即时层。** 优势是前端完全关闭时也能把通知送到锁屏，且点击能直接深链回具体页面。劣势是前置条件多（HTTPS、已安装、已授权），必然有一部分用户/场景拿不到。因此它承载「需要用户立刻决策」的事件，主要就是 agent 的人工确认请求。

**WebSocket + 应用内提示是前台层。** 用户正看着页面时，不该收到系统通知（重复且干扰）。通过 WS 推送 → `sonner` toast + 首页卡片，配合 `navigator.vibrate` 做震动反馈。判断依据是 `document.visibilityState === 'visible'`。

### 13.1 人工确认的触达设计

人工确认是三条通道唯一需要协同的场景。[README 决策表](./README.md#决策速查表)规定确认渠道是「前端经 WebSocket 收到待确认事件并弹卡片，超时自动拒绝」，但如果用户此刻没开页面，这个确认必然超时。所以实际是一个三级递进：

1. WebSocket 推 `confirm_request`。前端在线 → 首页置顶卡片 + toast + 震动。
2. 同时后端检查：若无活跃 WebSocket 连接，立即走 Web Push 推送。通知标题写清操作内容（「Agent 请求碎石 3 颗」），`data` 里带 confirmation id；点击通知的 `notificationclick` 处理器直接打开 `/?confirm=<id>` 并弹出确认卡片。
3. 若没有可用的 push 订阅（HTTP 部署 / 未安装 / 未授权），退到 Bark 或钉钉，消息体里带一个可点击的深链（`https://<host>/?confirm=<id>`）。

第 2 步的技术要点：Web Push 的 `userVisibleOnly: true` 是强制的（浏览器要求每次 push 都必须显示一个可见通知），所以 SW 的 `push` 事件处理器里必须调用 `showNotification()`，不能静默处理。

后端侧需要：VAPID 密钥对（生成一次，公钥下发给前端作为 `applicationServerKey`，私钥存配置）、`push_subscription` 表存 `endpoint` / `p256dh` / `auth` 三个字段、用 `pywebpush` 发送。订阅在 `pwa/push.ts` 里完成：

```ts
const reg = await navigator.serviceWorker.ready
const sub = await reg.pushManager.subscribe({
  userVisibleOnly: true,                       // 必需，浏览器强制
  applicationServerKey: vapidPublicKey,        // 从 GET /api/notify/vapid-public-key 取
})
await api.POST('/api/notify/push-subscriptions', { body: sub.toJSON() })
```

权限申请必须由真实用户手势触发（设置页里的「启用推送通知」按钮），不能在页面加载时自动调 `Notification.requestPermission()` —— iOS 会直接忽略非手势触发的请求，Chromium 会记一次「被动拒绝」影响后续提示。

### 13.2 确认超时与推送触达的矛盾

确认超时原定统一 120 秒（[02 §8.2](./02-系统架构设计.md)），这与推送触达之间有矛盾：推送从后端发出，到用户听见、解锁手机、点开应用、读完卡片再决定，120 秒往往不够。结果是 agent 的高风险操作几乎总是超时自动拒绝，确认机制形同虚设。

**已拍板：超时按风险级别分级。** 消耗类与破坏类默认 10 分钟，原子操作的会话授权保持 120 秒，两者都可配置。分级而非统一放长的理由是这两类等待场景不同 —— 前者靠推送触达，值得等；后者触发时用户正在对话界面前主动让 agent 动手，此刻就在看屏幕，放长反而会让一个已经没人管的授权请求挂在那里。

**同时已拍板：为 Chromium 平台做推送上的「准许 / 拒绝」按钮，作为渐进增强。** 成本不高，Android 上能省掉打开应用这一步。但流程绝不能以它为前提 —— 下面的核实结果说明 Apple 平台完全不渲染这些按钮。

**「在推送上放准许 / 拒绝按钮」这条路在 Apple 平台上不通。** 核实了 WebKit 的通知能力边界，结论是它对 Web Push 的支持范围远小于 Chromium：

| 通知选项 | Chromium（桌面 / Android） | WebKit（macOS / iOS） |
|---|---|---|
| `actions`（按钮） | 渲染，最多 2 个 | **忽略** |
| `requireInteraction`（常驻不自动消失） | 桌面端生效 | **忽略** |
| `image`、`icon`、`badge` | 渲染 | 忽略，只用应用自身图标 |
| `title`、`body`、`tag`、`data` | 生效 | 生效 |
| `notificationclick` 事件 | 正常触发 | 正常触发 |

被忽略的选项**静默失效**——不抛异常也不打控制台警告，所以本地调试时很容易误以为生效了。

这带来两个后果。其一，iOS 上唯一可行的响应路径是「点通知体 → 深链回确认卡片 → 在应用内批准」，中间多了打开应用这一步。其二，`requireInteraction` 被忽略意味着通知会自动消失，用户如果当时没看到，等回过神来通知已经不在通知中心显眼处了。

因此稳妥的做法是**把超时放长**，而不是指望在通知上直接响应。具体放多长、以及要不要为 Android 额外做 action 按钮，是下面这个取舍。

实现上通知本身要按「Apple 卡片优先」设计：把完整信息（要执行什么操作、涉及多少消耗）写进 `title` 与 `body`，用 `tag` 做同类合并，用 `data.url` 承载深链目标，这样它在两个平台上都读得通。Chromium 上的 `actions` 属于渐进增强，不能作为流程的前提。

`notificationclick` 要同时处理三种入口，其中「点通知体」是两个平台共有的路径：

```ts
self.addEventListener('notificationclick', (event) => {
  event.notification.close()
  const { confirmationId, url } = event.notification.data
  // action 为空字符串 = 点了通知体本身（iOS 只会走到这里）
  if (event.action === 'approve' || event.action === 'reject') {
    event.waitUntil(resolveConfirmation(confirmationId, event.action === 'approve'))
  } else {
    event.waitUntil(focusOrOpen(url))   // 深链回确认卡片
  }
})
```

三个细节容易写错。`event.action` 在点击通知体时是**空字符串**而非 `undefined`，所以分支要按具体 action 值判断而不是判空。`resolveConfirmation` 的 fetch 必须从 IndexedDB 取 token 注入 `X-Token` 头（原因见 [§10.1](#101-token-的录入与存储)），同源自动携带的 cookie 不足以通过写操作的鉴权。而 `focusOrOpen` 要先用 `clients.matchAll()` 查有没有已打开的窗口并 `focus()` 加导航，直接 `clients.openWindow()` 会在应用已经开着时又开一个。

从 action 按钮批准后要给用户一个结果反馈，否则他不知道到底生效了没有 —— 在 `resolveConfirmation` 的成功与失败分支里各 `showNotification()` 一条简短结果通知（「已准许：碎石 3 颗」／「操作已过期，未执行」）。失败分支尤其不能省：确认可能在这期间已经超时，静默失败会让用户以为批准成功了。

## 14. 构建与部署集成

### 14.1 Dockerfile 改多阶段构建

现有 Dockerfile 是单阶段 `python:3.11.9-slim` + poetry，没有前端构建步骤（旧前端不需要构建）。新方案加一个 node 阶段：

```dockerfile
# ---------- 阶段 1：构建前端 ----------
FROM node:22-slim AS web

WORKDIR /web
# 先只拷依赖清单，让 npm ci 的层能被缓存
COPY web/package.json web/pnpm-lock.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile

COPY web/ ./
RUN pnpm build          # 产物落在 /web/../static，即 /static

# ---------- 阶段 2：运行时 ----------
FROM python:3.11.9-slim

WORKDIR /app

RUN apt-get update && apt-get install -y --no-install-recommends \
      curl adb libatomic1 \
    && rm -rf /var/lib/apt/lists/*

COPY pyproject.toml poetry.lock ./
RUN pip install --no-cache-dir poetry -i https://mirrors.aliyun.com/pypi/simple/ \
    && poetry install --no-root --only main

COPY maa_api/ ./maa_api/
COPY scripts/ ./scripts/
COPY config.yaml ./
# 只把前端产物拷过来，node 与 node_modules 不进最终镜像
COPY --from=web /static ./static

EXPOSE 8002

CMD ["poetry", "run", "uvicorn", "maa_api.main:app", "--host", "0.0.0.0", "--port", "8002"]
```

三个要点：`web/` 阶段的 `vite build` 的 `outDir` 是 `../static`，在容器里就是 `/static`（因为 `WORKDIR /web`），第二阶段用 `COPY --from=web /static` 取；依赖清单单独一层拷贝，改业务代码时不触发重装依赖；最终镜像不含 Node.js。

另外现有 Dockerfile 缺了 `COPY` 应用代码的步骤（依赖挂载卷运行），新版本显式拷进去。`poetry install --only main` 排除开发依赖。

### 14.2 本地开发流程

两个进程同时跑，两个终端：

```bash
# 终端 1：后端。--reload 监听 maa_api/ 的改动
poetry run uvicorn maa_api.main:app --host 0.0.0.0 --port 8002 --reload

# 终端 2：前端 dev server，带 HMR
cd web && pnpm dev
```

开发时访问 **5173**（dev server），不是 8002。dev server 把 `/api`、`/mcp`、`/openapi.json`、`/docs` 代理到 8002，WebSocket 也一并转发（`ws: true`），所以前端代码里所有 URL 都写相对路径，开发与生产零差异。手机上调试时访问 `http://<电脑 LAN IP>:5173`（`server.host: true` 已开启外部访问）。

后端此时 `static/` 可能是空的或过期的，无所谓 —— 开发期没人访问 8002 的页面。`app.frontend(..., check_dir=False)` 保证后端在 `static/` 不存在时也能启动。

验证生产构建时跑一次 `pnpm build` 然后直接访问 8002，这一步在合并前必须做：dev server 与生产产物在路由兜底、SW 注册、资源路径上的行为是不同的，只在 5173 上测过的改动可能在 8002 上挂掉。

`scripts/start-maa-api.sh` 按 [02 §6](./02-系统架构设计.md) 的规划简化（ADB 等待逻辑移入服务），不承担前端构建职责。

### 14.3 `static/` 加入 `.gitignore`

```gitignore
# 前端构建产物
/static/
```

理由：产物是可重现的派生物，入库会让每次前端改动产生几十个哈希文件名变化的二进制 diff，PR 无法审查，仓库体积持续膨胀。

三件配套动作：

**一次性删除现有 `static/` 下的所有文件并从 git 索引移除**（`git rm -r --cached static/`）。旧的 `index.html`、`daily.html`、`js/app.js`、`css/style.css`、`favicon.ico` 全部废弃，`favicon.ico` 之类需要保留的静态资源移到 `web/public/`。

**部署文档必须写明构建是必需步骤。** 克隆仓库后直接跑 uvicorn 会得到一个没有前端的服务（API 正常、访问 `/` 返回 404）。Docker 路径下多阶段构建自动处理了；裸机部署要在文档里明确写出 `cd web && pnpm install && pnpm build`。

**Docker 镜像作为分发产物。** 不入库产物的代价是「拿到源码不等于拿到可运行的应用」，用发布镜像补上 —— 镜像里已经含构建好的 `static/`。

### 14.4 CI 的可选做法

不是必需项，但如果加，最小有用的形态是一个 PR 检查：

```yaml
# 概念示意，非完整配置
- pnpm install --frozen-lockfile
- pnpm typecheck          # tsc --noEmit
- pnpm lint
- pnpm gen:api:check      # 校验 api.d.ts 与 openapi.json 一致（见 10 号文档 §6.1）
- pnpm build              # 构建必须能过
```

`pnpm gen:api:check` 是其中最有价值的一条：它会在「后端改了接口但没同步类型」时让 CI 变红，而不是等到运行时才发现。

镜像构建可以做，但对私有部署项目收益有限 —— 除非有多台机器要部署，否则本地 `docker build` 就够。

| Recruit | `times` | 公招次数 |
| Infrast | `facility` | 换班设施 |
| Infrast | `drones` | 无人机用途 |
| Infrast | `replenish` | 源石碎片是否自动补货 |
| Fight | `stage` | 关卡 |
| Fight | `medicine` | 最大理智药使用数量 |
| Fight | `expiring_medicine` | 48小时内过期理智药使用数量 |
| Fight | `series` | 连战次数 |
| Mall | `shopping` | 是否购物 |
| Mall | `buy_first` | 优先购买 |
| CloseDown | `client_type` | 客户端类型 |

`app.js` 里的 `createTasks` 是一套经过实际使用调过的默认值，比 MaaCore 的原始默认值更贴近国服日常玩法，应当作为新前端「日常」预设模板保留：

```jsonc
[
  { "name": "StartUp",  "client_type": "Bilibili", "start_game_enabled": true },
  { "name": "Recruit",  "refresh": true, "select": [1, 4, 5], "confirm": [2, 3, 4, 5], "times": 4 },
  { "name": "Infrast",  "facility": ["Mfg", "Trade", "Power", "Control", "Reception", "Office", "Dorm"],
                        "drones": "Money", "replenish": false },
  { "name": "Fight",    "stage": "CE-6", "medicine": 0, "expiring_medicine": 0, "series": 0 },
  { "name": "Mall",     "shopping": true, "buy_first": ["招聘许可", "龙门币"] },
  { "name": "Award" },
  { "name": "CloseDown","client_type": "Bilibili" }
]
```

其中两处细节值得保留：`Infrast.facility` 的顺序是「制造 → 贸易 → 发电 → 控制中枢 → 会客室 → 办公室 → 宿舍」，这个顺序有换班逻辑上的意义（先把产出设施排好再填宿舍），[§7.4](#74-复杂参数的具体处理) 的有序列表控件必须能表达它。`Recruit.select` 是 `[1, 4, 5]` 而 `confirm` 是 `[2, 3, 4, 5]`，两者刻意不同（选择 1 星 Tag 用于计算但不确认、确认 2-3 星用于跑量），不要以为是笔误而「修正」成一致。

这套预设作为「日常」模板存进定时任务模块的任务组合库，用户首次使用时预置，而不是硬编码在前端组件里。

### 15.4 按星期配置的任务组合

`static/daily.html` 的数据结构是本次迁移信息量最大的一块。它的形态是：

```jsonc
{
  "enable": true,                       // 定时任务总开关
  "task_dict": {                        // 命名的任务组合库
    "日常": [ /* task 对象数组 */ ],
    "剿灭": [ /* ... */ ],
    "周本": [ /* ... */ ]
  },
  "weekday_task": {                     // 星期 → 组合名
    "0": "日常",   // 周一
    "1": "日常",   // 周二
    "2": "剿灭",   // 周三
    "3": "日常",
    "4": "日常",
    "5": "周本",
    "6": "周本"    // 周日
  }
}
```

对应接口是 `GET/PUT /api/maa/daily` 与 `POST /api/maa/daily/execute`。

**注意索引约定：`"0"` 是周一，`"6"` 是周日**，这与 JavaScript `Date.getDay()`（0 = 周日）和 Python `datetime.weekday()`（0 = 周一）中的后者一致。迁移时若弄错这个偏移，所有人的定时任务会整体错一天，而且这种错误在测试里很难发现（要跨周才显形）。新的定时任务模块应当在数据库里用明确的字段名（`weekday` 且注明 1=周一 或直接存 cron 表达式）而不是延续这个魔法索引。

**「命名的任务组合库 + 星期到组合的映射」这个两层模型要保留。** 它比「每天独立配一套任务」好用得多 —— 改一次「日常」组合，五天的配置同时生效。新模块在此基础上扩展：

- 组合库与首页「快捷启动」的收藏共用同一张表，避免同一套配置维护两遍
- `weekday_task` 的单一映射升级为支持 cron 表达式（决策表要求「可视化配置执行时间」，旧实现只能按星期、执行时刻写在后端配置里不可改）
- 一天可以有多条定时（早上跑日常、晚上跑剿灭），旧模型每天只能一条
- 每条定时记录上次执行结果与下次触发时间，旧版本完全没有可观测性

迁移路径：写一个一次性脚本读 `config.yaml` 里的旧 `daily` 配置，把 `task_dict` 转成新的任务组合记录、`weekday_task` 转成 7 条（或按去重后的组合数）cron 定时记录。这个脚本属于 [04-数据模型与持久化](./04-数据模型与持久化.md) 的数据迁移范畴。

### 15.6 在核对 `task.py` 时发现的问题

逐个任务类型核对参数时发现以下几处，需要在重构后端 `domain/task.py` 时一并处理，这里记录以免遗漏：

**`InfrastTask` 的 `failename` 是 `filename` 的拼写错误。** 构造函数参数名写作 `failename`，但文档字符串里写的是 `filename`，MaaCore 期望的键名也是 `filename`。当前这个参数实际上完全不生效 —— 传进去的键是 `failename`，内核不认。自定义基建方案（`mode == 10000`）因此从未真正可用。

**`InfrastTask.threshold` 的默认值与文档不符。** 代码里是 `threshold: float = 0.5`，文档字符串写「默认 0.3」。**已确认以 0.3 为期望值**，签名里的 0.5 是错的。前端表单不硬编码这个值，而是把 0.3 作为占位提示文案展示（「留空则使用内核默认值 0.3」）—— 请求体里该字段为 `None` 时不传给内核，由内核用自己的默认值，理由见 [05 §7.2](./05-API规范与路由清单.md)。

**`ReclamationTask` 的 `params` 字典构造方式是错的。** 它写的是 `{enable: enable, theme: theme, ...}` —— 用**变量**作为 key 而不是字符串字面量。这会让字典的键变成参数值本身（`None` 或传入值），产出的 params 完全不可用。这是 `Reclamation` 任务从未被前端暴露、因此错误一直没被发现的直接后果。其 `theme` 的文档字符串也写着「默认为 1」，但取值是 `"Fire"` / `"Tales"` 字符串。

**`Roguelike.theme` 的可选值可能已过时。** `task.py` 列了 `Phantom` / `Mizuki` / `Sami` / `Sarkaz` 四个，但本地 MaaCore 是 v6.17.x，其间官方可能已新增主题。这类会随内核版本变化的枚举不该在 Python 里写死 —— 建议 `GET /api/tasks/types` 在返回 schema 时，对这类枚举从 MaaCore 资源目录的 `tasks.json` 动态派生，资源热更新后自动跟上。这也是把 schema 放后端生成（而非前端硬编码）的又一个理由。

**任务类型的数量口径需要统一。** `task.py` 里有 9 个 `Task` 子类，本方案按 9 种覆盖。若「8 种」的口径来自排除 `Reclamation`（因其实现有上述缺陷），需要明确是修好它还是正式不支持 —— 这影响前端是否要为它生成表单。
