## 先问清需求
- 「必出六星」：只有本轮标签里出现【高级资深干员】才可能，任务本身变不出这个标签。先按 screen-recruit 看一眼标签，再回答能不能。
- 「必出五星」：需要【资深干员】或【高级资深干员】标签。
- 「日常刷公招」：用默认参数即可。
- 「用加急许可马上拿人」：expedite 属消耗类参数，提交会触发人工确认，必须先讲清并拿到同意。
- 只想看看有哪些标签：把 times 设为 0，内核只进公招页而不执行招募，可以当侦查用。

## 提交前的检查
1. 有流水线在跑、设备未连接、不支持视觉输入时按同一套处理：先说明在跑什么再用 ask_user 发卡问是等还是稍后；征得同意后 reconnect_device；读不了标签和结算画面就先说明限制再问用户怎么办。
2. 用 list_task_types 核对 Recruit 的字段与默认值——下面的说明可能落后于实现，以 schema 为准。

## Recruit 的关键参数
- `times` 招募次数，本服务默认 0。0 表示主循环不执行、只进公招页；**要真正招募必须显式给正数**。
- `select` / `confirm` 内核用自己的一套「Tag 等级」（1~6）=指代标签，分别是「会去点击」和「会去确认」的等级集合，本服务默认 `select=[1,4,5]`、`confirm=[2,3,4,5]`（沿用旧前端的日常预设）。等级与具体标签的对应关系在 PRTS 上没有权威列表，**不要向用户断言某个标签是几级**；拿不准就把 1~6 都写进去，免得内核因为等级过滤漏点或漏确认。
- `recruitment_time` Tag 等级到希望招募时限（分钟）的映射，本服务默认把各档都设为时限上界。**不要为了赶时间改小**：资深/高级资深标签只有把时限拉满才开始招募时才不会被划掉，改小就失去必出 5★/6★ 的保证（见 recruit-tags）。
- `set_time` 是否把游戏内计时器点到 `recruitment_time` 对应值，默认 True，只在真正招募时有用。
- `expedite` 是否使用加急许可，默认 False，消耗类参数；`expedite_times` 自内核 v6.17.5 起已不再使用，不要填。
- `refresh` 是否刷新标签，默认 False；打开会消耗办公室攒下的联络次数，**恢复周期与持有上限不要凭记忆报**，见 `get_prts_page(title="罗德岛基建/办公室")`。
- `first_tags` / `extra_tags_mode` / `skip_robot` 只影响内核挑标签的偏好，按用户明确要求设置，没要求就保持默认。
- `report_to_penguin` / `report_to_yituliu` 及对应 id 按用户已有设置，不要自作主张打开。

## 提交流水线
1. submit_pipeline，tasks 里只放需要的那一个 `{"name": "Recruit", ...}`，不要塞 StartUp、Fight 等无关任务。
2. expedite=true 时会触发人工确认；先告诉用户这一步会消耗加急许可。
3. wait_pipeline 等终态，不要反复 get_pipeline 轮询。
4. 失败或被取消就说明原因并停下，不要改用 click 硬闯公招界面；用户坚持时才用原子操作，且第一次点击会弹出会话授权确认。
5. 无消耗类参数时 submit_pipeline 不需要确认，可以直接提交；真正需要确认的是加急许可和原子操作。

## 核对结果
1. get_screenshot 看公招界面，确认招募位状态与剩余时间。
2. 用户问「招到了什么」，从截图读结算弹窗/干员信息；读不清就如实说读不清，不要猜名字和稀有度。
3. 回答里写明本次招募次数、是否用了加急、截图时间。要报剩余招聘许可得自己截图在仓库对应分类里找——MAA 自带的仓库识别只有「养成材料」页签（见 screen-depot），招聘许可不在其中，看不清就让用户确认。
4. 不要向用户承诺「这次一定出六星」，只能说本轮标签里有没有【高级资深干员】。
5. 结束时调用 back_to_home，它是安全操作，不需要确认。
