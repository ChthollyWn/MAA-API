# 单卡执行提示词模板

用法：**开一个全新会话**，把下面整段复制进去，把 `<卡号>` 替换成目标卡号（如 `M4-02`）。
一个会话只做一张卡，做完即弃——这是保住质量的关键纪律，不要在同一个会话里连做多张。

你是 MAA-API 重构的执行 worker。只做下面这一张任务卡，做完即止。

仓库：`/Users/chtholly/Developer/WorkSpace/MAA-API`
分支：`refactor/v2`（已切好，不要切换、不要 push）

**第一步：读 `.refactor/tasks/<卡号>.json`**，里面有你需要的全部信息：

- `title` 标题
- `reads` 必读的文档锚点 —— **只读这些，不要通读 `docs/` 目录**
- `constraints` 硬约束（摘自 docs/13 决策记录），必须遵守
- `deliverables` 预期产出文件
- `verify` 验收命令，你必须逐条跑通
- `prompt_extra` 补充指令

**第二步：动手前先读 `.refactor/ENVIRONMENT.md`**（已实测的环境事实）。其中三条最容易踩：

- `python` 不在 PATH，只有 `python3`；内核相关用仓库内 `.venv/bin/python`
- `import maa_api.main` 会在 import 期触发内核加载与网络（约 2.5 分钟），**不能当门禁**
- FastAPI 0.141 下 `app.routes` 里 include 进来的是 `_IncludedRouter`、没有 `.path`，
  取路径要用 `set(app.openapi()['paths'])`

**第三步：若仓库里已有前序卡产出的实测产物**（`tests/fixtures/` 下的结论文档与样本、
`scripts/` 下的探针脚本），而它与本卡相关，**以实测结论为准 —— 实测优先于文档推测**。
文档里的推断可能已被前序卡证伪；照文档写会实现出错误行为。

## 执行纪律

1. **只做这张卡。** 不要顺手重构无关代码，不要提前实现后续卡的内容。
2. 产出后逐条运行 `verify` 命令，必须全部通过；失败就修到通过。
   若某条 verify 因 `AttributeError` / `TypeError` 这类**门禁自身写错**的原因失败
   （而不是业务原因），停下来说明情况，不要为了过门禁去改无关代码。
3. `git add` **只加你的 `deliverables`**（不要 `git add -A`），然后 commit，
   message 格式：`<卡号>: <标题>`。不要 push、不要切换分支、不要 amend 他人提交。
4. **不要修改 `.refactor/` 下的任何文件** —— 台账由人管理。只有三处例外：
   - 实测出可复用的环境事实或坑 → 追加到 `.refactor/ENVIRONMENT.md` 对应小节末尾
   - 发现**前序已完成卡**的产物有真实缺陷、而本卡范围外修不了 → 追加到 `.refactor/DEFECTS.md`：
     `- [ ] <里程碑>-<归属卡号> | <一句话缺陷> | 复现：<命令或用例名> | 发现于 <你的卡号>`
   - 本卡就是修复卡时，把 `DEFECTS.md` 里对应那条改成 `- [x]` 并补一句修法
   三处都只做上述最小改动，不要 `git add`（台账由人提交）。
5. 如果这张卡在当前代码基础上无法完成（前置条件不成立），**不要硬做、不要留半成品**：
   直接说明阻塞原因并正常退出。

最后输出 200 字以内回执：做了什么、验收结果、遗留问题。
